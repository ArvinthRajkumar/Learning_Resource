Analytics SQL: funnels, cohorts, retention, percentiles and time series

Analysts and data engineers spend their days turning event logs into answers. This part gives the standard patterns, each run on a small users and events dataset so you can see exactly what comes back.

The dataset

Funnels

A funnel counts how many users reach each step. Count distinct users, not events, and decide whether steps must happen in order.

SELECT
  COUNT(DISTINCT CASE WHEN event = 'visit'       THEN user_id END) AS visited,
  COUNT(DISTINCT CASE WHEN event = 'add_to_cart' THEN user_id END) AS added_to_cart,
  COUNT(DISTINCT CASE WHEN event = 'purchase'    THEN user_id END) AS purchased
FROM events;

Result

visitedadded_to_cartpurchased
14139

Turn counts into conversion rates between steps and from the top:

WITH f AS (
  SELECT COUNT(DISTINCT CASE WHEN event = 'visit'       THEN user_id END) AS v,
         COUNT(DISTINCT CASE WHEN event = 'add_to_cart' THEN user_id END) AS c,
         COUNT(DISTINCT CASE WHEN event = 'purchase'    THEN user_id END) AS p
  FROM events)
SELECT v, c, p,
       ROUND(100.0 * c / v, 1) AS visit_to_cart_pct,
       ROUND(100.0 * p / c, 1) AS cart_to_purchase_pct,
       ROUND(100.0 * p / v, 1) AS overall_pct
FROM f;

A strict ordered funnel requires each step to occur after the previous one for the same user:

WITH first_step AS (
  SELECT user_id, MIN(ts) AS t FROM events WHERE event = 'visit' GROUP BY user_id),
second AS (
  SELECT e.user_id, MIN(e.ts) AS t FROM events e JOIN first_step f ON f.user_id = e.user_id AND e.ts >= f.t
  WHERE e.event = 'add_to_cart' GROUP BY e.user_id),
third AS (
  SELECT e.user_id, MIN(e.ts) AS t FROM events e JOIN second s ON s.user_id = e.user_id AND e.ts >= s.t
  WHERE e.event = 'purchase' GROUP BY e.user_id)
SELECT (SELECT COUNT(*) FROM first_step) AS step1,
       (SELECT COUNT(*) FROM second) AS step2,
       (SELECT COUNT(*) FROM third) AS step3;

Funnels by segment: add GROUP BY plan after joining users.

SELECT u.plan,
       COUNT(DISTINCT u.id) AS users,
       COUNT(DISTINCT CASE WHEN e.event = 'purchase' THEN u.id END) AS buyers,
       ROUND(100.0 * COUNT(DISTINCT CASE WHEN e.event = 'purchase' THEN u.id END) / COUNT(DISTINCT u.id), 1) AS buyer_pct,
       COALESCE(SUM(e.amount), 0) AS revenue
FROM users u LEFT JOIN events e ON e.user_id = u.id
GROUP BY u.plan
ORDER BY revenue DESC;

Why count DISTINCT user_id in a funnel?

  • It is faster Not the reason.

Self-check

Ordered versus unordered funnel?

Ordered requires each step to occur after the previous one for the same user; unordered only checks that each step occurred.

Cohorts and retention

A cohort groups users by when they first did something (signup month). Retention asks how many of each cohort were active in month 0, 1, 2 after joining.

WITH activity AS (
  SELECT DISTINCT u.id AS user_id,
         substr(u.signup_date, 1, 7) AS cohort,
         (CAST(substr(e.ts, 1, 4) AS INT) - CAST(substr(u.signup_date, 1, 4) AS INT)) * 12
         + CAST(substr(e.ts, 6, 2) AS INT) - CAST(substr(u.signup_date, 6, 2) AS INT) AS month_n
  FROM users u JOIN events e ON e.user_id = u.id)
SELECT cohort,
       COUNT(DISTINCT CASE WHEN month_n = 0 THEN user_id END) AS m0,
       COUNT(DISTINCT CASE WHEN month_n = 1 THEN user_id END) AS m1,
       COUNT(DISTINCT CASE WHEN month_n = 2 THEN user_id END) AS m2
FROM activity
GROUP BY cohort
ORDER BY cohort;

Result

cohortm0m1m2
2024-01432
2024-02742
2024-03320

Read each row left to right: users active in the signup month, one month later, two months later. Divide by cohort size for percentages. Cohorts that are too recent have no later months yet (not churn, just missing time). Rolling retention (active on or after day N) and classic retention (active exactly on day N) answer different questions; state which you use.

Customer lifetime value per cohort is the same shape with SUM(amount):

SELECT substr(u.signup_date, 1, 7) AS cohort,
       COUNT(DISTINCT u.id) AS users,
       COALESCE(SUM(e.amount), 0) AS revenue,
       ROUND(1.0 * COALESCE(SUM(e.amount), 0) / COUNT(DISTINCT u.id), 1) AS revenue_per_user
FROM users u LEFT JOIN events e ON e.user_id = u.id AND e.event = 'purchase'
GROUP BY cohort
ORDER BY cohort;

How this gets asked

What is a cohort?

  • A random sample No.
  • A group of users defined by a shared starting point, such as signup month Correct.
  • A table No.
  • An index No.

Retention is measured per cohort.

Why do recent cohorts show no later months?

  • Users churned Not necessarily.
  • Not enough time has passed to observe those months Correct.
  • A bug No.
  • Wrong joins No.

Missing time is not churn.

Self-check

Classic versus rolling retention?

Classic counts users active exactly on day N; rolling counts users active on or after day N.

Sessionisation

A session is a run of events with gaps shorter than a threshold (say 30 minutes). Mark a new session where the gap from the previous event exceeds the threshold, then take a running sum of those marks. This is the gaps-and-islands trick from SQL2.

WITH t AS (
  SELECT user_id, started,
         LAG(ended) OVER (PARTITION BY user_id ORDER BY started) AS prev_end
  FROM sessions),
m AS (
  SELECT user_id, started,
         CASE WHEN prev_end IS NULL OR (julianday(started) - julianday(prev_end)) * 1440 > 30 THEN 1 ELSE 0 END AS new_session
  FROM t)
SELECT user_id, started,
       SUM(new_session) OVER (PARTITION BY user_id ORDER BY started) AS session_no
FROM m
ORDER BY user_id, started;

       ROUND(AVG(amount) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 1) AS moving_avg_3,
       amount - LAG(amount) OVER (ORDER BY day) AS change,
       ROUND(100.0 * (amount - LAG(amount) OVER (ORDER BY day)) / LAG(amount) OVER (ORDER BY day), 1) AS change_pct,

For year-over-year, join a series to itself shifted by a year (date(day, '-1 year')) or use LAG(x, 12) over monthly rows. Seasonality makes month-over-month noisy; compare like with like.

A date spine ensures days with no events still appear. Generate it with a recursive CTE and LEFT JOIN the data:

WITH RECURSIVE spine(day) AS (
  SELECT '2024-03-01' UNION ALL SELECT date(day, '+1 day') FROM spine WHERE day < '2024-03-10')
SELECT s.day, COALESCE(l.logins, 0) AS logins
FROM spine s
LEFT JOIN (SELECT day, COUNT(*) AS logins FROM logins GROUP BY day) l ON l.day = s.day
ORDER BY s.day;

Percentiles, medians and distributions

PostgreSQL has percentile_cont; SQLite and MySQL do not, so use window functions: rank rows and pick the position.

WITH r AS (
  SELECT amount,
         ROW_NUMBER() OVER (ORDER BY amount) AS rn,
         COUNT(*) OVER () AS n
  FROM events WHERE event = 'purchase')
SELECT
  MIN(CASE WHEN rn >= 0.5 * n THEN amount END) AS p50,
  MIN(CASE WHEN rn >= 0.9 * n THEN amount END) AS p90,
  MIN(amount) AS min_amount, MAX(amount) AS max_amount, ROUND(AVG(amount), 1) AS mean
FROM r;

Result

p50p90min_amountmax_amountmean
501202012056.5

Use NTILE(4) to bucket into quartiles and a CASE to build histograms:

SELECT CASE WHEN amount < 40 THEN '1: under 40'
            WHEN amount < 90 THEN '2: 40 to 89'
            ELSE '3: 90 and over' END AS bucket,
       COUNT(*) AS purchases, SUM(amount) AS revenue
FROM events WHERE event = 'purchase'
GROUP BY bucket
ORDER BY bucket;

Segmentation: RFM and Pareto

RFM scores customers by Recency, Frequency and Monetary value.

WITH rfm AS (
  SELECT user_id,
         CAST(julianday('2024-05-01') - julianday(MAX(ts)) AS INT) AS recency_days,
         COUNT(*) AS frequency,
         SUM(amount) AS monetary
  FROM events WHERE event = 'purchase'
  GROUP BY user_id)
SELECT user_id, recency_days, frequency, monetary,
       NTILE(3) OVER (ORDER BY recency_days DESC) AS r_score,
       NTILE(3) OVER (ORDER BY frequency) AS f_score,
       NTILE(3) OVER (ORDER BY monetary) AS m_score
FROM rfm
ORDER BY monetary DESC;

A/B test summaries

SQL prepares the counts; a statistical test judges them. Assign users to variants, compute conversions and rates per variant, then test the difference in Python.

WITH assigned AS (
  SELECT id AS user_id, CASE WHEN id % 2 = 0 THEN 'control' ELSE 'variant' END AS grp FROM users),
conv AS (
  SELECT user_id, MAX(event = 'purchase') AS bought FROM events GROUP BY user_id)
SELECT a.grp, COUNT(*) AS users, SUM(COALESCE(c.bought, 0)) AS buyers,
       ROUND(100.0 * SUM(COALESCE(c.bought, 0)) / COUNT(*), 1) AS conversion_pct
FROM assigned a LEFT JOIN conv c ON c.user_id = a.user_id
GROUP BY a.grp;

Result

grpusersbuyersconversion_pct
control7571.4
variant7457.1

Check for sample ratio mismatch (groups far from the intended split), define the metric before the test, avoid peeking repeatedly, and compute significance and power with a statistics library. With small samples like these, differences are noise; the point here is the query shape.

How this gets asked

What is sample ratio mismatch?

  • A rounding error No.
  • Observed group sizes differ from the intended split, signalling an assignment or logging problem Correct.
  • A p-value No.
  • A join type No.

Check it before trusting the results.

Key idea

Define the population, count distinct users, aggregate before joining, use a date spine for gaps, state the retention and percentile definitions you choose, and sanity-check totals against a simple query. Most analytics errors are join fan-out and wrong denominators.

Interview questions: Analytics SQL

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic How do you compute a conversion rate in SQL?

Count distinct users at each step with conditional aggregation and divide, using a decimal literal to avoid integer division.

Basic Why COUNT(DISTINCT user_id) in a funnel?

A user can generate many events at a step but should count once.

Medium How do you compute cohort retention?

Assign each user a cohort (signup period), compute the activity period offset from it, count distinct active users per cohort and offset, and divide by cohort size.

Medium How do you compute a running total and a moving average?

SUM(x) OVER (ORDER BY day) and AVG(x) OVER (ORDER BY day ROWS BETWEEN n PRECEDING AND CURRENT ROW).

Medium How do you sessionise events?

Compute the gap from the previous event per user with LAG, flag gaps over a threshold, then take a running SUM of the flags to number sessions.

Medium How do you fill missing dates in a time series?

Generate a date spine with a recursive CTE or calendar table and LEFT JOIN the data, using COALESCE for zeros.

Medium How do you compute a median without a MEDIAN function?

Number rows with ROW_NUMBER and count with COUNT OVER, then average the one or two middle rows.

Medium What is join fan-out and how do you avoid it?

Joining two one-to-many tables multiplies rows and inflates sums. Aggregate each table to the join grain first, or use subqueries or CTEs.

Advanced Why is averaging averages wrong?

Groups with different sizes carry different weight. Sum the numerators and denominators across groups, then divide.

Advanced What is RFM analysis?

Segmenting customers by recency of last purchase, frequency of purchases and monetary value, often with NTILE scores.

Advanced How do you compute year-over-year growth?

Join or window each period to the same period a year earlier (LAG 12 for monthly data) and divide the difference by the earlier value, handling zero or missing prior values.

Advanced What is sample ratio mismatch in an A/B test?

Observed group sizes deviating from the planned split, indicating assignment or logging bugs that invalidate the result.

Advanced How do you handle time zones in daily metrics?

Convert timestamps to the business time zone before truncating to a date, and define the day boundary once in a shared view or model.

Advanced How would you design an events table for analytics?

Append-only rows with user_id, event name, timestamp (UTC), properties as columns or JSON, partitioned by date and clustered by user, plus a deduplication key.
