Schema design workshop: four worked designs with constraints and queries

Design questions are asked in almost every backend and data interview, and they are won by method, not memory. Each workshop here follows the same routine: list the questions the schema must answer, find the entities and relationships, add constraints, then test the design with real queries.

MediumAdvanced~5 hours

The design routine

  1. Requirements to queries: write the 5 to 10 questions the system must answer and the writes it must perform.
  2. Entities and relationships: nouns become tables; decide one-to-many (foreign key on the many side), many-to-many (a junction table) and one-to-one (shared key).
  3. Keys: a surrogate primary key per table, natural keys as UNIQUE.
  4. Types and constraints: NOT NULL, CHECK, UNIQUE, FOREIGN KEY. Constraints are the schema's way of making invalid states impossible.
  5. Normalise to remove redundancy (SQL3), then denormalise deliberately only for measured needs.
  6. Indexes for the foreign keys and the filters in your queries.
  7. Test with sample data and the planned queries, including the failure cases.

SQLite does not enforce foreign keys unless PRAGMA foreign_keys = ON (each connection); the snippets switch it on.

How this gets asked

What should schema design start from?

  • A diagram of every possible table No.
  • The questions the system must answer and the writes it must perform Correct.
  • The ORM No.
  • The index list No.

Queries and access patterns drive the model.

Self-check

Give the seven design steps.

Questions, entities, keys, types and constraints, normalise, indexes, then test with data and queries.

Workshop 1: a library

Needs: members borrow copies of books; a book can have several authors; a copy is on loan to at most one member at a time; track due dates and fines. Queries: who has overdue books; which books are available; which authors are most borrowed.

Entities: book (the work), copy (a physical item of a book), author, book_author (many-to-many), member, loan (a copy borrowed by a member).

PRAGMA foreign_keys = ON;
CREATE TABLE author (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE book (id INTEGER PRIMARY KEY, isbn TEXT NOT NULL UNIQUE, title TEXT NOT NULL, year INT CHECK (year BETWEEN 1400 AND 2100));
CREATE TABLE book_author (book_id INT NOT NULL REFERENCES book(id), author_id INT NOT NULL REFERENCES author(id), PRIMARY KEY (book_id, author_id));
CREATE TABLE copy (id INTEGER PRIMARY KEY, book_id INT NOT NULL REFERENCES book(id), barcode TEXT NOT NULL UNIQUE);
CREATE TABLE member (id INTEGER PRIMARY KEY, name TEXT NOT NULL, email TEXT NOT NULL UNIQUE);
CREATE TABLE loan (
  id INTEGER PRIMARY KEY, copy_id INT NOT NULL REFERENCES copy(id), member_id INT NOT NULL REFERENCES member(id),
  borrowed_on TEXT NOT NULL, due_on TEXT NOT NULL, returned_on TEXT,
  CHECK (due_on > borrowed_on), CHECK (returned_on IS NULL OR returned_on >= borrowed_on));
-- a copy can have at most one open (unreturned) loan: a partial unique index enforces it
CREATE UNIQUE INDEX one_open_loan_per_copy ON loan(copy_id) WHERE returned_on IS NULL;
CREATE INDEX idx_loan_member ON loan(member_id);

INSERT INTO copy VALUES (1,1,'B-1'),(2,2,'B-2'),(3,2,'B-3'),(4,3,'B-4');

SELECT m.name, b.title, l.due_on FROM loan l JOIN member m ON m.id = l.member_id JOIN copy c ON c.id = l.copy_id JOIN book b ON b.id = c.book_id
WHERE l.returned_on IS NULL AND l.due_on < '2024-03-20' ORDER BY l.due_on;

Overdue loans: open (no return date) and past due on the reference date. Next, availability: copies with no open loan, and a check that the constraint blocks a double loan.

PRAGMA foreign_keys = ON;
CREATE TABLE copy (id INTEGER PRIMARY KEY, book_id INT NOT NULL, barcode TEXT NOT NULL UNIQUE);
CREATE TABLE loan (id INTEGER PRIMARY KEY, copy_id INT NOT NULL REFERENCES copy(id), member_id INT NOT NULL, borrowed_on TEXT NOT NULL, due_on TEXT NOT NULL, returned_on TEXT);
CREATE UNIQUE INDEX one_open_loan_per_copy ON loan(copy_id) WHERE returned_on IS NULL;
INSERT INTO copy VALUES (1,1,'B-1'),(2,2,'B-2'),(3,2,'B-3');
INSERT INTO loan VALUES (1,1,1,'2024-03-01','2024-03-15',NULL),(2,2,1,'2024-03-05','2024-03-19','2024-03-12');
INSERT INTO loan VALUES (3,1,2,'2024-03-16','2024-03-30',NULL);

The third insert fails: copy 1 already has an open loan, and the database says so without any application code. Availability query:

CREATE TABLE copy (id INTEGER PRIMARY KEY, book_id INT, barcode TEXT);
CREATE TABLE loan (id INTEGER PRIMARY KEY, copy_id INT, returned_on TEXT);
INSERT INTO copy VALUES (1,1,'B-1'),(2,2,'B-2'),(3,2,'B-3');
INSERT INTO loan VALUES (1,1,NULL),(2,2,'2024-03-12');
SELECT c.book_id, COUNT(*) AS available_copies
FROM copy c WHERE NOT EXISTS (SELECT 1 FROM loan l WHERE l.copy_id = c.id AND l.returned_on IS NULL)
GROUP BY c.book_id ORDER BY c.book_id;

Design notes: separating book from copy avoids repeating the title for every physical item; book_author handles many authors per book; fines are derived (due date, return date, daily rate), so compute them in queries or a view instead of storing a number that can disagree with the dates.

How this gets asked

How do you guarantee a copy has at most one open loan?

  • Application code only Can race.
  • A partial unique index on copy_id WHERE returned_on IS NULL Correct.
  • A nullable column No.
  • A view No.

The database enforces it for every writer.

Why store a fine as a derived value instead of a column?

  • Columns are slow No.
  • A stored number can disagree with the dates it derives from Correct.
  • SQL cannot store money No.
  • Indexes forbid it No.

Compute from due and return dates.

Self-check

How do you model many authors per book?

A book_author junction table with a composite primary key of book id and author id.

Workshop 2: bookings without overlaps

Needs: rooms can be booked for date ranges; two bookings for the same room must never overlap. This is the classic "double booking" problem.

Two ranges [s1, e1) and [s2, e2) overlap exactly when s1 < e2 AND s2 < e1. Use half-open intervals (check-out day is free for the next guest). The strongest guarantee comes from the database: PostgreSQL has exclusion constraints on daterange. SQLite and MySQL have no such constraint, so use a trigger (and serialised writes or locking) as below.

CREATE TABLE room (id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE);
CREATE TABLE booking (id INTEGER PRIMARY KEY, room_id INT NOT NULL REFERENCES room(id), guest TEXT NOT NULL,
                      start_day TEXT NOT NULL, end_day TEXT NOT NULL, CHECK (end_day > start_day));
CREATE INDEX idx_booking_room_dates ON booking(room_id, start_day, end_day);
CREATE TRIGGER no_overlap BEFORE INSERT ON booking
BEGIN
  SELECT RAISE(ABORT, 'room already booked for those dates')
  WHERE EXISTS (SELECT 1 FROM booking b WHERE b.room_id = NEW.room_id AND b.start_day < NEW.end_day AND NEW.start_day < b.end_day);
END;
INSERT INTO room VALUES (1,'Sea view'),(2,'Garden');
INSERT INTO booking VALUES (1,1,'Ana','2024-05-01','2024-05-05'),(2,1,'Bo','2024-05-05','2024-05-08'),(3,2,'Cy','2024-05-02','2024-05-04');
INSERT INTO booking VALUES (4,1,'Di','2024-05-04','2024-05-06');

Result

error
room already booked for those dates

Booking 2 starts the day booking 1 ends (allowed), and the fourth booking overlaps the first, so the trigger aborts it. In production (PostgreSQL):

CREATE EXTENSION btree_gist;
ALTER TABLE booking ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (room_id WITH =, daterange(start_day, end_day) WITH &&);

Finding free rooms for a date range is an anti-join:

CREATE TABLE room (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE booking (id INTEGER PRIMARY KEY, room_id INT, start_day TEXT, end_day TEXT);
INSERT INTO room VALUES (1,'Sea view'),(2,'Garden'),(3,'Attic');
INSERT INTO booking VALUES (1,1,'2024-05-01','2024-05-05'),(2,2,'2024-05-02','2024-05-04'),(3,3,'2024-04-20','2024-04-25');
SELECT r.name AS free_room FROM room r
WHERE NOT EXISTS (SELECT 1 FROM booking b WHERE b.room_id = r.id AND b.start_day < '2024-05-04' AND '2024-05-03' < b.end_day)
ORDER BY r.name;

free_room
Attic

Concurrency: two requests can both pass the check before either inserts. Prevent it with the exclusion constraint, a serialisable transaction with retry, a row lock on the room (SELECT ... FOR UPDATE) or a per-room unique "slot" table (one row per room per night with a unique key), which turns overlap detection into a unique-violation (SD24, SQL8).

How this gets asked

Two half-open ranges [s1,e1) and [s2,e2) overlap when:

  • s1 = s2 Too narrow.
  • s1 < e2 AND s2 < e1 Correct.
  • e1 = e2 No.
  • s1 < s2 No.

Back-to-back bookings (e1 = s2) do not overlap.

Which prevents double booking even under concurrent requests in PostgreSQL?

  • An application check Racy.
  • An exclusion constraint on room and date range Correct.
  • A longer timeout No.
  • A cache No.

The constraint is checked atomically inside the database.

Self-check

Why use half-open intervals for bookings?

A guest's check-out day can be the next guest's check-in day without counting as an overlap.

Workshop 3: a social graph

Needs: users follow users; posts; a feed of posts from followed users; follower counts; mutual follows. Queries: who follows me; who do I follow; mutual follows; my feed, newest first.

PRAGMA foreign_keys = ON;
CREATE TABLE user (id INTEGER PRIMARY KEY, handle TEXT NOT NULL UNIQUE);
CREATE TABLE follow (follower_id INT NOT NULL REFERENCES user(id), followee_id INT NOT NULL REFERENCES user(id), since TEXT NOT NULL,
                     PRIMARY KEY (follower_id, followee_id), CHECK (follower_id <> followee_id));
CREATE INDEX idx_follow_followee ON follow(followee_id, follower_id);   -- the reverse lookup: who follows X
CREATE TABLE post (id INTEGER PRIMARY KEY, author_id INT NOT NULL REFERENCES user(id), body TEXT NOT NULL, created TEXT NOT NULL);
CREATE INDEX idx_post_author_created ON post(author_id, created DESC);
INSERT INTO user VALUES (1,'ana'),(2,'bo'),(3,'cy'),(4,'di');
INSERT INTO follow VALUES (1,2,'2024-01-01'),(1,3,'2024-01-02'),(2,1,'2024-01-03'),(3,1,'2024-01-04'),(4,1,'2024-01-05'),(2,3,'2024-01-06');
INSERT INTO post VALUES (1,2,'bo post 1','2024-03-01'),(2,3,'cy post 1','2024-03-02'),(3,2,'bo post 2','2024-03-03'),(4,4,'di post','2024-03-04'),(5,1,'ana post','2024-03-05');
-- feed for ana: posts by people ana follows, newest first
SELECT u.handle, p.body, p.created FROM post p JOIN follow f ON f.followee_id = p.author_id JOIN user u ON u.id = p.author_id
WHERE f.follower_id = 1 ORDER BY p.created DESC LIMIT 10;

Mutual follows (friends) and follower counts:

CREATE TABLE user (id INTEGER PRIMARY KEY, handle TEXT);
CREATE TABLE follow (follower_id INT, followee_id INT, PRIMARY KEY (follower_id, followee_id));
INSERT INTO user VALUES (1,'ana'),(2,'bo'),(3,'cy'),(4,'di');
INSERT INTO follow VALUES (1,2),(1,3),(2,1),(3,1),(4,1),(2,3);
SELECT a.handle AS person, b.handle AS mutual_friend
FROM follow f1 JOIN follow f2 ON f2.follower_id = f1.followee_id AND f2.followee_id = f1.follower_id
JOIN user a ON a.id = f1.follower_id JOIN user b ON b.id = f1.followee_id WHERE f1.follower_id < f1.followee_id ORDER BY 1, 2;
SELECT u.handle, (SELECT COUNT(*) FROM follow f WHERE f.followee_id = u.id) AS followers, (SELECT COUNT(*) FROM follow f WHERE f.follower_id = u.id) AS following FROM user u ORDER BY followers DESC, u.handle;

Scaling notes: the follow table is an edge list; both lookup directions need an index. Computing a feed with a join works for small graphs; at scale, precompute feeds (fan-out on write) for ordinary users and merge celebrity posts at read time (SD14). Follower counts become denormalised counters updated asynchronously. For deep graph traversals (friends of friends of friends) consider a graph database or a recursive CTE with limits.

How this gets asked

A follow table needs which indexes?

  • None Slow.
  • The primary key (follower, followee) plus an index for the reverse direction (followee, follower) Correct.
  • Only on handle No.
  • A full-text index No.

Both 'who do I follow' and 'who follows me' are common.

Self-check

Precompute feeds for ordinary users (fan-out on write) and merge celebrity posts at read time.

Workshop 4: an inventory ledger

Needs: track stock across warehouses; never lose track of why stock changed; prevent negative stock; produce the current level and the history. Principle: store movements (an append-only ledger), derive balances. Updating a "quantity" column in place loses history and invites errors.

PRAGMA foreign_keys = ON;
CREATE TABLE product (id INTEGER PRIMARY KEY, sku TEXT NOT NULL UNIQUE);
CREATE TABLE warehouse (id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE);
CREATE TABLE stock_movement (
  id INTEGER PRIMARY KEY, product_id INT NOT NULL REFERENCES product(id), warehouse_id INT NOT NULL REFERENCES warehouse(id),
  delta INT NOT NULL CHECK (delta <> 0), reason TEXT NOT NULL CHECK (reason IN ('receipt','sale','return','adjustment','transfer')),
  ref TEXT, created TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP);
CREATE INDEX idx_move_prod_wh ON stock_movement(product_id, warehouse_id);
-- derived balance as a view
CREATE VIEW stock_level AS SELECT product_id, warehouse_id, SUM(delta) AS on_hand FROM stock_movement GROUP BY product_id, warehouse_id;
-- guard: a movement may not take stock below zero
CREATE TRIGGER no_negative_stock BEFORE INSERT ON stock_movement
BEGIN
  SELECT RAISE(ABORT, 'insufficient stock')
  WHERE (SELECT COALESCE(SUM(delta), 0) FROM stock_movement WHERE product_id = NEW.product_id AND warehouse_id = NEW.warehouse_id) + NEW.delta < 0;
END;
INSERT INTO product VALUES (1,'PEN'),(2,'DESK');
INSERT INTO warehouse VALUES (1,'North'),(2,'South');
INSERT INTO stock_movement (product_id, warehouse_id, delta, reason, ref) VALUES (1,1,100,'receipt','PO-1'),(1,1,-30,'sale','ORD-9'),(1,2,50,'receipt','PO-2'),(2,1,5,'receipt','PO-3'),(1,1,-20,'sale','ORD-10');
SELECT p.sku, w.name AS warehouse, s.on_hand FROM stock_level s JOIN product p ON p.id = s.product_id JOIN warehouse w ON w.id = s.warehouse_id ORDER BY p.sku, w.name;

Attempting to sell more than is on hand is rejected:

CREATE TABLE stock_movement (id INTEGER PRIMARY KEY, product_id INT, warehouse_id INT, delta INT);
CREATE TRIGGER no_negative_stock BEFORE INSERT ON stock_movement
BEGIN
  SELECT RAISE(ABORT, 'insufficient stock')
  WHERE (SELECT COALESCE(SUM(delta), 0) FROM stock_movement WHERE product_id = NEW.product_id AND warehouse_id = NEW.warehouse_id) + NEW.delta < 0;
END;

Design notes: the ledger is auditable and supports time travel (WHERE created <= ?); summing a long ledger on every read is slow, so keep a balance table updated in the same transaction (or a snapshot plus recent movements) and reconcile it against the ledger regularly; a transfer is two movements (out of one warehouse, into another) in one transaction; reservations (stock held for a cart) are a separate table with expiry (SD24). Accounting systems use exactly this double-entry idea.

How this gets asked

Why store stock movements instead of updating a quantity?

  • It uses less space No.
  • It keeps a full audit trail and lets balances be derived and reconciled Correct.
  • It is required by SQL No.
  • It avoids transactions No.

Double-entry accounting uses the same idea.

Self-check

How do you keep a ledger fast?

Maintain a balance or snapshot table in the same transaction and reconcile it against the ledger.

Common design mistakes

MistakeBetter
Comma-separated lists in a columnA junction table
One generic attributes EAV table for everythingReal columns, or JSONB for truly variable extras
Storing derived values (totals, ages) that can driftCompute them, or maintain them transactionally
Missing foreign keys "for speed"Keep them; index them; the integrity is worth it
Nullable columns that mean different thingsSeparate tables or explicit status columns
Using floats for moneyNUMERIC or integer minor units
Natural keys that change (email as primary key)Surrogate key plus a unique constraint
Soft deletes everywhere with unique conflictsPartial unique indexes on WHERE deleted_at IS NULL
Time without time zoneStore UTC timestamps
No created_at/updated_atAdd audit columns by default
Key idea

Start from the queries, model entities and relationships, let constraints make bad states impossible (partial unique indexes, checks, triggers or exclusion constraints), store events or movements and derive balances, and index both directions of a relationship.

How this gets asked

Which is a design smell?

  • A junction table for many-to-many Correct design.
  • A comma-separated list of ids in one column Correct: violates first normal form and cannot be indexed or constrained.
  • Foreign keys Good.
  • UTC timestamps Good.

Use a child or junction table.

Interview questions: Schema design workshop

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic How do you start designing a schema?

List the queries and writes the system must support, identify entities and relationships, choose keys and constraints, normalise, then add indexes and test with data.

Basic How do you model many-to-many relationships?

A junction table whose composite primary key combines the two foreign keys, with indexes for both directions.

Medium How do you prevent two open loans of one book copy?

A partial unique index on copy_id where returned_on IS NULL.

Medium When do two date ranges overlap?

For half-open ranges, when start1 < end2 and start2 < end1.

Medium How do you stop double bookings in PostgreSQL?

An exclusion constraint on the resource and the date range (gist with the && operator), enforced atomically by the database.

Medium Why store movements in a ledger rather than a quantity?

It gives an audit trail, supports time travel and lets balances be derived and reconciled.

Medium Why derive values such as fines or totals instead of storing them?

Stored derived values can disagree with their sources; compute them or maintain them transactionally.

Medium How do you model followers in a social network?

An edge table (follower, followee) with a composite primary key and an index on the reverse direction, plus counters denormalised if needed.

Advanced How does feed design change at scale?

Compute feeds on write for ordinary users and merge celebrity posts at read time, using denormalised stores and caches.

Advanced How would you implement soft delete safely?

Add deleted_at, filter it in views or default scopes, use partial unique indexes where deleted_at IS NULL, and purge or anonymise on a schedule.

Advanced How do you model versioned or historical data?

History tables or temporal columns with valid_from and valid_to, or an event log from which state is derived.

Advanced EAV versus JSON columns versus real columns?

Use real columns for core attributes; JSONB for genuinely variable extras with indexes; avoid EAV, which loses types, constraints and query simplicity.

Advanced How do you design for multi-tenancy in the schema?

A tenant_id in every table and index, row-level security, unique constraints scoped by tenant, or separate schemas or databases for stronger isolation.

Advanced How do you migrate a live schema safely?

Expand and contract: add compatible structure, dual write, backfill in batches, switch reads, then remove the old structure.
