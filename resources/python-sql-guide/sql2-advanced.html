Advanced SQL: CTEs, window functions, recursion and upserts

These features turn multi-step reports and hard interview questions into short, readable queries. Window functions in particular are the single biggest step up in SQL skill.

MediumAdvanced~5 hours

Common table expressions (CTEs)

Intuition

A CTE is a named temporary result, defined with WITH, that later parts of the query can use. It lets you write a query as a sequence of readable steps instead of nesting subqueries.

WITH paid_totals AS (
    SELECT o.customer_id, SUM(i.qty * p.price) AS spent
    FROM orders o
    JOIN order_items i ON i.order_id = o.id
    JOIN products p    ON p.id = i.product_id
    WHERE o.status = 'paid'
    GROUP BY o.customer_id
),
averages AS (
    SELECT AVG(spent) AS avg_spent FROM paid_totals
)
SELECT c.name, t.spent
FROM paid_totals t
JOIN customers c ON c.id = t.customer_id
CROSS JOIN averages a
WHERE t.spent > a.avg_spent
ORDER BY t.spent DESC;

Result

namespent
Ben2000.0
Ada1590.0
Dev950.0

Benefits: readability, reuse of a step several times, easy debugging (run each CTE alone). Many engines inline CTEs like views; some (older PostgreSQL) materialise them, which can affect performance. Name CTEs for what they contain.

How this gets asked

What is the main benefit of a CTE?

  • It always makes the query faster Not guaranteed.
  • It names an intermediate result so the query reads as clear steps Correct.
  • It stores data permanently Temporary only.
  • It replaces indexes No.

CTEs improve readability and allow reuse of a step.

Window functions

The big idea

An aggregate with GROUP BY collapses rows. A window function computes over a set of related rows without collapsing: every row stays, and gains a new column.

SELECT name, dept_id, salary,
       AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg,
       salary - AVG(salary) OVER (PARTITION BY dept_id) AS vs_avg
FROM employees
WHERE dept_id IS NOT NULL
ORDER BY dept_id, salary DESC;

Syntax: function(...) OVER (PARTITION BY ... ORDER BY ... frame).

  • PARTITION BY: split rows into independent groups (like GROUP BY, but rows remain).
  • ORDER BY: the order inside each partition.
  • Frame: which rows around the current one to include.

Ranking functions

SELECT name, dept_id, salary,
       ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS row_num,
       RANK()       OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk,
       DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS dense_rnk,
       NTILE(2)     OVER (PARTITION BY dept_id ORDER BY salary DESC) AS half
FROM employees
WHERE dept_id IN (1, 3)
ORDER BY dept_id, salary DESC, name;

Top N per group

Window functions cannot be filtered in WHERE (they run after it), so wrap them.

SELECT dept_id, name, salary
FROM (
    SELECT dept_id, name, salary,
           DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS r
    FROM employees WHERE dept_id IS NOT NULL
) t
WHERE r <= 2
ORDER BY dept_id, salary DESC, name;

Running totals, moving averages and frames

SELECT day, amount,
       SUM(amount) OVER (ORDER BY day) AS running_total,
       ROUND(AVG(amount) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 1) AS moving_avg_3,
       amount - LAG(amount) OVER (ORDER BY day) AS change_vs_prev,
       LEAD(amount) OVER (ORDER BY day) AS next_day
FROM daily_sales
ORDER BY day;

How this gets asked

How does a window function differ from GROUP BY aggregation?

  • It cannot compute averages It can.
  • It keeps every row and adds a computed column Correct.
  • It needs a join No.
  • It only works on dates No.

OVER (...) computes across related rows without collapsing them.

Salaries 100, 100, 90 ordered descending. What are RANK and DENSE_RANK of 90?

  • 2 and 2 RANK leaves a gap.
  • 3 and 2 Correct.
  • 2 and 3 No.
  • 3 and 3 No.

RANK gives 1,1,3; DENSE_RANK gives 1,1,2.

Why do you wrap a window function in a subquery to filter on it?

  • Syntax requirement for JOIN No.
  • Window functions are evaluated after WHERE, so WHERE cannot see them Correct.
  • They are slow in WHERE Not the reason.
  • They are not supported in WHERE by choice of vendor It follows from evaluation order.

Compute in an inner query or CTE, then filter in the outer one.

Self-check

Write the window function syntax.

function() OVER (PARTITION BY ... ORDER BY ... frame).

How do you get top N per group?

Rank with ROW_NUMBER or DENSE_RANK partitioned by group in a subquery or CTE, then filter rank <= N.

Recursive CTEs

Hierarchies and sequences

A recursive CTE has an anchor (starting rows) and a recursive part that joins back to the CTE itself, repeating until no new rows appear. Use it for trees (org charts, categories), graphs (paths) and generated sequences.

WITH RECURSIVE org AS (
    SELECT id, name, manager_id, 0 AS depth, name AS path
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, o.depth + 1, o.path || ' > ' || e.name
    FROM employees e
    JOIN org o ON e.manager_id = o.id
)
SELECT depth, path FROM org ORDER BY path;

Generating a calendar

WITH RECURSIVE days(d) AS (
    SELECT '2024-03-01'
    UNION ALL
    SELECT date(d, '+1 day') FROM days WHERE d < '2024-03-09'
)
SELECT d, COALESCE(s.amount, 0) AS amount
FROM days
LEFT JOIN daily_sales s ON s.day = d
ORDER BY d;

Guard against infinite loops

A recursive part that never runs out of rows loops forever. Include a terminating condition (as above) or a depth limit. PostgreSQL and others support CYCLE detection or you can track visited ids.

How this gets asked

What are the two parts of a recursive CTE?

  • Select and delete No.
  • An anchor query and a recursive query joined with UNION ALL Correct.
  • A view and a trigger No.
  • Two joins No.

The anchor seeds rows; the recursive part generates more until none are produced.

Self-check

When use a recursive CTE?

For hierarchies, graph paths and generated sequences; always include a stopping condition.

Gaps and islands

The problem

Given a sorted series with missing values, find consecutive runs ("islands"). For example, consecutive login days.

The row-number trick

For consecutive days, day - row_number is constant inside an island. Group on that.

WITH numbered AS (
    SELECT user_id, day,
           julianday(day) - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY day) AS grp
    FROM logins
)
SELECT user_id, MIN(day) AS streak_start, MAX(day) AS streak_end, COUNT(*) AS days
FROM numbered
GROUP BY user_id, grp
ORDER BY user_id, streak_start;

Result

Finding the longest streak per user is then one more aggregation or a ranking over this result. Another approach: LAG to mark where a new streak starts, then a running sum of those flags.

A break in the dates changes the difference and starts a new group.

Pivoting and JSON

Pivot with conditional aggregation

SELECT strftime('%Y-%m', order_date) AS month,
       SUM(CASE WHEN status = 'paid' THEN 1 ELSE 0 END) AS paid,
       SUM(CASE WHEN status = 'pending' THEN 1 ELSE 0 END) AS pending,
       SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) AS cancelled
FROM orders
GROUP BY month
ORDER BY month;

JSON in SQL

Modern databases store and query JSON (JSONB in PostgreSQL, JSON in MySQL, SQLite JSON functions).

CREATE TABLE events (id INTEGER PRIMARY KEY, payload TEXT);
INSERT INTO events VALUES
 (1, '{"type":"click","user":{"id":7,"plan":"pro"},"tags":["a","b"]}'),
 (2, '{"type":"view","user":{"id":9,"plan":"free"},"tags":[]}');
SELECT id,
       json_extract(payload, '$.type') AS type,
       json_extract(payload, '$.user.plan') AS plan,
       json_array_length(payload, '$.tags') AS n_tags
FROM events
WHERE json_extract(payload, '$.user.id') = 7;

Result

idtypeplann_tags
1clickpro2

PostgreSQL syntax: payload->'user'->>'plan', payload @> '{"type":"click"}', with GIN indexes for fast containment queries. Use JSON for genuinely flexible attributes; keep core fields in real columns so they can be typed, indexed and constrained.

Upserts, returning and bulk changes

Insert or update in one statement

An upsert inserts a row, or updates it if the key already exists, atomically (no race between "check" and "write").

CREATE TABLE stock (sku TEXT PRIMARY KEY, qty INTEGER NOT NULL);
INSERT INTO stock VALUES ('pen', 10);
INSERT INTO stock (sku, qty) VALUES ('pen', 5), ('book', 3)
ON CONFLICT (sku) DO UPDATE SET qty = stock.qty + excluded.qty;
SELECT * FROM stock ORDER BY sku;

Result

skuqty
book3
pen15

Dialects: PostgreSQL and SQLite ON CONFLICT ... DO UPDATE, MySQL ON DUPLICATE KEY UPDATE, SQL Server and Oracle MERGE.

RETURNING and set-based updates

CREATE TABLE tasks (id INTEGER PRIMARY KEY, title TEXT, done INTEGER DEFAULT 0);
INSERT INTO tasks (title) VALUES ('write'), ('test'), ('ship');
UPDATE tasks SET done = 1 WHERE title IN ('write', 'test') RETURNING id, title, done;

Result

idtitledone
1write1
2test1

RETURNING (PostgreSQL, SQLite; OUTPUT in SQL Server) gives back the affected rows, saving a second query and avoiding races.

Think in sets, not loops

Write one UPDATE ... FROM or INSERT ... SELECT that changes many rows at once instead of looping row by row from application code. Batches are faster, fewer round trips, and are easier to make atomic.

CREATE TABLE customer_totals AS
SELECT c.id AS customer_id, COALESCE(SUM(i.qty * p.price), 0) AS spent
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'paid'
LEFT JOIN order_items i ON i.order_id = o.id
LEFT JOIN products p ON p.id = i.product_id
GROUP BY c.id;
SELECT COUNT(*) AS rows_created, SUM(spent) AS total FROM customer_totals;

Result

rows_createdtotal
85190.0

How this gets asked

What does an upsert guarantee?

  • Two statements in a row It is a single statement.
  • Atomic insert-or-update without a check-then-write race Correct.
  • Deleting rows No.
  • Faster scans No.

The database resolves the conflict inside the statement.

Self-check

Name the upsert syntax in PostgreSQL, MySQL, SQL Server.

ON CONFLICT DO UPDATE, ON DUPLICATE KEY UPDATE and MERGE.

Interview questions: SQL advanced

10 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What is a CTE?

A named temporary result defined with WITH, used to structure a query into readable steps.

Medium Window function versus GROUP BY?

GROUP BY collapses rows into one per group; a window function computes across related rows and keeps every row.

Medium ROW_NUMBER, RANK and DENSE_RANK?

ROW_NUMBER gives unique numbers; RANK gives ties the same rank and leaves gaps; DENSE_RANK gives ties the same rank without gaps.

Medium How do you get the top N rows per group?

Rank rows with a window function partitioned by the group in a subquery or CTE, then filter rank <= N.

Medium What do LAG and LEAD do?

Return a value from a previous or following row in the window order, useful for differences and period over period change.

Medium How do you compute a running total or moving average?

SUM or AVG as a window function with ORDER BY and a frame such as ROWS BETWEEN 2 PRECEDING AND CURRENT ROW.

Advanced Explain recursive CTEs.

An anchor query seeds rows and a recursive query joined with UNION ALL generates more until none appear. Used for hierarchies, paths and sequences; include a stopping condition.

Advanced Explain the gaps and islands technique.

Subtract ROW_NUMBER from the sequence value (or use LAG flags with a running sum) to create a constant group id per consecutive run, then aggregate by it.

Advanced What is an upsert?

A single atomic statement that inserts or updates on conflict: ON CONFLICT DO UPDATE (PostgreSQL, SQLite), ON DUPLICATE KEY UPDATE (MySQL), MERGE (SQL Server, Oracle).

Advanced How do you pivot rows to columns?

Conditional aggregation with SUM(CASE WHEN ...) per output column, or the PIVOT operator where available.
