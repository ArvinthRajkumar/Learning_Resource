Data warehousing and dimensional modelling: star schemas, slowly changing dimensions and ELT

Transactional databases are designed to record business events safely; warehouses are designed to answer questions about them quickly. This part explains the shapes that make analytical queries simple and fast, and builds a small star schema you can query.

Advanced~5 hours

Running analytics directly on the OLTP database slows the application and produces awkward 12-table joins. The usual pipeline copies data to a warehouse (see SD20) and reshapes it.

Facts and dimensions

Dimensional modelling (Kimball) splits data into two kinds of tables:

  • Fact table: the measurements of a business process, one row per event at a stated grain (granularity). Columns are foreign keys to dimensions plus numeric measures (quantity, amount). Facts are narrow, very long and append-heavy.
  • Dimension table: the descriptive context (who, what, where, when): customer, product, store, date. Dimensions are wide, short and rich in text attributes used to filter, group and label.

The grain decision comes first: "one row per order line" or "one row per day per product" or "one row per page view". Every column must be true at that grain. Mixing grains in one fact table causes double counting.

Types of facts and measures

KindMeaningExample
Transaction factOne row per eventEach order line
Periodic snapshotState at regular intervalsAccount balance at end of each day
Accumulating snapshotOne row per process instance, updated as it movesOrder with placed, shipped, delivered dates
Factless factRecords that an event occurred, no measureStudent attended class

Measures are additive (sum across all dimensions: revenue), semi-additive (sum across some: account balance can be summed across accounts but not across time), or non-additive (ratios, unit prices: store the numerator and denominator and compute the ratio at query time).

Every analytical question has the same shape: join the fact to the dimensions you need, filter and group by dimension attributes, aggregate measures. That regularity is what lets BI tools generate queries automatically.

CREATE TABLE dim_customer (customer_key INTEGER PRIMARY KEY, name TEXT, segment TEXT, country TEXT);
CREATE TABLE dim_product (product_key INTEGER PRIMARY KEY, category TEXT);
CREATE TABLE fact_sales (customer_key INT, product_key INT, revenue REAL, cost REAL);
INSERT INTO dim_customer VALUES (1,'Ana','retail','IN'),(2,'Bo','wholesale','US'),(3,'Cy','retail','US');
INSERT INTO dim_product VALUES (1,'stationery'),(2,'furniture');
INSERT INTO fact_sales VALUES (1,1,15,6),(2,2,300,180),(3,1,25,10),(1,1,20,8),(2,1,140,60),(3,2,600,360);
-- margin is a ratio: compute it from additive parts, never average stored ratios
SELECT c.country, c.segment, SUM(f.revenue) AS revenue,
       ROUND(100.0 * SUM(f.revenue - f.cost) / SUM(f.revenue), 1) AS margin_pct
FROM fact_sales f JOIN dim_customer c ON c.customer_key = f.customer_key
GROUP BY c.country, c.segment ORDER BY revenue DESC;

Dimension design

  • Surrogate keys: integer keys generated by the warehouse (customer_key), independent of source system ids (customer_id, the natural/business key). They isolate you from source changes, support history and make joins fast and small.
  • Conformed dimensions: the same dim_customer and dim_date are shared by all fact tables, so results from different processes can be compared ("drill across").
  • Degenerate dimensions: an identifier with no attributes, such as the order number, kept in the fact table.
  • Junk dimensions: combine low-cardinality flags (is_gift, payment_type) into one small dimension instead of many columns.
  • Role-playing dimensions: one dimension used several times (order_date, ship_date both join to dim_date).
  • Unknown member: row -1 / "Unknown" so facts with missing references still join (avoid null foreign keys).
  • Hierarchies are flattened into columns (product -> category -> department), which is what denormalisation in a star means. A snowflake schema normalises these into extra tables, saving a little space at the cost of more joins; stars are usually preferred.

The date dimension

Always build a calendar table instead of calling date functions in every query: it holds year, quarter, month, week, day of week, holiday, fiscal period and so on, making filters like "weekends" or "fiscal Q3" trivial and consistent.

WITH RECURSIVE d(day) AS (SELECT '2024-02-26' UNION ALL SELECT date(day, '+1 day') FROM d WHERE day < '2024-03-04')
SELECT day,
       CAST(strftime('%Y%m%d', day) AS INT) AS date_key,
       strftime('%w', day) AS weekday_num,
       CASE strftime('%w', day) WHEN '0' THEN 'Sun' WHEN '6' THEN 'Sat' ELSE 'weekday' END AS day_type,
       strftime('%W', day) AS week_of_year,
       strftime('%Y-%m', day) AS year_month
FROM d;

Slowly changing dimensions

Dimension attributes change: a customer moves country, a product moves category. How you record that decides whether last year's revenue is attributed to the country the customer lived in then or now.

TypeBehaviourHistory kept?Use when
Type 0Never changesn/aBirth date, original sign-up channel
Type 1Overwrite the old valueNoCorrections, attributes where history does not matter
Type 2Add a new row with validity datesYes, fullAttributes that must be analysed as of the time of the event
Type 3Add a column for the previous valueLimited (one change)Simple "before and after" comparisons
Type 4/6Mini-dimension or hybridVariesRapidly changing or combined needs

Type 2 is the workhorse: each version of the customer has its own surrogate key, valid_from, valid_to and an is_current flag. Facts loaded at the time point to the surrogate key that was current then.

CREATE TABLE dim_customer (customer_key INTEGER PRIMARY KEY AUTOINCREMENT, customer_id TEXT, name TEXT, country TEXT, valid_from TEXT, valid_to TEXT, is_current INT);
INSERT INTO dim_customer (customer_id, name, country, valid_from, valid_to, is_current) VALUES ('C-1', 'Ana', 'IN', '2023-01-01', '9999-12-31', 1);
CREATE TABLE fact_sales (sale_date TEXT, customer_key INT, revenue REAL);
INSERT INTO fact_sales VALUES ('2023-06-01', 1, 100);
-- Ana moves to the US on 2024-01-01: close the current row and insert a new version
UPDATE dim_customer SET valid_to = '2023-12-31', is_current = 0 WHERE customer_id = 'C-1' AND is_current = 1;
INSERT INTO dim_customer (customer_id, name, country, valid_from, valid_to, is_current) VALUES ('C-1', 'Ana', 'US', '2024-01-01', '9999-12-31', 1);
INSERT INTO fact_sales VALUES ('2024-03-01', 2, 250);
SELECT customer_key, customer_id, country, valid_from, valid_to, is_current FROM dim_customer ORDER BY customer_key;
SELECT d.country AS country_at_time_of_sale, SUM(f.revenue) AS revenue
FROM fact_sales f JOIN dim_customer d ON d.customer_key = f.customer_key GROUP BY d.country ORDER BY d.country;

The ETL logic for Type 2: compare incoming source rows with the current dimension row by business key and a hash of tracked attributes; if changed, close the old row and insert a new one; if new, insert; if unchanged, do nothing.

import hashlib
current = {"C-1": {"key": 2, "hash": hashlib.md5(b"Ana|US").hexdigest()}, "C-2": {"key": 3, "hash": hashlib.md5(b"Bo|DE").hexdigest()}}
incoming = [("C-1", "Ana", "US"), ("C-2", "Bo", "FR"), ("C-3", "Cy", "IN")]          # C-1 unchanged, C-2 moved, C-3 is new
for cid, name, country in incoming:
    h = hashlib.md5(f"{name}|{country}".encode()).hexdigest()
    if cid not in current: print(cid, "-> INSERT new member")
    elif current[cid]["hash"] != h: print(cid, "-> CLOSE old version and INSERT new version (type 2)")
    else: print(cid, "-> no change")

C-2 -> CLOSE old version and INSERT new version (type 2)
C-3 -> INSERT new member

Loading: ETL, ELT and incremental loads

  • ETL transforms data before loading; ELT loads raw data first and transforms inside the warehouse with SQL (dbt), exploiting its scale. ELT is now the common pattern.
  • Layers: raw/bronze (as received, immutable) -> cleaned/silver (typed, deduplicated, conformed) -> marts/gold (star schemas and aggregates for BI).
  • Incremental loading: process only new or changed rows using a high-water mark (updated_at > last_loaded) or change data capture; keep loads idempotent (merge/upsert by key, or replace a date partition) so reruns are safe.
  • Late-arriving facts (the dimension row does not exist yet) go to the unknown member and are repaired later; late-arriving dimension changes may require re-pointing historical facts.
  • Orchestrate with a scheduler (Airflow, Dagster) and test: not-null, unique, relationships (every fact key exists in its dimension), accepted values, freshness, and row-count reconciliation against the source.
CREATE TABLE stg_orders (order_id INT, amount REAL, updated_at TEXT);
CREATE TABLE fact_orders (order_id INTEGER PRIMARY KEY, amount REAL, updated_at TEXT);
INSERT INTO stg_orders VALUES (1, 10, '2024-03-01'), (2, 20, '2024-03-01');
INSERT INTO fact_orders SELECT * FROM stg_orders WHERE true ON CONFLICT(order_id) DO UPDATE SET amount = excluded.amount, updated_at = excluded.updated_at;
-- next day: order 2 corrected, order 3 new, order 1 unchanged and re-sent
DELETE FROM stg_orders;
INSERT INTO stg_orders VALUES (1, 10, '2024-03-01'), (2, 25, '2024-03-02'), (3, 30, '2024-03-02');
INSERT INTO fact_orders SELECT * FROM stg_orders WHERE true ON CONFLICT(order_id) DO UPDATE SET amount = excluded.amount, updated_at = excluded.updated_at;
INSERT INTO fact_orders SELECT * FROM stg_orders WHERE true ON CONFLICT(order_id) DO UPDATE SET amount = excluded.amount, updated_at = excluded.updated_at;   -- rerun: idempotent
SELECT * FROM fact_orders ORDER BY order_id;

Aggregates, materialised views and performance

For dashboards that scan billions of rows, precompute aggregate tables (daily sales by product, hourly counts) or materialised views refreshed on a schedule or incrementally. Partition large facts by date, cluster by commonly filtered columns, use columnar formats, and select only needed columns. Know the trade-off: faster reads against storage and freshness.

TechniqueEffect
Partition by dateQueries prune whole partitions; cheap retention
Cluster / sort keysSkip blocks that cannot match the filter
Column pruningRead only the columns used (columnar stores)
Pre-aggregationDashboards read thousands of rows instead of billions
Approximate distinctHyperLogLog for counts of unique users
Result cachingIdentical queries return instantly

Self-check

Name three ways to speed up warehouse queries.

Partitioning and clustering, columnar column pruning, and pre-aggregated tables or materialised views.

Modelling alternatives

  • Inmon (corporate information factory): first build a normalised enterprise warehouse, then data marts from it.
  • Kimball (dimensional): build conformed star-schema marts directly; faster to deliver; this page.
  • Data Vault: hubs (business keys), links (relationships), satellites (history) for auditable, flexible integration from many sources.
  • One Big Table (OBT): a fully denormalised wide table: simple and fast in columnar engines but redundant and harder to govern.
  • Semantic layer / metrics layer: define metrics once (revenue, active users) so every dashboard agrees.
Key idea

State the grain, put measurements in a fact table and context in conformed dimensions with surrogate keys, choose the slowly-changing-dimension type by whether history must be preserved, load incrementally and idempotently, and precompute what dashboards hit most.

Interview questions: Warehouse modelling

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic OLTP versus OLAP?

OLTP runs many small transactional reads and writes on normalised data; OLAP runs large analytical scans over denormalised, historical data.

Basic What is a fact table and a dimension table?

A fact table records measurable events at a chosen grain; a dimension table stores descriptive context used to filter and group.

Medium What is the grain and why decide it first?

What one fact row represents. Every column must be true at that grain, and mixing grains causes double counting.

Medium Star versus snowflake schema?

A star has denormalised dimensions joined directly to the fact; a snowflake normalises dimensions into extra tables, saving space at the cost of more joins.

Medium Why surrogate keys in dimensions?

They decouple the warehouse from source ids, allow several versions of one business key and make joins small and fast.

Medium Explain SCD Type 1, 2 and 3.

Type 1 overwrites, losing history; Type 2 adds a new row with validity dates, keeping full history; Type 3 adds a column for the previous value, keeping limited history.

Medium Additive, semi-additive and non-additive measures?

Additive sums across all dimensions (revenue), semi-additive across some (balances not across time), non-additive cannot be summed (ratios).

Medium What is a conformed dimension?

A dimension shared by multiple fact tables with the same keys and meaning, enabling drill-across.

Advanced ETL versus ELT?

ETL transforms before loading; ELT loads raw data into the warehouse and transforms there with SQL tools such as dbt, using the warehouse's scale.

Advanced How do you do an incremental, idempotent load?

Use a watermark or CDC to select changes and upsert by key or replace a date partition so reruns do not duplicate.

Advanced How do you handle late-arriving facts and dimensions?

Map missing dimension references to an unknown member and repair later; re-point historical facts when a late dimension version appears.

Advanced Data vault versus Kimball?

Kimball builds business-friendly star schemas; Data Vault uses hubs, links and satellites to integrate many sources with full auditability and then builds marts on top.

Advanced Why a date dimension?

A calendar table provides year, quarter, week, holiday and fiscal attributes consistently, making filters and grouping simple and fast.

Advanced How do you speed up a dashboard that scans billions of rows?

Partition and cluster the fact, prune columns, pre-aggregate or use materialised views, cache results and use approximate distinct counts.
