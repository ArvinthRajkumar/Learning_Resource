Database design: normalisation, keys, views, transactions and programmability

A good schema prevents whole classes of bugs, because the database refuses bad data. Transactions keep concurrent changes correct. This part teaches how to design tables and how to make changes safely.

MediumAdvanced~5 hours

Designing a schema

From requirements to tables

  1. List the entities (things): customer, product, order.
  2. List their attributes and decide the key that identifies each.
  3. Decide the relationships and their cardinality.
  4. Turn each entity into a table, each relationship into a foreign key or a junction table.
  5. Normalise, add constraints and indexes, then test with real queries.

Relationships

CardinalityExampleImplementation
One to manyOne customer has many ordersForeign key on the "many" side (orders.customer_id)
Many to manyOrders contain many products, products appear in many ordersJunction table (order_items(order_id, product_id)) with a composite primary key
One to oneUser and profileForeign key with UNIQUE, or the same primary key
 
CREATE TABLE authors (id INTEGER PRIMARY KEY, name TEXT NOT NULL);
CREATE TABLE books   (id INTEGER PRIMARY KEY, title TEXT NOT NULL, published INTEGER);
CREATE TABLE book_authors (
    book_id   INTEGER NOT NULL REFERENCES books(id)   ON DELETE CASCADE,
    author_id INTEGER NOT NULL REFERENCES authors(id) ON DELETE RESTRICT,
    role      TEXT NOT NULL DEFAULT 'author',
    PRIMARY KEY (book_id, author_id)
);
INSERT INTO authors VALUES (1, 'Ada'), (2, 'Ben');
INSERT INTO books VALUES (1, 'Joint Work', 2020);
INSERT INTO book_authors (book_id, author_id) VALUES (1, 1), (1, 2);
SELECT b.title, GROUP_CONCAT(a.name, ' & ') AS authors
FROM books b JOIN book_authors ba ON ba.book_id = b.id JOIN authors a ON a.id = ba.author_id
GROUP BY b.id;

Keys

  • Primary key: unique, not null, identifies a row. Keep it small and stable.
  • Natural key: a real-world identifier (email, ISBN). Risk: it can change or be reused.
  • Surrogate key: an artificial id (auto-increment integer, UUID). Stable and compact; keep a UNIQUE constraint on the natural key too.
  • Foreign key: a column referencing another table's key; the database rejects orphans. Choose referential actions: ON DELETE CASCADE (delete children), RESTRICT or NO ACTION (refuse), SET NULL.
  • Composite key: several columns together (as in a junction table).
PRAGMA foreign_keys = ON;
INSERT INTO orders (id, customer_id, order_date, status) VALUES (99, 12345, '2024-05-01', 'paid');

Result

error
FOREIGN KEY constraint failed

The statement above fails: customer 12345 does not exist, so the foreign key rejects it. (SQLite needs PRAGMA foreign_keys = ON; most databases enforce it by default.)

How this gets asked

How do you model a many-to-many relationship such as students and courses?

  • A comma-separated list column Violates 1NF.
  • A junction table with foreign keys to both Correct.
  • Duplicate rows Anomalies.
  • A view Not storage.

The junction (association) table holds one row per pairing.

Self-check

One-to-many versus many-to-many implementation?

One-to-many: a foreign key on the many side. Many-to-many: a junction table with a composite key.

Normalisation

Why normalise

Storing one fact in many places causes anomalies: update anomaly (change one copy, forget the others), insert anomaly (cannot record a fact without an unrelated one), delete anomaly (deleting one fact loses another). Normal forms are rules that remove them.

The normal forms in plain language

FormRuleViolation example
1NFEach cell holds one atomic value; no repeating groupsA phones column with "555-1, 555-2"
2NFIn 1NF and every non-key column depends on the whole key (matters for composite keys)order_items(order_id, product_id, product_name): product_name depends only on product_id
3NFIn 2NF and no non-key column depends on another non-key columnemployees(id, dept_id, dept_name): dept_name depends on dept_id
BCNFEvery determinant is a candidate key (a stricter 3NF)Rare edge cases with overlapping keys

Mnemonic: every non-key attribute depends on the key, the whole key, and nothing but the key.

Example: fixing a messy table

Before (one wide table, repeated customer and product data):

order_idcustomer_namecustomer_cityproductpriceqty
1AdaLondonPen210
2AdaLondonDesk3001

Problems: Ada's city is stored twice, a price change needs many updates, a product without orders cannot be stored. Split into customers, products, orders, order_items exactly as in the shop database.

Denormalisation

Normalised data needs joins. For read-heavy reporting you may denormalise on purpose: duplicate a column, store a precomputed total, use a summary table or materialised view. Do it after measuring, and keep the duplicate in sync (triggers, application code, or a periodic rebuild). OLTP schemas lean normalised; analytics schemas (star schema, wide tables) lean denormalised (SD4).

Design rules that save you later

  • Use the right types: DECIMAL for money, real date types, BOOLEAN.
  • Use NOT NULL by default; allow NULL only when "unknown" is meaningful.
  • Add CHECK, UNIQUE and foreign keys: constraints are bugs caught at the door.
  • Keep created_at and updated_at timestamps, store them in UTC.
  • Prefer soft deletes (deleted_at) only if you need history; they complicate every query and uniqueness rule.
  • Avoid storing lists in a column, EAV ("entity attribute value") tables for everything, and magic strings with no check.
  • Name things consistently (snake_case, singular or plural, table_id for foreign keys).

How this gets asked

  • 1NF Values are atomic.
  • 2NF Single-column key.
  • 3NF Correct: dept_name depends on dept_id, a non-key column.
  • None It violates 3NF.

Move department details into their own table.

Which phrase summarises 3NF?

  • The key, the whole key, and nothing but the key Correct.
  • All columns are indexed No.
  • No NULLs No.
  • Only one table No.

Each non-key attribute should depend on the key only.

What anomalies does normalisation prevent?

Update, insert and delete anomalies caused by duplicate facts.

Views

A view is a saved query that behaves like a table. It simplifies repeated queries, hides complexity and limits what users can see.

CREATE VIEW order_totals AS
SELECT o.id AS order_id, o.customer_id, o.status, SUM(i.qty * p.price) AS total
FROM orders o
JOIN order_items i ON i.order_id = o.id
JOIN products p ON p.id = i.product_id
GROUP BY o.id;

SELECT c.name, ROUND(SUM(t.total), 2) AS paid_total
FROM order_totals t JOIN customers c ON c.id = t.customer_id
WHERE t.status = 'paid'
GROUP BY c.id
ORDER BY paid_total DESC
LIMIT 3;

Ben2000.0

Dev950.0
  • A materialised view (PostgreSQL, Oracle) stores the result and must be refreshed; fast reads, stale until refresh.
  • Views can be updatable if they map simply to one table; complex ones are read-only.
  • A view is not faster by itself; the underlying query still runs.

Transactions

Intuition

A transaction is a group of statements that succeed or fail together. Transferring money = debit one account + credit another. Either both happen, or neither.

CREATE TABLE acct (name TEXT PRIMARY KEY, balance INTEGER NOT NULL CHECK (balance >= 0));
INSERT INTO acct VALUES ('alice', 100), ('bob', 20);
BEGIN;
UPDATE acct SET balance = balance - 30 WHERE name = 'alice';
UPDATE acct SET balance = balance + 30 WHERE name = 'bob';
SELECT * FROM acct ORDER BY name;
ROLLBACK;
SELECT * FROM acct ORDER BY name;

Result

namebalance
alice70
bob50
namebalance
alice100
bob20

Between BEGIN and ROLLBACK the changes are visible only inside the transaction; ROLLBACK undoes them. COMMIT makes them permanent and visible to others. A CHECK failure inside the transaction aborts the whole thing, protecting the invariant.

ACID recap

Atomicity, Consistency, Isolation, Durability (SD4). Durability comes from the write-ahead log; isolation from locks or MVCC.

Savepoints

SAVEPOINT name marks a point inside a transaction; ROLLBACK TO name undoes only the work after it.

How this gets asked

A transaction updates two rows and then hits a CHECK violation. What happens to the first update?

  • It stays committed Atomicity forbids that.
  • It is rolled back with the rest Correct.
  • It is queued No.
  • It is duplicated No.

Atomicity means all or nothing.

Self-check

What do COMMIT and ROLLBACK do?

COMMIT makes the transaction's changes permanent; ROLLBACK discards them.

-- PostgreSQL example
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance FROM accounts WHERE id = 1;     -- sees a snapshot
UPDATE accounts SET balance = balance - 10 WHERE id = 1;

Locks

  • Row locks (SELECT ... FOR UPDATE) block other writers of the same rows until commit.
  • Shared locks (FOR SHARE) allow reads but block writes.
  • Table locks for DDL and bulk operations.
  • MVCC lets readers see a snapshot without taking locks, so readers do not block writers.
-- Take a job from a queue table without two workers getting the same one (PostgreSQL, MySQL 8)
SELECT id FROM jobs WHERE status = 'new' ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;

Optimistic versus pessimistic

  • Pessimistic: lock first (FOR UPDATE), then change. Safe, can reduce throughput.
  • Optimistic: read a version number, update with WHERE version = :v, and retry if zero rows were updated.
CREATE TABLE doc (id INTEGER PRIMARY KEY, body TEXT, version INTEGER NOT NULL DEFAULT 1);
INSERT INTO doc (id, body) VALUES (1, 'draft');
-- two editors both read version 1; the first save wins
UPDATE doc SET body = 'edit A', version = version + 1 WHERE id = 1 AND version = 1;
SELECT changes() AS rows_updated_first;

Result

rows_updated_first
1
 
CREATE TABLE doc (id INTEGER PRIMARY KEY, body TEXT, version INTEGER NOT NULL DEFAULT 1);
INSERT INTO doc (id, body) VALUES (1, 'draft');
UPDATE doc SET body = 'edit A', version = version + 1 WHERE id = 1 AND version = 1;
UPDATE doc SET body = 'edit B', version = version + 1 WHERE id = 1 AND version = 1;   -- stale version
SELECT changes() AS rows_updated_second, (SELECT body FROM doc) AS body;

Result

rows_updated_secondbody
0edit A

The second editor's update changes 0 rows, so the application knows there was a conflict and can ask the user to retry or merge.

Deadlocks

Transaction A locks row 1 then wants row 2; B locked row 2 and wants row 1. The database detects the cycle and aborts one with a deadlock error. Reduce them by touching rows in a consistent order, keeping transactions short, and retrying on deadlock errors.

How this gets asked

Optimistic locking detects a conflict how?

  • A row lock held for the whole edit That is pessimistic.
  • A version check in the UPDATE's WHERE clause affecting 0 rows Correct.
  • A table lock No.
  • A trigger No.

If no row matched the expected version, someone else changed it first.

How do you reduce deadlocks?

  • Hold locks longer Worse.
  • Access rows in a consistent order and keep transactions short Correct.
  • Disable transactions Unsafe.
  • Use more indexes only Not the main fix.

Consistent ordering removes circular waits.

Self-check

What is MVCC?

Keeping row versions so readers see a snapshot and do not block writers.

Triggers, functions and stored procedures

Triggers

A trigger runs automatically on INSERT, UPDATE or DELETE. Typical uses: audit logs, maintaining derived columns, enforcing complex rules.

CREATE TABLE prices (sku TEXT PRIMARY KEY, price INTEGER);
CREATE TABLE price_audit (sku TEXT, old_price INTEGER, new_price INTEGER);
CREATE TRIGGER trg_price_audit AFTER UPDATE OF price ON prices
BEGIN
    INSERT INTO price_audit VALUES (OLD.sku, OLD.price, NEW.price);
END;
INSERT INTO prices VALUES ('pen', 2);
UPDATE prices SET price = 3 WHERE sku = 'pen';
SELECT * FROM price_audit;

Result

skuold_pricenew_price
pen23

Use triggers sparingly: they hide logic, complicate debugging and can cascade. Prefer constraints and application logic where possible.

Stored procedures and functions

Server-side programs written in PL/pgSQL, T-SQL, PL/SQL or MySQL's language. Pros: fewer round trips, close to the data, one place for rules. Cons: harder to test and version, tied to a vendor.

-- PostgreSQL function
CREATE FUNCTION add_tax(amount numeric, rate numeric DEFAULT 0.2) RETURNS numeric
LANGUAGE sql IMMUTABLE AS $$ SELECT round(amount * (1 + rate), 2) $$;

Access control

Create roles, grant the least privilege needed (GRANT SELECT ON orders TO reporting), use separate accounts for the application, migrations and analysts, and never use the superuser from application code. Row-level security (PostgreSQL) restricts which rows a role can see. See SD11 for security fundamentals.

Self-check

When use a trigger?

For audit trails and rules that must hold regardless of which application writes, used sparingly.

Interview questions: SQL design

11 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What is normalisation and why do it?

Organising tables so each fact is stored once, to avoid update, insert and delete anomalies. Typically to third normal form.

Basic Explain 1NF, 2NF and 3NF.

1NF: atomic values, no repeating groups. 2NF: every non-key column depends on the whole key. 3NF: no non-key column depends on another non-key column.

Medium When would you denormalise?

When measured read performance needs fewer joins, such as reporting or read-heavy paths, accepting duplicate data that must be kept in sync.

Medium Surrogate versus natural keys?

Surrogate keys are artificial ids, stable and compact. Natural keys are real attributes, which can change or collide. Use a surrogate primary key with a unique constraint on the natural key.

Medium Explain ACID.

Atomicity, consistency, isolation, durability: all-or-nothing, valid states, no interference between concurrent transactions, committed data survives crashes.

Medium What are the transaction isolation levels?

Read uncommitted, read committed, repeatable read and serializable, trading anomalies (dirty, non-repeatable and phantom reads) against concurrency.

Medium What is a view and a materialised view?

A view is a stored query used like a table. A materialised view stores the result and must be refreshed.

Advanced Optimistic versus pessimistic locking?

Pessimistic locks rows up front (SELECT FOR UPDATE). Optimistic reads a version and updates only if unchanged, retrying on conflict.

Advanced What causes deadlocks and how do you reduce them?

Transactions holding locks in different orders. Access rows in a consistent order, keep transactions short and retry on deadlock errors.

Advanced What is MVCC?

Multi-version concurrency control keeps several row versions so readers see snapshots without blocking writers.

Advanced Triggers: when and when not?

Use for audit trails and invariants that must hold for every writer. Avoid for business logic that hides side effects and complicates debugging.
