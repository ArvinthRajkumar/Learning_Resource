Clean code, SOLID and design patterns in Python

Interviews and code reviews ask how you structure code, not only whether it runs. Python's first-class functions and duck typing make many classic patterns much smaller than in Java. This part shows each pattern in its Pythonic form with a working example.

Advanced~5 hours

Clean code principles

  • Names reveal intent: days_since_signup, not d. Functions are verbs, classes are nouns.
  • Small functions that do one thing, at one level of abstraction.
  • No surprises: pure functions where possible, no hidden global state, no boolean flag arguments that change behaviour.
  • Fail early with guard clauses instead of deep nesting.
  • Don't repeat yourself, but don't abstract before the third repetition ("rule of three").
  • Comments explain why, code explains what. Delete dead code.
  • Prefer composition to inheritance, data classes for data, and explicit over implicit.
# Before: nested, flag argument, unclear names
def p(d, f):
    if d:
        if f:
            return [x * 2 for x in d if x > 0]
        else:
            return [x for x in d if x > 0]
    else:
        return []
# After: guard clause, two intention-revealing functions
def positives(values): return [v for v in values if v > 0]
def doubled_positives(values): return [v * 2 for v in positives(values)]
print(p([3, -1, 4], True), doubled_positives([3, -1, 4]), positives([]), p([3, -1, 4], False) == positives([3, -1, 4]))

Output

[6, 8] [6, 8] [] True

Refactoring checklist

Extract function, rename, replace magic numbers with named constants, replace conditionals with polymorphism or a dispatch dict, introduce a parameter object, remove duplication, and make the change under tests: refactoring means behaviour stays identical.

from typing import Protocol
class Notifier(Protocol):
    def send(self, to: str, message: str) -> None: ...
class EmailNotifier:
    def send(self, to, message): print(f"email to {to}: {message}")
class FakeNotifier:                                  # a test double, no inheritance needed
    def __init__(self): self.sent = []
    def send(self, to, message): self.sent.append((to, message))
class SignupService:
    def __init__(self, notifier: Notifier): self.notifier = notifier      # dependency injection
    def register(self, email):
        self.notifier.send(email, "Welcome!")
        return {"email": email}
SignupService(EmailNotifier()).register("a@x.com")
fake = FakeNotifier(); SignupService(fake).register("b@x.com")
print("test double recorded:", fake.sent)

Output

email to a@x.com: Welcome!
test double recorded: [('b@x.com', 'Welcome!')]

Duck typing plus Protocol gives dependency inversion without inheritance, and makes testing easy.

Creational patterns

Factory: choose a class from data

A dict of constructors replaces a chain of ifs and is open for extension.

import json, csv, io
class JsonReader:
    def read(self, text): return json.loads(text)
class CsvReader:
    def read(self, text): return list(csv.DictReader(io.StringIO(text)))
READERS = {"json": JsonReader, "csv": CsvReader}
def make_reader(kind):
    try: return READERS[kind]()
    except KeyError: raise ValueError(f"unknown format {kind!r}; choose from {sorted(READERS)}") from None
print(make_reader("json").read('[{"a": 1}]'), make_reader("csv").read("a,b\n1,2"))
try: make_reader("xml")
except ValueError as e: print(e)

Output

[{'a': 1}] [{'a': '1', 'b': '2'}]
unknown format 'xml'; choose from ['csv', 'json']

Singleton: usually a module

A Python module is imported once, so a module-level object is a singleton. Avoid classes enforcing __new__ tricks; global state makes testing hard, so prefer passing the object in.

Builder: construct complex objects step by step

Use keyword arguments, dataclasses with defaults, or a fluent builder when construction has many optional parts.

from dataclasses import dataclass, field, replace
@dataclass(frozen=True)
class Query:
    table: str
    columns: tuple = ("*",)
    where: tuple = ()
    limit: int | None = None
    def select(self, *cols): return replace(self, columns=cols)
    def filter(self, cond): return replace(self, where=self.where + (cond,))
    def take(self, n): return replace(self, limit=n)
    def sql(self):
        s = f"SELECT {', '.join(self.columns)} FROM {self.table}"
        if self.where: s += " WHERE " + " AND ".join(self.where)
        return s + (f" LIMIT {self.limit}" if self.limit is not None else "")
base = Query("users")
print(base.select("id", "name").filter("age > 18").filter("active = 1").take(10).sql())
print(base.sql(), "(the original is unchanged: frozen dataclass)")

Output

SELECT id, name FROM users WHERE age > 18 AND active = 1 LIMIT 10
SELECT * FROM users (the original is unchanged: frozen dataclass)

Structural patterns

Adapter: make an interface fit

class LegacyTemperatureSensor:
    def read_fahrenheit(self): return 98.6
class CelsiusSensor:                                   # the interface the rest of the code wants
    def __init__(self, legacy): self.legacy = legacy
    def read_celsius(self): return round((self.legacy.read_fahrenheit() - 32) * 5 / 9, 1)
print(CelsiusSensor(LegacyTemperatureSensor()).read_celsius())

Output

Decorator pattern (and Python decorators)

Wrap an object or function to add behaviour without changing it: logging, caching, retries, timing, authorisation.

import functools, time
def retry(times=3, exceptions=(Exception,)):
    def deco(fn):
        @functools.wraps(fn)
        def wrapper(*a, **kw):
            for attempt in range(1, times + 1):
                try: return fn(*a, **kw)
                except exceptions as e:
                    if attempt == times: raise
        return wrapper
    return deco
calls = {"n": 0}
@retry(times=3, exceptions=(ConnectionError,))
def fetch():
    calls["n"] += 1
    if calls["n"] < 3: raise ConnectionError("flaky")
    return "ok"
print(fetch(), "after", calls["n"], "attempts | name preserved:", fetch.__name__)

Output

ok after 3 attempts | name preserved: fetch

Facade and proxy

A facade gives a simple interface over a complex subsystem. A proxy stands in for another object (lazy loading, access control, caching) with the same interface.

class ExpensiveReport:
    def __init__(self): print("(building the report: slow)"); self.rows = [1, 2, 3]
class LazyReport:                                       # proxy: build only when first used
    def __init__(self): self._real = None
    def __getattr__(self, name):
        if self._real is None: self._real = ExpensiveReport()
        return getattr(self._real, name)
r = LazyReport()
print("created the proxy, nothing built yet")
print(r.rows, r.rows)

Output

created the proxy, nothing built yet
(building the report: slow)
[1, 2, 3] [1, 2, 3]

Behavioural patterns

Strategy: swap an algorithm

In Python a strategy is often just a function.

def flat(total): return total * 0.0
def percent(p): return lambda total: total * p
def tiered(total): return total * (0.2 if total > 100 else 0.05)
def checkout(total, discount): return round(total - discount(total), 2)
print(checkout(200, flat), checkout(200, percent(0.1)), checkout(200, tiered), checkout(50, tiered))

Output

200.0 180.0 160.0 47.5

Observer: notify subscribers

class EventBus:
    def __init__(self): self.handlers = {}
    def subscribe(self, event, fn): self.handlers.setdefault(event, []).append(fn)
    def publish(self, event, payload):
        for fn in self.handlers.get(event, []): fn(payload)
log = []
bus = EventBus()
bus.subscribe("order.paid", lambda o: log.append(f"email receipt for {o['id']}"))
bus.subscribe("order.paid", lambda o: log.append(f"update stock for {o['id']}"))
bus.publish("order.paid", {"id": 7}); bus.publish("order.cancelled", {"id": 8})
print(log)

Output

['email receipt for 7', 'update stock for 7']

Command: operations as objects (with undo)

class TextEditor:
    def __init__(self): self.text, self.history = "", []
    def do(self, command):
        command.apply(self); self.history.append(command)
    def undo(self):
        if self.history: self.history.pop().revert(self)
class Insert:
    def __init__(self, s): self.s = s
    def apply(self, ed): ed.text += self.s
    def revert(self, ed): ed.text = ed.text[: -len(self.s)]
ed = TextEditor()
ed.do(Insert("Hello")); ed.do(Insert(", world"))
print(repr(ed.text)); ed.undo(); print(repr(ed.text))

Output

'Hello, world'
'Hello'

State: behaviour depends on state

Use a transition table, which is declarative and testable.

TRANSITIONS = {("created", "pay"): "paid", ("paid", "ship"): "shipped", ("shipped", "deliver"): "delivered",
               ("created", "cancel"): "cancelled", ("paid", "cancel"): "refunded"}
class Order:
    def __init__(self): self.state = "created"
    def fire(self, event):
        nxt = TRANSITIONS.get((self.state, event))
        if nxt is None: raise ValueError(f"cannot {event} from {self.state}")
        self.state = nxt; return self
o = Order().fire("pay").fire("ship")
print(o.state)
try: o.fire("cancel")
except ValueError as e: print("rejected:", e)

Output

shipped
rejected: cannot cancel from shipped

Architecture patterns for applications

Repository: hide persistence behind an interface

The service talks to a repository; swap SQL for an in-memory fake in tests.

from dataclasses import dataclass
@dataclass
class User:
    id: int
    name: str
class InMemoryUserRepo:
    def __init__(self): self.data = {}
    def add(self, u): self.data[u.id] = u
    def get(self, uid): return self.data.get(uid)
class UserService:
    def __init__(self, repo): self.repo = repo
    def rename(self, uid, name):
        u = self.repo.get(uid)
        if u is None: raise KeyError(f"user {uid} not found")
        u.name = name; self.repo.add(u); return u
repo = InMemoryUserRepo(); repo.add(User(1, "ana"))
print(UserService(repo).rename(1, "Ana B."))

Output

User(id=1, name='Ana B.')

Layers and ports and adapters

Keep domain logic (pure Python, no I/O) in the centre; put web, database and queue code at the edges behind interfaces. Dependencies point inward. Benefits: fast unit tests, replaceable infrastructure.

Anti-patterns to avoid

God classes, deep inheritance trees, mutable global state, stringly-typed code, catching bare Exception and passing, premature abstraction, and copy-paste with tiny changes.

Key idea

In Python, functions are objects, so many patterns shrink to a dict of functions or a closure. Prefer composition, inject dependencies, keep domain logic free of I/O, and let tests tell you where the boundaries belong.

How this gets asked

  • To avoid SQL entirely No.
  • So business logic does not depend on the storage technology and can be tested with a fake Correct.
  • To speed up queries No.
  • To cache everything No.

Swap implementations without touching the service.

Interview questions: Design patterns

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What is the single responsibility principle?

A class or function should have one reason to change; split unrelated concerns such as parsing, validation, storage and reporting.

Basic Why prefer composition over inheritance?

Composition is more flexible and avoids tight coupling and fragile hierarchies. Use inheritance for true is-a relationships and shared behaviour.

Medium How is the strategy pattern implemented in Python?

Pass a function or callable that performs the varying step; a dict of functions can select among strategies.

Medium What is dependency injection and why use it?

Passing collaborators (database, clock, notifier) to a class or function instead of creating them inside, so they can be replaced in tests and configuration.

Medium What is a Protocol in Python?

A structural interface from typing: any class with the required methods satisfies it without inheriting, enabling duck typing with static checking.

Medium How do you implement a singleton in Python?

Usually a module-level object, since modules are imported once. Prefer passing the shared object explicitly to keep tests simple.

Medium Observer pattern in Python?

A publisher keeps a list of callables per event and calls them when the event fires; useful for decoupled notifications.

Medium Explain the Liskov substitution principle.

Instances of a subclass must be usable wherever the base class is expected without breaking behaviour: do not strengthen preconditions or weaken postconditions.

Advanced Factory versus builder?

A factory chooses which object to create; a builder constructs one complex object step by step, often immutably.

Advanced What is the repository pattern?

An abstraction of data access that the domain code uses, hiding SQL or an ORM behind an interface so storage can be swapped and tested with fakes.

Advanced State pattern versus a big if-chain?

State uses a transition table or state objects so each state's behaviour is explicit and illegal transitions are rejected centrally.

Advanced What is a code smell and name five?

A symptom of a design problem: long function, large class, duplicated code, feature envy, long parameter list, primitive obsession, deep nesting.

Advanced How do you refactor safely?

Cover the behaviour with tests first, make small steps, run tests after each, and avoid mixing refactoring with feature changes.

Advanced Ports and adapters (hexagonal) architecture?

Domain logic sits at the centre with no I/O; external systems connect through interfaces (ports) implemented by adapters, so dependencies point inward.
