Query performance, indexing and choosing a database engine

A query can return the right answer and still be unusable. This part teaches how to see what the database is doing, how to design indexes, and which patterns make queries slow. Execution plans below were produced by a real database.

Advanced~4 hours

How the database runs your query

Parse, plan, execute

  1. Parse the text and check names and permissions.
  2. The optimiser enumerates possible plans (access paths, join order, join algorithms) and picks the cheapest using statistics (row counts, value distributions).
  3. The executor runs the chosen plan.

Because SQL is declarative, two queries that mean the same can have very different plans; you tune by giving the optimiser good indexes and fresh statistics, and by writing queries it can reason about.

Access paths

MethodMeaningGood when
Full table scanRead every rowSmall tables, or you need most rows
Index seek (lookup)Walk the B-tree to matching rowsSelective filters (a few rows)
Index range scanWalk a range in an indexRanges, sorted output
Index-only (covering) scanAnswer from the index aloneAll needed columns are in the index

Join algorithms

AlgorithmHowBest when
Nested loopFor each outer row, look up matches in the inner (ideally by index)Small outer side, indexed inner side
Hash joinBuild a hash table on the smaller input, probe with the otherLarge unsorted inputs, equality joins
Merge joinMerge two sorted inputsBoth inputs already sorted (indexes)

How this gets asked

What does the query optimiser use to choose a plan?

  • The order you wrote the tables Mostly irrelevant.
  • Statistics about the data plus the available indexes Correct.
  • Random choice No.
  • Table names No.

It estimates costs from row counts and value distributions.

Self-check

Name three join algorithms.

Nested loop, hash join and merge join.

Reading execution plans

EXPLAIN

Every database has an EXPLAIN command: PostgreSQL EXPLAIN (ANALYZE, BUFFERS), MySQL EXPLAIN and EXPLAIN ANALYZE, SQL Server graphical plans, SQLite EXPLAIN QUERY PLAN. ANALYZE actually runs the query and shows real times and row counts versus estimates. Look for: scans on big tables, large gaps between estimated and actual rows, sorts spilling to disk, nested loops with huge outer sides.

An index changes the plan

Here is a table with 5,000 rows. First without an index:

CREATE TABLE t (id INTEGER PRIMARY KEY, email TEXT, country TEXT, score INTEGER);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 5000)
INSERT INTO t SELECT i, 'user' || i || '@x.com', CASE i % 4 WHEN 0 THEN 'US' WHEN 1 THEN 'UK' WHEN 2 THEN 'FR' ELSE 'DE' END, i % 100 FROM n;
EXPLAIN QUERY PLAN SELECT * FROM t WHERE email = 'user4242@x.com';

Now add an index and look again:

CREATE TABLE t (id INTEGER PRIMARY KEY, email TEXT, country TEXT, score INTEGER);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 5000)
INSERT INTO t SELECT i, 'user' || i || '@x.com', CASE i % 4 WHEN 0 THEN 'US' WHEN 1 THEN 'UK' WHEN 2 THEN 'FR' ELSE 'DE' END, i % 100 FROM n;
CREATE INDEX idx_t_email ON t(email);
EXPLAIN QUERY PLAN SELECT * FROM t WHERE email = 'user4242@x.com';

Result

plan
SEARCH t USING INDEX idx_t_email (email=?)

SCAN reads every row (O(n)); SEARCH ... USING INDEX walks the index (O(log n)). Same query, different cost, no change to the SQL.

How this gets asked

An EXPLAIN shows SCAN on a 100 million row table for a single-row lookup. What is the likely fix?

  • Add more RAM only Treats the symptom.
  • Create an index on the filtered column Correct.
  • Use SELECT * No.
  • Restart the database No.

An index turns the O(n) scan into an O(log n) seek.

Self-check

What do you look for in an execution plan?

Full scans on big tables, estimate versus actual row gaps, expensive sorts, and nested loops with large outer inputs.

Designing indexes

Which index helps

CREATE TABLE t (id INTEGER PRIMARY KEY, email TEXT, country TEXT, score INTEGER, created TEXT);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 5000)
INSERT INTO t SELECT i, 'user' || i || '@x.com', CASE i % 4 WHEN 0 THEN 'US' WHEN 1 THEN 'UK' WHEN 2 THEN 'FR' ELSE 'DE' END, i % 100, date('2024-01-01', '+' || (i % 365) || ' days') FROM n;
CREATE INDEX idx_country_score ON t(country, score);
EXPLAIN QUERY PLAN SELECT id FROM t WHERE country = 'FR' AND score > 90;

Result

plan
SEARCH t USING COVERING INDEX idx_country_score (country=? AND score>?)

The composite index (country, score) serves an equality on country and a range on score.

Composite index rules

  • Equality columns first, range column last. An index on (country, score) helps country = 'FR' AND score > 90; (score, country) would not use country after a range.
  • Leftmost prefix: (a, b, c) supports filters on a, a, b, a, b, c, not b alone.
  • Add ORDER BY columns after the filter columns so the index also provides ordering and avoids a sort.
  • Covering index: include every selected column (INCLUDE (...) in PostgreSQL and SQL Server) so the table is never read.
CREATE TABLE t (id INTEGER PRIMARY KEY, email TEXT, country TEXT, score INTEGER);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 2000)
INSERT INTO t SELECT i, 'u' || i, CASE i % 4 WHEN 0 THEN 'US' ELSE 'UK' END, i % 100 FROM n;
CREATE INDEX idx_cover ON t(country, score, email);
EXPLAIN QUERY PLAN SELECT email FROM t WHERE country = 'US' AND score = 5;

Result

plan
SEARCH t USING COVERING INDEX idx_cover (country=? AND score=?)

The plan says COVERING INDEX: the answer comes from the index alone.

Partial and unique indexes, expression indexes

CREATE TABLE users (id INTEGER PRIMARY KEY, email TEXT, deleted INTEGER DEFAULT 0);
CREATE UNIQUE INDEX uq_email_live ON users(lower(email)) WHERE deleted = 0;   -- partial + expression
INSERT INTO users (email) VALUES ('Ada@x.com');
SELECT name FROM sqlite_master WHERE type = 'index' ORDER BY name;

Result

name
uq_email_live

A partial index indexes only some rows (small and fast); an expression index supports queries on lower(email). A unique partial index enforces "unique among non-deleted users".

Index costs and rules of thumb

CostDetail
WritesEach index must be updated on insert, update, delete
SpaceIndexes can be as large as the table
MaintenanceBloat and fragmentation, rebuild occasionally
Wrong choicesLow-selectivity columns (a boolean) rarely help

Create indexes for real queries (found through slow query logs and plans), not speculatively. Remove unused indexes. Foreign key columns usually deserve an index (joins and cascading deletes).

  • (country, score) Correct.
  • (id) No.

Which are downsides of adding many indexes? Select all.

  • Slower inserts and updates
  • More disk space

Indexes usually speed reads; the cost is on writes, space and upkeep.

Common slow patterns and fixes

Non-sargable predicates

A sargable predicate lets the database use an index. Wrapping the column in a function defeats it.

Slow (index not used)Better
WHERE LOWER(email) = 'a@x.com'Expression index on lower(email), or store normalised email
WHERE YEAR(created) = 2024WHERE created >= '2024-01-01' AND created < '2025-01-01'
WHERE col + 1 = 10WHERE col = 9
WHERE name LIKE '%son'Full-text index, trigram index, or reverse column
WHERE CAST(id AS TEXT) = '5'Compare with the right type

Other frequent problems

  • SELECT \* reads unneeded columns and blocks covering indexes. Select what you need.
  • N+1 queries: one query for a list, then one per item. Replace with a join or an IN batch (PS0).
  • Large OFFSET pagination: the database reads and discards rows. Use keyset pagination (WHERE id > :last ORDER BY id LIMIT 20) (SD9).
  • Row-by-row processing in application code: use set-based SQL.
  • Missing join conditions or joining on unindexed columns.
  • Implicit type conversion (comparing a string column to a number) disables indexes.
  • DISTINCT or GROUP BY to hide join duplicates: fix the join instead.
  • COUNT(*) on huge tables: maintain a counter, use approximate counts, or index-only scans.
  • Long transactions hold locks and block vacuum or purge.
  • Stale statistics: run ANALYZE so estimates are accurate.
  • Functions in the join or filter (ON a.x = LOWER(b.y)).

Measure, change one thing, measure again

Workflow: find slow queries (slow query log, pg_stat_statements, performance schema), read the plan, add or fix an index or rewrite, re-run the plan, check that writes did not slow down, and keep the before and after numbers.

How this gets asked

Why is WHERE YEAR(created) = 2024 slow on an indexed created column?

  • Dates cannot be indexed They can.
  • The function on the column prevents the index being used (non-sargable) Correct.
  • YEAR is deprecated No.
  • Because of ORDER BY No.

Rewrite as created >= '2024-01-01' AND created < '2025-01-01'.

Which is the best fix for deep OFFSET pagination being slow?

  • Bigger OFFSET Slower.
  • Keyset pagination (WHERE id > last_id ORDER BY id LIMIT n) Correct.
  • COUNT(*) first No.
  • DISTINCT No.

Keyset pagination seeks with an index instead of skipping rows.

Dialect traps when moving code between engines: string concatenation (|| vs CONCAT), limiting rows (LIMIT vs TOP vs FETCH FIRST), date functions, auto-increment (SERIAL/IDENTITY/AUTO_INCREMENT), case sensitivity of comparisons, identifier quoting, boolean types, and upsert syntax (SQL2).

SQL versus NoSQL

Choose by access patterns, consistency needs and scale (SD4). A relational database is the right default; add specialised stores for caching, search, graphs, time series or huge write volumes when the numbers demand it.

OLTP versus OLAP, row versus column

Transactional databases are row-oriented; analytical warehouses (BigQuery, Snowflake, ClickHouse, DuckDB) are column-oriented and excel at scans and aggregations. Move heavy reporting off the transactional database.

Interview questions: SQL performance

10 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What is an index and what does it cost?

A sorted structure that speeds lookups and sorting. It uses space and slows inserts, updates and deletes.

Basic How do you find why a query is slow?

Read its execution plan with EXPLAIN (ANALYZE), look for full scans, bad estimates and sorts, and check indexes and statistics.

Medium What is a composite index and the leftmost prefix rule?

An index on several columns. It serves filters on a leftmost prefix of its columns, with equality columns first and the range column last.

Medium What is a covering index?

An index containing every column the query needs, so the table is not read.

Medium What makes a predicate non-sargable?

Applying a function or expression to the indexed column (YEAR(col), LOWER(col), col + 1) or a leading wildcard prevents index use. Rewrite or use an expression index.

Medium Why is deep OFFSET pagination slow and what is the alternative?

The database reads and discards the skipped rows. Use keyset pagination: WHERE id > :last ORDER BY id LIMIT n.

Advanced Nested loop, hash and merge joins?

Nested loop probes the inner side per outer row (good with indexes and small outer sets); hash join builds a hash table (large unsorted equality joins); merge join merges sorted inputs.

Advanced What is partitioning and when does it help?

Splitting a large table by range, list or hash so queries on the key touch fewer partitions and old data can be dropped quickly.

Advanced Order of scaling a database?

Fix queries and indexes, add caching and read replicas, partition, then shard. Each later step adds complexity.

Advanced Stale statistics?

The optimiser relies on row counts and distributions; outdated ones lead to bad plans. Run ANALYZE or autovacuum regularly.
