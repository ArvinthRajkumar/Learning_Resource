Professional Python: testing, logging, packaging and performance

Writing code that works once is the start. Professional code is tested, observable, reproducible and fast enough. This part covers the tools and habits that make Python projects maintainable.

MediumAdvanced~4 hours

Testing

Why test

Tests let you change code with confidence, document behaviour and catch regressions. A good suite is fast, independent, repeatable and tests behaviour, not implementation details.

A unit test with unittest

import unittest

def slugify(text):
    return "-".join(text.lower().split())

class TestSlugify(unittest.TestCase):
    def test_basic(self):
        self.assertEqual(slugify("Hello World"), "hello-world")
    def test_extra_spaces(self):
        self.assertEqual(slugify("  a   b "), "a-b")
    def test_empty(self):
        self.assertEqual(slugify(""), "")
    def test_type_error(self):
        with self.assertRaises(AttributeError):
            slugify(None)

suite = unittest.defaultTestLoader.loadTestsFromTestCase(TestSlugify)
import io
result = unittest.TextTestRunner(verbosity=0, stream=io.StringIO()).run(suite)
print("ran", result.testsRun, "failures", len(result.failures), "errors", len(result.errors))

Output

ran 4 failures 0 errors 0

The same tests with pytest

pytest (a third-party package, pip install pytest) is the most popular runner: plain assert, fixtures, parametrisation, rich failure output.

# test_slug.py
import pytest
from slug import slugify

@pytest.mark.parametrize("text, expected", [
    ("Hello World", "hello-world"),
    ("  a   b ", "a-b"),
    ("", ""),
])
def test_slugify(text, expected):
    assert slugify(text) == expected

@pytest.fixture
def db(tmp_path):                       # runs before each test that asks for it
    import sqlite3
    con = sqlite3.connect(tmp_path / "t.db")
    yield con
    con.close()                         # teardown

Run with pytest -q. Useful options: -k name (select by name), -x (stop at first failure), --cov (coverage with pytest-cov).

Test structure: arrange, act, assert

  1. Arrange the input and state.
  2. Act by calling the code.
  3. Assert on the result.

Keep one idea per test, name tests for the behaviour (test_rejects_negative_amount), and test edge cases: empty, one item, boundaries, invalid input, errors.

Mocks and fakes

Replace slow or non-deterministic dependencies (network, time, randomness) in tests.

from unittest.mock import Mock, patch

def convert(amount, client):
    rate = client.get_rate("EUR", "USD")
    return round(amount * rate, 2)

client = Mock()
client.get_rate.return_value = 1.1
print(convert(100, client))
client.get_rate.assert_called_once_with("EUR", "USD")

import time
def now_label():
    return "t=%d" % int(time.time())
with patch("time.time", return_value=1000):
    print(now_label())

Output

110.0
t=1000

Prefer fakes (a simple in-memory implementation, such as an SQLite database for tests) over deep mocks when behaviour matters. Patch where the name is used, not where it is defined.

The test pyramid

Many fast unit tests, fewer integration tests (several parts together, a real test database), few end-to-end tests. Aim for meaningful coverage, not 100 percent for its own sake.

How this gets asked

What does a well-written unit test do?

  • Tests many unrelated behaviours at once Hard to diagnose.
  • Checks one behaviour quickly and independently of other tests Correct.
  • Needs the live production database Fragile.
  • Prints results for a human to read Not automated.

Fast, isolated tests give reliable feedback.

With unittest.mock.patch, where do you patch a function?

  • Where it is defined Not necessarily.
  • Where it is looked up and used Correct.
  • Anywhere No.
  • In the standard library only No.

Patch the name in the namespace of the code under test.

Self-check

Arrange, act, assert?

Prepare the input and state, call the code, then check the outcome.

Logging, configuration and command-line tools

Use logging, not print

import logging, sys
logging.basicConfig(stream=sys.stdout, level=logging.INFO,
                    format="%(levelname)s %(name)s: %(message)s")
log = logging.getLogger("shop.orders")
log.debug("not shown at INFO level")
log.info("order %s created", 42)          # lazy %-style formatting
log.warning("stock low for %s", "pen")
try:
    1 / 0
except ZeroDivisionError as exc:
    log.error("failed to compute: %s", exc)   # log.exception(...) would also include the traceback

Output

INFO shop.orders: order 42 created
WARNING shop.orders: stock low for pen
ERROR shop.orders: failed to compute: division by zero

Levels: DEBUG, INFO, WARNING, ERROR, CRITICAL. Libraries should create a logger with logging.getLogger(__name__) and let the application configure handlers. In services emit structured (JSON) logs with a request id (SD11).

Command-line programs with argparse

import argparse
parser = argparse.ArgumentParser(description="Greeter")
parser.add_argument("name")
parser.add_argument("--times", type=int, default=1)
parser.add_argument("-v", "--verbose", action="store_true")
args = parser.parse_args(["Ada", "--times", "2", "-v"])     # normally reads sys.argv
for _ in range(args.times):
    print("hello", args.name)
print(args.verbose)

Output

hello Ada

Configuration

Keep settings out of code: environment variables (os.environ.get("DATABASE_URL")), config files (TOML via tomllib), and never commit secrets. The twelve-factor rule: config in the environment.

import os, tomllib
os.environ["APP_DEBUG"] = "1"
debug = os.environ.get("APP_DEBUG", "0") == "1"
cfg = tomllib.loads("""
[database]
host = "localhost"
port = 5432
""")
print(debug, cfg["database"]["port"])

Output

True 5432

How this gets asked

Why prefer logging over print in applications?

  • It is shorter No.
  • Levels, handlers, formats and configuration without changing code Correct.
  • It is faster No.
  • print is deprecated No.

Logging can be filtered, routed and structured by configuration.

Self-check

How should a library log?

Use logging.getLogger(__name__) and leave handler configuration to the application.

Environments and packaging

Virtual environments

A virtual environment is an isolated folder with its own interpreter links and installed packages, so projects do not conflict.

python -m venv .venv                 # create
source .venv/bin/activate            # macOS and Linux  (Windows: .venv\Scripts\activate)
pip install requests==2.32.3         # install a pinned version
pip freeze > requirements.txt        # record exact versions
pip install -r requirements.txt      # reproduce elsewhere
deactivate

Modern tools wrap this: uv, poetry, pipenv, hatch, pdm. They add lock files so every machine installs identical versions.

Project layout and pyproject.toml

mypkg/
  pyproject.toml          # metadata, dependencies, tool settings
  src/mypkg/__init__.py
  src/mypkg/core.py
  tests/test_core.py
  README.md
[project]
name = "mypkg"
version = "0.1.0"
requires-python = ">=3.10"
dependencies = ["requests>=2.30"]

[project.scripts]
mytool = "mypkg.cli:main"      # creates a command-line entry point

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

Build with python -m build, install locally with pip install -e . (editable). Version with semantic versioning (MAJOR.MINOR.PATCH).

Performance

Measure before optimising

"Premature optimisation is the root of all evil." Find the real bottleneck with measurement.

import timeit
setup = "data = list(range(10000))"
t_list = timeit.timeit("9999 in data", setup, number=2000)
t_set = timeit.timeit("9999 in s", setup + "; s = set(data)", number=2000)
print("set is faster than list for membership:", t_set < t_list)

Output

set is faster than list for membership: True
import cProfile, pstats, io

def slow():
    total = 0
    for i in range(200000):
        total += i % 7
    return total

pr = cProfile.Profile()
pr.enable(); slow(); pr.disable()
out = io.StringIO()
pstats.Stats(pr, stream=out).sort_stats("cumulative").print_stats(3)
print("profile captured:", "slow" in out.getvalue())

Output

profile captured: True

Use cProfile/snakeviz for CPU, tracemalloc for memory, and py-spy to profile running processes.

Typical wins

ProblemFix
Repeated membership tests on a listUse a set or dict
String building in a loop"".join(parts)
Repeated expensive pure functionfunctools.lru_cache
Python loop over numbersVectorise with NumPy, or use built-ins (sum, max, sorted)
Loading a huge file at onceStream with generators or chunks
Many small database queriesBatch, add indexes, avoid N+1 (PS0)
Slow I/O waitsThreads or asyncio (PY4)
Slow startup of many objects__slots__, dataclass(slots=True)
CPU-heavy loopsProcesses, Cython, Numba, Rust extensions
 
import sys
class Plain:
    def __init__(self): self.a, self.b = 1, 2
class Slim:
    __slots__ = ("a", "b")
    def __init__(self): self.a, self.b = 1, 2
print("slots saves per-instance dict:", not hasattr(Slim(), "__dict__"))

Output

How this gets asked

You must test membership in a large collection many times. Which is best?

  • list O(n) each.
  • set or dict Correct: O(1) average.
  • tuple O(n).
  • string No.

Hash-based containers give constant-time average lookup.

Self-check

What is the first step in optimising?

Measure and profile to find the real bottleneck.

Security and robustness habits

  • Never run eval or exec on untrusted input. Use ast.literal_eval for literals.
  • Never unpickle untrusted data: pickle can execute arbitrary code. Use JSON.
  • Parameterise SQL, never format user input into queries (PS0).
  • Use subprocess.run([...], check=True) with a list of arguments, never shell=True with user text.
  • Use secrets (not random) for tokens, hashlib.scrypt or bcrypt for passwords, hmac.compare_digest for constant-time comparison.
  • Validate and sanitise inputs at boundaries; keep dependencies updated and pinned, and scan them.
  • Do not store secrets in code or logs.
import ast, secrets, hmac
print(ast.literal_eval("[1, 2, {'a': 3}]"))
try:
    ast.literal_eval("__import__('os').system('echo hi')")
except ValueError:
    print("refused to evaluate code")
token = secrets.token_hex(8)
print(len(token), hmac.compare_digest("abc", "abc"))

Output

[1, 2, {'a': 3}]
refused to evaluate code
16 True

How this gets asked

Which are unsafe with untrusted input? Select all.

  • eval()
  • pickle.loads()
  • json.loads()
  • subprocess.run(cmd_string, shell=True)

json.loads only parses data; the others can execute attacker-controlled code.

Self-check

Why is pickle dangerous?

Loading a malicious pickle can run arbitrary code. Use JSON or other safe formats for untrusted data.

Interview questions: Python engineering

9 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Why use a virtual environment?

To isolate each project's dependencies and versions from the system and other projects, and to reproduce environments from a requirements or lock file.

Basic What is PEP 8?

The Python style guide: naming (snake_case, CapWords), indentation of four spaces, line length and import ordering. Automate with ruff or black.

Medium unittest versus pytest?

unittest is in the standard library with class-based tests. pytest uses plain asserts, fixtures, parametrisation and plugins, and also runs unittest tests.

Medium How do you test code with external dependencies?

Replace slow or non-deterministic dependencies with fakes or mocks (unittest.mock), inject them as parameters, and use a real test database or container for integration tests.

Medium How do you profile and speed up Python code?

Measure with cProfile, timeit and tracemalloc. Fix algorithms and data structures first, use built-ins and comprehensions, cache pure functions, vectorise with NumPy, and use processes or native code for CPU work.

Medium How should you handle configuration and secrets?

Keep them out of code: environment variables or config files, secret managers in production, never commit secrets or log them.

Advanced Why is pickle unsafe, and what is the alternative?

Unpickling untrusted data can execute arbitrary code. Use JSON or other data-only formats for untrusted input.

Advanced How would you package and distribute a library?

pyproject.toml with metadata and dependencies, a src layout, semantic versioning, build with python -m build, publish wheels to an index, and test across supported Python versions in CI.

Advanced What belongs in a logging setup for a service?

Structured logs with levels, request ids, no secrets, configured by the application (handlers and formatters) while libraries only get a logger by __name__.
