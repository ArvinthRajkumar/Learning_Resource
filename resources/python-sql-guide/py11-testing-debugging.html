Testing, debugging and profiling in depth: fixtures, mocks, property tests, tracing and performance

Testing and debugging are skills, not just tools. This part explains what to test and why, how to isolate dependencies without fooling yourself, how to hunt a bug methodically, and how to measure before optimising, with runnable examples throughout.

MediumAdvanced~5 hours

Why tests, and what kind

Tests are executable specifications and a safety net for change. They do not prove correctness; they raise confidence cheaply and repeatedly.

LevelTestsSpeedFailure tells you
UnitOne function or class, dependencies replacedMillisecondsExactly where the bug is
IntegrationSeveral components with real database, queue or HTTPSecondsThe pieces do not fit
End to endThe whole system through its UI or APIMinutesA user journey is broken
Property-basedProperties that must hold for many generated inputsSecondsAn edge case you did not think of
ContractProducer and consumer agree on an APISecondsA breaking change before release

Good tests are fast, isolated, repeatable, self-checking and meaningful. Test behaviour (inputs to outputs), not implementation details, so refactoring does not break them. A test that mocks the thing it claims to test proves nothing.

Fast tests give quick, precise feedback.

Anatomy of a good test

Arrange, act, assert: set up inputs, call the code, check one behaviour. Name tests by the behaviour: test_withdraw_more_than_balance_raises, not test_1.

import unittest
class Account:
    def __init__(self, balance=0): self.balance = balance
    def withdraw(self, amount):
        if amount <= 0: raise ValueError("amount must be positive")
        if amount > self.balance: raise ValueError("insufficient funds")
        self.balance -= amount
        return self.balance
class AccountTests(unittest.TestCase):
    def setUp(self): self.acct = Account(100)                      # fresh fixture for every test
    def test_withdraw_reduces_balance(self):
        self.assertEqual(self.acct.withdraw(30), 70)
    def test_cannot_overdraw(self):
        with self.assertRaisesRegex(ValueError, "insufficient"): self.acct.withdraw(101)
    def test_rejects_non_positive_amounts(self):
        for bad in (0, -5):
            with self.subTest(amount=bad):                          # parametrised cases with separate reporting
                with self.assertRaises(ValueError): self.acct.withdraw(bad)
    def test_exact_balance_can_be_withdrawn(self):
        self.assertEqual(self.acct.withdraw(100), 0)                # boundary value
import io
result = unittest.TextTestRunner(stream=io.StringIO(), verbosity=0).run(unittest.defaultTestLoader.loadTestsFromTestCase(AccountTests))
print("ran", result.testsRun, "tests | failures:", len(result.failures), "| errors:", len(result.errors))

Output

ran 4 tests | failures: 0 | errors: 0

What to test: normal cases, boundaries (0, 1, max, empty), invalid input, error handling, and each branch. Equivalence partitioning: pick one representative per class of input (negative, zero, small, huge) instead of every number.

Test doubles: stubs, fakes, mocks

When the code talks to a clock, network, database or payment provider, replace that dependency.

DoublePurpose
DummyFills a parameter, never used
StubReturns canned answers
FakeA working but simplified implementation (in-memory repository)
MockRecords calls so you can assert on interactions
SpyA real object that also records calls

Prefer fakes and stubs for state-based tests; use mocks sparingly, for outgoing side effects (email sent, event published). Over-mocking couples tests to implementation.

from unittest import mock
import datetime
class PaymentGateway:
    def charge(self, amount): raise RuntimeError("real network call")
def checkout(cart_total, gateway, notify, now=datetime.datetime.now):
    if cart_total <= 0: return "empty cart"
    receipt = gateway.charge(cart_total)
    notify(f"paid {cart_total} at {now().year}")
    return receipt
gateway = mock.Mock()
gateway.charge.return_value = "receipt-42"                            # stub the answer
notify = mock.Mock()                                                    # mock the side effect
result = checkout(250, gateway, notify, now=lambda: datetime.datetime(2030, 1, 1))     # inject the clock
print(result)
gateway.charge.assert_called_once_with(250)                              # verify the interaction
notify.assert_called_once_with("paid 250 at 2030")
print("interactions verified; the empty-cart branch does not touch the gateway:", checkout(0, gateway, notify), gateway.charge.call_count)

Output

receipt-42
interactions verified; the empty-cart branch does not touch the gateway: empty cart 1

Injecting the clock, random generators and IDs makes time-dependent code deterministic. mock.patch("module.name") replaces a name where it is used, not where it is defined (a very common mistake). Use autospec=True so a mock fails when called with a wrong signature, and freezegun-style helpers for time.

from unittest import mock
import os
def read_mode(): return os.environ.get("APP_MODE", "dev")
with mock.patch.dict(os.environ, {"APP_MODE": "prod"}):
    print("inside the patch:", read_mode())
print("after the patch is undone:", read_mode())
with mock.patch("os.path.exists", return_value=True) as fake_exists:
    print("patched exists says:", os.path.exists("/definitely/not/here"), "| call count:", fake_exists.call_count)

Output

inside the patch: prod
after the patch is undone: dev
patched exists says: True | call count: 1

Stub versus mock?

A stub returns canned data for the code under test; a mock records calls so you can assert on interactions.

Property-based testing

Instead of hand-picking examples, state a property that must hold for all inputs and let a library generate hundreds of random (and nasty) cases, shrinking a failure to a minimal one. In Python the library is hypothesis; the idea is simple enough to build:

import random
def my_sort(xs):                                       # code under test (a deliberately buggy variant is below)
    return sorted(xs)
def buggy_sort(xs):
    out = sorted(set(xs))                              # bug: drops duplicates
    return out
def check_sort_properties(sort, trials=500, seed=0):
    rng = random.Random(seed)
    for _ in range(trials):
        xs = [rng.randint(-5, 5) for _ in range(rng.randint(0, 8))]
        out = sort(xs[:])
        if out != sorted(out): return f"FAILS 'output is ordered' for {xs}"
        if sorted(xs) != sorted(out): return f"FAILS 'same elements as input' for {xs} -> {out}"
        if sort(out) != out: return f"FAILS 'idempotent' for {xs}"
    return "all properties held for 500 random inputs"
print("my_sort   :", check_sort_properties(my_sort))
print("buggy_sort:", check_sort_properties(buggy_sort))

Output

my_sort   : all properties held for 500 random inputs
buggy_sort: FAILS 'same elements as input' for [1, -5, -1, 3, 2, 1] -> [-5, -1, 1, 2, 3]

Useful properties: round trip (decode(encode(x)) == x), invariants (length, sum, ordering preserved), idempotence, commutativity, an oracle (compare a fast implementation with a slow obviously-correct one, as this guide does throughout), and no crash (never raises on valid input).

How this gets asked

Which is a good property for an encoder and decoder?

  • It is fast Not a property of correctness.
  • decode(encode(x)) == x for generated x (round trip) Correct.
  • Output is short No.
  • It prints nothing No.

The library generates many inputs and shrinks failures.

Debugging method

Debugging is the scientific method:

  1. Reproduce the failure reliably. Write a failing test if you can.
  2. Read the error and traceback. The last lines name the exception; the frames show how execution got there; your code is usually at the deepest frame of your files.
  3. Form a hypothesis, predict what you would see if it were true, and test it with a print, a log line or a debugger.
  4. Narrow down: bisect the input, the code path or the history (git bisect) to halve the search space each step.
  5. Fix the cause, not the symptom, add a regression test, and ask whether the same bug lurks elsewhere.
import traceback
def parse_age(record): return int(record["age"])
def average_age(records): return sum(parse_age(r) for r in records) / len(records)
try:
    average_age([{"age": "30"}, {"age": "x"}, {"age": "40"}])
except Exception as e:
    frames = [f.name for f in traceback.extract_tb(e.__traceback__)]
    print("call chain:", " -> ".join(frames))
    print(f"{type(e).__name__}: {e}")

Output

call chain: <module> -> average_age -> <genexpr> -> parse_age
ValueError: invalid literal for int() with base 10: 'x'

Read the call chain from left (outermost) to right (where it failed): <module> called average_age, which iterated a generator that called parse_age, where int('x') raised the ValueError: that is what; parse_age is where; average_age is who called it. In a real traceback the last lines show the exception and each frame shows the file, line number and code. The bad data came from the caller, so validate at the boundary.

Tools

  • **print/logging**: quick; prefer logging with levels so you can leave useful lines in.
  • **pdb / breakpoint()**: step through code. Commands: n (next line), s (step into), c (continue), l (list code), p expr (print), w (where, stack), u/d (up/down frames), b line (breakpoint), q. Post-mortem: python -m pdb script.py or pdb.pm() after an exception.
  • IDE debuggers show variables, watch expressions and conditional breakpoints.
  • **assert** documents and enforces assumptions during development.
  • Rubber-duck debugging: explain the code line by line aloud.
def find_bug_by_bisection(items, is_bad):
    """Binary search for the first bad item, assuming everything after the first bad one is bad (like git bisect)."""
    lo, hi, steps = 0, len(items) - 1, 0
    while lo < hi:
        mid = (lo + hi) // 2; steps += 1
        if is_bad(items[mid]): hi = mid
        else: lo = mid + 1
    return items[lo], steps
commits = list(range(1, 1001))
first_bad, steps = find_bug_by_bisection(commits, lambda c: c >= 637)
print(f"first bad commit: {first_bad}, found in {steps} checks instead of up to 1000")

Output

first bad commit: 637, found in 10 checks instead of up to 1000

Common Python bugs checklist

Mutable default arguments, late-binding closures in loops, modifying a list while iterating it, confusing is and ==, integer vs float division, shadowing built-ins (list, id), swallowed exceptions (except: pass), timezone-naive datetimes, off-by-one in slices and ranges, forgetting await, and shared state between threads.

funcs = [lambda: i for i in range(3)]
print("late binding closure bug:", [f() for f in funcs])
funcs = [lambda i=i: i for i in range(3)]
print("fixed with a default argument:", [f() for f in funcs])
xs = [2, 4, 6, 8, 9]
for x in xs:
    if x % 2 == 0: xs.remove(x)
print("removing every even number while iterating leaves some behind:", xs)
print("correct:", [x for x in [2, 4, 6, 8, 9] if x % 2 != 0])

Output

fixed with a default argument: [0, 1, 2]
removing every even number while iterating leaves some behind: [4, 8, 9]
correct: [9]

Profiling: measure, then optimise

"Premature optimisation is the root of all evil", but unmeasured optimisation is just guessing. Process: define the target (latency, memory), measure where time or memory goes, change one thing, measure again.

ToolAnswers
time.perf_counter() / timeitHow long does this snippet take?
cProfile + pstatsWhich functions use the most time, and how often are they called?
line_profilerWhich lines of this function are slow?
tracemallocWhere is memory allocated?
sys.getsizeof, pymplerHow big is this object?
py-spySample a running process without changing it
Flame graphsVisualise where time is spent
 
import cProfile, pstats, io
def slow_unique(items):
    out = []
    for x in items:
        if x not in out: out.append(x)               # O(n) membership in a list -> O(n^2) overall
    return out
def fast_unique(items):
    seen, out = set(), []
    for x in items:
        if x not in seen: seen.add(x); out.append(x)
    return out
data = [i % 2000 for i in range(20000)]
pr = cProfile.Profile(); pr.enable(); slow_unique(data); pr.disable()
stats = pstats.Stats(pr, stream=io.StringIO()).sort_stats("tottime")
slow_calls = {fn[2]: v[1] for fn, v in stats.stats.items()}
print("cProfile recorded one call to slow_unique:", slow_calls.get("slow_unique"))
import timeit
t_slow = timeit.timeit(lambda: slow_unique(data), number=1)
t_fast = timeit.timeit(lambda: fast_unique(data), number=1)
print("same result:", slow_unique(data) == fast_unique(data), "| the set-based version is at least 10x faster:", t_slow / t_fast > 10)

Output

cProfile recorded one call to slow_unique: 1
same result: True | the set-based version is at least 10x faster: True

Typical fixes, in order of payoff: a better algorithm or data structure, caching (functools.lru_cache), avoiding repeated work and I/O in loops, batching, built-in or vectorised operations, generators for memory, processes for CPU parallelism, and finally native code (Cython, Rust, NumPy).

Flaky and slow tests

A flaky test passes and fails without code changes. Causes: real time and sleeps, randomness, test order dependence and shared state, network and external services, concurrency races, uncontrolled data. Fixes: inject clocks and seeds, isolate state with fixtures and temp directories, wait on conditions not sleeps, fake external services, run tests in random order to expose coupling, and quarantine then fix (never ignore) flaky tests.

Speed up slow suites: run in parallel, share expensive setup with scoped fixtures, use in-memory databases for most tests, mark and separate slow tests, and run the full suite in CI on every push.

How this gets asked

How should tests wait for an asynchronous result?

  • sleep(5) Slow and still flaky.
  • Poll or wait on an explicit condition with a timeout Correct.
  • Ignore the failure No.
  • Run twice No.

Conditions are deterministic; arbitrary sleeps are not.

Coverage and what it means

Coverage shows which lines or branches ran, not whether behaviour was verified. 100% coverage with no assertions is worthless; 80% with meaningful tests on critical paths beats it. Use coverage to find untested code, set a floor in CI, and favour branch coverage and mutation testing (flip operators and see whether tests fail) to judge test quality.

Key idea

Test behaviour at the cheapest level that can catch the bug, replace slow or non-deterministic dependencies with fakes and injected clocks, state properties for generated inputs, debug by reproducing and bisecting, and profile before you optimise.

Self-check

Why is high coverage not enough?

It shows lines executed, not whether behaviour was asserted; weak assertions give a false sense of safety.

Interview questions: Testing and debugging

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Describe the test pyramid.

Many fast unit tests, fewer integration tests and a few end-to-end tests, because higher-level tests are slower, flakier and less precise.

Basic What makes a good unit test?

Fast, isolated, deterministic, self-checking, testing one behaviour with a clear name and meaningful assertions.

Medium Stub versus mock versus fake?

A stub returns canned answers, a mock records interactions for assertion, a fake is a simplified working implementation such as an in-memory repository.

Medium Where do you patch with mock.patch?

Where the name is looked up and used, not where it is defined.

Medium How do you test code that depends on time or randomness?

Inject the clock or random generator (or seed it) so tests are deterministic.

Medium What is property-based testing?

Stating properties that should hold for all inputs and letting a library such as Hypothesis generate many cases and shrink failures to minimal examples.

Medium What causes flaky tests and how do you fix them?

Real time, sleeps, randomness, shared state, test order, network and races. Inject dependencies, isolate state, wait on conditions and fix or quarantine them.

Medium How do you debug a failing function methodically?

Reproduce, read the traceback, form and test a hypothesis, narrow with bisection or logging, fix the cause and add a regression test.

Medium What does git bisect do?

It binary-searches the commit history using a good and a bad commit to find the commit that introduced a bug.

Advanced Why is 100% code coverage not enough?

It shows lines executed, not whether assertions verify behaviour. Branch coverage and mutation testing give better signals.

Advanced How do you profile a slow Python function?

Measure with timeit or cProfile to find hot functions, use line_profiler for lines and tracemalloc for memory, change one thing and measure again.

Advanced What is a contract test?

A test that checks a consumer and a provider agree on an API's shape, catching breaking changes without a full integration environment.

Advanced How do you design tests for database code?

Inject the connection, use an in-memory or disposable database with per-test fixtures for logic, and run key tests against the production engine in CI.

Advanced pytest fixtures versus unittest setUp?

Fixtures are composable, scoped (function, module, session), injected by name and can yield for teardown; setUp is per-class and less flexible.
