Transactions in depth: isolation anomalies, locking, MVCC and two-connection experiments

Concurrency bugs only show up under load, which makes them expensive. This part makes them visible: two connections, one database, and a clear picture of what each isolation level guarantees. Experiments run on SQLite; where PostgreSQL or MySQL behave differently, the text says so.

Advanced~5 hours

ACID, precisely

LetterGuaranteeMechanism
AtomicityAll of a transaction's changes happen or noneUndo log, rollback
ConsistencyConstraints hold before and afterConstraints, triggers, your code
IsolationConcurrent transactions do not see each other's partial workLocks or MVCC snapshots
DurabilityCommitted data survives a crashWrite-ahead log, fsync

Atomicity is easy to see: a failed transfer must not leave money half moved.

import sqlite3
db = sqlite3.connect(":memory:", isolation_level=None)
db.executescript("CREATE TABLE acct(id INTEGER PRIMARY KEY, bal INT CHECK (bal >= 0)); INSERT INTO acct VALUES (1, 100), (2, 50);")
def transfer(src, dst, amount):
    db.execute("BEGIN")
    try:
        db.execute("UPDATE acct SET bal = bal - ? WHERE id = ?", (amount, src))   # may violate CHECK
        db.execute("UPDATE acct SET bal = bal + ? WHERE id = ?", (amount, dst))
        db.execute("COMMIT"); return "committed"
    except sqlite3.Error as e:
        db.execute("ROLLBACK"); return f"rolled back ({e})"
print(transfer(1, 2, 30))
print(transfer(1, 2, 500))
print("balances:", db.execute("SELECT id, bal FROM acct ORDER BY id").fetchall(), "| total is still", db.execute("SELECT SUM(bal) FROM acct").fetchone()[0])

Output

committed
rolled back (CHECK constraint failed: bal >= 0)
balances: [(1, 70), (2, 80)] | total is still 150

Anomalies

An anomaly is a surprising result of concurrency. The standard list:

AnomalyWhat happens
Dirty readRead another transaction's uncommitted change
Non-repeatable readRead a row twice in one transaction and get different values (someone committed between)
Phantom readRun a range query twice and get different sets of rows
Lost updateTwo read-modify-write cycles overwrite each other
Write skewTwo transactions each check a condition on overlapping data, then write different rows, together violating a rule

Isolation levels (SQL standard)

LevelDirty readNon-repeatablePhantom
Read uncommittedPossiblePossiblePossible
Read committedNoPossiblePossible
Repeatable readNoNoPossible (not in PostgreSQL or MySQL InnoDB, which use snapshots)
SerializableNoNoNo

Defaults differ: PostgreSQL read committed; MySQL InnoDB repeatable read; SQL Server read committed (optionally snapshot); Oracle read committed; SQLite is effectively serializable (one writer at a time). Lost update and write skew are not in the classic table, which is why they surprise people: snapshot isolation (PostgreSQL's repeatable read) still allows write skew; only true serializable (SSI in PostgreSQL) prevents it.

Lost update, made visible

Both sessions read a balance, compute in the application, then write. The interleaving below is exactly what concurrent requests can produce.

import sqlite3
db = sqlite3.connect(":memory:", isolation_level=None)
db.executescript("CREATE TABLE counter(id INTEGER PRIMARY KEY, n INT); INSERT INTO counter VALUES (1, 10);")
a = db.execute("SELECT n FROM counter WHERE id = 1").fetchone()[0]          # session A reads 10
b = db.execute("SELECT n FROM counter WHERE id = 1").fetchone()[0]          # session B reads 10
db.execute("UPDATE counter SET n = ? WHERE id = 1", (a + 1,))               # A writes 11
db.execute("UPDATE counter SET n = ? WHERE id = 1", (b + 1,))               # B writes 11 (A's update is lost)
print("read-modify-write result:", db.execute("SELECT n FROM counter").fetchone()[0], "(two increments, but the value went up by one)")
db.execute("UPDATE counter SET n = 10")
db.execute("UPDATE counter SET n = n + 1 WHERE id = 1")                      # atomic, evaluated inside the database
db.execute("UPDATE counter SET n = n + 1 WHERE id = 1")
print("atomic increment result :", db.execute("SELECT n FROM counter").fetchone()[0])

Output

read-modify-write result: 11 (two increments, but the value went up by one)
atomic increment result : 12

Fixes, from simplest to most flexible:

  1. Atomic update in SQL (SET n = n + 1).
  2. Pessimistic lock: SELECT ... FOR UPDATE so the second reader waits.
  3. Optimistic lock: add a version column and update WHERE id = ? AND version = ?; if zero rows change, someone else won, so re-read and retry.
  4. Serializable isolation with retries.

Optimistic locking

import sqlite3
db = sqlite3.connect(":memory:", isolation_level=None)
db.executescript("CREATE TABLE doc(id INTEGER PRIMARY KEY, body TEXT, version INT); INSERT INTO doc VALUES (1, 'v1 text', 1);")
def load(): return db.execute("SELECT body, version FROM doc WHERE id = 1").fetchone()
def save(body, expected_version):
    cur = db.execute("UPDATE doc SET body = ?, version = version + 1 WHERE id = 1 AND version = ?", (body, expected_version))
    return cur.rowcount == 1
body_a, ver_a = load()          # editor A opens the document
body_b, ver_b = load()          # editor B opens the same version
print("A saves:", save("edited by A", ver_a))
print("B saves with a stale version:", save("edited by B", ver_b), "-> B must reload and merge")
print("stored:", load())

Output

A saves: True
B saves with a stale version: False -> B must reload and merge
stored: ('edited by A', 2)

Optimistic locking suits low contention (long think time, web forms) because nothing is held while the user thinks. Under high contention it wastes work in retries.

Two real connections

SQLite allows many readers but one writer at a time. Two connections to one file make that visible.

import sqlite3, os, tempfile
path = os.path.join(tempfile.mkdtemp(), "demo.db")
a = sqlite3.connect(path, isolation_level=None, timeout=0.2)
b = sqlite3.connect(path, isolation_level=None, timeout=0.2)
a.execute("CREATE TABLE t(id INTEGER PRIMARY KEY, v INT)"); a.execute("INSERT INTO t VALUES (1, 10)")
a.execute("BEGIN IMMEDIATE")                                  # A takes the write lock
a.execute("UPDATE t SET v = 20 WHERE id = 1")
try:
    b.execute("BEGIN IMMEDIATE")                              # B also wants to write
    b.execute("UPDATE t SET v = 99 WHERE id = 1")
except sqlite3.OperationalError as e:
    print("B is blocked:", e)
a.execute("COMMIT")
b.execute("BEGIN IMMEDIATE"); b.execute("UPDATE t SET v = v + 1 WHERE id = 1"); b.execute("COMMIT")
print("after both finish:", a.execute("SELECT v FROM t").fetchone()[0])

Output

B is blocked: database is locked
after both finish: 21

In PostgreSQL and MySQL row-level locks let writers to different rows proceed in parallel; a second writer to the same row waits until the first commits or rolls back.

Readers and snapshots (WAL mode)

In SQLite's WAL mode, readers see a consistent snapshot and do not block the writer: a read transaction keeps seeing the data as of its start.

import sqlite3, os, tempfile
path = os.path.join(tempfile.mkdtemp(), "wal.db")
w = sqlite3.connect(path, isolation_level=None)
r = sqlite3.connect(path, isolation_level=None)
print("journal mode:", w.execute("PRAGMA journal_mode=WAL").fetchone()[0])
w.execute("CREATE TABLE t(id INTEGER PRIMARY KEY, v INT)"); w.execute("INSERT INTO t VALUES (1, 10)")
r.execute("BEGIN"); first = r.execute("SELECT v FROM t WHERE id = 1").fetchone()[0]     # snapshot starts here
w.execute("UPDATE t SET v = 20 WHERE id = 1")                                          # committed by the writer
second = r.execute("SELECT v FROM t WHERE id = 1").fetchone()[0]                       # still the old snapshot
r.execute("COMMIT")
third = r.execute("SELECT v FROM t WHERE id = 1").fetchone()[0]                        # new transaction sees new data
print("reader saw", first, "then", second, "inside its transaction, and", third, "afterwards")

Output

journal mode: wal
reader saw 10 then 10 inside its transaction, and 20 afterwards

MVCC in one paragraph

Multi-version concurrency control keeps several versions of each row. Writers create new versions instead of overwriting; each transaction reads the versions visible to its snapshot, so readers never block writers and writers never block readers. PostgreSQL stores old row versions in the table (cleaned by VACUUM); MySQL InnoDB keeps old versions in undo logs. The cost: dead versions to clean, long transactions that hold back cleanup (bloat), and snapshot anomalies such as write skew.

Write skew

Rule: at least one doctor must stay on call. Two doctors each check "is someone else on call?" and both go off call. Each transaction wrote a different row, so there is no write-write conflict, yet the rule breaks.

import sqlite3
db = sqlite3.connect(":memory:", isolation_level=None)
db.executescript("CREATE TABLE oncall(doc TEXT PRIMARY KEY, on_duty INT); INSERT INTO oncall VALUES ('ana', 1), ('bo', 1);")
# Both transactions evaluate their check against the same snapshot (state at start), then write different rows
others_for_ana = db.execute("SELECT COUNT(*) FROM oncall WHERE on_duty = 1 AND doc <> 'ana'").fetchone()[0]
others_for_bo = db.execute("SELECT COUNT(*) FROM oncall WHERE on_duty = 1 AND doc <> 'bo'").fetchone()[0]
if others_for_ana >= 1: db.execute("UPDATE oncall SET on_duty = 0 WHERE doc = 'ana'")
if others_for_bo >= 1: db.execute("UPDATE oncall SET on_duty = 0 WHERE doc = 'bo'")
print("doctors on duty afterwards:", db.execute("SELECT COUNT(*) FROM oncall WHERE on_duty = 1").fetchone()[0], "(the invariant 'at least one' is broken)")

Output

doctors on duty afterwards: 0 (the invariant 'at least one' is broken)

Fixes: run at serializable isolation and retry on failure; lock the rows that the check reads (SELECT ... FOR UPDATE on the oncall set); materialise the conflict (a single row that every transaction must update); or enforce the rule with a constraint or a trigger.

Pessimistic locking and deadlocks

-- PostgreSQL / MySQL
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;      -- row locked until commit
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
COMMIT;

SELECT ... FOR UPDATE SKIP LOCKED;   -- take the next unlocked job (work queues)
SELECT ... FOR UPDATE NOWAIT;        -- fail immediately instead of waiting
SELECT ... FOR SHARE;                -- lock against modification, allow other readers

A deadlock is a cycle of waits: T1 holds row A and wants B while T2 holds B and wants A. The database detects it and aborts one transaction (an error you must retry). Prevent by locking rows in a consistent order, keeping transactions short, and avoiding user interaction inside a transaction.

def find_deadlock(waits_for):
    """waits_for: {transaction: transaction it waits for}. Returns a cycle if any."""
    for start in waits_for:
        seen, cur = [], start
        while cur in waits_for and cur not in seen:
            seen.append(cur); cur = waits_for[cur]
        if cur in seen:
            return seen[seen.index(cur):] + [cur]
    return None
print("T1 waits for T2, T2 waits for T1:", find_deadlock({"T1": "T2", "T2": "T1"}))
print("T1 waits for T2, T2 waits for T3:", find_deadlock({"T1": "T2", "T2": "T3"}))

Output

T1 waits for T2, T2 waits for T1: ['T1', 'T2', 'T1']
T1 waits for T2, T2 waits for T3: None

Advisory locks (pg_advisory_lock, GET_LOCK) lock an arbitrary application-chosen key, handy for "only one worker runs this job".

Savepoints and error handling

A savepoint lets you roll back part of a transaction. In PostgreSQL an error aborts the whole transaction unless you used a savepoint.

import sqlite3
db = sqlite3.connect(":memory:", isolation_level=None)
db.executescript("CREATE TABLE item(id INTEGER PRIMARY KEY, name TEXT UNIQUE);")
db.execute("BEGIN")
db.execute("INSERT INTO item(name) VALUES ('a')")
db.execute("SAVEPOINT sp1")
try:
    db.execute("INSERT INTO item(name) VALUES ('a')")          # duplicate: violates UNIQUE
except sqlite3.IntegrityError as e:
    db.execute("ROLLBACK TO sp1")                              # undo only the failed part
    print("duplicate rejected, transaction continues:", e)
db.execute("INSERT INTO item(name) VALUES ('b')")
db.execute("COMMIT")
print(db.execute("SELECT name FROM item ORDER BY name").fetchall())

Output

duplicate rejected, transaction continues: UNIQUE constraint failed: item.name
[('a',), ('b',)]

Retries and idempotent writes

Serialization failures, deadlocks and lock timeouts are normal in concurrent systems. Wrap the whole transaction in a retry loop with a small jittered back-off, and make the transaction idempotent so a retry after an ambiguous failure (a commit whose acknowledgement was lost) is safe. Use a unique key per request (INSERT ... ON CONFLICT DO NOTHING).

import sqlite3
db = sqlite3.connect(":memory:", isolation_level=None)
db.executescript("CREATE TABLE payment(request_id TEXT PRIMARY KEY, amount INT); CREATE TABLE ledger(total INT); INSERT INTO ledger VALUES (0);")
def pay(request_id, amount):
    db.execute("BEGIN")
    cur = db.execute("INSERT INTO payment VALUES (?, ?) ON CONFLICT(request_id) DO NOTHING", (request_id, amount))
    if cur.rowcount == 1:
        db.execute("UPDATE ledger SET total = total + ?", (amount,))
    db.execute("COMMIT")
    return "applied" if cur.rowcount == 1 else "duplicate ignored"
print([pay("req-1", 50), pay("req-1", 50), pay("req-2", 20), pay("req-1", 50)])
print("ledger total:", db.execute("SELECT total FROM ledger").fetchone()[0], "(70, not 170)")

Output

['applied', 'duplicate ignored', 'applied', 'duplicate ignored']
ledger total: 70 (70, not 170)

How this gets asked

What makes a retried transaction safe after an ambiguous commit failure?

  • Nothing No.
  • An idempotency key stored with a unique constraint so the work happens once Correct.
  • Sleep No.
  • A smaller batch No.

The retry becomes a no-op if the first attempt actually succeeded.

Practical rules

  1. Keep transactions short; never wait for a user or a network call inside one.
  2. Touch rows in a consistent order.
  3. Prefer atomic SQL (n = n + 1, conditional updates) over read-modify-write in the app.
  4. Choose the lowest isolation that is correct, and test the interleavings that matter.
  5. Retry on serialization failure, deadlock and timeout.
  6. Use constraints (unique, check, foreign key) as the final line of defence.
  7. Watch for long-running transactions: they hold locks and block cleanup.
  8. Monitor lock waits, deadlocks and replication lag.
Key idea

Concurrency bugs are about interleavings. Know which anomalies your isolation level allows, prefer atomic statements and constraints, use optimistic or pessimistic locks where you must read-then-write, and always be ready to retry.

Interview questions: Transactions in depth

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic State the ACID properties.

Atomicity, Consistency, Isolation, Durability: all-or-nothing changes, valid states, concurrent transactions behave as if separate, committed data survives crashes.

Basic What is a dirty read?

Reading another transaction's uncommitted change, which may later roll back.

Medium List the isolation levels and what each prevents.

Read uncommitted allows dirty reads; read committed prevents them; repeatable read also prevents non-repeatable reads; serializable also prevents phantoms and write skew.

Medium What is a lost update and how do you prevent it?

Two read-modify-write cycles overwrite each other. Use an atomic UPDATE expression, SELECT FOR UPDATE, optimistic versioning, or serializable isolation.

Medium Optimistic versus pessimistic locking?

Pessimistic locks rows up front and blocks others; optimistic checks at write time (version column) and retries on conflict. Optimistic suits low contention.

Medium What is a deadlock and how do you avoid it?

A cycle of transactions each waiting for a lock the other holds. Lock in a consistent order, keep transactions short, and retry when the database aborts one.

Medium What is MVCC?

Multi-version concurrency control keeps several versions of rows so readers see a snapshot and do not block writers, at the cost of cleanup of old versions.

Medium What does SELECT ... FOR UPDATE SKIP LOCKED do?

Locks selected rows and skips rows already locked by others, letting workers claim distinct jobs from a queue table.

Advanced What is write skew?

Two transactions read overlapping data, make decisions on it and write different rows, jointly violating an invariant. Snapshot isolation allows it; serializable, explicit locks or constraints prevent it.

Advanced How do savepoints help?

They allow rolling back part of a transaction, such as handling a duplicate key error and continuing, without aborting everything (essential in PostgreSQL).

Advanced How do you make a transaction safe to retry?

Use idempotency keys with a unique constraint so repeated attempts have no extra effect, and retry on serialization failure, deadlock and timeout with backoff.

Advanced Why do long-running transactions hurt?

They hold locks, block cleanup of old versions causing bloat, and widen conflict windows. Keep them short and never wait on users inside.

Advanced What is the default isolation level in PostgreSQL and MySQL InnoDB?

Read committed in PostgreSQL; repeatable read in InnoDB. SQL Server and Oracle default to read committed.

Advanced What is two-phase commit and why is it avoided across services?

A protocol to commit atomically across multiple resources via prepare and commit phases. It blocks on coordinator failure and couples availability, so sagas are often preferred.
