Python and SQL explained simply: analogies, misconceptions and model answers

When an idea feels slippery, an analogy often makes it click. This page gives one for each core concept in Python and SQL, names the misunderstanding that trips people up, and ends each with a 30-second answer you can say aloud in an interview.

BasicMedium~3 hours

How to use this page

Read the analogy, then try the small experiment. Cover the answer and say it aloud. Good answers say what it is, what problem it solves and one trade-off or pitfall.

Python: how values and names work

Variables are labels, not boxes

Analogy: a name tag stuck on an object. Assigning b = a sticks a second tag on the same object; it does not copy the object. Reassigning a = [9] moves the a tag to a new object and leaves b on the old one. Pitfall: expecting b to be an independent copy. Use copy() or copy.deepcopy() when you need one.

a = [1, 2]
b = a             # two labels on one list
b.append(3)
print("a is", a, "because both names point at the same list")
a = [9]           # moves the label a, leaving b alone
print("after rebinding a:", a, "| b is still", b)

Output

a is [1, 2, 3] because both names point at the same list
after rebinding a: [9] | b is still [1, 2, 3]

Mutable versus immutable

Analogy: an immutable object is a printed photograph (to change it you make a new one); a mutable object is a whiteboard (anyone holding it can erase and rewrite). Why it matters: immutable values (numbers, strings, tuples) are safe to share and can be dictionary keys; mutable ones (lists, dicts, sets) can surprise you when shared, for example as default arguments. Answer: "Immutable objects cannot change after creation, so sharing them is safe and they can be hashed. Mutable objects can change in place, which is convenient but means every name referring to the object sees the change."

Scope: where a name is visible

Analogy: a building with rooms. You look for something in the room you are in first, then the room that contains it, then the whole building, then the city's public library (built-ins). That is LEGB: Local, Enclosing, Global, Built-in.

Functions are objects

Analogy: a recipe card you can hand to someone, store in a drawer or write notes on. Because functions are values, you can pass them as arguments (callbacks, key=), return them (closures) and store them in dictionaries (dispatch tables).

Closures and decorators

Analogy for closures: a function that carries a small backpack of the variables it was created with. Decorator: a gift wrapper: it wraps a function in another function that adds behaviour (timing, caching, access checks) before or after, without changing the original.

import functools, time
def timed(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = fn(*args, **kwargs)
        wrapper.last_seconds = time.perf_counter() - start                     # the "backpack": wrapper remembers fn
        return result
    return wrapper
@timed
def add(a, b): return a + b
print(add(2, 3), "| name preserved by wraps:", add.__name__, "| measured something:", add.last_seconds >= 0)

Output

5 | name preserved by wraps: add | measured something: True

Answer: "A decorator is a function that takes a function and returns a new function that wraps it. @timed above def f means f = timed(f)."

Generators and iterators

Analogy: a printer that prints one page at a time on request instead of printing a thousand pages into a heap first. A generator produces values lazily, one yield at a time, using constant memory, and can only be read once.

def countdown(n):
    while n > 0:
        yield n                 # pause here and hand back one value
        n -= 1
it = countdown(3)
print(next(it), next(it), next(it), "| then:", list(it), "(already exhausted)")

Output

3 2 1 | then: [] (already exhausted)

Exceptions

Analogy: a fire alarm. When something goes wrong, normal flow stops and the alarm travels up through the building (the call stack) until someone (a try/except) handles it. Catch only what you can handle; let the rest rise. finally is the "turn off the stove whatever happened" step. Pitfall: except Exception: pass hides real problems.

Classes and objects

Analogy: a class is a cookie cutter, objects are the cookies. The cutter defines the shape (methods) and each cookie has its own decoration (attributes). Inheritance says "is a kind of"; composition says "has a" and is usually more flexible.

Threads, processes and async

Analogy: a kitchen. Threads are several cooks sharing one stove (in CPython only one holds the stove for Python code at a time, the GIL), fine when most cooks are waiting for deliveries (I/O). Processes are separate kitchens: truly parallel, but ingredients must be shipped between them. asyncio is one very organised cook who starts the pasta water, then chops while it heats, never standing idle: many waiting tasks, one thread. Answer: "Use asyncio or threads for I/O-bound work, processes for CPU-bound work."

How this gets asked

After b = a where a is a list, what does b.append(1) do to a?

  • Nothing No.
  • a also changes, because both names refer to the same list Correct.
  • It raises an error No.
  • a becomes a copy No.

Assignment never copies.

What does a generator hold in memory?

  • All values No.
  • Only its current state, producing one value at a time Correct.
  • A copy of the list No.
  • Nothing at all No.

That is why it handles huge or infinite streams.

Which workload suits threads or asyncio?

  • CPU-bound maths Use processes.
  • I/O-bound waiting (network, disk) Correct.
  • None No.
  • Only GUIs No.

The GIL is released while waiting on I/O.

Self-check

Explain LEGB in a sentence.

Python looks for a name in the local scope, then enclosing functions, then global, then built-ins.

What does @decorator do?

It replaces the function with decorator(function), letting you wrap extra behaviour around it.

SQL: how relational data works

Tables, rows, keys

Analogy: a spreadsheet with rules. Each row is one thing; the primary key is its unique ID card; a foreign key is a reference to another sheet's ID card, and the database refuses a reference to someone who does not exist.

SELECT is a recipe in a fixed order

You write SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY ... LIMIT, but the database thinks in this order: FROM (choose and join tables) -> WHERE (filter rows) -> GROUP BY (make groups) -> HAVING (filter groups) -> SELECT (compute columns) -> ORDER BY -> LIMIT. That is why you cannot use a SELECT alias in WHERE but can in ORDER BY, and why WHERE cannot test an aggregate while HAVING can.

SELECT city, COUNT(*) AS customers        -- 5. compute
FROM customers                              -- 1. take the table
WHERE city IS NOT NULL                      -- 2. filter rows
GROUP BY city                               -- 3. make groups
HAVING COUNT(*) > 1                         -- 4. filter groups
ORDER BY customers DESC, city;              -- 6. sort

Result

citycustomers
London2
Mumbai2
Paris2

Joins

Analogy: matching two lists by a shared ID, like matching guest names with their meal choices. Inner join: only guests found in both lists. Left join: every guest, with the meal if there is one (blank if not). The common mistake is joining on a column with duplicates, which multiplies rows.

NULL

Analogy: a blank on a form meaning "unknown", not "zero" and not "empty". Asking whether two unknowns are equal gives "unknown", not yes. That is three-valued logic: use IS NULL, not = NULL, and remember NOT IN returns nothing if the list contains an unknown.

SELECT NULL = NULL AS equal_to_itself, NULL IS NULL AS is_null, 1 NOT IN (2, NULL) AS not_in_with_null, COALESCE(NULL, 'fallback') AS coalesced;

Result

equal_to_itselfis_nullnot_in_with_nullcoalesced
NULL1NULLfallback

GROUP BY versus window functions

Analogy: a class's test results. GROUP BY produces one summary row per class (the average score per class) and the individual students disappear. A window function keeps every student and adds a column beside each one (their class average, their rank in class).

SELECT name, dept_id, salary,
       ROUND(AVG(salary) OVER (PARTITION BY dept_id)) AS dept_avg,
       RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rank_in_dept
FROM employees WHERE dept_id = 1 ORDER BY rank_in_dept, name;

Result

namedept_idsalarydept_avgrank_in_dept
Alice1150000130000.01
Bob1120000130000.02
Carol1120000130000.02

Index

Analogy: the index at the back of a book. Looking up "photosynthesis" there is quicker than reading every page; but the index takes space and must be updated whenever pages change. A composite index is like an index sorted by surname and then first name: it helps if you know the surname, not if you only know the first name.

Transactions and ACID

Analogy: a bank transfer written on a single sheet: either the whole sheet is filed (both the debit and credit happen) or it is torn up (neither does). Isolation means two clerks working at once do not see each other's half-finished sheets; durability means once filed it survives a power cut.

Normalisation

Analogy: do not write a customer's address on every order slip; write it once on a customer card and refer to the card. Then when the customer moves you correct one card, not hundreds of slips. The reverse (denormalisation) is photocopying the address onto every slip because reading is faster, accepting the burden of keeping copies in sync.

Constraints

Analogy: guard rails on a mountain road. NOT NULL, UNIQUE, CHECK, FOREIGN KEY make invalid data impossible no matter which program writes it, so you do not depend on every application remembering the rules.

Injection and parameters

Analogy: filling a form versus letting someone rewrite the form. With parameters, user input is data inside a box on the form; with string concatenation, the user can write new instructions on the form itself.

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("CREATE TABLE u(name TEXT, pw TEXT); INSERT INTO u VALUES ('ana','s3cret');")
evil = "nobody' OR '1'='1"
print("concatenated :", db.execute("SELECT name FROM u WHERE name = '" + evil + "'").fetchall())
print("parameterised:", db.execute("SELECT name FROM u WHERE name = ?", (evil,)).fetchall())

Output

concatenated : [('ana',)]
parameterised: []

How this gets asked

In SQL's logical processing order, which runs first?

  • SELECT Fifth.
  • WHERE Second.
  • FROM Correct.
  • ORDER BY Last-ish.

FROM and JOIN produce the rows everything else works on.

Why does WHERE x = NULL return nothing?

  • NULL is zero No.
  • NULL means unknown, and a comparison with unknown is unknown, not true; use IS NULL Correct.
  • A syntax error No.
  • NULL is empty text No.

Three-valued logic.

How does a window function differ from GROUP BY?

  • It is slower Not necessarily.
  • It adds a computed column to every row without collapsing rows into groups Correct.
  • It needs no ORDER BY No.
  • It only works on numbers No.

Use it for ranks, running totals and per-group comparisons.

Self-check

WHERE versus HAVING?

WHERE filters rows before grouping; HAVING filters groups after aggregation.

What does an index cost?

Storage and slower writes, in exchange for faster reads on the indexed columns.

Python meets SQL

Why an ORM

Analogy: a translator between two languages. The ORM turns rows into Python objects and method calls into SQL. It saves boilerplate and handles safe parameters, but a translator can say things clumsily (the N+1 problem: one query for the list plus one per item), so read the SQL it generates.

N+1 in a picture

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("CREATE TABLE author(id INT, name TEXT); CREATE TABLE book(id INT, author_id INT, title TEXT);"
                 "INSERT INTO author VALUES (1,'a'),(2,'b'),(3,'c'); INSERT INTO book VALUES (1,1,'x'),(2,1,'y'),(3,2,'z'),(4,3,'w');")
queries = 0
authors = db.execute("SELECT id, name FROM author").fetchall(); queries += 1
for aid, name in authors:                                               # N more queries, one per author
    db.execute("SELECT title FROM book WHERE author_id = ?", (aid,)).fetchall(); queries += 1
print("queries with the N+1 pattern for 3 authors:", queries)
joined = db.execute("SELECT a.name, b.title FROM author a JOIN book b ON b.author_id = a.id").fetchall()
print("queries with one join:", 1, "| rows:", len(joined))

Output

queries with the N+1 pattern for 3 authors: 4
queries with one join: 1 | rows: 4

Connections and pools

Analogy: taxis at a rank. Opening a database connection is like ordering a new taxi from the depot each time (slow). A pool keeps a few taxis waiting; you borrow one, ride, and give it back. Forgetting to give it back (not closing a connection) eventually leaves the rank empty.

How this gets asked

What is the N+1 query problem?

  • A bug in SQL No.
  • One query to fetch a list plus one extra query for each item, instead of a single join or batch Correct.
  • A deadlock No.
  • An index error No.

It multiplies round trips.

Why use parameters instead of string concatenation in SQL?

  • They are shorter No.
  • Input is treated as data, so it cannot change the meaning of the query (no injection) Correct.
  • They are required for SELECT No.
  • They cache results No.

Never put user input into SQL text.

Self-check

What does a connection pool do?

It reuses a fixed set of open connections to avoid the cost of connecting each time and to cap load on the database.

Key idea

Names are labels on objects; functions are values; generators are lazy; exceptions travel up. In SQL, think in the logical order (FROM before SELECT), treat NULL as unknown, keep rows with window functions and summarise with GROUP BY, protect data with constraints and transactions, and always pass values as parameters.

Interview questions: Explained simply

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Explain variables in Python to a beginner.

A variable is a name tag attached to an object; assignment attaches the tag, it does not copy the object.

Basic Explain mutable and immutable.

Immutable objects cannot change after creation, like a printed photo; mutable objects change in place, like a whiteboard that everyone holding it can edit.

Basic Explain a decorator.

A function that takes a function and returns a wrapped version adding behaviour such as timing or caching.

Basic Explain a generator.

A function that yields values one at a time on demand, using little memory and being single-use.

Medium Threads versus processes versus asyncio?

Threads and asyncio suit I/O-bound waiting; processes give true parallelism for CPU-bound work, with the cost of separate memory.

Medium Explain the order SQL evaluates a SELECT.

FROM and joins, WHERE, GROUP BY, HAVING, SELECT expressions, DISTINCT, ORDER BY, then LIMIT.

Medium Explain NULL.

NULL means unknown, so comparisons with it are unknown rather than true or false; use IS NULL and be careful with NOT IN.

Medium Window function versus GROUP BY?

GROUP BY collapses rows into one per group; a window function keeps all rows and adds a computed column.

Medium What is an index in plain words?

A sorted lookup structure like a book index that finds rows quickly at the cost of space and slower writes.

Medium What is a transaction in plain words?

A bundle of changes that all happen or none happen, isolated from others and durable once committed.

Medium Why normalise?

To store each fact once so updates are made in one place and contradictions cannot arise.

Advanced What is SQL injection and how is it prevented?

Attacker input altering the query's meaning when concatenated into SQL; prevented by parameterised queries and least-privilege accounts.

Advanced What is the N+1 problem?

Running one query for a list and one more per item; fix with a join, batch query or eager loading.

Advanced Why use a connection pool?

Opening connections is expensive; pools reuse a bounded set of connections, improving latency and protecting the database.
