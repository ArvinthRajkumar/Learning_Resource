Using SQL from Python: DB-API, transactions, ORMs, pandas and pipelines

SQL answers questions; Python glues the answers into programs. This part shows how the two work together correctly: safe queries, transactions that actually commit and roll back, efficient batches, ORMs and when to use them, and how to test database code.

MediumAdvanced~5 hours

The DB-API and sqlite3

One interface, many databases

Python defines a standard database interface, DB-API 2.0 (PEP 249). Every driver follows it: sqlite3 (built in), psycopg (PostgreSQL), mysqlclient and PyMySQL (MySQL), pyodbc (SQL Server), oracledb (Oracle). The core objects are the same: a connection, a cursor, execute, fetch*, commit, rollback. Only the connection string and the parameter placeholder style (?, %s, :name) differ.

First program

import sqlite3

con = sqlite3.connect(":memory:")            # a database held in memory (use a filename for a file)
cur = con.cursor()
cur.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL, age INTEGER)")
cur.execute("INSERT INTO users (name, age) VALUES (?, ?)", ("Ada", 36))
cur.executemany("INSERT INTO users (name, age) VALUES (?, ?)", [("Ben", 25), ("Cy", 41)])
con.commit()

cur.execute("SELECT id, name, age FROM users WHERE age > ? ORDER BY age", (30,))
print(cur.fetchall())
print(cur.description[0][0], "|", cur.rowcount)
cur.execute("SELECT COUNT(*) FROM users")
print(cur.fetchone()[0])
con.close()

Output

[(1, 'Ada', 36), (3, 'Cy', 41)]
id | -1
3

Fetching: fetchone() (one row or None), fetchmany(n), fetchall() (everything in memory). A cursor is also iterable, which streams rows and is best for big results: for row in cur.execute(...).

Named rows

import sqlite3
con = sqlite3.connect(":memory:")
con.row_factory = sqlite3.Row                 # rows behave like dicts and tuples
con.execute("CREATE TABLE t (a INTEGER, b TEXT)")
con.execute("INSERT INTO t VALUES (1, 'x'), (2, 'y')")
for row in con.execute("SELECT a, b FROM t ORDER BY a"):
    print(row["a"], row["b"], tuple(row), dict(row))

Output

1 x (1, 'x') {'a': 1, 'b': 'x'}
2 y (2, 'y') {'a': 2, 'b': 'y'}

Types

sqlite3 maps None/NULL, int, float, str, bytes automatically. Dates and decimals need explicit handling: store ISO strings or use adapters. Other drivers map date, datetime, Decimal and JSON natively.

import sqlite3, datetime, json
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE ev (at TEXT, payload TEXT)")
now = datetime.datetime(2024, 3, 5, 12, 0, tzinfo=datetime.timezone.utc)
con.execute("INSERT INTO ev VALUES (?, ?)", (now.isoformat(), json.dumps({"k": [1, 2]})))
at, payload = con.execute("SELECT at, payload FROM ev").fetchone()
print(datetime.datetime.fromisoformat(at).year, json.loads(payload)["k"])

Output

2024 [1, 2]

Parameters and SQL injection

The most important rule

Never build SQL by joining strings with user input. An attacker supplies text that changes the query. This is SQL injection, one of the most common and damaging vulnerabilities.

import sqlite3
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE users (name TEXT, secret TEXT)")
con.execute("INSERT INTO users VALUES ('ada', 's3cret'), ('ben', 'hunter2')")

user_input = "nobody' OR '1'='1"

unsafe = "SELECT name, secret FROM users WHERE name = '%s'" % user_input
print("UNSAFE query text:", unsafe)
print("unsafe rows leaked:", con.execute(unsafe).fetchall())

safe_rows = con.execute("SELECT name, secret FROM users WHERE name = ?", (user_input,)).fetchall()
print("safe rows:", safe_rows)

Output

UNSAFE query text: SELECT name, secret FROM users WHERE name = 'nobody' OR '1'='1'
unsafe rows leaked: [('ada', 's3cret'), ('ben', 'hunter2')]
safe rows: []

With parameter binding the SQL text and the values travel separately; the database never parses the value as SQL. Placeholders: ? (sqlite3), %s (psycopg, MySQL), :name or %(name)s (named style).

import sqlite3
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE t (a INTEGER, b TEXT)")
con.execute("INSERT INTO t VALUES (:a, :b)", {"a": 1, "b": "one"})
ids = [1, 2, 3]
placeholders = ", ".join("?" * len(ids))          # build placeholders, not values
print(con.execute(f"SELECT {placeholders} AS expanded", ids).fetchall())

Output

[(1, 2, 3)]

What cannot be a parameter

Placeholders replace values only, not identifiers (table or column names), keywords, or ORDER BY direction. If you must choose these dynamically, map user input through an allow-list.

ALLOWED_SORT = {"name": "name", "age": "age"}
def order_clause(user_col, direction):
    col = ALLOWED_SORT[user_col]                 # KeyError for anything unexpected
    d = "DESC" if direction == "desc" else "ASC"
    return f"ORDER BY {col} {d}"
print(order_clause("age", "desc"))
try:
    order_clause("age; DROP TABLE users", "asc")
except KeyError:
    print("rejected")

Output

ORDER BY age DESC
rejected

Also: give the application a least-privilege database account, and escape LIKE wildcards when searching for literal text.

Bind values as parameters so they are never parsed as SQL.

Can you bind a table name as a parameter?

  • Yes, always No.
  • No: placeholders are for values; map identifiers through an allow-list Correct.
  • Only in SQLite No.
  • Only for SELECT No.

Identifiers and keywords cannot be parameters.

Transactions from Python

Commit and rollback

Changes are not permanent until you commit. Use the connection as a context manager: it commits on success and rolls back if an exception occurs (it does not close the connection).

import sqlite3
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE acct (name TEXT PRIMARY KEY, bal INTEGER NOT NULL CHECK (bal >= 0))")
con.executemany("INSERT INTO acct VALUES (?, ?)", [("alice", 100), ("bob", 20)])
con.commit()

def transfer(src, dst, amount):
    with con:                                        # one transaction
        con.execute("UPDATE acct SET bal = bal - ? WHERE name = ?", (amount, src))
        con.execute("UPDATE acct SET bal = bal + ? WHERE name = ?", (amount, dst))

transfer("alice", "bob", 30)
print(con.execute("SELECT * FROM acct ORDER BY name").fetchall())
try:
    transfer("alice", "bob", 500)                     # violates CHECK, whole transaction rolls back
except sqlite3.IntegrityError as e:
    print("failed:", e)
print(con.execute("SELECT * FROM acct ORDER BY name").fetchall())

Output

[('alice', 70), ('bob', 50)]
failed: CHECK constraint failed: bal >= 0
[('alice', 70), ('bob', 50)]

Good habits

  • Keep transactions short: do slow work (HTTP calls, user input) outside them.
  • One logical operation = one transaction. Do not commit after every statement in a loop unless you must.
  • Retry on serialisation failures and deadlocks (with backoff).
  • Do not share a connection between threads unless the driver says it is safe; use one connection per thread or a pool.
  • Use try/finally or with to guarantee connections are closed.
import sqlite3
from contextlib import closing
with closing(sqlite3.connect(":memory:")) as con, con:      # closes the connection AND commits
    con.execute("CREATE TABLE x (v INTEGER)")
    con.execute("INSERT INTO x VALUES (1)")
    print(con.execute("SELECT * FROM x").fetchall())

Output

[(1,)]

How this gets asked

What does with con: do for a sqlite3 connection?

  • Closes the connection It does not close it.
  • Commits on success, rolls back on exception Correct.
  • Starts a new database No.
  • Locks the file forever No.

Use contextlib.closing as well if you also want it closed.

Self-check

How do you make a transfer atomic from Python?

Run both updates inside one transaction (with con:) so any error rolls everything back.

Efficient access patterns

Bulk inserts

Send many rows in one call and one transaction. This can be 10 to 100 times faster than inserting one by one with a commit each time.

import sqlite3, time
rows = [(i, f"user{i}") for i in range(20000)]

def one_by_one():
    con = sqlite3.connect(":memory:")
    con.execute("CREATE TABLE u (id INTEGER, name TEXT)")
    for r in rows[:2000]:
        con.execute("INSERT INTO u VALUES (?, ?)", r)
        con.commit()                                   # commit per row: slow on a real disk
    return time.perf_counter()

def bulk():
    con = sqlite3.connect(":memory:")
    con.execute("CREATE TABLE u (id INTEGER, name TEXT)")
    with con:
        con.executemany("INSERT INTO u VALUES (?, ?)", rows)
    return con.execute("SELECT COUNT(*) FROM u").fetchone()[0]

print(bulk(), "rows inserted with executemany")

Output

20000 rows inserted with executemany

For very large loads use the database's bulk path: PostgreSQL COPY, MySQL LOAD DATA, SQL Server BULK INSERT.

The N+1 query problem

Fetching a list, then running one query per item, turns one logical read into N+1 round trips. Over a network each costs about 1 ms or more.

import sqlite3
con = sqlite3.connect(":memory:")
con.executescript("""
CREATE TABLE author (id INTEGER PRIMARY KEY, name TEXT);
CREATE TABLE book (id INTEGER PRIMARY KEY, author_id INTEGER, title TEXT);
INSERT INTO author VALUES (1,'Ada'),(2,'Ben'),(3,'Cy');
INSERT INTO book VALUES (1,1,'A1'),(2,1,'A2'),(3,2,'B1'),(4,3,'C1'),(5,3,'C2');
""")
count = [0]
con.set_trace_callback(lambda sql: count.__setitem__(0, count[0] + 1))

# N+1: one query for authors, then one per author
for a_id, name in con.execute("SELECT id, name FROM author").fetchall():
    con.execute("SELECT title FROM book WHERE author_id = ?", (a_id,)).fetchall()
print("N+1 queries:", count[0])

count[0] = 0
rows = con.execute("SELECT a.name, b.title FROM author a JOIN book b ON b.author_id = a.id").fetchall()
print("single join queries:", count[0], len(rows), "rows")

Output

N+1 queries: 4
single join queries: 1 5 rows

Fixes: a join, an IN (...) batch, or in an ORM eager loading (joinedload, selectinload, Django select_related and prefetch_related). Detect with query logging and tests that count queries.

Streaming large results

import sqlite3
con = sqlite3.connect(":memory:")
con.execute("CREATE TABLE big (n INTEGER)")
con.executemany("INSERT INTO big VALUES (?)", ((i,) for i in range(100000)))
total = 0
for (n,) in con.execute("SELECT n FROM big"):            # iterates lazily instead of fetchall()
    total += n
print(total)
cur = con.execute("SELECT n FROM big ORDER BY n")
while batch := cur.fetchmany(25000):
    print(len(batch), batch[0][0])

Output

4999950000
25000 0
25000 25000
25000 50000
25000 75000

Server-side cursors (PostgreSQL named cursors) avoid loading the whole result into the client.

How this gets asked

What is the N+1 query problem?

  • A query with N joins No.
  • One query for a list followed by one query per item Correct.
  • A sorting problem No.
  • A transaction deadlock No.

Replace with a join, a batched IN query or eager loading.

An API returns 50 orders and runs one extra query per order for its customer. How many queries run in total?

1 query for the list plus 50 per-order queries = 51.

Self-check

How do you speed up inserting many rows?

executemany (or the database's bulk COPY/LOAD) in a single transaction.

ORMs and query builders

Layers of abstraction

LayerExampleTrade-off
Raw SQL with a driversqlite3, psycopgFull control, manual mapping
Query builderSQLAlchemy Core, pypikaComposable SQL in Python, dialect-aware
ORMSQLAlchemy ORM, Django ORM, PeeweeRows as objects, relationships, migrations; hides SQL

An ORM (object-relational mapper) maps classes to tables and objects to rows. It saves boilerplate and handles relationships, but it can generate inefficient SQL (N+1), hides what runs, and does not remove the need to understand SQL. Look at the SQL it emits.

SQLAlchemy 2.x (display only: needs pip install sqlalchemy)

from sqlalchemy import create_engine, select, ForeignKey, String
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column, relationship, Session, selectinload

class Base(DeclarativeBase): pass

class Author(Base):
    __tablename__ = "author"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50))
    books: Mapped[list["Book"]] = relationship(back_populates="author")

class Book(Base):
    __tablename__ = "book"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str]
    author_id: Mapped[int] = mapped_column(ForeignKey("author.id"))
    author: Mapped[Author] = relationship(back_populates="books")

engine = create_engine("sqlite:///:memory:", echo=True)     # echo=True prints the SQL
Base.metadata.create_all(engine)

with Session(engine) as session, session.begin():           # one transaction
    session.add(Author(name="Ada", books=[Book(title="A1"), Book(title="A2")]))

with Session(engine) as session:
    stmt = select(Author).options(selectinload(Author.books)).where(Author.name == "Ada")
    for author in session.scalars(stmt):
        print(author.name, [b.title for b in author.books])  # no N+1: books loaded in one extra query

Key ideas: an engine (connection pool plus dialect), a session (a unit of work that tracks changes and flushes them in a transaction), lazy versus eager loading, and migrations with Alembic.

SQLAlchemy Core (SQL expression language)

from sqlalchemy import create_engine, text
engine = create_engine("postgresql+psycopg://user:pass@localhost/shop")
with engine.begin() as conn:                                  # begin() commits on success
    rows = conn.execute(text("SELECT id, name FROM customers WHERE city = :city"), {"city": "London"})
    for row in rows:
        print(row.id, row.name)

Django ORM flavour

orders = Order.objects.filter(status="paid").select_related("customer").prefetch_related("items")
total = Order.objects.filter(status="paid").aggregate(Sum("amount"))

When to use what

Use an ORM for ordinary create, read, update, delete and relationships in application code. Drop to SQL (through the ORM's text interface or views) for reporting, complex window queries and bulk operations. Keep business rules in code and integrity rules in the database.

How this gets asked

What is a reasonable way to use an ORM?

  • Never look at the SQL it generates Dangerous.
  • Use it for routine CRUD, inspect the SQL, and drop to SQL for complex reports Correct.
  • Use it for everything including bulk loads Often slow.
  • Avoid learning SQL You still need it.

ORMs save boilerplate but do not replace SQL knowledge.

pandas and analytics

Reading SQL into a DataFrame (display only: needs pip install pandas)

import pandas as pd, sqlite3
con = sqlite3.connect("shop.db")
df = pd.read_sql_query(
    "SELECT o.order_date, p.category, i.qty * p.price AS revenue "
    "FROM orders o JOIN order_items i ON i.order_id = o.id JOIN products p ON p.id = i.product_id "
    "WHERE o.status = ?", con, params=("paid",), parse_dates=["order_date"])
monthly = df.groupby([df.order_date.dt.to_period("M"), "category"])["revenue"].sum().unstack(fill_value=0)
monthly.to_sql("monthly_revenue", con, if_exists="replace")  # write results back

Guideline: filter and aggregate in SQL (the database is built for it and sends less data); use pandas for what SQL does badly (complex reshaping, statistics, plotting, machine learning). Pass parameters, do not f-string values. For big data prefer chunked reads (chunksize=) or tools such as DuckDB and Polars.

DuckDB: SQL over files

DuckDB queries CSV and Parquet files and DataFrames with SQL, in process, with no server: duckdb.sql("SELECT category, SUM(revenue) FROM 'sales.parquet' GROUP BY 1").

Connections, pools, migrations and async

Connection pooling

Opening a database connection is expensive (network, authentication, memory on the server). A pool keeps connections open and lends them out. Size it from the database's limit and your concurrency; too many connections hurt the database. In web services use the framework's pool (SQLAlchemy QueuePool, psycopg_pool) and an external pooler (PgBouncer) in front of PostgreSQL for many app instances. Always return connections (with blocks) and set timeouts.

Migrations

Schema changes should be versioned code, applied in order, in every environment: Alembic (SQLAlchemy), Django migrations, Flyway, Liquibase, sqitch. A migration has an upgrade and ideally a downgrade. A minimal version of the idea:

import sqlite3
MIGRATIONS = [
    ("001_create_users", "CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL)"),
    ("002_add_email", "ALTER TABLE users ADD COLUMN email TEXT"),
    ("003_email_index", "CREATE INDEX idx_users_email ON users(email)"),
]

def migrate(con):
    con.execute("CREATE TABLE IF NOT EXISTS schema_migrations (version TEXT PRIMARY KEY)")
    done = {v for (v,) in con.execute("SELECT version FROM schema_migrations")}
    for version, sql in MIGRATIONS:
        if version not in done:
            with con:
                con.execute(sql)
                con.execute("INSERT INTO schema_migrations VALUES (?)", (version,))
            print("applied", version)

con = sqlite3.connect(":memory:")
migrate(con)
migrate(con)                       # second run applies nothing: idempotent
print([r[0] for r in con.execute("SELECT version FROM schema_migrations ORDER BY version")])

Output

applied 001_create_users
applied 002_add_email
applied 003_email_index
['001_create_users', '002_add_email', '003_email_index']

Make migrations backward compatible (expand and contract, see SD11) and test them against a copy of production data.

Async database access

For asyncio programs (PY4) use async drivers so queries do not block the loop: asyncpg or psycopg async mode for PostgreSQL, aiosqlite, aiomysql, SQLAlchemy's AsyncSession.

import asyncpg, asyncio
async def main():
    pool = await asyncpg.create_pool("postgresql://user:pass@localhost/shop", min_size=2, max_size=10)
    async with pool.acquire() as conn:
        async with conn.transaction():
            rows = await conn.fetch("SELECT id, name FROM customers WHERE city = $1", "London")
    print([dict(r) for r in rows])
asyncio.run(main())

(PostgreSQL drivers use $1 or %s placeholders, never string formatting.)

How this gets asked

Why use a connection pool?

  • To avoid transactions No.
  • Opening connections is expensive, so reuse them and cap the total Correct.
  • To encrypt data No.
  • To avoid indexes No.

Pools improve latency and protect the database from too many connections.

Test with the same engine you run in production for anything beyond trivial queries. Wrap each test in a transaction and roll back, or create a fresh schema per test.

import sqlite3, unittest, io

def create_user(con, name):
    with con:
        cur = con.execute("INSERT INTO users (name) VALUES (?)", (name,))
    return cur.lastrowid

def count_users(con):
    return con.execute("SELECT COUNT(*) FROM users").fetchone()[0]

class UserRepoTest(unittest.TestCase):
    def setUp(self):                                  # fresh database for every test
        self.con = sqlite3.connect(":memory:")
        self.con.execute("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT UNIQUE NOT NULL)")
    def tearDown(self):
        self.con.close()
    def test_create(self):
        uid = create_user(self.con, "ada")
        self.assertEqual(uid, 1)
        self.assertEqual(count_users(self.con), 1)
    def test_unique_name(self):
        create_user(self.con, "ada")
        with self.assertRaises(sqlite3.IntegrityError):
            create_user(self.con, "ada")
        self.assertEqual(count_users(self.con), 1)

suite = unittest.defaultTestLoader.loadTestsFromTestCase(UserRepoTest)
res = unittest.TextTestRunner(stream=io.StringIO()).run(suite)
print("tests run:", res.testsRun, "failures:", len(res.failures) + len(res.errors))

Output

tests run: 2 failures: 0

Also test: constraint violations, concurrent updates (optimistic locking), migrations up and down, and query counts (guard against N+1).

A small ETL pipeline

ETL means extract data from a source, transform it, load it into a destination. Here: parse CSV text, clean it, load into SQLite with a transaction, and report with SQL.

import csv, io, sqlite3
from datetime import date

RAW = """order_id,customer,amount,order_date
1,Ada,120.50,2024-01-05
2,Ben,80,2024-01-07
3,Ada,,2024-02-01
4,Cy,45.25,2024-02-10
2,Ben,80,2024-01-07
5,Dev,300,not-a-date
"""

def extract(text):
    return list(csv.DictReader(io.StringIO(text)))

def transform(rows):
    seen, good, bad = set(), [], []
    for r in rows:
        try:
            if r["order_id"] in seen:
                continue                                  # drop duplicates
            amount = float(r["amount"])                   # empty string raises ValueError
            day = date.fromisoformat(r["order_date"])
            seen.add(r["order_id"])
            good.append((int(r["order_id"]), r["customer"].strip().title(), round(amount, 2), day.isoformat()))
        except ValueError as e:
            bad.append((r["order_id"], str(e)))
    return good, bad

def load(con, rows):
    con.execute("CREATE TABLE IF NOT EXISTS orders (order_id INTEGER PRIMARY KEY, customer TEXT, amount REAL, order_date TEXT)")
    with con:
        con.executemany("INSERT OR REPLACE INTO orders VALUES (?, ?, ?, ?)", rows)   # idempotent reload

good, bad = transform(extract(RAW))
con = sqlite3.connect(":memory:")
load(con, good); load(con, good)                           # running twice changes nothing
print("loaded", len(good), "rejected", len(bad))
for order_id, reason in bad:
    print("  rejected order", order_id)
print(con.execute("""SELECT customer, SUM(amount) AS total, COUNT(*) AS n
                     FROM orders GROUP BY customer ORDER BY total DESC""").fetchall())

Output

loaded 3 rejected 2
  rejected order 3
  rejected order 5
[('Ada', 120.5, 1), ('Ben', 80.0, 1), ('Cy', 45.25, 1)]

Pipeline principles: idempotent loads (safe to re-run), validate and quarantine bad rows instead of crashing or silently dropping them, load in transactions, keep raw data for reprocessing, add data quality checks and logging, and orchestrate with a scheduler (cron, Airflow, Dagster) with retries. See SD12 for warehouses and streaming.

How this gets asked

Idempotent loads make retries and re-runs safe.

Interview questions: Python with SQL

10 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic How do you run a safe query from Python?

Use parameter placeholders: cursor.execute('SELECT ... WHERE id = ?', (id,)). Never concatenate or format user input into SQL.

Basic What is SQL injection?

An attack where user input is interpreted as SQL. Prevent with parameterised queries, allow-listed identifiers and least-privilege accounts.

Medium How do you make a multi-statement change atomic in Python?

Run the statements in one transaction: with connection: ... commits on success and rolls back on exception.

Medium What is the N+1 query problem?

One query for a list plus one per item. Fix with a join, an IN batch or ORM eager loading (selectinload, joinedload, select_related, prefetch_related).

Medium How do you insert many rows efficiently?

executemany in a single transaction, or the database's bulk loader (COPY, LOAD DATA) for very large loads.

Medium ORM versus raw SQL?

ORMs reduce boilerplate and manage relationships and migrations but can hide inefficient SQL. Use them for routine CRUD and raw SQL for complex reports and bulk work.

Medium What is a connection pool?

A set of reusable open connections shared by requests, avoiding the cost of reconnecting and capping load on the database.

Advanced How do you do database migrations safely?

Version every change, apply in order with a tool (Alembic, Django, Flyway), make changes backward compatible (expand then contract) and test on production-like data.

Advanced How do you test database code?

Use a real engine (a container or in-memory SQLite for simple cases), fresh schema or rolled-back transaction per test, and test constraints, concurrency and query counts.

Advanced When to use pandas versus SQL?

Filter, join and aggregate in SQL near the data; use pandas for reshaping, statistics and visualisation on the smaller result. Use chunking, DuckDB or Polars for large data.
