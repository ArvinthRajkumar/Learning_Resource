Part SQL11

Inside the query optimiser: join algorithms, cost estimates, statistics and index structures

Part SQL4 showed how to read plans and fix slow queries. This part explains why the plans look the way they do: the algorithms underneath, the arithmetic of cost estimation and the way statistics steer choices. Knowing this makes tuning predictable instead of trial and error.

Advanced~5 hours

From SQL text to results

A plan is a tree of operators: scans at the leaves (read a table or an index), joins, filters, aggregations and sorts above. Rows flow upward. Execution commonly follows the iterator (Volcano) model: each operator exposes next() which asks its children for rows.

Join algorithms

Joining tables R (n rows) and S (m rows) on equality can use three classic algorithms. Each is cheap in one situation and expensive in another.

AlgorithmIdeaCostBest when
Nested loopFor each row of R, scan S for matchesO(n x m), or O(n log m) with an index on SSmall outer side and an index on the inner join column
Hash joinBuild a hash table on the smaller side, probe it with the otherO(n + m) memory for the hash tableLarge unsorted inputs, equality joins
Merge (sort-merge) joinSort both on the key, walk them togetherO(n log n + m log m), or O(n + m) if already sortedInputs already ordered (index order), range or very large joins
 
import random
random.seed(1)
R = [(i, f"r{i}") for i in random.sample(range(10_000), 2_000)]          # (key, payload)
S = [(i, f"s{i}") for i in random.sample(range(10_000), 3_000)]
def nested_loop(R, S):
    out, comparisons = [], 0
    for rk, rv in R:
        for sk, sv in S:
            comparisons += 1
            if rk == sk: out.append((rk, rv, sv))
    return out, comparisons
def hash_join(R, S):
    table, out, ops = {}, [], 0
    for sk, sv in S: table.setdefault(sk, []).append(sv); ops += 1                 # build on one side
    for rk, rv in R:
        ops += 1
        for sv in table.get(rk, ()): out.append((rk, rv, sv))                        # probe with the other
    return out, ops
def merge_join(R, S):
    R, S = sorted(R), sorted(S); i = j = ops = 0; out = []
    while i < len(R) and j < len(S):
        ops += 1
        if R[i][0] < S[j][0]: i += 1
        elif R[i][0] > S[j][0]: j += 1
        else:
            out.append((R[i][0], R[i][1], S[j][1])); i += 1; j += 1                     # keys are unique here
    return out, ops
nl, c1 = nested_loop(R, S); hj, c2 = hash_join(R, S); mj, c3 = merge_join(R, S)
print("all three return the same rows:", sorted(nl) == sorted(hj) == sorted(mj), "| result size:", len(hj))
print(f"basic operations: nested loop {c1:,} | hash join {c2:,} | merge join {c3:,} (after sorting)")

Output

all three return the same rows: True | result size: 602
basic operations: nested loop 6,000,000 | hash join 5,000 | merge join 4,395 (after sorting)

Six million comparisons versus five thousand: that is why the choice matters. With an index on S(key), nested loop does one index lookup per outer row (n log m) and wins when the outer side is tiny, such as joining one customer to their orders.

Join order

For A JOIN B JOIN C there are many orders (n! for n tables), and an early huge intermediate result ruins everything. Optimisers search by dynamic programming (or heuristics for many tables) preferring plans that filter early and keep intermediate results small. Statistics decide which side is "small".

How this gets asked

When is a nested loop join the right choice?

  • Always No.
  • When the outer side is tiny and the inner side has an index on the join column Correct.
  • For very large unindexed tables Quadratic.
  • Only for range joins No.

Each outer row costs one index lookup.

A hash join needs:

  • Sorted inputs That is merge join.
  • Memory for a hash table on the smaller input, and an equality condition Correct.
  • An index No.
  • A cross product No.

Build on the small side, probe with the big side.

Self-check

Compare the three join algorithms in one line each.

Nested loop probes per outer row (good with an index), hash join builds a table on one side, merge join walks two sorted inputs together.

Cost estimation and statistics

The optimiser estimates the number of rows each operator returns (cardinality), then multiplies by per-row I/O and CPU cost. It gets cardinalities from statistics:

  • Table row count and page count.
  • For each column: number of distinct values, fraction of NULLs, minimum and maximum, most common values (MCV) with frequencies, and a histogram of the rest.
  • Selectivity is the fraction of rows a predicate keeps: col = value is about 1 / distinct_values; a range uses the histogram; AND multiplies selectivities (assuming independence), OR adds them.
import random, bisect
random.seed(3)
n = 100_000
country = random.choices(["IN", "US", "DE", "BR", "XX"], weights=[50, 30, 12, 7, 1], k=n)       # skewed distribution
age = [min(90, max(18, int(random.gauss(40, 12)))) for _ in range(n)]
distinct = len(set(country))
est_naive = n / distinct                                                                         # assumes a uniform distribution
actual_in = country.count("IN"); actual_xx = country.count("XX")
mcv = {c: country.count(c) / n for c in set(country)}                                             # what MCV statistics store
print(f"country = 'IN': naive estimate {est_naive:,.0f} | MCV estimate {mcv['IN'] * n:,.0f} | actual {actual_in:,}")
print(f"country = 'XX': naive estimate {est_naive:,.0f} | MCV estimate {mcv['XX'] * n:,.0f} | actual {actual_xx:,}")
sel_age = sum(1 for a in age if a >= 60) / n
sel_both_indep = mcv["IN"] * sel_age
actual_both = sum(1 for c, a in zip(country, age) if c == "IN" and a >= 60) / n
print(f"IN and age >= 60: independence estimate {sel_both_indep * n:,.0f} vs actual {actual_both * n:,.0f} (columns are independent here, so they agree)")

Output

country = 'IN': naive estimate 20,000 | MCV estimate 50,186 | actual 50,186
country = 'XX': naive estimate 20,000 | MCV estimate 970 | actual 970
IN and age >= 60: independence estimate 2,415 vs actual 2,381 (columns are independent here, so they agree)

When columns are correlated (city and country, make and model) the independence assumption underestimates, producing a bad plan. Remedies: extended statistics on column groups, rewriting the query, or hints as a last resort.

Seek versus scan

Reading many rows through an index is slower than a sequential scan: each index entry may mean a random page read. Rule of thumb: an index helps when the predicate keeps only a small fraction of the rows, from about 1 or 2% on spinning disks up to roughly 10% on fast SSDs. The toy cost model below breaks even between 1% and 5%. The optimiser compares the cost of both and may legitimately ignore your index.

def cost_seq_scan(pages, cpu_per_row=0.01, rows=0): return pages * 1.0 + rows * cpu_per_row
def cost_index(selected_rows, tree_height=3): return tree_height + selected_rows * 1.0 + selected_rows * 0.01   # about one random page per row
table_pages, table_rows = 10_000, 1_000_000
for pct in (0.001, 0.01, 0.1, 1, 5, 20):
    sel = int(table_rows * pct / 100)
    seq, idx = cost_seq_scan(table_pages, rows=table_rows), cost_index(sel)
    print(f"keeps {pct:>6}% of rows ({sel:>7,}): scan cost {seq:>9,.0f} vs index cost {idx:>9,.0f} -> {'index' if idx < seq else 'scan'}")

Output

keeps  0.001% of rows (     10): scan cost    20,000 vs index cost        13 -> index
keeps   0.01% of rows (    100): scan cost    20,000 vs index cost       104 -> index
keeps    0.1% of rows (  1,000): scan cost    20,000 vs index cost     1,013 -> index
keeps      1% of rows ( 10,000): scan cost    20,000 vs index cost    10,103 -> index
keeps      5% of rows ( 50,000): scan cost    20,000 vs index cost    50,503 -> scan

How this gets asked

What is selectivity?

  • The speed of a query No.
  • The fraction of rows a predicate keeps Correct.
  • Index size No.
  • The number of tables No.

Lower selectivity fraction means fewer rows and favours an index.

Why might the optimiser ignore an index?

  • It is broken Rarely.
  • The predicate keeps a large fraction of rows, so a sequential scan is cheaper than many random lookups Correct.
  • Indexes are optional No.
  • Statistics are always right No.

Compare estimated costs, not just availability.

Self-check

What statistics does the optimiser keep?

Row counts, distinct counts, null fractions, min and max, most common values and histograms.

Seeing the plan with real statistics

SQLite shows the same decision. Before gathering statistics it guesses; after ANALYZE it uses data distributions.

CREATE TABLE t (id INTEGER PRIMARY KEY, status TEXT, user_id INT, created TEXT);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 20000)
INSERT INTO t SELECT i, CASE WHEN i % 1000 = 0 THEN 'rare' ELSE 'common' END, i % 500, date('2024-01-01', '+' || (i % 365) || ' days') FROM n;
CREATE INDEX idx_status ON t(status);
ANALYZE;
EXPLAIN QUERY PLAN SELECT * FROM t WHERE status = 'rare';

Result

plan
SEARCH t USING INDEX idx_status (status=?)

Here SQLite chooses the index for both values: it has only coarse statistics, and the index is still a reasonable plan. An engine that keeps most-common-value lists and histograms (PostgreSQL) knows that 'common' matches about 99.9% of the rows and picks a sequential scan for it, while using the index for the rare value. If estimates drift from reality because statistics are stale after a big load, the plan degrades: run ANALYZE (or VACUUM ANALYZE) after bulk changes and compare EXPLAIN ANALYZE actual rows with estimated rows; a large mismatch is the first thing to investigate.

Composite index order

A B-tree on (a, b, c) is sorted by a, then b within a, then c. It can serve: a = ?, a = ? AND b = ?, a = ? AND b > ?, and ORDER BY a, b. It cannot efficiently serve a filter on b alone (no leading column). Put equality columns first, then the range or sort column; among equality columns put the more selective first unless sorting dictates otherwise.

CREATE TABLE ev (id INTEGER PRIMARY KEY, user_id INT, kind TEXT, ts TEXT, payload TEXT);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 5000)
INSERT INTO ev SELECT i, i % 100, CASE i % 3 WHEN 0 THEN 'view' WHEN 1 THEN 'click' ELSE 'buy' END, date('2024-01-01', '+' || (i % 200) || ' days'), 'x' FROM n;
CREATE INDEX idx_user_kind_ts ON ev(user_id, kind, ts);
EXPLAIN QUERY PLAN SELECT * FROM ev WHERE user_id = 7 AND kind = 'buy' AND ts >= '2024-03-01';
EXPLAIN QUERY PLAN SELECT * FROM ev WHERE kind = 'buy';
EXPLAIN QUERY PLAN SELECT user_id, kind, ts FROM ev WHERE user_id = 7;

Result

plan
SEARCH ev USING INDEX idx_user_kind_ts (user_id=? AND kind=? AND ts>?)
plan
SCAN ev
plan
SEARCH ev USING COVERING INDEX idx_user_kind_ts (user_id=?)

The first query uses all three columns, the second cannot use the index to seek (no leading user_id), and the third is covered: every column it needs lives in the index, so the table is never touched ("COVERING INDEX").

Covering, partial and expression indexes

  • Covering index: includes all columns a query reads, avoiding table lookups (INCLUDE columns in PostgreSQL and SQL Server).
  • Partial index: CREATE INDEX ... WHERE status = 'open' indexes only the interesting rows: smaller and faster for "open tickets".
  • Expression index: CREATE INDEX ON users (lower(email)) serves WHERE lower(email) = ?.
  • Unique index enforces a constraint and helps the optimiser.
CREATE TABLE ticket (id INTEGER PRIMARY KEY, status TEXT, email TEXT);
WITH RECURSIVE n(i) AS (SELECT 1 UNION ALL SELECT i + 1 FROM n WHERE i < 3000)
INSERT INTO ticket SELECT i, CASE WHEN i % 50 = 0 THEN 'open' ELSE 'closed' END, 'User' || i || '@Example.com' FROM n;
CREATE INDEX idx_open ON ticket(id) WHERE status = 'open';
CREATE INDEX idx_email_lower ON ticket(lower(email));
EXPLAIN QUERY PLAN SELECT id FROM ticket WHERE status = 'open' ORDER BY id;
EXPLAIN QUERY PLAN SELECT * FROM ticket WHERE lower(email) = 'user42@example.com';

Result

plan
SCAN ticket USING COVERING INDEX idx_open
plan
SEARCH ticket USING INDEX idx_email_lower (<expr>=?)

How this gets asked

With an index on (a, b, c), which query cannot seek on it?

  • WHERE a = 1 Uses it.
  • WHERE a = 1 AND b = 2 Uses it.
  • WHERE b = 2 AND c = 3 Correct: there is no leading column a.
  • WHERE a = 1 ORDER BY b Uses it.

A composite B-tree is sorted by its leading column first.

What is a covering index?

  • An index on every column No.
  • An index containing every column a query needs, so no table lookup is required Correct.
  • A hash index No.
  • A unique index No.

The plan shows COVERING INDEX.

Self-check

Where do the range column and sort column go in a composite index?

After the equality columns, because equality columns narrow to a contiguous slice that is then ordered by the next column.

Sargable predicates and rewrites

A predicate is sargable (Search ARGument ABLE) when the engine can use an index to seek. Wrapping the column in a function, adding to it, or comparing with a leading wildcard usually makes it non-sargable; move the work to the other side.

Why good plans go bad

  1. Stale or missing statistics: after bulk loads, run ANALYZE.
  2. Skewed data and parameter sniffing: a plan compiled for one parameter value (rare) is reused for another (common). Fixes include re-optimising per execution, using plan guides, or splitting query paths.
  3. Correlated columns break independence; create extended statistics.
  4. Cardinality errors compounding through many joins; simplify or materialise intermediate results (CTE materialisation, temp tables).
  5. Implicit casts (comparing a string column to a number) prevent index use.
  6. Memory settings too low make sorts and hashes spill to disk.
  7. ORM-generated queries with many joins or SELECT *.

A tuning loop that works: capture the slow query with real parameters; get EXPLAIN (ANALYZE, BUFFERS); compare estimated and actual rows at each node; find the first big mismatch or the most expensive node; fix statistics, index or query; re-measure; check the other queries that touch the same table.

Key idea

The optimiser chooses a join algorithm and order by estimating row counts from statistics. Hash and merge joins scale where nested loops explode; indexes win when the predicate is selective; composite index column order matters; sargable predicates are essential; and most bad plans come from wrong row estimates, so compare estimated with actual rows first.

How this gets asked

What is the first thing to compare when a plan looks wrong?

  • CPU model No.
  • Estimated rows versus actual rows at each plan node Correct.
  • The table name No.
  • Network latency No.

The first large mismatch usually locates the problem.

Interview questions: Optimiser internals

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What does a query optimiser do?

It enumerates equivalent plans, estimates their cost from statistics and picks the cheapest.

Basic Name the three join algorithms.

Nested loop, hash join and merge join.

Medium When is a hash join better than a nested loop?

For large unsorted inputs with an equality condition and no useful index, since it is O(n + m) versus O(n x m).

Medium When does nested loop win?

When the outer input is small and the inner side has an index on the join key.

Medium What is selectivity and cardinality estimation?

Selectivity is the fraction of rows a predicate keeps; the optimiser multiplies it by row counts using statistics to estimate each operator's output.

Medium Why might the optimiser ignore an index?

If the predicate keeps a large fraction of rows, random index lookups cost more than a sequential scan.

Medium What is a covering index?

An index containing all columns a query needs, allowing an index-only scan without reading the table.

Medium How does composite index column order matter?

The index is sorted by the leading column first, so queries must constrain a leading prefix; put equality columns before range or sort columns.

Medium What does sargable mean?

A predicate the engine can answer with an index seek; wrapping the column in a function or arithmetic usually breaks it.

Advanced Why do plans go wrong?

Stale statistics, skewed data with parameter sniffing, correlated columns, errors compounding across joins, implicit casts and insufficient memory causing spills.

Advanced How do you diagnose a bad plan?

Run EXPLAIN ANALYZE, compare estimated and actual rows per node, find the first large mismatch or the costliest node, then fix statistics, indexes or the query.

Advanced B-tree versus hash versus GIN versus BRIN?

B-tree for equality and ranges, hash for equality only, GIN for inverted lookups such as arrays and text, BRIN for huge naturally ordered tables.

Advanced What are extended statistics?

Statistics on groups of columns that capture correlation, fixing the independence assumption for predicates on related columns.

Advanced Partial and expression indexes?

A partial index covers only rows matching a predicate (smaller and faster); an expression index stores computed values such as lower(email) so those predicates can use it.
