Part 12

LLM system design and MLOps

The open-ended round: "design a document Q&A assistant" or "design a support agent". Interviewers look for a structured approach, back-of-envelope numbers, sensible tradeoffs, and an evaluation and monitoring plan. This page gives you the framework, the estimates, and two worked designs.

MediumAdvanced~2 hours

A framework for any LLM design question

Intuition

Do not jump to "use GPT plus a vector DB". Clarify what success means, estimate the load, sketch the simplest architecture that works, then deepen the parts that matter: quality (retrieval, evals), latency, cost, safety and operations. Say your tradeoffs out loud.

  1. Clarify requirements: users, use cases, inputs and outputs. Functional needs (cite sources? take actions?) and non-functional ones: latency SLOs (time to first token, total time), availability, quality bar, cost ceiling, privacy and compliance (PII, data residency), languages.
  2. Estimate scale: requests per day, peak QPS, tokens in and out, concurrency (Little's law), storage for documents and embeddings.
  3. High-level design: client, gateway (auth, rate limits), orchestrator, retrieval, model serving or API, tools, stores, async pipelines (ingestion), observability.
  4. Deep dives: retrieval quality, model choice and routing, caching, failure handling, safety, prompt versioning.
  5. Evaluation: offline golden sets and component metrics, then online metrics and A/B tests.
  6. Operations: monitoring, alerting, cost tracking, feedback loops, rollout and rollback.

How this gets asked

In an LLM design interview, what should come first?

  • Choosing the vector database Too early.
  • Clarifying requirements, success metrics and scale Correct: they drive every later choice.
  • Writing the prompt An implementation detail.
  • Fine-tuning a model This may not even be needed.

Requirements, then estimates, then a simple design, then deep dives and evals.

Self-check

Name four non-functional requirements for an LLM system.

Latency (TTFT and total), cost, availability, privacy and compliance (also quality bar, languages, throughput).

When does self-hosting beat an API?

High steady volume, strict data control, custom models or latency needs, and a team able to operate GPUs.

What must every design include beyond architecture?

An evaluation plan and monitoring and feedback loops.

Back-of-envelope: capacity, latency and cost

The formulas

Estimation toolkit
avg QPS = requests_per_day / 86,400; peak QPS ~ 2 to 5 x avg concurrency (Little's law) L = arrival_rate * time_in_system latency ~ TTFT + output_tokens * time_per_output_token API cost/day = tokens_in * price_in + tokens_out * price_out KV memory ~ concurrency * tokens_per_sequence * KV_bytes_per_token
1M requests/day, 1,500 input + 300 output tokens each
  1. Average QPS: 1,000,000 / 86,400 = 11.57. Peak at 3x is about 35 QPS.
  2. Tokens per day: 1.5B input, 300M output. Peak output demand: 35 x 300 = 10,500 tokens/s.
  3. API cost at illustrative prices ($0.50 per M input, $1.50 per M output): 1,500 x 0.5 + 300 x 1.5 = $1,200 per day. Real prices vary widely by model and provider, so plug in current ones. Prompt caching discounts can cut the input cost substantially.
  4. Latency: TTFT 0.5 s + 300 tokens x 20 ms = 6.5 s total. Stream tokens so users see progress after 0.5 s.
  5. Self-hosting check: requests spend about 10 s in the system, so concurrency = 35 x 10 = 350 sequences (Little's law). KV at 1,800 tokens x 128 KiB (Llama-3-8B fp16) is about 236 MB per sequence, so about 82.6 GB of KV cache at peak, on top of the weights. If one GPU sustains about 2,500 output tokens/s for this model (an illustrative figure: benchmark your stack), you need ceil(10,500 / 2,500) = 5 GPUs, plus headroom and redundancy.
~35 peak QPS, ~$1.2k/day API (illustrative), or ~5+ GPUs self-hosted

Cost levers

  • Model cascade / routing: send easy requests to a small model and escalate hard ones. If 80% go to a model costing 1 unit and 20% to one costing 10, the average cost is 2.8 instead of 10, a 72% saving (2.9 with a cheap router of cost 0.1 on every request).
  • Caching: exact-match cache for repeated requests, semantic cache (embedding similarity) for near-duplicates (careful with stale or personalized answers), provider prompt or prefix caching for shared context. A 30% cache hit rate removes 300k of 1M daily calls.
  • Shorter prompts: trim retrieved context (rerank to the top 3 to 5), compress the history, cap max tokens per task.
  • Batch APIs for offline jobs (often discounted by providers), and quantized self-hosted models.

About 11.6.

Three cost levers?

Serving architecture: gateway, routing, caching, fallbacks

  • Gateway: authentication, per-user and per-tenant rate limits (token bucket, part 08), quotas, request IDs.
  • Streaming over SSE or WebSockets for perceived latency. Handle client disconnects (cancel generation to free GPU slots).
  • Fallbacks: on timeouts or 5xx, retry with backoff, then fail over to a secondary model or provider. Degrade gracefully (return sources without a synthesis).
  • Self-hosted serving: vLLM, TGI, TensorRT-LLM or SGLang, with continuous batching, paged KV, prefix caching and quantization (part 01). Autoscale on queue depth and KV utilization, not CPU.
  • Async ingestion: document changes go through a queue to chunking, embedding and index upsert, with idempotent job IDs (part 05).
  • Multi-tenancy: tenant filters enforced in retrieval, per-tenant keys, and no cross-tenant caching of personalized answers.

How this gets asked

Which are sound reliability measures for an LLM-backed API? Select all.

  • Timeouts and bounded retries with jittered backoff Yes.
  • Fallback to a secondary model or provider Yes.
  • Autoscaling self-hosted GPUs on CPU utilization GPU inference load shows up in queue depth and KV usage, not CPU.
  • Cancelling generation when the client disconnects Yes: it frees capacity.

Bound the latency, degrade gracefully, and scale on the right signal.

Self-check

Exact vs semantic cache risk?

A semantic cache can return answers for similar but different questions, or stale and personalized content. It needs thresholds, TTLs and scoping.

What signal should autoscale an LLM server?

Queue depth or waiting requests, KV cache utilization, and latency SLOs.

Why stream responses?

Perceived latency drops to TTFT, and users can stop early.

  • Tracing: one trace per request, spanning retrieval, each model call (prompt version, model version, tokens, latency) and each tool call. This is essential for debugging agents.
  • Eval in CI/CD: every prompt, model or retrieval change runs the golden set. Block on significant regressions (paired tests, part 04).
  • Rollouts: shadow traffic, then canary (a few % of users), then a gradual ramp with guardrail metrics. Keep instant rollback (prompt and model versions behind a config flag).

  • Privacy: redact PII in logs, define retention, honor data processing agreements, keep a per-tenant data boundary.

How this gets asked

After a provider silently updates the model, answer quality drops. What would have caught this fastest?

  • CPU dashboards They do not measure quality.
  • Monthly user surveys Too slow.
  • Pinned model versions plus scheduled golden-set evals and online quality sampling with alerts Correct.
  • Higher rate limits Unrelated.

Quality is a production metric. Monitor it like latency.

Self-check

What does a trace for an LLM request contain?

Spans for retrieval, each model call (prompt and model versions, tokens, latency) and each tool call, all under one request ID.

Canary vs shadow deployment?

Shadow runs the new version on copied traffic without showing users. Canary serves a small slice of real users.

How do production failures improve the system?

They become golden-set test cases, get fixed, and then guard against regressions.

Worked design 1: enterprise document Q&A assistant

Prompt: "Design an assistant that answers employee questions from 2M internal documents (wikis, PDFs, tickets), with citations and access control."
  1. Requirements: answers grounded with citations. Respect document permissions. TTFT under 2 s at p95. 50k employees, about 100k questions per day (about 1.2 QPS average, about 5 peak). Documents update hourly. Admit "not found".
  2. Ingestion: connectors, then parsing (PDF and table extraction), structure-aware chunking (about 500 tokens with overlap, headings kept as metadata), near-duplicate removal, embedding, and upsert into a vector index plus a BM25 index. Store ACL groups, source, timestamp and URL per chunk. Incremental updates via change events with idempotent job keys.
  3. Query path: auth gives the user's groups. Optionally rewrite the query (resolve "it" from chat history). Hybrid retrieval (dense + BM25, RRF) pre-filtered by ACL, top 50. Cross-encoder rerank to the top 5. Build the prompt: system rules (answer only from sources, cite [doc-id], fallback phrase), sources, question. Stream the answer and render citations as links.
  4. Scale: 2M docs x about 5 chunks = 10M vectors x 1,024 dims x 4 B = about 41 GB (fp32), so HNSW on a few nodes, or a managed vector DB. Low QPS, so an API LLM is cheapest to start.
  5. Evals: 300 golden questions with source labels. Measure recall@5 after reranking, answer correctness (LLM judge validated against humans), citation precision, faithfulness and abstention accuracy. Paired tests for every change.
  6. Risks: permission leaks (enforce in retrieval, test with cross-group probes), stale content (freshness metadata, prefer recent), prompt injection inside documents (treat sources as untrusted data, no tool actions), PII in logs.
  7. Iteration: log queries with no or low-score retrieval to find content gaps. Use thumbs-down feedback to grow the golden set.

Storage check: 10M x 1,024 x 4 bytes = 40.96 GB (verified the same way as part 03's 6.1 GB for 1M x 1,536).

Self-check

Where must document permissions be enforced?

In retrieval (pre-filtering by ACL), never by asking the model to hide content.

Which metrics would you report for this assistant?

Recall@k, answer correctness, citation precision, faithfulness, abstention accuracy, latency and cost.

How do you handle hourly document updates?

Event-driven incremental ingestion with idempotent upserts and deletes, and freshness metadata.

Worked design 2: customer support agent that takes actions

Prompt: "Design an AI agent that resolves e-commerce support chats: order status, returns, refunds up to $200."
  1. Requirements: resolve common intents end to end, escalate to humans otherwise. Refunds must never duplicate. Audit trail. Containment rate and CSAT are the business metrics.
  2. Control flow: an intent classifier routes to deterministic workflows for known intents (status, return label). A tool-using agent handles the long tail, with a step limit and a token budget.
  3. Tools: get_order(order_id), create_return(order_id, items), create_refund(order_id, amount, idempotency_key). Each validates that the order belongs to the authenticated user (least privilege). Amount is capped at $200 and at the order total, enforced in code.
  4. Safety: human approval above thresholds or for anomalous patterns. Prompt-injection resistance (user text cannot change the tool scope). PII handling.
  5. Reliability: idempotency keys generated once per logical refund and persisted in conversation state. Timeouts plus jittered retries. Outbox for "refund issued" notifications. Checkpointed agent state so crashed sessions resume safely.
  6. Evals: simulated conversations (scripted user personas) scored for task success, policy compliance (no refund over the cap, no wrong order), tool-call accuracy and tone. Regression suite in CI. Online: containment, escalation rate, refund error rate, CSAT.
  7. Rollout: shadow mode (the agent drafts, humans send), then low-risk intents first, then expand by intent as metrics hold.

How this gets asked

How do you guarantee the agent can never refund more than $200 or refund someone else's order?

  • State the rule clearly in the system prompt Prompts are not enforcement.
  • Fine-tune on examples that respect the cap Still probabilistic.
  • Use a larger model Still probabilistic.
  • Enforce ownership and amount checks in the tool implementation (server-side), with human approval for exceptions Correct: deterministic enforcement.

Business invariants belong in code paths the model cannot bypass.

Self-check

Why route known intents to fixed workflows?

They are predictable, cheaper and easier to test. Reserve the agent for the long tail.

How do you evaluate a support agent offline?

Simulated conversations scored on task success, policy compliance, tool accuracy and tone.

Safe rollout path?

Shadow (drafts only), then low-risk intents, then gradual expansion with guardrail metrics.

Interview questions: system design and MLOps

Try to answer aloud in under a minute, then reveal. Tags show the level.

Basic What are the key latency metrics for an LLM service?

Time to first token, time per output token (inter-token latency), total latency at p50/p95/p99, and throughput in tokens/s and requests/s.

Basic Hosted API vs self-hosted model?

APIs: fast to start, top quality, pay per token, less control. Self-hosted: data control, customization, cost advantages at high steady volume, but GPU ops burden.

Basic Why stream LLM responses?

Users see output after the time to first token instead of waiting for the full response, which improves perceived latency, and they can stop early.

Medium How would you estimate the cost of an LLM feature?

Requests per day x (input tokens x input price + output tokens x output price), minus cache discounts. For self-hosting: peak tokens/s divided by per-GPU throughput gives the GPU count, then add redundancy.

Medium What is a model cascade?

Route easy requests to a cheap model and escalate hard or low-confidence ones to a stronger model. With 80% handled at cost 1 and 20% at cost 10, average cost is 2.8 instead of 10.

Medium What should you monitor in an LLM application?

Latency, errors, throughput, token usage and cost, cache hit rate, quality signals (judge samples, user feedback, groundedness), retrieval health, safety triggers, and drift in inputs.

Medium How do you roll out a new prompt or model safely?

Offline golden-set evals with paired tests, then shadow traffic, then a canary to a small slice, then a gradual ramp with guardrail metrics and instant rollback through versioned configs.

Medium Semantic caching: benefits and risks?

It saves cost and latency on near-duplicate queries. The risks are wrong answers for similar but different questions, stale content and leaking personalized answers. Use similarity thresholds, TTLs and per-user or tenant scoping.

Advanced Design a document Q&A assistant for 2M internal documents with permissions.

Event-driven ingestion (parse, structure-aware chunks, embeddings, vector + BM25 indexes with ACL metadata), hybrid retrieval pre-filtered by ACL, cross-encoder rerank to the top 5, a grounded prompt with citations and an abstain path, streaming, golden-set evals (recall@k, faithfulness, citation precision), and monitoring of retrieval gaps and permissions.

Advanced Design a support agent that can issue refunds.

Intent routing to deterministic workflows, plus a bounded agent for the long tail. Tools with server-side ownership and amount checks, idempotency keys, human approval above thresholds, checkpointed state, outbox notifications, simulated-conversation evals, and a shadow-then-canary rollout.

Advanced How would you serve a model with spiky traffic cheaply?

Autoscale on queue depth and KV utilization with warm pools, continuous batching, quantization, prefix caching, a cascade to smaller models, burst overflow to an API provider, request prioritization, and graceful degradation.

Advanced How do you use Little's law in LLM capacity planning?

Concurrency = arrival rate x time in system. At 35 req/s and 10 s each there are 350 concurrent sequences. Multiply by tokens per sequence and KV bytes per token to size KV memory (about 83 GB for Llama-3-8B at 1,800 tokens).
