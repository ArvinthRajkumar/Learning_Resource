Part A7

MLOps: shipping and running machine learning in production

A model in a notebook is a prototype; a model in production is a system that must be reproducible, observable and safe to change. This part covers the lifecycle and the practical checks that keep a model healthy after launch.

MediumAdvanced~5 hours

The ML lifecycle

Why ML systems differ from ordinary software

Code is only one input. Data and model change too, and behaviour is learned, so failures are often silent: the service returns 200 with a worse prediction. Hidden technical debt appears as entangled features, unstable data dependencies, undeclared consumers of predictions, feedback loops and glue code.

LevelDescription
0Manual: notebooks, hand-copied model files
1Automated training pipeline, continuous delivery of models
2Automated CI/CD for pipeline code, tests on data and models, automatic retraining and rollout

Framing first

Before modelling: what decision will the prediction change? Is ML needed (a rule may work)? What is the baseline and the success metric that matters to the business? What are the latency, cost and fairness constraints? What does a wrong prediction cost?

Self-check

Why are ML failures often silent?

The service still returns valid predictions; quality degrades through data or concept drift and only outcome monitoring reveals it.

Data quality and pipelines

Validate data like code

Most production incidents are data problems. Add automated checks at ingestion and before training:

  • Schema: columns, types, allowed values.
  • Completeness: missing-value rates, row counts against yesterday's.
  • Distribution: means, ranges, category frequencies against a reference (see drift below).
  • Integrity: duplicates, key relationships, impossible values (negative ages).
  • Freshness: the newest timestamp is recent.

Tools: Great Expectations, TFX Data Validation, Pandera, dbt tests, Deequ.

rows = [{"age": 34, "country": "US", "amount": 120.0}, {"age": -5, "country": "US", "amount": 80.0},
        {"age": 41, "country": "ZZ", "amount": None}, {"age": 29, "country": "FR", "amount": 55.5}]
allowed = {"US", "FR", "DE"}
errors = []
for i, r in enumerate(rows):
    if not (0 <= r["age"] <= 120): errors.append((i, "age out of range"))
    if r["country"] not in allowed: errors.append((i, "unknown country"))
    if r["amount"] is None: errors.append((i, "missing amount"))
print(errors)

Output

[(1, 'age out of range'), (2, 'unknown country'), (2, 'missing amount')]

Fail the pipeline (or quarantine rows) when checks fail rather than training on bad data.

Leakage and splitting

Leakage inflates offline metrics and kills production performance. Common forms: features computed with future information, the label hidden in a feature, duplicates across train and test, preprocessing fit on all data, and random splits of time series or grouped data. Split by time for temporal problems and by entity (user, patient) when rows are correlated.

Reproducibility

Version code, data, configuration and environment together: git for code, DVC or lakeFS or table snapshots for data, pinned dependencies and containers, seeds for randomness, and a recorded run for every model. Anyone should be able to rebuild a given model bit-for-bit (or nearly).

How this gets asked

Which is a leakage example?

  • Using a time-based split That avoids leakage.
  • Using a feature computed from information available only after the prediction time Correct.
  • Standardising inside cross-validation folds Correct practice.
  • Holding out a test set Correct practice.

The model sees the future in training but not in production.

Self-check

Name common sources of leakage.

Future-derived features, label-derived features, duplicates across splits, preprocessing fit on all data, random splits of time series.

Features, training and serving

Training-serving skew

The same feature must be computed identically in training and in production. Typical sources of skew: different code paths (SQL in training, Java in serving), different data freshness, missing values handled differently, and features unavailable at prediction time.

Feature stores

A feature store (Feast, Tecton, Vertex, SageMaker) provides: one definition of each feature, an offline store for historical training data with point-in-time correct joins (no future leakage), an online store (low-latency key-value) for serving, and reuse across teams.

# Point-in-time correctness: the feature value used for a label must be the latest value BEFORE the label time.
feature_history = [("u1", 10, 5), ("u1", 20, 9), ("u1", 30, 20)]       # (user, timestamp, purchases_30d)
labels = [("u1", 25, 1)]                                                 # (user, label_time, label)
def as_of(user, t):
    vals = [v for u, ts, v in feature_history if u == user and ts <= t]
    return vals[-1] if vals else None
for user, t, y in labels:
    print("label at t=%d uses feature value %s (not the later 20)" % (t, as_of(user, t)))

Output

label at t=25 uses feature value 9 (not the later 20)

Training pipelines

Orchestrate steps (extract, validate, featurise, train, evaluate, register) as a DAG with Airflow, Kubeflow, Dagster, Metaflow, Vertex Pipelines or SageMaker Pipelines. Track experiments (parameters, metrics, artifacts) with MLflow or Weights and Biases. Store promoted models in a model registry with versions, lineage and stage (staging, production).

Evaluation before release

  • Compare against the current production model and a simple baseline on a frozen, representative test set.
  • Evaluate slices (segments, regions, rare classes): an average hides regressions.
  • Check calibration, latency, memory, and fairness metrics.
  • Run unit tests for the model: invariance (a name change should not change a loan decision), directional expectations (more income, higher approval), and known-hard examples.
  • Gate release on thresholds in CI.

How this gets asked

What is training-serving skew?

  • Training is slower than serving No.
  • Features are computed differently in training and in production Correct.
  • The GPU differs No.
  • Batch size differs No.

A feature store with one definition prevents it.

Self-check

What is a point-in-time join?

A join that attaches to each label the latest feature value known before the label time.

Population stability index (PSI)

Bin a feature using the reference (training) data, compare the share of production data in each bin: PSI = sum (p_prod - p_ref) x ln(p_prod / p_ref). Rule of thumb: below 0.1 stable, 0.1 to 0.25 moderate shift, above 0.25 major shift.

import math
def psi(ref, cur):
    return sum((c - r) * math.log(c / r) for r, c in zip(ref, cur))
ref = [0.25, 0.25, 0.25, 0.25]            # share of training data in 4 quartile bins
stable = [0.24, 0.26, 0.26, 0.24]
shifted = [0.10, 0.20, 0.30, 0.40]
print("PSI stable  :", round(psi(ref, stable), 4))
print("PSI shifted :", round(psi(ref, shifted), 4))

Output

PSI stable  : 0.0016
PSI shifted : 0.2282

Kolmogorov-Smirnov and other tests

The KS statistic is the maximum gap between two empirical cumulative distributions; use a p-value cautiously because large samples flag trivial differences. Alternatives: Jensen-Shannon divergence, Wasserstein distance, chi-square for categories, classifier two-sample tests (train a model to tell reference from current data).

import random
random.seed(0)
def ks(a, b):
    a, b = sorted(a), sorted(b)
    pts = sorted(set(a + b))
    def cdf(s, x):
        lo, hi = 0, len(s)
        while lo < hi:
            mid = (lo + hi) // 2
            if s[mid] <= x: lo = mid + 1
            else: hi = mid
        return lo / len(s)
    return max(abs(cdf(a, x) - cdf(b, x)) for x in pts)
ref = [random.gauss(0, 1) for _ in range(2000)]
same = [random.gauss(0, 1) for _ in range(2000)]
moved = [random.gauss(0.5, 1) for _ in range(2000)]
print("KS same distribution : %.3f" % ks(ref, same))
print("KS shifted by 0.5    : %.3f" % ks(ref, moved))

Output

KS same distribution : 0.016
KS shifted by 0.5    : 0.216

Alerts and actions

Alert on drift and on outcome metrics; drift without a performance drop may be harmless. Define actions: investigate, fall back, retrain, or rollback. Retrain on a schedule, on a drift trigger, or continuously; always evaluate the retrained model before promoting.

How this gets asked

Training share per bin [0.5, 0.5] and production [0.3, 0.7]. PSI? (2 decimals, natural log)

(0.3 - 0.5) ln(0.3/0.5) + (0.7 - 0.5) ln(0.7/0.5) = 0.1022 + 0.0673 = 0.1695, about 0.17.

Concept drift means:

  • The input distribution changes That is covariate drift.
  • The relationship between inputs and the label changes Correct.
  • The model file changes No.
  • Latency changes No.

P(y given x) shifts, for example when fraudsters adapt.

Self-check

Data drift versus concept drift?

Data drift changes P(x); concept drift changes P(y given x), and needs labels or outcome metrics to detect.

Experimentation and A/B testing

Offline metrics predict but do not prove business impact. Run an online A/B test: randomise units (users) into control and treatment, measure the metric, test the difference.

import math
def ab_test(conv_a, n_a, conv_b, n_b):
    pa, pb = conv_a / n_a, conv_b / n_b
    p = (conv_a + conv_b) / (n_a + n_b)
    se = math.sqrt(p * (1 - p) * (1 / n_a + 1 / n_b))
    z = (pb - pa) / se
    return pa, pb, z
pa, pb, z = ab_test(480, 10000, 540, 10000)
print("rate A %.2f%%, rate B %.2f%%, z = %.2f (|z| > 1.96 means p < 0.05)" % (pa * 100, pb * 100, z))
def sample_size(p, mde, z_a=1.96, z_b=0.84):          # per group, two-sided alpha 0.05, power 80%
    return int(2 * ((z_a + z_b) ** 2) * p * (1 - p) / mde ** 2) + 1
print("users per group to detect a 0.5 point lift on a 5%% base: %d" % sample_size(0.05, 0.005))

Output

rate A 4.80%, rate B 5.40%, z = 1.93 (|z| > 1.96 means p < 0.05)
users per group to detect a 0.5 point lift on a 5% base: 29792

Details matter: pre-register the metric and sample size, do not peek and stop early on a good p-value (or use sequential methods), guard against sample ratio mismatch, watch guardrail metrics (latency, complaints), beware novelty effects, network interference and multiple comparisons (A11).

How this gets asked

Why not stop an A/B test as soon as p < 0.05?

  • It saves money That is a reason to stop.
  • Repeated peeking inflates false positives; fix the sample size in advance or use sequential methods Correct.
  • p-values are illegal No.
  • It needs more features No.

Optional stopping breaks the error guarantees.

Governance and cost

  • Documentation: model cards (intended use, data, metrics, limits), datasheets for datasets, decision logs.
  • Compliance and privacy: consent, minimisation, retention, the right to explanation or deletion, audit trails, regional rules.
  • Security: protect models and endpoints, rate limit, defend against extraction and adversarial inputs, scan dependencies, control access to data and features.
  • Fairness: measure per group, set thresholds, review regularly.
  • Cost: GPU hours, storage, feature computation and serving. Right-size, use spot instances for training, cache predictions, batch where possible, distil or quantise models.
  • Ownership: on-call rotation, runbooks, SLOs for the prediction service, deprecation of unused models.
Key idea

Treat the model as one artefact in a pipeline of data, features, code and monitoring. Most value comes from reliable data checks, identical features in training and serving, safe rollouts, and monitoring that detects silent decay.

Interview questions: MLOps

12 questions. Try to answer aloud in under a minute, then reveal. Tags show the level.

Basic What is training-serving skew?

Features computed differently in training and production, causing the model to see different data online; prevented by sharing feature definitions in a feature store.

Basic What is data leakage?

Information unavailable at prediction time reaching the training set, such as future-derived features or duplicates across splits, inflating offline metrics.

Basic What do you monitor for a deployed model?

System health (latency, errors), data quality and drift, prediction distributions, outcome metrics when labels arrive, and fairness slices.

Medium Data drift versus concept drift?

Data drift changes the input distribution; concept drift changes the relationship between inputs and the target. Concept drift needs labels or outcome metrics to detect.

Medium What is PSI and how do you read it?

The population stability index compares binned distributions: below 0.1 stable, 0.1 to 0.25 moderate shift, above 0.25 major shift.

Medium Shadow, canary and A/B deployment?

Shadow logs predictions without using them; canary serves a small share with monitoring; A/B randomises users to measure the causal impact of the new model.

Medium What does a feature store provide?

Single feature definitions, an offline store with point-in-time correct joins for training, an online store for low-latency serving, and reuse.

Medium How do you make ML experiments reproducible?

Version code, data, config and environment, fix seeds, record runs in a tracker such as MLflow, and store models in a registry with lineage.

Advanced How do you decide when to retrain?

On a schedule, on drift or performance triggers, or continuously; always evaluate the retrained model against production on a frozen set before promoting.

Advanced How would you handle delayed labels in monitoring?

Monitor proxy signals (drift, prediction distributions) immediately, join labels when they arrive to compute true metrics, and use holdout or randomised exploration traffic for unbiased evaluation.

Advanced What belongs in a pre-release model evaluation?

Comparison with production and a baseline on a frozen set, slice metrics, calibration, latency and memory, fairness checks, and behavioural tests such as invariance and directional expectations.

Advanced How do you reduce ML serving cost?

Batching, quantisation, distillation, caching predictions, right-sizing hardware, autoscaling, and routing easy requests to cheaper models.
