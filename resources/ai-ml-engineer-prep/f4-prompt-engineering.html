Prompt engineering

Prompting is the cheapest lever you have, and interviewers check that you use it systematically: clear structure, examples, reasoning, structured outputs, tools, and measuring every change against an eval set instead of by gut feel.

BasicMedium~1.5 hours

Anatomy of a good prompt

Intuition

Treat the model like a brilliant new colleague with no context. Tell it who it is serving, what the task is, what it can use, what good output looks like, and what to do when unsure. Most "the model is dumb" problems are really "the instructions were ambiguous" problems.

Principles

  • Be specific: length, audience, format, constraints ("3 bullet points, under 20 words each, for a non-technical manager").
  • Say what to do, not only what to avoid: "Answer only from the documents; if the answer is not there, reply 'Not in the provided documents.'"
  • Delimit inputs (XML-style tags, triple quotes) so the model knows what is instruction and what is data. This also helps against prompt injection, but is not a full defense.
  • Give the "why": a reason behind a rule helps the model generalize it.
  • Roles: the system prompt carries durable instructions, user messages carry requests, and assistant messages are prior model turns (you can also pre-fill one to steer the format).
  • Long documents: put long context before the question, and ask for relevant quotes first, then the answer.

Common traps

  • Contradictory instructions ("be concise" and "explain thoroughly").
  • Implicit formats: the parser expects JSON but the prompt never says so.
  • Burying the key instruction in the middle of a long prompt.
  • No escape hatch: forcing an answer when the information is missing invites hallucination.

How this gets asked

A support bot invents policy details when the answer is not in the retrieved docs. Best prompt change?

  • "Be accurate." Too vague to change behavior.
  • Raise the temperature Makes it worse.
  • Remove the documents to shorten the prompt Removes the grounding.
  • Instruct it to answer only from the delimited documents, cite them, and reply with a fixed fallback phrase when the answer is absent Correct: a specific rule with an escape hatch.

Grounding rules plus an allowed "I don't know" path reduce fabrication. Measure the change with a faithfulness eval.

Self-check

What belongs in the system prompt?

Durable instructions: role, rules, format, safety constraints and fallback behavior.

Why delimit documents?

To separate data from instructions, enable citations, and reduce (not eliminate) injection risk.

Why put the dynamic question last?

Prefix caching reuses static parts, and models attend well to the end of the prompt.

Zero-shot, few-shot, chain of thought, self-consistency

Intuition

Examples show the model exactly what you want, which is often clearer than any description. This is in-context learning: no weights change. For multi-step problems, letting the model write out its reasoning before the answer gives it "scratch space". Each reasoning token is computation the answer can build on.

Zero-shotinstructions onlysimple, well-specified tasks
Few-shot2 to 5 input/output examplesformat, style, labeling conventions, edge cases
Chain of thought (CoT)"think step by step" or worked reasoning in the examplesmath, logic, multi-hop questions

Why self-consistency helps (idealized)
  1. Suppose each sampled reasoning path is right with probability 0.6, independently, and wrong answers do not all agree.
  2. Majority of 5: P(at least 3 right) = sum over k = 3..5 of C(5,k) 0.6^k 0.4^(5-k) = 0.6826.
  3. Majority of 9: 0.7334. Accuracy rises with more samples, but so does cost (n times the tokens).
  4. Reality is less rosy: errors are correlated, so gains are smaller. This is the same intuition as ensembling.
0.60 to 0.68 to 0.73 (5 and 9 votes, independent-errors assumption)
  • Example selection matters: diverse and representative examples, covering edge cases. Order and label balance can bias outputs (models can over-copy the last example's label). Retrieve similar examples dynamically for big example pools.
  • Reasoning models are trained to think before answering. For them, explicit "think step by step" adds little. Give clear goals and constraints instead. Hidden reasoning tokens still cost latency and money.
  • For extraction or classification with structured output, put a short reasoning field before the answer field (part 01, constrained decoding).

How this gets asked

Select all true statements.

  • Few-shot prompting does not update model weights True: in-context learning.
  • Self-consistency uses greedy decoding for every sample False: greedy would give the same path each time. It needs sampling.
  • Chain of thought tends to help multi-step reasoning more than simple lookups True.
  • More examples always improve accuracy False: there are diminishing returns, cost and length effects, and possible bias.

Self-consistency = sample diverse paths, then aggregate.

Each of 5 independent samples is correct with probability 0.6. Probability the majority vote is correct? (4 decimals)

sum over k = 3..5 of C(5,k) 0.6^k 0.4^(5-k) = 0.3456 + 0.2592 + 0.07776 = 0.6826.

Self-check

What is in-context learning?

The model adapts to the examples or instructions in its prompt, without any weight updates.

Self-consistency in one line?

Sample several chains of thought and take the majority final answer.

Why might CoT be unnecessary for reasoning models?

They already generate internal reasoning by training. Extra instructions add little.

Structured outputs and function calling

Intuition

Applications need machine-readable outputs, not prose. You can ask for JSON in the prompt (works mostly), use a provider's JSON or structured-output mode (constrained decoding guarantees the schema), or use function (tool) calling: you describe functions with JSON Schemas, and the model returns which function to call with what arguments. Your code executes it and feeds the result back.

  • Write tool descriptions as documentation for the model: purpose, when to use it, argument meanings and units.
  • Validate arguments and permissions in code before executing anything (part 05).
  • Schema guarantees concern syntax, not correctness (part 01). Keep evals for field accuracy.

How this gets asked

In function calling, who executes the function?

  • The model, inside the provider's servers For user-defined tools, the model only emits the call.
  • Your application code, which then sends the result back to the model Correct.
  • The tokenizer No.
  • Nobody, the arguments are the answer Results are fed back for the final answer.

Some providers offer built-in server-side tools (for example web search), but user-defined functions run in your code.

Self-check

Prompted JSON vs constrained JSON mode?

Prompted JSON usually works but can break. Constrained decoding guarantees schema-valid syntax.

Steps of the function-calling loop?

Send messages and tools, receive a tool call, execute it, return the result, receive the final answer (repeat as needed).

Why validate tool arguments?

The model can choose wrong or unsafe values. Business rules and permissions must be enforced in code.

ReAct and agentic prompting

Intuition

ReAct (Yao et al., 2022) interleaves Reasoning and Acting: think about what to do, call a tool, observe the result, think again, until done. It is the conceptual core of most agent frameworks (LangChain agents, LangGraph tool nodes, CrewAI agents), which you already use.

Thought: I need the order status before answering.
Action: get_order(order_id="42")
Observation: {"status": "shipped", "eta": "2026-10-28"}
Thought: I can answer now.
Final Answer: Your order shipped and should arrive on Oct 28.
  • Planning variants: plan-and-execute (plan first, then run the steps), reflection loops, and multi-agent setups (a supervisor routing to specialists).
  • Give agents explicit stopping criteria, step limits, and tool-error handling guidance (part 05).
  • Simpler is often better: a fixed workflow (prompt chain) beats an open-ended agent when the steps are known.

How this gets asked

When should you prefer a fixed prompt chain (workflow) over an autonomous agent?

  • When the steps are known in advance, for predictability, lower cost and easier evals Correct.
  • Always, agents never work Agents help when steps are open-ended.
  • When you need the model to choose tools dynamically That is when agents help.
  • Only for chat UIs Unrelated.

Use the least autonomy that solves the task.

Self-check

What does ReAct stand for?

Reasoning + Acting: interleaved thoughts, tool actions and observations.

Plan-and-execute vs ReAct?

Plan-and-execute plans all steps up front. ReAct decides step by step from observations.

Why prefer workflows when possible?

They are predictable, cheaper and easier to test and debug.

Prompt reliability: versioning, evals, iteration

  1. Write the eval first: 50 to 200 representative inputs with expected outputs or rubrics, including edge cases and past failures.
  2. Baseline: run the current prompt and record accuracy, format-error rate, latency and cost.
  3. Change one thing at a time (an instruction, examples, model, temperature) and re-run.
  4. Compare with paired tests on the same items (part 04). A 3-point gain on 200 items is often noise.
  5. Version prompts like code (in git, with IDs logged per request) so production behavior is traceable and reversible.
  6. Watch for regressions when the provider updates a model. Pin model versions where possible.

Prompting is software engineering: specs, tests, version control, and statistics for comparisons.

How this gets asked

You tweak a prompt and five hand-picked examples look better. What should happen before shipping?

  • Ship, the examples look better Cherry-picked anecdotes.
  • Ask the model whether the new prompt is better Biased and unvalidated.
  • Run both prompts on a representative eval set and compare with a paired test Correct.
  • Increase max tokens Unrelated.

Measure on a fixed set, analyze correctly, and keep the old version to roll back to.

Self-check

First step of prompt iteration?

Build an eval set and a baseline.

Traceability, rollback, and attributing changes in metrics.

Why pin model versions?

Provider updates can silently change behavior and break prompts.

Interview questions: prompt engineering

Try to answer aloud in under a minute, then reveal. Tags show the level.

Basic What makes a good prompt?

A clear role and task, relevant context in delimiters, an explicit output format, constraints, examples for tricky cases, and a fallback instruction for when the answer is unknown.

Basic Zero-shot vs few-shot prompting?

Zero-shot gives only instructions. Few-shot adds a few input/output examples in the prompt (in-context learning), which helps with format and edge cases without changing weights.

Basic What is chain-of-thought prompting?

Asking the model to reason step by step before answering (or showing reasoning in examples). It gives the model intermediate computation, which helps multi-step problems.

Basic What is a system prompt?

Instructions with higher priority that set the model's role, rules, tone and format for the whole conversation, separate from user messages.

Medium What is self-consistency?

Sample multiple reasoning paths at non-zero temperature and take the majority final answer. With independent errors, accuracy improves (0.6 per sample gives 0.68 for majority-of-5). Costs scale with the number of samples.

Medium How do you get reliable JSON output from an LLM?

Use structured-output or JSON-schema mode (constrained decoding) or function calling. Validate with a parser, keep the schema simple, include an unknown option, and keep evals for value correctness.

Medium What is ReAct?

A prompting and agent pattern that interleaves reasoning (thoughts), actions (tool calls) and observations (tool results) until the task is solved. It is the basis of most tool-using agents.

Medium How do you iterate on prompts systematically?

Build an eval set and a baseline, change one thing at a time, measure on the same items with a paired comparison, version prompts in git, and log prompt versions in production.

Medium How does example order or selection affect few-shot prompting?

Models can be biased toward the most recent or most frequent labels in the examples. Use diverse, balanced, representative examples, and retrieve similar examples dynamically for large pools.

Advanced How would you defend a prompt against injection from retrieved documents?

Delimit untrusted content and tell the model to treat it as data, but rely on architecture: least-privilege tools, no actions triggered directly by retrieved text, human approval for risky actions, output filtering, and allowlisted links. Prompts alone are not a security boundary.

Advanced When would prompting not be enough, and what would you do?

When the task needs a consistent style or format at scale, domain behavior the model lacks, lower latency or cost, or knowledge that changes. Then add RAG for knowledge, fine-tune for behavior or distill for cost, measured against the prompt baseline.
