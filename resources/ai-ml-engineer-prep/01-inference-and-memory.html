Part 01

Inference and memory math

One idea explains most of this page: generating a token means reading every weight from GPU memory, and memory is far slower than the math units. Once that clicks, quantization, batching, speculative decoding and the KV cache all make sense.

Transformer inference: prefill vs decode

Intuition

A language model generates one token at a time. To pick token number 101 it must "look at" tokens 1 to 100. Attention does that by comparing the new token's query with every earlier token's key, then mixing their values. Keys and values of old tokens never change, so recomputing them every step would be pure waste. The KV cache stores them once.

Analogy: you are writing an essay and keep index cards for every sentence so far. For each new sentence you scan your cards instead of re-reading and re-summarizing the whole essay. The cards are the KV cache. They take desk space (GPU memory) that grows with every sentence.

The mechanism

Inference has two phases with very different hardware behavior:

  • Prefill: the whole prompt (say 2,000 tokens) goes through the model in one forward pass. All tokens are processed in parallel as a big matrix multiply. Every weight read from memory is reused for 2,000 tokens, so the GPU's math units are the bottleneck (compute bound). Prefill fills the KV cache for all prompt tokens and produces the first output token. Its duration is what you feel as time to first token (TTFT).
  • Decode: each later token needs its own forward pass, because token t+1 depends on token t. Each pass processes a single new token per sequence, so every weight is read from memory to do just one multiply-add. Memory bandwidth is the bottleneck (memory bound). The time per pass is the inter-token latency (ITL, also TPOT).

What the KV cache stores

In every layer, each token's hidden vector is projected into a key vector and a value vector for each KV head. The cache keeps those K and V vectors for every past token, in every layer. A new token computes only its own Q, K, V, appends its K and V, and attends over the stored ones. Without the cache, step t would recompute K and V for all t previous tokens. That turns generation from roughly linear into quadratic work in the sequence length.

Attention for the new token at position t (one head)
out_t = softmax( q_t · [k_1 ... k_t]^T / sqrt(d) ) · [v_1 ... v_t]
q_t
query of the new token (computed this step)
k_i, v_i
key and value of token i (read from the cache for i < t)
d
head dimension, e.g. 128

Common traps

  • "The KV cache stores the queries." No. Queries are only needed for the current token, so they are never cached.
  • "The KV cache stores attention scores or outputs." No. It stores K and V projections per layer and per KV head.
  • "Decode is compute bound because the model is big." No. Size makes it slower, but the bottleneck is bytes moved per token, not FLOPs.
  • "Disabling the KV cache saves memory, so it helps throughput." It saves memory but recomputes everything, which makes it far slower.

How this gets asked

A chat app's time to first token is high for long prompts, but tokens stream quickly afterward. Which phase dominates the delay?

  • Decode, because each token needs a full pass Decode determines the streaming speed after the first token, which is fine here.
  • Tokenization of the prompt Tokenizing even 100k characters takes milliseconds on a CPU.
  • Prefill, which processes the whole prompt before the first token can be emitted Correct. TTFT is mostly prefill time, which grows with prompt length.
  • KV cache eviction Eviction is not a phase. It would cause recomputation, but that is not the default story here.

TTFT is mostly prefill time (plus queueing). Inter-token latency is decode. Prefix caching and chunked prefill target TTFT. Quantization and speculative decoding mostly target decode.

Select all statements that are true about the KV cache.

  • It grows linearly with the number of tokens in the sequence True: one K and one V vector per token, per layer, per KV head.
  • It stores query vectors so attention can be recomputed faster False: queries are used once and discarded.
  • Its size depends on the number of KV heads, not the number of query heads True: this is why GQA and MQA shrink it.
  • It is only used during prefill False: prefill fills it, and decode reads it on every step.

The KV cache is written during prefill and appended during decode. Its size per token is 2 x layers x kv_heads x head_dim x bytes.

Self-check

Why is prefill compute bound and decode memory bound?

Prefill multiplies each weight with all N prompt tokens at once, so many FLOPs are done per byte read. Decode does one token per sequence, so each weight byte read supports only about one FLOP.

What would happen to generation cost without a KV cache?

Step t would recompute K and V for all t tokens, so total work over n tokens grows roughly with n squared instead of n (for the projection work).

Which latency metric does prefill drive, and which does decode drive?

Prefill drives time to first token (TTFT). Decode drives inter-token latency (time per output token).

KV cache size: the formula and the exam question

Intuition

Count the numbers you store, then multiply by bytes per number. For every token you store a K vector and a V vector (the 2), in every layer, for every KV head. Each vector has head_dim numbers. Then multiply by how many tokens you hold, across all sequences in the batch.

The mechanism

The formula

Per-token form: 2 x L x H_kv x d_head x b bytes. Multiply by the total tokens in flight (S x B).

Worked example: the assessment question

32 layers, 8 KV heads, head_dim 128, fp16, batch 4 x 8192 tokens. Options: 16, 1, 32, 4 GiB
  1. Per token per layer: 2 (K,V) x 8 heads x 128 dims = 2,048 numbers.
  2. All 32 layers: 2,048 x 32 = 65,536 numbers per token.
  3. fp16 is 2 bytes: 65,536 x 2 = 131,072 bytes = 128 KiB per token.
  4. Tokens in flight: 4 x 8,192 = 32,768 = 2^15.
  5. Total: 131,072 x 32,768 = 2^17 x 2^15 = 2^32 = 4,294,967,296 bytes.
  6. 2^32 / 2^30 = 4 GiB (4.295 GB in decimal units).
Answer: 4 GiB (option D)

Powers of two make this mental math: 2 x 2^5 x 2^3 x 2^7 x 2^13 x 2^2 x 2^1 = 2^(1+5+3+7+13+2+1) = 2^32.

Common traps

  • Plugging in query heads instead of KV heads.
  • Forgetting the factor 2, the batch, or the bytes per element.
  • Mixing GiB (2^30) and GB (10^9). 4 GiB = 4.29 GB. Exam options in GiB usually come out as clean powers of two.
  • Thinking the KV cache depends on parameter count. It depends on layers, KV heads and head_dim only. A 70B GQA model can need less KV per token than a 7B MHA model.
  • Thinking the cache is sized by max_new_tokens only. It holds prompt tokens plus generated tokens.

  • 1 GiB This is one sequence. There are 4.
  • 32 GiB This uses 32 heads and 4-byte elements.
  • 4 GiB 2 x 32 x 8 x 128 x 8192 x 4 x 2 = 2^32 bytes.

Why does GQA save memory without removing query heads?

Groups of query heads share one K/V head, and only K and V are cached. Each query head still has its own projection, so the model keeps most of its expressiveness.

Weight memory and total VRAM

Intuition

Weights are just numbers. Count them (the parameter count), multiply by bytes per number. 8 billion parameters at 2 bytes each is 16 billion bytes, which is 16 GB.

70B280 GB140 GB70 GB35 GB
 Decimal GB (10^9 bytes). In GiB: 8B bf16 = 14.9 GiB, 70B bf16 = 130.4 GiB. Real int4 formats add group scales: one fp16 scale per 128 weights is 4.125 bits per weight, so about 3% more.

What else uses VRAM during inference

  • KV cache: often the largest variable cost under concurrency (previous section).
  • Activations and workspace: temporary tensors for the current forward pass. They are small for decode and larger for long prefills. Chunked prefill caps them.
  • CUDA context and libraries: on the order of hundreds of MB to about 1 GB per GPU. This varies with driver and library versions.
  • Fragmentation: memory lost between allocations. PagedAttention exists largely to reduce it in the KV cache.
  • Server preallocation: vLLM, for example, grabs a fixed fraction of VRAM up front (its gpu_memory_utilization setting, 0.9 by default in recent versions) and uses whatever is not needed for weights as KV cache blocks. Check your version's docs.
Rule of thumb

Total inference VRAM is roughly weights + KV cache for your target concurrency + 10 to 20% overhead. An 8B bf16 model (16 GB) does not leave useful KV room on a 16 GB T4. On a 24 GB L4 or A10 it fits, leaving roughly 6 GB for KV cache after overhead. That is about 45k tokens of Llama-3-8B KV in fp16 (6 x 10^9 / 131,072). Training is far heavier: with Adam in mixed precision, plan on about 16 bytes per parameter before activations (weights, gradients, fp32 master weights and two optimizer moments).

Worked example

Can Llama-3-8B in bf16 serve 16 users at 4k context on one 40 GB A100?

  2. KV per token: 128 KiB. Tokens: 16 x 4,096 = 65,536. KV = 128 KiB x 65,536 = 8 GiB, about 8.6 GB.

  4. Total: about 27 to 29 GB, which is under 40 GB.

Common traps

  • "8B in bf16 is 8 GB." No, bf16 is 2 bytes per parameter, so 16 GB.
  • Comparing GB on a spec sheet with GiB from nvidia-smi (it reports MiB) without converting.
  • Forgetting the KV cache, and then being surprised by out-of-memory errors at high concurrency even though "the model fits".
  • Assuming int4 halves memory compared with int8 exactly. Group scales and unquantized parts (often the embeddings and the LM head) add overhead.

Why 4-bit weight quantization speeds up decoding

Intuition

Picture a chef (the GPU's math units) who can chop at lightning speed, fed by a narrow conveyor belt from the fridge (memory). When cooking one dish at a time, the chef waits on the belt almost the whole time. Shrinking each ingredient to a quarter of its size (4-bit weights instead of 16-bit) lets four times as much arrive per second. The chef barely notices the extra unwrapping (dequantization).

The mechanism: arithmetic intensity and the roofline

Arithmetic intensity = FLOPs performed / bytes moved from memory. Every GPU has a ridge point = peak FLOP/s divided by memory bandwidth. Below the ridge you are memory bound and speed = bandwidth x intensity. Above it you are compute bound.

The formulas

Decode time per token (memory bound regime)
t_token ~ (weight_bytes + KV_bytes_read) / memory_bandwidth intensity_decode ~ 2 x B / b (FLOP per byte of weights) ridge = peak_FLOPs / bandwidth
2
one multiply plus one add per weight per token
B
sequences decoded together (batch)
b
bytes per weight (2 for bf16, about 0.5 for int4)

Worked example: 8B model, single user

H100 SXM (approximate vendor figures: ~3.35 TB/s HBM, ~989 TFLOPS dense bf16)
  1. bf16 weights: 16 GB read per token. 16e9 / 3.35e12 = 4.78 ms per token, a ceiling of about 209 tokens/s.
  2. FLOPs needed per token: 2 x 8e9 = 16 GFLOP. At 989 TFLOPS that is 0.016 ms. Compute is about 300x faster than the memory traffic, so the GPU is idle waiting on memory.
  3. int4 weights with group scales: about 4.125 bits per weight, so 4.125 GB. 4.125e9 / 3.35e12 = 1.23 ms per token, a ceiling of about 812 tokens/s.
  4. Bytes ratio: 16 / 4.125 = 3.88x less data per token.
Up to ~3.9x faster decode ceiling; real gains are smaller (dequantization, KV reads, kernel efficiency)

On an A100 80GB (about 2.0 TB/s) the bf16 ceiling is 16e9 / 2.039e12 = 7.85 ms per token. Ridge points: A100 312 TFLOPS / 2.04 TB/s is about 153 FLOP/byte. H100 989 / 3.35 is about 295. Decode at batch 1 is near 1.

What AWQ and GPTQ actually do

  • Both are weight-only, post-training quantization to about 4 bits, with a scale (and often a zero point) per group of weights, typically 128.
  • GPTQ quantizes weights column by column and uses approximate second-order information (from calibration data) to adjust the remaining weights, compensating for each rounding error.
  • AWQ (activation-aware) notices that a small fraction of weight channels matter most, namely those hit by large activations. It scales those channels up before quantization so they lose less precision.
  • At run time, kernels load 4-bit weights, dequantize them to fp16/bf16 in registers, and multiply with fp16 activations. The matmul itself is not an int4 matmul. That is why it is called W4A16.

Why the tempting wrong options are wrong

ClaimWhy it is wrong
"Fewer layers run"Quantization changes the storage format of each weight, not the architecture. Every layer still runs. (Layer skipping and early exit are different techniques.)
"Attention becomes linear"Attention cost depends on the attention algorithm, not on how weights are stored. Quantizing weights leaves softmax attention quadratic in sequence length.
"Matmuls run in int4"Weight-only schemes dequantize to fp16/bf16 and multiply in 16-bit (W4A16). Integer tensor-core math needs activations quantized too (W8A8 or W4A4 schemes), which is a different technique. The win comes from fewer bytes moved, not faster arithmetic.
"It mostly helps prefill"Prefill is compute bound, so fewer bytes barely matters there. Dequantization overhead can even make large-batch prefill slightly slower.

How this gets asked

Why does 4-bit weight-only quantization (AWQ, GPTQ) speed up single-user decoding?

  • Fewer layers are executed per token All layers still run. Only the storage format changes.
  • Decoding is memory-bandwidth bound, so reading about 4x fewer weight bytes per token is the win Correct. At batch 1 the GPU waits on memory, and fewer bytes means less waiting.
  • Attention becomes linear in sequence length Weight format does not change the attention algorithm.
  • Matrix multiplications run in int4 on tensor cores Weights are dequantized to 16-bit before the multiply (W4A16).

Decode intensity is about 1 FLOP per byte versus a ridge of about 150 to 300. The bottleneck is bytes, so quarter-size weights give up to about 4x the decode ceiling.

A team quantizes a model to int4 weights and measures throughput at batch 256 with long prompts. The gain is much smaller than at batch 1. Most likely reason?

  • At large batch the workload is closer to compute bound, so saving memory bytes matters less Correct. Intensity grows with batch size and approaches the ridge.
  • int4 models produce longer outputs No mechanism for that.
  • The KV cache is quantized too That would help, not hurt.
  • Quantization disables batching It does not.

Batching reuses each weight read for B tokens, so intensity scales with B. Once near the ridge, compute (plus dequantization work) dominates.

Raising throughput for many concurrent requests

Intuition

Since decode wastes compute waiting on memory, the cheapest way to get more tokens per second is to serve many users in the same forward pass. Each weight read then feeds B tokens instead of 1. Almost every throughput technique either packs more sequences into each pass or frees memory so more sequences fit.

The mechanisms

TechniqueWhat it doesWhy it raises throughput
Continuous (in-flight) batchingThe scheduler adds and removes sequences at every decode step instead of waiting for a whole batch to finish.No idle slots behind long requests, so the effective batch stays high.
PagedAttention (vLLM)KV cache in fixed-size blocks with a block table, allocated on demand.Near-zero fragmentation and no max-length reservation, so more sequences fit. It also enables sharing blocks across sequences.
Prefix cachingReuses KV blocks for an identical prompt prefix (for example a shared system prompt).Skips repeated prefill compute and stores shared blocks once.
Chunked prefillSplits a long prefill into chunks mixed with decode steps.Keeps decode flowing for other users (better inter-token latency) and keeps GPU utilization high.
Tensor parallelismSplits each layer's matrices across GPUs. Every layer needs all-reduce communication.Pools memory and bandwidth across GPUs. Lower latency per token. Needs fast interconnect (NVLink).
Pipeline parallelismDifferent layers on different GPUs, with micro-batches flowing through.Fits bigger models across nodes. Adds pipeline bubbles and latency.
FlashAttentionTiled attention kernel that never writes the full attention matrix to HBM.Fewer memory reads and writes. Exact result. Big win for long sequences.
Quantized KV cache (fp8 / int8)Stores K and V in 1 byte instead of 2.Twice the tokens fit, and fewer bytes are read per decode step.
What does NOT help
  • Disabling the KV cache: every step recomputes K and V for all previous tokens. Throughput collapses.
  • Raising max_new_tokens for every request: requests run longer and reserve more KV, so fewer sequences fit and queues grow. If anything it lowers useful throughput. Set limits to what the task needs.
  • Raising temperature, or adding more few-shot examples (more prefill per request).

Worked example

How many concurrent 4k-token Llama-3-8B sequences fit in 24 GB of free KV space (fp16 vs fp8)?
  1. fp16: 128 KiB per token. 24 GB = 24 x 10^9 bytes. Divide by 131,072: about 183,105 tokens, so 183,105 / 4,096 is about 44 sequences.
  2. fp8 KV: 64 KiB per token, so about 89 sequences.
  3. With naive contiguous allocation reserving 8k per request "just in case", fp16 gives only about 22 sequences. That is the waste PagedAttention removes.
~44 (fp16) vs ~89 (fp8); reservations halve it

  • Continuous batching It keeps the batch full at every step.

Self-check

What problem does PagedAttention solve?

KV cache fragmentation and over-reservation from contiguous per-sequence allocation. It allocates fixed-size blocks on demand.

Tensor vs pipeline parallelism in one line each?

Tensor: split each layer's matrices across GPUs, with heavy communication on every layer. Pipeline: split layers into stages on different GPUs, which causes pipeline bubbles.

Does FlashAttention change the attention output?

No. It is an exact algorithm that reorders computation to cut memory traffic.

Speculative decoding

Intuition

A junior writer (small draft model) quickly drafts the next few words. The senior editor (target model) checks the whole draft in one read. Every word the editor would also have written is kept. At the first word the editor disagrees with, the editor writes their own word, and the junior drafts again from there. The editor reads once per batch of drafted words instead of once per word. Since decode is memory bound, checking 5 tokens in one pass costs about the same as generating 1.

The mechanism

The acceptance rule (why the output is exactly the target's)

Rejection sampling per drafted token x
accept x with probability min(1, p(x) / q(x)) on reject, sample from p'(y) = max(0, p(y) - q(y)) / sum_z max(0, p(z) - q(z))
p
target model's distribution at this position (after temperature, top-p and so on)
q
draft model's distribution at the same position

The probability of emitting y ends up being q(y) min(1, p/q) + P(reject) p'(y) = p(y) exactly. This holds at any temperature, because p and q are simply whatever distributions sampling would use. At temperature 0 it reduces to "accept if the draft token equals the target's argmax".

Numeric check: p = (A 0.6, B 0.3, C 0.1), q = (A 0.3, B 0.6, C 0.1)
  1. Draft proposes A (prob 0.3): accept with min(1, 0.6/0.3) = 1.
  2. Draft proposes B (prob 0.6): accept with min(1, 0.3/0.6) = 0.5.
  3. Draft proposes C (prob 0.1): accept with 1.
  4. P(reject) = 0.6 x 0.5 = 0.3. Residual max(0, p - q) = (0.3, 0, 0), normalized to (1, 0, 0): always A.
  5. P(A) = 0.3 x 1 + 0.3 x 1 = 0.6. P(B) = 0.6 x 0.5 = 0.3. P(C) = 0.1. That is exactly p.
Output distribution = target distribution (verified with exact fractions)

Facts that get tested

  • The output distribution is exactly the target model's, so quality is not capped by the draft.
  • It works at any temperature. Acceptance (and so the speedup) is usually higher at low temperature, where distributions are peaked.
  • Rejected tokens do not each cost a full extra target pass. The verification pass already happened, and the replacement token comes from that same pass.
  • Speedup depends on acceptance rate, draft cost and k. A poor draft (low a) can make things slower.
  • It helps most when decode is memory bound (small batches). At high batch the GPU is already busy, so extra verification work competes for compute.
  • Variants: Medusa (extra decoding heads instead of a separate draft), EAGLE (a feature-level draft head), n-gram or prompt-lookup drafting (copy spans from the prompt).

How this gets asked

Which statement about speculative decoding is correct?

  • Each rejected draft token costs a full extra target forward pass The single verification pass scores all positions, and the replacement comes from it.
  • With the standard acceptance rule, the output follows the same distribution as sampling from the target model alone Correct: that is the rejection-sampling guarantee.
  • It only speeds things up at temperature 0 The rule works for any sampling distribution.
  • Output quality is capped by the draft model The target decides every token, so the draft only affects speed.

Speculative decoding is lossless: it trades cheap draft compute for fewer expensive memory-bound target passes, without changing the distribution.

Self-check

State the acceptance probability and the resample distribution.

Accept with min(1, p/q). On reject, sample from max(0, p - q) normalized.

Why does verifying k tokens cost about the same as generating 1?

Decode is memory bound, so one pass reads all weights once whether it scores 1 or k+1 positions. The extra FLOPs are nearly free.

When can speculative decoding be slower than plain decoding?

When acceptance is low or the draft is expensive, or at large batch sizes where the target is already compute bound.

Grammar-constrained (structured) decoding

Intuition

At every step the model proposes scores for every token. A grammar engine knows which tokens can legally come next, given a JSON schema, a regex or a grammar. It sets the scores of illegal tokens to minus infinity before sampling. The model can only walk paths that stay inside the grammar. Think of a form with dropdowns: you cannot type an invalid value, but you can still pick the wrong item.

The mechanism

What it guarantees, and what it does not

Guaranteed
  • The output parses and matches the grammar: required keys, types, enums, brackets.
  • No retries for malformed JSON.
Not guaranteed
  • Values are correct or grounded.
  • Semantic constraints the schema cannot express.
  • That you can skip evals: you still measure accuracy.

Caveats: if generation hits max_tokens mid-object, the output is truncated and invalid. Some schema features (complex regex patterns, some oneOf forms) may be unsupported depending on the engine or provider.

Two subtle effects

  • Overly strict enums force wrong values. If the true answer is not among the enum options (for example the document does not mention a category), the mask still forces one of them. Add an explicit "unknown" or "other" option, or make the field nullable.
  • Field order matters. Tokens are generated left to right, and each token can only depend on earlier tokens. Putting a short "reasoning" field before "answer" lets the answer condition on that reasoning, which often improves accuracy. Putting the answer first means the reasoning becomes an after-the-fact justification.
  • Masking can distort the distribution. The model may have wanted to write a preamble, and forcing { pushes it into lower-probability territory. Few-shot examples in the target format reduce this.

How this gets asked

You use grammar-constrained decoding against a JSON schema. Which statements are true? Select all.

  • It removes the need for an eval set Syntax is guaranteed. Correctness still must be measured.
  • Adding a short reasoning field before the answer field can improve accuracy Generation is left to right, so the answer can condition on the reasoning.
  • An overly strict enum can force a wrong value If the truth is not in the enum, the mask forces a wrong choice. Add "unknown".
  • Field values are guaranteed correct Only the structure is guaranteed.
  • The output always parses as schema-valid JSON That is the guarantee (assuming generation is not cut off by a token limit).

Constrained decoding constrains form, not truth. Design the schema to allow honest answers, and put reasoning before conclusions.

Self-check

How is the constraint enforced at each step?

Logits of tokens that would violate the grammar are set to minus infinity before sampling.

Why add "unknown" to an enum?

Otherwise the model must pick a listed value even when none is true, which fabricates an answer.

Why does the order of fields matter?

Autoregressive generation means later fields can use earlier ones. Reasoning first can improve the answer that follows.

Prompt caching and prompt ordering

Intuition

Prefill turns a prompt into KV entries. If the next request starts with exactly the same tokens, the server can reuse those KV entries and skip that part of prefill. The match must be a prefix: K and V at position i depend on every token before i. So one changed early token invalidates everything after it.

The mechanism

Rule and cache-breaking mistakes

Order: static (system prompt, tool definitions) then semi-static (the weekly manual, retrieved docs shared by a session) then dynamic (user question, timestamps).

  • A timestamp, request ID or user name at the top of the system prompt breaks the cache on every request.
  • Tool definitions serialized in a non-deterministic order (for example from an unordered dict or set) change the prefix.
  • Editing one character of the system prompt invalidates every cached prefix after it.
  • Inserting retrieved chunks before the static instructions.
  • Provider specifics vary and change over time. Some providers cache automatically above a minimum prompt length (OpenAI documents automatic caching for prompts of 1,024 tokens or more), others need explicit cache breakpoints (Anthropic's cache_control). Cached entries expire after a few minutes of inactivity. Check current docs for minimums, TTLs and pricing.

How this gets asked

A prompt has a system prompt plus tool definitions (never change), a 20k-token product manual (updated weekly) and the user's question. For longest-repeated-prefix caching, which order is best?

  • System + tools, then manual, then question Most stable first, so the shared prefix is as long as possible.
  • Question, then system + tools, then manual The prefix differs on every request, so there are no hits.
  • Manual, then question, then system + tools The question in the middle breaks reuse of the system and tools part.
  • Order does not matter for caching Caching is prefix based, so order is everything.

KV at position i depends on all earlier tokens, so only an identical prefix is reusable. Static, then semi-static, then dynamic.

Self-check

Why must the cached part be a prefix?

Each token's K and V depend on all preceding tokens through attention in earlier layers. Change an early token and all later KV changes.

Name two common cache-breaking mistakes.

A timestamp or user ID at the top, and non-deterministic tool or JSON ordering.

Which latency metric does a prefix-cache hit improve most?

Time to first token, because prefill for the cached part is skipped. Cost also drops on providers that discount cached tokens.

Tokenization: byte-level BPE and why Tamil costs more

Intuition

Byte-level BPE starts from raw UTF-8 bytes (256 base symbols) and repeatedly merges the most frequent adjacent pair into a new token. It learns those merges from training text. Patterns that were frequent in the training data, mostly English, become single tokens. Rare byte sequences stay split into many small tokens.

The mechanism

The two causes

  1. UTF-8 encoding: ASCII letters are 1 byte. Tamil characters are 3 bytes each. Byte-level BPE starts from bytes, so Tamil text starts with 3x the symbols.
  2. Merge statistics: merges are learned from the tokenizer's training corpus, which is dominated by English (and code). English words become whole tokens. Tamil byte sequences rarely get merged, so they stay fragmented.

Consequences

  • Cost: providers bill per token, so the same message costs about 3x more in Tamil. It is not a "language surcharge", just more tokens.
  • Context: the same context window holds about 3x less Tamil text. Long-document RAG needs smaller chunks.
  • Latency: more output tokens means more decode steps.
  • Model differences: tokenizers differ across model families (vocabulary size, training mix). Newer tokenizers with larger, more multilingual vocabularies reduce the gap. Always count tokens with the target model's own tokenizer, never by characters or by another model's tokenizer.

Worked example

word = "வணக்கம்"
print(len(word), len(word.encode("utf-8")))   # 7 code points, 21 bytes
print(len("hello".encode("utf-8")))           # 5 bytes

Common traps

  • "The model translates to English internally, which costs tokens." No, tokens are counted on the input text as given.
  • "Tokenizers count characters." No, they segment bytes into learned subword units.
  • "Provider surcharge for non-English." Pricing is per token. The extra tokens come from the tokenizer.

How this gets asked

The same message uses about 3x more tokens in Tamil than in English with a byte-level BPE tokenizer. Why?

  • The model translates Tamil to English internally Tokenization happens on raw input, and there is no hidden translation step.
  • Tokenizers count characters They work on bytes and learned merges, not characters.
  • The provider adds a surcharge for non-English text Billing is per token. The token count itself is higher.
  • Tamil characters take 3 bytes each in UTF-8, and BPE merges were learned mostly from English text Correct: more starting symbols and fewer learned merges.

Byte-level BPE begins at UTF-8 bytes (Tamil: 3 per code point) and only compresses patterns it saw often in training.

Self-check

How many bytes is a Tamil code point in UTF-8? An ASCII letter?

3 bytes. 1 byte.

What does one BPE training step do?

It counts adjacent symbol pairs (weighted by frequency), merges the most frequent pair everywhere, and adds the merged symbol to the vocabulary.

Why must you count tokens with the target model's own tokenizer?

Vocabularies and merges differ across model families, so token counts for the same text differ.

Interview questions: inference

Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What is the KV cache and why does it exist?

It stores each past token's key and value vectors for every layer, so a new token only computes its own Q, K, V and attends to the cached ones. Without it, every step would recompute all previous tokens.

Basic What is the difference between prefill and decode?

Prefill processes the whole prompt in one parallel forward pass (compute bound) and produces the first token. Decode generates one token per pass (memory-bandwidth bound).

Basic What is time to first token vs time per output token?

TTFT is the delay before the first token (queueing + prefill). TPOT, or inter-token latency, is the time between subsequent tokens (decode speed).

Basic How much memory do an 8B model's weights need in bf16?

8e9 x 2 bytes = 16 GB (14.9 GiB), before KV cache and overhead.

Basic What is quantization?

Storing weights (and sometimes activations or KV) in fewer bits, like int8 or int4 instead of bf16. It cuts memory and bandwidth at some accuracy cost.

Medium Write the KV cache size formula and compute it for 32 layers, 8 KV heads, head_dim 128, fp16, 4 x 8192 tokens.

2 x layers x kv_heads x head_dim x seq x batch x bytes = 2 x 32 x 8 x 128 x 8192 x 4 x 2 = 2^32 bytes = 4 GiB.

Medium Why is single-stream decoding memory-bandwidth bound?

Each token requires reading every weight once but does only about 2 FLOPs per weight, around 1 FLOP per byte for bf16, far below GPU ridge points (about 150 to 300 FLOP/byte). Time is roughly bytes read divided by bandwidth.

Medium Why does 4-bit weight-only quantization speed up decoding?

It reads about 4x fewer weight bytes per token. Kernels dequantize to 16-bit and multiply in 16-bit (W4A16), so the win is bandwidth, not int4 arithmetic and not fewer layers.

Medium What is continuous batching?

The server adds new requests and removes finished ones at every decode step instead of waiting for a whole batch to finish. This keeps GPU slots busy and greatly increases throughput.

Medium What problem does PagedAttention solve?

KV cache fragmentation and over-reservation. KV is stored in fixed-size blocks allocated on demand and mapped by a block table, so more sequences fit and prefixes can be shared.

Medium How does speculative decoding preserve output quality?

A draft model proposes k tokens. The target verifies them in one pass, accepting each with probability min(1, p/q) and resampling from max(0, p - q) on rejection. The output distribution exactly equals the target's.

Medium What is prompt or prefix caching and how should prompts be ordered to benefit?

Reuse of KV (or provider-side cache) for an identical prompt prefix. Order content from static (system prompt, tools) to semi-static (documents) to dynamic (user question), and avoid timestamps or IDs early in the prompt.

Medium Why does Tamil text use about 3x more tokens than English?

Tamil code points are 3 bytes in UTF-8, and byte-level BPE merges were learned mostly from English, so Tamil byte sequences stay fragmented into many tokens.

Advanced Explain the roofline model and use it to compare prefill and decode.

Attainable FLOP/s = min(peak compute, bandwidth x arithmetic intensity). Decode at batch 1 has intensity of about 1 FLOP/byte (memory bound). Prefill over N tokens reuses each weight N times (compute bound). Batching moves decode right on the roofline.

Advanced When can speculative decoding make things slower?

When the acceptance rate is low, the draft is expensive, or the server already runs large batches (compute bound), so verifying extra tokens competes for compute.

Advanced What does grammar-constrained decoding guarantee and not guarantee?

It guarantees outputs match the grammar or schema (barring truncation) by masking illegal tokens. It does not guarantee correct values, removes no need for evals, and can force wrong values with overly strict enums.

Advanced How would you size GPUs to serve a 70B model to 32 users at 8k context?

Weights: 140 GB in bf16 (35 GB in int4). KV: 320 KiB/token x 262,144 tokens = 80 GiB in fp16. So bf16 needs about 230 GB plus overhead (for example 4 x 80 GB with tensor parallelism). int4 weights + fp8 KV fit in about 80 to 120 GB.

Advanced Tensor parallelism vs pipeline parallelism for inference latency?

Tensor parallelism splits each layer across GPUs and lowers per-token latency but needs fast interconnect for per-layer all-reduces. Pipeline parallelism adds stage-to-stage latency and helps fit models across nodes, mainly for throughput.
