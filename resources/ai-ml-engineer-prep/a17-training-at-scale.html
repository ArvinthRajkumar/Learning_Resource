Training at scale: GPU performance, parallelism, mixed precision and scaling laws

Training a large model is an exercise in accounting: how many floating-point operations, how many bytes in which memory, how many bytes over which wire. This part gives the formulas and calculators that let you answer 'will it fit, how fast, and what does it cost' before you launch a job.

Advanced~6 hours

The accounting mindset

Three resources limit training, and a good engineer tracks all of them:

ResourceQuestionUnit
ComputeHow many operations does the job need, and how fast is the hardware?FLOPs, FLOP/s
MemoryDo weights, gradients, optimiser state and activations fit on each GPU?bytes
CommunicationHow much data must move between GPUs each step, over which links?bytes, bytes/s

Everything in distributed training (sharding, pipelining, checkpointing, overlap) is a trade between these three.

Compute: how many FLOPs

For a dense transformer with N parameters trained on D tokens, a good rule is:

Training compute
FLOPs = 6 x N x D
N
parameters
D
training tokens

(The backward pass costs about twice the forward.) Inference costs about 2N FLOPs per generated token. Attention adds terms that grow with sequence length, but for typical context lengths the 6ND rule is within tens of percent.

Model FLOPs utilisation (MFU) is the fraction of the hardware's peak FLOP/s that your useful 6ND work achieves. Well-tuned large runs reach roughly 35 to 55%; naive code gets far less. Time to train is 6ND / (num_gpus x peak_flops x MFU).

def training_estimate(params, tokens, gpus, peak_tflops, mfu, price_per_gpu_hour):
    flops = 6 * params * tokens
    seconds = flops / (gpus * peak_tflops * 1e12 * mfu)
    gpu_hours = gpus * seconds / 3600
    return flops, seconds / 86400, gpu_hours, gpu_hours * price_per_gpu_hour
for name, N_, D_, g in [("1B model, 20B tokens", 1e9, 20e9, 8), ("7B model, 1T tokens", 7e9, 1e12, 512), ("70B model, 2T tokens", 70e9, 2e12, 2048)]:
    flops, days, gh, cost = training_estimate(N_, D_, g, peak_tflops=312, mfu=0.4, price_per_gpu_hour=2.0)      # an A100-class GPU, bf16 peak 312 TFLOP/s
    print(f"{name:>22}: {flops:.2e} FLOPs | {g:>4} GPUs -> {days:7.1f} days | {gh:>11,.0f} GPU-hours | about ${cost:>12,.0f} at $2/GPU-hour")

Memory: what lives on the GPU

For each parameter, training with the Adam optimiser in mixed precision typically stores:

ItemBytes per parameter
Weights in bf16/fp16 (used in forward and backward)2
Gradients in bf16/fp162
fp32 master copy of the weights4
Adam first moment (fp32)4
Adam second moment (fp32)4
Total16

Plus activations (stored for the backward pass; grow with batch size, sequence length and depth) and temporary buffers. A 7B model needs 7e9 x 16 = 112 GB for states alone, more than one 80 GB GPU, before any activations.

def memory_gb(params, bytes_per_param=16): return params * bytes_per_param / 1e9
for name, p in [("1B", 1e9), ("7B", 7e9), ("13B", 13e9), ("70B", 70e9)]:

def activation_gb(layers, hidden, seq, batch, bytes_per=2, factor=34):

print("activations for a 32-layer, 4096-wide model, seq 4096, micro-batch 1:", round(activation_gb(32, 4096, 4096, 1), 1), "GB without activation checkpointing")

Activation checkpointing (rematerialisation)

Instead of storing every layer's activations, store only a few checkpoints and recompute the rest during the backward pass. Memory drops from O(layers) to about O(sqrt(layers)) (or O(1) per layer with per-block checkpoints) at the price of roughly one extra forward pass (about 33% more compute). It is the standard way to trade compute for memory.

Mixed precision

Using 16-bit numbers for most arithmetic halves memory traffic and doubles tensor-core throughput.

FormatBitsExponent / mantissaRangeNotes
fp32328 / 23hugeMaster weights, optimiser state, sensitive reductions
bf16168 / 7same as fp32, coarse precisionDefault for training: no loss scaling needed
fp16165 / 10limited (about 6e-5 to 65504)Needs loss scaling to avoid gradient underflow
fp8 (E4M3, E5M2)8variesvery limitedPer-tensor scaling; used on recent GPUs
int8 / int48 / 4integersn/aMostly inference (quantisation, A5)
 
import struct
def to_bf16(x):                                             # keep the top 16 bits of the float32 representation (truncation)
    bits = struct.unpack(">I", struct.pack(">f", x))[0] & 0xFFFF0000
    return struct.unpack(">f", struct.pack(">I", bits))[0]
def to_fp16(x):
    try: return struct.unpack(">e", struct.pack(">e", x))[0]
    except OverflowError: return float("inf")
for x in (3.14159265, 1e-8, 70000.0, 0.1):
    print(f"{x!r:>12}: bf16 {to_bf16(x)!r:>14} | fp16 {to_fp16(x)!r:>14}")
print("fp16 overflows above 65504 and flushes tiny gradients toward zero, which is why it needs loss scaling; bf16 keeps the range but loses precision")

The roofline: compute-bound versus memory-bound

A GPU has a peak compute rate P (FLOP/s) and a memory bandwidth B (bytes/s). An operation's arithmetic intensity I is FLOPs performed per byte moved from memory. Attainable performance is min(P, B x I). The break-even intensity is P / B.

peak_flops, bandwidth = 312e12, 2.0e12                       # A100-class: 312 TFLOP/s bf16, 2 TB/s HBM
print(f"ridge point: {peak_flops / bandwidth:.0f} FLOPs per byte (below this an operation is memory bound)")
def matmul_intensity(m, k, n, bytes_per=2):
    flops = 2 * m * k * n; moved = bytes_per * (m * k + k * n + m * n); return flops / moved
for name, (m, k, n) in [("training matmul, batch 4096 tokens", (4096, 4096, 4096)), ("decoding, 1 token at a time", (1, 4096, 4096)), ("decoding, batch of 64 tokens", (64, 4096, 4096))]:
    I = matmul_intensity(m, k, n); perf = min(peak_flops, bandwidth * I)
    print(f"{name:>36}: intensity {I:7.1f} FLOP/byte -> {perf / 1e12:6.1f} TFLOP/s ({'compute' if I >= peak_flops / bandwidth else 'memory'} bound)")

Output

ridge point: 156 FLOPs per byte (below this an operation is memory bound)
  training matmul, batch 4096 tokens: intensity  1365.3 FLOP/byte ->  312.0 TFLOP/s (compute bound)
         decoding, 1 token at a time: intensity     1.0 FLOP/byte ->    2.0 TFLOP/s (memory bound)

Consequences you can state in an interview:

  • Large matrix multiplications in training are compute bound; keep tensor cores busy with big, aligned shapes.
  • Autoregressive decoding with small batches is memory bound: each token re-reads all the weights, so throughput is about bandwidth / model_bytes tokens per second per sequence, and batching raises intensity (A5).
  • Elementwise operations (layer norm, GELU, softmax, dropout) are memory bound; fusion (one kernel instead of many) and FlashAttention (tiling attention in fast on-chip memory so the n x n score matrix never hits HBM) reduce traffic.
  • torch.compile, fused optimisers and CUDA graphs cut launch overhead and memory round trips.

Communication: the interconnect

LinkTypical bandwidth

Collective operations: all-reduce (sum a tensor across GPUs and give everyone the result), all-gather (assemble shards on every GPU), reduce-scatter (sum and leave each GPU a shard) and all-to-all (used by mixture of experts). A ring all-reduce of S bytes across p GPUs moves about 2 S (p - 1) / p bytes per GPU, nearly independent of p, so it scales well if the link is fast.

def ring_allreduce_seconds(bytes_total, gpus, link_gbps):
    per_gpu = 2 * bytes_total * (gpus - 1) / gpus
    return per_gpu / (link_gbps * 1e9)
grads = 7e9 * 2                                                                   # bf16 gradients of a 7B model: 14 GB
for name, bw in [("PCIe (32 GB/s)", 32), ("InfiniBand node link (50 GB/s)", 50), ("NVLink (450 GB/s)", 450)]:
    print(f"all-reduce of 14 GB over 8 GPUs on {name:>30}: {ring_allreduce_seconds(grads, 8, bw) * 1000:7.0f} ms")
step_compute = 6 * 7e9 * 4096 * 8 / (8 * 312e12 * 0.4)                           # one step with a global batch of 8 sequences of 4096 tokens
print(f"compute per step on 8 GPUs at 40% MFU: {step_compute * 1000:.0f} ms -> communication must overlap with backward compute or it dominates")

ZeRO and FSDP: shard the model state

ZeRO (Zero Redundancy Optimizer) stages remove the replication in data parallelism:

StageShardsMemory per GPU for psi parameters with p GPUs (mixed-precision Adam)
Baseline DPnothing16 psi bytes
ZeRO-1optimiser states4 psi + 12 psi / p
ZeRO-2+ gradients2 psi + 14 psi / p
ZeRO-3 / FSDP+ weights16 psi / p
 
def zero_memory_gb(params, p, stage):
    psi = params
    per_param = {0: 16, 1: 4 + 12 / p, 2: 2 + 14 / p, 3: 16 / p}[stage]
    return psi * per_param / 1e9
for stage in (0, 1, 2, 3):
    print(f"7B model on 8 GPUs, ZeRO stage {stage}: {zero_memory_gb(7e9, 8, stage):6.1f} GB of model state per GPU" + ("   (fits in 80 GB)" if zero_memory_gb(7e9, 8, stage) < 60 else "   (does not fit in 80 GB with activations)"))
print("70B model on 64 GPUs, ZeRO-3:", round(zero_memory_gb(70e9, 64, 3), 1), "GB per GPU")

FSDP trades extra communication (gathering each layer's weights just before use, in both forward and backward) for memory. CPU or NVMe offload (ZeRO-Offload/Infinity) trades PCIe bandwidth for capacity.

Pipeline bubbles

With p stages and m micro-batches, a simple schedule leaves a fraction (p - 1) / (m + p - 1) of time idle (the bubble). Use many micro-batches (m >> p) or interleaved schedules to shrink it.

for p in (4, 8):
    print(f"{p} pipeline stages: " + " | ".join(f"{m} micro-batches -> bubble {(p - 1) / (m + p - 1):.0%}" for m in (4, 16, 64)))

Tensor parallel in one picture

A linear layer Y = X W with W split by columns across two GPUs: each computes its own slice of the output without communication; the next layer, split by rows, consumes those slices and needs one all-reduce to sum partial results. Transformer blocks are arranged so there are two all-reduces per layer (attention and MLP). The verified miniature:

import random
random.seed(1)
def matmul(A, B): return [[sum(a * b for a, b in zip(row, col)) for col in zip(*B)] for row in A]
X = [[random.randint(-3, 3) for _ in range(4)] for _ in range(3)]
W1 = [[random.randint(-3, 3) for _ in range(6)] for _ in range(4)]          # first layer: split by columns
W2 = [[random.randint(-3, 3) for _ in range(4)] for _ in range(6)]          # second layer: split by rows
full = matmul(matmul(X, W1), W2)
W1_a, W1_b = [r[:3] for r in W1], [r[3:] for r in W1]                       # "GPU a" and "GPU b" each hold half the columns
W2_a, W2_b = W2[:3], W2[3:]                                                 # and the matching half of the rows
part_a = matmul(matmul(X, W1_a), W2_a)                                      # computed independently on each device
part_b = matmul(matmul(X, W1_b), W2_b)
combined = [[a + b for a, b in zip(ra, rb)] for ra, rb in zip(part_a, part_b)]      # the single all-reduce (a sum)
print("tensor-parallel result equals the single-device result:", combined == full)

Output

tensor-parallel result equals the single-device result: True

(The nonlinearity between the layers is elementwise, so it acts on each GPU's own slice without communication; the all-reduce happens once at the end of the pair.)

Scaling laws and the compute budget

Empirically, loss falls as a power law in parameters, data and compute. Chinchilla (Hoffmann et al., 2022) found that for a fixed compute budget, parameters and tokens should grow together, at roughly 20 tokens per parameter; many earlier models were over-sized and under-trained. Given compute C = 6ND, the compute-optimal choice is about N = sqrt(C / 120) and D = 20 N.

import math
for C in (1e21, 1e23, 1e25):
    N_opt = math.sqrt(C / 120); D_opt = 20 * N_opt
    print(f"compute {C:.0e} FLOPs: compute-optimal about {N_opt / 1e9:7.1f}B parameters trained on {D_opt / 1e12:6.2f}T tokens")
print("A 7B model trained on 2T tokens uses", round(2e12 / 7e9), "tokens per parameter, far beyond 20: 'over-training' makes a smaller model that is cheaper to serve")

Output

compute 1e+21 FLOPs: compute-optimal about     2.9B parameters trained on   0.06T tokens
compute 1e+23 FLOPs: compute-optimal about    28.9B parameters trained on   0.58T tokens
compute 1e+25 FLOPs: compute-optimal about   288.7B parameters trained on   5.77T tokens
A 7B model trained on 2T tokens uses 286 tokens per parameter, far beyond 20: 'over-training' makes a smaller model that is cheaper to serve

Why train beyond compute-optimal? Training cost is paid once but inference cost is paid on every request; a smaller, longer-trained model gives the same quality at lower serving cost. Other scaling considerations: data quality and repetition (the supply of fresh high-quality text is limited; repeating data a few epochs is fine, many is not), emergent behaviours that appear with scale, and test-time compute (reasoning models spend extra inference compute for accuracy).

Hyperparameters and stability at scale

  • Learning rate scales with model width (use parameterisations such as muP so small-model experiments transfer); warm up the rate over the first thousands of steps and decay (cosine or linear).
  • Batch size: larger batches improve throughput up to the critical batch size; beyond it, extra examples add little. Scale learning rate with batch size carefully.
  • Gradient clipping (norm 1.0) tames spikes; weight decay (decoupled, AdamW); epsilon in Adam matters in low precision.
  • Loss spikes: monitor gradient norm, roll back to a checkpoint and skip the bad data window; consider QK-norm, z-loss and lower precision-sensitive operations in fp32.
  • Checkpointing: save model, optimiser and data-loader state frequently and asynchronously; failures are routine on thousands of GPUs (a 10,000 GPU cluster sees a hardware fault every few hours), so jobs must resume automatically.
  • Data loading must keep GPUs fed: sharded, streamed, shuffled deterministically by step so resumption reproduces the same stream.

Debugging performance

A checklist when throughput is lower than expected:

  1. Compute MFU from tokens per second: tokens/s x 6N / (gpus x peak). Compare with 40% as a target.
  2. Look at a profiler trace: are GPUs idle waiting for data, for communication, or on small kernels?
  3. Data pipeline: increase workers, prefetch, use faster storage and pre-tokenised packed sequences.
  4. Kernel efficiency: fused attention (FlashAttention), fused norm and optimiser kernels, large aligned shapes (multiples of 8 or 64), torch.compile.
  5. Communication: overlap, bucket gradients, place tensor-parallel groups within an NVLink domain, check network topology and stragglers.
  6. Memory: reduce fragmentation, tune micro-batch size, use activation checkpointing selectively, avoid CPU-GPU synchronisation (.item(), print in the loop).
  7. Stragglers: one slow GPU slows everyone; monitor per-rank step times.
def mfu(tokens_per_sec, params, gpus, peak_tflops): return tokens_per_sec * 6 * params / (gpus * peak_tflops * 1e12)
for label, tps in [("untuned baseline", 9_000), ("after fused kernels and data fixes", 21_000), ("well-tuned", 34_000)]:
    print(f"{label:>34}: {tps:>6} tokens/s on 8 GPUs training a 7B model -> MFU {mfu(tps, 7e9, 8, 312):.0%}")

Key idea

Do the arithmetic first: 6ND FLOPs for compute, about 16 bytes per parameter for training state, the ring all-reduce cost for communication. Fit the model with sharding, mixed precision and activation checkpointing; keep GPUs busy by overlapping communication with computation; respect the roofline (training is compute bound, decoding is memory bound); and choose model and data size with scaling laws, remembering serving cost.

Interview questions: Training at scale

15 questions. Try to answer aloud in under a minute, then reveal. Tags show the level.

Basic How many FLOPs does training a transformer need?

About 6 x parameters x tokens: 2ND for the forward pass and 4ND for the backward pass.

Basic How much memory per parameter does mixed-precision Adam training need?

About 16 bytes: 2 for bf16 weights, 2 for gradients, 4 for fp32 master weights and 8 for the two Adam moments, plus activations.

Medium Why bf16 instead of fp16 for training?

bf16 has fp32's exponent range so it needs no loss scaling, while fp16's narrow range risks overflow and underflow.

Medium What is MFU?

Model FLOPs utilisation: useful model FLOP/s divided by the hardware's peak FLOP/s; well-tuned runs reach about 35 to 55%.

Medium Explain activation checkpointing.

Store only some activations and recompute the others in the backward pass, trading about 33% more compute for much less memory.

Medium Data parallel versus tensor parallel versus pipeline parallel?

Data parallel splits the batch with full model copies; tensor parallel splits individual matrices; pipeline parallel splits layers into stages processed in micro-batches.

Medium What does ZeRO stage 3 / FSDP do?

Shards optimiser state, gradients and parameters across data-parallel ranks so memory per GPU falls to about 16 psi / p, at the cost of gathering weights layer by layer.

Medium What is the pipeline bubble?

Idle time of (p - 1)/(m + p - 1) with p stages and m micro-batches; reduced by more micro-batches or interleaved schedules.

Medium Why place tensor parallelism inside a node?

It requires an all-reduce per layer and so needs NVLink-class bandwidth; inter-node links are too slow.

Advanced Explain the roofline model.

Attainable performance is min(peak FLOP/s, bandwidth x arithmetic intensity); low-intensity operations are memory bound and high-intensity ones compute bound.

Advanced Why is decoding memory bound and how do you help it?

Each generated token reads all the weights for few FLOPs. Batch more sequences, use quantisation, KV-cache optimisations, speculative decoding and fused kernels.

Advanced What is FlashAttention?

An exact attention algorithm that tiles computation in on-chip memory so the n x n score matrix never materialises in HBM, reducing memory traffic and memory use.

Advanced State the Chinchilla result.

For a fixed compute budget, model size and training tokens should scale together, about 20 tokens per parameter; many earlier models were under-trained.

Advanced Why train a model beyond compute-optimal?

Inference cost dominates over a model's lifetime, so a smaller model trained on more data reaches a quality target with cheaper serving.

Advanced How do you handle failures in long training runs?

Frequent asynchronous checkpoints including optimiser and data-loader state, automatic restart, health checks to evict bad nodes, and monitoring for loss spikes with rollback.
