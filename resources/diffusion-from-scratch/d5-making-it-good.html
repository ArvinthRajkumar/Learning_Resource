Phase 4: Making it good

Everything that turns a working-but-mediocre model into one that produces images you are happy with, plus the practical survival skills for long training runs.

Advanced~3 hours

What to add, and in what order

Do not add all of these at once. Add one, confirm training still runs and loss still drops, then add the next. If you change five things and quality gets worse, you will have no idea which one caused it.

The order below is deliberate: the first three protect you from losing work or wasting hours, the middle three improve image quality, and the last two change what the model can do.

#UpgradeWhat it gets youEffort

4Horizontal flip augmentationRoughly doubles your effective dataset size, for free.One line

6Cosine noise scheduleNoticeably better results, especially at small image sizes.Small

8Class conditioningLets you ask for a specific class instead of a random image.Large

1. Resuming an interrupted run

On a laptop, a 100-epoch run will get interrupted. Windows will restart for an update, you will close the lid, or you will need the GPU for something else. Right now, train.py saves only the model weights, which means resuming restarts the optimizer from scratch and loses your epoch count.

Why the optimizer state matters

Recall from the autograd section that AdamW keeps running averages for every weight, which is what lets it take well-sized steps. Those averages live in the optimizer, not the model. If you reload only the model weights, AdamW starts cold and its first few hundred steps are poorly sized, which shows up as a visible loss spike right after resuming.

Save everything you need to continue, not just the weights:

def save_checkpoint(model, optimizer, scaler, epoch, path):
    torch.save({
        "epoch": epoch,
        "model": model.state_dict(),
        "optimizer": optimizer.state_dict(),
        "scaler": scaler.state_dict(),
    }, path)


def load_checkpoint(model, optimizer, scaler, path):
    checkpoint = torch.load(path, map_location=config.DEVICE)
    model.load_state_dict(checkpoint["model"])
    optimizer.load_state_dict(checkpoint["optimizer"])
    scaler.load_state_dict(checkpoint["scaler"])
    return checkpoint["epoch"] + 1        # the epoch to start from

Then in train(), before the epoch loop:

start_epoch = 0
resume_path = os.path.join(config.CHECKPOINT_DIR, "latest.pt")

if os.path.exists(resume_path):
    start_epoch = load_checkpoint(model, optimizer, scaler, resume_path)
    print(f"Resuming from epoch {start_epoch}")

for epoch in range(start_epoch, config.EPOCHS):
    ...

And at the end of each epoch, always overwrite the same latest.pt file, separately from your numbered milestone checkpoints: 

save_checkpoint(model, optimizer, scaler, epoch,
                os.path.join(config.CHECKPOINT_DIR, "latest.pt"))
  • checkpoint["epoch"] + 1 is deliberate. If the run died after finishing epoch 40, you want to start at epoch 41, not redo 40.
  • Keeping latest.pt separate from model_epoch50.pt style files means you always have one known-good "continue from here" file, plus milestone snapshots you can compare against each other later.
  • Saving the scaler state matters only if you use mixed precision. It stores the current loss-scaling factor, so resuming does not have to re-discover a safe value.
Watch out

A full checkpoint is roughly three times the size of a weights-only file, because the AdamW state holds two extra numbers per weight. For your small U-Net this is a few tens of MB, which is irrelevant against your 200GB. Do not be tempted to skip it to save space.

2. Watching progress while it trains

Loss is a weak signal for image quality. A loss of 0.03 versus 0.028 tells you almost nothing about whether the pictures look better. The only reliable check is looking at generated samples, so make training produce them automatically.

Add this to train.py and call it every few epochs:

@torch.no_grad()
def save_progress_samples(model, alpha_bars, alphas, betas, epoch, n=8):
    model.eval()

    x = torch.randn(n, config.CHANNELS, config.IMAGE_SIZE, config.IMAGE_SIZE,
                    device=config.DEVICE)

    for t_step in reversed(range(config.TIMESTEPS)):
        t = torch.full((n,), t_step, device=config.DEVICE, dtype=torch.long)
        predicted_noise = model(x, t)

        alpha_t = alphas[t_step]
        alpha_bar_t = alpha_bars[t_step]
        beta_t = betas[t_step]

        noise = torch.randn_like(x) if t_step > 0 else torch.zeros_like(x)

        x = (1 / torch.sqrt(alpha_t)) * (
            x - ((1 - alpha_t) / torch.sqrt(1 - alpha_bar_t)) * predicted_noise
        ) + torch.sqrt(beta_t) * noise

    os.makedirs(config.SAMPLE_DIR, exist_ok=True)
    x = (x.clamp(-1, 1) + 1) / 2
    torchvision.utils.save_image(
        x, os.path.join(config.SAMPLE_DIR, f"epoch_{epoch+1:04d}.png"), nrow=4
    )

    model.train()
  • This is the same sampling loop from sample.py, reused inside training. Nothing new mathematically.
  • model.eval() then model.train() at the end is important. If you forget the second one, the rest of training continues in evaluation mode.
  • f"epoch_{epoch+1:04d}.png" pads the number with zeros (0001, 0002, 0050), so your file browser sorts them in the right order instead of putting epoch_100 before epoch_20.
Watch out

Sampling runs the network 1000 times, so it is slow. Do it every 5 or 10 epochs, not every epoch, or you will spend more time generating progress pictures than training. Once you add DDIM later in this phase, you can switch this to 50 steps and sample far more often.

For the loss curve, you do not need any extra library. Collect the per-epoch averages in a plain Python list and save a plot at the end: 

import matplotlib
matplotlib.use("Agg")          # no GUI window, just write a file
import matplotlib.pyplot as plt

loss_history = []              # before the epoch loop

# ... inside the epoch loop, after computing avg_loss:
loss_history.append(avg_loss)

plt.figure()
plt.plot(loss_history)
plt.xlabel("epoch")
plt.ylabel("average loss")
plt.savefig(os.path.join(config.SAMPLE_DIR, "loss_curve.png"))
plt.close()

matplotlib.use("Agg") tells matplotlib not to try opening a window. Without it, matplotlib can hang or error when run from a plain script rather than a notebook.

3. Gradient clipping

This is the fix for the "loss becomes nan" row in the debugging table, and it is one line.

Term: Gradient clipping

Occasionally one batch produces a very large gradient, which makes the optimizer take a huge step, which wrecks the weights, which makes the next loss even larger. Once that feedback loop starts, loss goes to nan within a few steps and never recovers. Gradient clipping puts a ceiling on the overall size of the gradients before the optimizer uses them. If they exceed the ceiling, every gradient is scaled down proportionally so the direction is unchanged but the step size is capped.

In the training loop, between unscaling and stepping:

scaler.scale(loss).backward()

scaler.unscale_(optimizer)                                   # new
torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)      # new

scaler.step(optimizer)
scaler.update()
  • scaler.unscale_(optimizer) must come first. Remember the scaler multiplied the loss up before backward(), so the stored gradients are currently inflated by that factor. Clipping them while inflated would compare against the wrong ceiling. This call removes the inflation early so clipping sees true values.
  • 1.0 is the ceiling, and it is the standard default. You rarely need to tune it. Lower values clip more aggressively.
  • The trailing underscore in clip_grad_norm_ and unscale_ is PyTorch convention for "this modifies things in place rather than returning a new copy."

If you are not using mixed precision, drop the scaler.unscale_ line and just call clip_grad_norm_ after loss.backward().

4. Data augmentation

If your custom dataset is small, this is the cheapest quality improvement available. Add a random horizontal flip to the transform pipeline in dataset.py: 

transform = transforms.Compose([
    transforms.Resize((config.IMAGE_SIZE, config.IMAGE_SIZE)),
    transforms.CenterCrop(config.IMAGE_SIZE),
    transforms.RandomHorizontalFlip(p=0.5),      # new
    transforms.ToTensor(),
    transforms.Normalize(mean=[0.5, 0.5, 0.5], std=[0.5, 0.5, 0.5]),
])
Term: Data augmentation

Data augmentation means randomly altering training images slightly each time they are loaded, so the model sees a different version on every epoch. The flip happens fresh each time an image is loaded, not once up front, so an image the model saw facing left in epoch 3 may face right in epoch 4. With p=0.5, roughly half of each batch is flipped. The model effectively gets twice as much data without you collecting a single extra image.

Watch out

Only use horizontal flip when a mirrored image is still a valid example. For faces, animals, or landscapes, it is fine. For anything containing text, digits, or a meaningful left/right distinction, it is actively harmful. Do not use it on MNIST: a mirrored 2 is not a 2, and you would be teaching the model that backwards digits are normal. Vertical flips are almost never appropriate for photographs, since upside-down is not a natural orientation.

5. EMA weights

If you only add one quality upgrade from this phase, make it this one. Essentially every serious diffusion implementation uses it, and the difference in sample quality is large and immediate.

Term: EMA (exponential moving average)

The weights jump around from batch to batch, because each batch is a small random sample and pulls the weights in a slightly different direction. The weights at the exact moment you stopped training are therefore a slightly unlucky or slightly lucky snapshot rather than a settled answer. An EMA keeps a second, shadow copy of every weight, updated as a slow-moving average of the real weights. It lags behind and smooths out the jitter. You train using the normal weights, but you generate images using the EMA copy.

Analogy

Think of tracking someone's weight on a bathroom scale. Any single morning's reading bounces around based on water, food, and time of day. A 30-day rolling average is a much better description of where they actually are. The EMA is that rolling average, and the noisy daily reading is your raw model weights.

A small EMA helper, added to train.py:

class EMA:
    def __init__(self, model, decay=0.999):
        self.decay = decay
        self.shadow = {
            name: param.detach().clone()
            for name, param in model.named_parameters()
        }

    @torch.no_grad()
    def update(self, model):
        for name, param in model.named_parameters():
            self.shadow[name].mul_(self.decay).add_(param.detach(), alpha=1 - self.decay)

    @torch.no_grad()
    def copy_to(self, model):
        for name, param in model.named_parameters():
            param.copy_(self.shadow[name])

    def state_dict(self):
        return self.shadow

    def load_state_dict(self, state):
        self.shadow = state

Reading the important lines:

  • param.detach().clone() makes an independent copy that is not part of the computation graph. Without detach(), PyTorch would try to track gradients through your EMA bookkeeping, which you never want.
  • self.shadow[name].mul_(self.decay).add_(param, alpha=1 - decay) is the whole EMA in one line. It means shadow = 0.999 * shadow + 0.001 * current. Each update nudges the shadow copy 0.1% of the way toward the live weights, so it moves slowly and smoothly.
  • named_parameters() gives both the name and the tensor for every learnable weight, so the shadow dictionary lines up with the model by name.

Wiring it into training:

ema = EMA(model, decay=0.999)          # after creating the model

# ... inside the batch loop, immediately after scaler.update():
ema.update(model)

And when generating images, swap in the EMA weights:

import copy

ema_model = copy.deepcopy(model)
ema.copy_to(ema_model)
ema_model.eval()
# now sample using ema_model instead of model
Choosing the decay value

0.999 means the average covers roughly the last 1000 updates. That is a good default for runs of a few tens of thousands of steps. If your dataset is tiny and you only do a few thousand updates total, use 0.99 instead, because a 0.999 average would barely have moved away from the random starting weights by the time you stop.

Watch out

Add "ema": ema.state_dict() to your checkpoint saving, and load it back when resuming. If you forget, resuming silently restarts the EMA from the current weights and throws away all the smoothing you had accumulated.

6. The cosine noise schedule

Phase 2 mentioned that a cosine schedule is a common improvement over the linear one but did not show the code. Here it is.

The problem with the linear schedule is that it destroys the image too early. Real numbers from your current linear schedule versus a cosine one, for the same T of 1000:

Timestepᾱ with linear scheduleᾱ with cosine scheduleWhat that means
t = 1000.8950.972Both still mostly image
t = 2500.5210.846Linear has already lost half the signal
t = 5000.0780.492Linear is nearly pure noise at the halfway point
t = 7500.0030.143Linear has nothing left to learn from

With the linear schedule, well over half of your 1000 timesteps are spent on images that are already indistinguishable from pure static. Those training steps teach the network very little. The cosine schedule spreads the destruction out so that far more timesteps land in the range where there is still structure to recover.

Add this to schedule.py:

def cosine_beta_schedule(timesteps, s=0.008):
    steps = np.arange(timesteps + 1, dtype=np.float64)
    f = np.cos(((steps / timesteps) + s) / (1 + s) * np.pi * 0.5) ** 2
    alpha_bars = f / f[0]
    betas = 1 - (alpha_bars[1:] / alpha_bars[:-1])
    return np.clip(betas, 0, 0.999)

Then switch get_schedule() over to it:

def get_schedule():
    if config.SCHEDULE_TYPE == "cosine":
        betas = cosine_beta_schedule(config.TIMESTEPS)
    else:
        betas = np.linspace(config.BETA_START, config.BETA_END, config.TIMESTEPS)

    alphas = 1.0 - betas
    alpha_bars = np.cumprod(alphas)
    ...

And add SCHEDULE_TYPE = "cosine" to config.py.

  • This formula works backwards from the shape you want. It defines the ᾱ curve directly as a squared cosine, then recovers the β values from it by dividing each ᾱ by the previous one. That is the reverse of the linear approach, which picks β first and gets ᾱ as a consequence.
  • s=0.008 is a small offset that stops β from being exactly zero at the very first step. Use the standard value.
  • np.clip(betas, 0, 0.999) is a safety cap. Without it, the final few β values can reach 1.0, which makes sqrt(1 - alpha_bar) misbehave and can produce nan during sampling.
Watch out

Changing the schedule changes what the network learns to predict, so a model trained on the linear schedule will produce garbage if you sample it with the cosine schedule. Pick one and use it for both training and sampling. If you switch, retrain from scratch.

7. DDIM, for roughly 20x faster generation

Generating one image currently takes 1000 forward passes through the network. DDIM gets comparable quality in 50, using the exact same trained model. Nothing about training changes. Only the sampling loop changes.

Term: DDIM

DDIM (Denoising Diffusion Implicit Models) rewrites the reverse step so it does not have to move to the immediately previous timestep. Standard DDPM sampling can only go from t to t-1, so 1000 timesteps means 1000 steps. DDIM can jump from t straight to any earlier timestep, so you can visit only every 20th timestep and still land at 0.

The trick is that each DDIM step first estimates what the fully clean image would be, then re-noises that estimate to whatever timestep it is jumping to. It routes through a clean-image guess rather than crawling one step at a time. 

@torch.no_grad()
def sample_ddim(model, alpha_bars, num_images=8, num_steps=50):
    step_indices = torch.linspace(0, config.TIMESTEPS - 1, num_steps)
    step_indices = step_indices.round().long().flip(0)     # descending

    x = torch.randn(num_images, config.CHANNELS,
                    config.IMAGE_SIZE, config.IMAGE_SIZE,
                    device=config.DEVICE)

    for i in range(len(step_indices)):
        t_now = step_indices[i].item()
        t_prev = step_indices[i + 1].item() if i + 1 < len(step_indices) else None

        t = torch.full((num_images,), t_now, device=config.DEVICE, dtype=torch.long)
        predicted_noise = model(x, t)

        alpha_bar_now = alpha_bars[t_now]

        # step A: estimate the fully clean image from where we are
        x0 = (x - torch.sqrt(1 - alpha_bar_now) * predicted_noise) / torch.sqrt(alpha_bar_now)
        x0 = x0.clamp(-1, 1)

        if t_prev is None:
            x = x0
            break

        # step B: re-noise that estimate to the timestep we are jumping to
        alpha_bar_prev = alpha_bars[t_prev]
        x = torch.sqrt(alpha_bar_prev) * x0 + torch.sqrt(1 - alpha_bar_prev) * predicted_noise

    return x

Line by line on the parts that are new:

  • torch.linspace(0, TIMESTEPS-1, num_steps).round().long().flip(0) builds the list of timesteps to actually visit. With num_steps=50 you get 999, 979, 958, and so on down to 0. .flip(0) reverses it into descending order, since sampling runs backwards.
  • Step A is the forward shortcut formula rearranged to solve for the clean image instead of the noisy one. You know the noisy value, and the network just told you its noise guess, so you can subtract the noise out and rescale.
  • x0.clamp(-1, 1) is not optional. At high timesteps ᾱ is around 0.00004, so dividing by its square root multiplies everything by roughly 160. Tiny errors in the noise prediction get amplified into wildly out-of-range values. Clamping keeps the estimate inside the valid pixel range. Leave this out and the first few steps can poison the whole generation.
  • Step B is the plain forward shortcut formula again, applied to the estimated clean image, targeting t_prev. Notice it reuses the same predicted_noise rather than sampling fresh random noise, which is what makes this version deterministic: the same starting noise always produces the same image.
Picking the step count

50 steps is a good default. 100 steps gives slightly better quality. Below about 20 steps quality drops off noticeably. Because it is the same trained model, you can change this number freely between generations without retraining, so it is worth trying 20, 50, and 100 on the same starting noise and comparing.

Analogy

DDPM sampling is walking down a staircase one step at a time, 1000 steps. DDIM is realising that at each landing you can see roughly where the ground floor is, so you can take the stairs 20 at a time and still arrive in the right place.

8. Conditioning: telling it what to draw

Everything so far is unconditional: you get a random image from whatever the model learned, with no control. Conditioning adds the ability to ask for something specific. With MNIST that means asking for a 7. Text prompts are the same idea with a much heavier text encoder attached, which is well beyond a 4GB card, so class labels are the right version to learn on.

Step 1: feed the label into the network

You already have the machinery for this. The timestep is a number that gets embedded and added into every ResBlock. A class label is also just a number, so it takes the same path. 

self.label_embedding = nn.Embedding(config.NUM_CLASSES + 1, time_dim)

Then in the U-Net's forward:

def forward(self, x, t, labels):
    time_emb = self.time_embedding(t)
    time_emb = time_emb + self.label_embedding(labels)    # new
    ...
Term: nn.Embedding

nn.Embedding is a learnable lookup table. nn.Embedding(11, 512) holds 11 separate vectors of length 512, one per class. Passing in label 7 returns row 7. The network learns during training what each row should contain. It is simply a table of vectors that training fills in, indexed by class number.

Adding the label embedding onto the time embedding, rather than handling it separately, means every ResBlock now receives one combined signal saying both "this is timestep 400" and "this should be a 7." No other part of the U-Net needs to change.

Step 2: classifier-free guidance

Conditioning alone gives weak control. The model drifts toward generic images that vaguely satisfy the label. Classifier-free guidance fixes this, and it is the reason modern image generators follow prompts as closely as they do.

Term: Classifier-free guidance

During training, randomly replace the real label with a special "no label" value about 10% of the time. The single model therefore learns both jobs at once: generating with a label, and generating with no label at all. At generation time you run it twice per step, once with your label and once with the null label, then push the result away from the unconditional guess and toward the conditional one. You are measuring which direction the label pushes, then deliberately exaggerating it.

In the training loop:

labels = labels.to(config.DEVICE)

# 10% of the time, replace the label with the null class
drop = torch.rand(labels.shape[0], device=config.DEVICE) < 0.1
labels = torch.where(drop, config.NUM_CLASSES, labels)

predicted_noise = model(noisy_images, t, labels)

The null class is config.NUM_CLASSES, which is why the embedding table was created with NUM_CLASSES + 1 rows. For MNIST, real labels are 0 to 9 and the null label is 10.

In sampling, run the model twice and combine:

guidance_scale = 3.0

cond = model(x, t, labels)
uncond = model(x, t, torch.full_like(labels, config.NUM_CLASSES))

predicted_noise = uncond + guidance_scale * (cond - uncond)
  • (cond - uncond) is the direction the label is pulling in.
  • guidance_scale controls how hard you push along that direction. 1.0 means no guidance at all. 3.0 is a reasonable starting point. Higher values follow the label more strictly but reduce variety and can create harsh, oversaturated images.
  • The cost is that generation is now twice as slow, since every step runs the network twice. Combined with DDIM at 50 steps this is still 10x faster than your original 1000-step unconditional loop.
Watch out

This is the largest change in Phase 4 and it touches the U-Net, the training loop, and the sampling loop at once. Get an unconditional model working properly first. If conditioning produces nonsense, the usual cause is a mismatch between the null class index used in training and the one used in sampling.

How long training actually takes on your hardware

Rough expectations for an RTX 2050 with 4GB, so you can tell the difference between "this is slow" and "something is wrong." These assume mixed precision is on and the GPU is actually being used.

SetupRough time per epochRealistic total
MNIST, 32x32, batch 16, base 32 channels1 to 3 minutesRecognizable digits within 1 to 2 hours
Custom dataset, 5k images, 64x64, batch 83 to 8 minutesOvernight for something reasonable
Custom dataset, 64x64, base 64 channels8 to 20 minutesMultiple days, likely too slow to iterate on

Signs that something is wrong rather than merely slow:

  • Many times slower than the table. Check torch.cuda.is_available() again and watch nvidia-smi during training. GPU utilisation near zero means you are accidentally running on CPU.
  • GPU utilisation is low but memory is used. The GPU is waiting on data loading. Raise num_workers in the DataLoader, or check whether your images are very large files being resized down on every single load.
  • Loss is still flat after several epochs. This is not a speed problem. Check the debugging table in Phase 3.
Getting more done overnight

Train at 32x32 rather than 64x64 while you are still adjusting things. It is roughly four times faster per epoch, and almost every problem worth finding (broken shapes, bad schedule, no learning at all) shows up just as clearly at the smaller size. Move up to 64x64 only once you are confident the pipeline is correct.

With Phase 4 done you have essentially the full DDPM toolkit as it was published, running on a 4GB laptop. The remaining gap to something like Stable Diffusion is mostly scale plus one more architectural idea: moving out of pixel space into a compressed latent space, so the U-Net works on a small grid instead of full-resolution pixels. That is what makes 512x512 possible on consumer hardware, and it is the natural next thing to read about once this is all working.
