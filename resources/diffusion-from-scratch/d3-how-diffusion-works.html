Phase 2: How diffusion works

The complete theory: what noise has to do with any of this, what the network predicts, and why a U-Net specifically. No code yet, this phase is entirely about understanding, so that when you do write code, you know exactly what every line is for.

Medium~4 hours

The big picture, before any details

Here is the entire idea of diffusion models in one paragraph. Everything after this section is just unpacking each part of it carefully.

The whole idea, in one go

Take a real photo. Add a little bit of random static to it. Add a little more. Keep going, hundreds of times, until the photo is 100% pure static with absolutely no trace of the original image left, this is called the forward process, and it needs no neural network at all, it's just a fixed, known math formula. Now train a neural network to do the reverse: given a noisy image and "how noisy it currently is," guess what noise was added, so that subtracting the guessed noise moves the image one small step back toward being clean. Once the network is good at this one small "denoise a little" step, you can start from pure random static (something that looks like the fully noised end-state) and repeatedly apply the network's small denoising step hundreds of times. Each step removes a little more noise. At the end, you are left with an image that was never a real photo, the network invented it, but which looks like it belongs to the same kind of data it was trained on.

That's the entire trick. A diffusion model never learns to draw an image in one shot. It only ever learns the much easier job of "slightly improve a noisy image," and generation is just that easy job repeated many times in a row.

Term: Diffusion (the name)

The name comes from physics, diffusion is the process of particles (like a drop of ink) spreading out randomly in a liquid until they're evenly mixed. The "forward process" of gradually turning a sharp image into uniform random noise is mathematically the same kind of process as ink diffusing into water. The model's whole job is learning to run that spreading process backward.

Before going any deeper, here's the entire system laid out as two separate pipelines, training (how the model learns) and sampling (how you generate a new image afterward). Every box in both diagrams gets its own full explanation later in this phase; for now, just get the overall shape of each pipeline into your head.

What an image actually is to a computer

Before touching noise or networks, you need to be completely solid on how an image is represented as numbers, because literally everything in this project is operations on grids of numbers.

Term: Tensor

A tensor is just a grid of numbers with a specific shape (how many numbers along each dimension). A single number is a tensor with 0 dimensions. A list of numbers is a 1-dimensional tensor. A grid (rows and columns) is 2-dimensional. Images and batches of images need more dimensions than that, described below. PyTorch's entire job is storing tensors and doing fast math on them, optionally on the GPU.

A single color image is stored as a tensor with 3 dimensions:

  • Channels, for a normal color image, 3 channels: Red, Green, Blue. Each channel is its own full grid of numbers.
  • Height, number of pixel rows.
  • Width, number of pixel columns.

So a 64×64 color image is a tensor of shape (3, 64, 64), three stacked grids, each 64 numbers tall and 64 numbers wide, one grid per color channel. Every individual number in the grid is a pixel's brightness for that channel, typically stored as a value between 0 and 1 (or sometimes -1 and 1) rather than the more familiar 0-255, neural networks train much better on small, centered number ranges than on raw 0-255 integers.

Term: Batch

Training is almost never done on one image at a time, many images are processed together as a batch, because GPUs are efficient at doing the same operation on many pieces of data simultaneously. A batch of 16 images of size 64×64 is a 4-dimensional tensor of shape (16, 3, 64, 64), batch size, then channels, then height, then width. This ordering, (batch, channels, height, width), is PyTorch's standard convention and you'll see it everywhere, often abbreviated B, C, H, W.

Tensor operations you'll actually use, explained

A handful of operations on tensors come up constantly throughout this project. Understanding these deeply now will make every later section (noise schedule, U-Net, training loop) much easier to follow, since they're all just these few operations combined.

Element-wise operations

Term: Element-wise operation

An element-wise operation applies the same simple operation independently to every matching position across one or more tensors of the same shape. Addition, subtraction, multiplication, and the math functions (sqrt, exp, and so on) are all element-wise by default in PyTorch. If you add two tensors of shape (3, 64, 64), the result is also shape (3, 64, 64), where each of the 3×64×64 = 12,288 individual numbers is simply the sum of the two corresponding numbers from each input.

This matters because the entire shortcut formula (sqrt(alpha_bar_t) * clean_image + sqrt(1 - alpha_bar_t) * noise) and the entire loss calculation ((real_noise - predicted_noise) ** 2) are just chains of element-wise operations across whole tensors at once, no explicit loops over individual pixels are ever written; PyTorch and the GPU handle applying the operation to every element simultaneously.

Broadcasting

Term: Broadcasting

Broadcasting is the rule PyTorch uses to combine two tensors of different shapes in an element-wise operation, by automatically "stretching" the smaller one to match, without actually copying data in memory. A single number (shape with no dimensions) can be added to a tensor of any shape, the single number is treated as if it were repeated at every position. This is precisely how a per-image, per-batch alpha_bar_t value (one number per image in the batch) gets combined with a full image tensor: the single number for each image is automatically broadcast across every pixel and channel of that image.

Worked example: broadcasting a per-image scalar

Suppose you have a batch of 4 images, shape (4, 3, 64, 64), and for each image in the batch you sampled a different random timestep. That gives you 4 different alpha_bar_t values, one per image. You reshape this list of 4 numbers into shape (4, 1, 1, 1), still 4 numbers, just arranged to line up with the batch dimension. Now multiply this (4, 1, 1, 1) tensor against your (4, 3, 64, 64) image batch. Broadcasting automatically repeats each of the 4 numbers across all 3 channels and all 64×64 pixels of its matching image. The result: every image in the batch gets its own correctly-matched noise amount, all calculated at once, in one line, with no loop over the batch needed.

Indexing

Term: Indexing / gather

Your noise schedule (β, α, ᾱ) is stored as one long 1-dimensional tensor of length T (e.g. 1000 values). Given a batch of randomly sampled timesteps, itself a tensor of integers, one per image in the batch, you need to look up the corresponding schedule value for each image's specific timestep, all at once. This is done with tensor indexing: alpha_bar[timesteps], where timesteps is a tensor of index values, returns a new tensor containing the alpha_bar value at each of those specific indices, one per image in the batch, effectively a batch lookup in a single line.

Worked example: batch lookup
Batch positionSampled timestepLooked-up alpha_bar
image 0t = 50alpha_bar[50]
image 1t = 730alpha_bar[730]
image 2t = 12alpha_bar[12]
image 3t = 999alpha_bar[999]

If timesteps = torch.tensor([50, 730, 12, 999]), then alpha_bar[timesteps] returns all four looked-up values as one tensor of shape (4,), in one indexing operation, no Python for-loop needed, which matters for speed since Python loops don't run on the GPU efficiently.

permute and squeeze/unsqueeze

Term: permute

tensor.permute(new_order) reorders a tensor's existing dimensions without changing any values, used, for example, when converting a PyTorch image tensor (channels, height, width) into the (height, width, channels) order that matplotlib's imshow expects: tensor.permute(1, 2, 0) says "put what was dimension 1 first, dimension 2 second, dimension 0 last."

Term: unsqueeze / squeeze

tensor.unsqueeze(dim) inserts a new dimension of size 1 at the given position, used constantly to reshape a plain 1-dimensional list of per-image values (like the alpha_bar lookup above) into the (batch, 1, 1, 1) shape broadcasting needs. tensor.squeeze(dim) does the reverse, removing a size-1 dimension.

Example: a tensor of shape (4,), after .unsqueeze(1).unsqueeze(2).unsqueeze(3) (or equivalently, .view(4, 1, 1, 1)), becomes shape (4, 1, 1, 1), ready to broadcast-multiply against a (4, 3, 64, 64) image batch.

The forward process: deliberately destroying an image

The forward process (also called the diffusion process) takes a real image and gradually adds random noise to it over a series of timesteps, until nothing recognizable is left.

Term: Timestep

A timestep is just a step number in this gradual noising process, think of it as a frame number in a slow-motion video of an image turning into static. We call the total number of timesteps T. A common choice is T = 1000, meaning the clean image is step 0, and by step 1000 it's pure random noise. Every number in between represents "a little more noise than the step before it."

Term: Gaussian noise

The specific kind of randomness added at each step is Gaussian noise, random numbers drawn from a bell-curve distribution centered at zero (most random values are small and close to zero, occasionally you get a bigger positive or negative value, following the familiar bell-curve shape). This particular kind of randomness is chosen because it has convenient mathematical properties that make the whole forward and reverse process solvable, you don't need to know the deep math reason, just that "noise" in diffusion models always specifically means this bell-curve-shaped randomness, not, say, random pixel scrambling.

Watch out: this trips up a lot of beginners

The forward process (image → noise) uses no neural network at all. It's a fixed formula you apply directly. The neural network is only ever trained to do the reverse direction. It's easy to assume both directions need "the model," but only denoising does.

The noise schedule: how much noise gets added at each step

You need a rule for exactly how much noise to mix in at each timestep. This rule is called the noise schedule, and it's decided before training even starts, it's fixed, not learned.

Term: Beta (β) schedule

At every timestep t, there's a small number called βt (beta) that controls how much new noise gets mixed in at that specific step. Early on (small t), β is tiny, barely any noise is added, so the image is still almost entirely recognizable. Later on (large t), β is larger, more noise gets mixed in per step. The full list of β values across all T timesteps is called the noise schedule.

Analogy

Imagine slowly turning up radio static over a song, on a volume dial that you turn a tiny amount every few seconds. The schedule is simply your plan for exactly how much to turn the dial at each moment. A "linear schedule" turns it up by the same small amount every time. A "cosine schedule" (a common improvement) turns it up more gently at the very start and end, and faster through the middle, this tends to preserve useful image structure for longer near t=0, which tends to work better in practice. Either way, the point is: this schedule is a plan you write down in advance, not something the network figures out.

Two more symbols you will constantly see in any diffusion code or paper, both directly built from the betas:

  • αt (alpha), simply defined as 1 − βt. It represents "how much of the original signal survives this one step" (as opposed to beta, which represents how much noise is mixed in).
  • ᾱt (alpha-bar), the running product of every alpha from step 1 up through step t (that is, α₁ × α₂ × ... × α_t). This single number tells you "what fraction of the original clean image's structure is still mathematically present by timestep t, considering every step of noise added so far." This is the number that makes the shortcut in the next section possible.
Watch out

The Greek letters (β, α, ᾱ) look scary in papers, but they are only ever plain numbers between 0 and 1, calculated once as a fixed list at the very start of your code, a small array of length T. You never solve for them by hand; you just look them up by timestep number whenever you need them.

Here's how those three numbers are actually built, one from the other, as a simple pipeline, and what they look like as real numbers across all 1000 timesteps.

The one-step shortcut: the most important formula in this project

Here is the single fact that makes diffusion models practical to train at all. You do not need to actually simulate all 1000 tiny noising steps one after another to get a noisy image at some timestep t. There's a direct shortcut formula that jumps straight from the clean image to "the image after exactly t steps of noise," in one line: 

noisy_image = sqrt(alpha_bar_t) * clean_image + sqrt(1 - alpha_bar_t) * random_noise

Let's unpack every piece of that line in plain words:

  • clean_image, your real training image, as a tensor.
  • random_noise, a freshly sampled tensor of Gaussian noise, the exact same shape as the image, generated fresh every single time you use this formula.
  • alpha_bar_t, the running-product number from the previous section, looked up for whichever timestep t you're currently working with.
  • The formula is a weighted mix of the clean image and pure noise. At small t, alpha_bar_t is close to 1, so sqrt(alpha_bar_t) is close to 1 and sqrt(1 - alpha_bar_t) is close to 0, meaning the result is almost entirely the clean image, barely any noise. At large t (close to T), alpha_bar_t is close to 0, so it flips: almost entirely noise, barely any trace of the clean image.
Analogy

It's like mixing two paint cans, one can of "the original picture" and one can of "static noise", in a ratio that depends only on which timestep you picked. You don't need to physically pour a tiny bit in a thousand separate times to get to the mix you want; you can compute the exact final ratio and mix it in one pour. That's exactly what this formula does mathematically.

Why this matters for training

Because of this shortcut, during training you can pick a completely random timestep for each training image, jump directly to that noise level in one calculation, and train on it, without ever needing to simulate the earlier steps. This is a huge part of why diffusion models are practical to train at all: every single training example is one cheap formula, not a slow simulated sequence.

Worked example: running the formula with real numbers

Formulas with Greek letters can feel abstract until you've seen actual numbers pass through them once. Let's trace through the shortcut formula for a single, simplified pixel value, at three different timesteps, using a linear schedule with T = 1000, β ranging from 0.0001 to 0.02.

Setup

Say one particular pixel in your clean image has a value of 0.8 (recall pixel values are rescaled to roughly 0-1, or -1 to 1, not the raw 0-255 range). Say the random noise generated for this pixel happens to be -0.3 (Gaussian noise can be negative, remember, it's a bell curve centered at zero). We'll compute the noisy value at three timesteps using the formula: 

noisy_pixel = sqrt(alpha_bar_t) * 0.8 + sqrt(1 - alpha_bar_t) * (-0.3)
t = 10 (very early: barely any noise yet)

At this early timestep, alpha_bar is still very close to 1: for the linear schedule above it is approximately 0.9978. Then sqrt(0.9978) ≈ 0.9989 and sqrt(1 - 0.9978) = sqrt(0.0022) ≈ 0.047.

noisy_pixel = 0.9989 × 0.8 + 0.047 × (-0.3) = 0.799 − 0.014 = 0.785

Barely changed from the original 0.8, exactly as expected this early in the process.

t = 500 (halfway through)

By the midpoint the linear schedule has already destroyed most of the signal: alpha_bar has dropped to approximately 0.078 (the exact value depends on the schedule's shape, and the cosine schedule later in Phase 4 keeps it near 0.49 here). Then sqrt(0.078) ≈ 0.279 and sqrt(1 - 0.078) = sqrt(0.922) ≈ 0.960.

noisy_pixel = 0.279 × 0.8 + 0.960 × (-0.3) = 0.223 − 0.288 = -0.065

The value has moved far away from the original 0.8. The noise term (0.288 in size) is now larger than the signal term (0.223), so this pixel is no longer recognizably "mostly the original".

t = 999 (nearly the end: almost pure noise)

Near the very end, alpha_bar is close to 0: approximately 0.00004 (4 × 10-5). Then sqrt(0.00004) ≈ 0.0064 and sqrt(1 - 0.00004) ≈ 1.0.

noisy_pixel = 0.0064 × 0.8 + 1.0 × (-0.3) = 0.005 − 0.300 = -0.295

The original clean value of 0.8 has almost no influence left, the result is dominated entirely by the noise term, exactly matching the intuition that by t = 999 the image should be almost indistinguishable from pure static.

In actual code, this exact calculation happens all at once, across every one of the (batch × channels × height × width) numbers in your batch, using the tensor operations from the previous section. The three-line trace above is just one single number's worth of that much bigger, fully parallel calculation. It's there to make the formula concrete before you see it running on real image tensors.

The reverse process: what we actually want to learn

Now flip direction. The reverse process is: given a noisy image at some timestep t, produce a slightly less noisy image at timestep t−1. Unlike the forward process, this direction has no fixed formula, going from "static" back to "meaningful image structure" is not something you can compute directly, because there are countless possible clean images that could have produced the same noisy result. This is precisely the part that requires a trained neural network: it has to learn, from data, a good guess at which direction "less noisy" points in.

Analogy

Think of un-mixing cream from coffee. Mixing them (forward: order → chaos) is trivial and happens on its own. Un-mixing them (reverse: chaos → order) is not something you can compute with a simple formula, you'd need something that has learned, from experience, what patterns of swirling cream tend to un-mix into. The neural network is that learned "un-mixer," except instead of cream and coffee, it's untangling noise from image structure.

What, exactly, does the neural network predict?

This is the detail that confuses most beginners, so slow down here. Given a noisy image and the timestep number, you might expect the network's job is to directly output "the clean image." It's usually not. In the standard, most common formulation (called DDPM, after the paper that introduced it), the network's job is much narrower:

Term: Noise prediction

The network takes in a noisy image (at some timestep t) and outputs its best guess at exactly which noise tensor was added to produce it, a prediction the same shape as the image, meant to match the actual random_noise tensor from the shortcut formula in the previous section. It is not asked to guess the clean image directly. It's asked the narrower question: "if I mixed some clean image with some noise to get this, what did that noise probably look like?"

Analogy

Imagine looking at a hazy, foggy photo. Instead of being asked to redraw the whole clear scene from memory, you're asked something narrower: "just draw the fog itself, the pattern of grey haze sitting on top of the real scene." That's a much easier question to answer. And once you have a good drawing of just the fog, subtracting it gets you approximately the same clear photo either way. Predicting the noise turns out to be an easier, steadier target for a network to learn than predicting the clean image directly.

Once the network predicts the noise, getting a slightly-less-noisy image is straightforward arithmetic: you take the predicted noise, scale it correctly using the same α/β numbers from the schedule, and subtract a scaled amount of it from the current noisy image. The exact subtraction formula is what's called the sampling formula, covered in the sampling loop section further down, for now, the important idea is just: network predicts noise → simple formula uses that prediction to step the image toward being cleaner.

Watch out

When you read other papers or code, you may encounter variants that predict the clean image directly ("x0-prediction") or a different combined quantity called "v-prediction." These are legitimate alternatives used in some newer models, but noise-prediction (often written as predicting ε, the Greek letter epsilon) is the original, simplest, and most common starting point, this guide sticks to it, and you should too for your first working model.

Why a U-Net, specifically

You now know the job: take a noisy image plus a timestep number, output a predicted noise tensor of the exact same shape as the input image. Any neural network architecture that can take an image in and put an equally-sized image out could in principle be tried. A U-Net is the specific architecture that has become the standard choice, for good, learnable reasons.

Term: Architecture

The architecture of a neural network is simply its overall structure, how many layers it has, what kind of layers, and how they connect to each other. "U-Net" is the name of one specific, well-known architecture, the same way "sedan" or "SUV" names a particular structural layout of a car.

Two things any good architecture for this job needs to do well:

  • Understand the image at multiple scales. Removing noise needs both fine detail information (exact pixel-level texture) and broad structural information (is this shape roughly a face, a car, a cat, where are the big regions). A network that only ever looks at small local patches can't "see" the big picture; a network that immediately shrinks everything down loses fine detail.
  • Output something the same size as the input. The predicted noise tensor must match the image's height and width exactly, so whatever the architecture does internally, it has to end up back at the original resolution.

A U-Net satisfies both by shrinking the image down through several stages (seeing progressively broader context), then growing it back up through a mirrored series of stages back to full size, and, crucially, directly reusing the detailed fine-grained information from the shrinking half while rebuilding the growing half. This shape, drawn out, literally looks like the letter U, which is where the name comes from.

nn.Module: how every PyTorch network is actually built

Before walking through the U-Net's pieces, it helps to understand the pattern every single one of those pieces follows in code, since it's always the same two-part structure.

Term: nn.Module

nn.Module is the base class that every custom layer, block, or full network inherits from in PyTorch. Inheriting from it gives your class two things for free: automatic tracking of every learnable weight you define inside it (so .parameters() and .to(device) and .state_dict() all work without you writing any bookkeeping code), and the ability to be called like a function, writing my_layer(some_input) automatically runs your custom logic.

Every nn.Module subclass you write follows the same two-method shape:

def __init__(self):

The constructor, run once when you create the layer. This is where you declare every sub-layer you'll need (convolutions, normalization, activations) and store them as attributes on self. Declaring a layer here (e.g. self.conv1 = nn.Conv2d(...)) is what lets nn.Module automatically discover and track its weights, you must always call super().__init__() as the very first line, so the base class's own setup runs before yours.

def forward(self, x):

Defines what actually happens when data flows through this module, take the input x, pass it through the sub-layers you declared in __init__ in whatever order and combination you want, and return the result. This method is never called directly by name; calling the module itself (output = my_layer(x)) automatically triggers forward behind the scenes, while also setting up the bookkeeping autograd needs to later compute gradients through everything that happened inside it.

Concrete example: a tiny residual block as an nn.Module 
class ResBlock(nn.Module):
    def __init__(self, channels):
        super().__init__()
        self.norm1 = nn.GroupNorm(8, channels)
        self.conv1 = nn.Conv2d(channels, channels, 3, padding=1)
        self.act = nn.SiLU()
        self.norm2 = nn.GroupNorm(8, channels)
        self.conv2 = nn.Conv2d(channels, channels, 3, padding=1)

    def forward(self, x):
        h = self.conv1(self.act(self.norm1(x)))
        h = self.conv2(self.act(self.norm2(h)))
        return x + h   # the residual shortcut

Notice the last line: return x + h, the original input x is added directly to the processed result h. This is exactly the residual shortcut described in the U-Net section below: the block only had to learn h as a correction on top of x, rather than reconstructing everything from scratch.

Your full U-Net will also be one big nn.Module. Its __init__ creates a whole collection of smaller modules, several ResBlocks, downsampling layers, the bottleneck, upsampling layers. Its forward method then wires all of them together: calling the encoder stages, saving their outputs for the skip connections, running the bottleneck, then calling the decoder stages while joining in those saved encoder outputs at the matching resolution.

The U-Net, piece by piece

Here is the full architecture at a glance, with actual tensor shapes and channel counts at every stage, using the exact configuration this guide's code builds in Phase 3 (base channels = 32, multipliers 1/2/4, image size 64×64). Every box below is explained in detail in the sections that follow.

The encoder (left side, shrinking)

Term: Encoder

The encoder half of the U-Net repeatedly shrinks the image spatially (fewer pixels of height and width at each stage) while increasing the number of channels (going from 3 color channels up into dozens or hundreds of learned "feature channels", each one a grid the network has learned to fill with some useful pattern-detection signal, not necessarily anything humans can name). Shrinking width/height while growing channels is how the network trades "exact pixel position" for "richer description of what's roughly in this area."

Term: Downsampling

Downsampling is the specific operation that shrinks height and width, typically implemented as a strided convolution or a pooling operation that takes, say, every 2×2 block of pixels and reduces it to a single value, halving both dimensions.

Term: Convolution (conv layer)

A convolution is the basic building block used throughout the U-Net. A small grid of learnable numbers (called a kernel or filter, often 3×3) slides across the image, and at every position it multiplies its numbers against the pixels underneath it and sums the result into a single output value. Repeating this across the whole image produces a new grid, this is how the network detects local patterns like edges, textures, or eventually (in deeper layers) much more abstract shapes, since each layer's output feeds the next layer's convolutions.

Analogy

A convolution kernel is like a small rubber stamp with a specific texture pattern carved into it. You press it against every position of the image and record "how well did the stamp match here." Early layers' stamps end up detecting simple things (edges, color blobs). Because each layer feeds into the next, later layers combine simple detections into detectors for much more complex, abstract things, without you ever hand-designing what any individual stamp looks for. Training is what carves the right pattern into each stamp automatically.

A convolution with actual numbers

Worked example: one 3×3 kernel, one position

Say a tiny patch of your image (just one channel, to keep it simple) looks like this 3×3 grid of pixel values:

0.20.40.1
0.30.90.2
0.10.50.3

And say the learned 3×3 kernel currently contains these numbers:

010
1-41
010

The convolution multiplies each kernel number by the pixel underneath it, in the same position, then adds up every result: 

(0.2×0) + (0.4×1) + (0.1×0) +
(0.3×1) + (0.9×-4) + (0.2×1) +
(0.1×0) + (0.5×1) + (0.3×0)

= 0 + 0.4 + 0 + 0.3 - 3.6 + 0.2 + 0 + 0.5 + 0
= -2.2

That single number, -2.2, becomes one value in the output grid, at the position that matches the center of this patch. The kernel then slides one position over (or more, if stride is greater than 1) and repeats this same multiply-and-add for the next patch, continuing across the entire image to fill in the full output grid. The specific kernel used in this example happens to be a classic edge-detecting pattern from older, non-learned image processing, but in a real trained network, the numbers inside the kernel aren't set by hand like this. They start random and are slowly adjusted by training until they end up detecting whatever patterns turn out to be useful for the task.

Term: Receptive field

A single 3×3 convolution only ever looks at a 3×3 neighborhood at once, this is its receptive field, the region of the input that can affect one output number. But because layers stack, the receptive field grows with depth: a second 3×3 convolution stacked on top of the first can indirectly "see" a 5×5 region of the original input (since each of the 3×3 positions it looks at was itself calculated from a 3×3 neighborhood one layer back). This is a second, extra reason (alongside downsampling) that stacking many convolution layers lets deep layers respond to increasingly large regions of the original image, eventually covering most or all of it by the time you reach the bottleneck.

The bottleneck

Term: Bottleneck

The bottleneck is the middle of the U, the point of smallest height/width and largest channel count. This is where the network's representation of the image is most compressed and most abstract, containing broad "what kind of scene/object is this" information rather than pixel-level detail.

The decoder (right side, growing back)

Term: Decoder / Upsampling

The decoder half mirrors the encoder in reverse: it repeatedly grows the spatial size back up (upsampling) while decreasing channel count, stage by stage, until it's back at the original image's height, width, and channel count (3, for RGB, or more precisely, 3 again since we're predicting noise in the same shape as the input image).

Skip connections: the part that makes "U" shaped nets special

Term: Skip connection

A skip connection directly copies the output of an encoder stage across to the matching decoder stage at the same resolution, combining it with what the decoder computed there (typically by concatenating the two together along the channel dimension). Without skip connections, all the fine, precise pixel-level detail that existed early in the encoder would have to survive being squeezed all the way down to the bottleneck and back, in practice, a lot of that fine detail would get lost. Skip connections let the decoder "cheat" by directly seeing the original fine detail from the corresponding encoder stage, while still benefiting from the broad contextual understanding that passed through the bottleneck.

Analogy

Imagine restoring a damaged photograph. You'd want both a zoomed-out sense of the whole scene (to know what should logically be there) and the original close-up scraps of the photo itself (for exact detail) side by side on your desk, rather than trying to redraw fine detail purely from memory of the zoomed-out view. Skip connections give the decoder exactly that: the zoomed-out understanding from the bottleneck, plus direct access to the matching-resolution fine detail from the encoder, at every stage going back up.

Residual blocks: the actual repeated unit inside each stage

Term: Residual block (ResBlock)

Inside each down/up stage, the actual repeated building unit is usually a residual block: a small stack (typically two) of convolution layers, plus a direct shortcut path that adds the block's original input straight onto its output. So the block only has to learn a "correction" or "residual" on top of what came in, rather than having to reconstruct its entire input from scratch through the convolutions. This makes very deep networks much easier to train successfully, a well-established trick borrowed from a famous architecture called ResNet, used across almost all modern image networks, diffusion U-Nets included.

Normalization and activation: the small pieces between convolutions

Term: Normalization (GroupNorm)

Between convolutions, a normalization layer rescales its input's numbers to have a consistent, stable range (roughly zero-centered, controlled spread) before passing them on. Without this, numbers can drift to extreme values as they pass through many stacked layers, making training unstable or painfully slow. Diffusion U-Nets commonly use a variant called GroupNorm, which normalizes within small groups of channels, you don't need to implement the math yourself, PyTorch provides it as a ready-made layer (torch.nn.GroupNorm) that you'll simply insert into your residual blocks.

Term: Activation function

An activation function is a simple non-linear function applied to every number after a convolution, without it, stacking many linear layers (convolutions are linear operations) would mathematically collapse into being no more powerful than a single layer, no matter how many you stack. A common choice in modern diffusion U-Nets is called SiLU (also known as Swish), you don't need to know its formula by heart, just that it's a standard, ready-made PyTorch layer (torch.nn.SiLU) you insert after normalization, in every block.

Term: Attention (self-attention layer)

Convolutions only look at a small local neighborhood of pixels at once (as wide as the kernel, e.g. 3×3). Sometimes the network needs to relate distant parts of the image to each other directly, for example, making sure both eyes in a generated face are consistent with each other even though they're far apart in the grid. An attention layer lets every position in the feature grid directly look at every other position and weigh how relevant each one is, regardless of distance. Full attention is memory-expensive, so on a 4GB GPU you'll typically only add one attention layer at the bottleneck (the smallest, most compressed stage) rather than at every resolution, this is a normal, standard simplification, not a corner-cutting hack unique to weak hardware; even large diffusion models only use attention at select resolutions.

Attention, mechanically: what's actually inside it

The previous section gave you attention's job ("let distant positions directly relate to each other"). Here's how it actually accomplishes that, since you'll need this understanding to read or write attention code.

First, the feature grid coming out of the bottleneck (shape (batch, channels, height, width)) gets reshaped so that every spatial position becomes its own individual "token", a vector of length channels. A grid that was 16×16 spatially, with 256 channels, becomes 256 separate position-tokens, each a vector of length 256 (this is exactly the einops.rearrange operation shown in the einops section: "b c h w -> b (h w) c").

Term: Query, Key, Value (Q, K, V)

For every position-token, three separate learned linear layers (nn.Linear) transform it into three different vectors: a Query, a Key, and a Value. Intuitively: the Query represents "what this position is looking for," the Key represents "what this position has to offer, as advertised to others," and the Value represents "the actual content this position will contribute if chosen as relevant." All three come from the same input token, just passed through three separately-learned weight matrices.

Term: Attention score / softmax

Every position's Query is compared against every position's Key (via a dot product, multiply matching elements and sum, a similarity measure), giving a grid of raw "how relevant is position j to position i" scores. These raw scores are passed through a softmax function, which rescales a list of numbers so they're all positive and sum to exactly 1, turning raw scores into something interpretable as "percentage of attention to pay to each other position." Finally, each position's output is computed as a weighted sum of every position's Value vector, weighted exactly by these softmax percentages.

Analogy

Think of a room full of people at a conference, each holding a name badge (their Key) and looking for someone specific (their Query). Every person compares their search criteria against every badge in the room and decides what fraction of their attention to give each other person (softmax turns "how good a match" into "percentages that add up to 100%"). They then form their own understanding by blending together what each person actually has to say (their Value), weighted exactly by how much attention they decided to pay each one. Every person in the room does this simultaneously, that's why it's called self-attention, the room is attending to itself.

Real attention works on hundreds of positions at once, which is hard to follow by eye. Here's the exact same process with real numbers, shrunk down to just 3 positions, so you can see every step happen.

After this weighted blending, the tokens are reshaped back into the original (batch, channels, height, width) grid shape and continue through the rest of the U-Net as normal. You don't need to work out the matrix-multiplication form of this by hand (commonly written as softmax(QKᵀ/√d)V in papers) to use it, knowing what each of the three letters means and why softmax turns scores into a weighted blend is enough to understand any attention code you read or adapt.

Telling the network which timestep it's looking at

There's one problem left unsolved: the network needs to behave differently depending on how noisy the input currently is. Denoising a barely-noisy image (small t) is a different job from denoising something that's almost pure static (large t). So somehow, the timestep number t has to be fed into the network alongside the image itself.

You cannot simply feed in the raw integer (like "347") as one extra number, neural networks work far better with richer, higher-dimensional representations than a single bare number, and a raw integer gives the network no useful sense of "347 is fairly close to 350 but very different from 2." The standard solution is:

Term: Sinusoidal timestep embedding

A sinusoidal embedding turns the single integer t into a whole vector (list) of numbers. It does this using sine and cosine waves at many different speeds, all read at the point t. If you've seen the term "positional encoding" before, in Transformer language models, this is the same idea, just reused here for "how much noise" instead of "which word position." The resulting vector has a useful property: nearby timesteps produce similar-looking vectors, so the network can learn to read "how large is t" from the pattern, without you having to build that in by hand. This is a fixed formula, not something the network learns, and the PyTorch code for it is short and copyable, you don't need to invent this formula yourself, just understand what job it's doing.

After computing this sinusoidal vector, it's passed through one or two small fully-connected layers (a tiny mini neural network of its own, sometimes called the time MLP) that let the network learn a more useful transformation of the raw sinusoidal pattern. The result, a vector of numbers representing "this is timestep t", is then injected into every residual block throughout the whole U-Net (usually added onto the feature grid right after the first convolution in each block), so every single stage of the network, from the very first layer to the very last, knows what noise level it's currently dealing with.

Analogy

Think of the timestep embedding as a note passed to every single worker on an assembly line at the same time, saying "today's batch is 80% damaged, adjust your technique accordingly." Every stage of the network, early, middle, late, gets this same reminder, so its behavior can adapt to exactly how noisy the current input is, rather than only the first layer knowing.

The training loop, step by step

You now have every ingredient. Here is the exact sequence of steps that happens, repeatedly, for every batch during training, walk through this slowly, because this loop is the entire training script in miniature.

  1. Take a batch of real images

    Pulled from your dataset, already resized and converted to tensors, shape (B, 3, H, W).

  2. Sample a random timestep for each image in the batch

    A separate random integer between 0 and T, independently for every image in the batch, so within one batch, different images are being trained at completely different noise levels. This variety is important: over many batches, the network sees examples spanning every noise level, which is exactly what it needs since at generation time it must handle every timestep from T down to 0.

  3. Sample fresh random noise

    Generate a tensor of Gaussian noise, the same shape as the image batch. This is the "ground truth" noise the network will be trained to predict, remember it, you'll need it again in step 5.

  4. Create the noisy image using the shortcut formula

    Apply the one-step formula from earlier (sqrt(alpha_bar_t) * clean_image + sqrt(1 - alpha_bar_t) * noise) using the timestep from step 2 and the noise from step 3. This gives you the noisy input the network will actually see.

  5. Feed the noisy image and timestep into the U-Net

    The U-Net takes the noisy image tensor and the timestep (converted into its sinusoidal embedding, as covered above) and outputs a predicted noise tensor of the same shape as the image.

  6. Compare predicted noise to the actual noise

    Compute the loss: how different is the network's predicted noise (step 5) from the real noise you generated in step 3? This comparison is explained fully in the next section.

  7. Update the network's weights

    Using the loss from step 6, PyTorch's automatic differentiation works out how every single weight in the U-Net should be nudged to reduce that loss slightly, and an optimizer (a standard choice is Adam or AdamW, both ready-made in PyTorch) applies that nudge to every weight.

  8. Repeat, for thousands of batches

    Go back to step 1 with a new batch. One full pass through your entire dataset is called an epoch; you'll typically train for many epochs, watching the loss trend downward over time.

Term: Optimizer

An optimizer is the algorithm that decides exactly how much to change each weight, given the direction (from automatic differentiation) it should move in. Plain gradient descent moves every weight by a fixed small amount in the right direction each time; Adam (and its slightly improved variant AdamW, generally the better default today) instead adapts the step size per-weight based on that weight's recent history, which in practice trains much faster and more reliably. You will not implement this yourself, torch.optim.AdamW is a single ready-made line.

Term: Learning rate

The learning rate is a single number controlling how big each weight update step is. Too high, and training becomes unstable or the loss diverges (grows instead of shrinking); too low, and training crawls forward barely improving. A common reasonable starting point for training small diffusion U-Nets is around 1e-4 (0.0001), you will tune this by watching the loss curve, not by deriving it mathematically.

Term: Epoch

One epoch means the training loop has seen every image in your dataset exactly once (across however many batches that takes). Training runs for many epochs, commonly tens to low hundreds for a small custom diffusion model, since the network needs to see the same images multiple times, at different randomly-sampled timesteps, before the patterns really sink in.

What backward() and step() actually do

Step 7 of the training loop ("update the network's weights") is doing a lot of work behind one innocent-looking line of code. It's worth understanding what's actually happening, since this exact three-line pattern, zero_grad(), backward(), step(), appears in every PyTorch training loop you will ever write, for any model, not just this one.

Term: Computation graph

As your batch flows forward through the U-Net, every convolution, every normalization, every addition, PyTorch silently builds a computation graph behind the scenes: a record of every single operation that was performed and in what order, connecting the input all the way through to the final loss value. This recording happens automatically for any tensor involved in a chain of operations that eventually needs gradients (in other words, your model's weights), which is why you don't have to set anything up by hand for it to work.

Term: Gradient

For any single weight in the network, its gradient, how it relates to the loss, answers: "if I nudged this one weight up very slightly, would the loss go up or down, and by roughly how much?" A gradient is really just a slope, the same idea as the slope of a line from basic algebra, just worked out for a function with millions of inputs (the weights) instead of one.

loss.backward()

This single call walks the entire recorded computation graph backward, from the loss value all the way back to every weight that contributed to producing it, using the calculus chain rule at each step (multiplying local slopes together to get the overall slope from a weight all the way to the final loss), entirely automatically. This process is called backpropagation. After this call finishes, every weight tensor in your model has a new .grad attribute populated with its computed gradient, the weights themselves haven't changed yet, only the gradients have been computed and stored, ready for the optimizer to use.

optimizer.step()

Now the optimizer reads every weight's freshly calculated .grad value and actually changes the weight, moving it a small amount in the direction that reduces the loss (the opposite direction from the gradient, since the gradient points toward increasing loss). Plain gradient descent would simply do weight = weight - learning_rate * gradient for every weight. AdamW does something a bit smarter. For each weight, it keeps a running average of that weight's recent gradients, this gives it a form of "momentum," so it doesn't overreact to one noisy batch. It also keeps a running average of how large that weight's gradients have typically been. That second average lets it take smaller, more careful steps for weights whose gradients tend to be large and jumpy, and bigger steps for weights whose gradients are usually small and steady. You don't need to build any of this yourself, it's exactly what torch.optim.AdamW does on its own every time you call .step().

optimizer.zero_grad()

Called before the next batch's backward(). By default, PyTorch adds newly calculated gradients on top of whatever is already stored in .grad, instead of replacing it. That's actually useful for one advanced trick (simulating a bigger batch, called gradient accumulation, covered in the hardware section). But for a normal training loop, it means you have to manually clear the old gradients before working out new ones, otherwise they'll pile up, batch after batch, and quietly break your training.

The full pattern, annotated 
optimizer.zero_grad()          # clear old gradients
predicted_noise = model(noisy_image, t)   # forward pass, builds computation graph
loss = F.mse_loss(predicted_noise, real_noise)
loss.backward()                # walk graph backward, compute .grad for every weight
optimizer.step()               # use .grad to actually update every weight

The loss function: how "wrongness" is measured

The loss for diffusion training is refreshingly simple compared to most of what you've read so far.

Term: Mean Squared Error (MSE)

Mean Squared Error takes two tensors of the same shape (here: the real noise and the predicted noise), subtracts them element-by-element, squares every difference (so negative and positive errors both count as "bad," and bigger errors are penalized disproportionately more than small ones), and averages all those squared differences into a single number. That single number is the loss for this training example, the lower it is, the closer the network's predicted noise was to the real noise. 

loss = mean((real_noise - predicted_noise) ** 2)

That's genuinely the entire loss function for basic DDPM training, no exotic terms, no extra components. This simplicity, discovered by the original DDPM paper's authors after trying more complex alternatives, is part of why diffusion models turned out to be so practical: the training target is just "predict this noise tensor," measured with the most standard regression loss there is.

Analogy

If you guessed a friend's height and they told you the real answer, the squared error is like taking (your guess − real height), squaring it so it's always a positive "how far off" number, and that's your score for that one guess, lower is better, zero means a perfect guess. MSE loss here does exactly that, just for every number in the noise tensor at once, then averages all those individual scores together.

In PyTorch, this loss is entirely ready-made: torch.nn.functional.mse_loss(predicted_noise, real_noise), you will not need to write the averaging or squaring by hand.

The sampling loop: actually generating a new image

Once training is done, generating a brand-new image uses the trained network in a loop, running the reverse process for real this time.

  1. Start from pure random noise

    Generate a tensor of pure Gaussian noise, the shape of one image (or a batch, if generating several at once). This represents "timestep T," the fully-noised end state.

  2. Loop backward from t = T down to t = 1

    At each timestep, feed the current (still noisy) image and the current timestep number into the trained U-Net, getting back a predicted noise tensor, exactly the same forward pass used during training, just with no loss computation or weight update this time, since we're only doing inference now.

  3. Use the sampling formula to step to a slightly cleaner image

    Using the predicted noise plus the schedule's α/β numbers for this timestep, calculate a slightly less noisy version of the image. This formula is a rearranged, flipped version of the forward shortcut formula, it also adds back in a small controlled amount of fresh random noise at every step except the very last one (this keeps the generation process from collapsing onto overly repetitive, bland outputs; the amount is set by the schedule, not something you tune by feel).

  1. Repeat down to t = 0

    After looping through every timestep back down to zero, what remains is your generated image, never a real photo, entirely produced by the network's repeated small denoising guesses, starting purely from random static.

Watch out: this is where your 4GB GPU matters most

Basic DDPM sampling with T=1000 means running the network 1000 times, in sequence, to generate a single image, on a small model this is still workable but noticeably slow. Once your basic version works, look into DDIM sampling (a different, faster way of walking the same reverse process using far fewer steps, often just 20-50) as your very next upgrade, it reuses the exact same trained network, just changes the stepping formula, so nothing about training changes, only generation speed.

Fitting all of this into 4GB of VRAM

Tie everything above back to your specific hardware constraint. Here's exactly where VRAM goes during training, and your levers for controlling each:

What's using VRAMYour lever
The network's own weightsKeep the U-Net small, fewer channels per stage (start around 32-64 base channels), fewer stages (2-3 down/up stages is plenty at first), attention only at the bottleneck.
Image resolutionStart at 32×32 or 64×64, not larger. VRAM use for activations grows roughly with the square of resolution, so doubling resolution roughly quadruples this cost.
Batch sizeUse a small batch (4-16). If you need the statistical benefit of a larger batch, use gradient accumulation: run several small batches, add up their gradients, and only then do one weight update, same training effect as a bigger batch, far less peak VRAM.
Stored activations for backpropagationUse mixed precision training (torch.cuda.amp / torch.autocast), this stores many intermediate numbers using a smaller 16-bit format instead of the default 32-bit, roughly halving memory for a small accuracy trade-off that's negligible for this project.
Term: Gradient accumulation

Gradient accumulation means running the "forward pass → compute loss → compute gradients" steps for several small batches in a row without immediately updating the weights, letting the gradients add up across those batches, and only calling the optimizer's update step once, after a chosen number of small batches. The end result behaves like training with one larger batch, but only ever needs enough VRAM for the smaller batch size at any single moment.

Term: Mixed precision

Numbers in a computer can be stored with different levels of precision. The PyTorch default is 32-bit floating point (fp32), using 32 bits of storage per number. Mixed precision training uses the smaller 16-bit format (fp16, or a variant called bf16) for most of the calculation, only switching back to 32-bit for the specific steps that need the extra precision to stay numerically stable. Roughly halving the size of most numbers in memory roughly halves your VRAM usage for those parts, which on a 4GB card is often the difference between a model fitting or not.

Your concrete starting configuration
  • Image size: 32×32 (start here) or 64×64 (once 32×32 trains successfully)
  • U-Net base channels: 32-64, with 2-3 down/up stages
  • Attention layer: bottleneck only
  • Batch size: 8-16, with gradient accumulation if you want an effectively larger batch
  • Mixed precision (fp16/bf16) training enabled
  • Timesteps T: 1000 for training; plan to add DDIM later for faster sampling
