Time & Space Complexity

How to measure whether a solution is fast and small enough. You will use this on every single problem. Topics in this module: Big-O, Big-Omega, Big-Theta and common growth rates; analysing loops, recursion and choosing an algorithm.

Essential2 topics0 problems38 interview questions

Start from scratch: why this module exists

Early programmers noticed that a program fast on 100 items could collapse on 1,000,000. Measuring seconds does not help because machines differ. Complexity analysis was invented to compare algorithms by how their cost GROWS, which is stable across machines and predictable before you write the code.

In a timed test, complexity is your calculator: it tells you in ten seconds whether an idea can pass the largest input. It is also how interviewers judge whether you understand why a solution is good.

Who needs it: Every engineer who ships code that must scale: backend, data, game and mobile developers; every competitive-programming contestant.

Before you start: Module 1 (loops and functions).

After this module you can

  • Compute time and space complexity of loops, nested loops and recursion.
  • Estimate whether an approach will pass a given input size.
  • Explain best, average and worst case in plain words.
  • Choose between speed and memory deliberately.

Common pitfalls: Treating complexity as theory; forgetting hidden costs such as slicing, sorting and 'in list'; saying 'O(n)' without saying what n is.

Typical interview questions here: Complexity of this loop? Compare two algorithms. Why O(n log n) for sorting? Time and space of recursion? Optimise this O(n^2) code.

Big-O, Big-Omega, Big-Theta and common growth rates

Essential Topic 2.1

Simple definition

Time complexity describes how the number of steps grows as the input size n grows. Space complexity describes how extra memory grows. Big-O gives an upper bound (worst case), Big-Omega a lower bound (best case) and Big-Theta a tight bound (both).

Why it matters

Computers differ in speed, so we count steps instead of seconds. Complexity lets you predict whether a solution will pass the time limit before you write it.

Real-world analogy

Finding a name in a phone book: reading every page is O(n), flipping to the middle and halving is O(log n), asking every person to shake hands with every other person is O(n^2).

From scratch: why this idea exists and how you could invent it

Imagine two friends each write a program to check whether a name is in a list. Friend A's runs in 2 seconds on her laptop. Friend B's runs in 5 seconds on an old laptop. Whose algorithm is better? You cannot tell: the machines differ. We need a way to compare ALGORITHMS, not machines.

The idea: count basic steps as a function of the input size n, because for large n the shape of that function dominates everything else. A program that takes 100n steps and one that takes n^2 steps look similar at n = 10 (1000 vs 100), but at n = 10,000 the first needs a million steps and the second a hundred million. The growth rate decides who wins.

That is Big-O: describe the growth rate, ignoring constants and lower terms because they stop mattering as n grows. 3n^2 + 50n + 7 behaves like n^2 for large n. We keep the shape, not the exact number.

Why worst case? When a company promises 'this will finish', the safe promise is the slowest possible input. Best case is rarely informative. Average case needs assumptions about the data. Interviews usually ask for the worst case unless you say otherwise.

Big-Omega and Big-Theta complete the picture. Big-O says 'no worse than', Omega says 'no better than', Theta says 'exactly this growth'. In everyday speech people use Big-O to mean 'the tight worst-case bound'.

Space complexity exists because memory is finite too. Sometimes a faster algorithm needs more memory (a hash set), and knowing both lets you make a deliberate trade.

Step-by-step walkthrough

  1. Ignore constants and smaller terms: 3n^2 + 5n + 7 is O(n^2).
  2. Common classes from fastest to slowest: O(1) < O(log n) < O(n) < O(n log n) < O(n^2) < O(2^n) < O(n!).
  3. Rule of thumb for a ~1 second limit in Python: about 10^7 basic operations. n = 10^5 allows O(n log n); n = 10^3 allows O(n^2); n = 20 allows O(2^n).
  4. Best/average/worst: searching for x in a list - best case 1 step (first item, Omega(1)), worst case n steps (O(n)). Quick sort is O(n log n) on average but O(n^2) in the worst case.
  5. Big-Theta applies when the best and worst growth match: summing a list is Theta(n) always.

Deep dive in simple words

Time complexity answers one question: 'If I make the input 10 times bigger, how much slower does my code get?' O(n) gets 10 times slower, O(n^2) gets 100 times slower, O(log n) barely changes. We do not measure seconds because every computer is different. We count steps and look at the growth.

Big-O is the 'at most' (upper bound), Big-Omega is the 'at least' (lower bound) and Big-Theta is 'exactly this growth'. In interviews when people say 'the complexity is O(n)' they usually mean the worst-case Big-O. Best case is the luckiest input (finding the item at position 0), worst case is the unluckiest (item at the end or missing), average is the typical input.

How to simplify: (1) Drop constants: 5n becomes n. (2) Keep only the biggest term: n^2 + n becomes n^2. (3) Different inputs use different letters: looping over a list of size n and a list of size m is O(n + m) or O(n * m), not O(n). Practise by looking at a loop and asking 'how many times does the inside run?'

Space complexity counts EXTRA memory your algorithm needs, not the input itself. A few variables is O(1). A new list as big as the input is O(n). Recursion depth counts too. Often you can trade space for time: a set uses O(n) space but makes lookups O(1).

Memorise this order: O(1) < O(log n) < O(n) < O(n log n) < O(n^2) < O(2^n) < O(n!). Anything above O(n log n) is usually too slow for n = 10^5.

Under the hood: what really happens inside Python

  • A 'step' is one basic operation: compare, add, assign, index. Python executes roughly 10^7 to 5x10^7 of these per second in simple loops, which is where the '10^7-10^8 steps per second budget' guidance comes from.
  • Real time also depends on constants and memory: a list scan in C-implemented built-ins (like sum) can be 20-50 times faster per step than an equivalent Python for-loop. So two O(n) solutions can differ a lot in practice.
  • Hidden costs: slicing, concatenation and 'in list' are O(n) operations hiding inside one line. Dictionary lookups are O(1) on average because a hash maps the key straight to a slot.

Python tips and shortcuts for this topic

  • Python list operations: append/pop at the end are O(1); insert(0, x), pop(0), remove(x) and 'x in list' are O(n).
  • dict and set lookups are O(1) on average. Sorting with sorted() or .sort() is O(n log n).
  • String concatenation in a loop (s += ch) can be O(n^2). Use a list and ''.join(parts).
  • Slicing a[i:j] copies, so it costs O(j - i). Avoid slicing inside big loops.
  • Use time.perf_counter() to measure real time when experimenting.

def ops_linear(n):
    ops = 0
    for i in range(n):          # n iterations
        ops += 1
    return ops

def ops_quadratic(n):
    ops = 0
    for i in range(n):          # n x n iterations
        for j in range(n):
            ops += 1
    return ops

def ops_log(n):
    ops = 0
    while n > 1:                # halves each time
        n //= 2
        ops += 1
    return ops

Why? and Why not?

Why do we ignore constants in Big-O?

Constants depend on the machine and language. For large n the growth shape decides the winner, so 5n and 100n are both 'linear'.

Why not just measure seconds?

Seconds change with hardware, input and noise. Complexity predicts behaviour before running and compares algorithms fairly.

Why usually talk about the worst case?

It is a guarantee: no input can be slower. Best case is rarely realistic and average case needs assumptions about the data.

Why does O(log n) feel almost free?

Doubling the input adds only one step. log2 of a billion is about 30.

Why is O(n!) worse than O(2^n)?

n! multiplies by a bigger number each step (n, then n-1, ...) while 2^n multiplies by 2 each time. At n = 20, n! is about 2.4 x 10^18 versus 2^20 about 10^6.

Analysing loops, recursion and choosing an algorithm

Essential Topic 2.2

Simple definition

To find complexity, count how many times the most-repeated line runs as a function of n, then keep the dominant term. For recursion, count the calls and the work per call.

Why it matters

In an assessment you must decide on the fly if a brute force solution will pass. Complexity analysis makes that a 10-second calculation instead of a guess.

Real-world analogy

Planning a delivery route: checking every possible route is a disaster (n!), checking every pair of towns is heavy (n^2), but using a sorted address list (n log n) scales.

From scratch: why this idea exists and how you could invent it

Knowing the definition of Big-O is not enough; you must be able to read code and produce the complexity quickly. Start with the simplest unit: a statement without loops costs O(1). A loop multiplies the cost of its body by how many times it runs. Statements one after another add. That is nearly all the rules.

For loops with a changing step: i *= 2 or n //= 2 halves or doubles, so it runs log n times. A loop that runs sqrt(n) times appears in primality tests. A loop inside a loop where the inner bound depends on the outer variable gives a sum like 1 + 2 + ... + n = n(n+1)/2, still O(n^2).

For recursion write the recurrence: how much work per call plus how many smaller calls. T(n) = T(n-1) + 1 solves to O(n). T(n) = 2T(n-1) + 1 solves to O(2^n). T(n) = T(n/2) + 1 is O(log n). T(n) = 2T(n/2) + n is O(n log n). Draw the recursion tree: levels times work per level.

Why does this matter so much? Because it lets you reject bad ideas before coding. If your idea is O(n^2) with n = 10^5, you do not code it. This single habit saves more time in a test than any syntax trick.

Space is analysed the same way: count the memory you create (lists, dictionaries) and the recursion depth.

Step-by-step walkthrough

  1. Sequential blocks add: O(n) + O(n^2) = O(n^2).
  2. Nested loops multiply: outer n x inner m = O(n*m).
  3. A loop where the variable doubles (i *= 2) runs log n times.
  4. Recursion: T(n) = T(n-1) + O(1) is O(n) (factorial). T(n) = 2T(n-1) is O(2^n) (naive Fibonacci). T(n) = 2T(n/2) + O(n) is O(n log n) (merge sort). T(n) = T(n/2) + O(1) is O(log n) (binary search).
  5. Space counts extra memory: a few variables O(1); a new list of size n is O(n); recursion depth d adds O(d).
  6. Example: has_duplicate_slow compares all pairs (O(n^2)); has_duplicate_fast uses a set (O(n) time, O(n) space) - we trade memory for speed.

Deep dive in simple words

To find the complexity of code, find the line that runs the most times and count it. A simple for loop over n items: n times. A loop inside a loop: n times n. A loop where the counter doubles (i = i * 2): about log n times. Write the count as a formula and keep the biggest piece.

Recursion is the same idea: count the calls and the work per call. A function that calls itself once on n - 1 does n calls: O(n). A function that calls itself twice on n - 1 does about 2^n calls. A function that splits the input in half and does O(n) work (merge sort) has log n levels with n work each: O(n log n).

Hidden costs: sorted() is O(n log n). Slicing copies. 'x in list' scans. str concatenation copies. min(), max() and sum() scan all items. Always ask 'what does this one line really do inside Python?'.

A good habit before coding: estimate. Say n is 10^5 and your idea is O(n^2). That is 10^10 steps, far too slow, so think again. This takes ten seconds and saves a whole failed submission.

Trading space for time is the most common optimisation: store things you will need again (in a dict, set, prefix array). Saving a few thousand extra numbers in memory to avoid re-scanning is almost always worth it.

Under the hood: what really happens inside Python

  • The master theorem gives T(n) = a T(n/b) + O(n^d): compare log_b(a) with d. If d is bigger the top level dominates (O(n^d)); if equal every level contributes equally (O(n^d log n)); if smaller the leaves dominate. Merge sort: a = 2, b = 2, d = 1 gives O(n log n).
  • Python built-ins have their own costs: sorted O(n log n), list.sort the same, 'x in set' O(1) average, min/max O(n), list.insert(0, x) O(n), str.join O(total length), dict iteration O(n).

Python implementation

def has_duplicate_slow(nums):
    for i in range(len(nums)):              # n times
        for j in range(i + 1, len(nums)):   # up to n times
            if nums[i] == nums[j]:
                return True
    return False                            # O(n^2) time, O(1) space

def has_duplicate_fast(nums):
    seen = set()
    for x in nums:                          # n times
        if x in seen:                       # O(1) average
            return True
        seen.add(x)
    return False                            # O(n) time, O(n) space

Build it step by step: from the simplest idea to the best

Every stage is runnable and was checked against its stated result.

Stage 1 - compare every pair

Obvious and correct, but two nested loops cost O(n^2). Fails when n = 10^5.

def has_duplicate(nums):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] == nums[j]:
                return True
    return False

Check: has_duplicate([3, 1, 4, 1]) returns True

Stage 2 - sort first

After sorting, equal values sit next to each other, so one pass compares neighbours. O(n log n) time and no hash table.

def has_duplicate(nums):
    nums = sorted(nums)
    for i in range(1, len(nums)):
        if nums[i] == nums[i - 1]:
            return True
    return False

Check: has_duplicate([3, 1, 4, 1]) returns True

Stage 3 - remember what you have seen

A set answers 'seen before?' in O(1) on average, so one pass is enough: O(n) time, O(n) space. We traded memory for speed.

def has_duplicate(nums):
    seen = set()
    for x in nums:
        if x in seen:
            return True
        seen.add(x)
    return False

Check: has_duplicate([3, 1, 4, 1]) returns True

Why? and Why not?

Why do nested loops multiply but sequential loops add?

A nested inner loop runs fully for every iteration of the outer loop (n x m). Sequential loops run one after another (n + m).

Why must you count recursion depth as space?

Each active call holds a stack frame in memory. Depth d means d frames at once, which is O(d) extra space.

Why is trading space for time common?

Memory is cheap compared with time limits. A set or dictionary can remove an entire inner loop.

Why not always choose the lowest time complexity?

A lower complexity may use much more memory, be harder to write or be slower for small n. Choose the simplest solution that passes the limits.

Why does slicing hide a cost?

a[i:j] copies j - i elements, so a slice inside a loop can turn O(n) into O(n^2).

Interview questions: Time & Space Complexity

38 questions: try to answer aloud in under a minute, then reveal. All questions from every module are also in the interview bank.

Basic Conceptual What is the time complexity of binary search and why?

O(log n). Each step throws away half of the remaining items, so the number of steps is how many times you can halve n before reaching 1, which is log2(n).

Basic Conceptual What is the difference between O(n) and O(2n)?

No difference in Big-O. Constants are dropped, so O(2n) is O(n). Both grow in a straight line.

Basic Conceptual What is the complexity of two loops, one after the other, each running n times? What if one loop is inside the other?

One after the other: O(n) + O(n) = O(n). One inside the other: O(n * n) = O(n^2).

Basic Conceptual What is the worst case of searching a list with 'x in nums'?

O(n). In the worst case x is last or missing and Python has to check every element.

Basic Conceptual Is O(n log n) faster than O(n^2)?

Yes for large n. For n = 1000: n log n is about 10,000 steps while n^2 is 1,000,000. The gap grows as n grows.

Basic Conceptual What is amortised O(1)?

An operation that is occasionally expensive but cheap on average over many calls. list.append is amortised O(1): usually one step, sometimes it copies the list to a bigger memory block, but spread over all appends the average is constant.

Basic Conceptual Why do we drop constants and lower-order terms?

Because for large n the dominant term decides the growth, and constants depend on hardware and language. 5n^2 + 100n is O(n^2); the 5 and the 100n become minor as n grows.

Basic Conceptual What is the difference between O, Omega and Theta?

O is an upper bound, Omega a lower bound, Theta a tight bound (both). Everyday speech uses O for the tight worst case.

Basic Conceptual What is the complexity of: for i in range(n): for j in range(i, n): ...?

The inside runs n + (n-1) + ... + 1 = n(n+1)/2 times, which is O(n^2).

Basic Conceptual What is the complexity of: i = 1; while i < n: i *= 2?

O(log n). i doubles each time, so it takes log2(n) steps to reach n.

Basic Conceptual How would you reduce the time of checking if a list has duplicates?

Brute force compares all pairs in O(n^2). Put elements into a set while scanning; if an element is already in the set you found a duplicate. That is O(n) time and O(n) space.

Basic Conceptual What is the complexity of recursive Fibonacci and how can you improve it?

O(2^n) because each call makes two calls and subproblems repeat. Add memoisation (a dictionary or lru_cache) so each value is computed once: O(n) time, O(n) space.

Basic Conceptual Why does appending with s += ch in a loop matter for strings?

Strings are immutable, so each += builds a new string copying all previous characters. Over n steps this can be O(n^2). Better: collect characters in a list and use ''.join(list) at the end.

Basic Conceptual What is the space complexity of recursion?

O(depth of recursion) because each active call holds a frame. For a balanced tree that is O(log n); for a linked-list-shaped tree O(n).

Medium Why / Why not Why does slicing hide a cost?

a[i:j] copies j - i elements, so a slice inside a loop can turn O(n) into O(n^2).

Medium Why / Why not Why is 'x in list' risky inside a loop?

It scans the list: O(n) per check, so the loop becomes O(n^2). Use a set for O(1) average membership.

Medium Tricky output What is the complexity of sorting inside a loop that runs n times on a list of size n?

O(n^2 log n). Each sort costs O(n log n) and it runs n times.

Advanced Follow-up Your algorithm is O(n log n) and you have n = 10^6. Is that fine in Python?

About 2 x 10^7 basic steps: usually fine if the work per step is small and uses built-ins like sorted(); it may be tight with heavy Python loops. Prefer built-ins and avoid per-step overhead.

Advanced Follow-up Can you improve O(n log n) sorting-based duplicate detection?

Yes, use a set for O(n) average time at the price of O(n) space.

Advanced Follow-up How do you analyse a function that calls itself with n/2 twice and does O(1) extra work?

T(n) = 2T(n/2) + 1, which solves to O(n): the recursion tree has n leaves and about n total nodes.
