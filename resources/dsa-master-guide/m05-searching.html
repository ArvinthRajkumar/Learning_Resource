Module 5

Searching Algorithms

Linear search, binary search and its many variations - a favourite in assessments. Topics in this module: Linear search and binary search; binary search variants: first/last occurrence, insertion point, rotated arrays; binary search on the answer.

Essential3 topics11 problems55 interview questions

Start from scratch: why this module exists

Searching is the most frequent operation in computing. Scanning item by item is O(n). If data is sorted, you can discard half the possibilities with each comparison, which is binary search. The idea is older than computers (phone books, dictionaries).

Binary search is also a way of thinking: whenever a yes/no question changes only once along an ordered range, you can find the switch point in logarithmic time. That extension, searching on the answer, solves many hard-looking problems.

Who needs it: Database and file-system engineers, version-control tools (git bisect), search features in apps, and every interviewer.

Before you start: Modules 1-3.

After this module you can

  • Write bug-free iterative binary search.
  • Find first/last positions and insertion points.
  • Search rotated arrays and use peak finding.
  • Apply binary search on the answer to optimisation problems.

Common pitfalls: Using it on unsorted data, off-by-one in bounds, infinite loops from lo = mid, wrong direction when maximising.

Typical interview questions here: Implement binary search, first/last occurrence, search in rotated array, square root, koko eating bananas, ship packages in D days.

Linear search and binary search

Essential Topic 5.1

Simple definition

Linear search checks items one by one. Binary search repeatedly checks the middle of a SORTED list and throws away the half that cannot contain the target.

Why it matters

Binary search turns a million-item search into about 20 steps. It requires sorted data (or a monotonic condition).

Real-world analogy

Guessing a number between 1 and 100: you guess 50, hear "higher", then 75, and so on. Each guess halves the possibilities.

From scratch: why this idea exists and how you could invent it

Look up a name in a printed phone book. You never start at page 1. You open near the middle, see whether your name comes before or after, and repeat on the correct half. This works only because the book is sorted. That is binary search, a technique people used long before computers.

Why is it so powerful? Every step discards half the possibilities. Starting with a million names, after 20 halvings one is left. Growth in data costs only one extra step per doubling. That is what O(log n) means in practice.

The sorted requirement is the price: sorting costs O(n log n) once, then every search costs O(log n). If you search many times the investment pays off; if you search once in unsorted data, a linear scan is cheaper.

Why is binary search famous for bugs? It looks trivial but has small details: inclusive vs exclusive bounds, the loop condition, the mid formula and the update rules must all fit together. A famous bug existed in standard libraries for years (integer overflow in (lo + hi) / 2 for huge arrays). Choose one consistent template and test with arrays of length 0, 1 and 2.

Binary search generalises: whenever you can ask a yes/no question that flips from No to Yes exactly once along an ordered range, you can find the flip point in O(log n).

Deep dive in simple words

Linear search is checking every item one by one. It works on any list, sorted or not, and costs O(n). Binary search needs a SORTED list. It opens the middle item and asks 'is my target smaller or bigger?'. Then it throws away the half that cannot contain the target. Repeat on the remaining half.

A good mental picture is a window [lo, hi] that always contains every position where the target could still be. At the start it is the whole list. Each step shrinks it by half. When the window becomes empty (lo > hi) the target is not there.

Three bug sources: (1) the loop condition (use lo <= hi when hi starts at n - 1), (2) the updates (lo = mid + 1 and hi = mid - 1, never lo = mid), (3) the middle formula (lo + (hi - lo) // 2 avoids overflow in other languages; Python is safe with (lo + hi) // 2).

Binary search is not only for numbers in lists. Whenever a question can be answered by a monotonic yes/no (first no-then-yes, like 'is speed x fast enough?'), you can binary search over the answer. Keep this idea for the 'binary search on the answer' topic.

Use the built-in bisect module in real code: bisect_left(a, x) gives the first index where x could be inserted, bisect_right gives the last. But in exams you may be asked to write the loop yourself.

Under the hood: what really happens inside Python

  • Each iteration compares one element and halves the window: lo and hi move toward each other until lo > hi. The invariant is 'if the target exists, it is inside [lo, hi]'. Proving the invariant is how you prove the algorithm correct.
  • Python's bisect module implements it in C with the same logic. bisect_left returns the leftmost insertion point; bisect_right the rightmost.
  • Binary search on a Python list is O(log n) because indexing is O(1). On a linked list it would be O(n) because reaching the middle takes a walk.

  • from bisect import bisect_left, bisect_right, insort

Python implementation

def binary_search(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1         # discard left half
        else:
            hi = mid - 1         # discard right half
    return -1
Recursive version and Python's bisect module
def binary_search_rec(nums, target, lo, hi):
    if lo > hi:
        return -1
    mid = (lo + hi) // 2
    if nums[mid] == target:
        return mid
    if nums[mid] < target:
        return binary_search_rec(nums, target, mid + 1, hi)
    return binary_search_rec(nums, target, lo, mid - 1)

from bisect import bisect_left, bisect_right
a = [1, 2, 2, 2, 5]
print(bisect_left(a, 2), bisect_right(a, 2))   # 1 4  -> first index, one past last index

Build it step by step: from the simplest idea to the best

Every stage is runnable and was checked against its stated result.

Stage 1 - linear search

Check every element. Works on any list, O(n).

def search(nums, target):
    for i, x in enumerate(nums):
        if x == target:
            return i
    return -1

Check: search([1, 3, 5, 7, 9], 7) returns 3

Stage 2 - binary search

If the list is sorted, discard half each step: O(log n).

def search(nums, target):

Stage 3 - use bisect

The standard library already contains a tested binary search. Use it in real code.

from bisect import bisect_left

def search(nums, target):
    i = bisect_left(nums, target)
    return i if i < len(nums) and nums[i] == target else -1

Common mistakes and edge cases

  • Using binary search on unsorted data.
  • Infinite loop from lo = mid instead of mid + 1.
  • Using < instead of <= in the loop condition and missing the last element.
  • Overflow of (lo + hi) in other languages - use lo + (hi - lo) // 2.

Why? and Why not?

Why must the list be sorted for binary search?

The comparison with the middle element tells you which half to discard only if the data is ordered.

Why not always sort and binary search?

Sorting costs O(n log n). For a single search a linear scan (O(n)) is cheaper.

Why is lo <= hi the loop condition?

When lo equals hi there is still one candidate left to check. Using < would skip it.

Why mid + 1 and mid - 1 instead of mid?

mid has already been checked. Excluding it guarantees the window shrinks and the loop ends.

Why can (lo + hi) // 2 overflow in other languages?

lo + hi may exceed the integer limit. lo + (hi - lo) // 2 is safe. Python has no overflow.

Binary search variants: first/last occurrence, insertion point, rotated arrays

Essential Topic 5.2

Simple definition

Variants keep searching after a match (to find the first or last position) or decide which half is sorted (rotated arrays).

Why it matters

Real problems rarely ask for "any index of x". They ask for boundaries, counts, or work on twisted arrays.

Real-world analogy

Finding the first page of a chapter: when you land on a page of the chapter you keep flipping left to check if an earlier page also belongs.

From scratch: why this idea exists and how you could invent it

Plain search answers 'is it there?'. Real questions are sharper: 'what is the first time this happened?', 'where would this new value go to keep the list sorted?', 'how many records have this value?'. All of these are really questions about boundaries in a sorted list.

The cleanest way to think: for a target x, mark every element as 'less than x' (L) or 'not less than x' (N). In a sorted list the pattern is LLLLNNNN. The lower bound is the position of the first N. Binary search can find a boundary in an ordered pattern of two kinds. Upper bound is the same idea with 'less than or equal'.

Rotated sorted arrays are the interviewer's favourite twist: the order is broken in exactly one place. After cutting at mid, one half is still sorted. A sorted half is a half where plain reasoning about ranges works, so you can decide if the target belongs there; if not, it must be in the other half.

Seeing patterns this way converts a family of problems (first/last position, insert position, count, floor/ceiling, peak, minimum in a rotated list) into the same loop with slightly different conditions.

Visual explanation (interactive)

Step-by-step walkthrough

  1. First occurrence: when nums[mid] == target save ans = mid and continue with hi = mid - 1.
  2. Last occurrence: save ans and continue with lo = mid + 1.
  3. Count of target = last - first + 1.
  4. Insertion position (lower bound): first index with value >= target.
  5. Rotated sorted array: one half around mid is always sorted. Check whether the target lies in the sorted half; if yes search it, else search the other half.
  6. The animation mode "first occurrence" shows ans being recorded while the window keeps shrinking.

Deep dive in simple words

Plain binary search stops at ANY match. In real problems the same value may appear many times. To get the FIRST position, when you find the target remember the index and keep searching on the LEFT side. For the LAST position, keep searching on the RIGHT side. These two searches give you the count of the value too: last - first + 1.

Lower bound and upper bound are the cleanest tools. lower_bound(x) is the first index with value >= x. upper_bound(x) is the first index with value > x. Insert position, count, first and last occurrence all come from these two.

Rotated sorted array (like [4,5,6,7,0,1,2]) looks broken but has a trick: whenever you cut it at mid, at least one side is perfectly sorted. Find out which side is sorted by comparing nums[lo] with nums[mid]. Check if the target lies inside that sorted side; if yes, search there; if not, search the other side.

Finding the minimum of a rotated array works by comparing nums[mid] with nums[hi]: if mid is bigger than the right end the drop (the minimum) is on the right; otherwise the minimum is at mid or to the left.

A 'peak' problem shows you can binary search even without sorted data. If nums[mid] < nums[mid+1] you are walking uphill, so a peak must be to the right. Otherwise a peak is at mid or to the left.

Under the hood: what really happens inside Python

  • Using half-open range [lo, hi) with hi = len(a) and the update hi = mid keeps lower_bound simple and avoids off-by-one errors. The invariant: answer is in [lo, hi].
  • bisect_left(a, x) is exactly lower_bound; bisect_right(a, x) is upper_bound. count = right - left; last index = right - 1.
  • In a rotated array without duplicates, comparing a[mid] with a[hi] tells which side holds the pivot (minimum). With duplicates, a[mid] == a[hi] gives no information and you must shrink hi by one, so the worst case degrades to O(n).

Python tips and shortcuts for this topic

  • bisect_left(a, x) = lower bound; bisect_right(a, x) = upper bound.
  • first and last: lo = bisect_left(a, x); hi = bisect_right(a, x) - 1.
  • Check the answer exists: lo < len(a) and a[lo] == x.

Python implementation

def lower_bound(nums, target):
    lo, hi = 0, len(nums)            # hi = len, answer may be len
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid                 # nums[mid] >= target could be the answer
    return lo

Why? and Why not?

Why keep searching after finding the target for first/last occurrence?

The target may appear many times. Continuing left finds the first copy; continuing right finds the last.

Why does the rotated array search work?

After cutting at mid one side is always sorted, so you can check whether the target lies inside that sorted range.

Why use hi = len(a) for lower_bound?

The answer can be len(a) (insert at the end), so the search range must include that position.

Why not scan linearly from the match to find the first occurrence?

With many duplicates that costs O(n). A second binary search keeps O(log n).

Why compare with a[hi] when finding the rotated minimum?

a[hi] tells which side of mid contains the drop. If a[mid] > a[hi] the minimum is to the right.

Binary search on the answer

Important Topic 5.3

Simple definition

Instead of searching an array, you search over the range of POSSIBLE ANSWERS. If a yes/no check ("can we do it with value x?") flips from False to True exactly once as x grows, you can binary search x.

Why it matters

Minimise-the-maximum, capacity, speed and "kth smallest" problems become O(n log range) instead of exponential.

Real-world analogy

Finding the minimum oven temperature that bakes bread in under 30 minutes: you do not try every temperature, you halve the range after each trial.

From scratch: why this idea exists and how you could invent it

A baker wants the lowest oven temperature that cooks the bread in 30 minutes. The baker tests 200 degrees: too slow. Tries 250: fast enough. Tries 225: too slow... The baker is binary searching the answer. The key fact is monotonicity: a hotter oven never makes baking slower. That single fact makes halving the range valid.

In algorithm problems the 'oven' is a simulation: given a candidate answer x (speed, capacity, distance), can the task be done? If the function can_do(x) is False for small x and True for large x (or the reverse), the best x is the boundary. Searching x costs log(range) simulations, each O(n).

Why not search the original array? Because the answer is not an index in it. The real search space is the set of possible answers, which can be huge (up to 10^9) but is ordered, so binary search still takes about 30 steps.

The skill is learning to spot it: phrases like 'minimise the maximum', 'maximise the minimum', 'smallest x such that', 'largest x such that' signal this technique.

Visual explanation (interactive)

Step-by-step walkthrough

  1. Define the answer range [lo, hi] (for example 1 .. max(piles)).
  2. Write feasible(x): is the goal achievable with value x?
  3. If feasible(mid): the answer is mid or smaller -> hi = mid. Otherwise lo = mid + 1.
  4. Example (Koko eating bananas): piles [3,6,7,11] in h = 8 hours. Speed 4: hours = 1+2+2+3 = 8 OK. Speed 3: 1+2+3+4 = 10 too slow. Answer 4.
  5. Use the visualiser: each step tests a candidate speed and shows whether it is feasible.

Deep dive in simple words

Sometimes the thing you are looking for is not in a list. It is a NUMBER you have to choose: a speed, a capacity, a time, a distance. If you can write a function can_do(x) that answers yes/no, and the answers look like No No No Yes Yes Yes (or the reverse), you can binary search x instead of trying everything.

Recipe: (1) decide the smallest and largest possible answer, (2) write can_do(mid) by simulating the situation with mid, (3) if can_do(mid) is true, the answer is mid or smaller (hi = mid) for a minimum, otherwise lo = mid + 1, (4) when lo == hi that is the answer.

Example: Koko eats bananas. For a speed s, hours needed = sum of ceil(pile / s). Faster speed means fewer hours, so the check is monotonic. The slowest speed that finishes in h hours is the answer. Instead of trying every speed (up to max pile), binary search the speed in log(max) steps.

Same pattern appears in: shipping packages in D days, splitting an array into k parts with the smallest largest sum, placing cows/routers as far apart as possible (maximise the minimum), integer square root, and finding the k-th smallest in a multiplication table.

Always double check the direction. Minimising a value usually means 'hi = mid' on success; maximising a value usually means 'lo = mid' on success (use mid = (lo + hi + 1) // 2 to avoid an infinite loop).

Under the hood: what really happens inside Python

  • Each loop evaluates can_do(mid) in O(n) (or whatever the simulation costs) and halves the range, so total is O(n log R) where R is the range size.
  • To avoid infinite loops: for minimising use lo < hi with hi = mid on success and lo = mid + 1 on failure. For maximising use lo = mid on success with mid = (lo + hi + 1) // 2.
  • The predicate must be monotonic. If your yes/no function is not monotonic (yes, no, yes...), binary search gives wrong answers.

Python tips and shortcuts for this topic

  • math.ceil(a / b) can be written with integers as (a + b - 1) // b, which avoids floating point mistakes.
  • sum(generator) is a compact way to build the feasibility check.
  • Use float('inf') only when the answer might not exist.

Python implementation

def min_eating_speed(piles, h):
    def hours(speed):
        return sum((p + speed - 1) // speed for p in piles)   # ceil(p / speed)
    lo, hi = 1, max(piles)
    while lo < hi:
        mid = (lo + hi) // 2
        if hours(mid) <= h:
            hi = mid          # fast enough, try slower
        else:
            lo = mid + 1      # too slow
    return lo

Why? and Why not?

Why can you binary search something that is not an array?

You search the range of possible answers using a yes/no check that is monotonic.

Why must the check be monotonic?

Otherwise the result at mid does not tell you which half to discard.

Why not try every possible answer?

The range can be 10^9 wide. Binary search needs only about 30 checks.

Why is the lower bound often max(weights)?

Capacity below the heaviest item can never work.

Why use ceil division in the feasibility check?

A pile of 7 at speed 3 takes 3 hours (not 2.33) because partial hours count as full.

How this gets asked

What property must the feasibility check have?

  • It is monotonic
  • It is random
  • It returns an integer
  • It is recursive

It must change from False to True once, otherwise halving is invalid.

For ceil(p / speed) using integers, which expression is right?

  • p // speed
  • (p + speed - 1) // speed
  • p / speed
  • p % speed

Adding speed - 1 before floor division rounds up.

Basic Conceptual Why is binary search O(log n)?

Each comparison halves the search window. After k steps the window has n / 2^k items; it becomes 1 when k = log2(n).

Basic Conceptual Can you use binary search on an unsorted array?

No. The decision 'go left or right' only works because the data is ordered. You would first have to sort it (O(n log n)), which only pays off for many searches.

Basic Conceptual What is the difference between lo <= hi and lo < hi loops?

With lo <= hi and both ends inclusive you check every position including the last one; you use mid + 1 / mid - 1. With lo < hi and hi = len(nums) (half-open) you use hi = mid to keep a candidate. Pick one style and stick with it.

Basic Conceptual Write iterative binary search.
def binary_search(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1
Basic Conceptual When is linear search better than binary search?

For tiny lists, for unsorted data you only search once, or when the list is a linked list (no random access).

Basic Conceptual Why must the array be sorted?

The comparison with the middle element must tell you which half can contain the target; without order the discarded half might contain it.

Basic Behavioral Describe a time you used a divide-and-narrow approach to debug.

Strong answers describe cutting the search space in half repeatedly: comment out half the code, check logs at the midpoint of a pipeline, or bisect commits until the faulty change is isolated.

Basic Conceptual How do you find the first and last position of a target in a sorted array?

Run binary search twice. When nums[mid] == target save mid and continue left (hi = mid - 1) for the first position, or right (lo = mid + 1) for the last. O(log n) each.

Basic Conceptual How do you search in a rotated sorted array?

At each step one half is sorted. If nums[lo] <= nums[mid] the left half is sorted; check if the target is in [nums[lo], nums[mid]) and go there, else go right. The other case is symmetric. O(log n).

Basic Conceptual How do you find the insertion position of a value?

It is the lower bound: the first index whose value is >= target. In Python: bisect.bisect_left(nums, target).

Basic Conceptual How do you count how many times x appears in a sorted array?

bisect_right(a, x) - bisect_left(a, x), or last - first + 1 using two binary searches. O(log n).

Basic Conceptual What if the rotated array contains duplicates?

Sometimes nums[lo] == nums[mid] == nums[hi] and you cannot tell which half is sorted. You then shrink lo and hi by one. Worst case becomes O(n).

Basic Conceptual Why does the rotated search always find one sorted half?

Rotation splits the sorted list into two sorted runs. Any cut at mid leaves at least one side fully inside one run.

Basic Conceptual What is 'binary search on the answer'?

Instead of searching in an array, you search the range of possible answers. You need a yes/no function that switches from No to Yes exactly once as the candidate grows. Then you halve the range each step.

Basic Conceptual Explain how to find the minimum capacity to ship packages in D days.

Capacity is between max(weights) and sum(weights). For a capacity c, simulate loading days greedily and count days. If days <= D then c works (try smaller), else try bigger. O(n log(sum)).

Basic Conceptual How do you compute the integer square root without sqrt?

Binary search x in [0, n]: if mid * mid <= n it could be the answer (lo = mid + 1 and remember mid), else hi = mid - 1.

Basic Conceptual Why do you need the monotonic property?

Because the decision at mid must tell you which half to discard. If the yes/no answers were mixed randomly you could not safely throw half away.

Basic Conceptual How do you avoid an infinite loop when maximising?

Use mid = (lo + hi + 1) // 2 with lo = mid on success so the range always shrinks.

Basic Conceptual What does 'monotonic predicate' mean?

A yes/no function whose answers switch at most once as the input increases (all No then all Yes, or the reverse).

Medium Coding Search for a target in a sorted list using recursion.
def bs(a, t, lo, hi):
    if lo > hi:
        return -1
    mid = (lo + hi) // 2
    if a[mid] == t:
        return mid
    if a[mid] < t:
        return bs(a, t, mid + 1, hi)
    return bs(a, t, lo, mid - 1)

Medium Coding Find the smallest divisor such that the sum of ceil(a_i / d) is <= threshold.
def smallest_divisor(a, threshold):
    lo, hi = 1, max(a)
    while lo < hi:
        mid = (lo + hi) // 2
        if sum((x + mid - 1) // mid for x in a) <= threshold:
            hi = mid
        else:
            lo = mid + 1
    return lo

With mid = (lo + hi) // 2 and lo = mid, when hi = lo + 1 then mid = lo and nothing changes. Use mid = (lo + hi + 1) // 2 for that style.

Medium Coding Find the integer cube root of n by binary search.
def cbrt(n):
    lo, hi, ans = 0, n, 0
    while lo <= hi:
        mid = (lo + hi) // 2
        if mid ** 3 <= n:
            ans, lo = mid, mid + 1
        else:
            hi = mid - 1
    return ans
