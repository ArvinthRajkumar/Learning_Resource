Tries (prefix trees)

Advanced Topic 18.1

Simple definition

A trie is a tree where each edge is a character; the path from the root spells a prefix. A flag on a node marks the end of a stored word.

Why it matters

Tries answer "does any word start with this prefix?" in O(length of prefix), powering autocomplete and word-search puzzles.

Real-world analogy

A dictionary's thumb index: first letter, then second letter, then third - each step narrows the section.

From scratch: why this idea exists and how you could invent it

Autocomplete: type 'app' and the phone suggests 'apple', 'application', 'apply'. How can it do that instantly with a dictionary of 100,000 words? A hash set can tell you if 'app' is a word, but cannot list everything that starts with 'app' without scanning every word.

Notice the structure of the problem: words that start the same share a beginning. Why store the shared beginning many times? Store it once as a path, and branch only where words differ. That is a trie: every node is a prefix, and each word is a path from the root.

Lookup cost depends only on the length of the word, not on how many words are stored, and prefix queries are free: just walk to the prefix node. Listing all words with that prefix means exploring the subtree below it.

The cost is memory: many small nodes. Compressed tries (radix trees) merge chains of single-child nodes to cut this down.

Step-by-step walkthrough

  1. Insert: for each character go to (or create) the child; at the end mark is_end.
  2. Search: follow the characters; success only if the final node is marked as a word end.
  3. Prefix check: just follow the characters; no end flag needed.
  4. Time is O(L) per operation regardless of the number of words; space is O(total characters).
  5. Insert words in the visualiser and search for prefixes.

Deep dive in simple words

A trie (say 'try') is a tree for storing words where each edge is one letter. All words sharing a beginning share the same path. To store 'tea', 'ten' and 'to', you go t -> e -> a, t -> e -> n and t -> o; the first two letters of 'tea' and 'ten' are shared.

Each node needs: its children (a dictionary from letter to node) and a flag that says 'a word ends here'. Without the flag you could not tell 'app' (a prefix) from 'app' (a stored word).

Operations take time proportional to the length of the word (L), not the number of words stored. Insert: walk and create missing nodes, set the flag. Search: walk; success only if every letter exists and the end flag is set. Starts-with: walk; success if every letter exists.

When to use: autocomplete, spell checking, longest common prefix of many words, word search on a board with many words, and 'count words with a given prefix'. If you only need exact lookups, a Python set is simpler.

Memory can be large (a node per letter). A dictionary per node is compact for sparse alphabets; use a list of 26 for dense lowercase words.

Under the hood: what really happens inside Python

  • Dictionary-based nodes (dict per node) are flexible and memory efficient for sparse alphabets; arrays of size 26 give faster indexing for lowercase words.
  • Each insertion creates at most len(word) nodes. Total nodes <= total characters stored.
  • To delete a word, unmark the end flag and optionally prune nodes with no children on the way back up.

  • Use Python sets for simple membership; use a trie when prefixes matter.

Python implementation

class Trie:
    def __init__(self):
        self.root = {}

    def insert(self, word):
        node = self.root
        for ch in word:
            node = node.setdefault(ch, {})   # create the child if missing
        node["$"] = True                     # end-of-word marker

    def _find(self, text):
        node = self.root
        for ch in text:
            if ch not in node:
                return None
            node = node[ch]
        return node

    def search(self, word):
        node = self._find(word)
        return node is not None and "$" in node

    def starts_with(self, prefix):
        return self._find(prefix) is not None

Disjoint Set Union (Union-Find)

Advanced Topic 18.2

Simple definition

Union-Find tracks which elements belong to the same group. find(x) returns the representative (root) of x's group; union(a, b) merges two groups.

Why it matters

It answers connectivity questions on dynamically growing graphs in almost O(1) time per operation: cycle detection, Kruskal MST, components, accounts merge.

Real-world analogy

Friend circles at a party: introducing two people merges their whole circles into one.

From scratch: why this idea exists and how you could invent it

Imagine adding friendships one at a time and, at any moment, asking 'are A and B in the same friend circle?'. Recomputing connectivity with BFS after every new friendship is too slow. You need to maintain groups as they merge.

Represent each group by a leader. To ask whether A and B are together, ask each for their leader and compare. To merge two groups, make one leader point to the other. The structure is a forest where each node points to its parent and a root points to itself.

Naively, chains can grow long, making 'find the leader' slow. Two cheap fixes make it nearly constant: union by size (hang the smaller tree under the bigger) keeps trees shallow, and path compression (point nodes straight at the root while searching) flattens trees for the future.

Union-Find answers only connectivity questions, but it answers them extremely fast. It cannot give shortest paths or split groups, which is why graph traversals still exist.

Visual explanation (interactive)

Step-by-step walkthrough

  1. parent[i] = i initially (every element is its own group).
  2. find(x): follow parent pointers to the root. Path compression flattens the path while returning.
  3. union(a, b): ra, rb = find(a), find(b); if different, attach one root under the other (union by size/rank keeps trees shallow).
  4. With both optimisations each operation is O(alpha(n)) - effectively constant.
  5. Cycle detection: union returns False when ra == rb (the edge closes a cycle). Number of components = n - successful unions.
  6. Enter unions like "0-1,2-3,1-3" in the visualiser to see parent[] change.

Deep dive in simple words

Union-Find (also called DSU, disjoint set union) keeps track of groups. Each group has a leader (root). find(x) returns the leader of x's group; union(a, b) merges the two groups. Two elements are connected exactly when they have the same leader.

Store a parent array: parent[x] = x means x is a leader. find follows parent pointers until it reaches a leader. Path compression makes every visited node point directly closer to the leader, so later finds are faster. Union by size attaches the smaller tree under the bigger tree, keeping trees shallow.

With both tricks each operation is almost O(1) (inverse Ackermann). That makes DSU perfect for problems that add connections over time and ask 'are these two connected now?'.

Uses: count connected components (start with n groups; each successful union lowers the count), detect a cycle in an undirected graph (an edge whose endpoints already have the same leader closes a cycle), Kruskal's minimum spanning tree, grouping accounts or friends.

DSU is for 'merge and ask connectivity'. It cannot easily split groups or find shortest paths; use BFS/DFS or Dijkstra for those.

Under the hood: what really happens inside Python

  • With union by rank/size and path compression, the amortised cost per operation is the inverse Ackermann function, below 5 for any realistic input.
  • Path halving (parent[x] = parent[parent[x]]) is an iterative way to compress.
  • Total components = n minus the number of successful unions.

Python tips and shortcuts for this topic

  • parent = list(range(n)); size = [1] * n.
  • Iterative find with path halving: while parent[x] != x: parent[x] = parent[parent[x]]; x = parent[x].
  • Return False from union when roots are equal; this signals a cycle.
  • Components = number of x where find(x) == x.

Python implementation

class DSU:
    def __init__(self, n):
        self.parent = list(range(n))
        self.size = [1] * n
        self.groups = n

    def find(self, x):
        while self.parent[x] != x:
            self.parent[x] = self.parent[self.parent[x]]   # path compression
            x = self.parent[x]
        return x

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                  # already connected
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra              # attach smaller under larger
        self.size[ra] += self.size[rb]
        self.groups -= 1
        return True

Intervals and merging

Important Topic 18.3

Simple definition

An interval is a pair [start, end]. Merging combines overlapping intervals into larger ones.

Why it matters

Calendars, meeting rooms and ranges all use this, and it needs one sort plus one scan.

Real-world analogy

Highlighting overlapping time slots in a calendar to see when you are busy.

From scratch: why this idea exists and how you could invent it

Calendar apps highlight 'busy' blocks by combining overlapping appointments. The input is a jumble of [start, end] pairs in random order. Checking each pair for overlap would be quadratic. The key move is to sort by start time: after that, any interval that overlaps the current block must come right after it.

So one pass suffices: keep the last merged interval; if the next one starts before it ends, extend the end (to the larger end, because the next interval might be shorter and fully inside); otherwise start a new block.

Variants reuse the pattern. Insert an interval: three phases (before, overlapping, after). Free time: gaps between merged blocks. Maximum overlap: sort events and sweep. Intersection of two interval lists: two pointers over both sorted lists.

The main source of wrong answers is the boundary rule: do intervals that touch overlap? Read the statement and pick < or <= accordingly.

Visual explanation (interactive)

Step-by-step walkthrough

  1. Sort by start.
  2. Keep a result list. For each interval: if it starts <= the end of the last merged interval, they overlap -> set last end = max(last end, this end). Otherwise append it as a new interval.
  3. Insert an interval into a sorted list: copy those before, merge overlaps, copy those after.
  4. Check overlap of two intervals: a_start <= b_end and b_start <= a_end.
  5. Watch the merging process in the visualiser.

Deep dive in simple words

Intervals are ranges with a start and end. Questions: merge overlaps, insert a new range, find free time, count the maximum number of overlaps, remove the fewest ranges. The first move is almost always to SORT by start (or by end for selection problems).

After sorting by start, two intervals overlap exactly when the next one starts before or at the current end. Merge by setting end = max(end, next_end). Using max matters because the next interval may be completely inside the current one.

Insert interval: add all intervals that end before the new one starts, merge all that overlap with it, then add the rest.

Counting maximum overlaps: sort the starts and ends separately, or create events (time, +1) and (time, -1), sort them and keep a running count; the maximum count is the answer.

Complexity is dominated by sorting: O(n log n), then O(n) for the scan.

Under the hood: what really happens inside Python

  • Sorting O(n log n) dominates; the scan is O(n). Python sorts lists of lists lexicographically, so sorted(intervals) orders by start then end.
  • Interval trees support dynamic insertion and overlap queries in O(log n + k) when intervals change.

Python implementation

def merge_intervals(intervals):
    merged = []
    for start, end in sorted(intervals):
        if merged and start <= merged[-1][1]:
            merged[-1][1] = max(merged[-1][1], end)   # overlap: extend
        else:
            merged.append([start, end])
    return merged

Matrix traversal and spiral order

Important Topic 18.4

Simple definition

A matrix is a list of lists. Matrix problems rely on careful index arithmetic: rows, columns, diagonals, boundaries and four-direction moves.

Why it matters

Spiral order, rotation, transpose, diagonal sums and search in a sorted matrix are frequent.

Real-world analogy

Reading a page: left to right, top to bottom. A spiral is reading while walking inward along the edges.

From scratch: why this idea exists and how you could invent it

Tables of numbers (spreadsheets, game boards, images) are naturally two-dimensional. A matrix organises data in rows and columns. The challenge is purely geometric: moving around correctly without leaving the table.

Always draw a tiny example (3 x 3) with indices written in each cell. Row index first, then column. Diagonals have r == c (main) and r + c == n - 1 (anti). Boundaries shrink for layered traversals like spiral order.

Many 'rotate/flip' tasks are compositions of two simple moves: transpose (swap across the main diagonal) and reverse rows. Rotating 90 degrees clockwise is transpose then reverse each row; counter-clockwise is reverse each row then transpose.

Sorted matrices permit staircase search from a corner: at each step one comparison eliminates an entire row or column, giving O(rows + cols) instead of O(rows x cols).

Always check how matrices are created. [[0] * c] * r aliases rows; a comprehension creates independent rows.

Visual explanation (interactive)

Step-by-step walkthrough

  1. matrix[r][c]: r = row, c = column. rows = len(m), cols = len(m[0]).
  2. Main diagonal: (i, i). Anti-diagonal: (i, n-1-i). Cells on the same diagonal share r - c; the same anti-diagonal share r + c.
  3. Transpose: swap m[r][c] with m[c][r]. Rotate 90 degrees clockwise: transpose and then reverse every row.
  4. Spiral: keep four boundaries top/bottom/left/right; walk the top row, the right column, the bottom row, the left column, then shrink the boundaries.
  5. Row-wise sorted and column-wise sorted matrix search: start at the top-right, go left if too big, down if too small: O(rows + cols).
  6. Watch the spiral numbering in the visualiser.

Deep dive in simple words

A matrix is a list of lists: matrix[r][c] means row r, column c. rows = len(matrix), cols = len(matrix[0]). Most matrix questions are careful index work. Draw a small 3 x 3 grid with the indices written in each cell before you code.

Useful patterns: cells on the main diagonal have r == c; on the anti-diagonal r + c == n - 1. Transpose swaps m[r][c] with m[c][r]. Rotate 90 degrees clockwise = transpose, then reverse each row. Spiral order uses four shrinking boundaries: top, bottom, left, right.

Row and column sums, searching in a sorted matrix (start at a corner and move left or down), setting rows/columns to zero (first record which, then change), and checking diagonals (Toeplitz) all fit this pattern.

Build a matrix correctly: [[0] * cols for _ in range(rows)]. The shortcut [[0] * cols] * rows repeats ONE row object. Printing a matrix: for row in matrix: print(*row).

Complexity is usually O(rows x cols) because you touch every cell once.

Under the hood: what really happens inside Python

  • A Python matrix is a list of row lists; each row is separate in memory, so column access (m[r][c] varying r) is less cache friendly than row access. NumPy stores one contiguous block.
  • zip(*matrix) unpacks rows as arguments and pairs up their items, producing columns, which is why it transposes.

def transpose(m):
    return [list(row) for row in zip(*m)]

def rotate_clockwise(m):
    return [list(row) for row in zip(*m[::-1])]

def search_sorted_matrix(m, target):
    r, c = 0, len(m[0]) - 1               # start top-right
    while r < len(m) and c >= 0:
        if m[r][c] == target:
            return True
        if m[r][c] > target:
            c -= 1                         # too big: move left
        else:
            r += 1                         # too small: move down
    return False

Prefix sums, difference arrays and 2D prefix sums

Important Topic 18.5

Simple definition

A prefix sum answers "sum of a range" quickly. A difference array does the opposite: it applies "add v to a range" quickly, then rebuilds the final array with one prefix sum.

Why it matters

Together they turn O(n) per query/update into O(1), essential when there are up to 10^5 queries.

Real-world analogy

Prefix sum: the odometer. Difference array: marking only where a change starts and where it stops, instead of repainting every metre.

From scratch: why this idea exists and how you could invent it

If many questions ask 'what is the total of this rectangle?' on a fixed table, recomputing each rectangle costs the rectangle's area every time. Precompute totals of every rectangle anchored at the top-left corner. Any rectangle then equals a big one minus two strips plus the corner subtracted twice: four lookups, constant time. This is inclusion-exclusion, the same idea you use with Venn diagrams.

The reverse situation: many 'add v to everything in this range' updates and only one final question. Applying each update to every cell is slow. Instead record only where each update begins and ends: +v at l and -v just after r. A running total sweeping left to right reconstructs the final array. Updates become O(1).

Prefix sums and difference arrays are inverses: one integrates, one differentiates. Knowing both lets you flip between 'values' and 'changes' whichever makes the question easy.

With remainders as the keys, the same idea counts subarrays whose sum is divisible by k: two prefixes with equal remainder cancel out to a multiple of k.

Step-by-step walkthrough

  1. Prefix: P[i+1] = P[i] + nums[i]. Range sum l..r = P[r+1] - P[l].
  2. Difference: diff[l] += v and diff[r+1] -= v for each update; prefix-sum diff to get the result array.
  3. 2D prefix: P[r+1][c+1] = grid[r][c] + P[r][c+1] + P[r+1][c] - P[r][c]. Rectangle sum = P[r2+1][c2+1] - P[r1][c2+1] - P[r2+1][c1] + P[r1][c1].
  4. Prefix sums combined with a hash map count subarrays with a given sum even with negative numbers.
  5. Monotonic stacks and queues (Module 10) are the other key "advanced array" tools; see sliding window maximum.

Deep dive in simple words

Prefix sums answer 'sum of a range' in O(1) after one O(n) pass. The 2D version does the same for rectangles: P[r][c] holds the sum of the rectangle from the top-left corner to (r-1, c-1). The sum of any rectangle is four lookups: the big corner, minus the strip above, minus the strip on the left, plus the overlap that was subtracted twice.

A difference array is the reverse tool. If you must add v to every element from l to r many times, do not touch every element. Record diff[l] += v and diff[r + 1] -= v. At the end a running sum over diff gives the final array. It turns O(n) updates into O(1).

Together: use prefix sums when the data is fixed and the questions are many; use difference arrays when the questions are updates and you only need the final result. If updates and queries are mixed, you need a Fenwick tree or segment tree.

Prefix sums + dictionary also count subarrays with a given sum, and prefix remainders solve 'subarray sum divisible by k'.

Careful with indices: use a prefix array of length n + 1 with prefix[0] = 0 so the formula prefix[r+1] - prefix[l] works for l = 0.

Under the hood: what really happens inside Python

  • A 2D prefix table has size (R+1) x (C+1); build in O(RC); each query O(1).
  • Difference array of length n + 1 lets updates at r + 1 = n be written without a bounds check.
  • Both rely on associativity and invertibility of addition; for min/max you need other structures.

KMP pattern matching

Advanced Topic 18.6

Simple definition

KMP (Knuth-Morris-Pratt) finds a pattern in a text in O(n + m) by precomputing, for each prefix of the pattern, the length of the longest proper prefix that is also a suffix (the LPS table).

Why it matters

It avoids re-comparing characters after a mismatch, which naive search does, giving a worst-case guarantee.

Real-world analogy

When you misread a word halfway through, you do not restart from the beginning of the sentence - you reuse what you already matched.

From scratch: why this idea exists and how you could invent it

Searching 'ababc' inside 'ababababc' by comparing at each start position wastes effort: after matching 'abab' and failing on the next letter, naive search restarts at the second letter of the text and re-reads letters it has already seen. The failure itself taught us something: we know the last four text letters were 'abab'.

That knowledge should let us continue matching from where we are, but at a position inside the pattern consistent with what we saw. The pattern's own structure answers where: the longest part of the matched prefix that is also a suffix of what we matched ('ab' in 'abab'). We resume with two letters already matched.

That quantity, for every prefix of the pattern, is the LPS table. It depends only on the pattern, so it is built once in O(m). Using it, the text pointer never moves backwards, and the overall time is O(n + m).

Building the table uses the same trick on the pattern against itself: it is like KMP searching the pattern inside itself, falling back via earlier table entries when letters mismatch.

KMP is a rare algorithm whose cleverness is in the preprocessing: spend O(m) to organise knowledge about the pattern so the search never repeats work.

Visual explanation (interactive)

Step-by-step walkthrough

  1. LPS for "ababaca" = [0,0,1,2,3,0,1]. For "abab": [0,0,1,2].
  2. Build: k tracks the length of the current match. For each i, while k > 0 and pat[i] != pat[k]: k = lps[k-1]. If pat[i] == pat[k]: k++. lps[i] = k.
  3. Search: walk through the text; on a mismatch fall back with k = lps[k-1] instead of restarting; when k == m a match ends at i.
  4. The text pointer never moves backwards, so total work is O(n + m).

Deep dive in simple words

KMP solves 'find a pattern in a text' without ever moving backwards in the text. It uses the pattern's own structure: after a partial match fails, part of what you already matched may still be a valid start of a new match, so you do not start over.

LPS table: lps[i] is the length of the longest proper prefix of pattern[0..i] that is also a suffix of it. For 'ababaca' it is [0, 0, 1, 2, 3, 0, 1]. 'Proper' means not the whole string. This table tells you how far back to jump in the pattern after a mismatch.

Building the table: use a variable k for the current matched prefix length. For each position i, while k > 0 and the letters differ, set k = lps[k - 1] (fall back). If the letters match, k += 1. Store lps[i] = k.

Searching uses the same idea: walk through the text; on mismatch fall back with the table; when k reaches the pattern length you found a match, then set k = lps[k - 1] to continue (this allows overlapping matches).

In practice Python's 'pat in text' is fast and enough. Learn KMP for interviews, for questions about the longest prefix that is also a suffix, repeated-substring checks and string periodicity.

Under the hood: what really happens inside Python

  • lps[i] = k means pattern[0:k] equals pattern[i-k+1:i+1]. A string of length m is periodic with period m - lps[m-1] if that divides m.
  • Total fallback steps in the build are bounded by total increments of k, hence linear amortised time.

    lps = [0] * len(pat)
    k = 0
    for i in range(1, len(pat)):
        while k > 0 and pat[i] != pat[k]:
            k = lps[k - 1]               # fall back
        if pat[i] == pat[k]:
            k += 1
        lps[i] = k
    return lps

Segment trees and Fenwick trees (optional advanced)

Advanced Topic 18.7

Simple definition

A Fenwick tree (Binary Indexed Tree) and a segment tree support "update one element" and "query a range sum/min/max" both in O(log n).

Why it matters

Prefix sums are fast to query but slow to update. When updates and queries are interleaved, these trees give O(log n) for both.

Real-world analogy

A company with regional totals: when one store's sales change you update only its regions' totals, and any combined total is the sum of a few regional totals.

From scratch: why this idea exists and how you could invent it

Consider a game leaderboard where scores change constantly and players ask 'what is the total score of ranks 100 to 5000?'. A prefix sum answers range sums in O(1) but one score change forces rebuilding up to n entries. A plain array has fast updates but slow range sums. We need both to be cheap.

The idea: store sums of blocks of different sizes so that any prefix is made of a few blocks, and any single change touches only a few blocks. A Fenwick tree chooses block sizes as powers of two using the binary representation of the index: each cell covers a block whose length is the lowest set bit of its index.

To get a prefix sum, add the block ending at i, then jump to the block ending just before it (remove the lowest set bit), and repeat: at most log n blocks. To update, add the delta to the block containing the position, then to the next larger block that also contains it (add the lowest set bit): again at most log n blocks.

A segment tree stores the answer for whole ranges in a binary tree. It supports more operations (min, max, gcd, range assignment with lazy propagation) at the cost of more code.

These structures are advanced for entry-level rounds; learn them after the essentials, mainly to recognise the situation: many updates AND many range queries.

Step-by-step walkthrough

  1. Fenwick tree: tree[i] stores the sum of a range ending at i whose length is the lowest set bit of i (i & -i).
  2. Update index i by delta: while i <= n: tree[i] += delta; i += i & -i.
  3. Prefix sum up to i: while i > 0: total += tree[i]; i -= i & -i. Range sum l..r = prefix(r) - prefix(l-1).
  4. A segment tree stores aggregates for ranges in a binary tree; it also supports range min/max and lazy range updates (more code).
  5. These are rarely required in entry-level rounds; learn them after everything else is solid.

Deep dive in simple words

Sometimes you need two things on the same array: change one value AND ask for a range sum. A plain prefix array answers sums instantly but changing one value breaks everything after it (O(n) to rebuild). A Fenwick tree (binary indexed tree) and a segment tree answer both in O(log n).

Fenwick tree idea: cell i stores the sum of a block that ends at i and whose length is the lowest set bit of i (i & -i). To get a prefix sum, add cells while removing the lowest set bit from i. To update, add the change to cells while adding the lowest set bit to i. Both take at most about log n steps. The array is 1-indexed.

Segment tree idea: a binary tree where each node stores the answer (sum, min or max) of a range, the root covers everything and the leaves cover single elements. Queries combine a few nodes; updates fix the nodes on one path from leaf to root. It is more flexible (min/max, range updates with lazy propagation) but longer to write.

In entry-level coding rounds these are rare. Learn them only after arrays, hashing, trees, graphs and DP feel comfortable. If you meet a problem with many updates and many range queries on up to 10^5 elements, that is the clue.

Alternatives for simpler cases: sqrt decomposition (blocks of size sqrt n) is easy to code, and offline tricks (sort the queries) sometimes avoid trees completely.

Under the hood: what really happens inside Python

  • Fenwick is 1-indexed. i & -i gives the lowest set bit. Memory O(n), update and query O(log n); build O(n log n) or O(n) with a linear construction.
  • Segment tree is often stored in an array of size 4n with node i's children at 2i and 2i + 1. Queries combine O(log n) nodes.
  • Lazy propagation postpones range updates by marking nodes and pushing updates down only when needed.

class Fenwick:
    def __init__(self, n):
        self.n = n
        self.tree = [0] * (n + 1)         # 1-indexed

    def update(self, i, delta):           # add delta to position i (1-indexed)
        while i <= self.n:
            self.tree[i] += delta
            i += i & -i

    def prefix(self, i):                  # sum of positions 1..i
        total = 0
        while i > 0:
            total += self.tree[i]
            i -= i & -i
        return total

    def range_sum(self, l, r):
        return self.prefix(r) - self.prefix(l - 1)

Basic Conceptual What is Union-Find and what operations does it support?

Basic Conceptual What is path compression?

During find, point every visited node directly to the root (or to its grandparent) so future finds are shorter.

Sort edges by weight and add an edge to the MST if it connects two different components (checked with DSU). Stop after V - 1 edges.

Basic Conceptual What do union by size and path compression each achieve?

Union by size keeps trees shallow; path compression flattens them during finds. Together they give nearly constant amortised time.

O(n log n) for sorting plus O(n) for the pass.

Not sorting first, forgetting max for contained intervals, off-by-one when touching intervals count as overlapping or not.

Basic Conceptual Why sort by start for merging but by end for selection?

Merging needs overlapping intervals adjacent in order of start; selection wants the earliest finishing interval to maximise remaining room.

Basic Conceptual What is a difference array and when do you use it?

An array that stores changes between neighbours. It lets you apply many range additions in O(1) each and rebuild the final array with one prefix sum.

Basic Conceptual Count subarrays whose sum is divisible by k?

Basic Conceptual Prefix sum vs difference array?

They are inverse operations: prefix sum turns values into running totals; difference array turns values into changes. Prefix sum is for fast queries, difference array is for fast range updates.

Basic Conceptual Why is the prefix array of length n + 1?

The extra leading 0 makes range sums work uniformly, including ranges that start at index 0.

Basic Conceptual Why does the 2D formula add back P[r1][c1]?

The two subtracted strips both include that corner region, so it was removed twice.

Basic Conceptual What is the LPS array?

For each prefix of the pattern, the length of the longest proper prefix that is also a suffix. KMP uses it to skip comparisons after a mismatch.

Basic Conceptual Time complexity of KMP?

O(n + m): O(m) to build the table and O(n) to scan the text.

Basic Conceptual Why does KMP never move the text pointer backwards?

On a mismatch it only moves the pattern pointer using the LPS table, reusing information about the already matched text.

Basic Conceptual When would you use KMP over Python's built-in search?

When asked to implement it, or when you need the LPS information itself (periodic strings, longest border).

Basic Conceptual What does lps[i] represent?

The length of the longest proper prefix of pattern[0..i] that is also a suffix of it.

Basic Conceptual When would you use a Fenwick tree?

When you have many point updates and many prefix/range sum queries; both are O(log n).

Basic Conceptual Why does a Fenwick tree use i & -i?

It isolates the lowest set bit of i, which gives the length of the block that cell i is responsible for and the step to jump to the next cell.

Basic Conceptual Segment tree vs Fenwick tree?

Segment tree supports more operations (min, max, range updates with lazy propagation) but needs more code and memory. Fenwick is shorter and faster for sums.

Basic Conceptual Complexity of building and querying?

Query and update O(log n); build O(n) or O(n log n); space O(n).

Basic Conceptual Prefix sums vs Fenwick?

Prefix sums: O(1) query but O(n) update. Fenwick: O(log n) for both.

Basic Conceptual How does a Fenwick tree achieve O(log n) updates and queries?

Each index is responsible for a block sized by its lowest set bit; updates and queries touch at most log n blocks by adding/removing the lowest set bit.
