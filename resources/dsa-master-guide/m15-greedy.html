Greedy Algorithms

Make the locally best choice at every step - but only when you can justify it. Topics in this module: The greedy idea and why greedy sometimes fails; interval and activity-selection greedy strategies.

Important2 topics13 problems36 interview questions

Start from scratch: why this module exists

Sometimes the locally best choice is also globally best. When you can prove that, a problem collapses into a sort and one pass. The hard part is knowing when greedy is valid and when it is a trap.

This module trains both: efficient greedy algorithms (activity selection, jump game) and counterexamples that show where greedy fails and DP is needed.

Who needs it: Schedulers, compression tools (Huffman), network and resource planners, and interviewers testing reasoning rather than coding.

Before you start: Modules 6 and 7.

After this module you can

  • Recognise greedy-friendly problems.
  • Justify a greedy choice with an exchange argument.
  • Find counterexamples quickly.
  • Solve interval and scheduling problems.

Common pitfalls: Assuming greedy works because the sample passes, wrong sorting key, no proof or counterexample attempt.

Typical interview questions here: Activity selection, jump game, gas station, assign cookies, fractional knapsack, minimum platforms, why greedy fails for coin change.

The greedy idea and why greedy sometimes fails

Important Topic 15.1

Simple definition

A greedy algorithm builds a solution by always taking the choice that looks best right now, never reconsidering earlier choices.

Why it matters

When a greedy choice is provably safe it gives very fast, simple solutions (often O(n log n) from sorting). When it is not safe you get a wrong answer that passes samples and fails hidden tests.

Real-world analogy

Filling a backpack by always grabbing the most valuable-looking item first: it works if you can take fractions, but fails if items are indivisible.

From scratch: why this idea exists and how you could invent it

When you give change, you instinctively hand over the biggest coin that fits, then the next biggest. You never reconsider. This is the greedy strategy: pick the best-looking option now. It is fast and simple because there is no search; the whole algorithm is a sort and one pass.

But 'best-looking now' is not always best overall. With coins 1, 3, 4 and amount 6, the biggest-first rule gives 4+1+1 (three coins) while 3+3 needs two. The lesson is that a greedy choice must be proven safe, not just plausible.

A choice is safe if some optimal solution contains it (greedy-choice property) and what is left is a smaller version of the same problem (optimal substructure). The standard proof is the exchange argument: take any optimal solution that does not use the greedy choice and show you can swap the greedy choice in without making it worse.

In practice: sort by a candidate key, try small counterexamples, and if none breaks it and you can sketch the exchange argument, trust it; otherwise move to DP. In an interview, explaining WHY the greedy choice is safe often matters more than the code.

Step-by-step walkthrough

  1. A problem is greedy-friendly when (1) a local best choice is safe (greedy-choice property) and (2) the rest is a smaller instance of the same problem (optimal substructure).
  2. Typical greedy recipe: sort by a clever key, then scan once.
  3. Counterexample: coins [1, 3, 4], amount 6. Greedy takes 4 then 1 + 1 = 3 coins, but 3 + 3 = 2 coins is optimal. Greedy fails here, DP is needed.
  4. With coins [1, 2, 5, 10, 20, 50, 100] greedy IS optimal (canonical systems).
  5. How to test a greedy idea: try to find a counterexample with small inputs (brute force). If you cannot, try an exchange argument: show that swapping any optimal solution towards your greedy choice does not make it worse.
  6. Use the comparison tool: enter coins and an amount to see greedy vs optimal.

Deep dive in simple words

A greedy algorithm makes the best-looking choice at each step and never looks back. It is fast and simple, but only correct when a local best choice is always safe. Many problems look greedy and are not, so always test your idea on tricky small cases.

Two things make greedy work: the greedy-choice property (picking the best local option never ruins the global optimum) and optimal substructure (after the choice, what remains is a smaller version of the same problem). The usual proof method is an exchange argument: take any optimal answer and show you can swap in the greedy choice without making it worse.

A classic failure: coins 1, 3, 4 and target 6. Greedy takes 4 then 1 and 1 (3 coins), but 3 + 3 uses only 2. For coin systems like 1, 2, 5, 10, 20, 50, 100 greedy is optimal, but you cannot assume that. When greedy is unsafe, use dynamic programming.

Typical greedy recipe: sort by a smart key and scan once. Examples: sort intervals by end time, sort items by value/weight ratio (fractional knapsack), sort tasks by deadline.

How to decide in an exam: think of a small counterexample for your greedy rule. If you cannot break it after a few tries and you can explain why a swap never hurts, trust it. Otherwise, consider DP.

Under the hood: what really happens inside Python

  • Typical greedy runtime is O(n log n) for sorting plus O(n) for one scan. Memory is O(1) to O(n).
  • Huffman coding, Prim/Kruskal MST, Dijkstra and activity selection are all greedy algorithms with proofs.
  • Canonical coin systems (like 1, 2, 5, 10, 20, 50, 100) make greedy optimal; arbitrary systems do not.

Python implementation

def greedy_coins(coins, amount):
    count = 0
    for c in sorted(coins, reverse=True):     # biggest coin first
        count += amount // c
        amount %= c
    return count if amount == 0 else -1

def dp_coins(coins, amount):
    INF = float("inf")
    dp = [0] + [INF] * amount
    for a in range(1, amount + 1):
        for c in coins:
            if c <= a:
                dp[a] = min(dp[a], dp[a - c] + 1)
    return dp[amount] if dp[amount] != INF else -1

Why? and Why not?

Why is greedy fast?

It makes one choice per step with no searching, usually after one sort.

Why not trust greedy by default?

A plausible local rule can fail globally (coins 1, 3, 4).

Why use an exchange argument?

It shows any optimal solution can be changed to include the greedy choice without becoming worse.

Why does fractional knapsack allow greedy but 0/1 does not?

Splitting items lets you fill the bag exactly; whole items can leave unusable space.

Why test a greedy idea on small counterexamples?

Most failures show up on tiny inputs, and finding one saves a wrong submission.

How this gets asked

For coins [1, 3, 4] and amount 6 the greedy answer is...

  • 2 coins
  • 3 coins
  • 4 coins
  • 6 coins

Greedy: 4 + 1 + 1 = 3 coins, while 3 + 3 uses only 2.

Fractional knapsack is solved by greedy because...

  • Items can be split, so the best ratio is always safe
  • It is NP-hard
  • Weights are equal
  • Values are sorted

With fractions, taking the best value/weight first is optimal.

Interval and activity-selection greedy strategies

Important Topic 15.2

Simple definition

Interval problems ask to schedule, merge or cover ranges. Sorting the intervals by the right key (usually end time or start time) lets one linear scan decide everything.

Why it matters

Meeting rooms, activity selection, merging intervals and minimum platforms are common greedy/sorting questions.

Real-world analogy

Booking one conference room: always accept the meeting that ends earliest among those that fit - that leaves the most free time for the rest.

From scratch: why this idea exists and how you could invent it

You manage one meeting room and a pile of booking requests. You want to host as many meetings as possible. Which rule do you apply? Earliest start? Shortest meeting? Fewest conflicts? Try each on small examples and you will find counterexamples. The rule that always works is: take the meeting that ENDS earliest.

Why is earliest end the safe choice? Whatever the best schedule is, its first meeting ends no earlier than the earliest-ending meeting. Swap them: the new schedule has the same number of meetings and finishes at least as early, so it leaves at least as much room. That is the exchange argument in action.

Merging intervals is a related but different question: not 'pick as many as possible' but 'combine overlapping ones'. Sorting by START puts overlaps next to each other, so one pass merging into the last interval works.

Counting the maximum number of simultaneous events (rooms, platforms) is a sweep line problem: treat starts as +1 and ends as -1 on a timeline sorted by time and keep a running total; the peak is the answer.

Understanding which key to sort by (start, end, length) and why is the main skill; the code afterwards is tiny.

Visual explanation (interactive)

Step-by-step walkthrough

  1. Activity selection: sort by END time; take an activity if its start >= the last chosen end.
  2. Why end time? Choosing the earliest finish never blocks more options than any alternative (exchange argument).
  3. Merge intervals: sort by START; extend the last interval if the next one overlaps, else start a new one.
  4. Minimum platforms / rooms: sort starts and ends separately; sweep, counting how many are active at once.
  5. Remove minimum intervals to make the rest non-overlapping = n - (max non-overlapping activities).
  6. Use the visualiser to see which activities are accepted or skipped.

Deep dive in simple words

Interval problems ask about ranges [start, end]: meetings, trains, tasks. Nearly all of them start with sorting. The sort key depends on the question.

Activity selection (most non-overlapping meetings): sort by END time. Take the meeting that finishes earliest, then the next meeting that starts at or after that end, and so on. Finishing early leaves the most room for the rest.

Merge intervals: sort by START. If the next interval starts before or at the end of the current merged one, extend the end with max(end, next_end); otherwise start a new group. Do not forget max: a long interval can swallow a short one.

Minimum platforms / rooms: sort all arrival times and all departure times separately. Walk through them like a timeline: an arrival adds one train, a departure removes one. The maximum number at the same moment is the number of platforms needed.

Related: removing the fewest intervals to make the rest non-overlapping equals n minus the maximum selectable activities; inserting an interval into a sorted list; checking if a person can attend all meetings (any overlap after sorting means no).

Under the hood: what really happens inside Python

  • Sorting dominates: O(n log n). The greedy pass is O(n). The sweep-line method is O(n log n) for sorting events.
  • Touching intervals (end == next start) count as overlapping or not depending on the statement; the comparison operator (< vs <=) encodes this.
  • A min-heap of end times is an alternative for room allocation: pop the earliest end if it is <= the new start, otherwise open a new room.

Python tips and shortcuts for this topic

  • sorted(intervals) sorts by start then end.
  • sorted(zip(starts, ends), key=lambda p: p[1]) sorts by end.
  • Overlap test: a_start <= b_end and b_start <= a_end.
  • merged[-1][1] = max(merged[-1][1], end).

Python implementation

def select_activities(starts, ends):
    chosen, last_end = [], float("-inf")
    for s, e in sorted(zip(starts, ends), key=lambda p: p[1]):
        if s >= last_end:                 # compatible with the last chosen
            chosen.append((s, e))
            last_end = e
    return chosen

Overlapping intervals become adjacent, so one pass merges them.

The next interval may be contained inside the current one.

A short interval in the middle can block two longer ones that would fit around it.

Interview questions: Greedy Algorithms

36 questions: try to answer aloud in under a minute, then reveal. All questions from every module are also in the interview bank.

Basic Conceptual What is a greedy algorithm?

An algorithm that builds a solution by always choosing the locally best option, hoping (or proving) it leads to the global best.

Basic Conceptual Give an example where greedy fails.

Coin change with coins [1, 3, 4] and amount 6: greedy gives 4+1+1 (3 coins), optimal is 3+3 (2 coins).

Basic Conceptual Greedy vs dynamic programming?

Greedy commits to one choice per step and is usually faster but only valid under certain properties. DP considers all choices via subproblems and is always correct when the structure fits.

Basic Conceptual Fractional vs 0/1 knapsack - which is greedy?

Fractional: greedy by value/weight ratio is optimal. 0/1 needs DP because you cannot split items.

Basic Conceptual How do you prove a greedy algorithm?

Show the greedy choice property with an exchange argument and the optimal substructure.

Basic Conceptual How do you prove that a greedy algorithm is correct?

Show the greedy-choice property with an exchange argument (an optimal solution can be modified to include the greedy choice) and optimal substructure (the rest is the same kind of problem).

Basic Conceptual Maximum number of non-overlapping meetings - approach?

Sort by end time and greedily pick each meeting whose start is >= the last chosen end. O(n log n).

Basic Conceptual How do you merge overlapping intervals?

Sort by start; for each interval, if start <= last merged end extend the end to the max, otherwise append a new interval.

Basic Conceptual How do you find the minimum number of meeting rooms or platforms?

Sort starts and ends separately and sweep: count +1 on a start and -1 on an end; the peak count is the answer. Or use a min-heap of end times.

Basic Conceptual Why sort by end time for activity selection?

The activity that ends first leaves the maximum remaining time for other activities (exchange argument).

Basic Conceptual How do you decide if two intervals overlap?

They overlap if a.start <= b.end and b.start <= a.end (adjust the inequality if touching counts as no overlap).

Basic Conceptual Why does sorting by shortest duration fail for activity selection?

A short meeting in the middle of the day can block two longer ones that would otherwise fit on either side.

Medium Coding Minimum number of arrows to burst balloons (intervals).

Sort by end; shoot at the first end, skip all balloons starting at or before that end, shoot again at the next uncovered balloon's end. O(n log n).

Medium Coding Meeting rooms II: minimum number of rooms.
import heapq
def min_rooms(iv):
    iv.sort()
    heap = []
    for s, e in iv:
        if heap and heap[0] <= s:
            heapq.heapreplace(heap, e)
        else:
            heapq.heappush(heap, e)
    return len(heap)
