Sorting Algorithms

Know how the classic sorts work, their complexity, stability and when Python's built-in sort is the right answer. Topics in this module: Bubble, selection and insertion sort; merge sort and quick sort; counting sort, heap sort and choosing the right sort.

Start from scratch: why this module exists

Sorting arranges data so that later questions become cheap: finding the median, merging, spotting duplicates, ranking. A huge amount of computing time historically went into sorting, so it has been studied intensely, producing simple O(n^2) methods and the O(n log n) divide-and-conquer methods.

You rarely write your own sort in real Python (sorted() is excellent), but understanding sorting teaches divide and conquer, invariants, stability and why n log n is a lower bound for comparison sorting.

Who needs it: Library authors, database engineers, data analysts, and interviewers testing algorithmic fundamentals.

  • Use counting sort when values are small.
  • Use sorted() with keys for multi-field sorting.

Bubble, selection and insertion sort

Essential Topic 6.1

Simple definition

These are simple O(n^2) comparison sorts. Bubble sort swaps adjacent out-of-order pairs, selection sort repeatedly selects the minimum, insertion sort inserts each element into the sorted part on its left.

Why it matters

They are the foundation for understanding sorting, appear in theory questions, and insertion sort is great for nearly sorted or small data.

Real-world analogy

Insertion sort is sorting a hand of playing cards: take each new card and slide it left until it fits.

From scratch: why this idea exists and how you could invent it

Why do we sort at all? Ordered data makes questions cheap: finding the smallest, searching by halving, spotting duplicates (they sit together), merging two lists, ranking. Sorting is a one-time investment that makes many later operations faster. That is the reason sorting is the most studied problem in computer science.

Imagine sorting a hand of playing cards. Most people do insertion sort without knowing it: pick up a card and slide it into place among the cards already sorted. It works well because each insertion only touches nearby cards. Imagine instead laying all cards out and repeatedly choosing the smallest: that is selection sort. Or walking along the row swapping any two neighbours in the wrong order: bubble sort.

All three do about n^2 / 2 comparisons in the worst case because each element may have to be compared with many others. That is why they are slow for large inputs but perfectly fine (and simple) for tiny ones.

Two properties matter beyond speed. In place: does it need extra memory? Stable: do equal elements keep their original order? Stability matters when you sort by one field after another (sort employees by department, keeping the previous order of names inside each department).

Studying slow sorts is not wasted: they teach the invariants (the sorted part grows by one each pass) that you need to prove and debug the fast sorts.

Visual explanation (interactive)

Step-by-step walkthrough

  1. Bubble: repeat passes; each pass pushes the largest remaining value to the end. Stop early if a pass makes no swaps (best case O(n)).
  2. Selection: find the minimum of the unsorted part, swap it to the front. Always O(n^2), at most n - 1 swaps, NOT stable.
  3. Insertion: key = nums[i]; shift larger elements one step right; drop key into the gap. Stable, in-place, O(n) when nearly sorted.
  4. Stable = equal elements keep their original relative order.
  5. Choose the algorithm in the visualiser and enter your own array; counters show comparisons and swaps.

Deep dive in simple words

Sorting means putting items in order. The three simple methods all take O(n^2) time but think differently. Bubble sort compares neighbours and swaps them if they are in the wrong order; after each pass the biggest item 'bubbles' to the end. Selection sort finds the smallest item in the unsorted part and puts it at the front. Insertion sort takes the next item and slides it left into the right place in the already-sorted part.

Why learn slow sorts? Interviewers ask about them to see if you understand comparisons, swaps, stability and in-place work. Also insertion sort is genuinely the best choice for tiny lists or lists that are almost sorted, and Python's own Timsort uses it for small chunks.

Stable means equal items keep their original order. Imagine sorting students by marks: with a stable sort two students with the same marks stay in the order they were in before. Bubble and insertion sort are stable. Selection sort is not (its long-distance swaps can jump an item over an equal one).

In place means the sort needs only O(1) extra memory. All three simple sorts are in place. Bubble sort can stop early when a full pass makes no swaps, which gives O(n) on an already sorted list.

Counting swaps in bubble sort equals counting 'inversions' (pairs that are in the wrong order). This is a favourite exam question.

Under the hood: what really happens inside Python

  • Bubble sort invariant: after pass i the last i elements are in their final positions. Selection sort invariant: after pass i the first i positions hold the i smallest values in order. Insertion sort invariant: after processing i items the first i items are sorted among themselves.
  • Number of swaps in bubble sort equals the number of inversions (pairs i < j with a[i] > a[j]); insertion sort's shifts also equal the inversion count, which explains why it is fast on nearly sorted data (few inversions).
  • Selection sort does at most n - 1 swaps; useful when writes are expensive (flash memory).

Python implementation

def insertion_sort(nums):
    for i in range(1, len(nums)):
        key = nums[i]
        j = i - 1
        while j >= 0 and nums[j] > key:
            nums[j + 1] = nums[j]    # shift bigger element right
            j -= 1
        nums[j + 1] = key            # drop key into the gap
    return nums

Build it step by step: from the simplest idea to the best

Every stage is runnable and was checked against its stated result.

Stage 1 - plain bubble sort

Compare neighbours and swap. Always O(n^2), even for sorted input.

def sort(a):
    n = len(a)
    for i in range(n - 1):
        for j in range(n - 1 - i):
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
    return a

Check: sort([5, 2, 4, 1]) returns [1, 2, 4, 5]

Stage 2 - stop early

If a whole pass makes no swap the list is sorted, so sorted input costs O(n).

def sort(a):
    n = len(a)
    for i in range(n - 1):
        swapped = False
        for j in range(n - 1 - i):
            if a[j] > a[j + 1]:
                a[j], a[j + 1] = a[j + 1], a[j]
                swapped = True
        if not swapped:
            break
    return a

Check: sort([5, 2, 4, 1]) returns [1, 2, 4, 5]

Stage 3 - insertion sort

Slide each element left into place; far fewer writes on nearly sorted data.

def sort(a):
    for i in range(1, len(a)):
        key, j = a[i], i - 1
        while j >= 0 and a[j] > key:
            a[j + 1] = a[j]
            j -= 1
        a[j + 1] = key
    return a

Check: sort([5, 2, 4, 1]) returns [1, 2, 4, 5]

Why? and Why not?

Why learn bubble sort when nobody uses it?

It teaches comparisons, swaps, invariants and counting operations. These ideas explain every other sort.

Why is insertion sort fast on nearly sorted data?

Each element moves only a short distance, so total shifts equal the small number of inversions.

Why is selection sort not stable?

Its long-distance swap can jump an element over an equal one, changing their original order.

Why not use O(n^2) sorts for big inputs?

n = 10^5 means 10^10 steps. Use sorted() or merge/quick sort.

Why add a swapped flag to bubble sort?

If a pass makes no swap, the list is sorted, so you can stop early.

Merge sort and quick sort

Essential Topic 6.2

Simple definition

Both use divide and conquer. Merge sort splits the list in half, sorts both halves and merges them. Quick sort picks a pivot, partitions smaller values left and larger right, then sorts each side.

Why it matters

They are the O(n log n) sorts you will actually be asked about. Merge sort also solves "count inversions" style problems.

Real-world analogy

Merge sort: two exam-paper piles already sorted are combined by repeatedly taking the lower top paper. Quick sort: pick a reference student and make everyone shorter stand left and taller stand right.

From scratch: why this idea exists and how you could invent it

O(n^2) sorting is too slow for a million items (10^12 steps). We need an idea that avoids comparing everything with everything. The idea: divide and conquer. Split the big sorting job into smaller sorting jobs, sort those, and put the results together cheaply. If combining is O(n) and you can halve the problem log n times, the total is O(n log n).

Merge sort puts the work in combining. Merging two sorted lists is cheap because you only ever look at the two front items. That is the key insight: sorted pieces combine in linear time.

Quick sort puts the work in splitting. Pick a pivot and place every smaller item to its left and every larger item to its right. The pivot is now in its final position and the two sides are independent subproblems that can be sorted separately; no combining is needed. If the pivot lands near the middle, depth is log n; if it lands near an end every time, depth is n and the cost collapses to O(n^2).

Why is quick sort usually faster than merge sort on arrays? It sorts in place without copying, and scanning memory sequentially is cache friendly. Why is merge sort used for linked lists and external (disk) sorting? Merging needs only sequential access.

Randomising the pivot makes the bad case astronomically unlikely, regardless of input order, which is why it is the standard fix.

Step-by-step walkthrough

  1. Merge sort: split until each piece has 1 element, then merge pieces back. Merge uses two pointers on sorted lists.
  2. Complexity: log n levels of splitting and O(n) merging work per level = O(n log n) always. Needs O(n) extra space. Stable.
  3. Quick sort (Lomuto): pivot = last element. Move i to track the boundary of smaller values; swap smaller elements behind the boundary; finally put the pivot at position i + 1.
  4. Average O(n log n); worst O(n^2) when the pivot is always the min or max (sorted input with a bad pivot). Randomised pivots avoid this. In place, not stable.
  5. Use the animation to see the pivot (purple) and partition boundary or the merging of halves.

Deep dive in simple words

Both fast sorts use divide and conquer: split a big problem into smaller ones, solve them, and put the answers together. Merge sort does the hard work when COMBINING; quick sort does the hard work when SPLITTING.

Merge sort: cut the list in half until you have lists of 1 item (already sorted). Then merge two sorted lists into one by repeatedly taking the smaller front item. There are about log n levels and each level costs O(n) to merge, so O(n log n) always. It needs extra memory (O(n)) but it is stable and predictable.

Quick sort: pick a pivot, then rearrange so smaller items are left of the pivot and larger items right (partition). The pivot is now in its final place. Sort the left and right parts the same way. On average O(n log n) and very fast in practice because it works in place. If the pivot is always the smallest or biggest item, it degrades to O(n^2). Choosing a random pivot makes this very unlikely.

Which to choose? Need guaranteed speed or stability, or sorting linked lists: merge sort. Need in-place and fastest on average for arrays: quick sort. In Python just use sorted().

Merge sort can be modified to count inversions: when you take an item from the right half, all items still waiting in the left half are bigger than it, so add that count. This is why merge sort appears in harder questions.

Under the hood: what really happens inside Python

  • Merge sort recursion tree: log2(n) levels, each doing O(n) merging work, so O(n log n) regardless of data. It needs an auxiliary array of size n (O(n) extra space).
  • Quick sort partition (Lomuto): i marks the end of the 'smaller than pivot' zone. Hoare's partition does fewer swaps. Worst-case input for a naive pivot is an already-sorted array.
  • Median-of-three (first, middle, last) or random pivot avoids that. Introsort switches to heap sort when recursion depth gets too large, guaranteeing O(n log n).

Python implementation

def merge_sort(nums):
    if len(nums) <= 1:
        return nums
    mid = len(nums) // 2
    left, right = merge_sort(nums[:mid]), merge_sort(nums[mid:])
    merged, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:           # <= keeps the sort stable
            merged.append(left[i]); i += 1
        else:
            merged.append(right[j]); j += 1
    return merged + left[i:] + right[j:]

def quick_sort(nums, lo=0, hi=None):
    if hi is None:
        hi = len(nums) - 1
    if lo < hi:
        pivot, i = nums[hi], lo - 1
        for j in range(lo, hi):
            if nums[j] <= pivot:          # belongs on the left side
                i += 1
                nums[i], nums[j] = nums[j], nums[i]
        nums[i + 1], nums[hi] = nums[hi], nums[i + 1]
        quick_sort(nums, lo, i)           # left of pivot
        quick_sort(nums, i + 2, hi)       # right of pivot
    return nums

Merge sort: O(n log n) always, O(n) space. Quick sort: O(n log n) average, O(n^2) worst, O(log n) stack space.

  • Merge step forgetting the leftover elements.

It halves the list log n times and each level merges n items, regardless of the order of the input.

Counting sort, heap sort and choosing the right sort

Important Topic 6.3

Simple definition

Counting sort counts occurrences of each small integer value and rebuilds the output. Heap sort builds a max-heap and repeatedly moves the largest to the end.

Why it matters

Counting sort beats O(n log n) when the value range is small. Heap sort gives O(n log n) with O(1) extra space and no bad worst case.

Real-world analogy

Counting sort is sorting exam marks (0-100) by dropping each paper into one of 101 labelled trays, then reading the trays in order.

From scratch: why this idea exists and how you could invent it

There is a famous result: any algorithm that sorts by comparing pairs of elements needs at least about n log n comparisons in the worst case. Think of a decision tree: with n! possible orders and each comparison giving one of two answers, you need at least log2(n!) which is about n log n comparisons.

To beat n log n you must stop comparing and use extra knowledge about the data. Counting sort knows the values are small integers, so it can drop each item straight into its bucket (a tally slot) in O(1). Radix sort extends this to big numbers by sorting digit by digit. This shows a deep idea: more assumptions about the data can buy more speed.

Heap sort comes from a different place: a heap can always hand you the maximum cheaply (O(log n)). If you build a heap and repeatedly take the max, you get a sorted order. The structure does the comparing work. It uses no extra memory and has no bad case, which is why it is a safety net inside introsort.

Python's Timsort observed that real-world data often contains already-ordered runs. It detects the runs and merges them, doing less than n log n work on such data, while staying stable and never worse than O(n log n).

Visual explanation (interactive)

Step-by-step walkthrough

  1. Counting sort: counts = [0] * (max+1); counts[x] += 1 for each x; then output each value counts[v] times. O(n + k) where k = value range.
  2. Heap sort: heapify the array into a max-heap (O(n)), then repeat: swap the root (max) with the last unsorted element, shrink the heap, sift the new root down.
  3. Python's sorted() / list.sort() use Timsort: stable, O(n log n), fast on partially sorted data. In an assessment, use it unless the problem forbids it.
  4. Sort with a key: sorted(words, key=len), sorted(pairs, key=lambda p: (-p[1], p[0])), reverse=True for descending.
  5. Choosing: small n -> any; stability needed -> merge/insertion/Timsort; tiny integer range -> counting; memory-tight guaranteed bound -> heap sort.

Deep dive in simple words

Counting sort does not compare items at all. If you know all values are small whole numbers (like marks 0-100 or letters), make a tally list where index = value, count each item, and then write each value out as many times as its tally. It costs O(n + k) where k is the largest value. For small k this beats O(n log n).

Heap sort first turns the list into a max-heap (a tree where every parent is bigger than its children). The biggest item is at the root, so you swap it to the end of the list, shrink the heap by one, and fix the heap. Repeat. It is O(n log n) always and in place, but not stable and not as fast as quick sort in practice.

Python's built-in sort is Timsort. It looks for runs that are already in order, uses insertion sort on small pieces and merges runs. It is stable, O(n log n) worst case and O(n) on nearly sorted data. In a coding round, use it unless told otherwise.

The key argument is powerful: sorted(items, key=f) sorts by the value of f(item). For multiple fields return a tuple. For descending numbers return the negative: key=lambda p: (-p.score, p.name).

Stability trick: to sort by two criteria you can sort by the less important one first and the more important one second, because a stable sort keeps the earlier order for ties.

Under the hood: what really happens inside Python

  • Counting sort: counts array of size k + 1; then either rebuild from counts (unstable, simple) or compute prefix sums of counts to place items into an output array (stable). Time O(n + k), space O(n + k).
  • Heap sort: building a max-heap bottom-up is O(n); each of n extractions is O(log n), so total O(n log n). The sorted part grows at the end of the same array.
  • Timsort: finds natural runs, extends short runs with insertion sort (minrun about 32-64) and merges runs with rules that keep merges balanced, giving worst case O(n log n) and best case O(n).

Python implementation

def counting_sort(nums):
    if not nums:
        return nums
    counts = [0] * (max(nums) + 1)
    for x in nums:
        counts[x] += 1                 # tally
    out = []
    for value, c in enumerate(counts):
        out.extend([value] * c)        # rebuild in order
    return out

def heap_sort(nums):
    n = len(nums)
    def sift_down(i, size):
        while True:
            big, l, r = i, 2 * i + 1, 2 * i + 2
            if l < size and nums[l] > nums[big]: big = l
            if r < size and nums[r] > nums[big]: big = r
            if big == i:
                return
            nums[i], nums[big] = nums[big], nums[i]
            i = big
    for i in range(n // 2 - 1, -1, -1):    # build max-heap
        sift_down(i, n)
    for end in range(n - 1, 0, -1):        # move max to the end
        nums[0], nums[end] = nums[end], nums[0]
        sift_down(0, end)
    return nums

Time and space complexity

Counting sort O(n + k) time and space (negatives/large ranges need adjustment). Heap sort O(n log n) time, O(1) space, not stable.

Common mistakes and edge cases

  • Using counting sort with huge value ranges (memory blowup).
  • Negative numbers in counting sort without an offset.
  • Writing your own sort when sorted() is allowed.

How to recognise problems that use this technique

  • Values limited to 0..100 or letters a-z -> counting.
  • "Sort by multiple criteria" -> key with tuple.

Why? and Why not?

Why can counting sort beat n log n?

It does not compare items; it uses the values as indexes. The n log n bound applies only to comparison sorts.

Why not use counting sort for any list?

If the value range is huge (like 10^9), the count array needs too much memory.

Why use heap sort?

It guarantees O(n log n) and sorts in place with O(1) extra memory.

Why is Timsort fast on real data?

Real data often has ordered runs. Timsort detects and merges them, doing less work than n log n.

Why sort with key= instead of cmp?

A key is computed once per element and is faster and simpler than comparing pairs with a function.

Interview questions: Sorting Algorithms

Basic Conceptual What is the time complexity of bubble sort? Can it be improved?

O(n^2) in the worst and average case. With a flag that stops when a pass has no swaps, the best case (already sorted) becomes O(n).

Basic Conceptual What does a stable sort mean?

Equal elements keep their original relative order. This matters when you sort records by one field and want a previous order kept for ties.

Basic Conceptual Which simple sort makes the fewest swaps?

Selection sort makes at most n - 1 swaps, which is useful when writing to memory is expensive.

Basic Conceptual Which simple sort is best for nearly sorted data?

Insertion sort, because each element only moves a short distance. It runs in about O(n).

Basic Conceptual Write insertion sort.
def insertion_sort(a):
    for i in range(1, len(a)):
        key, j = a[i], i - 1
        while j >= 0 and a[j] > key:
            a[j + 1] = a[j]
            j -= 1
        a[j + 1] = key
    return a
Basic Conceptual Which O(n^2) sort is best for almost sorted data and why?

Insertion sort: it shifts each element only past larger neighbours, so work is proportional to the number of inversions, close to O(n).

Basic Conceptual Compare merge sort and quick sort.

Merge sort: always O(n log n), stable, needs O(n) extra space. Quick sort: average O(n log n), worst O(n^2), in place (O(log n) stack), not stable. Quick sort is usually faster in practice due to cache friendliness.

Basic Conceptual What is the worst case of quick sort and how do you avoid it?

O(n^2) when partitions are very unbalanced, e.g. an already sorted array with the last element as pivot. Avoid it with a random pivot or median-of-three.

Basic Conceptual What is the recurrence of merge sort?

T(n) = 2T(n/2) + O(n), which solves to O(n log n).

Basic Conceptual How can merge sort count inversions?

While merging, when an element from the right half is placed before elements still left in the left half, add len(left) - i to the count. Total O(n log n).

Basic Conceptual Why is merge sort good for linked lists?

Merging needs only pointer changes and no random access, so it is O(n log n) with O(1) extra space on lists.

Basic Conceptual Write the merge step.
def merge(a, b):
    out, i, j = [], 0, 0
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            out.append(a[i]); i += 1
        else:
            out.append(b[j]); j += 1
    return out + a[i:] + b[j:]
Basic Conceptual Why is merge sort stable and quick sort not?

Merge sort takes from the left half when values are equal, preserving order. Quick sort's partition swaps elements across the pivot and may reorder equal values.

Basic Conceptual When is counting sort a good choice?

When the range of values k is small compared to n, such as marks 0-100 or lowercase letters. Time O(n + k), space O(k).

Basic Conceptual What sorting algorithm does Python use?

Timsort: a stable hybrid of merge sort and insertion sort, O(n log n) worst case and fast on partially sorted data.

Basic Conceptual Is heap sort stable? Is it in place?

In place: yes. Stable: no.

Basic Conceptual How do you sort a list of tuples by the second item descending and the first ascending?
sorted(pairs, key=lambda p: (-p[1], p[0]))
Basic Conceptual What is the lower bound of comparison-based sorting?

Omega(n log n). Any algorithm that only compares items needs at least about n log n comparisons. Counting sort avoids this by not comparing.

Basic Conceptual Can you sort faster than O(n log n)?

Yes, when you are not limited to comparisons and know something about the data: counting sort O(n + k), radix sort O(d(n + k)), bucket sort O(n) on uniform data. For general comparison-based sorting n log n is the lower bound.

Medium Coding Implement selection sort.
def selection_sort(a):
    for i in range(len(a) - 1):
        m = i
        for j in range(i + 1, len(a)):
            if a[j] < a[m]:
                m = j
        a[i], a[m] = a[m], a[i]
    return a

Advanced Follow-up How do you make a stable version of selection sort?

Instead of swapping, shift the elements between i and m one step right and place the minimum at i (insertion-like), keeping equal elements in order.
