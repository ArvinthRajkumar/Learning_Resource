1. Skills that entry-level coding assessments commonly test

General preparation guidance based on how entry-level coding tests are usually designed, not an official Infosys syllabus.

  • Core programming logic: loops, conditions, functions, number and string manipulation.
  • Arrays/lists and strings: by far the most common containers.
  • Hashing (dictionary/set) and sorting to turn O(n^2) ideas into O(n) or O(n log n).
  • Searching (including binary search), two pointers and sliding window.
  • Basic recursion; for stronger tests also trees, graphs, greedy and dynamic programming.
  • Careful input parsing, edge cases and clean output formatting.

Suggested priority: modules 1 to 8 first (Essential), then stacks and queues, linked lists, recursion, trees, graphs, greedy and DP, then the advanced extras.

2. Analyse a problem before you code

  1. Read the whole statement twice. Underline: input format, output format, constraints, special words (distinct, contiguous, sorted, minimum/maximum, modulo).
  2. Restate it in one sentence in your own words.
  3. Work the sample by hand and make sure you can reproduce the sample output.
  4. List edge cases: empty/one element, all equal, negatives, zeros, maximum size, duplicates.
  5. Use the constraints to pick the target complexity (see the table below).
  6. Only then write code.

3. From brute force to an efficient solution

Always get a correct brute force first (even if only in your head), then ask "what work is repeated?" and use a tool to remove it.

Repeated workToolTypical gain
Searching the same list again and againHash set / dictO(n) to O(1) per lookup
Re-adding the same range sumsPrefix sumsO(n) to O(1) per query
Re-summing a moving windowSliding windowO(nk) to O(n)
Checking all pairs in sorted dataTwo pointersO(n^2) to O(n)
Searching sorted dataBinary searchO(n) to O(log n)
Recomputing the same subproblemMemoisation / DPO(2^n) to polynomial
Repeatedly finding min/maxHeapO(n) to O(log n)
"Next greater/smaller"Monotonic stackO(n^2) to O(n)

Worked example, Two Sum. Brute force: two nested loops, O(n^2). Observation: for each x we are asking "is target - x somewhere in the list?". A dict answers that in O(1), so one pass gives O(n). See the Two Sum problem.

6. Input parsing and output formatting in Python

Pick the input format shown in the problem statement and copy the matching template. Match the output format exactly: spacing, line breaks, True vs true, decimal places.

One integer

n = int(input())
print(n * 2)

Two integers on one line

a, b = map(int, input().split())
print(a + b)

n, then n numbers on the next line

n = int(input())
nums = list(map(int, input().split()))
print(sum(nums))

n lines, one value each

n = int(input())
vals = [int(input()) for _ in range(n)]
print(max(vals))

Matrix: r c then r rows

r, c = map(int, input().split())
grid = [list(map(int, input().split())) for _ in range(r)]
print(sum(map(sum, grid)))

A string / sentence

s = input().strip()
words = s.split()
print(len(words))

Several test cases

t = int(input())
for _ in range(t):
    n = int(input())
    arr = list(map(int, input().split()))
    print(max(arr))

Unknown amount of input (until EOF)

import sys
data = sys.stdin.read().split()
nums = list(map(int, data))
print(len(nums))

Output templates

print(*nums)                 # 1 2 3  (space separated, one line)
print("\n".join(map(str, nums)))  # one value per line
print("YES" if ok else "NO") # exact words required by the judge
print(f"{value:.2f}")         # exactly 2 decimals
print(int(x))                 # avoid printing 5.0 when 5 is expected

7. Test boundary conditions before submitting

  • Smallest allowed input (n = 0 or 1, empty string).
  • Largest allowed input (can your complexity survive it?).
  • All elements equal / all distinct / already sorted / reverse sorted.
  • Negative numbers, zeros, very large values.
  • Target at the first or last position; target absent.
  • Duplicates; off-by-one at the ends of ranges.
  • Strings: single character, spaces, upper/lower case.

8. Managing time across several questions

  • Spend the first minutes skimming ALL questions; mark the easiest.
  • Solve the easiest first to bank marks and confidence.
  • Time-box each problem. If you are stuck with no new idea for about 10 minutes, move on and return later.
  • A correct but slower solution that passes most test cases usually beats an unfinished perfect one: submit a working brute force, then improve it if time remains.
  • Leave the last few minutes to re-run sample tests and edge cases on every submitted solution.
  • Check how your platform scores (partial marks per test case vs all-or-nothing) in the instructions and plan accordingly.

9. Debugging wrong or slow solutions

  1. Re-read the statement: is the output exactly what was asked?
  2. Run the samples, then your own tiny tests (n = 1, 2, 3).
  3. Print intermediate variables or dry-run by hand (use the dry-run tables in this guide as a model).
  4. Compare with a slow brute-force solution on random small inputs to find a failing case.
  5. If the answer is right but times out, recompute the complexity and look for repeated work.
  6. If you get a runtime error (IndexError, RecursionError, division by zero), check bounds, base cases and zero inputs.

11. Practise under timed conditions

Simulate a coding round: pick two or three unseen problems from the problem sets (one easy, one medium, one hard), set a timer, and keep the hints and solutions closed until it rings. Then take the final assessment and build a plan on the roadmap.
