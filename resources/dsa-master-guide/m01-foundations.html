Python essentials for coding rounds

Essential Topic 1.1

Simple definition

Python is a language where you store values in named boxes (variables), combine them with operators, make decisions with if/elif/else, repeat work with for/while loops and package logic in functions.

Why it matters

Every DSA solution is built from these pieces. A coding round also needs fast, correct input parsing: many beginners lose marks because their code does not read the input format exactly.

Real-world analogy

Think of a recipe: ingredients are variables, cooking steps are statements, "repeat stirring 5 times" is a loop, "if the soup is cold, heat it" is a condition, and a recipe card you can reuse is a function.

From scratch: why this idea exists and how you could invent it

Start with the raw problem: a computer can only follow exact instructions, one after another. To solve anything you need three abilities: remember things, decide things and repeat things. Every programming language is a different spelling of those three abilities. Remembering = variables. Deciding = if / elif / else. Repeating = loops.

Why do variables exist? Without them the computer would have to re-type every value each time it was needed. A variable gives a value a name so one name can be reused in many places and changed in one place. Naming also lets YOU read the program like a story: total_marks is far clearer than 450.

Why do data types exist? The machine stores everything as bits. The type tells it how to read those bits: as a whole number, a fraction, text, or true/false. int + int adds, str + str glues. Mixing types ('5' + 3) is an error because the machine cannot guess what you meant. That is why we convert with int() and str().

Why loops and conditions? Imagine adding 1 to 1,000,000 by writing 1,000,000 lines. Loops let you write the instruction once and say how many times. Conditions let one program react to different data: pass or fail, even or odd, found or not found.

Why functions? Once a piece of logic works, you want to reuse it without copying it. A function packs logic behind a name with inputs (parameters) and an output (return value). This is also how you break a large problem into small solvable ones, which is the core skill of this entire guide.

Why does a coding round care about input/output details? An online judge is a machine, not a person. It feeds your program exact text and compares your exact text output. One extra space or a missing newline is a failed test, even if your logic is perfect. That is why we practise reading and printing carefully from day one.

Step-by-step walkthrough

  1. Variables hold values: age = 20 (int), pi = 3.14 (float), name = "Asha" (str), ok = True (bool), nums = [1, 2] (list), seen = {1, 2} (set), ages = {"a": 1} (dict), pair = (1, 2) (tuple).
  2. Operators: + - * / (true division gives float) // (floor division) % (remainder) ** (power). Comparisons give True/False. Combine with and, or, not.
  3. Remember: 7 // 2 = 3, 7 % 2 = 1, -7 // 2 = -4 (floors toward minus infinity), int(-3.5) = -3 (truncates toward zero).
  4. Loops: for x in nums iterates values; for i in range(n) gives 0..n-1; while cond repeats until the condition becomes False.
  5. Read input with input() (always a string) and convert: int(input()), list(map(int, input().split())).
  6. Trace the example below: the line "3 5 8 10" becomes [3, 5, 8, 10]; we add the even numbers (8 and 10) and also report the count and the maximum.

Deep dive in simple words

Think of a variable as a label stuck on a box. The box holds a value, and the label is the name you use to find it. In Python you do not declare the type: x = 5 makes an int box, and later x = 'hi' just moves the label to a new str box. This is called dynamic typing. It is easy to write, but it means a typo in a name can silently create a brand new variable, so read your names carefully.

Python has two kinds of values: immutable (cannot change in place) and mutable (can change in place). int, float, str, bool and tuple are immutable. list, dict and set are mutable. This matters a lot: if you write b = a for a list, both names point to the SAME list. Change one and the other changes too. To get a real copy write b = a[:] or b = list(a).

Truthiness is a handy trick. Empty things count as False: 0, '', [], {}, set() and None. Everything else counts as True. So 'if nums:' means 'if the list is not empty', and 'while stack:' means 'while the stack still has items'. Interviewers like short, readable code like this.

Loops: use 'for x in nums' when you only need the values, 'for i in range(len(nums))' when you need the index, and 'for i, x in enumerate(nums)' when you need both. Use 'while' only when you do not know how many repeats are needed. Beginners often write range(len(nums)) everywhere; enumerate is cleaner.

On coding platforms, the slowest part is often reading input. input() is fine for small data. For big data use sys.stdin.read().split() once and then walk through the list. Also, never print extra text such as 'Enter n:' - the judge compares your output exactly.

Under the hood: what really happens inside Python

  • In CPython a variable is not a box but a NAME that points to an object in memory. x = 5 makes a name x point at an int object 5. y = x makes y point at the same object. Because ints are immutable, x = x + 1 creates a new int object and re-points x; y still points at the old one.
  • A list is also an object. a = [1, 2]; b = a gives two names for ONE list, which is why changing through b changes a. The id(obj) function shows the identity (memory address) of an object, and 'is' compares identities.
  • Python integers have unlimited size. When a number grows past the machine word, Python switches to a multi-digit representation automatically, so you never worry about overflow, but very huge numbers are slower.
  • input() always reads a line as text (str). Conversion functions (int, float) parse text into numbers. sys.stdin.read() reads the whole input in one call, which is much faster than thousands of small input() calls on large tests.

Python tips and shortcuts for this topic

  • Swap two variables without a temp: a, b = b, a.
  • Chained comparison: 0 <= i < n works exactly like it reads. Python checks both sides.
  • Use // for whole-number division and % for remainder. divmod(a, b) gives both at once: q, r = divmod(17, 5).
  • Unpacking: first, *rest = [1, 2, 3, 4] gives first = 1 and rest = [2, 3, 4].
  • f-strings make output easy: print(f'{name} scored {score:.1f}').
  • Conditional expression: label = 'even' if n % 2 == 0 else 'odd'.

def summarize(line):
    nums = list(map(int, line.split()))   # "3 5 8 10" -> [3, 5, 8, 10]
    total = 0                             # sum of even numbers
    for x in nums:
        if x % 2 == 0:
            total += x
    return total, len(nums), max(nums)

Build it step by step: from the simplest idea to the best

Every stage is runnable and was checked against its stated result.

Stage 1 - use text

Easy to write: turn the number into a string and add the digits. Works, but converts types and allocates a string.

def digit_sum(n):
    return sum(int(ch) for ch in str(n))

Check: digit_sum(493) returns 16

Stage 2 - use arithmetic

Peel off the last digit with % 10 and drop it with // 10. No strings, constant memory, and it shows you understand how numbers work.

def digit_sum(n):
    total = 0
    while n > 0:
        total += n % 10
        n //= 10
    return total

Check: digit_sum(493) returns 16

Why? and Why not?

Why does Python not make you declare variable types?

Python decides the type from the value at run time (dynamic typing). It makes short programs easy to write. The price is that mistakes (like adding a number to text) appear only when that line runs.

Why not use input() for very large input?

Each input() call has overhead. For 10^5 lines the calls add up. sys.stdin.read().split() reads everything at once and is much faster.

Why convert with int() instead of just using the text?

Text '5' + '3' joins to '53'. Only numbers can be added. The conversion tells Python what kind of data you mean.

Why use a for loop instead of a while loop when counting?

A for loop updates the counter for you, so you cannot forget it and create an endless loop. while is for 'repeat until something changes'.

Why not name variables a, b, c?

Short names hide meaning. total_marks tells the reader (and you, an hour later) what the value is. Good names are a cheap form of documentation.

Understanding a problem and dry-running

Essential Topic 1.2

Simple definition

Understanding a problem means extracting its inputs, outputs, constraints and edge cases before writing any code. A dry run means executing your code by hand on a small example, writing down the value of each variable at each step.

Why it matters

Most failed submissions are not caused by hard algorithms but by misread requirements or untested edge cases. Dry running finds bugs without running a judge.

Real-world analogy

Before building furniture you read the instructions, check the dimensions and test the pieces fit. A dry run is assembling it once on the floor before screwing anything in.

From scratch: why this idea exists and how you could invent it

Think about how an experienced engineer is paid: not to type code fast, but to avoid building the wrong thing. A coding question is a tiny customer request. The customer has told you what they want (output), what they will give you (input) and the rules (constraints). Most of the work is understanding the request; typing the solution is the small part.

Why constraints? They were chosen by the problem setter to let one family of solutions pass and another fail. If n is 20, the setter expects brute force over all subsets (2^20 is about a million). If n is 10^5, the setter expects O(n log n). Reading constraints is like reading the answer key's hint for the intended complexity.

Why edge cases? Test writers add inputs that break careless code: empty, single item, duplicates, negatives, huge values. These tests usually carry a large share of the marks. Naming them BEFORE coding is a habit that separates strong candidates.

Why dry run? Your brain reads what you intended, not what you wrote. A table that records the real value of every variable after every line forces you to see what the computer sees. Debugging then becomes finding the first row where the table differs from what you expected.

Why break problems down? Human working memory holds about four things at once. A problem split into four small steps fits in your head; one big blob does not. This is exactly the same reason functions exist.

Step-by-step walkthrough

  1. Step 1 - Restate the problem in one sentence. "Count how many numbers in the list are divisible by k."
  2. Step 2 - Write the input and output format, with types and ranges. Constraints tell you the allowed complexity: n up to 10^5 means O(n log n) is fine, O(n^2) is not.
  3. Step 3 - List edge cases: empty input, one element, all equal, negatives, zeros, maximum size.
  4. Step 4 - Work a sample by hand. Here: nums = [4, 7, 8, 9, 12], k = 4.
  5. Step 5 - Write the plan in plain English, then code it.
  6. Step 6 - Dry-run the code (table below): count goes 0 -> 1 -> 1 -> 2 -> 2 -> 3. Answer 3.

Deep dive in simple words

A problem statement has five parts you should pull out like a detective: (1) what is GIVEN (input), (2) what must be PRODUCED (output), (3) the RULES (constraints), (4) the sample, and (5) the hidden traps (edge cases). Write them down in your own words. If you cannot explain the problem to a friend in one sentence, you are not ready to code.

Constraints are a secret hint about the answer. If n is at most 10, even a very slow method (checking every arrangement) works. If n is up to 100000, you need something close to one pass or one sort. If the numbers can be as big as 10^9, add them carefully in your head: sums of many such numbers can be huge, but Python handles big integers automatically, which is a big advantage over C or Java.

A dry run is the cheapest debugging tool you have. Draw a table with one column per variable. Run your code line by line on a tiny input (3-5 items). After every line, write the new values. When the table disagrees with what you expected, you have found your bug. The dry-run tables in this guide were made exactly this way.

Edge cases are inputs at the edge of what is allowed: empty list, a single element, all items equal, all negative numbers, zero, the biggest allowed input, already-sorted input. Most hidden test failures come from here. Before submitting, run your code on at least two of these.

Break big problems into small steps. Example: 'find the second largest number'. Step 1: handle lists shorter than 2. Step 2: track two variables, first and second. Step 3: update them as you scan. Step 4: return -1 if second was never found. Each step is easy on its own.

Under the hood: what really happens inside Python

  • A dry-run table is a manual simulation of the interpreter: Python executes one statement at a time, updating names in a frame (a small dictionary of local variables). Your table is that dictionary written out line by line.
  • When you use the debugger or print statements you are doing the same thing automatically. This guide's dry-run tables were produced by running the real code with a tracing hook that records local variables at every line.

Why? and Why not?

Why write down edge cases before coding?

Because after coding you will unconsciously test only inputs your code already handles. Listing them first makes you design for them.

Why not start coding as soon as you see a familiar problem?

Similar-looking problems often differ in one detail (distinct vs duplicates, sorted vs unsorted, indices vs values). Coding the wrong variant wastes the whole attempt.

Why do constraints decide the algorithm?

They tell you how many steps you can afford. n = 10^5 allows about n log n steps, so an O(n^2) idea is rejected before you write it.

Why dry-run instead of just running the code?

Running tells you the result is wrong; dry running shows exactly which line first goes wrong. It also works when no judge or tests are available.

Why break a problem into steps?

People hold only a few things in mind at once. Small steps fit in memory, are easy to test separately and map to functions.

Functions and recursion basics

Essential Topic 1.3

Simple definition

A function is a named, reusable block of code that takes inputs (parameters) and gives back a result (return value). Recursion is when a function calls itself on a smaller version of the problem until it reaches a simple base case.

Why it matters

Functions keep solutions organised and testable. Recursion is the natural way to express trees, backtracking and divide-and-conquer.

Real-world analogy

Looking up a word whose definition uses another word you do not know: you look that one up, and so on until you reach a word you understand (base case). Then you walk back out, understanding each in turn.

From scratch: why this idea exists and how you could invent it

Imagine solving a big problem like 'count down from 5 and multiply'. You could write one long program. But you notice that 'multiply n by the answer for n - 1' keeps appearing. A function lets you name that step once. This is abstraction: use a thing without re-thinking how it works inside.

Recursion starts from a natural observation: some problems contain a smaller copy of themselves. n! is n times (n-1)!. A folder contains folders. A tree contains smaller trees. If a function can call itself on the smaller copy, the code mirrors the problem's own structure and is often much shorter than a loop.

But a self-calling function would never stop, so you must specify where it ends. The base case is the smallest copy you can answer directly (0! = 1). Together: base case + smaller call = a complete definition, exactly like a proof by induction in mathematics: prove the smallest case, then show that if it holds for n - 1, it holds for n.

How can the machine do this? It needs to remember where to return to after each call. It uses the call stack: each call gets a frame containing its own variables and a return address. A deeper call pushes a frame; finishing pops it. That is why recursion costs memory proportional to depth.

Why does Python limit recursion to about 1000 frames? A runaway recursion would otherwise eat all memory and crash the whole interpreter. The limit is a safety net, and it tells you to use loops (or an explicit stack) when depth can be large.

Visual explanation (interactive)

Step-by-step walkthrough

  1. factorial(4) = 4 x factorial(3). The function calls itself with n - 1.
  2. Base case: factorial(0) = 1 (or 1 when n <= 1). Without it the calls never stop - Python raises RecursionError after about 1000 nested calls.
  3. Going down: factorial(4) -> factorial(3) -> factorial(2) -> factorial(1). Each call waits on the call stack.
  4. Coming back up: factorial(1) returns 1; factorial(2) returns 2 x 1 = 2; factorial(3) = 6; factorial(4) = 24.
  5. The dry-run table shows n shrinking by one on each deeper call (the depth column d).

Deep dive in simple words

A function should do one job and have a clear name. Parameters are the inputs written in the definition; arguments are the actual values you pass in a call. A function without a return statement quietly returns None, which is a very common beginner bug when you print the result and see 'None'.

Recursion looks like magic until you see the call stack. Every call is placed on top of a stack of 'unfinished jobs'. When a call finishes it is removed and its answer is handed to the call below it. Draw the stack on paper once for factorial(3) and it will click forever.

Every recursive function needs: (1) a base case that stops, (2) a step that moves toward the base case, and (3) trust that the smaller call returns the correct answer. Do not try to follow every call in your head. Just check the base case and the combine step.

Recursion costs memory: each active call uses space, so depth n means O(n) extra space. Python stops at about 1000 nested calls with RecursionError. When depth could be 10^5, switch to a loop or use sys.setrecursionlimit carefully.

Recursion is not always faster or nicer. A loop is better for simple counting. Recursion shines for trees, nested data, divide and conquer and backtracking where you naturally split a problem into smaller copies.

Under the hood: what really happens inside Python

  • Each call creates a frame object holding local variables, the instruction pointer and a link to the caller. The call stack is a list of these frames. When the base case returns, Python pops the frame and gives the value to the caller, which continues from where it paused.
  • Python does NOT optimise tail calls, so even a tail-recursive function uses one frame per call. sys.getrecursionlimit() shows the limit (usually 1000) and sys.setrecursionlimit() changes it, but a very large value can crash the process with a real stack overflow.
  • Default arguments are evaluated once, when the function is defined, not on each call. A mutable default (like []) persists between calls, which is both a classic bug and, when used deliberately, a cheap memo cache.

Recursion vs loopLoops use O(1) stack and are faster in Python. Recursion expresses tree/graph/divide-and-conquer logic more clearly. Use recursion when the structure is self-similar and depth is small (tree height, n up to ~1000).
Recursion vs explicit stackAn explicit stack avoids the recursion limit and gives you full control (iterative DFS), at the cost of more code.
When NOT to use recursionSimple counting, summing a list, or anything that goes 10^5 levels deep. Also avoid plain recursion when subproblems repeat (naive Fibonacci) unless you add memoisation.

Python tips and shortcuts for this topic

  • Default arguments: def power(x, n=2). Call power(5) or power(5, 3).
  • Return several values at once with a tuple: return total, count. Unpack with total, count = f(...).
  • from functools import lru_cache then @lru_cache(maxsize=None) above a recursive function gives automatic memoisation.
  • Nested functions can read outer variables; use nonlocal to change them.

def factorial(n):
    if n <= 1:                 # base case: stop
        return 1
    return n * factorial(n - 1)   # recursive case: smaller problem

Time and space complexity

Time O(n): n calls. Space O(n): n frames on the call stack.

Common mistakes and edge cases

  • Missing or wrong base case (infinite recursion).
  • The recursive call does not move toward the base case.
  • Forgetting to return the recursive result.

How to recognise problems that use this technique

  • Phrases like "defined in terms of a smaller version of itself" suggest recursion.
  • Write the base case first, then trust the recursive call to solve the smaller problem.

Why? and Why not?

Why does recursion need a base case?

Without a stopping point the function keeps calling itself until Python raises RecursionError. The base case is the smallest problem you can answer directly.

Why not always use recursion since it looks shorter?

Each call uses a stack frame and Python limits depth to about 1000. Loops are faster and use constant memory for simple repetition.

Why use functions at all?

To name a piece of logic, reuse it, test it alone and keep each part small enough to understand.

Why does a function return None if you forget return?

Python functions always return something; with no return statement the result is None. This is why print(f()) sometimes shows None.

Why use default arguments carefully?

Defaults are created once. A mutable default like [] is shared between calls, so values from earlier calls leak into later ones.

How this gets asked

What is the role of the base case?

Interview questions: Programming & Problem-Solving Foundations

54 questions: try to answer aloud in under a minute, then reveal. All questions from every module are also in the interview bank.

Basic Conceptual What is the difference between a list and a tuple in Python?

A list is mutable (you can add, remove or change items). A tuple is immutable (fixed once created). Tuples are slightly faster, use less memory, and can be used as dictionary keys because they are hashable. Lists cannot be dictionary keys.

Basic Conceptual What does 'is' do and how is it different from '=='?

'==' checks whether two values are EQUAL. 'is' checks whether two names point to the very SAME object in memory. [1,2] == [1,2] is True, but [1,2] is [1,2] is False because they are two separate lists. Use 'is' mostly for None: if x is None.

Basic Conceptual Why is b = a dangerous for lists?

It does not copy the list. Both a and b point to the same list, so changing one changes the other. Make a copy with b = a[:] or b = a.copy(). For lists inside lists use copy.deepcopy(a).

Basic Conceptual What is the output of print(7 // 2, -7 // 2, 7 % 3, -7 % 3)?

3 -4 1 2. Floor division rounds DOWN toward minus infinity, so -7 // 2 is -4. The remainder always has the same sign as the divisor, so -7 % 3 is 2. This differs from C and Java, so be careful.

Basic Conceptual How do you read n integers from one line in Python?
nums = list(map(int, input().split()))

input() reads the line as text, split() cuts it into pieces, map(int, ...) converts every piece to an integer, and list() collects them.

Basic Conceptual What is a mutable default argument bug?
def add(x, items=[]):
    items.append(x)
    return items

The default list is created ONCE when the function is defined, so every call that uses the default shares the same list. The fix is items=None and then 'if items is None: items = []' inside the function.

Basic Conceptual Why does Python have no integer overflow?

Python ints are arbitrary precision. When a value exceeds the machine word size, Python stores it as multiple digits. The cost is speed on enormous numbers, but correctness is automatic. This is why problems asking for answers modulo 10^9+7 are still required: the judge wants a small number.

Basic Behavioral Tell me about a bug you found because of an input/format mistake and how you prevented it later.

A good answer is a specific story: I misread that the first line was the count, so my list was off by one and the hidden tests failed. I now (1) rewrite the input format in a comment, (2) test the sample in the exact judge format, and (3) always test one empty or minimal case before submitting.

Basic Conceptual How do you approach a coding problem you have never seen?

I go in steps: (1) restate the problem in my own words, (2) note input, output and constraints, (3) work the sample by hand, (4) list edge cases, (5) think of a simple brute-force way and its time cost, (6) improve it with a suitable tool (hash map, sorting, two pointers...), (7) code it, and (8) dry-run it on the sample and an edge case.

Basic Conceptual What do you do if you are stuck?

I try a smaller input by hand and look for a pattern, ask what work is being repeated, and think about which data structure fits. If I still have no idea, I write the brute force first - a correct slow solution is better than nothing and often shows where to optimise.

Basic Conceptual Why do constraints matter?

They tell you the speed your solution needs. About 10^7 to 10^8 simple operations fit in one second. If n = 10^5 then O(n^2) (10^10 steps) is too slow but O(n log n) is fine.

Basic Conceptual What are edge cases? Give examples.

Edge cases are unusual inputs that often break code: an empty list, one element, all elements equal, negative numbers, zero, duplicate values, the largest allowed input, and a target that is missing.

Basic Conceptual Why should you ask clarifying questions in an interview?

Problems are deliberately underspecified. Asking about input size, duplicates, sorted or not, negative numbers and expected output on invalid input shows maturity, and the answers often reveal the intended algorithm.

Basic Behavioral Describe how you handle a task when requirements are unclear.

I restate the requirement in my own words, list assumptions and open questions, confirm them with the owner, and start with the smallest useful version while keeping the unclear parts easy to change.

Basic Conceptual What is recursion and what must every recursive function have?

Recursion is a function calling itself on a smaller problem. It must have a base case (stops the calls) and a recursive step that gets closer to the base case. Without them it never ends and Python raises RecursionError.

Basic Conceptual What is the time and space complexity of recursive factorial?

Time O(n) because there are n calls. Space O(n) because n frames sit on the call stack at the deepest point. An iterative loop uses O(1) space.

Basic Conceptual How do you avoid RecursionError for deep recursion?

Convert the recursion to a loop with your own stack, or raise the limit with sys.setrecursionlimit (use with care), or restructure the algorithm (for example iterative DFS).

Basic Conceptual What is the difference between a parameter and an argument?

A parameter is the variable name in the function definition. An argument is the real value you pass when calling. In def f(x): x is a parameter; in f(5) the 5 is an argument.

Basic Conceptual What is the difference between direct and indirect recursion?

Direct: f calls f. Indirect: f calls g and g calls f. Both need base cases to stop.

Medium Tricky output What does print(0.1 + 0.2 == 0.3) show and why?

False. Floats are stored in binary, and 0.1 and 0.2 cannot be represented exactly, so the sum is 0.30000000000000004. Compare floats with a tolerance: abs(a - b) < 1e-9, or use math.isclose(a, b).

Medium Coding Write a function that returns the sum of the digits of a number without converting to a string.
def digit_sum(n):
    total = 0
    while n > 0:
        total += n % 10
        n //= 10
    return total

n % 10 takes the last digit and n // 10 removes it.

Medium Real-world Why do online judges give wrong answer for an extra space at the end of a line?

Many judges compare output text exactly (some trim trailing whitespace, but you cannot rely on it). The safe habit: print exactly what the format says, use print(*items) for space-separated lines and avoid prompts like 'Enter n:'.

Medium Why / Why not Why does Python not make you declare variable types?

Python decides the type from the value at run time (dynamic typing). It makes short programs easy to write. The price is that mistakes (like adding a number to text) appear only when that line runs.

Medium Why / Why not Why not use input() for very large input?

Each input() call has overhead. For 10^5 lines the calls add up. sys.stdin.read().split() reads everything at once and is much faster.

Medium Why / Why not Why convert with int() instead of just using the text?

Text '5' + '3' joins to '53'. Only numbers can be added. The conversion tells Python what kind of data you mean.

Medium Why / Why not Why use a for loop instead of a while loop when counting?

A for loop updates the counter for you, so you cannot forget it and create an endless loop. while is for 'repeat until something changes'.

Medium Why / Why not Why not name variables a, b, c?

Short names hide meaning. total_marks tells the reader (and you, an hour later) what the value is. Good names are a cheap form of documentation.

Medium Why / Why not Why should you not print prompts like 'Enter a number' in a coding round?

The judge compares your output exactly with the expected output. Extra text makes every test fail even if your logic is correct.

Medium Tricky output What does print(type(5 / 2), type(5 // 2)) print?

<class 'float'> <class 'int'>. / always returns a float, // returns an int when both operands are ints.

n = int(input())
print(n * (n + 1) // 2)

Using the formula avoids a loop; // keeps the result an integer.

Medium Real-world How do constraints guide your choice of algorithm?

n up to about 20 permits exponential search; up to about 500 allows O(n^3); up to a few thousand O(n^2); 10^5 requires O(n log n) or O(n); 10^7 or more needs near O(n) or O(log n) per query.

Medium Tricky output What is wrong with testing only the sample input?

Samples are usually the easy case. Hidden tests cover boundaries, large inputs, and special values. A solution can pass the sample and fail most tests, so always add your own edge cases.

Medium Why / Why not Why write down edge cases before coding?

Because after coding you will unconsciously test only inputs your code already handles. Listing them first makes you design for them.

Medium Why / Why not Why not start coding as soon as you see a familiar problem?

Similar-looking problems often differ in one detail (distinct vs duplicates, sorted vs unsorted, indices vs values). Coding the wrong variant wastes the whole attempt.

Medium Why / Why not Why do constraints decide the algorithm?

They tell you how many steps you can afford. n = 10^5 allows about n log n steps, so an O(n^2) idea is rejected before you write it.

Medium Why / Why not Why dry-run instead of just running the code?

Running tells you the result is wrong; dry running shows exactly which line first goes wrong. It also works when no judge or tests are available.

Medium Why / Why not Why break a problem into steps?

People hold only a few things in mind at once. Small steps fit in memory, are easy to test separately and map to functions.

Medium Why / Why not Why not trust the sample test alone?

Samples are usually the easy case. Hidden tests include empty input, single values, duplicates, negatives and maximum size.

Medium Real-world Give an example where a misread requirement caused a bug.

A statement said 'positive integers' but the data contained 0, so a division failed. Re-reading constraints and testing zero would have caught it.

Medium Tricky output What does this print?
def f(n):
    if n == 0:
        return
    print(n)
    f(n - 1)
    print(n)
f(3)

3 2 1 1 2 3 (each on its own line). Going down it prints 3, 2, 1; after the base case returns, each pending call prints its own n on the way back up: 1, 2, 3.

Medium Coding Write a recursive function to reverse a string.
def rev(s):
    if len(s) <= 1:
        return s
    return rev(s[1:]) + s[0]

Base case: 0 or 1 characters. Recursive step: reverse the rest and put the first character at the end. O(n^2) because slicing copies; an index-based version is O(n).
