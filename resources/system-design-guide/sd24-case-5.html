Case 1: Nearby search (Yelp / proximity service)

Requirements

  • Find businesses within a radius of a location, filtered by category and sorted by distance or rating.
  • Owners add, update or remove businesses (changes may appear within minutes).
  • 100M businesses, 100M daily users, 5 searches each: about 500M reads/day, mostly reads.

Estimates

Reads: 500M / 86,400 = 5,800 QPS average, about 17,000 peak. Business data: 100M x 1 KB = 100 GB (fits on one big machine; shard for throughput and availability, not capacity). Location index: 100M x 16 bytes = 1.6 GB, fits in memory.

API

GET /v1/places?lat=..&lng=..&radius=5000&category=cafe&cursor=.., GET /v1/places/{id}, POST/PUT/DELETE /v1/places (owner).

Geospatial indexing

You cannot scan 100M rows by distance. Index space so "nearby" becomes a key lookup.

ApproachIdeaNotes
Two-dimensional SQL indexlat BETWEEN, lng BETWEENPoor: intersects two big ranges
GeohashInterleave latitude and longitude bits into a base32 string; longer prefix = smaller cellPrefix lookups in any key-value or B-tree index
QuadtreeRecursively split a region into 4 until a cell holds at most N placesAdapts to density; held in memory
S2 / H3Hierarchical cells on a sphereUniform cells, used by Google and Uber

Geohash gotchas: cells at the same prefix are near, but two close points can sit in different cells across a boundary, so query the target cell and its 8 neighbours, then compute exact distance and filter. Choose the precision from the radius: 5 characters is a cell of about 5 km, 6 about 1.2 km x 0.6 km, 7 about 150 m.

import math
BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz"
def encode(lat, lng, precision=7):
    lat_r, lng_r, bits, even, out, ch, n = [-90.0, 90.0], [-180.0, 180.0], [16, 8, 4, 2, 1], True, "", 0, 0
    while len(out) < precision:
        rng, val = (lng_r, lng) if even else (lat_r, lat)
        mid = (rng[0] + rng[1]) / 2
        if val >= mid: ch |= bits[n]; rng[0] = mid
        else: rng[1] = mid
        even = not even
        if n < 4: n += 1
        else: out += BASE32[ch]; ch, n = 0, 0
    return out
def haversine(a, b):
    R = 6371000
    p1, p2 = math.radians(a[0]), math.radians(b[0])
    dl, dp = math.radians(b[1] - a[1]), p2 - p1
    h = math.sin(dp / 2) ** 2 + math.cos(p1) * math.cos(p2) * math.sin(dl / 2) ** 2
    return 2 * R * math.asin(math.sqrt(h))
print("geohash of (57.64911, 10.40744):", encode(57.64911, 10.40744, 11), "(the standard reference is u4pruydqqvj)")
here = (37.7749, -122.4194)                       # San Francisco
print("a 5 m move keeps the 6-char cell:", encode(*here, 6) == encode(37.77494, -122.41940, 6))
for p in (4, 5, 6, 7):
    print(f"precision {p}: {encode(*here, p)}")
print("distance to Oakland:", round(haversine(here, (37.8044, -122.2712)) / 1000, 1), "km")

Output

geohash of (57.64911, 10.40744): u4pruydqqvj (the standard reference is u4pruydqqvj)
a 5 m move keeps the 6-char cell: True
precision 4: 9q8y
precision 5: 9q8yy
precision 6: 9q8yyk
precision 7: 9q8yyk8
distance to Oakland: 13.4 km

Architecture

  • Search service: holds a geohash (or quadtree) index; computes the 9 cells, merges candidates, filters by distance and category, ranks.
  • Database: places table with replicas; shard by place id (or by region). Writes are rare, so refresh the index every few minutes or on change events.
  • Rebuild strategy: quadtree in memory rebuilt on restart (about a minute for 100M entries) with a warm standby; or geohash rows in Redis (GEOADD/GEOSEARCH) or PostGIS.
  • Dense areas: cap results per cell and expand search only when too few results.
Deep dive: density

A fixed geohash precision gives 100 places in a city centre cell and 0 in a desert cell. Quadtrees split by count, so dense areas get small cells; for geohash, start at the target precision and shorten the prefix until enough results are found.

How this gets asked

Why query a geohash cell and its 8 neighbours?

  • To use more memory No.
  • Nearby points can sit on opposite sides of a cell boundary Correct.
  • Geohash is random No.
  • To reduce precision No.

Then filter candidates by exact distance.

A quadtree differs from a fixed-precision geohash because it:

  • Uses less data No.
  • Subdivides cells by density, so crowded areas get smaller cells Correct.
  • Needs no memory No.
  • Is a database No.

Adaptive resolution handles uneven density.

Self-check

Why does geohash need neighbour cells?

A boundary can split two close points into different cells, so search the cell and its 8 neighbours then filter by distance.

Case 2: Maps and routing

Requirements

Map display, search, and route computation with live traffic and ETA. Billions of map tile requests per day; hundreds of millions of route requests.

Key ideas

  • Map tiles: the world is pre-rendered (or vector-encoded) into tiles per zoom level (z/x/y). Serve them as static files from a CDN; clients fetch only visible tiles. Vector tiles are smaller and styleable.
  • Road network = weighted graph: intersections are nodes, road segments are edges with weights of travel time. Plain Dijkstra on a continent-size graph (tens of millions of nodes) is too slow per request.
  • Speed-ups: A* with a distance heuristic, bidirectional search, and above all hierarchical preprocessing (contraction hierarchies or hub labels) that precompute shortcuts so a query touches thousands of nodes instead of millions. Partition the graph into regions, with precomputed cross-region summaries.
  • Traffic: location pings from phones are map-matched to road segments and aggregated in a stream processor into current speeds; edge weights are updated every minute or so. ETA = sum of predicted segment times, using historical patterns by time of day plus live data and ML.
  • Re-routing: when a deviation or incident occurs, recompute from the current position.
import heapq
graph = {                     # node -> [(neighbour, minutes)]
    "A": [("B", 4), ("C", 2)], "B": [("D", 5)], "C": [("B", 1), ("D", 8), ("E", 10)],
    "D": [("F", 2)], "E": [("F", 3)], "F": [],
}
def dijkstra(src, dst, g):
    dist, prev, heap, pops = {src: 0}, {}, [(0, src)], 0
    while heap:
        d, u = heapq.heappop(heap); pops += 1
        if d > dist.get(u, 1e9): continue
        if u == dst: break
        for v, w in g[u]:
            if d + w < dist.get(v, 1e9):
                dist[v], prev[v] = d + w, u
                heapq.heappush(heap, (d + w, v))
    path = [dst]
    while path[-1] != src: path.append(prev[path[-1]])
    return dist[dst], path[::-1], pops
print("normal traffic:", dijkstra("A", "F", graph))
graph["C"] = [("B", 1), ("D", 8), ("E", 10)]
graph["B"] = [("D", 25)]                                           # an accident slows B->D, weights update
print("after an incident on B->D:", dijkstra("A", "F", graph))

Output

normal traffic: (10, ['A', 'C', 'B', 'D', 'F'], 7)
after an incident on B->D: (12, ['A', 'C', 'D', 'F'], 7)

Trade-offs

Exactness versus preprocessing time (a changed edge weight invalidates shortcuts unless the preprocessing is traffic-aware, so many systems use a static hierarchy plus a dynamic penalty layer); storage of tiles (petabytes, tiered storage); freshness of map data.

How this gets asked

How are map tiles best delivered?

  • Rendered per request Too slow.
  • Pre-rendered per zoom level and served from a CDN Correct.
  • Streamed over WebSockets No.
  • Stored on clients No.

Tiles are static, cacheable files.

Why is plain Dijkstra too slow for continental routing at scale?

  • It is incorrect It is correct.
  • It explores millions of nodes per query; hierarchical preprocessing cuts that to thousands Correct.
  • It cannot handle weights It can.
  • It needs negative edges No.

Contraction hierarchies precompute shortcuts.

Self-check

Name two routing speed-ups.

A* with a heuristic or bidirectional search, and contraction hierarchies/hub labels from preprocessing.

Case 3: E-commerce inventory and checkout

Requirements

Browse, cart, checkout, payment, order tracking. Never oversell stock, never double charge, survive retries. 10M orders/day with a Black Friday peak 10x.

Data model

products(id, price), inventory(sku, available, reserved), carts(user, items), orders(id, user, status, total), order_items, payments(id, order_id, idempotency_key, status). Order states: created, payment_pending, paid, fulfilling, shipped, delivered, cancelled, refunded.

Checkout flow

  1. Cart in a fast store (Redis or the database); prices are re-validated at checkout.
  2. Reserve inventory with a TTL (for example 10 minutes) so a held item is not sold twice and is released if payment fails.
  3. Create the order (pending) and call the payment provider with an idempotency key.
  4. On success mark paid, convert reservation to a sale, emit OrderPaid (outbox, SD19); fulfilment, email and analytics consume it.
  5. On failure or timeout, a saga compensates: release stock, cancel the order.

Preventing overselling

The correct primitive is an atomic conditional update, not read-then-write:

import sqlite3
db = sqlite3.connect(":memory:", isolation_level=None)
db.execute("CREATE TABLE inventory(sku TEXT PRIMARY KEY, available INT)")
db.execute("INSERT INTO inventory VALUES('phone', 1)")
# Racy read-modify-write, with the two buyers' steps interleaved exactly as concurrent requests can interleave
a_read = db.execute("SELECT available FROM inventory").fetchone()[0]       # buyer A reads 1
b_read = db.execute("SELECT available FROM inventory").fetchone()[0]       # buyer B reads 1
db.execute("UPDATE inventory SET available = ?", (a_read - 1,))            # A writes 0 and succeeds
db.execute("UPDATE inventory SET available = ?", (b_read - 1,))            # B also writes 0 and succeeds
print("read-then-write: both buyers think they bought the last phone (A saw", a_read, ", B saw", b_read, ")")
db.execute("UPDATE inventory SET available = 1")
wins = []
for buyer in ("A", "B"):                                                   # same two buyers, atomic conditional update
    cur = db.execute("UPDATE inventory SET available = available - 1 WHERE sku = 'phone' AND available > 0")
    wins.append((buyer, cur.rowcount == 1))
print("atomic conditional update:", wins, "| stock left:", db.execute("SELECT available FROM inventory").fetchone()[0])

Output

read-then-write: both buyers think they bought the last phone (A saw 1 , B saw 1 )
atomic conditional update: [('A', True), ('B', False)] | stock left: 0

The UPDATE ... WHERE available > 0 runs inside the database as one atomic statement; check rowcount to see whether you won. Alternatives: SELECT ... FOR UPDATE row locks, optimistic version columns, or Redis DECR with a Lua script.

Other deep dives

  • Idempotent payments: store an idempotency key per order attempt; a timeout means "unknown", so reconcile by querying the provider rather than retrying blindly.
  • Cart consistency: carts tolerate staleness (price changes caught at checkout).
  • Search and catalogue: read-heavy, served from Elasticsearch plus cache (SD12); keep the system of record separate.
  • Scaling: shard orders by user id; keep inventory per SKU on a strongly consistent store; use queues for fulfilment.

How this gets asked

  • Use an atomic conditional update such as UPDATE ... SET available = available - 1 WHERE available > 0 Correct.
  • Trust the cart No.
  • Cache the count No.

Check rowcount to see if the decrement succeeded.

After a payment timeout, what should you do?

  • Charge again Might double charge.
  • Treat the outcome as unknown and reconcile with the provider using the idempotency key Correct.
  • Assume failure Might lose a paid order.
  • Delete the order No.

Idempotency keys make retries safe.

Self-check

What is a reservation TTL for?

To hold stock briefly during payment and release it automatically if the user abandons or payment fails.

Case 4: Flash sale

The problem

10,000 units of a product go on sale at noon; 5 million users arrive within a second. The danger is a thundering herd that melts the database, plus overselling and bots.

Design

  1. Absorb at the edge: static page on a CDN; a waiting room / virtual queue admits users at a controlled rate; CAPTCHA and per-account limits filter bots; rate limit per IP and user.
  2. Pre-warm: load the stock count into Redis before the sale.
  3. Atomic decrement in Redis (Lua script or DECR): if the result is below zero, reject immediately. Only users who won a unit proceed. This turns 5M requests into at most 10,000 orders.
  4. Queue the winners: write a short-lived reservation, then process orders asynchronously through a queue at the database's pace; payment must happen within a time window or the unit returns to stock.
  5. Reconcile Redis against the database after the sale; the database remains the system of record.
from collections import deque
stock, queue, rejected = 10, deque(), 0
requests = 40                                       # arrive in a burst
for user in range(requests):
    if stock > 0:                                   # in production: one atomic Redis DECR / Lua script
        stock -= 1
        queue.append(f"user{user}")                 # winners get a reservation and go on to pay
    else:
        rejected += 1                               # everyone else is turned away cheaply at the edge
print(f"{requests} requests -> {len(queue)} reservations queued, {rejected} rejected without touching the database, stock left {stock}")

Output

40 requests -> 10 reservations queued, 30 rejected without touching the database, stock left 0

Trade-offs: fairness (first come versus lottery), perceived latency (queue position display), and graceful degradation (static "sold out" page when stock hits zero).

How this gets asked

How does a flash-sale design protect the database?

  • Bigger database Costly and insufficient.
  • An edge waiting room, an atomic Redis decrement, and asynchronous order processing for the few winners Correct.
  • Disabling checks No.
  • Random sleeps No.

Reject the losers cheaply before they reach the database.

Self-check

What are the layers of flash-sale defence?

CDN and waiting room, rate limiting and bot checks, atomic stock decrement in Redis, queued order processing.

Case 5: Hotel reservation system

Requirements

Search hotels by city and dates, view availability, book a room type for a date range, no double booking, cancellations, payments. Fewer writes than e-commerce (about 1M bookings/day), high search volume.

Data model

hotels, room_types(hotel, type, total_rooms), room_inventory(hotel, room_type, date, total, reserved) per night, reservations(id, user, hotel, room_type, start, end, status). A booking for nights [start, end) must decrement availability for every night atomically.

import sqlite3
db = sqlite3.connect(":memory:", isolation_level=None)
db.executescript("""CREATE TABLE inv(room_type TEXT, night INT, total INT, reserved INT, PRIMARY KEY(room_type, night));
                    CREATE TABLE res(id INTEGER PRIMARY KEY AUTOINCREMENT, room_type TEXT, start INT, end INT);""")
for n in range(1, 8): db.execute("INSERT INTO inv VALUES('double', ?, 2, 0)", (n,))
def book(room_type, start, end):
    db.execute("BEGIN IMMEDIATE")
    nights = (end - start)
    ok = db.execute("SELECT COUNT(*) FROM inv WHERE room_type=? AND night>=? AND night<? AND reserved < total", (room_type, start, end)).fetchone()[0] == nights
    if not ok:
        db.execute("ROLLBACK"); return False
    db.execute("UPDATE inv SET reserved = reserved + 1 WHERE room_type=? AND night>=? AND night<?", (room_type, start, end))
    db.execute("INSERT INTO res(room_type, start, end) VALUES(?,?,?)", (room_type, start, end))
    db.execute("COMMIT"); return True
print([book("double", 2, 5), book("double", 3, 6), book("double", 4, 7), book("double", 1, 3), book("double", 5, 7)])
print("reserved per night:", db.execute("SELECT night, reserved FROM inv ORDER BY night").fetchall())

Output

[True, True, False, True, True]
reserved per night: [(1, 1), (2, 2), (3, 2), (4, 2), (5, 2), (6, 1), (7, 0)]

Deep dives

  • Hold then confirm: lock the room for 10 to 15 minutes during payment (a reservation with an expiry), released by a TTL job.
  • Overbooking: hotels deliberately sell a few more rooms than exist since cancellations are common; model as total greater than physical rooms.
  • Concurrency: row locks or optimistic versions on inventory rows; partition by hotel so contention stays local.
  • Search: availability is a join of dates and inventory; precompute per hotel and date in a search index and verify against the database at booking time (staleness is acceptable in search, not in booking).
  • Idempotency: a client-supplied reservation id makes retries safe.
Key idea

Turn space into keys (geohash, tiles), turn contention into a single atomic conditional update, protect the database behind queues and edge filters, and separate the fast, stale-tolerant search path from the strictly consistent booking path.

How this gets asked

Why is hotel inventory modelled per night?

  • To store less data No.
  • A stay spans multiple nights and each night's availability must decrement atomically Correct.
  • It simplifies pricing only No.
  • Dates cannot be indexed otherwise They can.

Booking a range is all-or-nothing across its nights.

Self-check

How can a hotel sell more rooms than it has?

Deliberate overbooking, since cancellations and no-shows are common; modelled by allowing reserved to exceed physical rooms up to a limit.

Interview questions: Case studies 5

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Why is a geohash useful for nearby search?

It turns two-dimensional location into a string whose shared prefix means nearness, so proximity becomes a prefix lookup in a standard index.

Medium Why search neighbouring cells as well as the target cell?

Two close points can fall on opposite sides of a cell boundary, so query the cell and its eight neighbours, then filter by exact distance.

Medium Quadtree versus geohash?

A quadtree splits cells by density so crowded areas get finer cells; geohash cells are uniform per precision. Quadtrees live in memory; geohash works in any key-value store.

Medium How are map tiles served?

Pre-rendered or vector tiles per zoom level and x/y coordinates, stored as static files and served from a CDN.

Medium How do you prevent overselling in checkout?

Atomic conditional updates (UPDATE ... WHERE available > 0 and check rows affected), row locks or compare-and-set, with reservations that expire.

Medium How do you make payment calls safe to retry?

Send an idempotency key per payment attempt; on timeout reconcile with the provider before retrying, since the true outcome is unknown.

Medium Why is hotel inventory modelled per night?

A stay spans nights; the booking must decrement availability for every night atomically, which a per-night inventory row allows with a transaction.

Medium What is overbooking and why do hotels use it?

Selling more than capacity, expecting cancellations and no-shows, with a policy for handling the rare overflow.

Advanced How do routing services avoid running Dijkstra on the whole road graph?

Preprocessing such as contraction hierarchies or hub labels, A* and bidirectional search, and regional partitioning, with live traffic as updated edge weights.

Advanced Design the checkout flow as a saga.

Reserve inventory, create order, charge payment, confirm; on failure, compensate by releasing stock and cancelling or refunding, each step idempotent and driven by events.

Advanced How do you handle a flash sale with 5 million users and 10,000 items?

CDN and waiting room, bot and rate limits, atomic Redis stock decrement so only winners continue, queued order processing, expiry of unpaid reservations, and reconciliation with the database.

Advanced How do you separate search from booking consistency in a hotel system?

Search uses a denormalised, slightly stale index; booking re-checks availability in the strongly consistent database under a transaction.

Advanced How would you shard a proximity service?

By region or geohash prefix so queries hit one or a few shards, balancing dense areas by splitting cells; replicate for availability.

Advanced How do you compute ETA?

Sum predicted traversal times of road segments using historical profiles and live speeds from map-matched location pings, refined by ML and updated while driving.
