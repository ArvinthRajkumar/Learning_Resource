Part SD34

System design explained simply: analogies, misconceptions and how to say it in an interview

If you cannot explain an idea simply, you probably do not own it yet. This part restates the guide's big ideas with analogies a non-engineer would follow, points out the mistakes beginners make, and gives you a 30-second spoken answer to practise.

BasicMedium~3 hours

How to use this page

For each idea read the analogy, check the misconception, then cover the page and say the 30-second answer aloud. A good interview answer has three beats: what it is, why it exists (the problem), the trade-off.

Scaling and load

Vertical versus horizontal scaling

Analogy: a restaurant that is too busy. Vertical: replace the cook with a faster, stronger cook (limited, and expensive). Horizontal: hire more cooks and add more stoves (cheaper per unit, but now you need someone to hand out orders and keep the menu consistent). Misconception: "horizontal is always better". It adds coordination problems (load balancing, shared state, distributed failures). A single big machine is simpler and often enough. 30-second answer: "Vertical scaling makes one machine bigger; it is simple but capped and a single point of failure. Horizontal scaling adds machines behind a load balancer, which gives near-unlimited capacity and redundancy, but requires stateless services or partitioned state."

Load balancer

Analogy: the host at a restaurant who seats each new party at a table with free space, and stops seating people at a table where the waiter has vanished (health check). Misconception: "the load balancer is a single point of failure only if it breaks"; it is, so run at least two (active/standby or anycast). Answer: "It spreads requests over healthy servers using a policy such as round robin or least connections, removes failed servers using health checks, and can terminate TLS."

Stateless services

Analogy: a bank teller who does not remember you; you bring your account number and the bank's computers know the rest. Any teller can serve you. Why it matters: if servers keep user state in memory, you must always send the same user to the same server (sticky sessions), and a crash loses the state. Keep state in a database or cache so any server can handle any request.

Throughput versus latency

Analogy: a motorway. Latency is how long one car takes from A to B; throughput is how many cars pass per hour. Adding lanes raises throughput but does not make any car faster. Misconception: optimising average latency. Users feel the slowest requests, so watch p99.

How this gets asked

What is the key requirement to scale a service horizontally behind a load balancer?

  • Bigger servers That is vertical.
  • Keeping per-user state out of server memory (stateless or externalised state) Correct.
  • A faster network only No.
  • Using UDP No.

Any server must be able to handle any request.

Data and storage

Index

Analogy: the index at the back of a textbook: instead of reading every page to find "photosynthesis", look it up and jump to the page. It costs space and must be updated whenever the book changes. Misconception: "add an index to every column". Each index slows writes and uses memory; add them for real queries.

Replication

Analogy: keeping photocopies of an important document in different buildings. If one burns, you still have a copy; but when you edit the original you must update the copies, and for a moment they differ (replication lag). Answer: "Copies of data on several nodes for availability and read scaling. The leader takes writes and followers copy them; the price is lag and the question of what to do when the leader fails."

Sharding (partitioning)

Analogy: a library that splits books across rooms by the first letter of the author's name. Each room is smaller and quicker to search, but finding books across several rooms (joins, ranges) is harder, and the "S" room might be much busier than the "X" room (hot shard). Misconception: sharding and replication are the same. Replication copies the same data; sharding splits different data. Real systems do both.

import hashlib
def shard_for(key, n): return int(hashlib.md5(key.encode()).hexdigest(), 16) % n
keys = [f"user{i}" for i in range(10_000)]
before = {k: shard_for(k, 4) for k in keys}
after = {k: shard_for(k, 5) for k in keys}
moved = sum(before[k] != after[k] for k in keys)
print(f"mod-N hashing: adding a 5th shard moves {moved / len(keys):.0%} of all keys (that is why consistent hashing exists)")

Output

mod-N hashing: adding a 5th shard moves 80% of all keys (that is why consistent hashing exists)

Consistent hashing

Analogy: guests sit around a circular table; each person serves the dishes in front of them up to the next person. When a new person sits down, they take over only the dishes between them and their neighbour; nobody else's food moves. Answer: "Place nodes and keys on a hash ring; each key belongs to the next node clockwise. Adding or removing a node moves only about 1/N of the keys, unlike modulo hashing which reshuffles almost everything. Virtual nodes even out the load."

import bisect, hashlib
h = lambda s: int(hashlib.md5(s.encode()).hexdigest(), 16)
def build_ring(nodes, vnodes=100): return sorted((h(f"{n}#{v}"), n) for n in nodes for v in range(vnodes))
def owner(ring, key):
    hashes = [x[0] for x in ring]
    return ring[bisect.bisect(hashes, h(key)) % len(ring)][1]
keys = [f"user{i}" for i in range(10_000)]
r4, r5 = build_ring(["A", "B", "C", "D"]), build_ring(["A", "B", "C", "D", "E"])
moved = sum(owner(r4, k) != owner(r5, k) for k in keys)
print(f"consistent hashing: adding a 5th node moves {moved / len(keys):.0%} of keys (ideal is 20%)")

Output

consistent hashing: adding a 5th node moves 19% of keys (ideal is 20%)

Caching

Analogy: keeping the books you read most on your desk instead of walking to the library each time. Fast, small, and sometimes out of date. Two hard things: deciding what to evict when the desk is full, and deciding when a copy is stale. Misconception: "caching always helps". It helps when the same data is read often and can be slightly stale; it adds bugs when data changes frequently or must be exactly right.

SQL versus NoSQL

Analogy: SQL is a well-organised filing cabinet with strict forms, cross-references and a clerk who guarantees consistency. NoSQL stores are specialised: a coat-check ticket system (key-value), a folder per customer (document), a conveyor belt for huge volumes (wide-column). Misconception: "NoSQL scales, SQL does not". Both can scale; they trade features differently. Start with a relational database and move parts out when a measured need appears.

How this gets asked

What is the difference between sharding and replication?

  • None No.
  • Sharding splits different data across nodes; replication copies the same data to several nodes Correct.
  • Sharding is for reads only No.
  • Replication splits data No.

Real systems combine both.

Why does modulo hashing cause trouble when a node is added?

  • It is slow No.
  • Nearly all keys map to a different node, causing a mass cache miss or data move Correct.
  • It uses too much memory No.
  • It cannot hash strings No.

Consistent hashing moves only about 1/N of the keys.

Self-check

Why use virtual nodes in consistent hashing?

They spread each physical node across many ring positions, evening out the load and the data moved on changes.

Consistency and reliability

CAP theorem

Analogy: two bank branches whose phone line breaks. A customer wants to withdraw. The branch can (a) refuse until it can talk to the other branch (consistent, but unavailable), or (b) allow it and reconcile later (available, but possibly overdrawn). Misconception: "pick any two of three". Partitions will happen; the real choice is between consistency and availability during one.

Eventual consistency

Analogy: gossip in an office. Tell one person a secret and soon everyone knows, but for a short while some people have not heard it yet. Good for: likes, view counts, feeds. Bad for: money, stock counts, unique usernames.

Idempotency

Analogy: pressing the lift button repeatedly. The lift still comes once. Pressing "pay" twice should not charge twice; that is why payments carry an idempotency key. Answer: "An operation is idempotent when repeating it has the same effect as doing it once. It lets clients retry safely after timeouts, which are unavoidable in distributed systems."

Retries, backoff and jitter

Analogy: a crowd all calling a restaurant that is full, redialling every second, keeps the line jammed. If everyone waits longer after each failed call, and waits a random amount, the line clears.

Circuit breaker

Analogy: the fuse in your house. When a dependency keeps failing, stop calling it for a while (open the circuit) so you fail fast and give it time to recover, then test with a few calls (half-open).

import random
random.seed(2)
def storm(clients, backoff, jitter):
    load = {}
    for _ in range(clients):
        t = backoff * (random.random() if jitter else 1)
        load[round(t, 1)] = load.get(round(t, 1), 0) + 1
    return max(load.values())
print("1000 clients all retry after 2 s:", storm(1000, 2, False), "requests land in the same instant")
print("with random jitter over 2 s:      ", storm(1000, 2, True), "requests in the busiest 0.1 s slot")

Output

1000 clients all retry after 2 s: 1000 requests land in the same instant
with random jitter over 2 s:       63 requests in the busiest 0.1 s slot

Replication lag and read-your-writes

Analogy: you post a comment, refresh, and it is gone, because your refresh hit a follower that has not received it yet. Fix: for a short time after a write, read from the leader (or from where you wrote).

Consensus (Raft, Paxos)

Analogy: a committee that needs a majority vote before any decision is final, so two rival committees can never both decide. If the chair disappears, members elect a new one. Answer: "Nodes agree on a sequence of decisions using majority votes, so that any two majorities overlap and conflicting decisions are impossible. It is used for leader election, locks and replicated configuration, not for bulk data."

How this gets asked

Which fits 'eventual consistency' best?

  • A bank balance Needs strong consistency.
  • A like counter on a social post Correct.
  • Seat reservations Needs strong consistency.
  • Passwords No.

Brief staleness is harmless there.

Why add jitter to retries?

  • To make clients slower No.
  • So many clients do not retry in the same instant and overload the recovering service Correct.
  • To avoid TLS No.
  • To change the HTTP verb No.

Random delays spread the retry load.

Self-check

Explain CAP with an analogy.

Two bank branches with a broken phone line must either refuse transactions (consistent) or allow them and reconcile later (available).

Communication

Queue

Analogy: a ticket rail in a kitchen. Waiters (producers) clip tickets; cooks (consumers) take them at their own pace. If lunch rush hits, tickets pile up instead of crashing the kitchen. Why use it: absorb bursts, decouple teams, retry failures. Cost: delay, duplicate delivery, harder debugging.

Pub/sub versus queue versus log

  • Queue: each message goes to one worker; once handled it is gone (a to-do list).
  • Pub/sub: each message goes to every subscriber (a newsletter).
  • Log (Kafka): an ordered notebook many readers can replay from any page (a ledger).

Rate limiting

Analogy: a nightclub bouncer admitting a fixed number per minute so the dance floor does not get dangerously crowded. A token bucket lets a burst through if people saved up tokens, then enforces the long-run rate.

API gateway

Analogy: a hotel reception desk: guests deal with one desk, which checks identity, forwards requests to the right department and refuses suspicious people.

Microservices

Analogy: instead of one chef who makes everything, a team of specialists (grill, pastry, salads) who each own a station. Faster teams and independent scaling, but now you need good communication, and a missing pastry chef can ruin a dinner. Misconception: "microservices are modern, so use them". Start with a well-structured monolith; split when team size, scaling or release cadence demand it.

How this gets asked

Which messaging model delivers each message to every subscriber?

  • Queue One consumer.
  • Pub/sub Correct.
  • Cache No.
  • Load balancer No.

Queues compete for messages; subscribers each get a copy.

Self-check

When should you not use microservices?

For small teams or early products, where a modular monolith is simpler and faster to build and operate.

Operating systems in production

Observability

Analogy: the dashboard, warning lights and black box of an aircraft. Metrics tell you something is wrong, logs tell you what happened, traces show where the time went across the whole journey.

SLO and error budget

Analogy: a delivery company promises 99% on-time. The 1% late deliveries is a budget: if you are well within it you can try new routes; if you have spent it, stop experimenting and fix reliability.

Blue-green and canary deploys

Analogy: blue-green builds a second, identical restaurant next door and moves all customers across at once (instant swap back if the food is bad). Canary sends a few customers first to taste the new menu before everyone else.

Backups versus replication

Replication copies mistakes instantly: if someone deletes a table, the replicas delete it too. Backups are point-in-time copies you can restore from. You need both, and you must test restores.

How this gets asked

Why are backups still needed when you have replication?

  • Replication is slower No.
  • Replication copies deletions and corruption immediately, backups let you restore an earlier state Correct.
  • Backups are faster No.
  • Replication is optional No.

Test restores regularly.

Self-check

Metrics, logs and traces: what does each answer?

Metrics say that something is wrong, logs say what happened, traces say where the time or failure occurred across services.

Putting numbers on it

Back-of-the-envelope maths is simply organised common sense:

  1. Turn users into a rate: daily users x actions per user / 86,400 = average per second; multiply by 2 to 5 for the peak.
  2. Turn the rate into machines: peak per second divided by what one server handles.
  3. Turn a rate and an item size into storage: writes per day x bytes x retention days.
  4. Turn a rate and a size into bandwidth: requests per second x bytes x 8 bits.
users, actions_per_user, bytes_each = 100_000_000, 5, 2_000
per_second = users * actions_per_user / 86_400
print(f"average {per_second:,.0f} requests/s, peak (x3) about {per_second * 3:,.0f}/s")
print(f"storage per year: {users * actions_per_user * bytes_each * 365 / 1e12:,.0f} TB | bandwidth at peak: {per_second * 3 * bytes_each * 8 / 1e9:.1f} Gbit/s")

Output

average 5,787 requests/s, peak (x3) about 17,361/s
storage per year: 365 TB | bandwidth at peak: 0.3 Gbit/s
Key idea

Each design idea exists to solve one specific pain: capacity (scale out), speed (cache, index), safety (replicate, back up), coordination (consensus, idempotency), and bursts (queues, rate limits). When explaining, name the pain first, then the tool, then what it costs.

How this gets asked

100M users x 5 actions per day gives about how many average requests per second (in thousands, rounded)?

500M / 86,400 is about 5,787, i.e. about 6 thousand.

Interview questions: Explained simply

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Explain sharding to a non-engineer.

Like splitting a library's books across rooms by author name: each room is smaller and faster to search, but finding things across rooms is harder and some rooms get busier.

Basic Explain caching in one analogy.

Keeping the books you use most on your desk instead of walking to the library; fast, small and sometimes out of date.

Basic What is the difference between replication and sharding?

Replication copies the same data to several nodes for safety and read capacity; sharding splits different data across nodes for capacity.

Basic Explain a load balancer.

A host who seats each party at a table with space and stops seating at tables without a waiter.

Medium Explain CAP with an analogy.

Two bank branches with a broken phone line must either refuse withdrawals until they can talk (consistent) or allow them and reconcile later (available).

Medium Explain consistent hashing in plain words.

Servers and keys are placed on a circle; each key belongs to the next server clockwise, so adding a server moves only the keys between it and its neighbour.

Medium Why do we need idempotency?

Retries after timeouts are unavoidable, and repeating a non-idempotent action such as payment would duplicate its effect.

Medium Explain a queue versus pub/sub versus a log.

A queue gives each message to one worker, pub/sub gives it to every subscriber, a log keeps an ordered history many readers can replay.

Medium Why are backups needed in addition to replication?

Replication faithfully copies mistakes such as deletes and corruption; backups give a point-in-time state to restore.

Medium Why is p99 more useful than the average?

Users and fan-out requests experience the slow tail; averages hide it.

Advanced How do you explain a trade-off to an interviewer?

Name the pain, the tool that addresses it, what it costs, and the condition under which you would choose differently.

Advanced When is a monolith the better choice?

For small teams and early products where a modular monolith is simpler to build, test, deploy and debug; split into services when scale, team or release independence demand it.

Advanced Explain eventual consistency and where it is not acceptable.

Replicas converge if updates stop, fine for likes and feeds; unacceptable for money, inventory counts and uniqueness constraints without extra coordination.

Advanced Give the back-of-the-envelope recipe.

Convert users into per-second rates, rates into servers, rates times size into storage and bandwidth, and state assumptions and peak factors explicitly.
