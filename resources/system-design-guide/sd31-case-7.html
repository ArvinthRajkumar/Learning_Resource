Case 1: Trending topics

Requirements

Show the top 10 trending hashtags per region for the last hour, updating within a minute. 500M tweets per day (about 6,000/s average, 20,000/s peak), each with about 2 hashtags.

Why it is hard

Counting is easy; counting recent items, per region, at 40,000 increments per second without storing every event is the problem. "Trending" is also not "most popular": it means unusually fast growth compared with normal.

Design

  • Time buckets: count per minute; a 60-minute window is the sum of the last 60 buckets. Subtract the expiring bucket instead of rescanning.
  • Top-K: keep a heap of size K per window; merge partial heaps from partitions.
  • Approximation: a Count-Min Sketch plus a small heap approximates heavy hitters in fixed memory when there are billions of distinct tags.
  • Trend score: compare the current rate with a baseline, for example (current - expected) / sqrt(expected + 1), or a ratio against the same hour yesterday, so a steadily popular tag (#monday) does not dominate a surging one.
  • Abuse: spam and bots inflate counts; dedupe per user, weight by account quality, and apply a blocklist.
from collections import defaultdict, deque
import math
class Trending:
    def __init__(self, window=5):
        self.window, self.buckets, self.total, self.baseline = window, deque(), defaultdict(int), defaultdict(lambda: 1.0)
    def push_minute(self, counts):
        self.buckets.append(counts)
        for tag, n in counts.items(): self.total[tag] += n
        if len(self.buckets) > self.window:
            old = self.buckets.popleft()
            for tag, n in old.items():
                self.total[tag] -= n
                if self.total[tag] == 0: del self.total[tag]
    def score(self, tag):                                              # surprise relative to the usual rate
        expected = self.baseline[tag] * self.window
        return (self.total[tag] - expected) / math.sqrt(expected + 1)
    def top(self, k=3): return sorted(((round(self.score(t), 1), t, self.total[t]) for t in self.total), reverse=True)[:k]
t = Trending(window=5)
t.baseline.update({"#monday": 100.0, "#coffee": 20.0})
for minute in range(6):
    t.push_minute({"#monday": 100, "#coffee": 20, "#goal": 5 * (minute > 2) * 40 + 1, "#rare": 2})
print("by score (score, tag, count in window):", t.top())
print("by raw count:", sorted(((n, tag) for tag, n in t.total.items()), reverse=True)[:3])

Output

by score (score, tag, count in window): [(244.9, '#goal', 605), (2.0, '#rare', 10), (0.0, '#monday', 500)]
by raw count: [(605, '#goal'), (500, '#monday'), (100, '#coffee')]

The popular tag leads on raw count while the surging tag leads on score: that difference is the product. Per region, shard the same pipeline by region and keep a global rollup.

How this gets asked

Why is a trend score based on growth rather than raw counts?

  • It is cheaper No.
  • Constantly popular tags would otherwise always dominate; trending means unusually fast growth Correct.
  • Counts are inaccurate No.
  • It needs less memory No.

Compare to a baseline.

How do you maintain a sliding 60-minute count efficiently?

  • Rescan all events Too slow.
  • Keep per-minute buckets and subtract the expiring bucket Correct.
  • Recount hourly Not sliding.
  • Use a cache No.

Add the new bucket, remove the oldest.

Self-check

Name two ways to keep top-K cheap at huge scale.

Count-Min Sketch with a small heap, and merging per-partition top-K lists.

Case 2: Food delivery dispatch

Requirements

Customers order from restaurants; couriers deliver. Show an ETA, assign a courier within seconds, and track the delivery live. 1M orders/hour at peak in a large country; 200k couriers sending location every 4 seconds (50,000 updates/s).

Components

  • Location service: ingests courier GPS pings into an in-memory geo index (geohash or H3 cells, see SD24); the latest position lives in Redis, the history in a stream or time-series store.
  • Order service: state machine placed -> accepted -> preparing -> ready -> picked_up -> delivered with transactional updates and events.
  • Dispatch (matching) service: chooses a courier per order, balancing speed, fairness and cost.
  • ETA service: restaurant preparation time + courier to restaurant + restaurant to customer, from road graphs, live traffic and a learned model.
  • Tracking: push courier positions to the customer through WebSocket or SSE (SD29); throttle updates to every few seconds.

Matching

Greedy "nearest courier" is simple but can be globally poor. Batched matching collects orders and couriers for a short window (say 5 seconds) and solves an assignment problem minimising total cost (travel time, delay penalty), solved with the Hungarian algorithm or heuristics. Add batching (one courier carries two nearby orders) and re-dispatch if a courier declines.

import itertools
orders = {"o1": (3, 0), "o2": (0, 0)}
couriers = {"c1": (1, 0), "c2": (7, 0)}
dist = lambda a, b: abs(a[0] - b[0]) + abs(a[1] - b[1])
# greedy: process orders in arrival order, give each the nearest free courier
free, greedy = dict(couriers), {}
for o, loc in orders.items():
    c = min(free, key=lambda c: dist(free[c], loc)); greedy[o] = c; free.pop(c)
greedy_cost = sum(dist(orders[o], couriers[c]) for o, c in greedy.items())
# optimal assignment by brute force over permutations (Hungarian does this in O(n^3) for large n)
best = min(itertools.permutations(couriers), key=lambda perm: sum(dist(orders[o], couriers[c]) for o, c in zip(orders, perm)))
best_cost = sum(dist(orders[o], couriers[c]) for o, c in zip(orders, best))
print("greedy:", greedy, "total distance", greedy_cost)
print("batched optimal:", dict(zip(orders, best)), "total distance", best_cost)

Output

greedy: {'o1': 'c1', 'o2': 'c2'} total distance 9
batched optimal: {'o1': 'c2', 'o2': 'c1'} total distance 5

Greedy gave the first order the nearest courier, who was also the only good option for the second order, which was left with the distant courier. Looking at the batch together is cheaper overall.

Deep dives

  • Surge and balance: when demand exceeds couriers, raise delivery fees, extend ETAs, pause new orders per zone (supply and demand are balanced per area).
  • Idempotent order creation and payment authorisation first, capture on delivery (SD24 checkout).
  • Failure: a courier goes silent (mark stale after N missed pings and re-dispatch); restaurant rejects (refund and notify).
  • Hot areas: shard by city or geohash prefix; stadiums and rain create spikes.

How this gets asked

Why can batched assignment beat greedy nearest-courier matching?

  • It is simpler No.
  • It minimises total cost across all orders together instead of locally Correct.
  • It uses less memory No.
  • It avoids GPS No.

Greedy can steal the only good courier for another order.

Self-check

What are the services in a delivery platform?

Location, order, dispatch/matching, ETA, tracking, payments and notifications.

Case 3: Online auction

Requirements

Sellers list items with an end time. Buyers place bids; the highest bid at the end wins. Thousands of bids on popular items in the last seconds. Rules: a bid must exceed the current highest by a minimum increment; anti-sniping extends the end time if a bid arrives in the last minute.

Correctness is the whole problem

Two bids arrive simultaneously: only one can win the same price. The check "is this bid higher than the current?" and the update must be atomic. Per auction, bids form a serial history.

Options: a row lock or conditional update in the database (UPDATE auction SET high_bid = ? WHERE id = ? AND high_bid < ? - increment), a single-writer per auction (route all bids for an auction to one partition and process in order) or optimistic versioning. Single-writer through a partitioned queue gives a natural ordering, an audit log of bids and a place to apply anti-sniping.

class Auction:
    def __init__(self, end, increment=5, snipe_window=60, extension=120):
        self.end, self.inc, self.win, self.ext = end, increment, snipe_window, extension
        self.high, self.leader, self.history = 0, None, []
    def bid(self, user, amount, now):                       # processed by one writer, in order
        if now >= self.end: return "rejected: auction ended"
        if amount < self.high + self.inc: return f"rejected: need at least {self.high + self.inc}"
        self.high, self.leader = amount, user
        self.history.append((now, user, amount))
        if self.end - now <= self.win:                      # anti-sniping
            self.end = now + self.ext
            return f"accepted, end extended to {self.end}"
        return "accepted"
a = Auction(end=1000)
for t, u, amt in [(100, "ana", 50), (200, "bo", 52), (300, "bo", 60), (950, "cy", 70), (1030, "ana", 75), (1160, "di", 90), (1200, "bo", 95)]:
    print(f"t={t:>4} {u}: {amt:>3} -> {a.bid(u, amt, t)}")
print("winner:", a.leader, "at", a.high, "| bids recorded:", len(a.history))

Output

t= 100 ana:  50 -> accepted
t= 200 bo:  52 -> rejected: need at least 55
t= 300 bo:  60 -> accepted
t= 950 cy:  70 -> accepted, end extended to 1070
t=1030 ana:  75 -> accepted, end extended to 1150
t=1160 di:  90 -> rejected: auction ended
t=1200 bo:  95 -> rejected: auction ended
winner: ana at 75 | bids recorded: 4

Other parts

  • Proxy bidding (automatic bidding up to a maximum), reserve prices, buy-it-now.
  • Real-time updates to watchers: pub/sub fan-out per auction through WebSockets; throttle to a few updates per second.
  • Closing: a scheduler (SD25) closes auctions at the (possibly extended) end time; closing is idempotent and creates the order and payment hold.
  • Fraud: shill bidding detection, bid retraction rules, payment verification before bidding on large items.
  • Fair time: use server time only; clients display countdowns corrected by a server offset.

How this gets asked

How do you ensure two simultaneous bids cannot both win?

  • Hope No.
  • Serialise bids per auction with a conditional update or a single ordered writer Correct.
  • Faster servers No.
  • Client-side checks Untrusted.

The check and the update must be atomic.

What does anti-sniping do?

  • Blocks bots No.
  • Extends the end time when a bid arrives in the final window Correct.
  • Hides bids No.
  • Refunds bidders No.

It gives others a chance to respond.

Self-check

What events appear in an auction audit log?

Every accepted and rejected bid with time, user, amount and the resulting state and end time.

Case 4: Team chat at scale (Slack, Discord)

What differs from one-to-one chat (SD14)

Workspaces contain channels with up to hundreds of thousands of members, threads, reactions, search, file sharing, unread counts per user per channel, mentions and presence. The same message is read by many, so reads dominate writes.

Design

  • Message path: client sends over WebSocket to a gateway, which writes to the channel's partition (a log keyed by channel id, assigning increasing message ids), then publishes to subscribers.
  • Fan-out strategy: for a channel with M members, do not enqueue M copies. Gateways subscribe to the channels their connected users belong to; one publish reaches every gateway that has at least one member online. Offline members read from the log on return and get push notifications only for mentions or direct messages.
  • Unread counts: store per user per channel only the last read message id; unread = latest id minus last read, with a cap for display. Avoid per-message read rows for large channels.
  • Storage: messages keyed by (channel_id, message_id) in a wide-column or partitioned store, with time-bucketed partitions for old data; hot recent messages cached. Edits and deletes are new events or tombstones.
  • Search: index messages asynchronously into a search cluster partitioned by workspace, enforcing channel permissions at query time.
  • Presence: heartbeats into a fast store with TTL; broadcast changes only to people who care (same channel, or contacts), batched, because presence for 100,000 members is a storm.
  • Large channels ("announcement" with 500k members): switch to pull for most members and rate limit posting and typing indicators.
def fanout_cost(members, online_fraction, gateways=200):
    online = int(members * online_fraction)
    per_member_queue = members                                # naive: one queue write per member
    per_gateway = min(gateways, online)                       # gateway-level pub/sub: one message per gateway with a subscriber
    return per_member_queue, per_gateway
for members in (50, 5_000, 500_000):
    naive, smart = fanout_cost(members, 0.2)
    print(f"channel of {members:>7,} members: naive {naive:>7,} queue writes vs {smart:>3} gateway publishes per message")

Output

channel of      50 members: naive      50 queue writes vs  10 gateway publishes per message
channel of   5,000 members: naive   5,000 queue writes vs 200 gateway publishes per message
channel of 500,000 members: naive 500,000 queue writes vs 200 gateway publishes per message

How this gets asked

How do you store unread counts for huge channels?

  • A row per message per user Enormous.
  • The last-read message id per user per channel; unread = latest id minus last read Correct.
  • Count on every open Slow.
  • Not at all No.

One small pointer per membership.

Self-check

Why fan out per gateway instead of per member?

A message needs only one publish per gateway holding a subscriber, not one write per member.

Case 5: Email service

Requirements

Send and receive email at scale (Gmail-style): mailboxes with folders and labels, search, attachments, spam filtering, and reliable delivery over the legacy SMTP protocol.

How email works

SMTP moves mail between servers (sender's server looks up the recipient domain's MX record in DNS and connects, usually on port 25); IMAP/POP3 or a web API lets clients read it. Key features: store and forward with retries on temporary failure (4xx) for days, bounce messages on permanent failure (5xx).

Sending pipeline

Reputation matters: SPF (which IPs may send for a domain), DKIM (a cryptographic signature on the message) and DMARC (policy and reporting) prove authenticity. Warm up new sending IPs gradually, honour unsubscribe and bounces, and separate transactional from marketing streams.

Receiving and storage

  • Inbound: accept the message, run virus and spam checks (authentication results, IP reputation, content classifiers, user feedback), then deliver to the mailbox.
  • Storage: messages are immutable blobs in object storage; metadata (labels, read flags, thread id) in a partitioned database keyed by user. Deduplicate large attachments by hash. Threading groups messages by References/In-Reply-To headers.
  • Search: per-user inverted index (see SD33), updated asynchronously.
  • Scale: shard by user id so each mailbox lives on one shard; replicate across zones; back up and keep deletes recoverable for a period.
import re
SPAM_WORDS = {"winner": 2.0, "free": 1.0, "urgent": 1.5, "click here": 2.5, "unsubscribe": -0.5}
def spam_score(subject, body, spf_pass, dkim_pass, links):
    text = (subject + " " + body).lower()
    score = sum(w for word, w in SPAM_WORDS.items() if word in text)
    score += 0 if spf_pass else 2.0
    score += 0 if dkim_pass else 1.5
    score += 0.5 * max(0, links - 2)
    score += 1.0 if re.search(r"[A-Z]{6,}", subject) else 0.0
    return round(score, 1)
msgs = [("Team notes", "meeting at 3", True, True, 0), ("URGENT WINNER", "free prize click here now", False, False, 6)]
for s, b, spf, dkim, links in msgs:
    sc = spam_score(s, b, spf, dkim, links)
    print(f"{s!r}: score {sc} -> {'SPAM folder' if sc >= 5 else 'inbox'}")

Output

'Team notes': score 0.0 -> inbox
'URGENT WINNER': score 13.5 -> SPAM folder

Real filters combine many signals with machine-learning classifiers, user feedback loops and sender reputation, and are tuned to avoid false positives, because losing a real email is worse than letting some spam through.

Key idea

Trending is a growth statistic over sliding windows, dispatch is an assignment problem solved over a batch, auctions need one ordered writer per item, team chat survives huge channels by fanning out per gateway and tracking read pointers, and email is a store-and-forward protocol made reliable with queues, retries and authentication.

How this gets asked

What do SPF and DKIM do?

  • Compress mail No.
  • Prove the sending server is authorised (SPF) and the message is signed by the domain (DKIM) Correct.
  • Encrypt mailboxes No.
  • Route mail No.

They support DMARC policy and fight spoofing.

How does SMTP handle a temporary delivery failure?

  • Drops the mail No.
  • Queues and retries with backoff for days, bouncing only on permanent failure Correct.
  • Calls the user No.
  • Retries immediately forever No.

Store-and-forward gives reliability.

Self-check

Why queue every stage of mail delivery?

To survive crashes and temporary failures: messages are never lost and retried with backoff.

Interview questions: Case studies 7

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic How do you compute trending topics over the last hour?

Count per minute buckets, maintain the sliding window by adding the new bucket and removing the oldest, keep top-K per partition and merge, and score growth relative to a baseline.

Medium Why use a Count-Min Sketch for trending?

It tracks approximate frequencies of billions of distinct items in fixed memory with overestimate-only error, paired with a heap for the top items.

Medium Why is greedy nearest-courier matching suboptimal?

It can use up the only good courier for another order; batched assignment minimises total cost over the group.

Medium What services make up a food-delivery platform?

Location, order, dispatch, ETA, tracking, payments and notifications, with an event stream connecting them.

Medium How do you prevent two simultaneous auction bids both winning?

Serialise bids per auction through a single ordered writer or atomic conditional update that checks the current highest bid and increment.

Medium What is anti-sniping?

Extending the end time when a bid arrives near the end, so others can respond.

Medium How does email delivery handle failures?

Store-and-forward queues with retries and backoff on temporary (4xx) errors for days and bounces on permanent (5xx) errors.

Medium What are SPF, DKIM and DMARC?

SPF lists servers allowed to send for a domain, DKIM signs messages with the domain's key, and DMARC sets policy and reporting based on both.

Advanced How does Slack-style chat avoid per-member fan-out?

Gateways subscribe to channels for their connected users, so one publish reaches each gateway with an interested user; offline users read from the log and unread counts are last-read pointers.

Advanced Why store the last read message id instead of read flags?

One small pointer per user per channel replaces millions of per-message rows, and unread is latest id minus pointer.

Advanced How does presence scale for large channels?

Heartbeats with TTL in a fast store, broadcasting changes only to interested peers in batches, and not showing presence for huge channels.

Advanced How would you design the ETA service?

Prep time plus courier-to-restaurant plus restaurant-to-customer travel from a road graph with live traffic, corrected by a model trained on historical delivery outcomes.

Advanced How do you handle a courier who stops sending location?

Mark the courier stale after missed pings, alert the customer if needed, and re-dispatch the order.

Advanced How would you detect bidding fraud?

Pattern analysis of bidder-seller relationships, new account behaviour, bid timing and retractions, plus payment verification for high-value items.
