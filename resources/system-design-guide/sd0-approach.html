Part SD0

How to approach a system design interview

A system design interview is a conversation about building something big enough that no single machine, person or idea is enough. This part gives you a repeatable framework so you never stare at a blank whiteboard.

Basic~1.5 hours

What the interview really tests

Intuition

Nobody expects you to reproduce a real company's architecture. The interviewer wants to see how you think: do you ask the right questions, size the problem with numbers, pick components for reasons, notice what will break, and explain trade-offs calmly. A design with a clear reason behind each box beats a fancier design you cannot defend.

The signals interviewers look for

SignalWhat it looks like
Problem explorationYou clarify scope and requirements before drawing anything
Quantitative senseYou estimate traffic, storage and bandwidth and let the numbers drive choices
BreadthYou know the standard building blocks: load balancers, caches, queues, databases, CDNs
DepthYou can go two or three levels down on one or two components
Trade-off reasoningEvery choice comes with "because" and "the cost is"
Failure thinkingYou ask what happens when a node, a network link or a whole region fails
CommunicationYou structure the time, check in with the interviewer and adapt
Remember

There is no single right answer. A good answer is one whose assumptions are stated, whose numbers are sane and whose weak points you can name before the interviewer does.

Self-check

What do interviewers actually want to see?

How you think: clarifying questions, numbers, justified components, failure analysis and trade-off reasoning, rather than a memorised architecture.

A repeatable framework

The six steps

Use these steps in order. A 45 minute interview splits roughly as shown.

StepMinutesOutput
1. Clarify requirements5Functional and non-functional requirements, scope, out-of-scope list
2. Estimate scale5Requests per second, storage per year, bandwidth, read to write ratio
3. Define the API and data model5Main endpoints and core entities
4. High-level design10Boxes and arrows covering the main flows end to end
5. Deep dive15Two or three bottleneck areas designed in detail
6. Wrap up5Failure modes, monitoring, trade-offs, what you would do next

Step 1: requirements

Ask until you can write down three lists.

  • Functional requirements: what the system must do ("a user can shorten a URL and be redirected").
  • Non-functional requirements: how well it must do it. Availability, latency, consistency, durability, scalability, cost, security.
  • Out of scope: what you will deliberately skip ("analytics dashboards", "user accounts") so the problem fits the time.

Good clarifying questions are specific and change the design:

  • Who are the users and how many? Is traffic global?
  • Is the workload read-heavy or write-heavy?
  • What matters more when things fail: showing slightly stale data or showing an error?
  • What latency does the user notice? Is a few seconds of delay acceptable?
  • Is data loss ever acceptable?
Trap

Jumping straight to "I would use Kafka and microservices" is the classic failure. Technologies are answers. Requirements are the questions that choose between them.

Step 2: estimation

Turn user numbers into engineering numbers: requests per second, storage, bandwidth. These decide whether you need one database or a sharded fleet. Part SD1 is dedicated to this skill.

Step 3: API and data model

Name the two or three most important endpoints and the entities behind them. Writing POST /urls {long_url} -> {short_url} and a table sketch takes a minute and exposes missing requirements.

Step 4: high-level design

Draw the request path from the client to the data store and back. Start simple: client, load balancer, stateless application servers, database. Then add components only when a requirement or a number demands it, and say why.

Step 5: deep dive

The interviewer will usually pick the area, or you propose the two riskiest. Typical deep dives: the data model and sharding key, the cache strategy, how a feed is generated, how a write is made durable, how you avoid a single point of failure.

Step 6: wrap up

Summarise the design in a few sentences, list the failure modes you handled, say how you would monitor it, and name the next improvements. This is where senior candidates stand out.

Rules of thumb for the whole interview

Think aloud. State assumptions. Prefer boring, proven technology. Design for the stated scale, not for Google scale. Revisit the requirements whenever a choice contradicts them.

How this gets asked

In a 45 minute interview, what should you do first?

  • Draw the database schema Too early; you do not know the requirements.
  • Clarify requirements and scope Correct.
  • Name the technologies you will use Technologies answer requirements; they do not replace them.
  • Estimate storage for ten years Useful, but only after you know what is being stored.

Requirements decide everything that follows. A few minutes of questions prevents designing the wrong system.

Self-check

List the six steps in order.

Requirements, estimates, API and data model, high-level design, deep dive, wrap up.

Why estimate before drawing the architecture?

The numbers decide whether one database is enough or you need caching, sharding and queues. Choices without numbers look arbitrary.

Functional and non-functional requirements

The non-functional vocabulary

These words appear in every design. Know what each one means and how it is measured.

QualityMeaningTypical measure
AvailabilityThe system answers when askedPercent uptime, for example 99.9%
LatencyTime to answer one requestp50, p95, p99 in milliseconds
ThroughputWork done per unit timeRequests per second, MB per second
ScalabilityHandles growth by adding resourcesLoad vs. resources curve
DurabilityCommitted data is not lostAnnual loss probability, copies kept
ConsistencyReaders see agreed, up-to-date dataLinearizable, eventual, and so on
ReliabilityDoes the right thing even with faultsError rate, mean time between failures
MaintainabilityEasy to operate and changeTime to deploy, time to recover
CostMoney for hardware, cloud and peopleDollars per month, per million requests

Percentiles, not averages

Average latency hides pain. If 99 requests take 10 ms and one takes 1,000 ms, the mean is about 20 ms but one user in a hundred waits a second. Services are judged on p95 and p99 because slow tail requests are what users remember, and because one user request often fans out to many internal calls, so the tail of the fan-out dominates.

import statistics
lat = [10] * 99 + [1000]
print("mean =", statistics.mean(lat))
print("median =", statistics.median(lat))
s = sorted(lat)
print("p99 =", s[int(0.99 * len(s)) - 1], "max =", s[-1])

Output

mean = 19.9
median = 10.0
p99 = 10 max = 1000

Trade-offs are the whole game

You cannot maximise everything. Strong consistency costs latency and availability. Durability costs write speed. Low cost costs redundancy. Whenever you pick a point on one axis, say what you gave up.

How this gets asked

Which of these are non-functional requirements? Select all.

  • Users can upload a photo
  • p99 latency under 300 ms
  • 99.95% availability
  • Users can follow other users

Uploading and following describe behaviour (functional). Latency and availability describe quality (non-functional).

99 requests take 10 ms and one takes 1000 ms. What is the mean latency in ms?

(99 x 10 + 1000) / 100 = 19.9 ms. The mean looks fine while one user in 100 waits a second, which is why we use percentiles.

Self-check

Why report p99 latency instead of the average?

Averages hide slow tail requests, and users and fan-out calls are dominated by the tail.

Reading the problem: read-heavy or write-heavy

Why the ratio matters

Most design decisions depend on how reads compare with writes.

  • Read-heavy (a URL shortener, a news site, a product catalogue): add caches, read replicas and CDNs. Writes are rare, so even a single leader can cope.
  • Write-heavy (logging, metrics, IoT telemetry, chat messages): add queues and batching, partition the write path, use storage built for appends such as LSM-tree databases.
  • Balanced (a social feed, a shopping cart): you need both, plus a careful consistency story.

Access patterns drive storage

Ask "how will this data be read?" before choosing a database. A lookup by key suits a key-value store. Range scans by time suit a wide-column or time-series store. Free-text queries need a search index. Relationships traversal might justify a graph database. Joins and transactions across many entities favour a relational database.

Key idea

Choose the data store from the access pattern and the consistency need, not from fashion.

How this gets asked

A system is 99% reads and 1% writes. Which first move helps most?

  • Shard the write path Writes are rare, so this is premature.
  • Add caching and read replicas Correct.
  • Use a write-ahead log only Does not address read load.
  • Move everything to a queue Does not speed up reads.

For read-heavy workloads, serve reads from memory (cache) and from replicas, and keep a simple write path.

Self-check

How do you choose a data store?

From the access pattern (lookup, range scan, search, relationships, transactions) and the consistency need.

Communicating well

Habits that help

  • Start with a one sentence restatement of the problem.
  • Write the requirements and numbers on the board where both of you can see them.
  • Draw as you speak. Number the arrows for the main flows ("1. client sends, 2. server checks cache...").
  • Name alternatives: "I could use X or Y. Given our read ratio I will pick X, and the cost is Z."
  • Ask for feedback: "Would you like me to go deeper on storage or on the feed generation?"
  • When you do not know something, say how you would find out or reason it out from first principles.

How this gets asked

Which behaviour is most likely to hurt you in the interview?

  • Stating assumptions aloud This helps.
  • Saying what you give up with each choice This helps.
  • Naming many technologies without reasons Correct: it shows memorisation, not design.
  • Asking the interviewer which area to go deeper on This is good collaboration.

Interview questions: Approach

8 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic How do you start a system design interview?

Clarify the problem: functional requirements, non-functional requirements (scale, latency, availability, consistency) and what is out of scope. Then estimate, define the API and data model, draw a high-level design, deep dive, and wrap up.

Basic What is the difference between functional and non-functional requirements?

Functional requirements describe what the system does (a user can post a photo). Non-functional requirements describe how well (p99 latency under 300 ms, 99.95 percent availability, durability, security).

Basic Why do we talk about p99 latency instead of the average?

Averages hide slow outliers. Users and fan-out calls experience the tail, so p95 and p99 reflect real experience far better.

Medium How do you decide between consistency and availability for a feature?

Ask what a wrong or missing answer costs. Money and unique identifiers need strong consistency. Feeds, likes and catalogue views tolerate staleness. Choose per operation, not for the whole system.

Medium What if you do not know a technology the interviewer mentions?

Say so, then reason from first principles: what problem it solves, what guarantees it needs, and compare with something you know. Honesty plus structured reasoning scores better than bluffing.

Medium How do you decide what to deep dive into?

Pick the components where the numbers are hardest or the requirements most demanding (the write path at scale, the hot partition, the consistency boundary), and ask the interviewer which they prefer.

Advanced How do you evolve a design when the interviewer changes a requirement mid-way?

State what changes (for example read to write ratio or consistency), identify the components affected, adjust only those with justified alternatives and say what you gave up. Show the design is modular.

Advanced What are signs of over-engineering in a design?

Technologies without a requirement or number behind them, sharding for a few hundred requests per second, many microservices for a small team, custom components where a managed one fits. Start from the simplest design that meets the numbers.
