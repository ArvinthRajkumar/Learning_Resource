Client-side and mobile system design: offline-first, sync, push and media pipelines

Servers are reliable and always on; phones are neither. Interviews for mobile and full-stack roles probe whether you can design for slow, flaky, battery-limited clients that go offline, return later and expect their changes to survive. This part shows the patterns.

MediumAdvanced~4 hours

The client is a distributed system

A mobile app is a replica of server data that lives on a device you do not control. The network is slow, expensive, intermittent and sometimes absent; the operating system kills your app at any moment; the battery is finite; old app versions stay in the wild for years. Design principles:

  • Local first: render from local storage immediately, then sync in the background.
  • Assume failure: every request can time out; every write can happen twice.
  • Minimise bytes and wake-ups: compress, batch, delta-sync, cache.
  • Be backward compatible: servers must support old clients (version APIs, ignore unknown fields, feature flags).
  • Protect the user: secure storage for tokens, certificate pinning where justified, privacy defaults.

Offline-first architecture

Key pieces:

  • Local database (SQLite, Room, Core Data, Realm) as the single source of truth for the UI; the UI observes it and updates when sync writes arrive.
  • Outbox: user actions are written locally with a client-generated id and pending status, shown immediately (optimistic UI), and sent when connectivity allows, with retry and backoff.
  • Idempotency: each queued action carries a unique id (idempotency key) so a retry after an ambiguous failure does not create duplicates (SD9).
  • Background sync scheduled by the OS (WorkManager, BackgroundTasks) respecting battery and network constraints.
  • Connectivity is a hint, not a fact: "online" does not mean reachable, so rely on request results.
import uuid
class Server:
    def __init__(self): self.items, self.seen = {}, set()
    def apply(self, op):
        if op["id"] in self.seen: return "duplicate ignored"               # idempotent by operation id
        self.seen.add(op["id"]); self.items[op["item"]] = op["value"]; return "applied"
class Client:
    def __init__(self, server): self.server, self.local, self.outbox, self.online = server, {}, [], False
    def set(self, item, value):
        self.local[item] = value                                          # optimistic: UI updates at once
        self.outbox.append({"id": str(uuid.uuid4())[:8], "item": item, "value": value})
    def sync(self):
        if not self.online: return "offline: nothing sent, %d queued" % len(self.outbox)
        results = []
        for op in list(self.outbox):
            results.append(self.server.apply(op))
            if len(results) == 1: results.append(self.server.apply(op))      # simulate an ack lost -> the client retries the same op
            self.outbox.remove(op)
        return results
srv = Server(); cl = Client(srv)
cl.set("note", "draft 1"); cl.set("note", "draft 2"); cl.set("title", "Trip")
print(cl.sync(), "| local view:", cl.local)
cl.online = True
print(cl.sync(), "| server state:", srv.items)

Output

offline: nothing sent, 3 queued | local view: {'note': 'draft 2', 'title': 'Trip'}
['applied', 'duplicate ignored', 'applied', 'applied'] | server state: {'note': 'draft 2', 'title': 'Trip'}

Sync protocols

How does a client catch up after being offline for a week?

Rules for good sync: use monotonic sequence numbers or tokens, represent deletes as tombstones for a retention period (otherwise offline devices resurrect deleted items), page the changes, make each page idempotent, and have a full resync fallback when the token is too old.

class ChangeLog:
    def __init__(self): self.seq, self.entries = 0, []
    def record(self, op, key, value=None):
        self.seq += 1; self.entries.append((self.seq, op, key, value))
    def since(self, token, limit=3):
        page = [e for e in self.entries if e[0] > token][:limit]
        return page, (page[-1][0] if page else token), len(page) == limit            # entries, next token, more pages?
log = ChangeLog()
for k, v in [("a", 1), ("b", 2), ("c", 3)]: log.record("put", k, v)
log.record("delete", "b"); log.record("put", "d", 4); log.record("put", "a", 10)
state, token, more = {}, 0, True
while more:
    page, token, more = log.since(token)
    for seq, op, key, value in page:
        if op == "put": state[key] = value
        else: state.pop(key, None)
    print("fetched", [(s, o, k) for s, o, k, _ in page], "-> token", token)
print("final client state:", state, "| matches replaying the full log:", state == {"a": 10, "c": 3, "d": 4})

How this gets asked

Why prefer sync tokens or sequence numbers over 'changes since timestamp'?

  • They are shorter No.
  • They avoid clock skew and ties that lose changes, and are resumable Correct.
  • They need no server storage They need a log.
  • They encrypt data No.

Logical positions are exact.

Why keep tombstones for deleted items for a while?

  • To save disk No.
  • So devices that were offline learn about the delete instead of resurrecting the item Correct.
  • For analytics only No.
  • For caching No.

Without them a delete cannot be synchronised.

Conflict resolution

Two devices edit the same item offline. Choose a strategy consistent with the data's meaning:

StrategyBehaviourFits
Last write wins (server time)Newest save replaces olderSettings, simple profile fields
Field-level mergeMerge independent fields; conflict only on the same fieldRecords with many fields
Operation-based mergeSend operations (increment, add to list), not final valuesCounters, lists, carts
CRDTs (SD28)Automatic convergenceCollaborative text, sets
Version check and ask the userServer rejects stale version, client shows a merge UIDocuments, important data
Server authoritativeServer decides by rules, client reconcilesInventory, payments
 
def merge_fields(base, mine, theirs):
    merged, conflicts = {}, []
    for k in sorted(base.keys() | mine.keys() | theirs.keys()):
        b, m, t = base.get(k), mine.get(k), theirs.get(k)
        if m == t: merged[k] = m
        elif m == b: merged[k] = t                    # only the other side changed it
        elif t == b: merged[k] = m                    # only I changed it
        else: conflicts.append(k); merged[k] = t       # both changed differently: needs a rule or the user
    return merged, sorted(conflicts)
base = {"title": "Trip", "date": "May 1", "notes": "pack"}
mine = {"title": "Trip to Goa", "date": "May 1", "notes": "pack sunscreen"}
theirs = {"title": "Trip", "date": "May 3", "notes": "pack"}
print(merge_fields(base, mine, theirs))
print("both edited the notes differently:", merge_fields(base, mine, {"title": "Trip", "date": "May 1", "notes": "pack hat"}))

Output

({'date': 'May 3', 'notes': 'pack sunscreen', 'title': 'Trip to Goa'}, [])
both edited the notes differently: ({'date': 'May 1', 'notes': 'pack hat', 'title': 'Trip to Goa'}, ['notes'])

This three-way merge uses the common ancestor (base) to tell who changed what, the same idea as git merge.

Self-check

When is last-write-wins acceptable?

For simple, low-value fields where losing a concurrent edit is tolerable, such as a preference.

Push notifications

Mobile operating systems provide the channel (APNs for Apple, FCM for Android); your server sends a message addressed to a device token, and the OS delivers it even when the app is closed.

  • Pipeline: event -> notification service -> user preferences, quiet hours and rate limits -> template and localise -> provider (APNs/FCM) -> device. Track delivery and opens.
  • Tokens change and expire: refresh on app start, delete tokens when the provider reports them invalid, support several devices per user.
  • Delivery is best effort: do not depend on it for correctness; keep the data fetchable in the app. Use collapse keys so a burst becomes one notification and TTL so stale ones are dropped.
  • Silent/data pushes can trigger a background sync but are throttled by the OS.
  • Respect the user: opt-in, categories, frequency caps, deduplicate across channels (push, email, in-app).
  • Fan-out: queue per provider with rate limiting and retries; batch sends; partition by user.

How this gets asked

Why must push notifications not be required for correctness?

  • They cost money No.
  • Delivery is best effort and can be delayed, dropped or throttled by the OS Correct.
  • They are encrypted No.
  • They are slow to write No.

The app must be able to fetch the data itself.

Self-check

What are collapse keys for?

Replacing earlier pending notifications of the same kind so a burst shows as one.

Client-side data loading

  • Pagination: cursor/keyset pages (SD9); infinite scroll with prefetch of the next page; keep a stable ordering and handle inserts at the top.
  • Caching layers: in-memory cache, disk cache, HTTP cache; stale-while-revalidate (show cached, refresh behind). Define a freshness policy per data type.
  • Reduce chattiness: batch calls (GraphQL or aggregated endpoints), request only needed fields, compress responses, prefer binary formats on hot paths.
  • Resilience: timeouts, retry with backoff and jitter, cancel requests when the user navigates away, and show cached data with a stale indicator rather than an error.
  • Image loading: request the right size from a resizing CDN, progressive or blurred placeholders, memory and disk caches keyed by URL and size, and downsample large bitmaps to the view size (out-of-memory crashes are a leading mobile crash cause).
class LRU:
    def __init__(self, capacity_bytes): self.cap, self.used, self.items = capacity_bytes, 0, {}
    def get(self, k):
        if k in self.items: v = self.items.pop(k); self.items[k] = v; return v
    def put(self, k, size):
        if k in self.items: self.used -= self.items.pop(k)
        self.items[k] = size; self.used += size
        while self.used > self.cap:
            oldest = next(iter(self.items)); self.used -= self.items.pop(oldest)
cache = LRU(capacity_bytes=10_000_000)                     # 10 MB image cache
for name, size in [("a", 4_000_000), ("b", 4_000_000), ("c", 4_000_000)]: cache.put(name, size)
print("keys after adding three 4 MB images to a 10 MB cache:", list(cache.items), "| used:", cache.used)
cache.get("b"); cache.put("d", 3_000_000)
print("after touching b and adding d:", list(cache.items))

Media upload and video

Large uploads: use resumable, chunked uploads (upload parts with an upload id; on failure ask the server which parts it has and continue), upload directly to object storage with a pre-signed URL so bytes bypass your servers, verify with checksums, and process asynchronously.

Image pipeline: original stored once; background jobs create thumbnails and formats (WebP/AVIF); the CDN serves sizes on demand.

Video pipeline: upload original, transcode into several resolutions and bitrates, cut into short segments (HLS or DASH), generate a manifest listing renditions. The player picks a rendition using adaptive bitrate streaming based on measured throughput, switching quality seamlessly. Preview thumbnails, subtitles and DRM are extra tracks.

def pick_rendition(throughput_kbps, ladder=((240, 400), (480, 1000), (720, 2500), (1080, 5000)), safety=0.8):
    usable = throughput_kbps * safety
    best = ladder[0]
    for res, bitrate in ladder:
        if bitrate <= usable: best = (res, bitrate)
    return best
for kbps in (300, 1200, 3000, 20000):
    res, br = pick_rendition(kbps)
    print(f"measured {kbps:>6} kbps -> play {res}p at {br} kbps")

measured   1200 kbps -> play 240p at 400 kbps
measured   3000 kbps -> play 480p at 1000 kbps

Battery, data and security

  • Battery: batch network calls (radios use most energy waking up), avoid polling, use push and OS scheduling, respect low-power mode.
  • Data: allow Wi-Fi-only for big downloads, compress, delta updates for app content.
  • Security: tokens in the platform keystore/keychain, never in plain preferences; short-lived access tokens with refresh rotation; TLS only, optional certificate pinning (with a rotation plan); do not trust client-side checks, enforce rules on the server; obfuscation is not protection.
  • Releases: staged rollouts, feature flags and remote config, a minimum supported version and a kill switch, crash reporting and analytics with privacy controls.
  • Observability: client metrics (startup time, frame drops, request failures by network type) are your only view of real user experience.
Key idea

Treat the device as an unreliable replica: render from local data, queue changes with idempotent ids, sync with tokens and tombstones, resolve conflicts by data meaning, deliver pushes as hints, load data in cached pages, upload resumably to object storage, and respect battery and bandwidth.

Self-check

Why store tokens in the keychain or keystore?

They are protected by the OS and hardware, unlike plain preferences, which any compromise or backup can expose.

Interview questions: Client and mobile design

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What does offline-first mean?

The UI reads from a local database and writes locally first, and a sync engine reconciles with the server in the background.

Basic Why queue actions with client-generated ids?

So retries after timeouts are idempotent and duplicates are ignored by the server.

Medium How do you sync after being offline for days?

Use a cursor or sequence token to fetch changes in pages, apply tombstones for deletes, and fall back to a full resync if the token is too old.

Medium Why are tombstones needed?

Without them an offline device cannot learn about a deletion and may push the old item back.

Medium How do you resolve conflicting offline edits?

Choose by data meaning: last write wins for trivial fields, field-level three-way merge, operation-based merge for counters and lists, CRDTs for collaboration, or ask the user.

Medium Why can't you rely on push notifications for correctness?

Delivery is best effort and can be delayed, dropped or throttled; the app must be able to fetch the data itself.

Medium How would you upload a large video from a phone?

Resumable chunked upload directly to object storage with a pre-signed URL, verify checksums, then process asynchronously.

Medium What is adaptive bitrate streaming?

Video is transcoded into several renditions and cut into short segments; the player picks a rendition each segment based on measured throughput.

Advanced How do you design the API to support old app versions?

Version the API, add only optional fields, ignore unknown fields, keep behaviour for minimum supported versions, use feature flags and force upgrades only as a last resort.

Advanced How do you reduce battery drain from networking?

Batch requests, avoid polling, use push and OS-scheduled background work, compress, and respect low-power and data-saver modes.

Advanced How do you handle token storage and refresh on mobile?

Store tokens in the keychain or keystore, use short-lived access tokens with rotating refresh tokens, and handle revocation gracefully.

Advanced How do you prevent out-of-memory crashes from images?

Request right-sized images from a resizing CDN, downsample bitmaps to view size, use bounded memory and disk caches, and avoid holding full-size decoded images.

Advanced What metrics matter for mobile client observability?

Startup time, frame drops, crash-free sessions, network failures by connection type, API latency from the client and battery impact.

Advanced How do silent pushes and background sync interact?

A data push can wake the app to sync, but the OS throttles frequency and execution time, so the app must tolerate missed or delayed wake-ups.
