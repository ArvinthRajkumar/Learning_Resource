Part SD1

Back-of-the-envelope estimation

Estimation turns vague user numbers into engineering numbers. You do not need exact answers. You need the right order of magnitude, quickly, and a clear chain of assumptions.

BasicMedium~2 hours

Numbers every engineer should know

Powers of two and units

Storage and memory are counted in powers of two, but for estimates we round.

PowerExact valueApproximateName
2^101,0241 thousand1 KB

A shortcut: 1 million seconds is about 12 days, and a day has about 86,400 seconds, which we round to 10^5. Rounding 86,400 to 100,000 makes daily to per-second conversion trivial and errs by only 14%.

Time units

1 second = 1,000 ms = 1,000,000 microseconds = 1,000,000,000 ns.

Latency numbers (orders of magnitude)

These come from the well-known "latency numbers every programmer should know" list. Exact values vary by hardware and year. The ratios are what matter.

Round trip across continents100 to 150 ms

What the table teaches

  • Memory is about 100 times faster than an SSD read and about 100,000 times faster than a disk seek.
  • Sequential access is far faster than random access on every medium.
  • A network call inside a data center costs about as much as thousands of memory reads. Avoid chatty designs.
  • Crossing an ocean costs 100 ms or more, which is why we replicate data close to users and use CDNs.
  • Compression is cheap compared with network and disk time, so compress before sending large payloads.
Key idea

Keep hot data in memory, do I/O in large sequential chunks, send fewer and bigger messages, and put data near users.

How this gets asked

Which statements about latency are true? Select all.

  • A main memory read is much faster than an SSD read
  • A round trip inside one data center is cheaper than a cross-continent one
  • Random disk access is as fast as sequential access
  • Compression is usually cheap compared with network time for large payloads

Sequential access beats random access on every medium, so the third statement is false.

Self-check

Roughly how much slower is a disk seek than a memory read?

About 100,000 times (10 ms versus 100 ns).

Why is a chatty design bad?

Each network round trip inside a data center is about 0.5 ms, equal to thousands of memory reads, and across regions about 100 ms or more.

Requests per second

The basic conversion

Start from users and behaviour, end at requests per second (QPS).

Average QPS
QPS = daily active users x requests per user per day / 86,400
DAU
daily active users
requests per user
average actions per user per day
86,400
seconds in a day (round to 10^5 for speed)

Traffic is never flat. Real traffic has a daily peak. Use a peak factor of 2 to 5 times the average, and say which you chose.

Worked example: a photo-sharing app
  1. 100 million daily active users, each views 50 photos and uploads 0.2 photos per day.
  2. Reads per day = 100 M x 50 = 5 billion. Average read QPS = 5,000,000,000 / 86,400 = about 57,900.
  3. Writes per day = 100 M x 0.2 = 20 million. Average write QPS = 20,000,000 / 86,400 = about 231.
  4. Peak is 3 times the average: about 174,000 read QPS and 700 write QPS.
Read to write ratio is 250 to 1, so this is a read-heavy system that needs caching and a CDN.
dau = 100_000_000
reads_per_user, writes_per_user = 50, 0.2
sec = 86_400
read_qps = dau * reads_per_user / sec
write_qps = dau * writes_per_user / sec
print(round(read_qps), round(write_qps))
print("peak (x3):", round(read_qps * 3), round(write_qps * 3))
print("read:write =", round(read_qps / write_qps))

57870 231
peak (x3): 173611 694
read:write = 250

How this gets asked

10 million daily active users each make 20 requests a day. What is the average QPS? (round to the nearest whole number, use 86,400 seconds)

10,000,000 x 20 / 86,400 = 2,314.8, so about 2,315 requests per second.

To convert a daily total into a per second rate, divide by (use the usual rounded number of seconds in a day, 10 to the power of 5 is also fine).

A day has 86,400 seconds, often rounded to 100,000 for speed.

Self-check

Which peak factor do you use and why?

Two to five times the average, because real traffic has daily and event peaks. State the factor you chose.

Storage and bandwidth

Storage

Storage needed
storage = items per day x size per item x retention days x replication factor
replication factor
copies kept, commonly 3
Worked example: storing 5 years of tweets
  1. 500 million tweets per day. Each tweet stores about 300 bytes of text and metadata.
  2. Per day: 500 M x 300 B = 150 GB.
  3. Per year: 150 GB x 365 = about 55 TB. Five years: about 274 TB.
  4. With replication factor 3: about 820 TB.
About 0.8 PB of text storage, which tells you a single database server is not enough and you must shard.
tweets_per_day = 500_000_000
bytes_each = 300
per_day_gb = tweets_per_day * bytes_each / 1e9
per_year_tb = per_day_gb * 365 / 1e3
five_years_tb = per_year_tb * 5
print(per_day_gb, "GB/day")
print(round(per_year_tb, 1), "TB/year")
print(round(five_years_tb), "TB for 5 years")
print(round(five_years_tb * 3), "TB with 3 replicas")

Media is different

Text is tiny. Images and video dominate storage and bandwidth. Estimate them separately: average image 200 KB to 2 MB, one minute of video 10 to 100 MB depending on resolution. Large media belongs in object storage (such as S3) served through a CDN, not in a database.

Bandwidth

Bandwidth
bandwidth = QPS x average response size
ingress
data coming in (uploads)
egress
data going out (downloads), usually larger and more expensive
Worked example: outbound bandwidth
  1. 58,000 read QPS, each returns a 200 KB photo (mostly from a CDN).
  2. 58,000 x 200 KB = 11.6 GB per second = about 93 Gbps.
  3. If the CDN absorbs 95 percent, origin egress is about 4.6 Gbps.
Without a CDN you would need around ten 10 Gbps links just for egress. The CDN is not optional.

Memory for caching

The 80/20 rule says about 20 percent of items cause about 80 percent of reads. To cache the hot set, estimate 20 percent of daily unique reads x item size.

Worked example: cache size
  1. 5 billion reads per day of 1 KB metadata objects. Suppose 10 percent are unique objects: 500 million unique reads.
  2. Cache 20 percent of those: 100 million objects x 1 KB = 100 GB.
100 GB fits across a handful of cache nodes of 32 or 64 GB.

How this gets asked

1 billion records per year at 1 KB each, kept 3 years with 3 replicas. How many TB in total? (1 TB = 10^12 bytes)

1e9 x 1e3 B = 1e12 B = 1 TB per year; 3 years = 3 TB; x3 replicas = 9 TB.

Self-check

What do you multiply by for durability?

The replication factor, commonly 3, and add headroom for indexes and growth.

Availability and the nines

What a percent of uptime means

Availability = uptime / (uptime + downtime). More nines means much less allowed downtime.

Combining components

  • In series (a request needs A and B): availability multiplies. Two 99.9% parts give 99.9% x 99.9% = about 99.8%. More dependencies means less availability.
  • In parallel (either A or B can serve, with failover): failure probabilities multiply. Two 99% parts in parallel give 1 - 0.01 x 0.01 = 99.99%.
a = 0.999
series = a * a * a
parallel_two = 1 - (1 - a) ** 2
print("3 in series:", round(series * 100, 4))
print("2 in parallel:", round(parallel_two * 100, 6))

Output

3 in series: 99.7003
2 in parallel: 99.9999
Trap

Redundancy only helps if failures are independent. Two replicas in the same rack, the same power feed, or running the same buggy deploy fail together. Spread across availability zones.

How this gets asked

Two independent components, each 99.9% available, must both work for a request to succeed. The combined availability is closest to:

  • 99.99% That would require parallel redundancy.
  • 99.9% Dependencies reduce availability, not keep it.
  • 99.8% Correct.
  • 99.0% Too pessimistic.

In series availability multiplies: 0.999 x 0.999 = 0.998.

How many minutes of downtime per year does 99.99% allow? (round to the nearest minute)

0.0001 x 525,600 minutes = 52.56 minutes, about 53.

Self-check

How do you compute availability for components in series and in parallel?

Series multiplies availabilities. Parallel multiplies failure probabilities, then subtracts from 1, assuming independent failures.

Doing a full estimate

A reusable template

  1. State assumptions and round them.
  2. Users to QPS (average, then peak).
  3. Payload sizes to bandwidth.
  4. Items to storage (with retention and replication).
  5. Hot set to cache memory.
  6. Compare with single-machine capacity and decide: one box, replicas, shards?
Worked example: URL shortener
  1. 100 million new URLs per month, redirects are 100 times writes.
  2. Write QPS = 100 M / (30 x 86,400) = about 39. Read QPS = 39 x 100 = about 3,900.
  3. Record size is 500 bytes (short key, long URL, metadata). Ten years: 100 M x 12 x 10 = 12 billion records x 500 B = 6 TB.
  4. Peak 3x: about 12,000 read QPS. A cache with 20 percent of daily reads (about 340 M reads per day, 20 percent hot) needs about 34 GB of 500 byte entries.
Reads fit on a few replicas plus a cache, and 6 TB fits on one modern database, so sharding is optional but replication and a cache are needed.
new_per_month = 100_000_000
write_qps = new_per_month / (30 * 86_400)
read_qps = write_qps * 100
records_10y = new_per_month * 12 * 10
storage_tb = records_10y * 500 / 1e12
reads_per_day = read_qps * 86_400
cache_gb = reads_per_day * 0.2 * 500 / 1e9
print(round(write_qps), round(read_qps))
print(records_10y, round(storage_tb, 1), "TB")
print(round(reads_per_day / 1e6), "M reads/day;", round(cache_gb), "GB cache")

Output

39 3858
12000000000 6.0 TB
333 M reads/day; 33 GB cache

Tips

  • Say numbers out loud and round aggressively (86,400 to 10^5, 30 days to a month).
  • Label every number with its unit.
  • A wrong constant is fine if the logic is right and you state it.
  • Always finish by comparing to capacity: the point of estimating is the decision it supports.

How this gets asked

Your estimate shows 1 TB of data and 2,000 read QPS. What is the most reasonable starting design?

  • 100 shards with a global lock Absurd for this size.
  • One primary database with replicas and a cache Correct.
  • A custom storage engine Never first.
  • Move all data into memory 1 TB in RAM is possible but needlessly costly.

The numbers are small. Start simple and scale only when a number demands it.

Interview questions: Estimation

9 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Estimate the QPS of a service with 10 million daily active users each making 20 requests a day.

10 M x 20 = 200 M requests per day, divided by 86,400 seconds gives about 2,300 average QPS. With a peak factor of 3 that is about 7,000 QPS.

Basic How many seconds are in a day, and what do you use in estimates?

86,400. Round to 100,000 (10^5) to simplify, accepting about 14 percent error.

Basic What is 2^10, 2^20, 2^30, 2^40?

About a thousand (KB), a million (MB), a billion (GB), a trillion (TB).

Medium Compare memory, SSD and disk latencies.

Main memory about 100 ns, SSD random read about 100 microseconds (1,000 times slower), spinning disk seek about 10 ms (100,000 times slower than memory). Sequential access is far faster than random on all of them.

Medium How do you estimate storage for five years of data?

Items per day x size per item x 365 x 5 x replication factor, plus headroom for indexes and growth. Estimate media separately from text.

Medium What does 99.99 percent availability allow?

About 52 minutes of downtime per year, 4.4 minutes per month.

Medium How do you estimate cache size?

Take the hot set, often 20 percent of daily unique items, multiplied by item size, then add overhead. Check the expected hit rate against the load the database can take.

Advanced Two services in series each have 99.9 percent availability. What is the total, and how do you improve it?

About 99.8 percent. Improve with redundancy (parallel replicas across failure domains), fewer synchronous dependencies, caching and graceful degradation, remembering failures must be independent.

Advanced How do you sanity-check an estimate?

Compare with a known system, with single-machine capacity (does one box handle it?), and with unit costs. If the result implies absurd hardware, revisit assumptions.
