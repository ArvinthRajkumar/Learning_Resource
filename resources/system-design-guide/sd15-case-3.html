Case studies 3: video streaming, file sync, ride sharing, ticket booking, payments

These cases add hard constraints: huge media bandwidth, many devices staying in sync, real-time location, scarce inventory and money. Each shows which part of the toolbox the constraint pulls into the design.

Advanced~4.5 hours

Case 1: Video streaming (YouTube or Netflix)

Requirements

Users upload videos; millions watch with smooth playback on any device and network; search and recommendations exist but focus on upload, transcoding and delivery.

Estimates

500 hours of video uploaded per minute is 30,000 hours per hour. Raw uploads are large: 1 hour at 1080p is about 3 GB. Assume 10 million daily uploads of 5 minutes at 100 MB raw: 1 PB per day raw. Viewing is far larger: 1 billion hours watched per day at an average 3 Mbps is about 1.35 EB of egress per day, so delivery must come from CDNs, and storage keeps several renditions per video.

hours_per_day = 1_000_000_000
mbps = 3
bytes_per_hour = mbps * 1e6 / 8 * 3600
total_pb = hours_per_day * bytes_per_hour / 1e15
print(round(bytes_per_hour / 1e9, 2), "GB per hour watched;", round(total_pb), "PB per day egress")
print(round(total_pb * 8 / 86_400 * 1000), "Tbps average")

Output

1.35 GB per hour watched; 1350 PB per day egress
125 Tbps average

Upload and processing pipeline

  1. The client asks the API for an upload and receives a presigned URL, then uploads the file in resumable chunks straight to object storage (never through app servers).
  2. A completion event goes to a queue. A workflow splits the video into segments (about 2 to 10 seconds, at keyframes).
  3. Workers transcode segments in parallel into several resolutions and bitrates (240p to 4K) and codecs (H.264, VP9, AV1), plus audio tracks, thumbnails and captions.
  4. Segments and manifest files are written to storage, metadata is updated, and the video is marked ready.

Parallel segment transcoding makes a 2 hour film process in minutes. Use a DAG workflow engine so a failed segment is retried alone.

Playback: adaptive bitrate streaming

The video is stored as short segments at several quality levels. A manifest (HLS .m3u8 or MPEG-DASH .mpd) lists them. The player downloads segments over plain HTTP, measures throughput and buffer level, and switches rendition between segments: higher quality when the network is good, lower when it drops. This avoids stalls and lets plain CDNs serve the content, since segments are ordinary cacheable files.

Delivery

  • CDN with multi-tier caching. Popular content is cached at edge locations; long-tail content falls back to regional or origin caches.
  • Large providers place cache appliances inside ISPs (Netflix Open Connect), moving traffic off the internet backbone.
  • Pre-position (push) popular new releases to edges overnight.
  • Choose segment size as a trade-off: shorter segments adapt faster but add request overhead.

Metadata and search

Metadata (title, owner, counts) in a sharded relational or NoSQL store with caches. View counts are high-write: aggregate in a stream and flush in batches. Search uses an inverted index (SD12); recommendations are a separate ML pipeline.

Trade-offs

Storage grows with every rendition, so use cold storage for rarely watched videos and encode extra renditions only after a video becomes popular. Protect content with signed URLs and DRM where needed.

How this gets asked

How does adaptive bitrate streaming avoid stalls?

  • It uploads faster No.
  • Segments exist at several quality levels and the player switches between segments based on bandwidth Correct.
  • It uses UDP only No.
  • It stores one big file No.

The manifest lists renditions and the player picks per segment.

Why are uploads sent directly to object storage with presigned URLs?

  • To avoid HTTPS No.
  • To keep huge files off the application servers Correct.
  • To skip transcoding No.
  • To avoid metadata No.

App servers would otherwise become a bandwidth bottleneck.

Self-check

Why CDN and segments?

Segments are cacheable HTTP files, so CDNs serve them near users and the player adapts quality per segment.

Case 2: File storage and sync (Dropbox or Google Drive)

Requirements

Store files, sync them across devices automatically, share folders, keep version history, work offline and resolve conflicts. Files can be large; changes are usually small.

Key idea: blocks

Split each file into fixed or content-defined blocks (for example 4 MB). Give each block a hash. A file is an ordered list of block hashes.

Benefits:

  • Delta sync: after an edit only changed blocks are uploaded.
  • Deduplication: blocks with an existing hash are not stored again, saving large amounts across users.
  • Resumable uploads and parallel transfer.
  • Version history is just a list of block hashes per version.
import hashlib
def blocks(data, size=4):
    return [data[i:i + size] for i in range(0, len(data), size)]
def hashes(data):
    return [hashlib.sha1(b).hexdigest()[:6] for b in blocks(data)]
v1 = b"AAAABBBBCCCCDDDD"
v2 = b"AAAABBBBXXXXDDDD"          # only the third block changed
h1, h2 = hashes(v1), hashes(v2)
print(h1)
print(h2)
print("blocks to upload:", [i for i, (a, b) in enumerate(zip(h1, h2)) if a != b])

Output

['e25121', '4c55e5', '56900f', '4c4518']
['e25121', '4c55e5', 'e3a880', '4c4518']
blocks to upload: [2]

Architecture

Sync flow

  1. A client watcher detects a local change, splits the file, hashes blocks.
  2. It asks the block service which hashes are missing and uploads only those.
  3. It sends a commit to the metadata service with the new block list. The service writes a new version atomically and emits an event.
  4. The notification service tells other devices (long poll or push). They fetch the metadata change, download missing blocks and reassemble.

Conflicts

Two devices edit the same file offline. Detect with a base version check on commit: if the server's current version differs from the base, the commit conflicts. Typical resolution: keep both and rename one ("file (conflicted copy)"). Documents with real-time collaboration use operational transformation or CRDTs instead (SD16).

Other concerns

Metadata needs strong consistency (relational, ACID) because of the folder tree and permissions. Blocks are immutable and eventually replicated. Encrypt blocks at rest, optionally client-side. Trash and retention windows. Sharing via ACLs. Large per-user quotas tracked in the metadata store.

How this gets asked

A 100 MB file changes in one 4 MB block. How much is uploaded with block-based delta sync?

  • 100 MB That is a full upload.
  • About 4 MB Correct.
  • 0 MB The change must be sent.
  • 400 MB No.

Only blocks whose hash changed are transferred.

Self-check

What are the benefits of blocks and hashes?

Delta sync, deduplication, resumable parallel transfer and cheap versioning.

Case 3: Ride sharing (Uber or Lyft)

Requirements

Riders request a ride from their location; the system finds nearby available drivers, matches one, shows the driver's live location and ETA, tracks the trip and computes the fare. Low latency matching, high availability, live location updates.

Estimates

1 million concurrent drivers each sending a location update every 4 seconds is 250,000 writes per second. Updates are small (50 bytes) but frequent, and only the latest position matters, so keep it in memory rather than a durable log.

Location indexing

Divide the map into cells with a geospatial index (geohash, S2, H3) and keep, per cell, the set of available drivers. A ride request looks up the rider's cell plus neighbouring cells and ranks nearby drivers.

Matching

  1. Find candidate drivers in the rider's cell and its neighbours, widening the radius if few are found.
  2. Rank by estimated time of arrival using a routing service, not straight-line distance.
  3. Offer the trip to the best driver with a short timeout (about 10 to 15 seconds). If declined or timed out, offer to the next. Mark the driver reserved so two riders are not matched to one driver (atomic state change in the location store).
  4. On acceptance, create the trip and stream live updates.

Live tracking

The driver's updates go to the location service. The rider's app subscribes to its trip's updates through a WebSocket gateway or push. Throttle updates (every 4 seconds, more often near pickup). Persist a downsampled breadcrumb trail for fare and dispute purposes.

Trip state machine

requested -> matched -> driver_arriving -> in_progress -> completed (or cancelled). Keep transitions in a strongly consistent store, publish each change as an event for pricing, notifications, analytics and payments. The fare combines route distance, time and dynamic (surge) pricing computed from supply and demand per cell.

Scaling

Shard the location service by cell (consistent hashing over geographic cells), so a city's traffic is spread but a cell's data is local. Hot cells (airports, events) may need finer cells. Keep matching regional; one region failing should not affect another.

How this gets asked

How are nearby drivers found quickly?

  • Scan all drivers Too slow.
  • A geospatial index (geohash, S2, H3) with drivers grouped per cell Correct.
  • Sort by name No.
  • Ask riders No.

Look up the rider's cell and its neighbours, then rank by ETA.

Self-check

How do you prevent matching one driver to two riders?

Atomically reserve the driver in the location store at offer time.

Case 4: Ticket booking (concerts, flights)

Requirements

Users browse events, pick seats, and pay. Never sell the same seat twice. Traffic spikes enormously when popular tickets open (hundreds of thousands arrive in seconds for a few thousand seats).

The core problem: contention on scarce inventory

Selling means "check the seat is free, then mark it sold". Without protection, two buyers both see it free and both succeed. This is the lost update problem (SD6).

A seat reservation flow

available -> held (with expiry) -> sold, and back to available when a hold expires.

  1. Hold: when the user selects a seat, atomically move it from available to held with an expiry (for example 10 minutes).
  2. User pays within the hold window. Payment is initiated with an idempotency key.
  3. Confirm: on payment success move the seat to sold. On timeout a sweeper (or lazy check) releases it.
import sqlite3, time
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE seats (id INTEGER PRIMARY KEY, status TEXT, held_by TEXT, hold_until REAL)")
db.execute("INSERT INTO seats VALUES (1, 'available', NULL, NULL)")

def hold(seat, user, now, ttl=600):
    # one atomic statement: succeeds only if the seat is available or its hold expired
    cur = db.execute("""UPDATE seats SET status='held', held_by=?, hold_until=?
                        WHERE id=? AND (status='available' OR (status='held' AND hold_until < ?))""",
                     (user, now + ttl, seat, now))
    return cur.rowcount == 1

print("alice:", hold(1, "alice", now=0))
print("bob  :", hold(1, "bob", now=100))        # still held by alice
print("bob after expiry:", hold(1, "bob", now=700))

Output

alice: True
bob  : False
bob after expiry: True

The conditional UPDATE ... WHERE is atomic, so exactly one buyer wins. This is optimistic concurrency. Alternatives: SELECT ... FOR UPDATE row locks, or a Redis SET seat NX EX hold.

Handling the stampede

  • Virtual waiting room: put users in a queue and admit them at the rate the booking service can handle. This protects the system and is fair.
  • Static pages and event data through a CDN; only the booking path hits the core.
  • Rate limit per user and block bots (CAPTCHA, proof of work, purchase limits per account).
  • Scale reads (seat maps) with caches, and let the seat map be slightly stale: the atomic hold is the source of truth, and a failed hold simply asks the user to pick another seat.
  • Partition inventory by event so one popular event does not slow others.

Payment and failure cases

Payment can succeed after the hold expired, or the confirmation message can be lost. Use idempotent payment calls, a reconciliation job that compares payments with orders, and automatic refunds for orders that cannot be fulfilled. Keep the order as a state machine (pending, paid, confirmed, refunded).

How this gets asked

Two buyers click the last seat at the same moment. What guarantees only one succeeds?

  • A cache Does not serialise writes.
  • An atomic conditional update (or row lock) on the seat Correct.
  • Two retries No.
  • Larger servers No.

UPDATE ... WHERE status = available changes at most one row for one buyer.

Self-check

What is a waiting room?

A queue that admits users at a sustainable rate during a ticket-sale spike.

Case 5: Payment system

Requirements

Accept payments, pay out to sellers, support refunds, integrate with card networks and banks through a payment service provider (PSP), and above all never lose or duplicate money. Correctness and auditability matter more than raw speed.

Estimates

1 million transactions per day is only about 12 per second. The challenge is not volume but correctness, security and reliability of each one.

The flow

Principles

  • Idempotency keys on every payment request (SD8). A retry returns the stored result, not a second charge.
  • State machine for each payment (created, authorised, captured, failed, refunded). Only allowed transitions, each persisted before side effects.
  • Never store raw card numbers. Use the PSP's hosted fields or tokenisation, so you stay out of the heaviest PCI DSS scope. Store tokens.
  • Double-entry ledger: every movement is recorded as two entries, a debit and a credit, which always sum to zero. The ledger is append-only; errors are corrected with new entries, never edits. Balances are derived from entries.
  • Webhooks and asynchronous results: the PSP may confirm later. Verify signatures, dedupe by event id, and make handlers idempotent.
  • Timeouts are unknown outcomes: if a call to the PSP times out you do not know whether it charged. Query the PSP by your idempotency key or reference rather than retrying blindly.
  • Reconciliation: a daily job compares your records with the PSP and bank settlement files and flags mismatches. This is how real systems catch bugs.
# Double-entry: every transfer is a debit and an equal credit; the ledger always balances.
ledger = []
def transfer(src, dst, amount, ref):
    ledger.append((ref, src, -amount))
    ledger.append((ref, dst, +amount))
transfer("customer", "merchant", 100, "pay-1")
transfer("merchant", "customer", 30, "refund-1")
balances = {}
for ref, acct, amt in ledger:
    balances[acct] = balances.get(acct, 0) + amt
print(balances, "sum =", sum(balances.values()))

Output

{'customer': -70, 'merchant': 70} sum = 0

Consistency and transactions

Use a relational database with ACID transactions for the payment and ledger records. Cross-service workflows (order, inventory, payment) use sagas with compensations (refund) and the outbox pattern (SD6, SD8). Choose consistency over availability: it is better to reject a payment than to charge twice.

Security and compliance

Encrypt in transit and at rest, restrict access, audit every action, tokenise cards, use fraud detection (rules plus ML scoring) before capture, and follow PCI DSS and strong customer authentication (3-D Secure) requirements.

How this gets asked

A call to the payment provider times out. What should you do?

  • Retry immediately with a new request May double charge.
  • Query the provider for the outcome using your idempotency key or reference, then act Correct.
  • Assume failure May lose a charge record.
  • Assume success May give goods for free.

A timeout is an unknown outcome; resolve it rather than guess.

In a double-entry ledger, what is always true?

  • Debits exceed credits No.
  • The sum of all entries is zero Correct.
  • Entries may be edited Append-only: use correcting entries.
  • Balances are stored only as totals Derive from entries.

Every transfer is a debit and an equal credit, so the ledger balances.

Self-check

List the payment safety principles.

Idempotency keys, state machine, tokenised cards, append-only double-entry ledger, reconciliation, resolve unknown outcomes.

Medium Design video streaming: how does playback adapt to bandwidth?

Videos are transcoded into segments at several bitrates with a manifest; the player downloads segments over HTTP via a CDN and switches rendition per segment based on throughput and buffer.

Medium How do you speed up video processing?

Split into segments, transcode in parallel with a workflow engine, retry failed segments independently and write outputs to object storage.

Medium Design Dropbox: how do you sync large files efficiently?

Block-level chunking with hashes gives delta sync and deduplication; metadata in a relational store; clients notified of changes and conflicts resolved with versions.

Medium What is a double-entry ledger?

Each movement of money is two entries, a debit and a credit, summing to zero. Entries are append-only and balances are derived, giving auditability.

Advanced Design Uber: how do you match riders and drivers?

Maintain driver locations in a geospatial index in memory, query nearby cells, rank by ETA, reserve the driver atomically, and track the trip with a state machine.

Advanced Design ticket booking: how do you avoid double booking?

Atomic conditional updates or row locks on seats, a hold with expiry, a payment step and a waiting room to absorb spikes.

Advanced Design a payment system.

Idempotency keys, a payment state machine, tokenised cards via a PSP, a double-entry append-only ledger, webhook handling and reconciliation, with strong consistency.

Advanced A payment provider call times out. What now?

Treat the outcome as unknown: query the provider using the idempotency key or reference, then proceed. Never blindly retry with a new request.
