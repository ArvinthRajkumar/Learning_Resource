Case studies 2: news feed, chat, notifications, typeahead, web crawler

These designs revolve around fan-out: one event needs to reach many people or many places. Each case shows how the answer changes with the numbers, such as follower counts, online users and crawl frontier size.

Advanced~4.5 hours

Case 1: News feed

Requirements

  • Functional: users post; users follow others; a user sees a feed of recent posts from people they follow, newest or ranked first; feed supports pagination.
  • Non-functional: feed loads in under 200 ms; new posts appear within seconds; highly available; eventual consistency is fine.

Estimates

300 million daily active users, each opens the feed 10 times a day and posts 0.5 times. Feed reads: 3 billion per day, about 35,000 per second (about 100,000 peak). Posts: 150 million per day, about 1,700 per second. Average user follows 200 accounts. Reads dominate by 20 to 1, so make reads cheap.

The central question: fan-out

Fan-out on read (pull): when a user opens the feed, fetch recent posts from everyone they follow, merge, sort. Cheap writes, expensive reads (200 lookups per feed).

Fan-out on write (push): when a user posts, push the post id into the precomputed feed list of every follower. Reads become one lookup, writes cost one insert per follower.

Fan-out on readFan-out on write
Read costHigh (merge many sources)Very low (one list)
Write costOne insertOne insert per follower
StoragePosts onlyPosts plus feed lists
ProblemSlow feedsThe celebrity problem: 50 million followers means 50 million inserts per post
FreshnessAlways currentSlight delay while fan-out completes

Hybrid (what real systems do): push for normal users, pull for celebrities. At read time merge the precomputed feed with recent posts from the few celebrities the user follows.

from collections import defaultdict
followers = {"alice": ["bob", "carol"], "star": ["bob", "carol", "dave"]}
CELEB = 2                       # followers above this count are not pushed
feeds = defaultdict(list)       # precomputed feed list per user (post ids, newest last)
posts, celeb_posts = {}, defaultdict(list)

def post(author, pid, ts):
    posts[pid] = (author, ts)
    if len(followers.get(author, [])) > CELEB:
        celeb_posts[author].append(pid)          # pull later
    else:
        for f in followers.get(author, []):
            feeds[f].append(pid)                 # push now

def read_feed(user, follows_celebs):
    ids = list(feeds[user])
    for c in follows_celebs:
        ids += celeb_posts[c]
    return sorted(ids, key=lambda p: -posts[p][1])

post("alice", "p1", 1); post("star", "p2", 2); post("alice", "p3", 3)
print(read_feed("bob", ["star"]))

Output

['p3', 'p2', 'p1']

High-level design

Deep dives

  • Storage: posts in a sharded store keyed by post_id (Snowflake ids sort by time). The follower graph in a store that supports "followers of X" and "followed by X" (two denormalised tables or a graph store). Feed lists in Redis as sorted sets scored by time, capped to the latest 500 to 1,000 ids.
  • Hydration: the feed holds only ids; the API fetches post content, author and counters from caches in batch (MGET).
  • Ranking: sort by time first; later add a ranking service using engagement signals and a machine learning model.
  • Pagination: cursor on post id or timestamp, not offsets, so new posts do not shift pages.
  • Inactive users: do not push to users who have not logged in for 30 days; build their feed on demand.
  • Deletions and blocks: filter at read time, because removing from millions of lists is costly.
  • Counters (likes, comments) are updated asynchronously and cached.

How this gets asked

What is the celebrity problem in fan-out on write?

  • Celebrities post too rarely No.
  • A post by a user with tens of millions of followers causes tens of millions of inserts Correct.
  • Celebrity feeds are encrypted No.
  • They cannot be cached No.

Use a hybrid: push for normal users, pull and merge at read time for celebrities.

The feed list stores only post ids. Why?

  • Ids are secret No.
  • Keeps the feed small; content is hydrated from caches in batch and stays up to date Correct.
  • Databases cannot store text They can.
  • To avoid pagination No.

Duplicating full posts in every feed would multiply storage and make edits and deletes expensive.

Self-check

Fan-out on write versus read?

Write pushes ids to followers' feeds (fast reads, costly writes); read merges at request time (cheap writes, slow reads). Hybrid handles celebrities.

Case 2: Chat system

Requirements

One-to-one and group chat (up to 500 members), delivery in near real time, message history, online presence, push notifications for offline users, multi-device sync, ordering within a conversation, messages are not lost.

Estimates

50 million daily users, 40 messages per user per day: 2 billion messages per day, about 23,000 per second (70,000 peak). Messages of 100 bytes: 200 GB per day, 73 TB per year. Concurrent connections about 10 million, so connection servers matter.

Transport

Use WebSocket for a persistent two-way connection; fall back to long polling. A connection (gateway) server holds each user's socket. Each server can hold about 50,000 to 100,000 connections, so 10 million concurrent users need a few hundred gateway servers.

Message flow (one-to-one)

  1. A sends the message through gateway 1 with a client-generated message id (for idempotency).
  2. The chat service assigns a sequence number within the conversation, persists the message, and acknowledges to A.
  3. It looks up B's gateway in the registry. If B is online, deliver through gateway 2; B's client acks.
  4. If B is offline, store it as undelivered and send a push notification; B syncs missed messages on reconnect, using "give me messages after sequence N".

Ordering and ids

Order messages per conversation, not globally. Use a per-conversation sequence number (a counter owned by the partition for that conversation) or a time-ordered id. Clients display by sequence and detect gaps to request missing ones. Assign ids on the server, since client clocks lie.

Storage

Access pattern: "latest N messages of a conversation". Use a wide-column store (Cassandra, HBase) with partition key = conversation id and clustering key = message id descending. Keep a separate table of each user's conversation list. Old messages can move to cheaper storage.

Group chat

Fan-out per member: for small groups, deliver to each member's gateway; for large channels use pub/sub topics per group and have gateways subscribe on behalf of connected members. Store the message once, with delivery state per member only when needed.

Presence

Track online status with heartbeats from the client every few seconds stored in Redis with a TTL. A missing heartbeat expires the key and the user shows offline. For large friend lists, avoid broadcasting every change: fetch presence lazily when a chat is opened or subscribe only to visible contacts.

Other concerns

Delivery receipts (sent, delivered, read), end-to-end encryption (keys on devices), media via object storage with presigned URLs, rate limiting against spam, multi-device sync (each device has its own cursor).

How this gets asked

Why use a per-conversation sequence number rather than client timestamps for ordering?

  • Timestamps are too long No.
  • Client clocks are unreliable and a server-assigned sequence gives a total order per conversation Correct.
  • Sequence numbers are faster to type No.
  • Timestamps cannot be stored No.

Clocks differ and drift, so ordering must come from a single owner of the conversation.

One gateway server holds 50,000 connections. How many servers for 10 million concurrent connections?

10,000,000 / 50,000 = 200 servers (plus headroom).

Self-check

How does a message reach an online and an offline user?

Online: delivered through the user's gateway found via the session registry. Offline: stored, push notification sent, synced on reconnect by sequence.

Case 3: Notification system

Requirements

Send push, SMS and email notifications for events (promotions, alerts, receipts), respecting user preferences, at high volume, reliably, with no duplicates, and with rate limits and quiet hours.

Estimates

10 million notifications per day typical, with bursts of millions in minutes (a flash sale). Third-party providers (APNs, FCM, SMS gateways, email providers) are slow and rate-limited, so queues are essential.

Design

StepResponsibility
Intake APIAuthenticate, validate, idempotency key to avoid duplicates
Preferences and policyOpt-outs, channel choice, quiet hours, frequency caps, localisation
TemplatingFill templates with data, per language
RoutingPut a job on the right channel queue with priority (OTP codes high, marketing low)
WorkersCall the provider with retries and backoff, rate limited to provider quotas
TrackingRecord sent, delivered, opened, failed; handle provider callbacks and bounces

Deep dives

  • Reliability: at-least-once from queues plus idempotent sends (dedupe on notification id) for effectively once. DLQ for permanent failures.
  • Priorities: separate queues or priority levels so a marketing blast never delays one-time passwords.
  • Rate limits: per-provider and per-user throttles; spread a campaign over time (jittered scheduling).
  • Providers: abstract behind an interface and fail over between vendors.
  • Scheduling: a scheduler stores future jobs (sorted by time) and enqueues them when due.
  • Unsubscribe and compliance: honour opt-out immediately, store consent, include required footers.

How this gets asked

Why give each channel its own queue and worker pool?

  • To use more queues Not a goal.
  • A slow or failing provider cannot block other channels, and each can scale and rate-limit independently Correct.
  • Because SMS needs TLS No.
  • To avoid templates No.

Isolation (a bulkhead) keeps one provider outage from stalling everything.

Self-check

How do you avoid duplicate notifications?

Idempotency keys at intake, at-least-once queues with deduplication on notification id before sending.

Case 4: Typeahead (autocomplete)

Requirements

As the user types a prefix, show the top 5 to 10 suggested queries in under 100 ms, ranked by popularity and recency, updated over time.

Estimates

5 billion searches per day, each typed with about 4 requests, so tens of billions of suggestion requests: about 230,000 per second, 700,000 at peak. Latency is the main challenge, so everything is cached or in memory.

Data structure: trie with top-k at each node

A trie stores queries character by character. Store at each node the precomputed top K completions, so a lookup walks the prefix (O(length)) and returns the stored list, with no subtree scan.

import heapq
class Trie:
    def __init__(self, k=3):
        self.k, self.root = k, {}
    def add(self, query, count):
        node = self.root
        for ch in query:
            node = node.setdefault(ch, {})
            top = node.setdefault("#", [])
            top.append((count, query))
            top.sort(reverse=True)
            del top[self.k:]
    def suggest(self, prefix):
        node = self.root
        for ch in prefix:
            if ch not in node: return []
            node = node[ch]
        return [q for c, q in node.get("#", [])]

t = Trie()
for q, c in [("system design", 90), ("system", 60), ("sql join", 80), ("sql index", 40), ("syntax", 10)]:
    t.add(q, c)
print(t.suggest("sy"), t.suggest("sql"), t.suggest("z"))

Output

['system design', 'system', 'syntax'] ['sql join', 'sql index'] []

Architecture

  • Read path (fast): the client sends the prefix after a short debounce (about 100 to 200 ms of typing pause), cancels outdated requests, and caches results. A CDN or edge cache serves popular prefixes. Trie servers keep the structure in memory, sharded by prefix range.
  • Write path (slow): do not update the trie on every search. Log queries, aggregate counts per hour or day with a batch or stream job, rebuild the top-k trie, and swap it in atomically (blue/green data).
  • Freshness: add a small recent-trending overlay computed from a stream with time-decayed counts.
  • Filtering: remove offensive or illegal suggestions before serving.
  • Personalisation and language: separate tries per language or locale, a small personal layer from history.

How this gets asked

How do you serve suggestions in under 100 ms at 700,000 requests per second?

  • Query the database for each keystroke Too slow.
  • Precompute top-k at each trie node, keep it in memory, cache and debounce on the client Correct.
  • Sort the full query log per request Too slow.
  • Use SMS No.

Precomputation and caching turn each request into a prefix lookup.

Self-check

What do you store at each trie node?

The precomputed top K completions for that prefix.

Case 5: Web crawler

Requirements

Crawl billions of pages, discover new URLs by following links, store content for indexing, be polite (obey robots.txt, rate limits per host), avoid duplicates and traps, and be able to recrawl for freshness.

Estimates

1 billion pages per month: about 400 pages per second. At 100 KB average per page: 100 TB per month raw (less if compressed). Downloading dominates time, so crawl in parallel across many workers.

Components

The URL frontier

A queue of URLs to fetch with two jobs:

  • Priority: crawl important or frequently changing pages first (PageRank-like score, change rate).
  • Politeness: never hammer one host. Keep one queue per host and a rule that only one worker takes from a host at a time with a delay between requests (respect Crawl-delay).

Avoiding duplicates

  • URL dedupe: normalise URLs (lowercase host, remove fragments, sort query parameters, resolve relative links) and keep a set of seen URLs. Billions of URLs are too many for a plain set in memory, so use a Bloom filter in front of a disk-backed store.
  • Content dedupe: hash page content (or use SimHash for near-duplicates) so mirrors are stored once.
  • Spider traps (infinitely generated URLs such as calendars): cap depth, URL length and pages per host.

Other concerns

robots.txt caching, DNS caching (DNS is a bottleneck), handling timeouts and slow servers, recrawl scheduling by change frequency, rendering JavaScript pages (headless browsers are expensive: use selectively), and checkpointing the frontier so a crash does not lose progress. Distribute by hashing the host so each worker owns a set of hosts, which makes politeness local.

How this gets asked

Why keep one frontier queue per host?

  • To store more URLs No.
  • To enforce politeness: rate limit requests per host Correct.
  • To encrypt URLs No.
  • To avoid DNS No.

A per-host queue lets one worker pace requests to each site.

Self-check

How do you avoid re-crawling the same URL?

Normalise URLs and check a Bloom filter backed by a persistent seen-set; hash content to dedupe mirrors.

Interview questions: Case studies 2

8 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic News feed: fan-out on read or write?

Write fan-out gives fast reads for most users; read fan-out avoids huge write amplification for celebrities. Use a hybrid.

Medium How do you store and paginate a feed?

Store post ids in per-user sorted sets (capped), hydrate content from caches in batch, and paginate with a cursor on id or time.

Medium Design chat: how are messages delivered and ordered?

Persistent WebSocket gateways with a session registry, messages persisted and sequenced per conversation, push for offline users, clients sync by last sequence.

Medium Design a notification system.

Intake API with idempotency, preference and template services, per-channel queues and worker pools with provider rate limits, retries, DLQs, priorities and delivery tracking.

Medium Design typeahead.

A trie with precomputed top-k per node served from memory and caches, rebuilt periodically from aggregated query logs, with client debouncing and a trending overlay.

Advanced How do you implement presence at scale?

Client heartbeats set a TTL key in Redis; absence means offline. Fetch or subscribe only for visible contacts to avoid broadcast storms.

Advanced Design a web crawler.

A prioritised URL frontier with per-host queues for politeness, distributed fetchers, DNS and robots caches, URL dedupe with a Bloom filter, content hashing, trap limits and recrawl scheduling.

Advanced How do you prevent a crawler from overloading a site?

One queue per host, a minimum delay between requests, obey robots.txt and Crawl-delay, and assign hosts to workers by hash so politeness is local.
