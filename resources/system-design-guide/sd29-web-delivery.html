Web delivery: HTTP caching, TLS, CDNs, real-time connections and client performance

A fast backend can still feel slow if the path to the user is slow. This part follows a request from the address bar to your servers and back, explains what each hop costs, and shows how caching and connection reuse remove most of that cost.

MediumAdvanced~4 hours

The life of a request

When someone opens https://shop.example.com/:

Round trips dominate for far-away users. With a 100 ms round trip, a fresh HTTPS connection costs roughly: DNS 1 RTT, TCP 1 RTT, TLS 1.3 1 RTT, then the request 1 RTT: about 400 ms before the first byte arrives, even if the server answers instantly.

def first_byte_ms(rtt, dns=1, tcp=1, tls=1, request=1, server=20, reuse=False):
    rtts = request if reuse else dns + tcp + tls + request
    return rtts * rtt + server
for rtt in (10, 50, 100, 250):
    print(f"RTT {rtt:>3} ms: cold connection {first_byte_ms(rtt):>5} ms | reused connection {first_byte_ms(rtt, reuse=True):>4} ms | TLS 1.2 (2 RTTs) cold {first_byte_ms(rtt, tls=2):>5} ms")

Output

RTT  50 ms: cold connection   220 ms | reused connection   70 ms | TLS 1.2 (2 RTTs) cold   270 ms
RTT 100 ms: cold connection   420 ms | reused connection  120 ms | TLS 1.2 (2 RTTs) cold   520 ms
RTT 250 ms: cold connection  1020 ms | reused connection  270 ms | TLS 1.2 (2 RTTs) cold  1270 ms

Ways to shave the path: put content near users (CDN), keep connections alive and multiplexed (HTTP/2, HTTP/3), use TLS 1.3 and session resumption, preconnect hints, and fewer, smaller responses.

How this gets asked

With a 100 ms RTT, a cold HTTPS connection with TLS 1.3 and instant server takes about how many round trips before the first response byte arrives (DNS, TCP, TLS, request)?

One round trip each: DNS, TCP, TLS 1.3 and the request.

Self-check

Name the round trips on a cold HTTPS request.

DNS lookup, TCP handshake, TLS handshake, then the HTTP request itself.

DNS

DNS maps names to IP addresses through a hierarchy: resolver, root, TLD (.com), then your authoritative servers. Answers are cached for the record's TTL. Record types: A/AAAA (IPv4/IPv6), CNAME (alias), MX (mail), TXT (verification), NS (delegation).

Design uses of DNS: geographic or latency-based routing, weighted records for gradual migrations, failover with health checks. The catch: TTLs make changes slow, and some resolvers ignore low TTLs, so DNS is a coarse tool for failover. Anycast (the same IP announced from many places) sends users to the nearest site and is how CDNs and public resolvers (1.1.1.1, 8.8.8.8) work.

TLS in two minutes

TLS gives encryption, integrity and server authentication. In the handshake the server presents a certificate signed by a trusted authority; the client verifies it, both sides agree on a shared key using ephemeral Diffie-Hellman (giving forward secrecy: stealing the server key later does not decrypt recorded traffic), and then the rest of the conversation uses fast symmetric encryption (AES-GCM or ChaCha20).

  • TLS 1.3 needs one round trip (and zero for resumed sessions with 0-RTT, which has replay risks).
  • Terminate TLS at the load balancer or CDN edge and use TLS (or mTLS) inside the network too.
  • HSTS tells browsers to use HTTPS only; certificate transparency and short-lived certificates (Let's Encrypt, automatic renewal) limit mis-issuance and expiry outages. An expired certificate is a classic outage, so automate and monitor renewal.

How this gets asked

What does forward secrecy provide?

  • Faster handshakes No.
  • Stolen long-term keys cannot decrypt previously recorded sessions Correct, because session keys are ephemeral.
  • No certificates are needed No.
  • Free bandwidth No.

Ephemeral Diffie-Hellman keys are discarded after the session.

HTTP caching: the cheapest speed-up

The fastest request is the one that never leaves the browser. HTTP caching is controlled by response headers.

HeaderMeaning
Cache-Control: max-age=3600Fresh for one hour; use without asking the server
Cache-Control: no-cacheMay store, but must revalidate before each use
Cache-Control: no-storeNever store (sensitive data)
Cache-Control: public / privateShared caches (CDN) may store / only the user's browser may
Cache-Control: s-maxage=...Lifetime for shared caches only
stale-while-revalidate=60Serve stale content while refreshing in the background
ETag: "abc123"Opaque version tag of the content
Last-ModifiedTimestamp of last change
Vary: Accept-EncodingThe cache key also depends on this request header

Validation: when content is stale the client sends If-None-Match: "abc123" (or If-Modified-Since). If unchanged, the server replies 304 Not Modified with no body, saving bandwidth but still costing one round trip.

Immutable assets (the best pattern): put a content hash in the file name (app.3f9a1c.js) and send Cache-Control: public, max-age=31536000, immutable. A change produces a new URL, so there is never a stale copy and never a purge. HTML pages stay short-lived or revalidated because they reference the hashed files.

import hashlib
class Server:
    def __init__(self): self.body, self.hits, self.bytes_sent = b"console.log('v1')" * 100, 0, 0
    def etag(self): return hashlib.md5(self.body).hexdigest()[:8]
    def get(self, if_none_match=None):
        self.hits += 1
        if if_none_match == self.etag(): return 304, b""
        self.bytes_sent += len(self.body); return 200, self.body
class BrowserCache:
    def __init__(self, server): self.server, self.etag, self.body, self.fetched_at = server, None, None, None
    def fetch(self, now, max_age=60):
        if self.body is not None and now - self.fetched_at < max_age: return "fresh cache hit (no network)"
        status, body = self.server.get(self.etag)
        if status == 304: self.fetched_at = now; return "304 revalidated (no body)"
        self.body, self.etag, self.fetched_at = body, self.server.etag(), now; return f"200 downloaded {len(body)} bytes"
srv = Server(); b = BrowserCache(srv)
for t in (0, 10, 70, 80, 140):
    print(f"t={t:>3}s:", b.fetch(t))
srv.body = b"console.log('v2')" * 100
print("t=200s after the file changed:", b.fetch(200))
print("server saw", srv.hits, "requests and sent", srv.bytes_sent, "bytes for 6 browser loads")

Output

t= 10s: fresh cache hit (no network)
t= 70s: 304 revalidated (no body)
t= 80s: fresh cache hit (no network)

Cache invalidation, honestly

Two ways to be correct: version the URL (best for static files) or keep short lifetimes with validators (for HTML and APIs). Purging a CDN is possible but slow and error prone. Cache keys must include everything that changes the response (language, device class, auth state), otherwise one user sees another's page: never cache personalised or authenticated responses in a shared cache without Vary or private.

How this gets asked

What does a 304 Not Modified response mean?

  • The page is missing That is 404.
  • The cached copy is still valid; no body is sent Correct.
  • A redirect No.
  • A server error No.

It saves bandwidth but still costs a round trip.

What is the best caching pattern for JavaScript and CSS files?

  • no-store Wastes bandwidth.
  • Content-hashed file names with a one-year immutable max-age Correct.
  • max-age=1 Little benefit.
  • No headers Heuristic caching only.

A change produces a new URL, so no purge is needed.

What is the danger of caching authenticated pages in a shared cache?

  • Slower pages No.
  • One user may be served another user's personalised content Correct.
  • Larger files No.
  • None No.

Use private or no-store, and Vary correctly.

Self-check

Fresh versus stale versus revalidate?

Fresh content is used directly; stale content must be revalidated with a conditional request; a 304 means the copy is still valid.

CDNs

A content delivery network is a global fleet of caching proxies. A request goes to the nearest edge; on a miss the edge asks an origin shield (a mid-tier cache) or your origin, stores the response, and serves later requests locally.

Benefits: lower latency, lower origin load, absorbing traffic spikes and DDoS attacks, TLS termination close to users, and edge compute (Workers, Lambda@Edge) for redirects, A/B tests and personalisation.

Key concepts:

  • Cache hit ratio is the metric to watch. Normalise query strings, strip tracking parameters, avoid unnecessary Vary and cookies on static paths.
  • Push versus pull CDN: pull (lazy fetch from origin on first request) is the default.
  • Origin shield / tiered cache collapses many edge misses into one origin request.
  • Request coalescing: if 1,000 users ask for the same uncached object, send one origin request.
  • Dynamic acceleration: even uncacheable requests benefit from a warm backbone connection between edge and origin.
  • Signed URLs/cookies protect private media; range requests enable seeking in video.
def origin_load(requests, hit_ratio): return requests * (1 - hit_ratio)
reqs = 10_000_000
for hr in (0.50, 0.90, 0.99):
    print(f"hit ratio {hr:.0%}: origin sees {origin_load(reqs, hr):>9,.0f} of {reqs:,} requests ({(1 - hr):.0%} of traffic)")
print("Raising the hit ratio from 90% to 99% cuts origin traffic by", f"{(1 - 0.99) / (1 - 0.90):.0%} of what it was", "(10x fewer requests).")

Output

hit ratio 50%: origin sees 5,000,000 of 10,000,000 requests (50% of traffic)
hit ratio 90%: origin sees 1,000,000 of 10,000,000 requests (10% of traffic)
hit ratio 99%: origin sees   100,000 of 10,000,000 requests (1% of traffic)

Self-check

How do you raise the CDN hit ratio?

Normalise cache keys, strip irrelevant query strings and cookies, set long TTLs for static assets and use tiered caching.

Compression and payloads

Compress text with gzip or Brotli (Content-Encoding); do not recompress images and video. Minify scripts, split bundles, lazy-load. Use modern image formats (WebP, AVIF), responsive sizes (srcset), and a CDN image service. JSON APIs gain from field selection, pagination and binary formats (Protocol Buffers) on hot internal paths.

import gzip, json, zlib
rows = [{"id": i, "name": f"product {i % 50}", "category": ["tools", "toys", "books"][i % 3], "price": 10 + i % 7} for i in range(2000)]
raw = json.dumps(rows).encode()
print(f"JSON {len(raw):,} bytes -> gzip {len(gzip.compress(raw)):,} bytes ({len(gzip.compress(raw)) / len(raw):.1%}) -> zlib level 9 {len(zlib.compress(raw, 9)):,}")
slim = json.dumps([[r["id"], r["name"], r["category"], r["price"]] for r in rows], separators=(",", ":")).encode()
print(f"array-of-arrays {len(slim):,} bytes -> gzip {len(gzip.compress(slim)):,} bytes (compression already removes most key repetition)")

Output

HTTP versions

VersionTransportKey idea
HTTP/1.1TCPOne request at a time per connection; browsers open about 6 connections per host; head-of-line blocking
HTTP/2TCP + TLSMultiplexing many streams on one connection, header compression (HPACK), server push (rarely used)
HTTP/3QUIC over UDPStreams are independent (no TCP head-of-line blocking on loss), faster handshakes, connection migration between networks

With HTTP/2 you no longer need old tricks such as domain sharding and sprite sheets. TCP-level head-of-line blocking remains for HTTP/2 on lossy mobile networks, which HTTP/3 fixes.

How this gets asked

What problem does HTTP/3 over QUIC address?

  • Weak encryption No.
  • TCP head-of-line blocking and slow connection setup, especially on lossy mobile networks Correct.
  • Large headers only No.
  • DNS No.

Streams are independent and loss on one does not stall the others.

Scaling persistent connections

Each connection is a file descriptor and some memory, so one tuned server holds hundreds of thousands to a million idle connections. Challenges:

  • Stateful: a user is attached to one gateway; keep a presence/session registry (Redis) mapping user to gateway, and route messages through pub/sub so any server can reach any user.
  • Load balancing: use L4 balancing or WebSocket-aware L7, with connection draining on deploys and jittered reconnect backoff so a restart does not cause a reconnect stampede.
  • Heartbeats detect dead peers; mobile networks drop idle connections silently.
  • Fallback to SSE or long polling where proxies block upgrades; resume with the last seen event id.
import random
random.seed(11)
def reconnect_peak(clients, jitter_window):
    buckets = {}
    for _ in range(clients):
        t = int(random.uniform(0, jitter_window))          # each client picks a random delay
        buckets[t] = buckets.get(t, 0) + 1
    return max(buckets.values())
for window in (1, 10, 60):
    print(f"1,000,000 clients reconnecting spread over {window:>2} s: busiest second sees {reconnect_peak(1_000_000, window):>9,} connections")

Output

1,000,000 clients reconnecting spread over  1 s: busiest second sees 1,000,000 connections
1,000,000 clients reconnecting spread over 10 s: busiest second sees   100,351 connections
1,000,000 clients reconnecting spread over 60 s: busiest second sees    16,972 connections

How this gets asked

Why add jitter to client reconnect backoff?

  • To use more bandwidth No.
  • To avoid a thundering herd when many clients reconnect at once Correct.
  • To slow users down No.
  • For encryption No.

Random delays spread the load over time.

Self-check

WebSocket versus SSE?

WebSocket is bidirectional over a custom protocol; SSE is one-way server push over HTTP with built-in reconnect.

Front-end performance in one page

Users judge speed by when they see and can use the page. The standard measurements (Core Web Vitals): LCP (largest contentful paint, aim for under 2.5 s), INP (interaction responsiveness, under 200 ms) and CLS (layout shift, under 0.1).

What to do about them:

  1. Send HTML quickly (server-side rendering or static generation for the first view, CDN cached).
  2. Keep the critical rendering path short: inline critical CSS, defer non-critical JavaScript, avoid render-blocking resources.
  3. Optimise images and fonts (right size and format, font-display: swap, preload the hero image).
  4. Cache with hashed file names and service workers where appropriate.
  5. Measure real users (RUM) as well as lab tests, and set performance budgets in CI.
Key idea

Latency is mostly round trips. Cache aggressively with versioned URLs, terminate TLS at the edge, reuse multiplexed connections, serve from a CDN, compress text, and treat persistent connections as stateful infrastructure that needs a registry, draining and jittered reconnects.

Self-check

What are the three Core Web Vitals?

Largest contentful paint, interaction to next paint, and cumulative layout shift.

Interview questions: Web delivery

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What happens when you type a URL and press enter?

DNS resolves the name, a TCP connection and TLS handshake are made (or reused), the HTTP request is sent through load balancers to a server, which responds; the browser parses and renders, fetching more resources.

Basic What does Cache-Control: max-age=3600 mean?

The response is fresh for an hour and may be reused without contacting the server.

Basic What is a CDN?

A geographically distributed network of caching proxies that serves content from locations near users, reducing latency and origin load.

Medium How do ETag and 304 work?

The server sends an ETag identifying the version; later the client asks conditionally with If-None-Match, and an unchanged resource returns 304 with no body.

Medium What is the best caching strategy for static assets?

Content-hashed file names with long immutable max-age, so changes get new URLs and never need purging, while HTML stays short-lived.

Medium Why can caching authenticated pages in a shared cache be dangerous?

One user may receive another's personalised response. Use private or no-store and correct Vary headers.

Medium HTTP/1.1 versus HTTP/2 versus HTTP/3?

1.1 handles one request per connection at a time; 2 multiplexes streams over one TCP connection with header compression; 3 runs over QUIC (UDP) removing TCP head-of-line blocking and speeding up handshakes.

Medium Polling, long polling, SSE and WebSocket: when each?

Polling for simple low-frequency needs, long polling as a fallback, SSE for one-way server push, WebSocket for bidirectional low-latency messaging.

Medium How do you scale WebSocket servers?

Keep a registry of which gateway holds each user, route messages via pub/sub, load-balance at L4 or WebSocket-aware L7, drain connections on deploy and use jittered reconnects.

Advanced What does TLS give you and what is forward secrecy?

Encryption, integrity and server authentication. Forward secrecy uses ephemeral key exchange so recorded traffic stays secret even if long-term keys leak later.

Advanced What is an origin shield and request coalescing?

A mid-tier cache that collapses many edge misses into one origin request, and coalescing sends a single origin fetch when many users ask for the same uncached object.

Advanced How do you improve Largest Contentful Paint?

Serve HTML fast from the edge, optimise and preload the hero image, inline critical CSS, defer blocking scripts and reduce server response time.

Advanced How can DNS be used for traffic management, and what are its limits?

Geo or latency routing, weighted records and health-checked failover, limited by TTL caching and resolvers that ignore low TTLs, so failover is slow compared with anycast or load balancers.

Advanced Why do HTTP caches need Vary?

Vary lists request headers that change the response (such as Accept-Encoding or language) so the cache key includes them and serves the right variant.
