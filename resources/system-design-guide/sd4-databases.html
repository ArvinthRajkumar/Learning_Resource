Part SD4

Databases: SQL, NoSQL and how to choose

The database is usually the hardest thing to change later, so the choice deserves care. This part explains what each kind of database is good at and why, from how it stores bytes up to how you choose.

Medium~3 hours

Why there are so many databases

Intuition

A database promises to store data durably and give it back quickly. Different workloads need different promises. A bank needs every transfer to be exact. A social feed needs to write millions of posts per second. A search box needs to find words inside text. No single design is best at all of these, so we have families of databases, each tuned for a different trade-off.

Terms

SQL is the query language. Relational is the data model. NoSQL loosely means "not only relational". Many NoSQL systems now support SQL-like queries, and many SQL systems store JSON. Judge a database by its guarantees and access patterns, not by the label.

Relational databases and ACID

The model

Data is stored in tables. A row is one record, a column is one field with a type. A primary key uniquely identifies a row. A foreign key points at another table's primary key. Queries combine tables with joins. The schema enforces structure and constraints (NOT NULL, UNIQUE, CHECK, FOREIGN KEY), so bad data is rejected at the door.

ACID

A transaction groups several operations into one all-or-nothing unit. ACID describes the guarantees.

LetterMeaningPlain languageHow it is built
AtomicityAll or nothingA transfer debits and credits, or does neitherWrite-ahead log, undo
ConsistencyValid state to valid stateConstraints always hold after commitConstraints, triggers, application rules
IsolationConcurrent transactions do not interfereTwo transfers on one account do not corrupt itLocks, multi-version concurrency control (MVCC)
DurabilityCommitted data survives crashesPower loss does not lose a committed paymentWrite-ahead log flushed to disk, replication

Write-ahead logging

Before changing data pages, the database appends the intended change to a sequential write-ahead log (WAL) and flushes it. After a crash it replays the log to restore committed work and undo unfinished work. Sequential appends are fast, which is why durability costs less than you would think. The same log is shipped to replicas for replication (SD5).

Normalisation and its cost

Normalising splits data into tables so each fact is stored once, avoiding update anomalies. The cost is joins. At large scale, selective denormalisation (copying a field into another table) trades extra storage and update work for faster reads. Decide per access pattern.

When relational is the right default

  • Data has relationships and you need joins and constraints.
  • You need multi-row transactions (payments, inventory, bookings).
  • The access patterns are not fully known yet, so ad hoc queries matter.
  • Data fits one machine, or one machine plus replicas (this covers most products for a long time).
Boring is good

For most new systems, start with PostgreSQL or MySQL. Move a specific workload to another store only when you can name the numbers that justify it.

How this gets asked

In ACID, which property is typically implemented with a write-ahead log?

  • Isolation Isolation uses locks or MVCC.
  • Durability and atomicity Correct: the log lets the database redo committed work and undo unfinished work.
  • Consistency only Consistency also depends on constraints.
  • None of them The WAL is central to durability.

The WAL records the change before it is applied, enabling crash recovery.

Self-check

Define ACID.

Atomicity, consistency, isolation, durability: all-or-nothing, valid state, no interference between concurrent transactions, committed data survives crashes.

How a database finds data: indexes

Intuition

Without an index, a query scans every row (a full table scan). An index is a separate sorted structure that lets the database jump to matching rows, like the index at the back of a book.

B-tree indexes

The default in relational databases. A balanced tree of pages with high fan-out (hundreds of keys per page), so even a billion rows need only 3 to 4 page reads to find a key. B-trees keep keys sorted, so they support equality, range queries, ORDER BY and prefix matches. Updates modify pages in place, so random writes can be costly, and the tree needs rebalancing.

LSM trees

Used by Cassandra, RocksDB, LevelDB and HBase. Writes go to an in-memory sorted table (memtable) plus a log. When the memtable fills it is flushed as an immutable sorted file (SSTable). Background compaction merges files. Reads check the memtable and several SSTables, aided by Bloom filters that skip files that definitely lack the key.

B-treeLSM tree
WritesIn-place, random I/O, slower under heavy writesSequential appends, very fast
ReadsOne tree walk, predictableMay touch several files, tuned by Bloom filters and compaction
SpaceSome fragmentationSpace amplification until compaction
Write amplificationLower to moderateHigher (data rewritten by compaction)
Best forRead-heavy and mixed OLTPWrite-heavy ingestion, time-ordered data

Index design rules

  • Index columns used in WHERE, JOIN and ORDER BY.
  • A composite index on (a, b) helps queries on a or on a and b, but not on b alone (leftmost prefix rule).
  • Put equality columns first, then the range column.
  • A covering index contains every column the query needs, so the table is never touched.
  • Every index speeds reads and slows writes and uses space. Do not index everything.
  • Low-selectivity columns (a boolean) are poor index candidates.
  • Read the query plan (EXPLAIN) to confirm the database really uses the index. The Python and SQL guide covers plans in depth.

How this gets asked

A B-tree has fan-out 100. About how many levels does it need for 10^6 keys?

log base 100 of 10^6 = 3 levels.

You have a composite index on (country, city). Which query can use it efficiently?

  • WHERE city = 'Paris' Skips the leftmost column.
  • WHERE country = 'FR' Correct: leftmost prefix.
  • WHERE city LIKE '%ar%' A leading wildcard cannot use an index.
  • None Query B works.

Composite indexes support queries on a leftmost prefix of their columns.

Which structure is best for a very write-heavy workload with sequential appends?

  • B-tree In-place updates cause random I/O.
  • LSM tree Correct.
  • Hash index on disk Not designed for this.
  • No index Reads would suffer.

LSM trees turn random writes into sequential flushes and compaction.

Self-check

B-tree versus LSM tree?

B-trees update in place and read predictably; LSM trees append sequentially and compact later, favouring writes.

What is the leftmost prefix rule?

A composite index on (a, b, c) serves queries on a, (a, b) and (a, b, c) but not on b or c alone.

Choosing a NoSQL model

Key-value stores

get(key), put(key, value), delete(key). The value is opaque, so no queries on contents. This simplicity gives extreme speed and trivial partitioning. Use for sessions, caches, feature flags, shopping carts, rate limit counters, user profiles read by id. DynamoDB adds secondary indexes and conditional writes.

Document stores

Store a self-contained JSON document per key, with a flexible schema and the ability to query inside documents. Good when an entity is read and written as a whole and has nested structure (a product with variants, a user profile, a blog post with comments). Weakness: joins across documents are weak or manual, and transactions across documents are limited or newer.

Wide-column stores

Data is addressed by row key, then column family and column, sorted by key. Designed for massive write throughput and horizontal scale, with queries planned around the partition key and a clustering order. In Cassandra you design one table per query, denormalising heavily.

-- Cassandra: tweets by user, newest first (query-first modelling)
CREATE TABLE tweets_by_user (
  user_id uuid,
  created_at timeuuid,
  tweet_id uuid,
  body text,
  PRIMARY KEY ((user_id), created_at)
) WITH CLUSTERING ORDER BY (created_at DESC);

Graph databases

Nodes, edges and properties, with traversal queries ("friends of friends who like X") that would be many self-joins in SQL. Choose when relationships are the point (social graphs, fraud rings, recommendation, knowledge graphs, network topology).

Time-series databases

Optimised for append-only timestamped data: columnar compression, downsampling, retention policies and fast range aggregations. Use for metrics, IoT, finance ticks.

Search engines

An inverted index maps each term to the list of documents containing it, enabling fast full-text search, ranking (TF-IDF, BM25), fuzzy matching and facets. They are secondary stores: keep the source of truth elsewhere and index into the search engine (SD12).

Object storage

Stores immutable blobs addressed by key with eleven nines of durability, very low cost and huge scale, accessed over HTTP. Use for images, video, backups, logs, data lake files. Not for small random updates or low-latency queries.

How this gets asked

Which are good fits for a key-value store? Select all.

  • User sessions
  • Complex multi-table joins
  • Rate limit counters
  • Shopping cart by user id

Key-value stores excel at point lookups and counters; joins are the relational strength.

Self-check

In Cassandra how do you model data?

Query first: one table per query, partition key chosen for the hottest lookup, with deliberate duplication.

Data modeling for access patterns

The approach

  1. List the queries first: what do we read, by what key, how often, how fast?
  2. Design the key (partition key and sort key) to serve the hottest query with one lookup.
  3. Add secondary indexes or duplicate data for other queries.
  4. Check for hot partitions: one key receiving a disproportionate share of traffic.
  5. Estimate size per partition and growth.

Example: chat messages

Queries: "latest 50 messages in a conversation" and "all conversations of a user".

Messages of a conversationmessagesconversation_idmessage_time descending
Conversations of a useruser_conversationsuser_idlast_message_time descending

Writing one message updates both tables. That duplication is deliberate: reads become single-partition lookups.

Hot keys

If one celebrity account or one popular product gets enormous traffic, its partition becomes a bottleneck. Remedies: add a random suffix to spread writes, cache aggressively, or split the key by time bucket.

How this gets asked

A single celebrity partition key is overloaded. Which is a valid mitigation?

  • Make the key longer Does not spread load.
  • Add a random suffix or time bucket to spread writes, and cache reads Correct.
  • Turn off replication Makes it worse.
  • Use fewer servers Makes it worse.

Spread hot keys across partitions and shield them with caching.

Polyglot persistence

Real systems use several stores, each doing what it is best at, linked by events or change data capture: a relational source of truth, a cache in front, a search index for queries, object storage for media, a warehouse for analytics. The price is that you must keep them in sync and reason about which is authoritative.

Trap

Do not choose MongoDB or Cassandra because "it scales" and then rebuild joins and transactions in application code. Do not choose a relational database for a 1 million writes per second ingest without partitioning. Name the access pattern and the number first.

How this gets asked

Which store should be the source of truth for payments with invariants across rows?

  • Key-value cache No transactional guarantees.
  • Relational database with transactions Correct.
  • Search engine A secondary index, not a source of truth.
  • Object storage Not suitable for updates.

Use ACID transactions where correctness across rows matters.

Self-check

What is polyglot persistence?

Using several specialised stores in one system, each for the job it is best at, with one declared source of truth.

Row stores keep all fields of a row together (fast to fetch a record). Column stores keep each column together, which compresses well and lets an aggregate read only the columns it needs. Run analytics on a separate warehouse so heavy scans do not slow the live product.

Interview questions: Databases

10 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic SQL versus NoSQL: how do you choose?

From access patterns and consistency needs. Relational for joins, transactions and flexible queries. Key-value for fast lookups, document for nested entities, wide-column for massive writes, graph for relationships, search engines for text.

Basic What does ACID mean?

Atomicity (all or nothing), consistency (valid state to valid state), isolation (concurrent transactions do not interfere), durability (committed data survives crashes).

Basic What is an index and what does it cost?

A sorted structure (usually B-tree) that lets the database find rows without scanning the table. It speeds reads but uses space and slows writes.

Medium B-tree versus LSM tree?

B-trees update in place, with predictable reads and more random write I/O. LSM trees buffer writes in memory, flush sorted files and compact later, giving very fast writes and heavier read paths.

Medium What is the leftmost prefix rule for composite indexes?

An index on (a, b, c) supports queries filtering on a, on a and b, or on a, b and c, but not on b or c alone.

Medium When would you denormalise?

When read performance and simplicity for known queries outweigh the cost of duplicate data and more complex updates, typically at large scale or in NoSQL designs.

Medium OLTP versus OLAP?

OLTP handles many small transactions on row stores with millisecond latency. OLAP runs large scans and aggregations on column stores in warehouses. Keep analytics off the transactional database.

Advanced How does a write-ahead log provide durability?

The change is appended and flushed to a sequential log before data pages are modified. After a crash the database replays the log to redo committed work and undo uncommitted work. The log also feeds replication.

Advanced Why would you pick Cassandra and how do you model data in it?

For huge write throughput, linear scale and high availability. Model by query: one table per query with a partition key for the lookup and clustering columns for ordering, accepting duplication and no joins.

Advanced What is polyglot persistence and its risk?

Using different stores for different workloads. The risk is keeping them consistent, so declare one source of truth and propagate changes through events or change data capture.
