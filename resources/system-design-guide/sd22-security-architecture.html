Part SD22

Security architecture: authentication, tokens, encryption, zero trust and threat modelling

Security is a property of the whole design, not a feature added at the end. This part covers the identity, cryptography and network ideas every architect must know, with short runnable demonstrations of the key mechanisms.

Advanced~4 hours

Security principles

  • Least privilege: grant the minimum access, for the minimum time.
  • Defence in depth: layers (network, identity, application, data) so one failure is not fatal.
  • Fail closed: on error, deny.
  • Secure by default, minimise attack surface, separation of duties, assume breach.
  • Never roll your own crypto: use vetted libraries and managed services.

The CIA triad: Confidentiality, Integrity, Availability. Add authenticity and non-repudiation where needed.

Authentication: proving who you are

Authentication (who are you?) versus authorization (what may you do?). Factors: something you know (password), have (phone, hardware key), are (biometrics). MFA combines two or more; phishing-resistant options are WebAuthn/passkeys.

Storing passwords

Never store plaintext or a fast hash. Use a slow, salted, memory-hard password hash (argon2id, scrypt, bcrypt). The salt is random per user, defeating rainbow tables; the work factor slows brute force.

import hashlib, hmac, os, time
def hash_password(pw, iterations=200_000):
    salt = os.urandom(16)
    return salt, iterations, hashlib.pbkdf2_hmac("sha256", pw.encode(), salt, iterations)
def verify(pw, salt, iterations, digest):
    cand = hashlib.pbkdf2_hmac("sha256", pw.encode(), salt, iterations)
    return hmac.compare_digest(cand, digest)               # constant-time comparison
salt, it, dg = hash_password("correct horse battery staple")
print("right password:", verify("correct horse battery staple", salt, it, dg), "| wrong password:", verify("hunter2", salt, it, dg))
t = time.perf_counter(); hashlib.sha256(b"x").digest(); fast = time.perf_counter() - t
t = time.perf_counter(); hashlib.pbkdf2_hmac("sha256", b"x", salt, it); slow = time.perf_counter() - t
print("PBKDF2 (200k rounds) is slower than a single SHA-256:", slow > 100 * fast)

Output

right password: True | wrong password: False
PBKDF2 (200k rounds) is slower than a single SHA-256: True

The work factor is the large cost every attacker guess must pay; raise it as hardware improves.

A signed token, from scratch

A JWT is base64(header).base64(payload).signature where the signature (HMAC for symmetric, RSA/ECDSA for asymmetric) covers the first two parts. Anyone can read the payload; only the key holder can forge it. Always check the signature and expiry, and fix the accepted algorithm.

import base64, hashlib, hmac, json, time
b64 = lambda b: base64.urlsafe_b64encode(b).rstrip(b"=").decode()
unb64 = lambda s: base64.urlsafe_b64decode(s + "=" * (-len(s) % 4))
def sign(payload, key):
    head = b64(json.dumps({"alg": "HS256", "typ": "JWT"}, separators=(",", ":")).encode())
    body = b64(json.dumps(payload, separators=(",", ":")).encode())
    sig = b64(hmac.new(key, f"{head}.{body}".encode(), hashlib.sha256).digest())
    return f"{head}.{body}.{sig}"
def verify(token, key, now):
    head, body, sig = token.split(".")
    if json.loads(unb64(head))["alg"] != "HS256": return "rejected: unexpected algorithm"
    good = b64(hmac.new(key, f"{head}.{body}".encode(), hashlib.sha256).digest())
    if not hmac.compare_digest(sig, good): return "rejected: bad signature"
    claims = json.loads(unb64(body))
    return "rejected: expired" if claims["exp"] < now else claims
key = b"server-secret-key"
tok = sign({"sub": "user42", "role": "admin", "exp": 1000}, key)
print("valid     :", verify(tok, key, now=500))
print("expired   :", verify(tok, key, now=2000))
h, b, s = tok.split(".")
forged_body = b64(json.dumps({"sub": "user42", "role": "superadmin", "exp": 9999}, separators=(",", ":")).encode())
print("tampered  :", verify(f"{h}.{forged_body}.{s}", key, now=500))

Output

valid     : {'sub': 'user42', 'role': 'admin', 'exp': 1000}
expired   : rejected: expired
tampered  : rejected: bad signature

How this gets asked

Why use a salt when hashing passwords?

  • To make hashes shorter No.
  • So identical passwords hash differently and precomputed tables fail Correct.
  • To encrypt them Hashing is not encryption.
  • To speed up logins No.

Each user gets a unique random salt.

Which is appropriate for storing passwords?

  • MD5 Fast and broken.
  • Plain SHA-256 Too fast.
  • argon2id, scrypt or bcrypt Correct.
  • Base64 Encoding, not hashing.

Slow, salted and memory-hard resists brute force.

What can anyone do with a signed JWT without the key?

  • Modify it undetected Signature check fails.
  • Read the payload Correct, the payload is only encoded, not encrypted.
  • Extend the expiry That breaks the signature.
  • Nothing They can read it.

Do not put secrets in a JWT payload.

Authorization

Models: RBAC (roles), ABAC (attributes and policies), ReBAC (relationships, as in Google Zanzibar: "viewer of the parent folder"), and ACLs. Enforce on the server, at every request, close to the data, and check object-level access (prevent IDOR/BOLA: user 5 reading /orders/9). Centralise policy (OPA, Cedar) where many services share rules.

How this gets asked

IDOR (BOLA) is prevented by:

  • Hiding ids Obscurity.
  • Checking that the caller may access that specific object on every request Correct.
  • Using POST No.
  • Using HTTPS Does not authorize.

Object-level authorization.

OAuth 2.0 and OpenID Connect

  • OAuth 2.0 is delegated authorization: an app gets a limited access token to call an API on a user's behalf without learning their password.
  • OpenID Connect (OIDC) adds an ID token (who the user is) on top of OAuth.

Authorization Code flow with PKCE (the standard for web, mobile and single-page apps):

Short-lived access tokens plus long-lived refresh tokens (rotate and bind them). Client credentials flow is for service-to-service. Avoid the implicit flow and password grant. Validate iss, aud, exp and scopes.

How this gets asked

What does PKCE protect against?

  • SQL injection No.
  • An intercepted authorization code being redeemed by an attacker Correct.
  • Weak passwords No.
  • DNS spoofing No.

The code is bound to the original code verifier.

Self-check

OAuth versus OIDC?

OAuth delegates authorization with access tokens; OIDC adds an ID token to say who the user is.

Encryption

KindUseExamples
SymmetricEncrypt bulk data, one shared keyAES-GCM, ChaCha20-Poly1305
AsymmetricKey exchange, signatures, identityRSA, ECDSA, Ed25519, X25519
HashIntegrity, fingerprints (no key)SHA-256
MACIntegrity and authenticity with a shared keyHMAC-SHA256
KDFDerive keys from secretsPBKDF2, scrypt, HKDF
  • In transit: TLS 1.2+ everywhere (also between internal services); mTLS gives mutual authentication; HSTS forces HTTPS.
  • At rest: disk or database encryption, envelope encryption: a data key encrypts data, a master key in a KMS/HSM encrypts the data key, so rotating the master key is cheap.
  • End-to-end encryption: only the endpoints hold keys (messaging apps), at the cost of server-side features like search.
  • Use authenticated encryption (GCM), never reuse a nonce, and rotate keys.

How this gets asked

What is envelope encryption?

  • Encrypting emails No.
  • A data key encrypts the data and a master key in a KMS encrypts the data key Correct.
  • Hashing twice No.
  • Using RSA only No.

Rotating the master key avoids re-encrypting all data.

Self-check

TLS versus mTLS?

TLS authenticates the server to the client; mTLS makes both sides present certificates.

Secrets management

Never commit secrets or bake them into images. Use a secret manager (Vault, AWS Secrets Manager), inject at runtime, scope per service, rotate, audit access, and prefer short-lived credentials (workload identity, IAM roles) over static keys. Scan repositories for leaked keys.

Network security and zero trust

Traditional model: a hard perimeter, trusted inside. Zero trust: never trust, always verify: authenticate and authorize every request regardless of network location, with device and identity checks, microsegmentation and least-privilege access.

Practical layers: WAF and DDoS protection at the edge, private subnets for data stores, security groups as allow-lists, egress control, API gateway with authentication and rate limits, service mesh with mTLS between services.

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("CREATE TABLE users(name TEXT, secret TEXT); INSERT INTO users VALUES('ana','a-secret'),('bo','b-secret');")
evil = "x' OR '1'='1"
unsafe = db.execute(f"SELECT name FROM users WHERE name = '{evil}'").fetchall()          # string building
safe = db.execute("SELECT name FROM users WHERE name = ?", (evil,)).fetchall()           # parameter binding
print("injected query returns:", unsafe, "| parameterised query returns:", safe)

How this gets asked

How do you prevent SQL injection?

  • Escape quotes by hand Fragile.
  • Use parameterised queries Correct.
  • Use longer passwords Unrelated.
  • Hide the table names No.

Data is bound as parameters and never parsed as SQL.

Threat modelling

Ask four questions: What are we building? What can go wrong? What will we do about it? Did we do a good job? Draw a data-flow diagram, mark trust boundaries, and walk STRIDE:

LetterThreatProperty violated
SSpoofing identityAuthentication
TTampering with dataIntegrity
RRepudiationNon-repudiation (audit logs)
IInformation disclosureConfidentiality
DDenial of serviceAvailability
EElevation of privilegeAuthorization

Also keep audit logs (who did what, tamper-evident), plan incident response, and follow privacy rules (data minimisation, retention limits, consent, regional residency such as GDPR).

Key idea

Authenticate strongly, authorize every object access on the server, encrypt in transit and at rest with managed keys, keep secrets out of code, assume the network is hostile, validate all input with parameterised interfaces, and threat-model new designs with STRIDE.

How this gets asked

In STRIDE, what does the 'E' stand for?

  • Encryption No.
  • Elevation of privilege Correct.
  • Errors No.
  • Eavesdropping That is information disclosure.

Gaining capabilities one should not have.

Interview questions: Security architecture

15 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Authentication versus authorization?

Authentication verifies who you are; authorization determines what you may do.

Basic How should passwords be stored?

As salted hashes from a slow, memory-hard function such as argon2id, scrypt or bcrypt. Never plaintext, never fast hashes like MD5 or plain SHA-256.

Basic How do you prevent SQL injection?

Parameterised queries or prepared statements so user input is bound as data, plus least-privileged database accounts.

Medium Sessions versus JWTs?

Sessions keep state on the server and are easy to revoke; JWTs are self-contained and verifiable by any service but hard to revoke, so use short lifetimes and refresh tokens.

Medium Explain the OAuth 2.0 authorization code flow with PKCE.

The app redirects to the authorization server with a code challenge; after login it receives a one-time code and exchanges it with the code verifier for tokens, so an intercepted code is useless.

Medium OAuth versus OpenID Connect?

OAuth delegates authorization with access tokens; OIDC adds an ID token and standard claims to authenticate the user.

Medium What is IDOR/BOLA and how do you prevent it?

Accessing another user's object by changing an id. Enforce object-level authorization on the server for every request.

Medium Symmetric versus asymmetric encryption?

Symmetric (AES) uses one shared key and is fast for bulk data; asymmetric (RSA, ECC) uses key pairs for key exchange and signatures. TLS combines both.

Medium What is envelope encryption?

Data is encrypted with a data key, which is encrypted by a master key in a KMS or HSM. Rotating the master key re-wraps small data keys instead of re-encrypting all data.

Advanced What is zero trust?

No implicit trust from network location: every request is authenticated, authorized and encrypted, with device and identity checks, microsegmentation and least privilege.

Advanced How do you secure service-to-service calls?

mTLS (often via a service mesh) for mutual authentication, short-lived workload identities, per-service authorization policies and network policies.

Advanced Explain CSRF and its defences.

A malicious site makes the user's browser send an authenticated request. Defend with SameSite cookies, anti-CSRF tokens and checking Origin headers.

Advanced How do you manage secrets?

Store in a secret manager, inject at runtime, scope narrowly, rotate, audit and prefer short-lived credentials such as workload identity over static keys; never commit them.

Advanced Walk through STRIDE on a login endpoint.

Spoofing (credential stuffing, MFA), Tampering (TLS, signed tokens), Repudiation (audit logs), Information disclosure (generic errors, no secrets in logs), Denial of service (rate limits), Elevation (authorization checks).

Advanced How do you defend an API against abuse?

Authentication, per-key rate limits and quotas, WAF and bot detection, input validation and size limits, idempotency keys, monitoring and anomaly alerts.
