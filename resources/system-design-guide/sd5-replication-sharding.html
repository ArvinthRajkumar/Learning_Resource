Part SD5

Replication, partitioning and consistent hashing

One machine cannot hold unlimited data or serve unlimited requests, and it will eventually fail. Replication copies data for safety and read capacity. Partitioning splits data for capacity. Almost every large data system uses both.

MediumAdvanced~3 hours

Why copy and why split

Two different problems

  • Replication keeps the same data on several machines. It gives availability (survive a node loss), durability, and read scaling (spread reads) and can place data closer to users.
  • Partitioning (sharding) puts different data on different machines. It gives capacity and write scaling, because each machine holds and serves only a slice.

Replication

Leader-follower (primary-replica)

One node, the leader, accepts all writes and records them in a replication log. Followers apply the log and serve reads. If the leader fails, a follower is promoted (failover).

Synchronous versus asynchronous

SynchronousAsynchronous
Leader waits for follower to confirmYesNo
Write latencyHigherLower

A common compromise is semi-synchronous: wait for one follower and replicate asynchronously to the rest, so at least two copies exist before acknowledging.

Replication lag and its anomalies

With asynchronous followers, a read from a follower can be stale. This causes visible bugs:

AnomalyWhat the user seesTypical fix
Read your own writesYou post a comment, reload, it is missingRead your own recent writes from the leader, or from a follower that has caught up to your write's position
Monotonic readsPage shows new data, then older data on refreshPin a user to one replica
Consistent prefixReply appears before the questionKeep causally related writes in order (same partition)

Failover and its dangers

Failover needs to detect failure (heartbeat timeout), choose a new leader (usually the most up-to-date follower) and reconfigure clients. Dangers:

  • Lost writes: the chosen follower lacked recent writes from the old leader.
  • Split brain: the old leader comes back and thinks it is still leader, so two nodes accept writes. Prevent with fencing tokens, leases and consensus (SD6).
  • Timeouts too short: a brief pause triggers an unnecessary failover that adds load and may cascade.

Quorums

With N replicas, a write must succeed on W nodes and a read must query R nodes. If R + W > N, every read set overlaps every write set, so a read sees the latest acknowledged write (absent concurrent writes and sloppy quorums).

How this gets asked

A user writes a comment then reloads and does not see it. This is a violation of:

  • Durability The write was acknowledged and stored.
  • Read-your-own-writes consistency Correct: the read hit a lagging follower.
  • Atomicity Not related.
  • Isolation Not related.

Route the user's reads to the leader (or an up-to-date replica) for a short time after a write.

With N = 5 replicas and W = 3, what is the smallest R that guarantees read and write sets overlap?

R + W > N means R > 5 - 3 = 2, so R = 3.

What prevents a returning old leader from corrupting data after failover (split brain)?

  • Bigger disks Irrelevant.
  • Fencing tokens or leases checked by the storage layer Correct.
  • More followers Does not prevent two leaders.
  • A faster network Does not solve it.

Monotonic fencing tokens let storage reject writes from a stale leader.

Self-check

What is the quorum rule?

R + W > N guarantees read and write sets overlap.

Synchronous versus asynchronous replication trade-off?

Synchronous: no acknowledged data loss but higher latency and availability risk. Asynchronous: faster, may lose recent writes on failure.

Partitioning strategies

What a shard key does

The shard key (or partition key) decides which shard stores a row. Choose it so that data and traffic spread evenly and so that your most common queries touch one shard.

Range partitioning

Each shard owns a contiguous range of keys (A to F, G to M, and so on, or date ranges).

  • Pro: efficient range scans and sorted output.
  • Con: hot spots. Time-based keys send all current writes to the newest shard.

Hash partitioning

Hash the key and map the hash to a shard.

  • Pro: even distribution.
  • Con: range queries must scatter to all shards. Key order is lost.
  • The naive mapping shard = hash(key) % number_of_shards reshuffles almost everything when the shard count changes.
import hashlib
def h(k): return int(hashlib.md5(k.encode()).hexdigest(), 16)
keys = ["user%d" % i for i in range(10000)]
before = {k: h(k) % 4 for k in keys}
after = {k: h(k) % 5 for k in keys}
moved = sum(1 for k in keys if before[k] != after[k])
print("moved when going from 4 to 5 shards:", moved, "of", len(keys), "(%.0f%%)" % (100 * moved / len(keys)))

Output

moved when going from 4 to 5 shards: 7973 of 10000 (80%)

Directory-based (lookup) partitioning

A separate service stores a mapping from key (or key range) to shard. Flexible, since you can move individual tenants, but the directory becomes a critical component that needs replication and caching.

Geo or tenant partitioning

Keep a user's or customer's data in their region for latency and legal residency. Large tenants may get their own shard.

Choosing the key

CandidateProblem
TimestampAll writes go to one shard (hot spot)
CountryA few countries hold most users (skew)
User id (hashed)Good for per-user queries, bad for cross-user analytics
Auto-increment idMonotonic: with range partitioning it is a hot spot

Costs of sharding

  • Cross-shard queries and joins are slow or impossible. Denormalise or use a search or analytics store.
  • Cross-shard transactions need two-phase commit or sagas (SD6).
  • Resharding is operationally hard.
  • Unique ids and constraints must work across shards (SD12).
Rule of thumb

Postpone sharding. First optimise queries, add indexes, add read replicas and cache. Shard when a single primary cannot handle the write volume or the dataset no longer fits.

How this gets asked

Why is timestamp a poor shard key under range partitioning?

  • Timestamps are large Not the reason.
  • All current writes hit the newest shard (hot spot) Correct.
  • Timestamps cannot be hashed They can.
  • It breaks replication Unrelated.

Monotonic keys concentrate writes. Hash the key or add a prefix to spread them.

Which are downsides of sharding? Select all.

  • Cross-shard joins are hard
  • Cross-shard transactions are complex
  • Capacity is limited to one machine
  • Resharding is operationally difficult

Sharding exists to break the single-machine capacity limit, but it introduces cross-shard complexity.

Self-check

Range versus hash partitioning?

Range keeps order and supports range scans but risks hot spots; hash spreads evenly but loses order.

Consistent hashing

The problem it solves

With hash(key) % N, changing N moves almost every key, which would flush a whole cache cluster or trigger a huge data migration. Consistent hashing moves only about 1/N of keys when a node is added or removed.

The ring

Hash both servers and keys onto the same circular space (for example 0 to 2^32 - 1). A key is stored on the first server found moving clockwise from the key's position.

When server B is removed, only the keys that mapped to B move, to the next server (C here). Everything else stays.

Virtual nodes

With few servers, positions on the ring are uneven, so one server may own a big arc. Give each physical server many virtual nodes (100 to 500 points on the ring). Load evens out, and a failed server's load spreads across all others instead of landing on a single neighbour. Powerful servers can get more virtual nodes.

A working implementation

import bisect, hashlib

class Ring:
    def __init__(self, nodes=(), vnodes=100):
        self.vnodes = vnodes
        self.keys = []      # sorted hash positions
        self.owner = {}     # position -> node
        for n in nodes:
            self.add(n)

    @staticmethod
    def _h(s):
        return int(hashlib.md5(s.encode()).hexdigest(), 16)

    def add(self, node):
        for i in range(self.vnodes):
            p = self._h("%s#%d" % (node, i))
            bisect.insort(self.keys, p)
            self.owner[p] = node

    def remove(self, node):
        for i in range(self.vnodes):
            p = self._h("%s#%d" % (node, i))
            self.keys.remove(p)
            del self.owner[p]

    def get(self, key):
        i = bisect.bisect(self.keys, self._h(key)) % len(self.keys)
        return self.owner[self.keys[i]]

keys = ["user%d" % i for i in range(10000)]
ring = Ring(["A", "B", "C", "D"])
before = {k: ring.get(k) for k in keys}
ring.add("E")
after = {k: ring.get(k) for k in keys}
moved = sum(1 for k in keys if before[k] != after[k])
print("keys moved after adding a 5th node: %.1f%% (ideal 20%%)" % (100 * moved / len(keys)))
counts = {}
for k in keys:
    counts[after[k]] = counts.get(after[k], 0) + 1
print(sorted(counts.items()))

Output

keys moved after adding a 5th node: 18.8% (ideal 20%)
[('A', 2034), ('B', 2286), ('C', 2020), ('D', 1778), ('E', 1882)]

Compare with the 80 percent shuffle of the modulo scheme above. Consistent hashing is used by Dynamo, Cassandra, memcached clients, CDNs and many load balancers.

How this gets asked

In consistent hashing, what do virtual nodes fix?

  • They encrypt keys No.
  • Uneven load from few ring positions, and uneven load transfer after a failure Correct.
  • They remove the need for hashing No.
  • They make writes synchronous No.

Many virtual nodes per server smooth out the distribution.

Approximately what fraction of keys move when you add a 5th node to a consistent hash ring of 4 equal nodes? (answer as a percent)

About 1/5 of the keys, or 20 percent, move to the new node. Modulo hashing would move about 80 percent.

Self-check

Why consistent hashing?

Adding or removing a node moves only about 1/N of the keys instead of nearly all of them.

Rebalancing and resharding

Fixed number of partitions

Create many more partitions than nodes (say 1,000 partitions on 10 nodes). Adding a node steals some whole partitions from existing nodes. Only the partitions move, and the key to partition mapping never changes. Used by Elasticsearch, Riak, Couchbase and Kafka.

Dynamic splitting

Start with few partitions. When one grows beyond a size limit it splits in two, and small ones merge. Used by HBase, MongoDB and range-sharded systems.

Doing it online

  1. Add the new shard and start dual writes or log shipping to it.
  2. Backfill existing data.
  3. Verify with checksums and shadow reads.
  4. Switch reads, then writes.
  5. Clean up the old data.

Throttle the copy so rebalancing does not hurt production traffic.

Rebalancing and failure detection

Do not rebalance automatically on a brief failure: a slow node looks dead, and moving its data creates even more load. Many systems require a human or a long timeout before moving data.

Self-check

How do you reshard online?

Dual write or ship the log, backfill, verify, switch reads then writes, clean up, all throttled.

Interview questions: Replication and sharding

11 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Replication versus sharding?

Replication copies the same data to several nodes for availability, durability and read scaling. Sharding splits data across nodes for capacity and write scaling.

Basic What is leader-follower replication?

One leader accepts writes and ships a log to followers, which serve reads and take over if the leader fails.

Medium Synchronous versus asynchronous replication?

Synchronous waits for followers (no acknowledged data loss, higher latency, availability risk). Asynchronous is faster but can lose recent writes on leader failure. Semi-synchronous waits for one follower.

Medium What is replication lag and how do you cope?

Followers apply changes after the leader, so reads can be stale. Read your own writes from the leader, pin users to a replica for monotonic reads, and keep related writes in one partition.

Medium Range versus hash partitioning?

Range keeps ordered data and supports range scans but can create hot spots. Hash spreads load evenly but loses ordering and makes range queries scatter.

Medium What is consistent hashing and why use it?

Servers and keys are hashed onto a ring and a key belongs to the next server clockwise. Adding or removing a server moves only about 1/N of keys instead of nearly all.

Medium What are virtual nodes?

Many ring positions per physical server, which evens out load and spreads a failed server's load across many others.

Advanced Explain quorum reads and writes.

With N replicas, writes wait for W acknowledgements and reads query R replicas. If R + W > N the sets overlap, so a read sees the latest acknowledged write.

Advanced What is split brain and how do you prevent it?

Two nodes both act as leader after a partition or a false failure detection, accepting conflicting writes. Prevent with consensus-based leader election, leases and fencing tokens.

Advanced How do you reshard without downtime?

Add the new shard, dual write or ship the log, backfill, verify, switch reads then writes, then clean up, throttling the copy. Fixed many partitions or consistent hashing makes it cheaper.

Advanced What problems does sharding introduce?

Cross-shard joins and transactions, rebalancing, hot keys, global unique ids and constraints, and more operational complexity. Delay it until optimisation, replicas and caching are not enough.
