Scaling, load balancing and proxies

Scaling means handling more work by adding resources. The art is to add them in a way that keeps the system simple, fast and cheap. Load balancers are the first component almost every large design introduces.

BasicMedium~2 hours

Scaling up and scaling out

Intuition

One cashier serves customers until the queue gets long. You can hire a faster cashier (scale up) or open more registers (scale out). A faster cashier has a limit and costs more per extra speed. More registers are easier to extend but need someone to direct customers to the shortest line: the load balancer.

Vertical versus horizontal

Vertical (scale up)Horizontal (scale out)
What changesBigger machine: more CPU, RAM, diskMore machines
ComplexityLow: no code changeHigher: needs load balancing, shared state design
LimitHardware ceiling, cost grows faster than capacityPractically very high
FailureSingle point of failureSurvives losing a node
Downtime to scaleOften a restartUsually none
Good forEarly stage, databasesStateless web tier, caches, workers
Rule of thumb

Scale up first while it is cheap and simple. Design the web tier so it can scale out. Databases scale up first, then read replicas, then sharding (SD5).

Stateless services

A service is stateless if any instance can handle any request, because nothing needed to answer is stored in that instance's memory or disk between requests. State lives elsewhere: a database, a cache, a token in the client.

Why it matters: stateless instances can be added, removed, restarted and load balanced freely. If instance A holds a user's session in RAM, the load balancer must always send that user to A, and when A dies the session is lost.

Where session state can live

OptionHowProsCons
Sticky sessionsLB pins a user to one serverNo code changeUneven load, lost on failure
Shared session storeRedis or database holds sessionsAny server can serveExtra dependency and hop
Client-side tokenSigned token (JWT) holds the claimsNo server lookupHard to revoke, size limit

How this gets asked

Why is a stateless web tier easier to scale out?

  • It uses less memory Not the reason.
  • Any instance can serve any request, so instances can be added or removed freely Correct.
  • It does not need a load balancer It needs one.
  • It avoids TLS Unrelated.

No per-instance state means the load balancer is free to send any request anywhere and instances are disposable.

Four servers each handle 500 requests per second at 70 percent target utilisation. What total QPS can the pool take while staying at target?

4 x 500 x 0.7 = 1,400 requests per second.

Self-check

When do you scale up and when out?

Scale up while simple and cheap, especially databases; scale out stateless tiers that are designed for it.

Where can session state live?

Sticky servers, a shared store such as Redis, or a signed client-side token.

Load balancing algorithms

What a load balancer does

A load balancer receives requests and distributes them across a pool of servers. It also performs health checks, removes bad servers, can terminate TLS, and presents a single stable address.

Common algorithms

AlgorithmHow it picksBest whenWeakness
Round robinNext server in orderEqual servers, similar requestsIgnores current load
Weighted round robinMore requests to bigger serversMixed hardwareStatic weights
Least connectionsServer with fewest active connectionsLong, uneven requestsNeeds connection tracking
Least response timeFastest recent responsesHeterogeneous latencyNeeds measurement
IP hashHash of client IPSimple stickinessUneven when many users share an IP
Consistent hashingHash of a key onto a ringCaches and sharded backends (SD5)More complex
Random with two choicesPick two at random, take the less loadedLarge pools, no coordinationSlightly more logic

Here is round robin versus least connections on uneven requests, simulated.

import random
random.seed(1)
servers = 3
# each request has a "cost" in time units; a few are very expensive
reqs = [1] * 40 + [20] * 4
random.shuffle(reqs)

# round robin: assign in order
load_rr = [0] * servers
for i, c in enumerate(reqs):
    load_rr[i % servers] += c

# least loaded (a proxy for least connections / least work)
load_lc = [0] * servers
for c in reqs:
    j = min(range(servers), key=lambda k: load_lc[k])
    load_lc[j] += c

print("round robin  :", load_rr, "max", max(load_rr))
print("least loaded :", load_lc, "max", max(load_lc))

Output

round robin  : [34, 34, 52] max 52
least loaded : [38, 38, 44] max 44
Key idea

Round robin is fine for uniform requests. When request costs vary, balance on actual load. The "power of two choices" gets most of the benefit without global state.

How this gets asked

Request costs vary a lot (some take 20 times longer). Which algorithm handles this best?

  • Round robin Ignores cost, so one server can get several heavy requests in a row.
  • Least connections or least load Correct.
  • IP hash Distributes by client, not by cost.
  • Always the first server Obviously poor.

Balance on actual load when request cost varies. Round robin is fine only when requests are uniform.

Self-check

What is the power of two choices?

Pick two servers at random and send the request to the less loaded one. It nearly matches global least-load with no coordination.

Layer 4 versus layer 7

Two levels of understanding traffic

Layer 4 (transport)Layer 7 (application)
SeesIP addresses and portsFull HTTP: path, headers, cookies, body
DecisionForward TCP or UDP connectionRoute by URL, host, header, cookie
SpeedFaster, simplerSlower, more CPU
FeaturesBasic balancing, TLS passthroughTLS termination, path routing, rewrites, compression, auth, rate limiting, caching
ExamplesAWS NLB, HAProxy in TCP mode, LVSAWS ALB, NGINX, Envoy, HAProxy HTTP mode

Path-based routing is the reason layer 7 matters for microservices: /api/users goes to the users service, /api/orders to the orders service, /static to a bucket.

High availability of the load balancer itself

A single load balancer is a single point of failure. Run at least two as an active-passive pair (a failover with a shared virtual IP) or active-active (both serve, with DNS or anycast spreading clients). Cloud load balancers do this for you across availability zones.

How this gets asked

Which are things a layer 7 load balancer can do that a layer 4 one cannot? Select all.

  • Route by URL path
  • Route by HTTP header or cookie
  • Forward raw TCP by IP and port
  • Terminate TLS and inspect the request

Layer 4 sees only addresses and ports. Layer 7 understands HTTP. Forwarding raw TCP is something both can do, so it is not a distinguishing capability.

Self-check

Why use layer 7 for microservices?

It can route by path, host and headers and also terminate TLS, apply auth and rate limits.

A load balancer is a reverse proxy that specialises in distribution. In practice NGINX, HAProxy and Envoy do both.

Health checks and failure handling

Health checks

The load balancer probes each server and removes unhealthy ones from rotation.

  • Passive: watch real traffic for errors and timeouts.
  • Active: send a probe request (GET /healthz) every few seconds. Require several failures to eject and several successes to re-add, to avoid flapping.
  • Distinguish liveness (the process is running, restart it if not) from readiness (it can serve traffic now, for example after warmup and with dependencies available).
Trap

A health endpoint that checks the database means a database blip marks every server unhealthy, and the load balancer ejects the entire fleet. Keep health checks shallow, or protect against removing everyone at once ("panic mode" that keeps at least a minimum number in rotation).

Connection draining

Before removing a server for deploy or scale-in, stop sending new requests and let in-flight requests finish (for 30 to 60 seconds). Otherwise users see errors during every deploy.

Retries and the thundering herd

When a server dies, its share of requests moves to the others. If each is already near capacity they can fall over too, a cascading failure. Keep headroom (run at 50 to 70 percent), use timeouts, retries with backoff and jitter, and load shedding (SD10).

How this gets asked

Your health check endpoint queries the database, and the database has a 10 second blip. What can go wrong?

  • Nothing, this is best practice It is a known anti-pattern.
  • Every server is marked unhealthy and removed at once Correct.
  • The database restarts Not caused by the check.
  • Latency drops Unlikely.

Deep health checks can eject the whole fleet. Prefer shallow checks, or a floor on how many servers must stay in rotation.

Self-check

What is connection draining?

Stop sending new requests to a server about to be removed and let in-flight requests finish.

Autoscaling

The idea

Automatically add instances when load rises and remove them when it falls, which saves cost and absorbs spikes.

What to scale on

SignalNotes
CPU or memory utilisationSimple, lags behind sudden spikes
Requests per instance or queue lengthBetter indicator of actual demand
Custom metrics (latency, backlog)Best for workers: scale on messages waiting
ScheduleFor predictable peaks such as morning or sale events

Practical rules

  • New instances take time (boot, warmup, cache fill), so scale before you need to, with headroom, or keep a warm pool.
  • Add quickly, remove slowly (cooldown periods) to avoid thrashing.
  • Set a maximum so a bug or an attack does not create a huge bill.
  • Stateful nodes (databases) do not autoscale as easily. Scale the stateless layer first.

How this gets asked

A new instance takes 3 minutes to boot and warm up. What does this imply for autoscaling?

  • Scale only after CPU hits 100 percent Users will suffer for 3 minutes.
  • Scale earlier, keep headroom or a warm pool Correct.
  • Disable autoscaling Throws away the benefit.
  • Use only one big server Single point of failure.

Warmup time means reactive scaling lags. Use lower thresholds, predictive or scheduled scaling, or spare capacity.

Interview questions: Load balancing

9 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What does a load balancer do?

Distributes requests across servers, performs health checks, removes failed servers, can terminate TLS and presents one stable address.

Basic Vertical versus horizontal scaling?

Vertical adds power to one machine (simple, limited, single point of failure). Horizontal adds machines (scales further, needs load balancing and stateless design).

Basic Why make web servers stateless?

Any instance can serve any request, so instances can be added, removed or replaced freely and failures lose no user state. State lives in shared stores or tokens.

Medium Layer 4 versus layer 7 load balancing?

L4 balances TCP or UDP connections by address and port, fast and simple. L7 understands HTTP and routes by path, header or cookie, terminates TLS and can apply auth and rate limits.

Medium Round robin versus least connections?

Round robin is simple and fine for uniform requests. Least connections adapts to uneven or long-lived requests by sending to the least busy server.

Medium What are sticky sessions and why avoid them?

The balancer pins a user to one server. It causes uneven load and loses session state on failure. Prefer a shared session store or client-side token.

Medium How do health checks go wrong?

Deep checks that depend on the database can eject the whole fleet during a blip. Use shallow checks, require several failures, and keep a minimum number of servers in rotation.

Advanced How do you make the load balancer itself highly available?

Run several in active-active across availability zones behind DNS or anycast, or an active-passive pair with a floating IP. Managed cloud load balancers do this for you.

Advanced What is the power of two choices?

Pick two random servers and send the request to the less loaded one. It nearly matches full least-load balancing with no global state and avoids herding.
