Part SD8

Queues, streams and asynchronous processing

Not every task should be done while the user waits. Queues and streams let you accept work quickly, process it at a safe pace, survive spikes and decouple services. They also bring duplicates, ordering and failure questions you must answer.

MediumAdvanced~3 hours

Why go asynchronous

Intuition

At a restaurant the waiter does not stand at the stove until your dish is ready. They hand a ticket to the kitchen and serve other tables. The ticket rail is a queue: the waiter (producer) is not blocked by the speed of the cook (consumer).

What a queue buys you

BenefitExplanation
DecouplingProducer and consumer need not know each other or be up at the same time
Load levellingA spike is absorbed by the queue and drained at a steady rate
ResilienceIf the consumer is down, work waits instead of failing
ScalabilityAdd more consumers to drain faster
Faster responsesReturn to the user immediately, finish slow work later

What it costs

Eventual results (the user does not see the outcome instantly), more moving parts, duplicates and reordering, harder debugging and the need for monitoring (queue depth, age).

Good candidates for async

Sending email or push notifications, image and video processing, report generation, payment settlement, search indexing, webhooks, analytics events, anything calling a slow or flaky third party.

Self-check

What do queues give you?

Decoupling, load levelling, resilience, scalability and fast responses.

Queues versus pub/sub versus logs

Point-to-point queue

Each message is delivered to one consumer (a worker pool). After processing and acknowledgement it is removed. Used for task distribution. Examples: Amazon SQS, RabbitMQ queues, Celery with a broker.

Publish/subscribe

A publisher sends to a topic. Every subscriber gets a copy. Used for fan-out: an order_placed event goes to inventory, email, analytics. Examples: SNS, Google Pub/Sub, RabbitMQ exchanges, Redis pub/sub (no durability).

Distributed log (Kafka)

Messages are appended to a durable, ordered log split into partitions. The log is retained for days (or forever), not deleted on read. Each consumer group keeps its own offset, so many independent consumers can read the same data, and new consumers can replay history.

Queue (SQS, RabbitMQ)Log (Kafka, Pulsar, Kinesis)
After consumeMessage deletedMessage stays until retention expires
ReplayNoYes, by resetting the offset
OrderingBest effort, FIFO queues availableStrict per partition
Fan-out to many appsNeeds copiesNative: independent consumer groups
ThroughputModerateVery high (millions of messages per second)
Best forTask queues, retries, delaysEvent streaming, event sourcing, pipelines

Partitions and ordering

Kafka guarantees order only within a partition. Choose the partition key (for example user_id) so that all events that must stay ordered share a partition. The number of partitions caps consumer parallelism in one group: 10 partitions can be read by at most 10 consumers in a group.

import hashlib
def partition(key, n=4):
    return int(hashlib.md5(key.encode()).hexdigest(), 16) % n
events = [("alice", "login"), ("bob", "login"), ("alice", "buy"), ("alice", "logout"), ("bob", "buy")]
parts = {}
for key, ev in events:
    parts.setdefault(partition(key), []).append((key, ev))
for p in sorted(parts):
    print("partition", p, parts[p])     # per key, the order is preserved

Output

partition 0 [('alice', 'login'), ('bob', 'login'), ('alice', 'buy'), ('alice', 'logout'), ('bob', 'buy')]

How this gets asked

Which gives you the ability to replay old events for a new consumer?

  • A classic task queue (message deleted after ack) Data is gone.
  • A log with retention, such as Kafka Correct.
  • A direct HTTP call No history.
  • Redis pub/sub Messages are not stored.

Logs keep data for the retention period and consumers track their own offsets.

A Kafka topic has 6 partitions. What is the maximum number of consumers in one consumer group that can read in parallel?

Each partition is consumed by at most one consumer in a group, so 6.

Self-check

Queue versus pub/sub versus log?

Queue: one consumer per message. Pub/sub: every subscriber gets a copy. Log: ordered, retained, consumers track offsets.

Delivery guarantees

The three semantics

SemanticsMeaningHow
At most onceA message may be lost, never duplicatedAcknowledge before processing
At least onceNever lost, may be duplicatedAcknowledge after processing, retry on failure
Exactly onceProcessed once in effectAt least once plus idempotent processing, or transactions inside one system

True exactly-once delivery over an unreliable network is impossible: if an acknowledgement is lost the sender cannot know whether the work happened. Practical systems get effectively once by combining at-least-once delivery with idempotent consumers. Kafka offers idempotent producers and transactions that give exactly-once within Kafka; once you touch an external system you still need idempotency.

Idempotency

An operation is idempotent if doing it twice has the same effect as doing it once. Techniques:

  • Idempotency key: the client sends a unique id with each request. The server stores (key, result) and returns the stored result on retries.
  • Natural idempotency: SET balance = 100 is idempotent; balance = balance + 10 is not.
  • Deduplication table: record processed message ids and skip repeats (with a unique constraint).
  • Conditional writes: UPDATE ... WHERE version = 7.
processed = set()
balance = {"acct": 100}

def handle(msg):
    if msg["id"] in processed:          # deduplicate
        return "duplicate ignored"
    balance["acct"] += msg["amount"]
    processed.add(msg["id"])
    return "applied"

m = {"id": "pay-123", "amount": 25}
print(handle(m), handle(m), handle(m), balance)   # redelivered three times

Output

applied duplicate ignored duplicate ignored {'acct': 125}
Key idea

Assume every message can arrive twice. Design consumers so that is harmless.

How this gets asked

A consumer acknowledges a message after processing it. Which semantics does this give?

  • At most once That is acknowledge before processing.
  • At least once Correct: a crash before the ack causes redelivery.
  • Exactly once, automatically Not by itself.
  • None It gives at-least-once.

Redelivery after a crash means duplicates are possible, so consumers must be idempotent.

How do practical systems achieve 'effectively once' processing?

  • By turning off retries That would lose messages.
  • At-least-once delivery plus idempotent consumers Correct.
  • Using larger messages No.
  • Using UDP No.

Duplicates are tolerated because applying them twice has the same effect as once.

Self-check

Why is exactly-once delivery impossible over a network?

A lost acknowledgement leaves the sender unable to know whether the work happened, so it must retry, which can duplicate.

Reliability patterns

Acknowledgements, visibility timeout and redelivery

A consumer receives a message, which becomes invisible for a visibility timeout. If the consumer acknowledges in time, the message is deleted. If it crashes or is slow, the timeout expires and the message is redelivered. Set the timeout above your worst-case processing time.

Retries with backoff

Retry transient failures with exponential backoff and jitter: wait base x 2^attempt plus a random amount, up to a cap. Without jitter, all clients retry together and overload the recovering service.

import random
random.seed(7)
def backoff(attempt, base=0.1, cap=5.0):
    return random.uniform(0, min(cap, base * 2 ** attempt))   # "full jitter"
print([round(backoff(a), 2) for a in range(8)])

Output

[0.03, 0.03, 0.26, 0.06, 0.86, 1.17, 0.29, 2.54]

Dead-letter queues

A poison message always fails (bad data, bug). After N attempts move it to a dead-letter queue (DLQ) for inspection, so it does not block everything or retry forever. Alert on DLQ depth, and build a way to replay after fixing.

The transactional outbox

Problem: you update the database and publish an event. If the process dies between the two, they disagree. The outbox pattern writes the event into an outbox table in the same database transaction as the business data. A separate relay (a poller, or change data capture from the transaction log such as Debezium) publishes the outbox rows and marks them sent. Delivery is at least once, so consumers deduplicate.

Ordering

Queues generally do not guarantee global order. If order matters per entity, partition by that entity's key and process each partition sequentially. Global ordering across everything limits you to one consumer and is rarely worth it.

How this gets asked

A message fails every time because of malformed data. What should happen?

  • Retry forever Blocks progress.
  • After several attempts move it to a dead-letter queue and alert Correct.
  • Delete it silently Loses data.
  • Restart the broker Does not help.

DLQs isolate poison messages so the rest of the queue flows.

What problem does the transactional outbox solve?

  • Slow queries No.
  • The dual-write problem: updating the DB and publishing an event atomically Correct.
  • Cache stampedes No.
  • DNS failover No.

The event is written in the same transaction as the data, and a relay publishes it later.

Self-check

How should retries be spaced?

Exponential backoff with jitter and a cap, so clients do not retry in lockstep.

Backpressure and flow control

If producers outpace consumers the queue grows without bound. Choices:

  • Bound the queue and block or reject new work when full (load shedding).
  • Scale consumers with autoscaling on queue depth or message age.
  • Rate limit producers or slow them (backpressure signals in reactive streams, TCP windows).
  • Drop or sample low-value work (metrics, logs).

Watch queue depth and especially age of the oldest message: depth can look fine while work is stuck.

How this gets asked

A useful health signal for a queue is the age of the message, not just its depth.

Depth can stay low while a stuck message keeps ageing; the oldest message's age shows real delay.

Self-check

How do you handle producers faster than consumers?

Bound the queue, scale consumers, rate limit producers, shed or sample low-value work.

Interview tip

When you add a queue to a design, always say three things: what happens on duplicates (idempotency), what happens on poison messages (DLQ), and what happens when the queue grows (backpressure and scaling).

Interview questions: Messaging

11 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Why use a message queue?

It decouples producers and consumers, absorbs spikes, enables retries, and lets slow work happen after returning to the user.

Basic Queue versus pub/sub?

A queue delivers each message to one consumer in a pool. Pub/sub delivers each message to every subscriber.

Medium At-most-once, at-least-once and exactly-once?

At most once may lose messages. At least once may duplicate. Exactly once in effect needs at-least-once plus idempotent consumers or transactional processing within one system.

Medium What is idempotency and how do you implement it?

Repeating an operation has the same effect as doing it once. Use idempotency keys with stored results, deduplication tables with unique constraints, natural idempotent updates, or conditional writes.

Medium What is a dead-letter queue?

A queue for messages that repeatedly fail, so poison messages do not block processing. Alert on its depth and provide a way to inspect and replay.

Medium How does Kafka differ from a traditional queue?

Kafka is a partitioned, replicated, retained log. Consumers track offsets, can replay, and many consumer groups read independently. Ordering holds within a partition.

Medium How do you preserve ordering?

Partition by the entity key so related events share a partition and process each partition sequentially. Global ordering is expensive and rarely needed.

Advanced Explain the transactional outbox.

Write the event to an outbox table in the same transaction as the business data. A relay or CDC publishes it afterwards, which avoids the dual-write inconsistency. Delivery is at least once so consumers deduplicate.

Advanced How do you handle backpressure?

Bound queues, autoscale consumers on lag or message age, rate limit or slow producers, and shed or sample low-value work. Monitor oldest message age.

Advanced Batch versus stream processing and watermarks?

Batch processes bounded data periodically; stream processes unbounded data continuously. Watermarks track event-time progress so windows can close despite late events.

Advanced Lambda versus Kappa architecture?

Lambda runs batch and speed layers and merges them (two code paths). Kappa uses only a stream layer and reprocesses by replaying the log.
