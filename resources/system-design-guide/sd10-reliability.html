Reliability, availability and resilience

Everything fails eventually: disks, networks, deploys, data centers, people. Reliable systems are not those that never fail, but those whose failures are contained, detected and recovered from fast. This part is the toolbox of patterns for that.

MediumAdvanced~3 hours

Measuring reliability

SLI, SLO, SLA

TermMeaningExample
SLI (indicator)A measured quantity about service healthFraction of requests answered under 300 ms without error
SLO (objective)An internal target for an SLI99.9 percent of requests succeed over 30 days
SLA (agreement)A contract with consequencesCredits if availability drops below 99.5 percent

Choose SLIs the user feels: availability (success rate), latency (percentiles), correctness, freshness, durability. Set the SLO below the SLA so you act before you pay.

Error budgets

An SLO of 99.9 percent allows 0.1 percent failure, about 43 minutes per month. That allowance is the error budget. While budget remains, ship features quickly. When it is spent, freeze risky launches and invest in reliability. This turns the argument between "move fast" and "be stable" into a shared number.

slo = 0.999
minutes_month = 30 * 24 * 60
budget = (1 - slo) * minutes_month
print("budget:", round(budget, 1), "minutes per 30 days")
used = 18
print("remaining after an 18 minute outage:", round(budget - used, 1))

Output

budget: 43.2 minutes per 30 days
remaining after an 18 minute outage: 25.2

The golden signals

Monitor latency, traffic, errors and saturation for every service (SD11).

Failure vocabulary

Fault (a component deviates), error (a wrong state), failure (the service stops meeting its spec). Resilience is stopping faults from becoming failures. MTBF is mean time between failures; MTTR is mean time to recover. Availability = MTBF / (MTBF + MTTR). Cutting recovery time is often cheaper than preventing every fault.

How this gets asked

An SLO of 99.95 percent over a 30 day month allows how many minutes of downtime? (round to the nearest minute)

Redundancy and failover

Eliminate single points of failure

List every component on the request path and ask "if this dies, what happens?" Every box needs a second copy or a justified exception: load balancers, app servers, databases, caches, queues, DNS, and even people (on-call rotas) and credentials (expiring certificates).

Redundancy styles

Failure domains

Spread copies across independent failure domains: different servers, racks, availability zones (separate data centers in one region) and regions. A zone outage should be a non-event (N+1 capacity: enough remaining capacity to carry full load when one zone is lost).

Self-check

What is N+1 capacity?

Enough spare capacity that losing one unit (such as a zone) still leaves enough to carry the full load.

Defensive patterns

Timeouts

Every network call needs a timeout. Without one, a hung dependency ties up threads and connections until you run out and the caller fails too. Choose timeouts from the callee's latency distribution (a little above p99), and make each caller's timeout smaller than its own caller's, so budgets nest (a deadline passed down the chain).

Retries

Retry only transient errors on idempotent operations, with exponential backoff and jitter and a retry budget (for example, at most 10 percent extra load). Retrying at every layer multiplies: three layers with three attempts each makes 27 calls for one failure, a retry storm that finishes off a struggling service.

Circuit breaker

Like an electrical breaker: after too many failures the breaker opens and calls fail immediately without hitting the sick dependency. After a cool-down it goes half-open, lets a trial request through and closes again if it succeeds.

class CircuitBreaker:
    def __init__(self, threshold=3, reset_after=10):
        self.threshold, self.reset_after = threshold, reset_after
        self.failures, self.state, self.opened_at = 0, "closed", 0
    def call(self, fn, now):
        if self.state == "open":
            if now - self.opened_at >= self.reset_after:
                self.state = "half-open"
            else:
                return "rejected (fail fast)"
        try:
            r = fn()
        except Exception:
            self.failures += 1
            if self.state == "half-open" or self.failures >= self.threshold:
                self.state, self.opened_at = "open", now
            return "error"
        self.failures, self.state = 0, "closed"
        return r

def bad(): raise RuntimeError("down")
def good(): return "ok"

cb = CircuitBreaker()
out = [cb.call(bad, t) for t in range(4)]          # trips open after 3 failures
out += [cb.call(good, 5)]                          # still open, rejected
out += [cb.call(good, 14)]                         # half-open probe succeeds
print(out, cb.state)

Output

['error', 'error', 'error', 'rejected (fail fast)', 'rejected (fail fast)', 'ok'] closed

Bulkheads

Isolate resources so one failing part cannot sink the ship: separate thread pools or connection pools per dependency, separate queues per customer tier, separate clusters for critical versus best-effort traffic.

Load shedding and rate limiting

When overloaded, deliberately reject some requests quickly (503 with Retry-After) rather than slow down for everyone. Shed low-priority work first (analytics before checkout). A system that does 100 percent of work for 50 percent of users beats one that times out for 100 percent.

Backpressure and queue limits

Bound every queue and thread pool. Unbounded queues turn overload into huge latency and memory exhaustion.

Graceful degradation

When a dependency fails, return something useful: serve cached or stale data, hide the recommendations widget, fall back to a default ranking, switch to read-only mode. Decide in advance which features are critical and which are optional.

Idempotency and safe retries

Make operations idempotent (SD8) so retries and replays are safe.

Health, watchdogs and self-healing

Automatic restarts on failed liveness checks, replacement of unhealthy instances by autoscaling groups or Kubernetes, and automatic failover of databases. Be careful that automation does not amplify a problem (a crash loop that restarts every pod during an outage).

Cascading failure

How it happens

  1. A dependency slows down.
  2. Callers' threads wait on it, pools fill, callers slow down.
  3. Their callers' resources fill. Retries add load.
  4. The whole call graph degrades, even parts that did not use the original dependency.

Defences

Timeouts, circuit breakers, bulkheads, retry budgets with jitter, load shedding, caching, capacity headroom (run at 50 to 70 percent so a node loss does not overload the rest), and gradual rollouts that limit blast radius.

Key idea

Fail fast and fail small. A fast error is cheaper than a slow success that blocks everything else.

Self-check

How do cascading failures start and spread?

A slow dependency fills callers' pools, causing slowness upstream, amplified by retries.

Disaster recovery

RPO and RTO

  • RPO (recovery point objective): how much data you can afford to lose, measured in time. RPO of 5 minutes means you may lose the last 5 minutes.
  • RTO (recovery time objective): how long you can be down.
StrategyRPORTOCost
Backup and restoreHoursHours to a dayLowest
Pilot light (data replicated, minimal compute)MinutesTens of minutesLow

Backups

Back up automatically, store copies in another region or account, encrypt them, keep versions, and test restores regularly. A backup you have never restored is a hope, not a backup. Use point-in-time recovery from the transaction log.

Multi-region

ConcernNotes
Traffic routingGeoDNS, anycast or a global load balancer, with health-based failover
Data replicationAsynchronous replication (risk of loss, low latency) or synchronous consensus across regions (strong but slow)
ConflictsActive-active writes need conflict resolution or region ownership of data
Cost and complexityLarge; justify with an RTO/RPO or latency requirement

Practising failure

Run game days and chaos engineering (kill instances, inject latency, drop a zone) in controlled ways to find weaknesses before real incidents do. Write blameless post-mortems with action items.

Deploying safely

Many outages come from changes. Reduce blast radius:

  • Canary: send 1 percent of traffic to the new version, watch metrics, then expand.
  • Blue/green: run two full environments and switch traffic, with instant rollback.
  • Feature flags: decouple deploy from release and kill a bad feature without a deploy.
  • Automatic rollback on SLO breach.
  • Backward-compatible database migrations in several steps (add column, backfill, switch, remove).

See SD11 for pipelines and observability.

Interview questions: Reliability

11 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What are SLI, SLO and SLA?

SLI is a measured indicator, SLO is the internal target for it, SLA is the contractual commitment with penalties.

Basic What is a single point of failure?

A component whose failure takes down the system. Remove by redundancy across independent failure domains, with automatic failover.

Medium What is an error budget?

The allowed unreliability implied by the SLO (0.1 percent for 99.9). Spend it on velocity; when exhausted, prioritise reliability work.

Medium Explain timeouts, retries and backoff.

Every call needs a timeout. Retry only transient errors on idempotent operations with exponential backoff, jitter and a retry budget, at one layer only to avoid retry storms.

Medium How does a circuit breaker work?

After enough failures it opens and fails fast, then after a cool-down goes half-open to probe, closing again if the probe succeeds.

Medium What is a bulkhead?

Isolating resources (thread pools, queues, clusters) per dependency or tenant so one failure cannot exhaust everything.

Medium What is graceful degradation?

Keeping core functionality when parts fail by serving cached or default data, disabling optional features or switching to read-only mode.

Advanced How do cascading failures happen and how do you stop them?

A slow dependency fills caller pools and retries add load, spreading the failure. Stop with timeouts, circuit breakers, bulkheads, load shedding, retry budgets and capacity headroom.

Advanced RPO and RTO and DR strategies?

RPO is tolerable data loss; RTO is tolerable downtime. Strategies range from backup and restore (hours) through pilot light and warm standby to active-active multi-region (near zero) at rising cost.

Advanced How would you design for multi-region?

Route with GeoDNS or anycast, replicate data (asynchronous for latency, consensus for strictness), decide data ownership per region to avoid write conflicts, and test failover regularly.

Advanced How do you deploy safely?

Canary and blue/green releases, feature flags, automatic rollback on SLO breach, backward-compatible migrations, and small frequent changes.
