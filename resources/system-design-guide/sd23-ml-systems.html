Designing ML and AI systems: feature stores, serving, recommendation, search and LLM applications

Interviewers increasingly ask you to design systems with a model in the middle. The model is a small box; most of the design is the data, features, serving path, feedback loop and monitoring around it. This part gives the architecture and the numbers.

Advanced~4 hours

The ML system lifecycle

Start every ML design by pinning down: the business metric (revenue, watch time, fraud loss), the model metric (precision, recall, AUC, NDCG), the latency budget (e.g. 100 ms end to end), the data available and the cost of errors (a false fraud block versus a missed fraud).

Data and features

  • Sources: event logs, databases (via CDC), third-party data, human labels, implicit feedback (clicks, dwell time).
  • Label quality dominates model quality. Beware leakage (features that contain the future), selection bias (you only see outcomes for what you showed) and delayed labels (a fraud chargeback arrives weeks later).
  • Training-serving skew: features computed one way offline and another online silently destroy accuracy. Fix with one definition of each feature, shared code, and a feature store.
Feature store partRole
Offline store (warehouse/lake)Large history for training, point-in-time correct joins
Online store (Redis, DynamoDB)Low-latency latest values for serving, single-digit ms
RegistryNames, owners, definitions, freshness SLAs
PipelinesBatch and streaming jobs that keep both stores in sync

Point-in-time correctness means a training row for time t uses only feature values known before t.

import bisect
history = {"u1": [(1, 3), (5, 7), (9, 12)]}          # user_id -> [(timestamp, purchases_so_far)]
def feature_at(user, t):
    ts = [x[0] for x in history[user]]
    i = bisect.bisect_right(ts, t) - 1
    return history[user][i][1] if i >= 0 else 0
for event_time in (4, 5, 8, 10):
    print(f"label at t={event_time}: feature value known then = {feature_at('u1', event_time)} (using the latest value, 12, would leak the future)")

How this gets asked

What is training-serving skew?

  • Slow training No.
  • Features computed differently offline and online, degrading live accuracy Correct.
  • A GPU bug No.
  • Class imbalance No.

A feature store with shared definitions prevents it.

What does point-in-time correctness require?

  • Using the latest feature value for every row That leaks the future.
  • Training rows use only feature values available before the label time Correct.
  • Random sampling No.
  • Normalising features No.

Otherwise offline metrics are inflated.

Self-check

Why a feature store?

To share one definition of each feature across training and serving and provide both historical and low-latency access.

Serving design: model behind a stateless service (TorchServe, Triton, TF Serving, a plain API), dynamic batching to raise GPU throughput, quantisation and distillation to cut cost, autoscaling on queue depth, a model registry with versioning, canary and shadow deployments, and a fallback (default or simple model) when the model is slow or down.

Capacity maths: a GPU handling a batch of 32 in 40 ms serves about 800 requests/s. For 20,000 requests/s at peak you need at least ceil(20000 / 800) = 25 GPUs plus headroom.

import math
batch, batch_ms, peak_qps, headroom = 32, 40, 20000, 1.3
per_gpu = batch / (batch_ms / 1000)
print(f"per GPU: {per_gpu:.0f} req/s | GPUs for peak: {math.ceil(peak_qps / per_gpu)} | with 30% headroom: {math.ceil(peak_qps * headroom / per_gpu)}")

Output

per GPU: 800 req/s | GPUs for peak: 25 | with 30% headroom: 33

How this gets asked

A GPU serves 32 requests per 40 ms batch. Requests per second per GPU?

32 / 0.040 = 800.

Self-check

Name three serving optimisations.

Dynamic batching, quantisation or distillation, and caching or routing easy requests to smaller models.

Recommendation and ranking: funnel architecture

You cannot score millions of items per request. Use a funnel:

  1. Candidate generation (retrieval): from millions to hundreds, with cheap methods: collaborative filtering, two-tower embeddings plus approximate nearest neighbours, popular and recent items, "followed accounts". Several retrievers are merged.
  2. Ranking: a heavier model (gradient boosting or a deep network) scores a few hundred with rich features and predicts click, watch, purchase.
  3. Re-ranking: apply business rules and diversity, freshness, fairness, deduplication, ads insertion.

Metrics: offline recall@k, NDCG, AUC; online CTR, watch time, retention via A/B tests. Handle cold start (new users and items) with content features and exploration (bandits), and the feedback loop (you train on what you showed) with exploration and counterfactual care.

import math
def dcg(rels): return sum(r / math.log2(i + 2) for i, r in enumerate(rels))
def ndcg(rels):
    ideal = dcg(sorted(rels, reverse=True))
    return dcg(rels) / ideal if ideal else 0.0
print("relevant item first :", round(ndcg([3, 2, 0, 0]), 3))
print("relevant item last  :", round(ndcg([0, 0, 2, 3]), 3))

Output

relevant item first : 1.0
relevant item last  : 0.538

How this gets asked

Why use a retrieval then ranking funnel?

  • It is simpler No.
  • Scoring millions of items with a heavy model per request is too slow; cheap retrieval narrows candidates first Correct.
  • Models cannot rank No.
  • It reduces accuracy No.

The funnel balances recall, accuracy and latency.

Which metric rewards putting relevant items near the top?

  • Accuracy Position-blind.
  • NDCG Correct.
  • Recall at N with no order Position-blind.
  • RMSE Regression metric.

Discounts relevance by log of rank.

What are the three stages of a recommender?

Candidate retrieval, ranking, and re-ranking with business rules.

Vector search and embeddings

An embedding maps text, images or items to vectors where similar things are close. Nearest neighbour search finds the closest vectors; exact search is O(N d), so systems use approximate nearest neighbour (ANN) indexes: HNSW (graph, high recall, memory heavy), IVF (cluster then search a few clusters), PQ (compress vectors). Trade recall for latency and memory. Add metadata filters, hybrid keyword plus vector search, and periodic re-embedding when the model changes.

import math, random
random.seed(0)
d, N = 16, 2000
vecs = [[random.gauss(0, 1) for _ in range(d)] for _ in range(N)]
norm = lambda v: math.sqrt(sum(x * x for x in v))
unit = lambda v: [x / norm(v) for x in v]
db = [unit(v) for v in vecs]
q = unit([x + random.gauss(0, 0.3) for x in vecs[123]])          # a noisy copy of item 123
dot = lambda a, b: sum(x * y for x, y in zip(a, b))
best = sorted(range(N), key=lambda i: -dot(db[i], q))[:3]
print("exact top-3 by cosine similarity:", best, "(item 123 should be first)")
# IVF-style: assign to 20 random centroids, search only the nearest 3 clusters
cents = random.sample(db, 20)
assign = [max(range(20), key=lambda c: dot(db[i], cents[c])) for i in range(N)]
near = sorted(range(20), key=lambda c: -dot(q, cents[c]))[:3]
cand = [i for i in range(N) if assign[i] in near]
approx = sorted(cand, key=lambda i: -dot(db[i], q))[:3]
print(f"approximate search scanned {len(cand)} of {N} vectors, top-3:", approx, "| finds item 123:", 123 in approx)

Output

exact top-3 by cosine similarity: [123, 1197, 363] (item 123 should be first)
approximate search scanned 269 of 2000 vectors, top-3: [123, 1197, 363] | finds item 123: True

How this gets asked

Why use approximate nearest neighbour search?

  • It is exact No.
  • Exact search over millions of vectors is too slow; ANN trades small recall loss for large speedups Correct.
  • It needs no memory No.
  • It avoids embeddings No.

HNSW, IVF and PQ are common ANN techniques.

LLM and RAG application architecture

  • Ingestion: parse documents, chunk (200 to 800 tokens with overlap), embed, store vectors plus metadata and permissions.
  • Serving: stream tokens to the client, cache by prompt hash, set max tokens and timeouts, retry with backoff, route simple questions to a smaller, cheaper model.
  • Cost model: cost = (input tokens x input price) + (output tokens x output price); long contexts and repeated prefixes dominate, so use prompt caching and trim context.
  • LLM serving internals: the KV cache stores attention keys and values to avoid recomputation; continuous batching and paged attention (vLLM) raise throughput; latency is time to first token plus tokens per second.
  • Safety and quality: prompt-injection defences (treat retrieved text as untrusted data), PII filtering, output validation (JSON schema), evaluation sets with automated and human grading, observability of prompts, retrieved context and costs.
  • Agents add tool calls and loops: bound iterations, validate tool arguments, sandbox side effects, require approval for risky actions.
price_in, price_out = 3.00, 15.00                          # dollars per million tokens (illustrative)
def cost(tin, tout, requests): return requests * (tin * price_in + tout * price_out) / 1e6
base = cost(6000, 400, 1_000_000)
trimmed = cost(2500, 400, 1_000_000)
print(f"1M requests/month: ${base:,.0f} with 6000 input tokens vs ${trimmed:,.0f} after trimming context to 2500 ({1 - trimmed / base:.0%} saved)")

Output

1M requests/month: $24,000 with 6000 input tokens vs $13,500 after trimming context to 2500 (44% saved)

How this gets asked

What is the main purpose of RAG?

  • To train a new model No.
  • To ground the model's answers in retrieved, current, private documents Correct.
  • To compress prompts No.
  • To avoid tokens No.

It reduces hallucination and keeps knowledge fresh without retraining.

Self-check

What does the KV cache do?

Stores attention keys and values of earlier tokens so each new token needs only incremental computation.

Monitoring ML in production

Models decay because the world changes.

  • Data drift: input distributions shift (new devices, seasons). Track feature statistics (PSI, KS test).
  • Concept drift: the relationship between inputs and the label changes.
  • Quality: delayed ground truth, online A/B metrics, shadow comparisons, human review samples.
  • System metrics: latency percentiles, errors, GPU utilisation, queue depth, cost per prediction.
  • Triggers: scheduled retraining, drift alerts, or performance drops. Keep reproducibility (data version, code, parameters) and the ability to roll back a model like any release.
Key idea

Design the loop: data, features (one definition, point-in-time correct), a funnel from cheap retrieval to expensive ranking, a serving path with batching and fallbacks, and monitoring for drift and cost. State the latency budget and capacity numbers, and say how you would know the model is getting worse.

How this gets asked

What is data drift?

  • A broken pipeline Different problem.
  • A change in the distribution of input features over time Correct.
  • A GPU error No.
  • Overfitting No.

It can degrade a model silently.

Self-check

Data drift versus concept drift?

Data drift changes the inputs; concept drift changes the relationship between inputs and the target.

Interview questions: ML systems design

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What are the stages of an ML system?

Define objective and metrics, collect and label data, build features, train and evaluate, deploy and serve, monitor and retrain.

Basic Batch versus online inference?

Batch precomputes predictions on a schedule and stores them; online computes per request with latency limits. Choose by freshness needs and cost.

Medium What is training-serving skew and how do you avoid it?

Features computed differently in training and production silently hurt accuracy. Use shared feature definitions, a feature store and logging served features for training.

Medium What does a feature store provide?

Consistent feature definitions, an offline store for training with point-in-time joins, an online store for low-latency serving, and a registry with ownership and freshness.

Medium Explain the recommendation funnel.

Candidate generation narrows millions of items to hundreds cheaply, ranking scores them with a richer model, and re-ranking applies diversity, business rules and freshness.

Medium How do you handle cold start?

Use content features, popularity and context, explore with bandits, and ask for explicit preferences; update quickly as interactions arrive.

Medium How do you decide a new model is better?

Offline metrics on a held-out, time-split set, then an online A/B test on business metrics with guardrail metrics and enough statistical power.

Medium What is data drift and how do you detect it?

The input distribution changes over time. Monitor feature statistics with PSI or KS tests, and track prediction distributions and delayed label performance.

Advanced How do you serve a model at 20,000 requests per second?

Estimate per-instance throughput, use dynamic batching, quantisation or distillation, autoscaling on queue depth, caching, a fallback model and canary deployments.

Advanced Explain approximate nearest neighbour search.

Exact search is O(N d). ANN indexes such as HNSW, IVF and PQ trade a little recall for large speedups and memory savings.

Advanced Design a RAG system.

Ingest, chunk and embed documents with permissions; at query time rewrite, retrieve (vector plus keyword), re-rank, build a prompt, generate with citations, and apply guardrails, caching and evaluation.

Advanced How do you control LLM application cost and latency?

Trim context, cache prompts and results, route simple requests to smaller models, stream output, set token limits and batch offline work.

Advanced What is a feedback loop problem in recommenders?

The model is trained on what it previously showed, reinforcing its own biases. Counter with exploration, randomised traffic and counterfactual evaluation.

Advanced How do you avoid label leakage?

Ensure features use only information available at prediction time, split data by time, and make joins point-in-time correct.
