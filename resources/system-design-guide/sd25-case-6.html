Case studies 6: ID generator, distributed lock, job scheduler, order book, code judge, distributed file system

These cases are the building blocks other systems depend on. They are shorter to describe but full of subtle correctness points: clocks, leases, ordering and failure of coordinators. Each has a small program that demonstrates the key mechanism.

Case 1: Unique ID generator

Requirements

Generate 64-bit ids, unique across many machines without coordination on each call, roughly time-sortable (useful for database indexes), at 10,000+ ids/s per node, with no single point of failure.

Options

ApproachProsCons
Auto-increment in one databaseSimple, orderedSingle point of failure and bottleneck
UUID v4 (128-bit random)No coordinationBig, random order wrecks B-tree locality
UUID v7 / ULID (time prefix + random)Sortable, no coordination128-bit
Ticket server with rangesFewer round tripsGaps, coordinator dependency
Snowflake64-bit, sortable, no coordinationNeeds unique worker ids and a sane clock

Snowflake layout

1 sign bit | 41 bits timestamp (ms since a custom epoch) | 10 bits worker id | 12 bits sequence. 41 bits of milliseconds is about 69 years. 12 bits allow 4096 ids per millisecond per worker, so 4 million ids/s per worker, 1024 workers.

Hard parts: assigning unique worker ids (via ZooKeeper/etcd or config) and clock going backwards (NTP step): refuse to generate until time catches up, or use the last timestamp.

import threading
EPOCH = 1_600_000_000_000
class Snowflake:
    def __init__(self, worker, clock):
        self.worker, self.clock, self.last, self.seq = worker, clock, -1, 0
    def next(self):
        now = self.clock() - EPOCH
        if now < self.last: raise RuntimeError(f"clock moved backwards by {self.last - now} ms")
        if now == self.last:
            self.seq = (self.seq + 1) & 0xFFF
            if self.seq == 0:                         # sequence exhausted: wait for next millisecond
                now = self.last + 1
        else:
            self.seq = 0
        self.last = now
        return (now << 22) | (self.worker << 12) | self.seq
    @staticmethod
    def decode(i): return {"ms_since_epoch": i >> 22, "worker": (i >> 12) & 0x3FF, "seq": i & 0xFFF}
t = [EPOCH + 5000]
a, b = Snowflake(1, lambda: t[0]), Snowflake(2, lambda: t[0])
ids = [a.next() for _ in range(3)] + [b.next() for _ in range(2)]
t[0] += 1
ids += [a.next()]
print("ids:", ids)
print("decoded last:", Snowflake.decode(ids[-1]))
print("unique:", len(set(ids)) == len(ids), "| sorted by time within a worker:", ids[:3] == sorted(ids[:3]))
t[0] -= 10
try: a.next()
except RuntimeError as e: print("clock rollback handled:", e)

Output

decoded last: {'ms_since_epoch': 5001, 'worker': 1, 'seq': 0}
unique: True | sorted by time within a worker: True

How this gets asked

How many ids per millisecond can one Snowflake worker generate with a 12-bit sequence?

2^12 = 4096.

What is the main risk of Snowflake ids?

  • Too long They are 64-bit.
  • The system clock moving backwards, or two workers sharing a worker id Correct.
  • They are random They are time ordered.
  • They need a database call No.

Duplicates are possible if either assumption is broken.

Snowflake bit layout?

1 sign bit, 41 bits of timestamp, 10 bits of worker id and 12 bits of sequence.

Case 2: Distributed lock

Requirements

Mutual exclusion across processes on different machines (leader duty, singleton jobs), safe under crashes, pauses and network partitions.

The naive lock and its flaw

SET key owner NX PX 30000 in Redis acquires a lock with a lease (expiry), so a crashed holder cannot block everyone forever. But a client may pause (GC, VM freeze) beyond the lease, wake up and write, while another client has taken the lock: two writers at once.

Fencing tokens

The lock service returns a monotonically increasing token with each grant. The protected resource (database, storage) remembers the highest token it has seen and rejects older ones. Now a zombie holder's write is refused.

class LockService:
    def __init__(self): self.token, self.holder, self.expires = 0, None, 0
    def acquire(self, client, now, lease):
        if self.holder is None or now >= self.expires:
            self.token += 1
            self.holder, self.expires = client, now + lease
            return self.token
        return None
class Storage:
    def __init__(self): self.max_token, self.value = 0, None
    def write(self, token, value):
        if token < self.max_token: return f"REJECTED stale token {token} (seen {self.max_token})"
        self.max_token, self.value = token, value
        return f"accepted token {token}"
lock, store = LockService(), Storage()
t1 = lock.acquire("A", now=0, lease=10)
print("A acquires, token", t1)
print("A pauses (GC) past its lease; B acquires at t=15:", lock.acquire("B", now=15, lease=10))
t2 = lock.token
print("B writes:", store.write(t2, "from B"))
print("A wakes up and writes with its old token:", store.write(t1, "from A (zombie)"))
print("final value:", store.value)

Output

A acquires, token 1
A pauses (GC) past its lease; B acquires at t=15: 2
B writes: accepted token 2
A wakes up and writes with its old token: REJECTED stale token 1 (seen 2)
final value: from B

Production options

  • ZooKeeper / etcd: lock via ephemeral nodes or leases built on consensus (Raft/Zab); tokens are the revision numbers. Strongest guarantees.
  • Redis: fast but not consensus-based; failover can lose a lock. Redlock is debated; for correctness-critical work use a consensus service plus fencing.
  • Database row lock or a unique-key insert: simplest when you already have a database.
  • Prefer designs that avoid locks: idempotent operations, partition ownership, or compare-and-set.

How this gets asked

What do fencing tokens protect against?

  • Slow networks No.
  • A paused client that wakes after its lease expired and writes as if it still held the lock Correct.
  • Weak passwords No.
  • Clock skew only Partly, but not their purpose.

The resource rejects tokens older than the newest seen.

Why give locks a lease (expiry)?

  • To save memory No.
  • So a crashed holder cannot block everyone forever Correct.
  • To speed up writes No.
  • For logging No.

At the cost of needing fencing for safety.

Self-check

Why is a leased lock alone unsafe?

A paused holder can still write after expiry; fencing tokens let the resource reject it.

Case 3: Job scheduler

Requirements

Run jobs at a time or on a cron schedule, at scale (millions of jobs), at least once, with retries, priorities, and no missed or duplicate runs after failures.

Design

  • Job table: id, schedule, next_run_at, payload, status, attempts, lease_until. Index on (next_run_at) for the due scan.
  • Polling scan each second for jobs with next_run_at <= now; mark them with a lease using a conditional update so only one scheduler instance claims each job. Partition by job id hash so several schedulers share the load without overlap.
  • Workers pull from the queue, run the job, then update the status. If a worker dies, its lease expires and the job becomes claimable again (at-least-once, so jobs must be idempotent).
  • Retries with exponential backoff and jitter, then a dead letter state. Cron jobs compute the next run after each execution.
  • Precision at scale: a min-heap or timing wheel in memory for the next few seconds, with the database as the durable truth.
import heapq
class Scheduler:
    def __init__(self): self.heap, self.log = [], []
    def add(self, run_at, name, every=None): heapq.heappush(self.heap, (run_at, name, every))
    def run_until(self, now):
        while self.heap and self.heap[0][0] <= now:
            t, name, every = heapq.heappop(self.heap)
            self.log.append((t, name))
            if every: heapq.heappush(self.heap, (t + every, name, every))      # reschedule cron-like job
s = Scheduler()
s.add(5, "report", every=10); s.add(7, "email"); s.add(12, "cleanup")
s.run_until(30)
print(s.log)

Output

[(5, 'report'), (7, 'email'), (12, 'cleanup'), (15, 'report'), (25, 'report')]

How this gets asked

How are due jobs claimed safely by multiple scheduler instances?

  • Everyone runs all jobs Duplicates.
  • A conditional update that sets a lease and succeeds for only one instance Correct.
  • Random sleep Unreliable.
  • Manual assignment No.

Compare-and-set on job state.

Self-check

Why must scheduled jobs be idempotent?

Delivery is at least once: leases expire and jobs may run twice.

Case 4: Stock exchange order book

Requirements

Match buy and sell orders with price-time priority and deterministic results, at very low latency (microseconds) and high throughput (hundreds of thousands of orders/s), with strict fairness and audit.

Core model

For one symbol: a bid book (buyers, highest price first) and an ask book (sellers, lowest price first). Within a price level, the earliest order goes first. An incoming order is matched against the opposite side while prices cross; any remainder rests in the book (limit order). Matching is single-threaded per symbol to be deterministic and avoid locks; scale by sharding symbols across engines.

import heapq, itertools
class OrderBook:
    def __init__(self): self.bids, self.asks, self.seq, self.trades = [], [], itertools.count(), []
    def add(self, side, price, qty, oid):
        order = [qty, oid]
        if side == "buy":
            while order[0] and self.asks and self.asks[0][0] <= price:
                ap, _, ao = self.asks[0]
                fill = min(order[0], ao[0]); order[0] -= fill; ao[0] -= fill
                self.trades.append((oid, ao[1], ap, fill))
                if ao[0] == 0: heapq.heappop(self.asks)
            if order[0]: heapq.heappush(self.bids, (-price, next(self.seq), order))
        else:
            while order[0] and self.bids and -self.bids[0][0] >= price:
                bp, _, bo = self.bids[0]
                fill = min(order[0], bo[0]); order[0] -= fill; bo[0] -= fill
                self.trades.append((bo[1], oid, -bp, fill))
                if bo[0] == 0: heapq.heappop(self.bids)
            if order[0]: heapq.heappush(self.asks, (price, next(self.seq), order))
book = OrderBook()
book.add("sell", 101, 50, "S1"); book.add("sell", 100, 30, "S2"); book.add("sell", 100, 20, "S3")
book.add("buy", 99, 40, "B1")                # does not cross: rests in the book
book.add("buy", 101, 70, "B2")               # crosses: takes S2 (30) and S3 (20) at 100 (time priority), then 20 of S1 at 101
print("trades (buyer, seller, price, qty):", book.trades)
print("resting asks:", [(p, o[1], o[0]) for p, _, o in sorted(book.asks)], "| resting bids:", [(-p, o[1], o[0]) for p, _, o in sorted(book.bids)])

Output

trades (buyer, seller, price, qty): [('B2', 'S2', 100, 30), ('B2', 'S3', 100, 20), ('B2', 'S1', 101, 20)]
resting asks: [(101, 'S1', 30)] | resting bids: [(99, 'B1', 40)]

Deep dives

  • Latency: in-memory book, no database in the hot path, kernel bypass networking, pinned CPU cores, preallocated memory, a single writer.
  • Durability: an input event journal (sequenced, replicated) is the truth; the book is rebuilt by replaying it (event sourcing). Hot standby engines process the same sequence and take over on failure.
  • Gateways validate and risk-check orders; a sequencer assigns global order; market data is multicast to subscribers; the settlement system consumes trades asynchronously.
  • Fairness and audit: deterministic replay must reproduce every trade exactly.

How this gets asked

What does price-time priority mean?

  • Oldest orders first regardless of price Ignores price.
  • Best price first, and earlier orders first within the same price Correct.
  • Largest orders first No.
  • Random No.

It is the standard fairness rule.

Self-check

Why is matching single-threaded per symbol?

Determinism and no locking; scale by sharding symbols.

Case 5: Online code judge

Requirements

Users submit code; run it against hidden tests under limits (time, memory, no network, no file access) and report a verdict within seconds. Contest bursts: thousands of submissions in a minute.

Design

  1. API stores the submission and enqueues a job; the client polls or subscribes for the verdict.
  2. Queue decouples bursts from capacity; autoscale workers on queue depth; prioritise contest traffic.
  3. Sandboxed workers: a fresh container or microVM (gVisor, Firecracker) per run, with cgroups limiting CPU and memory, seccomp syscall filters, no network, read-only filesystem, a temporary writable directory, and wall-clock and CPU timeouts. Never run untrusted code on the application host.
  4. Compile once, run many: compile in the sandbox, cache binaries by hash, run each test case with the limits.
  5. Verdicts: accepted, wrong answer, time limit exceeded, memory limit exceeded, runtime error, compile error. Compare outputs with a checker (exact, token-based or special judge).
  6. Storage: test data in object storage, cached on workers; results in a database; leaderboard in Redis for contests.
  7. Fairness: run on identical hardware class, measure CPU time not wall time, repeat borderline timings.
import subprocess, sys, tempfile, os
def judge(code, stdin, expected, timeout=2):
    with tempfile.TemporaryDirectory() as d:
        path = os.path.join(d, "sol.py")
        open(path, "w").write(code)
        try:
            r = subprocess.run([sys.executable, "-I", path], input=stdin, capture_output=True, text=True, timeout=timeout)
        except subprocess.TimeoutExpired:
            return "Time Limit Exceeded"
        if r.returncode != 0: return "Runtime Error"
        return "Accepted" if r.stdout.split() == expected.split() else "Wrong Answer"
good = "a, b = map(int, input().split())" + chr(10) + "print(a + b)"
print(judge(good, "3 4", "7"))
print(judge("print(1)", "", "2"))
print(judge("while True: pass", "", "", timeout=1))
print(judge("raise SystemExit(3)", "", ""))

  • To save disk No.
  • To prevent it from attacking the host, using the network or exhausting resources Correct.
  • To format code No.
  • To speed up compiles No.

Containers/microVMs with syscall filters and cgroup limits.

Case 6: Distributed file system (GFS / HDFS)

Requirements

Store huge files (GB to TB) across thousands of commodity machines that fail daily; optimised for large sequential reads and appends rather than small random writes.

Architecture

  • Files are split into large blocks/chunks (64 to 256 MB), each replicated (default 3) on different machines and racks.
  • A metadata server (NameNode / GFS master) keeps the namespace and the map file to block to locations in memory, persisted via an edit log plus checkpoints. It is a single point of failure, so use a standby with shared journal (HDFS HA with ZooKeeper).
  • DataNodes / chunkservers store blocks and send heartbeats and block reports. Missing heartbeats mark a node dead and trigger re-replication to restore the replica count.
  • Read: client asks the metadata server for block locations, then reads directly from the nearest DataNode (data never flows through the master).
  • Write: the client gets a list of nodes for each block and streams data through a replication pipeline (A to B to C); acknowledgements flow back.
  • Rack awareness: put replicas on at least two racks, so a rack failure loses at most one replica.
  • Integrity: checksums per block, verified on read and by background scrubbing.
  • Small files are a problem (the metadata is in memory): pack them into larger containers (sequence files, Parquet).
  • Erasure coding (for example 6 data + 3 parity blocks) cuts storage overhead from 3x to 1.5x for cold data at the price of reconstruction cost.
import random
random.seed(5)
nodes = [f"n{i}" for i in range(9)]
racks = {n: f"rack{i // 3}" for i, n in enumerate(nodes)}                  # 3 racks of 3 nodes
def place(replicas=3):
    first = random.choice(nodes)
    second = random.choice([n for n in nodes if racks[n] != racks[first]])
    third = random.choice([n for n in nodes if racks[n] == racks[second] and n != second])
    return [first, second, third]
blocks = {f"blk{i}": place() for i in range(6)}
print({b: [f"{n}/{racks[n]}" for n in ns] for b, ns in list(blocks.items())[:2]})
dead = "n4"
under = [b for b, ns in blocks.items() if dead in ns]
for b in under:                                                           # re-replicate to restore 3 copies
    live = [n for n in blocks[b] if n != dead]
    new = random.choice([n for n in nodes if n not in blocks[b]])
    blocks[b] = live + [new]
print(f"node {dead} died: re-replicated {len(under)} block(s); every block still has 3 copies on >= 2 racks:",
      all(len(set(ns)) == 3 and len({racks[n] for n in ns}) >= 2 for ns in blocks.values()))

Output

{'blk0': ['n4/rack1', 'n8/rack2', 'n7/rack2'], 'blk1': ['n8/rack2', 'n0/rack0', 'n2/rack0']}
node n4 died: re-replicated 1 block(s); every block still has 3 copies on >= 2 racks: True
Key idea

Infrastructure cases are won on correctness details: Snowflake needs unique workers and a monotonic clock, locks need fencing tokens, schedulers need leases and idempotent jobs, exchanges need a deterministic single-threaded matcher with a journal, judges need a real sandbox, and file systems need replication placement and re-replication.

How this gets asked

In HDFS, how does a client read a file?

  • All data flows through the NameNode Only metadata does.
  • It gets block locations from the metadata server and reads blocks directly from DataNodes Correct.
  • From a single machine No.
  • From the database No.

This keeps the master off the data path.

Self-check

What triggers re-replication?

Missed heartbeats mark a DataNode dead, and the metadata server copies its blocks to restore the target replica count.

Interview questions: Case studies 6

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Why are UUIDs sometimes a poor primary key?

Random 128-bit values are large and scatter inserts across a B-tree. Time-ordered ids such as ULID, UUIDv7 or Snowflake give locality.

Medium Describe the Snowflake id layout.

1 sign bit, 41 bits of milliseconds since a custom epoch, 10 bits of worker id and 12 bits of sequence, giving 4096 ids per millisecond per worker.

Medium What goes wrong if the clock moves backwards in a Snowflake generator?

It could repeat timestamps and produce duplicate ids. Detect it, wait or refuse, and keep the last timestamp.

Medium Why does a lease-based distributed lock need fencing tokens?

A paused holder can wake after its lease expired and write while another holds the lock. The resource rejects tokens older than the newest seen.

Medium How do multiple scheduler instances avoid running the same job twice?

Partition jobs by hash and claim jobs with a conditional update that sets a lease, so only one instance wins; jobs are still idempotent for lease expiry.

Medium How are retries handled in a job scheduler?

Exponential backoff with jitter, an attempt counter and a dead letter state after the limit.

Medium How does a code judge keep untrusted code safe?

Containers or microVMs with cgroup CPU and memory limits, seccomp filters, no network, read-only filesystems and wall-clock timeouts, with fresh sandboxes per run.

Medium How does a client read a file in HDFS?

It asks the NameNode for block locations, then reads blocks directly from the nearest DataNodes; data does not flow through the NameNode.

Advanced Redis lock versus ZooKeeper or etcd lock?

Redis is fast but not consensus-based, so failover can lose a lock. ZooKeeper and etcd use consensus and provide stronger guarantees and revision numbers usable as fencing tokens.

Advanced Why is an exchange matching engine single-threaded per symbol?

Price-time priority needs strict deterministic ordering, and avoiding locks gives microsecond latency. Throughput scales by sharding symbols.

Advanced How does a matching engine recover from a crash?

Replay the sequenced input journal into a fresh book (event sourcing), or fail over to a hot standby that processed the same sequence.

Advanced How does HDFS stay available when nodes die?

Blocks are replicated (3 by default) across racks; missed heartbeats trigger re-replication; the NameNode has a standby with a shared edit log.

Advanced Why does HDFS struggle with many small files?

The NameNode keeps all metadata in memory, so millions of small files exhaust it; pack them into larger containers.

Advanced Replication versus erasure coding?

Replication (3x) is simple and fast to read; erasure coding (for example 6+3) cuts overhead to 1.5x for cold data but makes reconstruction costlier.
