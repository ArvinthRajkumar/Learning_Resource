Search, big data and specialised data structures

Some problems keep appearing in system designs: searching text, counting unique things cheaply, finding nearby places, generating unique ids, handling mountains of data. Each has a standard solution worth knowing in detail.

Advanced~4 hours

Search

The inverted index

A search engine does not scan documents. It builds an inverted index: for every term, the list of documents containing it (a postings list), often with positions and counts.

TermPostings (doc ids)
cache1, 4, 7
database1, 2, 7
queue3, 4

A query for cache AND database intersects the postings: documents 1 and 7. Postings are kept sorted so intersection is a fast merge.

import re
docs = {
    1: "cache the database reads",
    2: "database replication and sharding",
    3: "a queue decouples workers",
    4: "queue and cache for speed",
    7: "database cache design",
}
index = {}
for doc_id, text in docs.items():
    for term in set(re.findall(r"[a-z]+", text.lower())):
        index.setdefault(term, []).append(doc_id)
for t in index:
    index[t].sort()

def search_and(*terms):
    sets = [set(index.get(t, [])) for t in terms]
    return sorted(set.intersection(*sets))

print(index["cache"], index["database"])
print(search_and("cache", "database"))

Output

[1, 4, 7] [1, 2, 7]
[1, 7]

From text to terms

Analysis: lowercase, split into tokens, remove stop words ("the", "a"), stem or lemmatise (running to run), handle synonyms and n-grams. The same analysis must be applied to queries.

Ranking

Relevance scoring combines how often a term appears in a document (term frequency), how rare it is across all documents (inverse document frequency), and document length. TF-IDF and BM25 are classic. Modern search blends in freshness, popularity, personalization and learned ranking, plus vector similarity for semantic search.

Scaling search

Split the index into shards by document id, replicate each shard. A query is sent to every shard, each returns its top results, and a coordinator merges them. Elasticsearch and OpenSearch work this way. New documents go to a small in-memory segment first, which is why newly indexed items appear after a refresh interval (near real time, not instant).

Keep the source of truth elsewhere

Treat the search index as a derived view. Write to the primary database, then update the index through a queue or change data capture. Rebuilding the index from the source must always be possible.

Typeahead (autocomplete)

A trie (prefix tree) maps prefixes to top suggestions. Precompute the top K completions at each node, refresh periodically from query logs, and cache heavily (SD14).

How this gets asked

Which structure makes full-text search fast?

  • B-tree on the full text column Cannot find words inside text.
  • Inverted index mapping terms to documents Correct.
  • Hash map on document id Only exact id lookups.
  • Linked list of documents No.

The inverted index maps each term to its postings list so queries intersect lists instead of scanning documents.

Self-check

What is an inverted index?

A map from each term to the sorted list of documents containing it.

Batch and stream architectures

Batch

Process large bounded datasets periodically. MapReduce idea: map transforms records in parallel, a shuffle groups by key, reduce aggregates per key. Modern engines (Spark) keep data in memory and use DAGs of operations.

from collections import Counter
lines = ["to be or not to be", "to see or not to see"]
# map: emit (word, 1); shuffle+reduce: sum per word
pairs = [(w, 1) for line in lines for w in line.split()]
counts = Counter()
for w, n in pairs:
    counts[w] += n
print(sorted(counts.items()))

Output

[('be', 2), ('not', 2), ('or', 2), ('see', 2), ('to', 4)]

Stream

Process an unbounded flow of events continuously (Flink, Kafka Streams, Spark Structured Streaming). Key ideas: windows, event time with watermarks (to handle late events), state with checkpoints, and exactly-once state updates.

WindowMeaning
TumblingFixed, non-overlapping (every minute)
SlidingFixed length, moves by a smaller step (last 5 min, every 1 min)
SessionGrouped by activity with a gap of inactivity

Lambda and Kappa

  • Lambda architecture: a batch layer (accurate, slow) and a speed layer (approximate, fast), merged at query time. Two code paths to maintain.
  • Kappa architecture: one stream-processing path; reprocess history by replaying the log. Simpler if the stream engine is good enough.

Change data capture

Read a database's transaction log and publish each change as an event (Debezium). It feeds search indexes, caches, warehouses and other services without dual writes (SD8).

How this gets asked

What does a watermark do in stream processing?

  • Encrypts events No.
  • Tracks event-time progress so the system knows when to close a window despite late events Correct.
  • Deletes old data No.
  • Balances partitions No.

Watermarks estimate how late events can be and let windows fire.

Self-check

Lambda versus Kappa?

Lambda has separate batch and speed layers; Kappa uses one stream path and replays the log for reprocessing.

Probabilistic data structures

These trade a small, controlled error for huge savings in memory.

Bloom filter: "have I seen this?"

A bit array plus several hash functions. To add an item, set the bits at its hash positions. To test, check those bits: if any is 0 the item is definitely not present; if all are 1 it is probably present (false positives possible, no false negatives). Used to avoid disk lookups for missing keys (LSM trees, caches), check usernames, spot malicious URLs.

False positive rate
p = (1 - e^(-k n / m))^k
m
bits in the array
n
items inserted
k
number of hash functions (best k is about (m / n) x ln 2)
import hashlib, math
class Bloom:
    def __init__(self, m, k):
        self.m, self.k, self.bits = m, k, bytearray(m)
    def _pos(self, item):
        for i in range(self.k):
            h = hashlib.sha256(("%d:%s" % (i, item)).encode()).digest()
            yield int.from_bytes(h[:8], "big") % self.m
    def add(self, item):
        for p in self._pos(item): self.bits[p] = 1
    def __contains__(self, item):
        return all(self.bits[p] for p in self._pos(item))

n, m = 1000, 10000
k = round(m / n * math.log(2))
b = Bloom(m, k)
for i in range(n): b.add("key%d" % i)
fp = sum(("other%d" % i) in b for i in range(10000)) / 10000
print("k =", k, "no false negatives:", all(("key%d" % i) in b for i in range(n)))
print("measured false positive rate: %.3f, theory: %.3f" % (fp, (1 - math.exp(-k * n / m)) ** k))

Output

k = 7 no false negatives: True
measured false positive rate: 0.009, theory: 0.008

HyperLogLog: "how many distinct?"

Estimates the number of unique items with a standard error of about 1 percent using only a few kilobytes (Redis PFADD / PFCOUNT). Idea: hash items to bits and track the longest run of leading zeros; rare long runs imply many distinct items. Sketches from different shards can be merged.

Count-min sketch: "how often?"

A small grid of counters with several hash rows. Increment one counter per row; the estimate is the minimum across rows (it can only overestimate). Used to find heavy hitters (top trending items) in streams.

Others

Reservoir sampling keeps a uniform random sample of a stream of unknown length. Merkle trees hash data in a tree so replicas can find differences quickly (anti-entropy in Dynamo, Git).

How this gets asked

A Bloom filter says an item is NOT present. This answer is:

  • Possibly wrong No false negatives.
  • Definitely correct Correct.
  • Correct only half the time No.
  • Meaningless No.

Bloom filters have no false negatives; a positive answer may be a false positive.

You must count distinct visitors of a huge site using a few KB of memory per counter. Use:

  • A hash set Memory grows with the count.
  • HyperLogLog Correct.
  • A sorted list Memory grows.
  • A queue No.

HyperLogLog estimates cardinality with about 1 percent error in kilobytes.

Self-check

Bloom filter guarantee?

No false negatives; possible false positives, controlled by size and number of hashes.

Geospatial indexing

How to answer "restaurants within 2 km?" without checking every place.

MethodIdeaNotes
GeohashInterleave latitude and longitude bits into a string; shared prefix means nearbySimple, works in any key-value or SQL store; edge cases at cell borders (query neighbours)
QuadtreeRecursively split the map into 4 cells until each has at most K pointsIn-memory, adapts to density
S2 (Google) and H3 (Uber)Hierarchical cells on a sphere or hexagonsUniform cells, good for ride matching
R-treeBounding boxes in a balanced treeUsed by PostGIS and spatial databases
 
def geohash_encode(lat, lon, bits=20):
    lat_lo, lat_hi, lon_lo, lon_hi = -90.0, 90.0, -180.0, 180.0
    out, even = 0, True
    for _ in range(bits):
        if even:
            mid = (lon_lo + lon_hi) / 2
            bit = lon >= mid
            lon_lo, lon_hi = (mid, lon_hi) if bit else (lon_lo, mid)
        else:
            mid = (lat_lo + lat_hi) / 2
            bit = lat >= mid
            lat_lo, lat_hi = (mid, lat_hi) if bit else (lat_lo, mid)
        out = (out << 1) | int(bit)
        even = not even
    return format(out, "0%db" % bits)

print(geohash_encode(48.8566, 2.3522))    # Paris
print(geohash_encode(48.8606, 2.3376))    # nearby, shares a long prefix
print(geohash_encode(40.7128, -74.0060))  # New York, very different prefix

Output

11010000000100111001
11010000000100111001
01100101110010110111

Always search the cell and its neighbouring cells, then filter by exact distance (haversine).

How this gets asked

Two nearby points on different sides of a geohash cell boundary can have very different prefixes. What do you do?

  • Ignore it You will miss neighbours.
  • Query the cell and its 8 neighbouring cells, then filter by distance Correct.
  • Use a longer hash Does not remove boundaries.
  • Use random sampling No.

Prefix proximity is not guaranteed across boundaries, so search neighbours and verify exact distance.

Unique ID generation

In a sharded system you cannot use a single database auto-increment. Requirements: unique, roughly time-ordered (helps indexes), generated without coordination, fast.

MethodProsCons
UUID v4No coordination, trivial128 bits, random so poor index locality
UUID v7 / ULIDTime-ordered plus random128 bits
Database ticket serverSimple, orderedSingle point of failure, bottleneck
Snowflake (Twitter)64 bits, time-ordered, no coordinationNeeds unique machine ids, depends on clocks

Snowflake layout (64 bits): 1 sign bit, 41 bits timestamp in milliseconds (about 69 years), 10 bits machine id (1,024 machines), 12 bits sequence (4,096 ids per millisecond per machine).

import time
EPOCH = 1_700_000_000_000
class Snowflake:
    def __init__(self, machine):
        self.machine, self.last, self.seq = machine, -1, 0
    def next(self, now_ms=None):
        now = now_ms if now_ms is not None else int(time.time() * 1000)
        if now == self.last:
            self.seq = (self.seq + 1) & 0xFFF
            if self.seq == 0:
                raise RuntimeError("sequence exhausted this millisecond")
        else:
            self.seq, self.last = 0, now
        return ((now - EPOCH) << 22) | (self.machine << 12) | self.seq

g = Snowflake(machine=5)
ids = [g.next(EPOCH + 1000) for _ in range(3)] + [g.next(EPOCH + 1001)]
print(ids, ids == sorted(ids))
print("timestamp bits:", ids[0] >> 22, "machine:", (ids[0] >> 12) & 0x3FF, "seq:", ids[0] & 0xFFF)

Output

[4194324480, 4194324481, 4194324482, 4198518784] True
timestamp bits: 1000 machine: 5 seq: 0

A Snowflake style id uses a 12 bit sequence. How many ids can one machine create in one millisecond?

2^12 = 4,096.

Distributed locks and coordination

Why locks are hard

A lock held by a process that pauses, crashes or is partitioned can be taken by another while the first still believes it holds it. Use a lease (lock with expiry) and fencing tokens (SD6).

Options

ToolNotes
Database row lock or advisory lockSimple if you already have one database
Redis SET key id NX PX 30000Fast, single node; not safe under failover without care (Redlock debated)
ZooKeeper, etcd, ConsulConsensus-based, strong guarantees, ephemeral nodes, watches

Prefer designs that avoid locks: idempotent operations, partitioning so one owner handles a key, optimistic concurrency with versions, or a single-threaded queue consumer per key.

How this gets asked

Which are good ways to avoid distributed locks? Select all.

  • Idempotent operations
  • Partition so a single owner handles each key
  • Optimistic concurrency with versions
  • Hold the lock forever

Locks held without leases or fencing are dangerous; prefer designs that do not need them.

Blob and file storage

Store large objects in object storage (S3 style): flat namespace of buckets and keys, objects immutable, replicated across zones with very high durability (eleven nines), served over HTTP. Keep metadata (owner, name, size, checksum, location) in a database and the bytes in object storage.

Techniques: multipart upload (parallel chunks, resumable), presigned URLs (clients upload and download directly from storage, bypassing your servers), chunking and deduplication by content hash, erasure coding (store data plus parity pieces for durability at lower cost than 3 full copies), lifecycle rules to move cold data to cheaper tiers.

Interview questions: Data systems

10 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What is an inverted index?

A map from each term to the list of documents containing it, enabling fast full-text search.

Basic What is a Bloom filter and where is it used?

A compact probabilistic set with no false negatives and tunable false positives. Used to skip disk lookups for missing keys, check URLs and prevent cache penetration.

Medium How would you generate unique ids across shards?

UUIDs, time-ordered ids like Snowflake (timestamp, machine id, sequence), or a ticket server. Snowflake is compact, sortable and coordination free but depends on clocks and unique machine ids.

Medium How do you count unique visitors at scale?

HyperLogLog gives about 1 percent error in kilobytes and sketches merge across shards; exact counts need large sets or sampling.

Medium How does geospatial search work?

Cells such as geohash, quadtree, S2 or H3 index locations. Query the target cell and its neighbours, then filter by exact distance.

Medium Data warehouse versus data lake?

A warehouse holds modelled, structured data with schema on write. A lake stores raw files cheaply with schema on read. Lakehouses add table formats and transactions to lakes.

Advanced How do you scale search?

Shard the index by document, replicate shards, query all shards and merge top results, and keep the index as a derived view updated via queue or CDC.

Advanced What is change data capture?

Reading a database's transaction log and publishing each change as an event, feeding caches, search indexes and warehouses without dual writes.

Advanced How do you build a distributed lock safely?

Use a lease with expiry and fencing tokens on a consensus-backed store, or avoid locks with idempotency, ownership by partition or optimistic versioning.

Advanced Why use erasure coding for object storage?

It stores data plus parity pieces and survives multiple losses at lower overhead than keeping three full copies.
