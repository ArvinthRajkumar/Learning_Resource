Part SD17

Low-level design and design patterns

High-level design decides which services exist. Low-level design decides which classes exist inside one of them. Interviews ask for it as 'design a parking lot': identify entities, give each one a clear job, and make the design easy to extend.

MediumAdvanced~4 hours

The LLD interview method

Steps

  1. Clarify requirements and list use cases ("park a car", "pay and exit").
  2. Identify entities (nouns) that become classes, and behaviours (verbs) that become methods.
  3. Define relationships: has-a (composition), is-a (inheritance), uses (dependency).
  4. Apply principles and patterns only where they solve a real extension point.
  5. Write the core code and walk through a scenario.
  6. Discuss extensions (new vehicle type, new pricing rule, concurrency).

Self-check

What are the steps of an LLD answer?

Clarify, find entities and relations, design classes, code the core flow, discuss extensions.

Object-oriented principles

Four pillars

PillarMeaningExample
EncapsulationHide state, expose behaviourA Account hides balance and exposes deposit
AbstractionDepend on what something does, not howPaymentMethod.pay(amount)
InheritanceA subclass reuses and specialises a parentCar and Truck extend Vehicle
PolymorphismSame call, different behaviour by typeshape.area() on a circle or square

Prefer composition over inheritance. Inheritance couples subclasses to parent internals and creates deep hierarchies. Compose objects and delegate.

SOLID

PrincipleRuleViolation smell
Single responsibilityA class has one reason to changeA class that parses, validates, saves and emails
Open/closedOpen for extension, closed for modificationAn if type == ... chain you edit for every new type
Liskov substitutionSubtypes must work wherever the parent is expectedA Penguin that raises in Bird.fly()
Interface segregationMany small interfaces beat one fat oneForcing a printer to implement fax()
Dependency inversionDepend on abstractions, inject dependenciesA service that constructs its own MySQLDatabase

Other rules of thumb: DRY (do not repeat knowledge), KISS (keep it simple), YAGNI (do not build what you do not need), law of Demeter (talk only to your direct collaborators).

Patterns that matter

Patterns are named solutions to recurring design problems. Use the name as shared vocabulary, and only apply one when the problem is real.

Creational

PatternUseNote
FactoryCreate objects without hard-coding the classShapeFactory.create("circle")
BuilderConstruct complex objects step by stepMany optional parameters
SingletonExactly one instanceOften an anti-pattern (hidden global state); prefer dependency injection

Structural

PatternUse
AdapterMake an incompatible interface fit the one you expect
DecoratorAdd behaviour by wrapping an object with the same interface (logging, caching)
FacadeA simple interface over a complicated subsystem
ProxyA stand-in that controls access (lazy loading, access control, caching)

Behavioural

PatternUse
StrategySwap an algorithm at runtime (pricing, sorting, routing)
ObserverNotify many listeners when something changes

CommandTurn a request into an object (undo, queues)

Strategy and Observer in code

from abc import ABC, abstractmethod

# Strategy: pricing algorithms are interchangeable
class Pricing(ABC):
    @abstractmethod
    def fee(self, hours): ...
class Hourly(Pricing):
    def fee(self, hours): return 5 * hours
class DayCap(Pricing):
    def fee(self, hours): return min(5 * hours, 30)

# Observer: listeners react to events
class EventBus:
    def __init__(self): self.subs = []
    def subscribe(self, fn): self.subs.append(fn)
    def publish(self, event):
        for fn in self.subs: fn(event)

bus = EventBus()
bus.subscribe(lambda e: print("email:", e))
bus.subscribe(lambda e: print("audit:", e))
bus.publish("order_placed")
print(Hourly().fee(10), DayCap().fee(10))

Output

email: order_placed
audit: order_placed
50 30

  • Adapter No.
  • Facade No.

Strategy encapsulates interchangeable algorithms behind one interface.

Several listeners must react when an order is placed. Which pattern?

  • Observer Correct.
  • Builder No.
  • Proxy No.
  • Flyweight No.

Observer (publish/subscribe) decouples the source from its listeners.

When is Singleton a bad idea?

It hides global state and hinders testing; prefer injecting a shared instance.

Problem 1: Parking lot

Requirements

Multiple floors with spots of different sizes (motorcycle, car, large). Vehicles enter, get a ticket, park in the nearest suitable free spot, and pay on exit based on duration. Report availability.

Entities

ParkingLot (floors, tickets), Floor (spots), Spot (size, free or occupied), Vehicle (type), Ticket (spot, entry time), Pricing (strategy).

from dataclasses import dataclass, field

SIZES = {"moto": 1, "car": 2, "large": 3}

@dataclass
class Spot:
    id: str
    size: int
    vehicle: str = None
    def fits(self, kind): return self.vehicle is None and self.size >= SIZES[kind]

@dataclass
class Ticket:
    id: int
    spot: Spot
    vehicle: str
    entry: float

class ParkingLot:
    def __init__(self, spots, rate_per_hour=5):
        self.spots, self.rate, self.tickets, self.next_id = spots, rate_per_hour, {}, 1
    def park(self, vehicle, kind, now):
        # best fit: smallest free spot that fits (keeps big spots for big vehicles)
        cands = [s for s in self.spots if s.fits(kind)]
        if not cands:
            raise RuntimeError("lot full for " + kind)
        spot = min(cands, key=lambda s: s.size)
        spot.vehicle = vehicle
        t = Ticket(self.next_id, spot, vehicle, now)
        self.tickets[t.id] = t
        self.next_id += 1
        return t
    def leave(self, ticket_id, now):
        t = self.tickets.pop(ticket_id)
        t.spot.vehicle = None
        hours = max(1, -(-int(now - t.entry) // 3600))       # round up to whole hours
        return hours * self.rate

lot = ParkingLot([Spot("A1", 1), Spot("A2", 2), Spot("A3", 3)])
t1 = lot.park("bike", "moto", 0)
t2 = lot.park("sedan", "car", 0)
print(t1.spot.id, t2.spot.id)
print("fee:", lot.leave(t2.id, 2 * 3600 + 1))
print("free for large:", [s.id for s in lot.spots if s.fits("large")])

Output

A1 A2
fee: 15
free for large: ['A3']

Extensions

New vehicle type: add an entry to SIZES (open/closed). New pricing: new Pricing strategy. Concurrency: guard park with a lock or use atomic spot reservation in a database. Many entrances: per-floor free lists (min-heaps) for O(log n) nearest-spot lookups.

How this gets asked

To keep large spots free for large vehicles, which allocation is better?

  • First free spot May waste large spots.
  • Best fit: smallest free spot that fits Correct.
  • Random spot Wasteful.
  • Largest spot Wasteful.

Best fit preserves flexibility for future large vehicles.

Problem 2: Vending machine (State pattern)

Idea

Behaviour depends on state: with no money inserted, pressing "select" does nothing; with enough money, it dispenses. Model each state as a class or use a state table.

class VendingMachine:
    def __init__(self, stock):
        self.stock, self.balance, self.state = dict(stock), 0, "idle"
    def insert(self, cents):
        if self.state == "dispensing":
            raise RuntimeError("busy")
        self.balance += cents
        self.state = "has_money"
    def select(self, item):
        if self.state != "has_money":
            return "insert money first"
        price, qty = self.stock[item]
        if qty == 0:
            return "sold out"
        if self.balance < price:
            return "need %d more" % (price - self.balance)
        self.state = "dispensing"
        self.stock[item] = (price, qty - 1)
        change, self.balance, self.state = self.balance - price, 0, "idle"
        return "dispensed %s, change %d" % (item, change)
    def cancel(self):
        refund, self.balance, self.state = self.balance, 0, "idle"
        return refund

vm = VendingMachine({"cola": (150, 1)})
print(vm.select("cola"))
vm.insert(100); print(vm.select("cola"))
vm.insert(100); print(vm.select("cola"))
vm.insert(200); print(vm.select("cola"), vm.cancel())

Output

insert money first
need 50 more
dispensed cola, change 50
sold out 200

A full State pattern makes each state a class with insert, select, cancel methods, so adding a state (maintenance mode) adds a class instead of editing every if.

How this gets asked

Behaviour changes depending on whether money has been inserted. Which pattern models that cleanly?

  • State Correct.
  • Decorator No.
  • Prototype No.
  • Iterator No.

The State pattern turns each state into its own behaviour and transitions.

Problem 3: Elevator system

Requirements

Several elevators, many floors, hall calls (up or down) and cabin calls (go to floor N). Pick which elevator serves a call, and minimise waiting.

Design

Entities: Elevator (current floor, direction, queue of stops), Controller (dispatch policy), Request. Use the SCAN (elevator) algorithm: keep moving in one direction serving stops, then reverse. Dispatch uses a Strategy: nearest idle elevator, or the one already moving toward the call with the smallest added cost.

class Elevator:
    def __init__(self, floor=0):
        self.floor, self.dir, self.up, self.down = floor, 0, set(), set()
    def request(self, f):
        (self.up if f >= self.floor else self.down).add(f)
    def step(self):
        """Move one floor along SCAN order and return the floor visited."""
        if self.dir >= 0 and any(f >= self.floor for f in self.up):
            self.dir = 1
        elif self.down:
            self.dir = -1
        elif self.up:
            self.dir = 1
        else:
            self.dir = 0
            return None
        self.floor += self.dir
        self.up.discard(self.floor); self.down.discard(self.floor)
        return self.floor

e = Elevator(0)
for f in (3, 5, 2): e.request(f)
trace = []
for _ in range(7):
    trace.append(e.step())
print(trace)

Output

[1, 2, 3, 4, 5, None, None]

The trace lists each floor the cabin passes. It serves requests 2, 3 and 5 in one upward sweep rather than jumping around. Real systems add door timing, capacity, priority and zones.

Problem 4: LRU cache and thread safety

Implement get and put in O(1) with a hash map and doubly linked list (see SD7). The extra LLD discussion: thread safety and extensibility.

import threading
from collections import OrderedDict

class ThreadSafeLRU:
    def __init__(self, capacity, on_evict=None):
        self.cap, self.d, self.lock, self.on_evict = capacity, OrderedDict(), threading.Lock(), on_evict
    def get(self, k):
        with self.lock:
            if k not in self.d: return None
            self.d.move_to_end(k)
            return self.d[k]
    def put(self, k, v):
        with self.lock:
            self.d[k] = v
            self.d.move_to_end(k)
            if len(self.d) > self.cap:
                old = self.d.popitem(last=False)
                if self.on_evict: self.on_evict(*old)

evicted = []
c = ThreadSafeLRU(2, on_evict=lambda k, v: evicted.append(k))
for i in range(5):
    c.put(i, i)
print(list(c.d), evicted)

Output

[3, 4] [0, 1, 2]

Discuss: a single lock is simple but a bottleneck; use striped locks (shard the cache into N independent LRUs by key hash) for more concurrency. The on_evict callback is an Observer-style extension point. An eviction policy interface (LRU, LFU) is a Strategy.

Self-check

How do you make an LRU thread safe and scalable?

A lock around operations, then striped locks by sharding keys across several independent LRUs.

Problem 5: Notification hub

Requirements: send notifications through email, SMS and push; add channels without changing existing code; user preferences decide channels.

from abc import ABC, abstractmethod

class Channel(ABC):
    @abstractmethod
    def send(self, user, msg): ...

class Email(Channel):
    def send(self, user, msg): return "email to %s: %s" % (user["name"], msg)
class Sms(Channel):
    def send(self, user, msg): return "sms to %s: %s" % (user["name"], msg)
class Push(Channel):
    def send(self, user, msg): return "push to %s: %s" % (user["name"], msg)

class ChannelFactory:
    _reg = {"email": Email, "sms": Sms, "push": Push}
    @classmethod
    def create(cls, name): return cls._reg[name]()

class NotificationHub:
    def notify(self, user, msg):
        return [ChannelFactory.create(c).send(user, msg) for c in user["prefs"]]

hub = NotificationHub()
print(hub.notify({"name": "Ada", "prefs": ["email", "push"]}, "Order shipped"))

Output

['email to Ada: Order shipped', 'push to Ada: Order shipped']

Adding Slack means one new class and one registry entry: open for extension, closed for modification. This combines Strategy (channels), Factory (creation) and dependency inversion (the hub depends on Channel).

Concurrency in LLD

  • Race condition: two threads read-modify-write shared state. Fix with a lock, an atomic operation or by confining state to one thread.
  • Deadlock: threads wait for each other's locks. Avoid by locking in a consistent global order, using timeouts or lock-free structures.
  • Prefer immutable objects and message passing (queues) over shared mutable state.
  • Make operations idempotent where retries can happen.
  • In a distributed setting, in-process locks do not help: use database constraints, atomic conditional updates or a coordination service (SD12).

How this gets asked

Two threads must lock accounts A and B. How do you avoid deadlock?

  • Lock in whatever order arrives Can deadlock.
  • Always acquire locks in a fixed global order Correct.
  • Never unlock No.
  • Use sleep No.

A consistent lock ordering removes circular waits.

Self-check

Name a race condition fix and a deadlock fix.

Use locks or atomic operations for races; use a consistent lock order or timeouts for deadlocks.

Interview questions: Low-level design

8 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What are the SOLID principles?

Single responsibility, open/closed, Liskov substitution, interface segregation and dependency inversion.

Basic Composition versus inheritance?

Prefer composition: it is more flexible and avoids tight coupling and deep hierarchies. Use inheritance for real is-a relationships.

Medium When do you use the Strategy pattern?

When an algorithm should be swappable at runtime, such as pricing, routing or eviction policy, replacing conditionals with polymorphism.

Medium State pattern example?

A vending machine or order lifecycle where behaviour depends on state; each state encapsulates its behaviour and transitions.

Medium Design a parking lot.

Entities: ParkingLot, Floor, Spot, Vehicle, Ticket, Pricing strategy. Allocate best-fit spots, issue a ticket, compute fee on exit; extend with new vehicle types and pricing rules without modifying core code.

Medium Why is Singleton often discouraged?

It is global mutable state that hides dependencies and complicates testing. Inject a single shared instance instead.

Advanced How do you make a class thread safe?

Protect shared mutable state with locks or atomics, prefer immutability and message passing, keep critical sections small, avoid deadlocks with consistent lock ordering.

Advanced How do you make an LRU cache scale across threads?

Shard keys into independent LRU segments each with its own lock (striped locking) to reduce contention.
