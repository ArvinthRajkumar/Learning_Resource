How to use the case studies

For every case: set a 35 minute timer, write requirements and numbers, draw the design, pick two deep dives, then read the model answer. The goal is not to match it, but to find gaps in your reasoning. Parts SD1 to SD12 hold the building blocks used here.

Case 1: URL shortener

Requirements

  • Functional: create a short URL for a long URL; redirect from short to long; optional custom alias and expiry.
  • Non-functional: very high availability for redirects, redirect latency under 50 ms, short links are not guessable in order, links should not be lost.
  • Out of scope: analytics dashboard, user accounts (mention as extensions).

Estimates

100 million new URLs per month and reads 100 times writes, as worked in SD1: about 40 writes per second, about 4,000 reads per second (12,000 peak), 6 TB over ten years, a cache of about 34 GB.

How long must the key be?

Use a-z, A-Z, 0-9 (base 62). A key of length L gives 62^L keys.

for L in (6, 7, 8):
    print(L, "chars:", format(62 ** L, ","), "keys")
need = 100_000_000 * 12 * 10
print("need over 10 years:", format(need, ","))

Output

6 chars: 56,800,235,584 keys
7 chars: 3,521,614,606,208 keys
8 chars: 218,340,105,584,896 keys
need over 10 years: 12,000,000,000

Seven characters give 3.5 trillion keys, far more than the 12 billion needed.

API

POST /v1/urls        {long_url, custom_alias?, expires_at?}  ->  201 {short_url}
GET  /{key}                                                   ->  301 or 302 Location: long_url

Use 302 (temporary) if you want every click to reach you for analytics or to change targets. 301 (permanent) lets browsers cache the redirect and reduces load, but you lose control.

Data model

urls(key PK, long_url, user_id, created_at, expires_at). Access is by key only, so a key-value store or a sharded SQL table keyed by key works. 500 bytes per row x 12 billion rows is 6 TB.

Generating the key

ApproachHowNotes
Hash and truncateMD5 or SHA of the long URL, take 7 chars of base62Collisions possible: check and retry with a salt; same URL gives same key
Counter and base62Global counter encoded in base62No collisions; keys are guessable in order unless you scramble the counter
Pre-generated key serviceA service hands out unused keys in batches to app serversNo collisions at write time, simple servers; manage the key pool
RandomRandom 7 chars, retry on collisionSimple, collision rate low while the space is mostly empty
 
import string
ALPHABET = string.digits + string.ascii_lowercase + string.ascii_uppercase
def b62(n):
    if n == 0: return ALPHABET[0]
    s = ""
    while n: n, r = divmod(n, 62); s = ALPHABET[r] + s
    return s
def unb62(s):
    n = 0
    for ch in s: n = n * 62 + ALPHABET.index(ch)
    return n
for n in (0, 61, 62, 123456789, 3521614606207):
    print(n, b62(n), unb62(b62(n)) == n)

Output

0 0 True
61 Z True
62 10 True
123456789 8m0Kx True
3521614606207 ZZZZZZZ True

High-level design

Deep dive

  • Read path: look up the key in cache; on a miss read the database and cache with a TTL. Hot links follow a skewed distribution, so a modest cache gives a 90 percent hit rate. Redirect with the right status code.
  • Write path: take a key from the key service, store, return. Key service pre-generates keys into a table with used flag and hands out ranges (for example 1,000 at a time) to each app server, so no per-request coordination.
  • Sharding: hash the key. Use consistent hashing or many fixed partitions to rebalance (SD5).
  • Expiry: lazy deletion on read plus a background sweeper; return 410 Gone for expired.
  • Abuse: rate limit creation per user and IP, scan target URLs for malware, block loops to your own domain.

Trade-offs and failures

Cache outage raises database load, so size the database for partial misses. Custom aliases need uniqueness checks on a strongly consistent store. Analytics can be added by emitting click events to a queue instead of writing synchronously.

How this gets asked

How many distinct 7 character base62 keys exist, in trillions? (round to one decimal)

62^7 = 3,521,614,606,208, about 3.5 trillion.

Which redirect status lets you change the destination later and count every click?

  • 301 Moved Permanently Browsers cache it, so later clicks may not reach you.
  • 302 Found (temporary) Correct.
  • 200 OK Not a redirect.
  • 404 No.

Temporary redirects are not cached by browsers, so each click hits your servers.

Self-check

How do you generate short keys without collisions?

Counter in base62, or a pre-generated key service handing out ranges, or random with collision retry.

Case 2: Pastebin

Requirements

Users paste text, get a unique link, and others read it. Pastes expire after a chosen time. Reads dominate.

Estimates

1 million new pastes per day (12 per second), reads 5 times writes (60 per second). Average paste 10 KB: 10 GB per day, 3.6 TB per year. The numbers are small.

Design

  • Metadata in a database: pastes(id, owner, created_at, expires_at, size, object_key).
  • Content in object storage keyed by id, because it is larger and rarely queried by anything but id. Serve popular pastes through a CDN.
  • Key generation as in the URL shortener (pre-generated keys).
  • Read: look up metadata (cache), check expiry, return a redirect or stream the content from storage or CDN.
  • Expiry: store expires_at, ignore expired pastes on read, delete with a periodic job and with storage lifecycle rules.
  • Large pastes: limit size (for example 10 MB), compress, and upload directly to object storage with presigned URLs.

The twist compared with the shortener: the payload is big, so separate metadata from blobs and offload reads to the CDN. Private pastes need unguessable ids (use long random ids, not counters) and authorisation checks.

How this gets asked

Where should the bytes of large pastes be stored?

  • In the metadata table Bloats the database.
  • Object storage, served via a CDN, with metadata in a database Correct.
  • In memory only Not durable.
  • In DNS No.

Large immutable blobs belong in object storage; the database keeps small metadata.

Self-check

What is the key twist compared with the URL shortener?

Payloads are large, so metadata goes in a database and bytes in object storage behind a CDN.

Case 3: Rate limiter

Requirements

Limit each client (by API key, user or IP) to N requests per window. Low overhead (adds under 1 ms), accurate enough, works across many gateway servers, tolerates failure of the limiter store.

Where it sits

In the API gateway or as middleware, before the application. Return 429 with Retry-After.

Algorithms

Token bucket, leaky bucket, fixed and sliding windows (SD9). Token bucket is the usual pick.

Distributed state

All gateway nodes must share counters. Store in Redis, keyed by limit:{client}:{window}. Increment and set expiry atomically with a Lua script (check and update must not race).

-- Redis Lua sketch for a fixed window
local c = redis.call('INCR', KEYS[1])
if c == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
return c

Deep dives

  • Race conditions: a read-then-write across two calls lets two requests both pass. Use atomic scripts or INCR.
  • Sliding window counter gives accuracy without storing every timestamp: estimate = current_count + previous_count x (1 - elapsed fraction).
  • Scale: shard Redis by client key. Keep a small local token bucket per gateway and sync periodically if exact global limits are not required (trade accuracy for no network hop).
  • Failure: if Redis is down, fail open (allow, risk overload) or closed (reject, risk outage). Choose per endpoint: open for reads, closed for expensive or sensitive calls.
  • Rules: change limits without deploys via a rules service cached at the gateway.
  • Fairness and burst: different limits per tier, plus a global limit to protect the backend.
def sliding_window_estimate(prev_count, curr_count, elapsed_fraction):
    return curr_count + prev_count * (1 - elapsed_fraction)
# limit 100/min; previous minute had 80 requests, this minute 30 so far, 25% through
print(sliding_window_estimate(80, 30, 0.25))   # 90.0, still under 100

Output

90.0

How this gets asked

Why must the counter check and increment be atomic?

  • To save memory Not the reason.
  • Two concurrent requests could both read the old value and both be allowed Correct.
  • To log requests No.
  • To avoid TLS No.

Use INCR or a Lua script so the read-modify-write cannot interleave.

Self-check

Which algorithm and store?

Token bucket with atomic counters in Redis, enforced at the gateway, failing open or closed per endpoint.

Case 4: Key-value store (Dynamo style)

Requirements

put(key, value) and get(key). Highly available for writes, horizontally scalable, low latency, tunable consistency, survives node and zone failure. Single-key operations only.

Core design (the Dynamo recipe)

ConcernTechnique
PartitioningConsistent hashing with virtual nodes (SD5)
ReplicationEach key stored on N successive nodes on the ring
ConsistencyQuorum: W writes, R reads, R + W > N for stronger reads
Versioning and conflictsVector clocks; client or last-write-wins resolution
Temporary failuresSloppy quorum with hinted handoff: a stand-in node holds the write and passes it back
Permanent failuresAnti-entropy with Merkle trees to compare and repair replicas
Membership and failure detectionGossip protocol
Local storageLSM tree (memtable, commit log, SSTables, Bloom filters, compaction)

Write path

  1. The client contacts any node, which becomes the coordinator (or uses a token-aware client).
  2. The coordinator finds the N replicas for the key from the ring and sends the write to them in parallel.
  3. Each replica appends to its commit log, writes to the memtable, and acknowledges.
  4. The coordinator replies after W acknowledgements.

Read path

Query R replicas, compare versions, return the newest (or all siblings if concurrent), and read repair: write the winner back to stale replicas.

Tuning

Setting (N=3)Effect
W=1, R=1Fastest, eventual
W=2, R=2Strong enough for most uses, tolerates one failure
W=3, R=1Fast reads, writes fail with any node down

Trade-offs

Choose availability over strict consistency, so applications must handle conflicts. Do not offer multi-key transactions (they would need coordination across partitions). Hot keys and large values need care.

How this gets asked

In a 3-replica Dynamo-style store, which settings guarantee read-write overlap?

  • W=1, R=1 No overlap.
  • W=2, R=2 Correct, 2 + 2 > 3.
  • W=1, R=2 1 + 2 = 3, not greater than 3.
  • W=0, R=3 No.

R + W > N guarantees that every read quorum intersects every write quorum.

What does hinted handoff do?

  • Compresses data No.
  • A stand-in node holds writes for a temporarily down replica and returns them when it recovers Correct.
  • Elects a leader No.
  • Encrypts data No.

It keeps writes available during short failures.

Self-check

List the Dynamo techniques.

Consistent hashing, replication, quorums, vector clocks, sloppy quorum with hinted handoff, Merkle tree anti-entropy, gossip.

Case 5: Distributed cache

Requirements

A cache cluster (Memcached or Redis-like): low latency (about 1 ms), very high throughput, horizontal scaling, hot-key handling, eviction, optional persistence and replication, node failures tolerated.

Design

  • Sharding: clients or a proxy map keys to nodes using consistent hashing. Adding a node moves about 1/N of keys, so most of the cache survives.
  • Per node: a hash table for lookup and an LRU list for eviction (O(1) get and put, see SD7), TTL expiry (lazy plus periodic sampling), memory managed with slab allocation to avoid fragmentation.
  • Replication: a primary and replica per shard. On primary loss, promote the replica. Warm replicas avoid a cold cache after failure.
  • Protocol: a lightweight binary or text protocol over persistent connections, pipelining and batching (MGET).
  • Client library: handles hashing, retries, timeouts, and a circuit breaker so a slow cache does not take down the app.

Deep dives

  • Hot keys: detect with counters, then replicate the hot key to several nodes (key#1, key#2) and add a short-lived local cache in the client.
  • Consistency with the database: cache-aside with delete on write; TTLs bound staleness.
  • Failure: a lost node causes a miss spike for its keys; protect the database with request coalescing and rate limits.
  • Memory limits and eviction policy per use: LRU for general, LFU for stable popularity, TTL for sessions.
  • Multi-region: independent caches per region, with invalidation events or short TTLs rather than synchronous replication.

How this gets asked

Why use consistent hashing in a cache cluster?

  • It encrypts keys No.
  • Adding or removing a node remaps only a small fraction of keys Correct.
  • It makes keys shorter No.
  • It removes the need for eviction No.

Naive modulo hashing would invalidate nearly the entire cache on resize.

Self-check

How do you handle hot keys?

Replicate the key across nodes and add a short local cache in the client.

Interview questions: Case studies 1

8 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Design a URL shortener: how do you generate the key?

Use base62 on a counter or pre-generated unique ids, or hash and handle collisions. Seven base62 characters give 3.5 trillion keys.

Medium 301 or 302 for the redirect?

302 keeps traffic flowing through you for analytics and changeable targets. 301 is cached by browsers and cuts load but loses control.

Medium Design Pastebin: where does the content go?

In object storage behind a CDN, with metadata in a database and expiry handled by stored timestamps and lifecycle rules.

Medium Design a rate limiter: which algorithm and where is state?

Token bucket at the gateway with atomic counters in Redis per client key, with rules in a cached config service.

Medium Design a distributed cache.

Sharded nodes with consistent hashing, LRU and TTL eviction per node, replicas for failover, client library with timeouts and circuit breaker, hot-key handling and request coalescing.

Advanced How do you avoid races in a distributed rate limiter?

Make the check and update atomic using Redis INCR or a Lua script, or accept approximate limits with local buckets that sync periodically.

Advanced Design a key-value store with high availability.

Consistent hashing with virtual nodes, replication to N nodes, tunable quorums, vector clocks, hinted handoff, Merkle-tree anti-entropy, gossip membership and LSM storage.

Advanced How does hinted handoff work?

When a replica is down, another node accepts the write with a hint and delivers it when the replica returns, keeping writes available.
