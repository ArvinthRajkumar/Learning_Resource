Case 1: Metrics and monitoring system

Requirements

Collect metrics (CPU, request counts, latency) from thousands of servers, store them, query them for dashboards, and fire alerts. Writes are constant and huge; reads are dashboards and alert evaluations.

Estimates

100,000 servers each emit 100 metrics every 10 seconds: 1 million data points per second. Each point about 16 bytes (timestamp plus value) plus series metadata: about 1.4 TB per day uncompressed. Time-series compression (delta of delta timestamps, XOR floats) brings 16 bytes to about 1.5 bytes per point.

points_per_sec = 100_000 * 100 / 10
raw_tb_day = points_per_sec * 16 * 86_400 / 1e12
comp_tb_day = points_per_sec * 1.5 * 86_400 / 1e12
print(int(points_per_sec), "points/s;", round(raw_tb_day, 2), "TB/day raw;", round(comp_tb_day, 2), "TB/day compressed")

Output

1000000 points/s; 1.38 TB/day raw; 0.13 TB/day compressed

Pull versus push collection

Pull (Prometheus)Push (StatsD, agents)
HowThe collector scrapes each target's /metrics endpointServices send data to a collector
ProsCollector knows who is up; central config; easy debuggingWorks for short-lived jobs and behind firewalls
ConsNeeds service discovery and reachabilityHarder to know if a silent service is dead

Architecture

Storage and queries

  • Data model: a series identified by metric name plus a set of labels (http_requests_total{service="cart", status="500"}), with (timestamp, value) points. Index labels with an inverted index; write points sequentially in time order.
  • Sharding: hash the series id; keep a recent window in memory and flush blocks to disk.
  • Downsampling and retention: keep raw data for 7 to 15 days, 1 minute rollups for 3 months, 1 hour rollups for years. Queries over long ranges read rollups.
  • Cardinality control: every unique label combination is a new series. High cardinality labels (user id, request id) explode storage. Enforce limits.

Alerting

An evaluator runs rules every minute (error_rate > 2% for 5m), tracks state (pending, firing, resolved), groups and de-duplicates notifications, supports silences and routing by team, and escalates. Evaluate on a replicated path so alerting survives the loss of one instance, and alert on the monitoring system itself ("the watchdog" alert that must always fire).

How this gets asked

Which is the biggest risk for a time-series store?

  • Using timestamps Core feature.
  • High-cardinality labels creating millions of series Correct.
  • Compression Helps.
  • Downsampling Helps.

Every unique label set is a new series; unbounded labels such as user id explode storage.

Self-check

Pull versus push collection?

Pull: collector scrapes targets (knows who is alive). Push: services send data (good for short-lived jobs).

Case 2: Ad click aggregation

Requirements

Count ad clicks (and impressions) per ad, per minute, for billing and dashboards. Billing needs accurate counts (no loss, no double counting); dashboards want low latency. Handle late and duplicate events, fraud and huge volume.

Estimates

1 billion clicks per day: about 12,000 per second average, 50,000 at peak. Event size 100 bytes: 100 GB per day. Aggregated results are small.

Design

  • Ingest: clients and servers publish click events to a log (Kafka) partitioned by ad_id, so all events for one ad are on one partition.
  • Stream aggregation: a stream processor (Flink) computes tumbling windows of one minute per ad, using event time and watermarks to accept late events (for example up to 5 minutes), keeping state with periodic checkpoints.
  • Exactly-once effect: checkpoints plus idempotent writes keyed by (ad_id, window_start) mean a replay overwrites rather than double counts. Deduplicate events by click_id inside a dedupe window.
  • Storage: aggregates in an OLAP or time-series store for dashboards. All raw events also go to cheap object storage in Parquet.
  • Reconciliation (lambda-style): a nightly batch job recomputes exact counts from raw data and corrects the stream results. The bill uses the batch-verified numbers.

Hot ads

A viral ad is one partition key. Mitigate by adding a salt to the key (ad_id#0..7), aggregating partial counts and merging in a second stage.

Fraud and quality

Filter bots and click spam with rules and ML (impossible click rates, repeated IPs, device fingerprints) before counting for billing; keep the unfiltered stream for investigation.

How this gets asked

How do you make stream aggregation effectively exactly-once?

  • Disable retries Would lose data.
  • Checkpointed state plus idempotent writes keyed by (ad, window), and a batch reconciliation Correct.
  • Count twice Wrong.
  • Use a bigger cluster Does not address duplicates.

Replays overwrite the same key rather than adding again; the batch job verifies numbers used for billing.

Self-check

Why keep raw events and run a batch job?

To audit, reprocess and correct stream results so billing uses verified counts.

Case 3: Leaderboard

Requirements

A game shows the top 100 players, a player's own rank, and nearby players. Updates arrive when scores change. Millions of players, real-time feel.

Why not just SQL?

SELECT ... ORDER BY score DESC LIMIT 100 is fine for thousands of rows, but finding a given player's rank (COUNT(*) WHERE score > mine) over millions of rows per request is too slow.

Redis sorted set

A sorted set keeps members ordered by score in a skip list plus hash map. Operations are O(log N): ZADD to set or update a score, ZREVRANK for rank, ZREVRANGE 0 99 for the top 100, ZINCRBY to add points, ZREVRANGE rank-5 rank+5 for neighbours.

import bisect
class Leaderboard:
    """Sorted list stand-in for a Redis sorted set (insert O(n) here, O(log n) in Redis)."""
    def __init__(self):
        self.items = []                 # sorted ascending by (score, player)
        self.score = {}
    def update(self, player, score):
        if player in self.score:
            self.items.remove((self.score[player], player))
        bisect.insort(self.items, (score, player))
        self.score[player] = score
    def top(self, n):
        return [(p, s) for s, p in reversed(self.items[-n:])]
    def rank(self, player):             # 1-based, highest score is rank 1
        i = self.items.index((self.score[player], player))
        return len(self.items) - i

lb = Leaderboard()
for p, s in [("ann", 50), ("bob", 80), ("cy", 65), ("di", 90)]:
    lb.update(p, s)
lb.update("ann", 85)
print(lb.top(3), lb.rank("bob"), lb.rank("ann"))

Output

[('di', 90), ('ann', 85), ('bob', 80)] 3 2

Scaling

  • One Redis sorted set holds tens of millions of members in a few GB, so one node (plus replica) may be enough for a single global board. Peak writes of 10,000 to 100,000 per second fit.
  • To go beyond: shard by score range (each shard owns a range, top 100 from the top shard) or shard by player and merge top-k from each shard.
  • Time windows (daily, weekly): separate sorted sets per window key with a TTL.
  • Persistence: Redis is a derived view. Keep the source of truth in a database and rebuild on loss.
  • Ties: break by earliest achievement time (encode into the score or use secondary ordering).
  • Very large scale, approximate ranks: bucket scores and estimate rank from bucket counts ("you are in the top 3%").

How this gets asked

Which Redis structure and command find a player's rank in O(log N)?

  • List and LRANGE O(N).
  • Sorted set and ZREVRANK Correct.
  • Hash and HGET No ordering.
  • String and GET No.

Sorted sets keep members ordered by score using a skip list.

Self-check

How to scale beyond one sorted set?

Shard by score range or by player and merge top-k, with per-window keys and a database as source of truth.

Case 4: Design a distributed message queue

Requirements

Build the system from SD8: producers publish, consumers subscribe, high throughput, durable, ordered per partition, scalable, supports consumer groups and replay.

Core design (a Kafka-like log)

  • A topic is split into partitions; each partition is an append-only log of records with increasing offsets, stored as segment files on disk. Sequential disk writes and reads, plus the OS page cache and zero-copy sends, make this very fast.
  • A broker hosts many partitions. A partition has one leader and several follower replicas (the in-sync replica set). Producers write to the leader; followers fetch from it.
  • Acknowledgement levels: acks=0 (fire and forget), acks=1 (leader wrote it), acks=all (all in-sync replicas). Use acks=all and a minimum ISR size for durability.
  • Consumer groups: partitions are divided among consumers in a group; each partition belongs to one consumer at a time. Consumers commit offsets (stored in an internal topic) so they can resume after failure.
  • Retention: delete segments by age or size, or compact by key (keep the latest value per key).
  • Coordination: a metadata and controller layer (ZooKeeper historically, now Raft in KRaft) tracks brokers, partition leaders and group membership. Leader election uses consensus (SD6).

Delivery semantics

  • Producer retries can duplicate; idempotent producers (producer id and sequence numbers) let the broker discard duplicates.
  • Consumer at-least-once: commit the offset after processing. At-most-once: commit before. Exactly-once within the platform via transactions across produce and offset commit.

Choices and trade-offs

Ordering only within a partition. More partitions give parallelism but cost more metadata and slower rebalances. A larger replication factor raises durability and cost. Latency versus throughput is tuned by batching (linger.ms) and compression.

How this gets asked

Which acknowledgement setting gives the strongest durability in a Kafka-like log?

  • acks=0 May lose data.
  • acks=1 Leader only.
  • acks=all with a minimum in-sync replica count Correct.
  • No replication No.

The write is acknowledged only after all in-sync replicas have it.

A topic has 12 partitions and a consumer group has 20 consumers. How many consumers are actually active?

Each partition is read by at most one consumer in the group, so 12 are active and 8 idle.

Self-check

What is a consumer group?

A set of consumers that share a topic's partitions so each message is processed by one member.

Case 5: Collaborative document editing

Requirements

Many users edit the same document at once (Google Docs). Edits appear in real time for others; the document must converge to the same text for everyone, preserve intent, work with brief offline gaps, keep history and cursors.

The core problem

Alice and Bob both start from "cat". Alice inserts "X" at position 1. Bob inserts "Y" at position 0. If each applies the other's operation unchanged, Alice ends with YcXat but Bob with YXcat, so they diverge.

Operational Transformation (OT)

Transform each incoming operation against operations that happened concurrently, adjusting positions so intent is preserved. A central server defines the order of operations, which simplifies the transform. Used by Google Docs.

# Concurrent edits on "cat": A inserts 'X' at 1, B inserts 'Y' at 0.
def apply(text, op):
    kind, pos, ch = op
    return text[:pos] + ch + text[pos:] if kind == "ins" else text[:pos] + text[pos + 1:]

def transform(op, other):
    """Adjust op so it can be applied after 'other' has already been applied."""
    kind, pos, ch = op
    okind, opos, _ = other
    if okind == "ins" and opos <= pos:
        pos += 1
    elif okind == "del" and opos < pos:
        pos -= 1
    return (kind, pos, ch)

a = ("ins", 1, "X")
b = ("ins", 0, "Y")
# naive: apply in different orders without transform -> diverge
print("naive A then B:", apply(apply("cat", a), b), "| B then A:", apply(apply("cat", b), a))
# with transform both converge
print("OT   A then B':", apply(apply("cat", a), transform(b, a)), "| B then A':", apply(apply("cat", b), transform(a, b)))

Output

naive A then B: YcXat | B then A: YXcat
OT   A then B': YcXat | B then A': YcXat

CRDTs

A conflict-free replicated data type gives every character a unique, ordered identifier so operations commute: they can be applied in any order and still converge, without a central server. Sequence CRDTs (RGA, Logoot, Yjs, Automerge) assign positions between neighbours. Pros: works peer to peer and offline. Cons: metadata overhead (ids for every character, tombstones for deletes) and harder garbage collection.

Architecture

  • Optimistic local apply: a client applies its own edit immediately (zero latency), sends it, and reconciles when the server's order arrives.
  • One session server per document keeps ordering simple; route by document id (consistent hashing). Scale by having many documents, not one document on many servers.
  • Persistence: append operations to a log, snapshot periodically so loading does not replay the entire history; this also enables version history and undo.
  • Presence: cursors and selections are ephemeral, sent over the same channel with throttling and stored in memory only.
  • Large documents: split into blocks or pages to bound transform cost; limit simultaneous editors for performance.

How this gets asked

Why do concurrent edits need transformation or CRDTs?

  • To compress text No.
  • Applying edits in different orders at different replicas would diverge Correct.
  • To encrypt edits No.
  • To speed up typing No.

OT adjusts positions; CRDTs make operations commutative so every replica converges.

Self-check

OT versus CRDT?

OT transforms operations against concurrent ones with a central order; CRDTs use unique ids so operations commute and need no server.

Interview questions: Case studies 4

7 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Medium Design a metrics system: pull or push?

Pull gives liveness knowledge and central config; push suits short-lived jobs. Buffer through a queue, store in a compressed time-series database with downsampling and cardinality limits.

Medium Design a leaderboard.

A Redis sorted set with ZADD, ZREVRANK and ZREVRANGE for updates, rank and top-k; separate sets per time window; database as the source of truth.

Advanced Design ad click aggregation with accurate counts.

Kafka partitioned by ad id, stream windows with event time and watermarks, checkpoints and idempotent writes, raw events archived and a batch job reconciling numbers for billing.

Advanced How do you handle a hot key in aggregation?

Add a salt to the key, aggregate partial counts, then merge in a second stage.

Advanced How would you design Kafka?

Partitioned append-only logs with leaders and followers, in-sync replicas and acks, consumer groups with committed offsets, retention and compaction, and a Raft-based controller.

Advanced Design Google Docs collaboration.

WebSocket sessions with one server per document, operational transformation or CRDTs for convergence, optimistic local application, operation log with snapshots and ephemeral presence.

Advanced OT versus CRDT?

OT transforms concurrent operations with a central ordering; CRDTs give every element a unique id so operations commute and no server is needed, at the cost of metadata.
