Part SD18

Storage engine internals: B-trees, LSM trees, WAL, bloom filters and indexes

Choosing a database is choosing a storage engine. This part opens the box: how a B-tree page is found, why an LSM tree writes fast, what a write-ahead log guarantees and why bloom filters save disk reads, with small working models you can run.

Advanced~4 hours

Why storage engines matter

Every database answers two questions: how are bytes laid out on disk and how is a key found quickly. Disks (even SSDs) reward sequential access and large blocks, and punish small random writes. The two dominant designs trade differently:

B-tree (PostgreSQL, MySQL InnoDB, SQLite)LSM tree (RocksDB, Cassandra, LevelDB, HBase)
Write pathFind the page, modify in placeAppend to memory and a log, flush sorted files later
ReadsOne tree walk, O(log n) page readsCheck memtable and several files, helped by bloom filters
StrengthPredictable reads, range scans, transactionsVery high write throughput, compression
WeaknessRandom writes, page splits, fragmentationRead and space amplification, compaction work
Write amplificationPage rewritten plus logData rewritten at each level during compaction

How this gets asked

Why are LSM trees good for write-heavy workloads?

  • They avoid logging They log to a WAL.
  • They turn random writes into sequential appends and batched flushes Correct.
  • They keep everything in RAM No.
  • They never compact They compact.

Sequential I/O is far cheaper than random page updates.

Pages and B-trees

Data is stored in fixed-size pages (4 to 16 KB). A B+tree keeps keys sorted in a high fan-out tree: internal nodes hold separator keys and child pointers; leaves hold records (or pointers) and are linked for range scans.

With a fan-out of about 500, a tree of height 3 addresses 500^3 = 125 million keys, so a lookup needs at most 3 to 4 page reads, and the top levels stay cached in memory.

import bisect, random
random.seed(0)
class BPlusTree:
    """Tiny B+tree with insert and range scan (order = max keys per node)."""
    def __init__(self, order=4):
        self.order, self.root = order, {"leaf": True, "keys": [], "vals": [], "next": None}
        self.splits = 0
    def _find_leaf(self, node, k):
        while not node["leaf"]:
            node = node["kids"][bisect.bisect_right(node["keys"], k)]
        return node
    def insert(self, k, v):
        split = self._insert(self.root, k, v)
        if split:
            sep, right = split
            self.root = {"leaf": False, "keys": [sep], "kids": [self.root, right]}
    def _insert(self, node, k, v):
        if node["leaf"]:
            i = bisect.bisect_left(node["keys"], k)
            if i < len(node["keys"]) and node["keys"][i] == k: node["vals"][i] = v; return None
            node["keys"].insert(i, k); node["vals"].insert(i, v)
            if len(node["keys"]) <= self.order: return None
            mid = len(node["keys"]) // 2
            right = {"leaf": True, "keys": node["keys"][mid:], "vals": node["vals"][mid:], "next": node["next"]}
            node["keys"], node["vals"], node["next"] = node["keys"][:mid], node["vals"][:mid], right
            self.splits += 1
            return right["keys"][0], right
        i = bisect.bisect_right(node["keys"], k)
        res = self._insert(node["kids"][i], k, v)
        if not res: return None
        sep, right = res
        node["keys"].insert(i, sep); node["kids"].insert(i + 1, right)
        if len(node["keys"]) <= self.order: return None
        mid = len(node["keys"]) // 2
        up = node["keys"][mid]
        right = {"leaf": False, "keys": node["keys"][mid + 1:], "kids": node["kids"][mid + 1:]}
        node["keys"], node["kids"] = node["keys"][:mid], node["kids"][:mid + 1]
        self.splits += 1
        return up, right
    def get(self, k):
        leaf = self._find_leaf(self.root, k)
        i = bisect.bisect_left(leaf["keys"], k)
        return leaf["vals"][i] if i < len(leaf["keys"]) and leaf["keys"][i] == k else None
    def scan(self, lo, hi):
        leaf, out = self._find_leaf(self.root, lo), []
        while leaf:
            for k, v in zip(leaf["keys"], leaf["vals"]):
                if k > hi: return out
                if k >= lo: out.append(k)
            leaf = leaf["next"]
        return out
    def height(self):
        h, n = 1, self.root
        while not n["leaf"]: n = n["kids"][0]; h += 1
        return h
keys = random.sample(range(100000), 5000)
t = BPlusTree(order=8)
for k in keys: t.insert(k, k * 2)
assert all(t.get(k) == k * 2 for k in keys[:500]) and t.get(-5) is None
assert t.scan(1000, 2000) == sorted(k for k in keys if 1000 <= k <= 2000)
print("5000 keys, order 8: height", t.height(), "| node splits", t.splits, "| point lookups and range scan verified")

Output

5000 keys, order 8: height 5 | node splits 1018 | point lookups and range scan verified

What to remember

  • Inserts may split a full page into two and push a separator key up; the tree grows at the root, so all leaves stay at the same depth.
  • Range scans follow leaf links. That is why B-tree indexes are great for BETWEEN and ORDER BY.
  • Clustered index: table rows are stored in the leaf (InnoDB primary key). Secondary index: leaves hold the primary key, requiring a second lookup.
  • Key size matters: smaller keys, larger fan-out, shallower tree. Random UUID primary keys cause scattered inserts and page splits; time-ordered ids append at the right edge.

How this gets asked

A B-tree with fan-out 100 and height 3 can address roughly how many keys (in thousands)? (100^3 / 1000)

100^3 = 1,000,000 keys, i.e. 1000 thousand.

What happens when a B-tree leaf is full and a key is inserted?

  • The insert fails No.
  • The page splits and a separator is pushed up to the parent Correct.
  • All pages are rewritten No.
  • The tree is rebuilt No.

Splits keep all leaves at the same depth.

Self-check

Why do B-trees have such high fan-out?

Nodes are sized to a disk page, so each reads hundreds of keys, making the tree very shallow.

The write-ahead log

Updating a page in place is not atomic: a crash mid-write leaves a torn page. The write-ahead log (WAL) records each change sequentially before the page is modified, and the commit is acknowledged once the log record is flushed (fsync). After a crash the database replays the log to redo committed changes (and undoes uncommitted ones).

Why it works: sequential log appends are fast, and the log is the single source of truth for recovery. WALs also enable replication (ship the log), point-in-time recovery and change data capture.

import json
class TinyDB:
    """Key-value store with a write-ahead log; the 'disk page' may be lost in a crash."""
    def __init__(self): self.log, self.pages = [], {}
    def put(self, k, v):
        self.log.append(json.dumps({"op": "put", "k": k, "v": v}))   # 1. log first (fsync)
        self.pages[k] = v                                                # 2. page later (may be lost)
    def crash(self): self.pages = {}                                     # in-memory state vanishes
    def recover(self):
        for line in self.log:
            r = json.loads(line)
            if r["op"] == "put": self.pages[r["k"]] = r["v"]
db = TinyDB()
db.put("a", 1); db.put("b", 2); db.put("a", 3)
db.crash()
print("after crash:", db.pages)
db.recover()
print("after replaying the log:", db.pages)

Output

after crash: {}
after replaying the log: {'a': 3, 'b': 2}

Related ideas: checkpoints (flush dirty pages so replay starts later), group commit (batch many commits into one fsync), fsync cost (about 0.1 to 1 ms on SSD, several ms on a network disk), and synchronous_commit = off trading a few ms of durability for throughput.

How this gets asked

What does the write-ahead rule require?

  • Write data pages before the log Reverse.
  • Log the change durably before modifying or flushing data pages Correct.
  • Never fsync No.
  • Log only deletes No.

That ordering is what makes crash recovery possible.

Self-check

Why can the commit be acknowledged after the log fsync only?

The log has the full change, so recovery can redo it even if the data pages never reached disk.

LSM trees

A log-structured merge tree turns random writes into sequential ones:

  1. A write goes to the WAL (durability) and into an in-memory sorted memtable.
  2. When the memtable is full it is flushed as an immutable sorted file, an SSTable.
  3. Reads check the memtable, then SSTables from newest to oldest.
  4. Background compaction merges SSTables, dropping overwritten values and deleted keys (tombstones).

Deletes write a tombstone marker; the data physically disappears only when compaction merges it with the older value.

import bisect
class LSM:
    def __init__(self, memtable_limit=4):
        self.mem, self.limit, self.tables, self.reads_touched = {}, memtable_limit, [], 0
    def put(self, k, v):
        self.mem[k] = v
        if len(self.mem) >= self.limit: self.flush()
    def delete(self, k): self.put(k, None)             # tombstone
    def flush(self):
        self.tables.insert(0, sorted(self.mem.items()))  # newest first
        self.mem = {}
    def get(self, k):
        if k in self.mem: return self.mem[k]
        for t in self.tables:
            self.reads_touched += 1
            i = bisect.bisect_left(t, (k,))
            if i < len(t) and t[i][0] == k: return t[i][1]
        return None
    def compact(self):
        merged = {}
        for t in reversed(self.tables):                  # oldest first, newer overwrites
            merged.update(dict(t))
        self.tables = [sorted((k, v) for k, v in merged.items() if v is not None)]
db = LSM()
for i in range(10): db.put(f"k{i}", i)
db.put("k3", 333); db.delete("k5")
for i in range(10, 14): db.put(f"k{i}", i)
print("sstables before compaction:", len(db.tables))
print("k3 =", db.get("k3"), "| k5 (deleted) =", db.get("k5"), "| k0 =", db.get("k0"), "| sstables touched so far:", db.reads_touched)
db.compact()
print("sstables after compaction:", len(db.tables), "| entries:", len(db.tables[0]), "| k3 =", db.get("k3"), "| k5 =", db.get("k5"))

Output

sstables before compaction: 4
k3 = 333 | k5 (deleted) = None | k0 = 0 | sstables touched so far: 8
sstables after compaction: 1 | entries: 13 | k3 = 333 | k5 = None

What is a tombstone?

Self-check

What does compaction do?

Merges sorted files, discards overwritten values and tombstoned keys, and bounds the number of files a read must check.

Bloom filters

A bloom filter says "definitely not present" or "maybe present". LSM engines keep one per SSTable so most lookups for missing keys skip the file without touching disk.

With m bits, k hash functions and n items, the false-positive rate is about (1 - e^(-kn/m))^k. About 10 bits per key and 7 hash functions give roughly 1%.

import hashlib, math
class Bloom:
    def __init__(self, m, k): self.m, self.k, self.bits = m, k, bytearray(m)
    def _hashes(self, x):
        for i in range(self.k):
            yield int(hashlib.sha256(f"{i}:{x}".encode()).hexdigest(), 16) % self.m
    def add(self, x):
        for h in self._hashes(x): self.bits[h] = 1
    def __contains__(self, x): return all(self.bits[h] for h in self._hashes(x))
n, m, k = 5000, 50000, 7
b = Bloom(m, k)
for i in range(n): b.add(f"user{i}")
assert all(f"user{i}" in b for i in range(n))                     # no false negatives
fp = sum(f"other{i}" in b for i in range(20000)) / 20000
theory = (1 - math.exp(-k * n / m)) ** k
print(f"false positive rate: measured {fp:.4f}, formula {theory:.4f} (10 bits per key, k = 7)")

Output

false positive rate: measured 0.0078, formula 0.0082 (10 bits per key, k = 7)

Variants: counting bloom (supports delete), cuckoo filter, quotient filter. Used in LSM files, CDNs (skip one-hit wonders), spell checkers and "have I seen this URL?" crawlers.

How this gets asked

A bloom filter reports a key as absent. What does that mean?

  • It might still exist No, that applies to 'present'.
  • It definitely does not exist Correct, there are no false negatives.
  • The filter is full No.
  • Nothing No.

False positives are possible; false negatives are not.

Self-check

How does a bloom filter save disk reads?

It cheaply proves a key is absent from an SSTable so that file need not be read.

Amplification: the cost model

TermMeaning
Write amplificationBytes physically written per byte logically written
Read amplificationDisk reads per query
Space amplificationBytes on disk per byte of live data

The RUM conjecture: you cannot minimise Reads, Updates and Memory/space together. B-trees favour reads; leveled LSM favours space and reads over writes; size-tiered LSM favours writes.

How this gets asked

Which statement about the RUM conjecture is right?

  • You can have all of fast reads, fast updates and low space No.
  • Optimising two of read, update and memory costs the third Correct.
  • It only applies to RAM No.
  • It only applies to SQL No.

Every design chooses what to sacrifice.

Self-check

Define write amplification.

Physical bytes written to storage divided by logical bytes written by the application.

Row stores versus column stores

  • Row store (PostgreSQL, MySQL): all columns of a row are adjacent. Best for transactional access to whole records.
  • Column store (Parquet, ClickHouse, BigQuery, Redshift, Snowflake): each column is stored separately. Analytical queries read only the needed columns, and similar values compress extremely well (run-length, dictionary, delta encoding), and vectorised execution processes many values per CPU instruction.
import random, zlib, json
random.seed(1)
rows = [{"id": i, "country": random.choice(["IN", "US", "DE"]), "amount": random.randint(1, 5) * 10} for i in range(20000)]
row_bytes = zlib.compress(json.dumps(rows).encode(), 6)
cols = {c: [r[c] for r in rows] for c in rows[0]}
col_bytes = sum(len(zlib.compress(json.dumps(v).encode(), 6)) for v in cols.values())
print(f"row layout: {len(row_bytes):,} bytes | column layout: {col_bytes:,} bytes (compressed) | ratio {len(row_bytes) / col_bytes:.2f}x")

Output

row layout: 75,278 bytes | column layout: 60,820 bytes (compressed) | ratio 1.24x

How this gets asked

Why do column stores compress well?

  • They use encryption No.
  • Values in one column are similar and can use run-length, dictionary or delta encoding Correct.
  • They delete data No.
  • They store fewer rows No.

Homogeneous data is compressible.

Putting it together: choosing an engine

WorkloadPrefer

Heavy ingestion, time series, logsLSM (Cassandra, RocksDB, ClickHouse MergeTree)
Mostly point lookups of a huge key spaceLSM or hash-partitioned KV

Key idea

B-trees update pages in place and read in O(log n) pages; LSM trees append, sort and merge, trading read and space amplification for write throughput. Every durable engine has a WAL. Bloom filters rescue LSM reads. Say which amplification you are optimising when you pick an engine.

Interview questions: Storage engines

15 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Why do databases store data in pages?

Disks and SSDs read and write in blocks. Fixed-size pages (4 to 16 KB) match that unit, so each I/O fetches many records and the buffer pool can cache them.

Basic What is a write-ahead log and why does every durable database have one?

An append-only record of changes written and flushed before the data pages are modified. After a crash the database replays it, so committed changes are not lost and half-written changes can be undone.

Basic How deep is a B-tree for a billion keys?

With a fan-out of several hundred, three to four levels; the upper levels stay cached, so a lookup costs about one or two disk reads.

Medium B-tree versus LSM tree: when do you choose each?

B-trees for read-heavy and transactional workloads with range queries and predictable latency; LSM trees for write-heavy or ingestion workloads, accepting read and space amplification and background compaction.

Medium How does an LSM tree handle a write and a read?

A write goes to the WAL and the in-memory memtable; full memtables flush to immutable sorted SSTables. A read checks the memtable then SSTables from newest to oldest, using bloom filters to skip files.

Medium What is a tombstone and why are deletes slow to reclaim space in LSM engines?

A delete writes a marker because SSTables are immutable. The old value and the marker are physically removed only when compaction merges the files that contain them.

Medium What is write amplification?

The ratio of bytes physically written to storage to bytes the application wrote. LSM compaction and B-tree page rewrites both cause it; it affects SSD lifetime and throughput.

Medium How does a bloom filter reduce reads in an LSM tree?

Each SSTable has a filter that can say a key is definitely absent, so most lookups for missing keys skip that file with no disk access.

Medium Why can random UUID primary keys hurt a B-tree?

Inserts land on random leaf pages, causing cache misses and page splits and fragmentation. Time-ordered ids append at the right edge and keep locality.

Advanced Explain compaction strategies.

Size-tiered merges similar-sized files (cheap writes, more space and read amplification); leveled keeps non-overlapping files per level (better reads and space, higher write amplification); time-window compaction suits TTL time series.

Advanced What is the RUM conjecture?

A storage design cannot minimise read cost, update cost and memory/space at the same time; optimising two worsens the third.

Advanced Why are column stores faster for analytics?

They read only the needed columns, compress similar values well (run-length, dictionary, delta) and use vectorised execution. They are slower for single-row transactional access.

Advanced What does group commit do?

Batches the log flushes of many concurrent transactions into one fsync, greatly improving throughput at a small latency cost.

Advanced How does MVCC let readers avoid blocking writers?

Each write creates a new row version tagged with transaction ids; a reader sees a snapshot of versions committed before it began. Old versions are cleaned later (vacuum or purge).

Advanced What is a checkpoint?

A point where dirty pages are flushed so recovery needs to replay the log only from that point forward, bounding recovery time and allowing old log segments to be removed.
