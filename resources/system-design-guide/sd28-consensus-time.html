Consensus, clocks and coordination: Raft, leader election, logical time and CRDTs

Most hard distributed-systems questions reduce to two problems: nodes disagree about time, and nodes disagree about who is in charge. This part explains the tools that solve them, in plain language first and then with small programs you can run and break.

Advanced~5 hours

Why agreement is hard

Put three servers in three buildings. Messages between them can be slow, lost, duplicated or reordered, and any server can crash and restart. You cannot tell a crashed server from a slow one, because both are silent. Yet the system must still answer questions such as "who is the leader?", "was this payment recorded?" and "which update came first?".

The famous results explain the limits:

  • Two Generals: with an unreliable channel, two parties can never be certain they agree.
  • FLP impossibility: in a fully asynchronous network, no algorithm can guarantee consensus if even one node may crash. Real protocols work around it using timeouts (partial synchrony) and randomisation.
  • CAP: during a network partition you choose consistency or availability.

Think of consensus as a group of friends choosing a restaurant over unreliable text messages: they need a rule so that everyone who finally decides decides the same place, even if some phones were off.

Clocks lie

Every machine has its own clock, and clocks drift (by milliseconds per day) and jump (when NTP corrects them). Two events on different machines cannot be ordered reliably by wall-clock time. Consequences:

  • "Last write wins" by timestamp can silently drop a newer write written from a machine whose clock is behind.
  • Lease and lock expiry based on local clocks is unsafe if a process pauses (garbage collection) or the clock jumps. Use fencing tokens (SD25).
  • Google Spanner uses atomic clocks and GPS to bound clock uncertainty (TrueTime) and waits out the uncertainty before committing; most systems cannot afford that and use logical time instead.

Monotonic clocks (time.monotonic()) measure durations on one machine and never go backwards; wall clocks measure calendar time and can. Use the first for timeouts and the second for display.

Logical time

What matters is usually causality: did A happen before B because A could have influenced B? Write A -> B ("happened before"). Events on one node are ordered; a send happens before its receive; and the relation is transitive. Two events with no path between them are concurrent.

Lamport clocks

Each node keeps a counter. Increment it on every event; stamp each message with it; on receive, set counter = max(local, message) + 1. If A -> B then L(A) < L(B). The converse is false: a smaller stamp does not prove causality. Lamport clocks give a consistent total order (break ties with the node id) but cannot detect concurrency.

class Node:
    def __init__(self, name): self.name, self.t, self.log = name, 0, []
    def event(self, what):
        self.t += 1; self.log.append((self.t, self.name, what)); return self.t
    def send(self, what):
        self.t += 1; self.log.append((self.t, self.name, "send " + what)); return self.t
    def receive(self, stamp, what):
        self.t = max(self.t, stamp) + 1; self.log.append((self.t, self.name, "recv " + what))
a, b, c = Node("A"), Node("B"), Node("C")
a.event("start"); s = a.send("m1"); b.event("local"); b.receive(s, "m1")
s2 = b.send("m2"); c.event("local"); c.receive(s2, "m2")
for line in sorted(a.log + b.log + c.log): print(line)

Vector clocks

Each node keeps a vector with one counter per node. This can tell whether two events are ordered or concurrent: V1 <= V2 componentwise means "before"; if neither is <= the other, they are concurrent (a real conflict, as in Dynamo-style stores).

def merge(a, b): return {k: max(a.get(k, 0), b.get(k, 0)) for k in sorted(a.keys() | b.keys())}
def compare(a, b):
    keys = a.keys() | b.keys()
    le = all(a.get(k, 0) <= b.get(k, 0) for k in keys)
    ge = all(a.get(k, 0) >= b.get(k, 0) for k in keys)
    return "equal" if le and ge else "before" if le else "after" if ge else "CONCURRENT"
v1 = {"A": 1}                         # write on node A
v2 = merge(v1, {"B": 1})              # B saw v1 then wrote
v3 = {"A": 2}                         # A wrote again without seeing B's write
print("v1 vs v2:", compare(v1, v2))
print("v2 vs v3:", compare(v2, v3), "-> a genuine conflict that the application must merge")
print("merged:", merge(v2, v3))

Output

v1 vs v2: before
v2 vs v3: CONCURRENT -> a genuine conflict that the application must merge
merged: {'A': 2, 'B': 1}

Hybrid logical clocks (HLC) combine physical time and a logical counter so timestamps stay close to real time yet respect causality (used by CockroachDB and others).

Quorums

With N replicas, a write acknowledged by W and a read from R replicas always overlap if R + W > N. Majority quorums (N/2 + 1) are special: any two majorities intersect, so two different leaders cannot both be elected in the same term, which is the key safety fact behind Paxos and Raft.

Leader election and Raft

Raft was designed to be understandable. A cluster has one leader; clients send writes to it; it replicates a log of commands to followers; a command is committed once a majority has stored it; every node applies committed commands in order to the same state machine. Because all nodes apply the same log in the same order, they end in the same state (replicated state machine).

The three sub-problems

  1. Leader election. Followers use a randomised election timeout (for example 150 to 300 ms). The first to time out increments its term, votes for itself and requests votes. A node grants its vote if it has not voted in that term and the candidate's log is at least as up to date as its own. Randomised timeouts make split votes rare and quickly resolved.
  2. Log replication. The leader appends the command, sends AppendEntries to followers, and when a majority acknowledge, marks it committed and tells followers. Followers must have a matching previous entry, otherwise they reject and the leader backs up and repairs their log.
  3. Safety. Only a candidate with all committed entries can win, so a committed entry is never lost, and a new leader never overwrites committed entries.

A runnable miniature

The simulation below runs three nodes through an election, replication, a leader crash and a re-election. It is simplified (no real network or timers) but follows the rules above.

class RaftNode:
    def __init__(self, nid): self.id, self.term, self.voted_for, self.log, self.commit, self.role, self.alive = nid, 0, None, [], 0, "follower", True
    def last(self): return (self.log[-1][0], len(self.log)) if self.log else (0, 0)    # (term of last entry, length)
class Cluster:
    def __init__(self, n=3): self.nodes = [RaftNode(i) for i in range(n)]
    def alive(self): return [n for n in self.nodes if n.alive]
    def election(self, cand_id):
        c = self.nodes[cand_id]; c.term += 1; c.role = "candidate"; c.voted_for = c.id; votes = 1
        for n in self.alive():
            if n is c: continue
            if n.term < c.term: n.term, n.voted_for = c.term, None        # newer term: reset the vote
            if n.voted_for in (None, c.id) and c.last() >= n.last():       # candidate log at least as up to date
                n.voted_for = c.id; votes += 1
        if votes > len(self.nodes) // 2:
            c.role = "leader"
            for n in self.alive():
                if n is not c: n.role = "follower"
            return True
        c.role = "follower"; return False
    def leader(self): return next((n for n in self.alive() if n.role == "leader"), None)
    def write(self, cmd):
        L = self.leader()
        if L is None: return "no leader"
        L.log.append((L.term, cmd)); acks = 1
        for n in self.alive():
            if n is not L:
                n.log = list(L.log); n.term = L.term; acks += 1               # followers copy the leader's log
        if acks > len(self.nodes) // 2:
            for n in self.alive(): n.commit = len(L.log)
            return "committed"
        return "not committed (no majority)"
cl = Cluster(3)
print("node 0 election won:", cl.election(0))
print("write x=1:", cl.write("x=1"), "| write y=2:", cl.write("y=2"))
cl.nodes[0].alive = False
print("leader crashed; leader now:", cl.leader())
print("node 1 election (term", cl.nodes[1].term + 1, ") won:", cl.election(1))
print("write z=3 with 2 of 3 alive:", cl.write("z=3"))
cl.nodes[2].alive = False
print("write w=4 with 1 of 3 alive:", cl.write("w=4"))
print("logs:", {n.id: [c for _, c in n.log] for n in cl.nodes})

Output

node 0 election won: True
write x=1: committed | write y=2: committed
leader crashed; leader now: None
node 1 election (term 2 ) won: True
write z=3 with 2 of 3 alive: committed
write w=4 with 1 of 3 alive: not committed (no majority)
logs: {0: ['x=1', 'y=2'], 1: ['x=1', 'y=2', 'z=3', 'w=4'], 2: ['x=1', 'y=2', 'z=3']}

Notice that with two of three nodes alive the cluster keeps working; with one of three it refuses writes (it chooses consistency over availability). That is CAP in action.

Raft failure cases to be able to explain

  • Leader partitioned away: it keeps thinking it leads but cannot reach a majority, so it cannot commit; the majority side elects a new leader with a higher term; when the partition heals the old leader sees the higher term and steps down, discarding uncommitted entries.
  • Split vote: no candidate gets a majority; timeouts expire at different random moments; another election occurs.
  • Stale reads: a deposed leader may serve old data unless reads go through the log, use a leader lease, or use ReadIndex confirmation with a majority.
  • Membership changes: adding or removing nodes safely needs joint consensus or one-at-a-time changes.
  • Log compaction: take snapshots so the log does not grow forever.

Paxos in one paragraph

Paxos reaches the same goal with proposers, acceptors and learners, in two phases: prepare/promise (a proposer asks acceptors to promise not to accept lower-numbered proposals and to report anything already accepted) and accept/accepted (it proposes a value, which must be the highest-numbered previously accepted value if any). Multi-Paxos elects a stable leader to skip phase one. Raft, Zab (ZooKeeper) and Viewstamped Replication are close relatives. Byzantine fault tolerant protocols (PBFT, blockchains) tolerate lying nodes and need 3f + 1 nodes.

Leader election, log replication, and safety (only up-to-date candidates win, committed entries are never lost).

Coordination services

You rarely implement consensus yourself. You use a small replicated service (ZooKeeper, etcd, Consul) for:

  • Leader election and distributed locks (ephemeral nodes or leases, with fencing tokens).
  • Configuration and service discovery with watches that notify on change.
  • Membership and health tracking via sessions and heartbeats.
  • Barriers and queues for coordinating batch workers.

Keep them small and off the hot path: they provide strongly consistent metadata for hundreds of thousands of data-plane requests, not the data itself. Examples of consensus inside bigger systems: Kafka's controller (KRaft), Kubernetes (etcd stores all cluster state), CockroachDB and Spanner (a Raft or Paxos group per data range).

Gossip and failure detection

For large clusters of hundreds of nodes, all-to-all heartbeats do not scale. Gossip has each node periodically exchange state with a few random peers; information spreads exponentially, reaching all N nodes in O(log N) rounds, with no central coordinator. Cassandra and Consul use it for membership. Phi accrual failure detectors output a suspicion level instead of a yes/no, adapting to network jitter. SWIM adds indirect probes to reduce false positives.

import random
random.seed(3)
def gossip_rounds(n, fanout=2):
    informed, rounds = {0}, 0
    while len(informed) < n:
        new = set()
        for node in informed:
            new |= set(random.sample(range(n), fanout))
        informed |= new; rounds += 1
    return rounds
for n in (10, 100, 1000, 10000):
    print(f"{n:>6} nodes: all informed after {gossip_rounds(n)} rounds")

Output

    10 nodes: all informed after 3 rounds
   100 nodes: all informed after 8 rounds
  1000 nodes: all informed after 10 rounds
 10000 nodes: all informed after 14 rounds

The round count grows with log N, not N.

Self-check

How fast does gossip spread information?

In O(log N) rounds, because the informed set roughly multiplies each round.

CRDTs: agreement without coordination

Sometimes you do not want consensus, you want replicas that accept writes anywhere (even offline) and merge automatically. A conflict-free replicated data type has a merge operation that is commutative, associative and idempotent, so replicas converge regardless of message order or duplication (they form a join semilattice).

G-CounterOne counter per replica, only increments; value is the sum; merge is componentwise max

Sequence CRDTs (RGA, Logoot)Collaborative text editing without a central server
 
class GCounter:
    def __init__(self, rid): self.rid, self.counts = rid, {}
    def inc(self, n=1): self.counts[self.rid] = self.counts.get(self.rid, 0) + n
    def value(self): return sum(self.counts.values())
    def merge(self, other):
        for k, v in other.counts.items(): self.counts[k] = max(self.counts.get(k, 0), v)
a, b, c = GCounter("a"), GCounter("b"), GCounter("c")
a.inc(3); b.inc(2); c.inc(4)
# merge in different orders, with a duplicate delivery: all replicas converge
x, y = GCounter("x"), GCounter("y")
for r in (a, b, c, a): x.merge(r)
for r in (c, a, b): y.merge(r)
print("replica x:", x.value(), "| replica y:", y.value(), "| identical state:", x.counts == y.counts)
class ORSet:
    def __init__(self, rid): self.rid, self.n, self.adds, self.removed = rid, 0, set(), set()
    def add(self, e): self.n += 1; self.adds.add((e, f"{self.rid}{self.n}"))
    def remove(self, e): self.removed |= {t for t in self.adds if t[0] == e}
    def elements(self): return sorted({e for e, tag in self.adds if (e, tag) not in self.removed})
    def merge(self, o): self.adds |= o.adds; self.removed |= o.removed
p, q = ORSet("p"), ORSet("q")
p.add("milk"); q.merge(p)                      # both see milk
p.remove("milk"); q.add("milk")                # concurrent: p removes the old milk, q adds a new milk
p.merge(q); q.merge(p)
print("concurrent remove and add -> add wins on both replicas:", p.elements(), q.elements())

Output

replica x: 9 | replica y: 9 | identical state: True
concurrent remove and add -> add wins on both replicas: ['milk'] ['milk']

CRDTs trade away some semantics (for example you cannot enforce "balance never below zero" without coordination) for availability and low latency. They power Redis Enterprise active-active, Riak, and collaborative editors.

Key idea

Do not trust wall clocks; use logical time for ordering. Use majority quorums so decisions cannot conflict. Use an existing consensus service rather than writing your own. Where you can tolerate merging, CRDTs avoid coordination altogether.

Interview questions: Consensus and time

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Why can't distributed machines rely on wall-clock time to order events?

Clocks drift and can jump when corrected, so two machines disagree. Ordering by timestamps can drop newer writes; use logical or hybrid clocks, or version vectors.

Basic What is a quorum?

A majority (or configured number) of replicas that must participate. Any two majorities overlap, so conflicting decisions cannot both succeed.

Medium Explain Lamport clocks.

Each node keeps a counter, increments it per event, stamps messages, and on receive sets it to max(local, received) + 1. If A happened before B then its stamp is smaller; the reverse does not hold.

Medium What do vector clocks add?

One counter per node lets you decide whether two versions are ordered or concurrent, which detects true conflicts (as in Dynamo-style stores).

Medium Describe Raft in three parts.

Leader election with terms and randomised timeouts, log replication where an entry commits once a majority stores it, and safety rules ensuring only up-to-date candidates win and committed entries are never lost.

Medium Why use odd cluster sizes for consensus?

Majorities of 2n+1 nodes tolerate n failures; adding one more node (2n+2) needs a larger majority and tolerates no more failures.

Medium What happens in Raft when the leader is partitioned from the majority?

It cannot commit new entries. The majority side elects a new leader with a higher term; when the partition heals the old leader steps down and its uncommitted entries are discarded.

Medium Why must stale leaders not serve reads blindly?

A deposed leader may not know it was replaced and return old data. Reads go through the log, use a leader lease with bounded clock drift, or confirm leadership with a quorum.

Advanced State the FLP result and how real systems cope.

In a fully asynchronous system consensus cannot be guaranteed if even one node may crash. Real protocols assume partial synchrony and use timeouts and randomisation, giving up liveness (not safety) during bad periods.

Advanced Paxos versus Raft?

Both give consensus with majorities. Paxos separates proposers, acceptors and learners with two phases and is notoriously subtle; Raft decomposes the problem around a strong leader and a replicated log and is easier to implement and teach.

Advanced What is a CRDT and where is it used?

A data type whose merge is commutative, associative and idempotent so replicas converge without coordination: counters, sets, registers, collaborative text. Used in active-active databases and editors, with limits on enforceable invariants.

Advanced Hybrid logical clocks: what and why?

They combine physical time with a logical counter so timestamps stay near real time but still respect causality; used by distributed databases to order transactions without special hardware.

Advanced How does gossip detect failures and spread membership?

Nodes periodically exchange state with random peers so information reaches all nodes in O(log N) rounds; failure detectors such as phi accrual or SWIM turn missed heartbeats into suspicion levels.

Advanced Why does Spanner use atomic clocks?

TrueTime exposes a bounded uncertainty interval; Spanner waits out the uncertainty before committing so timestamps give external consistency across the globe.
