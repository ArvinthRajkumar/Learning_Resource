Cloud architecture and deployment: containers, Kubernetes, multi-region and cost

A design is only real once it runs somewhere. This part explains the building blocks of cloud platforms, how services are packaged and released safely, how to scale and survive a region loss, and how to reason about cost.

Shared responsibility: the provider secures the data centre and hypervisor; you secure your configuration, identities and data. Regions are separate geographic areas; availability zones (AZs) are isolated data centres within a region, so spreading across 2 to 3 AZs survives a data-centre failure while a multi-region design survives a regional outage.

How this gets asked

What does deploying across multiple availability zones protect against?

  • A whole region failure That needs multi-region.
  • Failure of a single data centre Correct.
  • Bugs No.
  • DDoS only No.

AZs are isolated failure domains inside a region.

Containers and Kubernetes

A container packages an application with its dependencies, sharing the host kernel (lighter than a VM). Build once from a Dockerfile, run anywhere. Keep images small, run as non-root, pin versions and scan for vulnerabilities.

Kubernetes schedules containers across machines.

ObjectRole
PodSmallest unit: one or more containers sharing network and storage
DeploymentDeclares the desired number of replicas and handles rolling updates
ServiceStable virtual IP and DNS name in front of changing pods (load balancing)
IngressHTTP routing from outside the cluster
ConfigMap / SecretConfiguration and sensitive values injected into pods
HPAHorizontal Pod Autoscaler: scale replicas on CPU, memory or custom metrics
StatefulSetPods with stable identity and storage (databases)
ProbesLiveness (restart if stuck) and readiness (send traffic only when ready)
Requests and limitsResources reserved versus the cap per container

The control loop is the core idea: you declare desired state; controllers continuously make the actual state match it (self-healing).

apiVersion: apps/v1
kind: Deployment
metadata: {name: api}
spec:
  replicas: 3
  selector: {matchLabels: {app: api}}
  template:
    metadata: {labels: {app: api}}
    spec:
      containers:
      - name: api
        image: registry.example.com/api:1.4.2
        resources: {requests: {cpu: "250m", memory: "256Mi"}, limits: {memory: "512Mi"}}
        readinessProbe: {httpGet: {path: /healthz, port: 8080}}

How this gets asked

What does a readiness probe control?

  • Restarting the container That is liveness.
  • Whether the pod receives traffic Correct.
  • Scaling No.
  • Image pulls No.

Not-ready pods are removed from service endpoints.

What is the core Kubernetes idea?

  • Imperative scripts No.
  • Declare desired state and controllers reconcile reality toward it Correct.
  • Manual scheduling No.
  • Static IPs No.

Self-healing comes from the control loop.

Self-check

Pod, Deployment, Service: one line each.

Infrastructure as code and CI/CD

  • Infrastructure as code (Terraform, Pulumi, CloudFormation): declare infrastructure in version-controlled files, review changes like code, reproduce environments, detect drift. Keep state remote and locked.
  • CI builds, tests and scans every commit. CD promotes the same immutable artifact through staging to production.
  • Environments: dev, staging (production-like), production. Config differs; the artifact does not ("build once, deploy many").

Database migrations: use expand and contract (add the new column, deploy code that writes both, backfill, switch reads, then remove the old column) so every step is backward compatible.

How this gets asked

What is the advantage of a canary release?

  • No monitoring needed Opposite.
  • Limits the blast radius by exposing a small share of traffic first Correct.
  • Doubles capacity That is blue-green.
  • Removes tests No.

Metrics on the small slice decide whether to proceed.

Self-check

What is expand and contract?

Make schema changes in backward-compatible steps: add, dual-write, backfill, switch reads, then remove.

Autoscaling

Reactive autoscaling targets a utilisation level. For a target tracking policy, desired replicas = ceil(current * currentMetric / targetMetric). Add cooldowns to avoid flapping and keep a minimum for cold-start safety.

import math
def desired(current, metric, target, lo=2, hi=50):
    return max(lo, min(hi, math.ceil(current * metric / target)))
replicas, target = 4, 60
for minute, cpu in enumerate([55, 90, 95, 70, 40, 30, 50]):
    new = desired(replicas, cpu, target)
    print(f"min {minute}: cpu {cpu}% with {replicas} pods -> {new}")
    replicas = new

Output

min 0: cpu 55% with 4 pods -> 4
min 1: cpu 90% with 4 pods -> 6
min 2: cpu 95% with 6 pods -> 10
min 3: cpu 70% with 10 pods -> 12
min 4: cpu 40% with 12 pods -> 8
min 5: cpu 30% with 8 pods -> 4
min 6: cpu 50% with 4 pods -> 4

Queue-based workloads scale on queue depth per worker. Scheduled scaling handles known peaks. Scaling stateful tiers (databases) is harder: read replicas, partitioning, or managed autoscaling.

How this gets asked

4 pods at 90% CPU with a 60% target: desired replicas = ceil(4 x 90 / 60)?

4 x 1.5 = 6.

Self-check

Target-tracking formula?

desired = ceil(current replicas x current metric / target metric), bounded by min and max.

Multi-region and disaster recovery

ObjectiveMeaning
RPO (recovery point objective)Maximum acceptable data loss, measured in time
RTO (recovery time objective)Maximum acceptable time to restore service
PatternRPO / RTOCostNotes
Backup and restoreHours / hours to a dayLowestTest restores regularly
Pilot lightMinutes / tens of minutesLowCore data replicated, compute off
Warm standbySeconds to minutes / minutesMediumScaled-down copy running
Active-active multi-regionNear zero / near zeroHighestNeeds conflict resolution, data residency awareness

Routing between regions uses DNS failover (TTL delays), anycast or a global load balancer with health checks. Always drill failover: an untested plan is a hope. Backups follow 3-2-1 (three copies, two media types, one off-site) and must be restorable and immutable against ransomware.

How this gets asked

RPO measures:

  • Time to restore service That is RTO.
  • Maximum tolerable data loss, as time Correct.
  • Cost No.
  • Throughput No.

An RPO of 5 minutes means losing at most 5 minutes of writes.

Which DR pattern has the lowest cost and the longest recovery?

  • Active-active Highest cost.
  • Backup and restore Correct.
  • Warm standby Middle.
  • Pilot light Between.

Nothing runs until disaster strikes.

Self-check

RPO versus RTO?

RPO is how much data you may lose; RTO is how long you may be down.

Cost thinking

Cost is a design constraint. Estimate it like capacity:

HOURS = 730
compute = 10 * 0.17 * HOURS             # 10 instances at $0.17/h
storage = 5000 * 0.023                  # 5 TB object storage at $0.023/GB-month
egress = 20000 * 0.09                   # 20 TB out at $0.09/GB
db = 2 * 0.60 * HOURS                   # 2 DB nodes at $0.60/h
total = compute + storage + egress + db
for name, v in [("compute", compute), ("object storage", storage), ("data egress", egress), ("database", db)]:
    print(f"{name:>15}: ${v:>9,.0f} ({v / total:5.1%})")
print(f"{'total/month':>15}: ${total:>9,.0f}")

Output

        compute: $    1,241 (30.8%)
 object storage: $      115 ( 2.9%)
    data egress: $    1,800 (44.6%)
       database: $      876 (21.7%)
    total/month: $    4,032

Levers: right-size instances, reserved/committed use for steady load, spot instances for fault-tolerant batch, storage tiering and lifecycle rules, CDN to cut egress, compress and cache, delete idle resources, and tag everything for FinOps attribution. Watch hidden costs: cross-AZ and cross-region traffic, NAT gateways, logs and metrics volume.

Key idea

Package once, deploy declaratively, release gradually behind health checks and flags, scale on the right metric, spread across zones, choose a DR pattern from RPO and RTO, and put a dollar estimate next to the architecture.

How this gets asked

Which is a hidden cloud cost?

  • Idle CPU only Not hidden.
  • Cross-AZ and cross-region data transfer and NAT gateway traffic Correct.
  • Free tier No.
  • Open source licences No.

Network egress between zones often surprises teams.

Self-check

Three ways to cut cloud cost?

Right-size and commit for steady load, use spot for batch, and reduce egress and storage with CDN, compression and lifecycle rules.

Interview questions: Cloud and deployment

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Region versus availability zone?

A region is a geographic area; an availability zone is an isolated data centre inside it. Multi-AZ survives a data centre failure; multi-region survives a regional outage.

Basic Container versus virtual machine?

A container shares the host kernel and packages the app with its dependencies, so it is lighter and faster to start; a VM includes a full guest operating system.

Basic What is infrastructure as code?

Declaring infrastructure in version-controlled files (Terraform, CloudFormation) so it is reviewable, reproducible and drift is detectable.

Medium What does Kubernetes do?

Schedules containers across machines, keeps the declared number of replicas running, load-balances Services, rolls out updates and restarts failed pods by reconciling actual state to desired state.

Medium Liveness versus readiness probes?

Liveness failing causes a restart; readiness failing removes the pod from load balancing until it is ready.

Medium Blue-green versus canary deployments?

Blue-green switches all traffic between two full environments for instant rollback at double capacity; canary exposes a small share first and expands as metrics stay healthy.

Medium How do you deploy a breaking database change safely?

Expand and contract: add the new structure, write both, backfill, move reads, then remove the old. Every step stays compatible with the running code.

Medium How does target-tracking autoscaling decide replicas?

desired = ceil(current replicas x current metric / target metric), within min and max, with cooldowns to avoid flapping.

Medium Define RPO and RTO and relate them to DR patterns.

RPO is tolerable data loss, RTO tolerable downtime. Backup-restore is cheapest and slowest; pilot light, warm standby and active-active reduce both at rising cost.

Advanced What are the hidden costs in a cloud bill?

Cross-AZ and cross-region traffic, NAT gateway processing, egress, log and metric ingestion, idle resources and over-provisioned storage.

Advanced Serverless: strengths and limits?

No server management and pay-per-use scaling to zero; but cold starts, execution time limits, vendor lock-in, and unpredictable cost at sustained high load.

Advanced How would you design for a regional failure?

Replicate data across regions (async or sync depending on RPO), keep stateless services deployable in both, use health-checked global routing, and rehearse failover regularly.

Advanced Why immutable infrastructure and one artifact for all environments?

It removes configuration drift and makes what you tested what you ship; environment differences live in configuration and secrets.

Advanced What are spot instances good for?

Interruptible, fault-tolerant work such as batch jobs, CI and stateless workers, at large discounts, with checkpointing and graceful handling of reclaim notices.
