Observability, security and deployment

Designing a system is half the job. The other half is seeing what it is doing, defending it, shipping changes safely and paying for it. Interviewers expect you to mention all four.

MediumAdvanced~3.5 hours

Observability

Intuition

Monitoring tells you that something is wrong. Observability lets you ask new questions to find out why, without shipping new code. You need three kinds of telemetry: logs, metrics and traces.

The three pillars

PillarWhat it isGood forCost
LogsTimestamped records of eventsDetailed debugging of one eventHigh volume, expensive to store and search
MetricsNumbers over time (counters, gauges, histograms)Dashboards, alerts, trends, capacityCheap, aggregated
TracesThe path of one request across services, as spansFinding which service or call is slowNeeds sampling, instrumentation

Logging well

  • Use structured logs (JSON) with fields such as timestamp, level, service, request_id, user_id, latency_ms so they can be queried.
  • Include a correlation id (request id) in every log line and pass it across services.
  • Log at the right level: DEBUG for development, INFO for key events, WARN for recoverable issues, ERROR for failures.
  • Never log secrets, passwords, tokens or full card numbers. Mind personal data.
  • Ship logs asynchronously to a central store (ELK or OpenSearch, Loki, Splunk, cloud logging). Sample high-volume low-value logs.

Metrics well

Metric types: counter (only goes up: requests, errors), gauge (goes up and down: queue depth, memory), histogram (distribution: latency buckets, giving percentiles).

Use RED for services: Rate, Errors, Duration. Use USE for resources: Utilisation, Saturation, Errors. The four golden signals (Google SRE): latency, traffic, errors, saturation.

Avoid high-cardinality labels (user id as a label creates millions of time series and breaks the metrics store).

Distributed tracing

Each request gets a trace id. Every service call creates a span (name, start, duration, parent). Propagate the trace context in headers (W3C traceparent). A trace view shows a waterfall that reveals the slow hop. Tools: OpenTelemetry (standard instrumentation), Jaeger, Zipkin, Tempo.

Alerting

  • Alert on symptoms users feel (error rate, latency SLO burn rate), not on every cause (high CPU alone).
  • Every alert must be actionable, urgent and have a runbook. Noisy alerts cause on-call fatigue and real incidents get ignored.
  • Burn-rate alerts warn when the error budget is being consumed too quickly.
  • Page for urgent, ticket for non-urgent.

Dashboards and incident response

A top-level dashboard per service with the golden signals. During an incident: detect, triage, mitigate (roll back first), resolve, then post-mortem. Mitigate before you root-cause.

How this gets asked

Which signal best finds which service in a call chain is slow?

  • Logs from one server Hard to correlate.
  • Distributed traces Correct.
  • Disk usage metric Not related.
  • DNS TTL Not related.

Traces show a waterfall of spans for one request across services.

Why is putting the user id in a metric label a problem?

  • It leaks passwords Not the main issue.
  • High cardinality creates millions of time series and breaks the metrics store Correct.
  • It breaks dashboards only It breaks the store.
  • It is encrypted No.

Use logs or traces for per-user detail, keep metric labels low-cardinality.

An alert fires on CPU above 80 percent, but users are fine. Better practice is to alert on:

  • Symptoms users feel, such as error rate or SLO burn Correct.
  • Every metric Causes alert fatigue.
  • Nothing No.
  • Log volume Not user-facing.

Alert on user-visible symptoms. Use dashboards for causes.

Security fundamentals

Think in layers

Defence in depth: assume any single control can fail. Apply least privilege (every user, service and key has only the access it needs) and zero trust (authenticate and authorise every call, even inside the network).

The CIA triad

Confidentiality (only authorised access), Integrity (data not tampered with), Availability (service stays up). DoS attacks target availability.

Data in transit and at rest

  • In transit: TLS everywhere, including between internal services (mTLS). HSTS for browsers.
  • At rest: encrypt disks, databases and backups with keys from a KMS (key management service). Rotate keys. Separate who manages data from who holds keys.
  • Secrets: never in source code or images. Use a secrets manager (Vault, AWS Secrets Manager), short-lived credentials and automatic rotation.
  • Passwords: store only a salted, slow hash (bcrypt, scrypt, Argon2), never plain text or fast hashes like SHA-256 alone.
import hashlib, os
salt = os.urandom(16)
pw = b"correct horse battery staple"
slow = hashlib.scrypt(pw, salt=salt, n=2**12, r=8, p=1)
print(len(slow), "byte derived key; same input with a different salt gives:", hashlib.scrypt(pw, salt=os.urandom(16), n=2**12, r=8, p=1) != slow)

Output

64 byte derived key; same input with a different salt gives: True

Common web attacks and defences

AttackWhat happensDefence
SQL injectionAttacker input becomes part of a queryParameterised queries, ORM, least-privilege DB user
XSS (cross-site scripting)Script injected into a page runs in victims' browsersOutput encoding, Content Security Policy, HttpOnly cookies
CSRFA malicious site makes the browser send an authenticated requestSameSite cookies, CSRF tokens
IDOR / broken access controlAccess to others' objects by changing an idCheck ownership on every request
SSRFServer fetches an attacker-chosen internal URLAllow-lists, block metadata IPs, network egress rules
Brute force and credential stuffingGuessing or reusing leaked passwordsRate limiting, MFA, breached-password checks

The OWASP Top 10 is the standard checklist for web risks.

Network security

Put databases and internal services in private subnets with no public IP. Expose only the load balancer. Use security groups and network policies as default-deny allow lists. A WAF (web application firewall) filters malicious requests at the edge. Bastion hosts or identity-aware proxies for admin access.

Privacy and compliance

Know where personal data lives. Support deletion (GDPR "right to be forgotten") and export. Minimise what you collect, encrypt, restrict access, and keep audit logs of sensitive actions. Data residency may force regional storage.

How this gets asked

Which defend against SQL injection? Select all.

  • Parameterised queries
  • String concatenation of user input
  • A least-privilege database account
  • Using an ORM correctly

Never build queries by concatenating untrusted input.

How should passwords be stored?

  • Plain text Never.
  • SHA-256 without salt Fast and rainbow-table friendly.
  • Salted slow hash such as bcrypt, scrypt or Argon2 Correct.
  • Encrypted with a fixed key Reversible.

Slow, salted hashing makes offline guessing expensive.

What is defence in depth?

Layered controls so no single failure leaves the system exposed, plus least privilege and zero trust.

Containers and orchestration

Containers

A container packages an application with its dependencies and runs as an isolated process sharing the host kernel (using Linux namespaces and cgroups). Lighter and faster to start than a virtual machine. An image is the immutable template, built from a Dockerfile in layers.

Virtual machineContainer
IsolationStrong (own kernel)Process-level (shared kernel)
Start timeMinutesSeconds or less
SizeGBsMBs to hundreds of MBs
DensityLowerHigher

Kubernetes in one page

Kubernetes schedules containers across a cluster and keeps the desired state.

ConceptMeaning
PodSmallest unit: one or more containers sharing network and storage
DeploymentDeclares N replicas of a pod, handles rolling updates and rollbacks
ServiceStable virtual IP and DNS name that load balances across pods
IngressRoutes external HTTP traffic to services
ConfigMap, SecretConfiguration and sensitive values injected into pods
HPAHorizontal pod autoscaler, scales replicas on metrics
StatefulSetPods with stable identity and storage (databases, queues)
ProbesLiveness (restart if dead) and readiness (receive traffic when ready)

Declare resource requests and limits so the scheduler can place pods and one pod cannot starve others.

Self-check

Pod, Deployment, Service?

Pod runs containers; Deployment keeps N replicas and rolls updates; Service gives a stable address with load balancing.

CI/CD and release strategies

Continuous integration and delivery

CI: every change is built and tested automatically. CD: every passing change is automatically deployable (delivery) or deployed (deployment).

Release strategies

StrategyHowProsCons
RollingReplace instances graduallyNo extra capacityMixed versions during the roll
Blue/greenTwo environments, flip trafficInstant rollbackDouble capacity during switch
CanarySend a small percentage first, watch metrics, expandLimits blast radiusNeeds good metrics and automation
Feature flagsShip dark, enable per user or percentDecouples deploy from releaseFlag debt, more test combinations
Shadow trafficMirror real requests to the new version without returning its answersSafe load and correctness testingCareful with side effects

Database migrations without downtime

Use expand and contract: add the new column (nullable), deploy code that writes both, backfill, switch reads, then drop the old column in a later release. Never ship a change that requires code and schema to flip at the same instant.

Infrastructure as code

Describe infrastructure in versioned files (Terraform, CloudFormation, Pulumi) reviewed like code, so environments are reproducible and drift is detected. Treat servers as cattle, not pets: replace, do not repair.

How this gets asked

You must rename a database column with zero downtime. What is the safest approach?

  • Rename it in one deploy Old code breaks instantly.
  • Expand and contract over several releases Correct.
  • Take the site offline Downtime.
  • Drop and recreate the table Data loss.

Add new, dual write, backfill, switch reads, then remove the old column.

Which release strategy limits blast radius by exposing a new version to a small share of traffic first?

  • Big bang Opposite.
  • Canary Correct.
  • Cold standby A DR concept.
  • Sticky sessions Unrelated.

Watch metrics on the canary and roll back automatically if they degrade.

Self-check

Rolling, blue/green and canary?

Gradual replacement, full environment flip with instant rollback, and small-percentage exposure with metric checks.

Cost and capacity

Why cost is a design input

Cloud bills often decide between two good designs. Know the big levers:

LeverIdea
Right-sizingDo not run 8-core machines at 5 percent
AutoscalingPay for what you use
Reserved or committed use, spot instancesLarge discounts for predictable or interruptible work
Data transferEgress and cross-region traffic are expensive; keep traffic inside a zone and use CDNs
Storage tiersMove cold data to cheaper classes with lifecycle rules
Caching and compressionReduce backend and bandwidth cost

Capacity planning

Measure current load, project growth, load test to find per-node limits, keep headroom, and review regularly. Load test before big events. Plan for the peak, not the average.

Interview tip

In the wrap-up say: "I would monitor error rate, p99 latency and saturation, alert on SLO burn, deploy with canaries and feature flags, encrypt in transit and at rest with least-privilege access, and review cost per request." That one sentence covers this entire part.

Interview questions: Operations

10 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What are logs, metrics and traces?

Logs are event records, metrics are aggregated numbers over time, traces follow one request across services. Together they provide observability.

Basic What are the golden signals?

Latency, traffic, errors and saturation.

Medium RED versus USE methods?

RED (rate, errors, duration) for request-driven services. USE (utilisation, saturation, errors) for resources like CPUs and disks.

Medium What makes a good alert?

It reflects user-visible symptoms, is actionable, urgent and linked to a runbook. Burn-rate alerts on SLOs are better than raw resource thresholds.

Medium How do you store passwords?

Salted slow hashes such as bcrypt, scrypt or Argon2, never plain text or fast hashes alone.

Medium How do you prevent SQL injection and XSS?

Parameterised queries and least privilege for SQL injection. Output encoding, content security policy and HttpOnly cookies for XSS.

Medium What is defence in depth and least privilege?

Layered controls so one failure is not fatal, and giving each identity only the access it needs.

Advanced Describe expand and contract migrations.

Add the new schema element, write both old and new, backfill, switch reads, then remove the old in a later release, so code and schema never need to change at the same instant.

Advanced Containers versus VMs and what Kubernetes provides?

Containers share the host kernel and are light and fast; VMs have stronger isolation. Kubernetes schedules containers, restarts failures, scales replicas, rolls out updates and provides service discovery.

Advanced How do you control cloud cost in a design?

Right-size, autoscale, use commitments or spot capacity, reduce egress with CDNs and locality, tier cold storage, and cache and compress.
