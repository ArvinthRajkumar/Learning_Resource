Distributed data processing: MapReduce, Spark, streaming and lakehouses

When data no longer fits on one machine, computation has to move to the data. This part explains the model behind MapReduce and Spark, how streaming handles time and late events, how to avoid skew, and how modern data platforms are organised.

Advanced~4 hours

Batch versus stream

BatchStream
InputBounded datasetUnbounded, continuous events
LatencyMinutes to hoursMilliseconds to seconds
Typical toolsHadoop MapReduce, Spark, Hive, dbtKafka Streams, Flink, Spark Structured Streaming
CorrectnessEasy to reason about, rerunnableNeeds state, time handling and late data rules
UseReports, ML training, backfillsAlerts, fraud, live dashboards, CDC

Many systems need both. Lambda architecture: a batch layer for accuracy plus a speed layer for freshness, merged at query time (duplicated logic). Kappa architecture: a single stream processor over a replayable log (Kafka); reprocess history by replaying.

MapReduce

The model: map turns each input record into key-value pairs; the framework shuffles (groups all pairs with the same key onto one reducer); reduce aggregates each key's values. Because map and reduce are independent per record/key, they run in parallel over many machines, and a failed task is simply re-run.

import zlib
from collections import defaultdict
from itertools import chain
docs = ["the cat sat on the mat", "the dog sat on the log", "the cat saw the dog"]
def mapper(doc): return [(w, 1) for w in doc.split()]
def combiner(pairs):                       # local pre-aggregation reduces shuffle volume
    local = defaultdict(int)
    for k, v in pairs: local[k] += v
    return list(local.items())
def shuffle(all_pairs, n_reducers=2):
    parts = [defaultdict(list) for _ in range(n_reducers)]
    for k, v in all_pairs: parts[zlib.crc32(k.encode()) % n_reducers][k].append(v)
    return parts
def reducer(k, vs): return k, sum(vs)
mapped = [combiner(mapper(d)) for d in docs]
raw = sum(len(mapper(d)) for d in docs); after = sum(len(m) for m in mapped)
parts = shuffle(chain.from_iterable(mapped))
result = dict(reducer(k, vs) for p in parts for k, vs in p.items())
print("top words:", sorted(result.items(), key=lambda kv: (-kv[1], kv[0]))[:4])
print(f"pairs shuffled: {raw} without combiner, {after} with combiner")

Output

top words: [('the', 6), ('cat', 2), ('dog', 2), ('on', 2)]
pairs shuffled: 17 without combiner, 14 with combiner

Joins at scale

  • Reduce-side join: shuffle both datasets by join key (general, expensive).
  • Broadcast (map-side) join: ship the small table to every mapper, no shuffle for the large one.
  • Sort-merge and bucketed joins when both sides are pre-partitioned by key.

Less data crosses the network.

A broadcast join is best when:

  • Both tables are huge Shuffle join.
  • One table is small enough to send to every worker Correct.

  • Data is unsorted No.

No shuffle of the big table is needed.

Partitioning and data skew

Work is split by key. If one key is extremely common (a celebrity user, null), one reducer receives most of the data and the whole job waits for it (a straggler). Fixes: salting the hot key (append a random suffix, aggregate twice), a broadcast join for the small side, filtering nulls, and sampling to find heavy hitters.

import random, zlib
random.seed(0)
keys = ["hot"] * 8000 + [f"k{i}" for i in range(2000)]
def load(keys, n=4, salt=1):
    buckets = [0] * n
    for k in keys:
        kk = f"{k}#{random.randrange(salt)}" if k == "hot" else k
        buckets[zlib.crc32(kk.encode()) % n] += 1
    return buckets
print("no salting :", load(keys, 4, 1), "-> one reducer carries most of the data")
print("salted x 16:", load(keys, 4, 16), "-> spread across reducers (then a small second aggregation)")

Output

no salting : [499, 8501, 499, 501] -> one reducer carries most of the data
salted x 16: [2479, 2498, 2542, 2481] -> spread across reducers (then a small second aggregation)

How this gets asked

How does salting fix a hot key?

  • It deletes the key No.
  • It splits one key into several sub-keys spread over reducers, then combines the partial results Correct.
  • It encrypts it No.
  • It sorts it No.

Random suffixes distribute the load.

Spark: lazy DAGs in memory

Spark keeps data in memory as partitioned datasets (RDDs, now mostly DataFrames) and builds a DAG of transformations that is executed only when an action (count, collect, write) is called (lazy evaluation).

IdeaMeaning
Narrow transformationmap, filter: each output partition depends on one input partition; pipelined, no shuffle
Wide transformationgroupByKey, join, repartition: needs a shuffle and starts a new stage
LineageThe recipe to recompute a lost partition (fault tolerance without replication)
Cachingcache() keeps a dataset in memory for reuse (iterative ML, interactive work)
Catalyst / TungstenQuery optimiser and code generation for DataFrames and SQL

Practical tips: prefer reduceByKey/aggregations that combine locally before shuffling over groupByKey; choose partition counts of 2 to 4 per core; avoid collecting big data to the driver; use columnar formats (Parquet) with predicate pushdown and partition pruning.

class Lazy:
    """Miniature lazy pipeline: transformations record steps, an action runs them."""
    def __init__(self, data, steps=()): self.data, self.steps = data, tuple(steps)
    def map(self, f): return Lazy(self.data, self.steps + (("map", f),))
    def filter(self, f): return Lazy(self.data, self.steps + (("filter", f),))
    def collect(self):
        out = []
        for x in self.data:                       # one pass: narrow steps are pipelined
            keep = True
            for kind, f in self.steps:
                if kind == "map": x = f(x)
                elif not f(x): keep = False; break
            if keep: out.append(x)
        return out
pipeline = Lazy(range(10)).map(lambda x: x * x).filter(lambda x: x % 2 == 0).map(lambda x: x + 1)
print("steps recorded, nothing computed yet:", len(pipeline.steps))
print("action runs the DAG:", pipeline.collect())

Output

steps recorded, nothing computed yet: 3
action runs the DAG: [1, 5, 17, 37, 65]

Stream processing: time, windows and state

Two clocks: event time (when it happened) and processing time (when we saw it). Networks reorder and delay events, so streams use:

  • Windows: tumbling (fixed, non-overlapping), sliding (overlapping), session (gap-based).
  • Watermarks: a moving estimate "no event older than T will arrive"; a window is emitted when the watermark passes its end. Later events are late data: drop, side-output, or allow a bounded allowed lateness.
  • State and checkpoints: operators keep state (counts, joins), snapshotted periodically to durable storage so a restart resumes exactly where it left off (Flink's checkpoints give exactly-once state).
  • Delivery semantics: at-most-once, at-least-once, exactly-once (state), with idempotent or transactional sinks for effects.
events = [(1, "a"), (3, "a"), (4, "b"), (11, "a"), (2, "b"), (12, "b"), (25, "a"), (5, "a")]   # (event_time, key); some arrive out of order
WINDOW, LATENESS = 10, 3
windows, watermark, emitted, late = {}, 0, [], []
for t, k in events:
    w = t // WINDOW * WINDOW
    if w + WINDOW <= watermark - LATENESS:
        late.append((t, k)); continue
    windows.setdefault(w, {}); windows[w][k] = windows[w].get(k, 0) + 1
    watermark = max(watermark, t)
    for ws in sorted(list(windows)):
        if ws + WINDOW <= watermark - LATENESS:
            emitted.append((ws, windows.pop(ws)))
print("emitted windows:", emitted)
print("still open:", windows, "| dropped as too late:", late)

Output

emitted windows: [(0, {'a': 2, 'b': 2}), (10, {'a': 1, 'b': 1})]
still open: {20: {'a': 1}} | dropped as too late: [(5, 'a')]

Approximate algorithms at scale

Exact answers can be too expensive; sketches give small, mergeable approximations.

ProblemStructureError / size
Set membershipBloom filter (SD18)False positives only
Distinct countHyperLogLogAbout 2% error in roughly 12 KB
Frequency of itemsCount-Min SketchOverestimates only
Heavy hitters (top-k)Space-Saving / Misra-GriesBounded error
Quantiles (p99)t-digest, GK, DDSketchSmall relative error
 
import random, hashlib
random.seed(2)
class CountMin:
    def __init__(self, w=500, d=4): self.w, self.d, self.t = w, d, [[0] * w for _ in range(d)]
    def _h(self, x, i): return int(hashlib.md5(f"{i}{x}".encode()).hexdigest(), 16) % self.w
    def add(self, x):
        for i in range(self.d): self.t[i][self._h(x, i)] += 1
    def est(self, x): return min(self.t[i][self._h(x, i)] for i in range(self.d))
stream = [f"u{min(int(random.paretovariate(1.2)), 2000)}" for _ in range(20000)]
cm, exact = CountMin(), {}
for x in stream:
    cm.add(x); exact[x] = exact.get(x, 0) + 1
top = sorted(exact, key=exact.get, reverse=True)[:3]
print([(u, exact[u], cm.est(u)) for u in top], "(item, exact, estimate); estimates never undercount:", all(cm.est(u) >= exact[u] for u in exact))

Output

[('u1', 11320, 11320), ('u2', 3320, 3320), ('u3', 1570, 1570)] (item, exact, estimate); estimates never undercount: True

  • Underestimates only No.

Storage formats and platforms

  • Formats: CSV/JSON (easy, slow, big), Parquet/ORC (columnar, compressed, splittable, with statistics for pruning), Avro (row based, schema evolution, great for Kafka).
  • Data warehouse: structured, SQL, governed, fast analytics (BigQuery, Snowflake, Redshift).
  • Data lake: cheap object storage of raw files (S3/GCS), schema on read; flexible but can become a swamp.
  • Lakehouse: open table formats (Delta Lake, Apache Iceberg, Hudi) add ACID transactions, schema evolution and time travel on lake files.
  • ELT with dbt: load raw data, transform in the warehouse with versioned SQL models and tests.
  • Orchestration: Airflow, Dagster, Prefect schedule dependent jobs as DAGs with retries and backfills. Make tasks idempotent, partition outputs by date, and record lineage.
Key idea

Move code to data, minimise shuffles, watch for skew, partition by the key you filter and join on, handle event time with watermarks, and use sketches when exact is too costly. Reprocessable, idempotent jobs on columnar storage are the foundation of reliable pipelines.

Interview questions: Data processing

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Batch versus stream processing?

Batch processes bounded datasets with high latency and simple reasoning; stream processes unbounded events continuously with low latency and needs state and time handling.

Basic Explain MapReduce.

Map transforms records into key-value pairs, the shuffle groups pairs by key across the network, and reduce aggregates each key's values. Failed tasks are simply rerun.

Medium What is data skew and how do you fix it?

A few keys carry most of the data so one task straggles. Fix by salting hot keys, broadcasting the small side of a join, filtering nulls or splitting heavy keys.

Medium Why is Spark often faster than MapReduce?

It keeps intermediate data in memory, pipelines narrow transformations, and optimises whole DAGs, instead of writing to disk between every stage.

Medium Narrow versus wide transformations?

Narrow ones (map, filter) work within a partition and are pipelined. Wide ones (join, groupBy) need a shuffle and start a new stage.

Medium What are event time, processing time and watermarks?

Event time is when it happened, processing time when it is seen. A watermark estimates how far event time has progressed so windows can close, trading completeness against latency.

Medium Lambda versus Kappa architecture?

Lambda runs batch and speed layers and merges them, duplicating logic. Kappa uses only a stream processor over a replayable log and reprocesses by replay.

Medium Why use Parquet instead of CSV for analytics?

Columnar layout, compression, schema and statistics enable column pruning and predicate pushdown, reading far less data.

Advanced How does Flink provide exactly-once state?

Periodic distributed checkpoints (barrier snapshots) of operator state and source offsets; on failure it restores the last checkpoint and replays. Sinks need transactions or idempotence for exactly-once effects.

Advanced Name sketches for approximate analytics.

Bloom filters (membership), HyperLogLog (distinct counts), Count-Min sketch (frequencies), t-digest (quantiles); small, mergeable and with bounded error.

Advanced How would you count unique visitors across billions of events per day?

HyperLogLog per dimension, merged across partitions; about 12 KB per counter gives around 2% error. Use exact counts only where required.

Advanced What problem do Delta Lake, Iceberg and Hudi solve?

ACID transactions, concurrent writes, schema evolution, time travel and efficient upserts on files in object storage.

Advanced Why must pipeline tasks be idempotent and partitioned by date?

Retries and backfills rerun tasks; overwriting a deterministic partition gives the same result without duplicates.

Advanced How do you join a huge fact table with a small dimension?

Broadcast join: send the small table to all workers and join locally, avoiding a shuffle of the large table.
