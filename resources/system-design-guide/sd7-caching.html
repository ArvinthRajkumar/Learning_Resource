Caching

A cache stores a copy of data in a faster place so repeated requests skip the slow path. It is the single most effective performance tool in system design, and the source of its most confusing bugs.

BasicMediumAdvanced~2.5 hours

Why caching works

Intuition

You keep the milk in the kitchen fridge rather than going to the shop every time. Access patterns are not random: a small set of items is requested over and over (temporal locality), and items near a recently used one are likely to be used next (spatial locality). A cache keeps that small hot set in fast storage.

The payoff

Effective access time
T = hit_rate x T_cache + (1 - hit_rate) x T_backend
hit rate
fraction of requests served by the cache
T_cache
cache latency
T_backend
latency on a miss
t_cache, t_db = 1, 20          # milliseconds
for hit in (0.0, 0.5, 0.9, 0.99):
    t = hit * t_cache + (1 - hit) * t_db
    print("hit rate %.2f -> average %.2f ms" % (hit, t))

Output

hit rate 0.00 -> average 20.00 ms
hit rate 0.50 -> average 10.50 ms
hit rate 0.90 -> average 2.90 ms
hit rate 0.99 -> average 1.19 ms

A 90 percent hit rate cut average latency from 20 ms to about 2.9 ms and removed 90 percent of load from the database. The second effect often matters more.

Self-check

Why does a cache help beyond latency?

It removes load from the backend, protecting the database and letting it scale.

Caching strategies

Cache-aside (lazy loading)

The application owns the logic.

  1. Read: look in the cache. On a hit, return it.
  2. On a miss, read the database, write the result into the cache (with a TTL), return it.
  3. Write: update the database, then delete (invalidate) the cache entry.

Pros: only requested data is cached, the cache can fail without breaking correctness, simple. Cons: first read after expiry is slow, brief staleness window, and application code must do it right. This is the most common pattern (Redis in front of SQL).

Read-through

The application asks the cache, and the cache itself loads from the database on a miss. Same effect, cleaner application code, but needs a cache library that supports loaders.

Write-through

Writes go to the cache and the database together, synchronously. Pros: cache always fresh, reads fast. Cons: slower writes, caches data that may never be read.

Write-back (write-behind)

Writes go to the cache and are persisted to the database asynchronously in batches. Pros: very fast writes, absorbs bursts, batching saves I/O. Cons: data loss if the cache dies before flushing, more complex. Fits metrics, counters, view counts.

Write-around

Writes go directly to the database, bypassing the cache. Avoids filling the cache with data that is written once and rarely read. Reads fill it on demand.

A cache-aside implementation

import time

class Cache:
    def __init__(self):
        self.d = {}
    def get(self, k):
        v = self.d.get(k)
        if v and v[1] > time.monotonic():
            return v[0]
        self.d.pop(k, None)
        return None
    def set(self, k, val, ttl):
        self.d[k] = (val, time.monotonic() + ttl)
    def delete(self, k):
        self.d.pop(k, None)

db = {"user:1": "Ada"}
db_reads = [0]
cache = Cache()

def get_user(k):
    v = cache.get(k)
    if v is not None:
        return v
    db_reads[0] += 1                 # slow path
    v = db[k]
    cache.set(k, v, ttl=60)
    return v

def update_user(k, v):
    db[k] = v
    cache.delete(k)                  # invalidate, do not update

for _ in range(5): get_user("user:1")
update_user("user:1", "Grace")
print(get_user("user:1"), "db reads:", db_reads[0])

Output

Grace db reads: 2
Delete, do not update, on write

Updating the cache with the new value on write can race: two writers may finish in a different order in the cache than in the database, leaving the cache wrong until the TTL. Deleting the key lets the next read reload the latest value.

How this gets asked

In cache-aside, what should the writer do to the cache after updating the database?

  • Update the cached value Can race and leave stale data.
  • Delete the cached key Correct.
  • Nothing Readers would see stale data until the TTL.
  • Flush the whole cache Far too heavy.

Deleting lets the next read reload the latest value and avoids ordering races.

Which strategy risks losing acknowledged writes if the cache crashes?

  • Write-through Writes the database synchronously.
  • Write-back Correct.
  • Cache-aside The database is the source of truth.
  • Write-around Writes go straight to the database.

Write-back acknowledges after the cache write and persists later.

Eviction

What eviction is

A cache is smaller than the data, so when it is full it must remove something.

LRU with O(1) operations

Combine a hash map (find any key in O(1)) with a doubly linked list ordered by recency (move to front and remove the tail in O(1)). Python's OrderedDict does exactly that.

from collections import OrderedDict

class LRU:
    def __init__(self, capacity):
        self.cap, self.d = capacity, OrderedDict()
    def get(self, k):
        if k not in self.d:
            return None
        self.d.move_to_end(k)            # mark most recently used
        return self.d[k]
    def put(self, k, v):
        self.d[k] = v
        self.d.move_to_end(k)
        if len(self.d) > self.cap:
            self.d.popitem(last=False)   # evict least recently used

c = LRU(2)
c.put("a", 1); c.put("b", 2)
c.get("a")                # a becomes most recent
c.put("c", 3)             # evicts b
print(c.get("a"), c.get("b"), c.get("c"))

Output

1 None 3

How this gets asked

Which data structure pair gives O(1) get and put for an LRU cache?

  • Array and binary search Not O(1).
  • Hash map and doubly linked list Correct.
  • Heap and set Not O(1) updates.
  • Two stacks Wrong structure.

The hash map finds nodes; the linked list reorders recency in constant time.

Self-check

LRU versus LFU?

LRU evicts the least recently used; LFU evicts the least frequently used. LRU adapts faster, LFU keeps stable favourites.

Invalidation and consistency

A famous joke says there are only two hard things in computer science: cache invalidation and naming things.

Approaches

Add jitter to TTLs so many keys do not expire at the same instant.

Stale data races

Reader A misses and reads old value from DB. Writer updates DB and deletes the key. Reader A then writes the old value into the cache. Now the cache is stale until the TTL. Mitigations: short TTL as a safety net, versioning, or a delayed second delete.

Self-check

Why add jitter to TTLs?

To stop many keys from expiring at the same moment and causing a stampede or avalanche.

Cache failure modes

Cache stampede (thundering herd)

A hot key expires and thousands of requests miss at once, all hitting the database. Fixes: request coalescing (one request rebuilds, others wait), a lock or lease on rebuild, stale-while-revalidate (serve the old value while refreshing), randomised TTLs, and early refresh shortly before expiry.

Cache penetration

Requests for keys that do not exist always miss and always hit the database (often an attack or bug). Fix: cache negative results with a short TTL, or use a Bloom filter of valid keys to reject impossible ones.

Cache avalanche

Many keys expire together, or the whole cache is down, so the database is overloaded. Fix: jittered TTLs, replicate the cache, rate limit and load shed, warm the cache before cutting over.

Hot key

One key receives more traffic than one cache node can handle. Fix: replicate the hot key across nodes (key suffixes key#1..N) and keep a small in-process cache in front.

Cold start

After a deploy or restart the cache is empty and the database sees full load. Fix: warm the cache from replay or a snapshot, ramp traffic.

Design rule

Never let the cache become required for correctness. If Redis dies, the system should slow down, not lose data or fall over. Size the database to survive some misses.

How this gets asked

A very popular key expires and thousands of requests hit the database at once. This is:

  • Cache penetration That is requests for non-existent keys.
  • Cache stampede Correct.
  • Cold start That is an empty cache after restart.
  • Eviction No.

Use request coalescing, locks, stale-while-revalidate and jittered TTLs.

A bot requests ids that do not exist, and every request goes to the database. What helps most?

  • A longer TTL on valid keys Does not help invalid keys.
  • Cache negative results and use a Bloom filter of valid ids Correct.
  • More database replicas only Treats the symptom.
  • Disable the cache Worse.

Reject or cache the 'not found' answer so the database is not hit repeatedly.

Self-check

Name cache stampede, penetration and avalanche.

Stampede: one hot key expiring. Penetration: misses for non-existent keys. Avalanche: many keys expire or the cache fails together.

Handy Redis patterns: INCR counters and rate limits, sorted sets for leaderboards, SET key value NX EX 30 for a simple lock, lists as queues, pub/sub for fan-out, EXPIRE for sessions.

Memory sizing example: 100 million keys x (key 20 B + value 100 B + about 50 B overhead) is about 17 GB, which fits one big node but you shard for throughput and availability.

Multi-level and CDN caching

  • Cache at the edge (CDN), application (in-process), and data (Redis) layers. Each layer has a different hit rate and consistency window.
  • An in-process cache of a few seconds in front of Redis absorbs hot keys with zero network cost, at the price of per-instance staleness.
  • HTTP caching headers (Cache-Control, ETag) let browsers and CDNs do the work for free (SD2).
  • Cache keys must include everything the response varies on (user, language, device, version). A missing dimension serves one user's data to another, a serious security bug.

How this gets asked

Missing a dimension in the key can leak personalised data across users.

Sizing a cache

Worked example: product catalogue cache
  1. 50 million products, 2 KB each, total 100 GB. Traffic follows an 80/20 pattern.
  2. Cache the hot 20 percent: 10 million products x 2 KB = 20 GB.
  3. At 20 GB per node, two nodes plus one replica each need about 80 GB of RAM including overhead, or use bigger nodes.
  4. Expected hit rate about 80 to 90 percent. At 20,000 requests per second, the database sees about 2,000 to 4,000.
A small Redis cluster protects the database. Measure the real hit rate and adjust.

Interview questions: Caching

10 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Why use a cache?

It serves repeated reads from fast memory, cutting latency and protecting the backend. It works because access patterns are skewed toward a hot set.

Basic Explain cache-aside.

The application checks the cache, on a miss reads the database and populates the cache with a TTL, and on writes updates the database then invalidates the key.

Medium Write-through versus write-back?

Write-through updates cache and database together (fresh, slower writes). Write-back writes to cache and persists later (fast, risks data loss if the cache fails before flushing).

Medium LRU versus LFU?

LRU evicts the least recently used item; LFU evicts the least frequently used. LRU adapts quickly; LFU preserves stable favourites but adapts slowly. TinyLFU combines both.

Medium What is a cache stampede and how do you prevent it?

A popular key expires and many requests rebuild it simultaneously. Prevent with request coalescing or locks, stale-while-revalidate, jittered TTLs and early refresh.

Medium Cache penetration and avalanche?

Penetration: repeated requests for non-existent keys bypass the cache; fix with negative caching or a Bloom filter. Avalanche: many keys expire together or the cache fails; fix with jitter, replication and rate limiting.

Medium Why delete rather than update the cache on write?

Updating can race with other writers and leave the cache holding an older value. Deleting lets the next read load the latest data.

Advanced How do you handle a hot key?

Replicate it across nodes with key suffixes, add a short in-process cache in front, and cache aggressively. Sharding alone does not help because one key lives on one node.

Advanced Redis versus Memcached?

Memcached is a simple multi-threaded string cache. Redis offers rich data types, persistence, replication, clustering, scripts and atomic operations, so it doubles as a lightweight data store.

Advanced How do you keep cache and database consistent?

Accept bounded staleness with TTLs, invalidate on writes, use change data capture to invalidate or update, and avoid dual writes. For strict needs read from the database or use versioned keys.
