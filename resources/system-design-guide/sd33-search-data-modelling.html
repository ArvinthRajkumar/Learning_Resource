Search internals and data modelling patterns: inverted indexes, BM25, multi-tenancy and time series

Two skills separate strong designs from vague ones: knowing how a search box actually finds results, and shaping data so that the most important queries are cheap. This part builds a small search engine from scratch and then walks through the modelling patterns that appear in almost every product.

Advanced~5 hours

How a search engine works

A database LIKE '%word%' scans every row. A search engine inverts the problem: for each term, store the list of documents that contain it (the postings list). Finding documents containing "red" and "shoes" becomes intersecting two sorted lists, not scanning text.

The analysis chain

  1. Character filters (strip HTML, normalise accents).
  2. Tokeniser splits text into terms (words, n-grams for partial matches, language-specific for Chinese or Japanese).
  3. Token filters: lowercase, remove stop words ("the", "and"), stem or lemmatise ("running", "ran" to "run"), add synonyms.

A working inverted index

import re, math
from collections import defaultdict
STOP = {"the", "a", "an", "and", "of", "to", "is", "in", "for", "on", "with"}
def stem(t):
    if t.endswith("ies") and len(t) > 4: return t[:-3] + "y"
    if t.endswith("ing") and len(t) > 5:
        t = t[:-3]
        return t[:-1] if len(t) > 2 and t[-1] == t[-2] else t           # running -> runn -> run
    if t.endswith("s") and not t.endswith("ss") and len(t) > 3: return t[:-1]
    return t
def analyse(text):
    return [stem(t) for t in re.findall(r"[a-z0-9]+", text.lower()) if t not in STOP]
DOCS = {
    1: "Red running shoes for men",
    2: "Blue running shorts with pockets",
    3: "Red leather shoes, classic style",
    4: "Waterproof trail running shoes in red and blue",
    5: "Leather belt for men",
}
index, doc_len = defaultdict(dict), {}
for doc_id, text in DOCS.items():
    terms = analyse(text); doc_len[doc_id] = len(terms)
    for t in terms: index[t][doc_id] = index[t].get(doc_id, 0) + 1          # term -> {doc: term frequency}
print("terms:", sorted(index))
print("postings for 'shoe':", dict(index["shoe"]), "| for 'red':", dict(index["red"]))
def search_and(query):
    postings = [set(index.get(t, {})) for t in analyse(query)]
    return sorted(set.intersection(*postings)) if postings else []
print("'red shoes' (AND):", search_and("red shoes"), "| 'running shoes red blue':", search_and("running shoes red blue"))

Output

terms: ['belt', 'blue', 'classic', 'leather', 'men', 'pocket', 'red', 'run', 'shoe', 'short', 'style', 'trail', 'waterproof']
postings for 'shoe': {1: 1, 3: 1, 4: 1} | for 'red': {1: 1, 3: 1, 4: 1}
'red shoes' (AND): [1, 3, 4] | 'running shoes red blue': [4]

Real engines (Lucene, which powers Elasticsearch, OpenSearch and Solr) store postings in compressed, skippable blocks, keep term positions for phrase queries, and merge small index segments in the background.

Name the steps of text analysis.

Character filtering, tokenisation, then token filters such as lowercasing, stop-word removal, stemming and synonyms.

Ranking: TF-IDF and BM25

Matching is not enough; results must be ordered by relevance.

  • TF (term frequency): a document mentioning a term more often is more relevant, with diminishing returns.
  • IDF (inverse document frequency): rare terms are more informative than common ones: idf = ln(1 + (N - df + 0.5) / (df + 0.5)).
  • Length normalisation: a short document with the term is more focused than a long one.

BM25 is the standard formula that combines these:

BM25 score of a document for a query
sum over query terms of idf(t) x ( tf x (k1 + 1) ) / ( tf + k1 x (1 - b + b x len / avglen) )
tf
term count in the document
len
document length
avglen
average length

DOCS = {
    1: "Red running shoes for men",
    2: "Blue running shorts with pockets",
    3: "Red leather shoes, classic style",
    4: "Waterproof trail running shoes in red and blue",
    5: "Leather belt for men",
}
index, doc_len = defaultdict(dict), {}
for doc_id, text in DOCS.items():
    terms = analyse(text); doc_len[doc_id] = len(terms)
    for t in terms: index[t][doc_id] = index[t].get(doc_id, 0) + 1          # term -> {doc: term frequency}
def bm25_search(query, k1=1.2, b=0.75, top=5):
    N = len(DOCS); avg = sum(doc_len.values()) / N
    scores = defaultdict(float)
    for t in analyse(query):
        df = len(index.get(t, {}))
        if df == 0: continue
        idf = math.log(1 + (N - df + 0.5) / (df + 0.5))
        for d, tf in index[t].items():
            scores[d] += idf * tf * (k1 + 1) / (tf + k1 * (1 - b + b * doc_len[d] / avg))
    return sorted(((round(s, 3), d, DOCS[d]) for d, s in scores.items()), reverse=True)[:top]
for q in ("red shoes", "running"):
    print(f"query {q!r}:")
    for row in bm25_search(q): print("   ", row)

Output

query 'red shoes':
    (1.12, 1, 'Red running shoes for men')
    (1.021, 3, 'Red leather shoes, classic style')
    (0.938, 4, 'Waterproof trail running shoes in red and blue')
query 'running':
    (0.56, 2, 'Blue running shorts with pockets')
    (0.56, 1, 'Red running shoes for men')
    (0.469, 4, 'Waterproof trail running shoes in red and blue')

Documents matching more query terms and the rarer terms rise to the top; the OR semantics here returns partial matches ranked below full ones. Production relevance adds field boosts (title over body), freshness, popularity and click signals, and often a learning-to-rank model on top of the BM25 candidates, or vector search (SD23) combined with keywords as hybrid search.

How this gets asked

What does IDF capture?

  • Document length No.
  • Rare terms are more informative than common ones Correct.
  • Recency No.
  • Popularity No.

A match on 'xylophone' says more than on 'the'.

What does the b parameter in BM25 control?

  • Term frequency saturation That is k1.
  • How strongly document length normalises the score Correct.
  • The number of shards No.
  • Stop words No.

b = 0 ignores length, b = 1 fully normalises.

Self-check

BM25 in one sentence?

It scores documents by summed term weights: rare terms count more, repeated terms count with diminishing returns, and longer documents are penalised.

Search at scale

  • Sharding: split the index into shards (by document id hash); every query goes to all shards (scatter-gather), each returns its top-k, and a coordinator merges them. More shards means more parallelism but more overhead; typical shard size is tens of gigabytes.
  • Replicas give availability and read throughput.
  • Indexing path: the database is the source of truth; changes flow via CDC or a queue to the indexer. The index is eventually consistent, so a just-saved item may not appear for about a second. Support reindexing from scratch with a new analyser by building a new index and switching an alias.
  • Near-real-time: documents become searchable after a periodic refresh (about 1 s) that opens a new segment.
  • Deep pagination (page 10,000) is expensive: each shard must produce that many results. Use search_after cursors, or limit depth.
  • Filters and facets (brand, price, colour) use doc values or bitsets, cached and combined cheaply with AND.
import heapq
shards = [[(0.9, "doc1"), (0.5, "doc4"), (0.1, "doc7")], [(0.8, "doc2"), (0.7, "doc5")], [(0.95, "doc3"), (0.2, "doc9")]]
def scatter_gather(shards, k):
    top_per_shard = [sorted(s, reverse=True)[:k] for s in shards]               # each shard answers locally
    return heapq.nlargest(k, (hit for hits in top_per_shard for hit in hits))   # coordinator merges
print("global top 3 from three shards:", scatter_gather(shards, 3))

Output

global top 3 from three shards: [(0.95, 'doc3'), (0.9, 'doc1'), (0.8, 'doc2')]

How this gets asked

How does a distributed search query run?

  • On one shard only No.
  • Scatter to all shards, each returns local top-k, a coordinator merges them Correct.
  • Locally on the client No.
  • Using joins No.

Deep pages are costly because each shard must return many results.

Why is a search index only eventually consistent with the database?

  • A bug No.
  • Changes reach it asynchronously through a queue or CDC and become visible after a refresh Correct.
  • Indexes cannot be updated No.
  • It is read-only No.

The database remains the source of truth.

Self-check

Why avoid deep pagination in search?

Every shard must compute and return all earlier results, so cost grows with the offset; use search_after cursors.

Typo tolerance and autocomplete

  • Edit distance (Levenshtein): allow 1 to 2 edits for longer words. Engines use finite-state automata or n-gram indexes to find candidates quickly instead of comparing with every term.
  • Phonetic matching (Soundex, Metaphone) for names.
  • Autocomplete: a trie or edge n-grams (index "sho", "shoe", "shoes" as prefixes) with ranking by popularity (SD14).
  • Did you mean?: suggest the corrected query using term statistics and past queries.

def edit_distance(a, b):
    prev = list(range(len(b) + 1))
    for i, ca in enumerate(a, 1):
        cur = [i]
        for j, cb in enumerate(b, 1):
            cur.append(min(prev[j] + 1, cur[j - 1] + 1, prev[j - 1] + (ca != cb)))
        prev = cur
    return prev[-1]
vocabulary = sorted(index)
for typo in ("shose", "leathr", "blu"):
    best = sorted((edit_distance(typo, t), t) for t in vocabulary)[:2]
    print(f"{typo!r} -> suggestions {[t for d, t in best if d <= 2]} (distances {[d for d, t in best]})")

Data modelling for the query, not the entity

Start from the access patterns (the queries and their frequency), then shape the data. The relational rule (normalise) and the NoSQL rule (denormalise for the query) are two answers to the same question. Review each table with: What are the keys? What are the top 5 queries? What is the growth rate? What must be transactional?

Audit trails and history

  • Append-only history table (entity_id, changed_at, changed_by, before, after), written in the same transaction, or event sourcing (SD19).
  • Temporal tables with valid_from/valid_to answer "what was true on 1 March?" (slowly changing dimensions in warehouses).
  • Soft delete (deleted_at) keeps data recoverable but pollutes every query and breaks unique constraints (use partial unique indexes), so decide per entity and purge on a schedule; honour deletion laws such as GDPR with real deletion or crypto-shredding.

Time series

Metrics, sensor data and events arrive in time order and are mostly appended and read by time range.

  • Partition by time (daily or monthly) so old partitions are dropped or archived in one cheap operation and queries touch few partitions.
  • Cluster or sort by (series_id, time) for per-series scans; keep a recent hot tier on fast storage and a cold tier in object storage.
  • Downsample with rollups (1 s -> 1 min -> 1 h) and set retention per resolution.
  • Beware high cardinality labels (user id as a metric label) which explode index size.
  • Engines: TimescaleDB, InfluxDB, ClickHouse, Prometheus, Cassandra with time-bucketed partition keys.

Schema evolution without downtime

Use expand and contract (SD21): add nullable columns or new tables, write both, backfill in batches, switch reads, then drop the old. Never rename in one step. Version document schemas (schema_version field) and migrate lazily on read. For events and APIs, evolve compatibly (optional fields, never reuse numbers).

Choosing keys

  • Prefer surrogate keys (ids that carry no meaning) as primary keys; keep natural keys as unique constraints.
  • Choose time-ordered ids (ULID, UUIDv7, Snowflake ids from SD25) to keep index inserts local.
  • Pick a shard key with high cardinality and even access, that appears in most queries; avoid monotonically increasing keys on range-sharded stores (hot last shard) unless you hash them.
  • Money in integer minor units; times in UTC; enums as lookup tables if they change.
Key idea

Search engines invert text into term-to-document postings, rank with TF-IDF-style scores such as BM25, scatter queries over shards and merge top-k lists, and are fed asynchronously from the source-of-truth database. Model data from the queries backwards: tenant ids in every key, the right hierarchy pattern, time-partitioned series, and compatible schema changes.

Interview questions: Search and data modelling

14 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What is an inverted index?

A mapping from each term to the documents (and positions) that contain it, so queries intersect postings lists instead of scanning text.

Basic What is text analysis in search?

Tokenising and normalising text (lowercase, stop words, stemming, synonyms) the same way at index and query time.

Medium Explain TF-IDF and BM25.

TF rewards terms frequent in a document, IDF rewards terms rare across the corpus. BM25 adds saturating term frequency and document length normalisation with parameters k1 and b.

Medium How does a distributed search query execute?

Scatter to all shards, each returns local top-k with scores, and the coordinator merges them; replicas add availability and throughput.

Medium Why is search eventually consistent with the primary database?

Updates flow asynchronously through CDC or a queue and become visible after the next refresh; the database remains the source of truth.

Medium How would you implement autocomplete?

A trie or edge n-gram index keyed by prefix, with candidates ranked by popularity and recency, cached and updated from query logs.

Medium How do you add typo tolerance?

Fuzzy matching with edit distance via automata or n-gram candidates, phonetic algorithms for names, and query suggestions from term statistics.

Medium Compare multi-tenancy models.

Shared tables with tenant_id are cheapest but need strict filtering; schema per tenant and database per tenant increase isolation and cost; cells or hybrids group tenants by size.

Medium Hierarchy storage patterns?

Adjacency list (parent_id), materialised path, nested sets and closure table, trading read simplicity, subtree queries and move cost.

Advanced How do you reindex without downtime?

Build a new index with the new analyser in parallel, replay or backfill data, keep it updated, then switch an alias atomically.

Advanced Why is deep pagination expensive in search?

Each shard must compute and return all results up to the offset; use search_after cursors or cap the depth.

Advanced How do you model time-series data?

Partition by time, key by series and time, downsample with rollups and retention tiers, and control label cardinality.

Advanced How do you make schema changes with no downtime?

Expand and contract: add compatible structure, dual write, backfill in batches, switch reads, then remove the old structure.

Advanced Soft delete trade-offs?

Recoverability and auditing versus polluted queries, broken unique constraints (use partial indexes) and legal deletion duties; purge on a schedule or use crypto-shredding.
