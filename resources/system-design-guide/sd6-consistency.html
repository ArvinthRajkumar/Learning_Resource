Part SD6

Consistency, CAP, transactions and consensus

Once data lives on more than one machine, 'what value does a read return?' stops being obvious. This part builds the vocabulary and the mechanisms: consistency models, the CAP theorem, transactions across services, time, and consensus.

Advanced~4 hours

Why distributed data is hard

Intuition

On one machine there is one memory and one clock, so "the latest value" is meaningful. Across machines, messages are delayed, lost or reordered, machines crash and restart, and clocks disagree. You cannot tell a crashed machine from a slow network. Every consistency model is a different promise about what you may observe in that mess.

Failure modes to design for

FailureMeaning
CrashA node stops and may restart, losing memory
OmissionA message or response is dropped
DelayA message arrives late (long garbage collection pause, congestion)
PartitionThe network splits into groups that cannot talk to each other
ByzantineA node behaves arbitrarily or maliciously (rare inside one company, central to blockchains)
Key idea

You cannot distinguish a dead node from a slow one. Systems use timeouts to guess, and every guess can be wrong. That single fact explains most of distributed systems theory.

Self-check

Why can you not tell a dead node from a slow one?

A missing reply could be a crash, a lost message or a long delay. Timeouts are only guesses.

Consistency models

The spectrum

From strongest to weakest. Stronger models are easier to program against and cost more latency and availability.

ModelPromiseExample behaviour
Linearizable (strong)Every operation appears to take effect at a single instant between its start and end, in real-time orderBehaves like one copy. Once a write finishes, all later reads see it
SequentialAll see the same order of operations, which respects each client's own order, but not real timeSlightly weaker than linearizable
CausalOperations that are causally related are seen in order by everyoneA reply is never seen before its question
Read-your-writes, monotonic readsSession guarantees for one clientYour own post always appears for you
EventualIf writes stop, all replicas converge to the same valueReads may be stale or out of order for a while

Linearizability in practice

Linearizability is what most people mean by "strongly consistent". It is required for: unique usernames, leader election and distributed locks, bank balances where overdrafts are not allowed, and inventory where overselling is unacceptable. It costs a round trip to a quorum or a leader on every operation, and it is unavailable on the minority side of a network partition.

Eventual consistency in practice

Good for: social counters, likes, feeds, product catalogue views, analytics, DNS. Pair it with techniques that make convergence safe: conflict resolution by version vectors or last-write-wins, CRDTs (data types that merge deterministically), read repair and anti-entropy.

# A grow-only counter CRDT (G-Counter): each node counts only its own increments.
# Merging takes the per-node maximum, so merges are order independent and repeatable.
class GCounter:
    def __init__(self, node):
        self.node, self.counts = node, {}
    def incr(self, n=1):
        self.counts[self.node] = self.counts.get(self.node, 0) + n
    def value(self):
        return sum(self.counts.values())
    def merge(self, other):
        for k, v in other.counts.items():
            self.counts[k] = max(self.counts.get(k, 0), v)

a, b = GCounter("A"), GCounter("B")
a.incr(3); b.incr(2)          # concurrent updates on two replicas
a.merge(b); b.merge(a)        # gossip in any order, any number of times
b.merge(a)
print(a.value(), b.value())   # both converge to 5

Output

5 5

How this gets asked

Which model guarantees that once a write completes, every later read from any client sees it?

  • Eventual Allows stale reads for a while.
  • Linearizable Correct.
  • Read-your-writes Only for the same client.
  • Causal Only for causally related operations.

Linearizability behaves as if there is a single copy of the data.

The CAP theorem and PACELC

CAP

During a network Partition, a system must choose between Consistency (linearizable reads and writes, so some requests must fail or wait) and Availability (every request to a working node gets a non-error response, possibly stale). Partitions are a fact of life, so the real choice is C or A when a partition happens.

ChoiceDuring a partitionExamples
CPRefuses or blocks requests that cannot be made consistentZooKeeper, etcd, Consul, HBase, Spanner, MongoDB with majority writes
APKeeps answering, may return stale data, reconciles laterCassandra, DynamoDB (default), Riak, CouchDB, DNS
Common misreadings

CAP does not say "pick two of three" in normal operation. Consistency in CAP means linearizability, not the C in ACID. A system is not "CA": a single machine that cannot partition is not distributed. And many databases are tunable per request.

PACELC

CAP only describes partitions. PACELC adds the everyday trade-off: if Partition, choose A or C; Else (normal operation) choose Latency or Consistency. Replicating synchronously gives consistency at the cost of latency.

SystemDuring partitionElse
DynamoDB, Cassandra (defaults)AL
Spanner, HBaseCC
MongoDB (defaults)CC (reads from primary)
Cosmos DBtunabletunable (five levels)

How this gets asked

During a network partition a CP system will:

  • Return stale data from both sides That is the AP choice.
  • Refuse or block requests that cannot be made consistent Correct.
  • Ignore the partition It cannot.
  • Delete the minority side No.

CP systems sacrifice availability on the side that cannot reach a quorum.

PACELC adds what to CAP?

  • Cost No.
  • The latency versus consistency trade-off in normal operation Correct.
  • Security No.
  • Compression No.

Else, when there is no partition, you still trade latency against consistency.

Self-check

State CAP correctly.

During a network partition you must choose between linearizable consistency and availability.

Transactions and isolation

The problem

Many transactions run at once. Perfect serializability (the result equals some one-at-a-time order) is the safest and the slowest. Databases offer weaker isolation levels that allow certain anomalies for speed.

The anomalies

AnomalyDescriptionExample
Dirty readRead data another transaction has not committedSee a deposit that is later rolled back
Non-repeatable readSame row read twice gives different valuesBalance changes between two reads
Phantom readSame query returns different rowsNew rows appear in a range
Lost updateTwo read-modify-write cycles overwrite each otherTwo increments become one
Write skewTwo transactions each read overlapping data and write different rows, together violating a ruleTwo doctors go off call, leaving none

The standard levels (SQL standard)

LevelDirty readNon-repeatable readPhantom
Read uncommittedPossiblePossiblePossible
Read committedNoPossiblePossible
Repeatable readNoNoPossible (not in some implementations)
SerializableNoNoNo

Real engines differ. PostgreSQL's default is read committed and its repeatable read is snapshot isolation, which prevents phantoms but still allows write skew. MySQL InnoDB's default is repeatable read. Serializable is implemented by strict two-phase locking, or by serializable snapshot isolation that aborts conflicting transactions.

MVCC

Multi-version concurrency control keeps several versions of each row so readers see a consistent snapshot without blocking writers. This is why long reads in PostgreSQL do not block writes, and why old versions must be cleaned up (vacuum).

Fixing lost updates

  • Use an atomic update: UPDATE accounts SET balance = balance - 10 WHERE id = 1 instead of read then write.
  • Optimistic locking: store a version number and update WHERE id = 1 AND version = 7. If zero rows change, retry.
  • Pessimistic locking: SELECT ... FOR UPDATE locks the row until commit.
  • Run at serializable and be ready to retry.

How this gets asked

Which statements about snapshot isolation (PostgreSQL repeatable read) are true? Select all.

  • Readers do not block writers
  • It prevents dirty reads
  • It prevents write skew
  • It still allows write skew

MVCC lets readers and writers proceed together and prevents dirty reads, but write skew is possible; only serializable prevents it.

Self-check

What is write skew?

Two transactions read overlapping data and write different rows so that a combined invariant breaks, which snapshot isolation does not prevent.

Transactions across services

Two-phase commit (2PC)

A coordinator asks all participants to prepare (do the work and promise to commit). If all vote yes it tells everyone to commit, otherwise to abort.

Problems: it blocks if the coordinator crashes after prepare, participants hold locks while waiting, and it adds latency and a single coordinator. Use it inside one database cluster or between a few trusted systems, not across many independent services.

Sagas

A saga breaks a business transaction into a sequence of local transactions, each with a compensating action that semantically undoes it. If step N fails, run compensations for steps N-1 down to 1.

StepActionCompensation
1Create order (pending)Cancel order
2Reserve inventoryRelease inventory
3Charge paymentRefund payment
4Confirm ordernot needed

Two styles: choreography (each service reacts to events, no central brain, harder to follow) and orchestration (a coordinator tells each service what to do, easier to reason about). Sagas give eventual consistency and no isolation, so handle intermediate states (an order is "pending") and make every step idempotent (SD8).

def run_saga(steps, fail_at=None):
    done = []
    for i, (name, do, undo) in enumerate(steps):
        if i == fail_at:
            print("FAIL at", name)
            for dn, dundo in reversed(done):
                print("  compensate", dn); dundo()
            return False
        do(); done.append((name, undo)); print("ok", name)
    return True

noop = lambda: None
steps = [("create order", noop, noop), ("reserve stock", noop, noop), ("charge card", noop, noop)]
run_saga(steps)
print("---")
run_saga(steps, fail_at=2)

Outbox and idempotency

Updating a database and publishing a message are two writes that can disagree. The transactional outbox writes the event into an outbox table in the same transaction as the data and a relay publishes it afterwards. Consumers must be idempotent, because delivery is at least once. See SD8.

How this gets asked

A saga step fails halfway. What happens?

  • Everything rolls back automatically through locks That is 2PC, not a saga.
  • Compensating actions undo earlier steps Correct.
  • Nothing, the data stays inconsistent Compensation restores a consistent state.
  • The coordinator crashes Not by design.

Sagas use compensating transactions instead of distributed locks.

Self-check

2PC versus saga?

2PC gives atomicity with blocking locks and a coordinator; a saga gives eventual consistency with local transactions and compensations.

Time and ordering

Clocks lie

Physical clocks drift and jump (NTP corrections, leap seconds). Two machines never agree exactly, so "last write wins" by timestamp can silently drop data. Never use wall clocks to order events across machines unless you bound the uncertainty (Google Spanner uses atomic clocks and GPS with TrueTime and waits out the uncertainty window).

Logical clocks

  • Lamport clock: each node keeps a counter; increment on each event; on receiving a message set the counter to max(local, received) + 1. If A happened-before B then L(A) < L(B). It gives a consistent order but cannot tell whether two events were concurrent.
  • Vector clock: a vector of counters, one per node. It can detect concurrent updates (neither vector dominates), which is what conflict resolution needs. Used in Dynamo-style stores.
class Lamport:
    def __init__(self): self.t = 0
    def event(self): self.t += 1; return self.t
    def send(self): return self.event()
    def recv(self, ts): self.t = max(self.t, ts) + 1; return self.t

a, b = Lamport(), Lamport()
a.event(); a.event()
ts = a.send()
print("A sends with", ts, "-> B local time after receive:", b.recv(ts))

Output

A sends with 3 -> B local time after receive: 4

Fencing tokens

A client holds a lock with a lease. It then pauses for a long garbage collection. The lease expires, another client gets the lock, and the first resumes and writes, thinking it still holds the lock. The fix: each lock grant carries an increasing fencing token, and the storage rejects writes with a token lower than one it has already seen.

How this gets asked

Why can last-write-wins by wall-clock timestamp lose data?

  • Timestamps are too long No.
  • Clocks across machines drift, so a later write may carry an earlier timestamp Correct.
  • Databases ignore timestamps No.
  • It needs consensus No.

Without bounded clock error, timestamps cannot reliably order events from different machines.

A clock lets you detect that two updates were concurrent.

Vector clocks compare per-node counters; if neither dominates the other, the updates are concurrent.

Consensus and leader election

What consensus is

Consensus is getting several nodes to agree on one value (for example "who is leader" or "what is the next log entry") even when some nodes and messages fail. It underpins replicated state machines, distributed locks, configuration stores and leader election. The classic results: it is impossible to guarantee both safety and termination in a fully asynchronous system with even one crash failure (FLP), so practical algorithms use timeouts for liveness while always keeping safety.

Majority quorums

A group of 2f + 1 nodes tolerates f failures, because any two majorities overlap in at least one node. So 3 nodes tolerate 1 failure, 5 tolerate 2, and 7 tolerate 3. More nodes slow every decision, so five is common.

Raft in plain language

Raft is designed to be understandable and is used by etcd, Consul and CockroachDB.

  1. Each node is a follower, candidate or leader. Time is divided into numbered terms.
  2. A follower that hears nothing from a leader for a random timeout becomes a candidate, increments the term and asks for votes. A node votes once per term. A candidate with votes from a majority becomes leader.
  3. The leader receives client commands, appends them to its log and sends them to followers (AppendEntries). An entry is committed once stored on a majority, then applied to the state machine.
  4. Randomised election timeouts avoid repeated ties. Voting rules ensure a new leader has all committed entries.

Where consensus is used

  • Leader election for databases and queues.
  • Metadata stores: ZooKeeper (ZAB), etcd (Raft), Consul (Raft).
  • Replicated databases: Spanner and CockroachDB replicate every range with Paxos or Raft.
  • Distributed locks and service discovery.

Keep the consensus group small and used for coordination, not for bulk data.

Gossip and failure detection

Large clusters use gossip: each node periodically tells a few random peers what it knows, and information spreads exponentially fast. Failure detectors such as phi-accrual estimate suspicion from heartbeat arrival times rather than a single hard timeout.

How this gets asked

How many node failures can a 7-node Raft cluster tolerate?

A majority is 4 of 7, so up to 3 nodes can fail.

Self-check

Why do consensus groups have an odd size?

A majority quorum of 2f+1 tolerates f failures; an even size adds a node without tolerating more failures.

Interview tip

When asked "strong or eventual?", never answer globally. Say which operations need strong consistency and why, and use the cheaper model everywhere else.

Interview questions: Consistency

11 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What is eventual consistency?

If no new writes happen, all replicas eventually converge to the same value. Reads in the meantime may be stale.

Basic State the CAP theorem.

During a network partition a distributed system must choose between consistency (linearizability) and availability. Normal operation has no such forced choice.

Medium What is PACELC?

If there is a Partition choose Availability or Consistency; Else choose Latency or Consistency. It captures the everyday trade-off CAP ignores.

Medium Name the isolation levels and anomalies.

Read uncommitted (dirty reads), read committed (no dirty reads), repeatable read (no non-repeatable reads, phantoms possible), serializable (no anomalies). Write skew and lost updates need care at lower levels.

Medium What is MVCC?

Multi-version concurrency control keeps several versions of rows so readers see a consistent snapshot without blocking writers.

Medium Two-phase commit versus saga?

2PC gives atomic commit across participants through prepare and commit with a coordinator, but blocks and holds locks. A saga runs local transactions with compensating actions, giving eventual consistency without distributed locks.

Advanced Linearizability versus serializability?

Linearizability is a recency guarantee for single objects (operations appear instant in real-time order). Serializability is an isolation guarantee for transactions (equivalent to some serial order). Strict serializability combines both.

Advanced Why are wall clocks unsafe for ordering events?

Clocks drift and are corrected, so timestamps from different machines may not reflect causality. Use logical or vector clocks, or bounded uncertainty such as Spanner's TrueTime.

Advanced Explain Raft briefly.

Nodes elect a leader per term by majority vote with randomised timeouts. The leader appends client commands to its log and replicates them; an entry commits when stored on a majority. A new leader always has all committed entries.

Advanced What is a fencing token?

A monotonically increasing number issued with each lock or lease. Storage rejects writes with a lower token, preventing a paused former lock holder from corrupting data.

Advanced What is a CRDT?

A data type whose replicas can be updated independently and merge deterministically without coordination, such as counters, sets and sequences. They give strong eventual consistency.
