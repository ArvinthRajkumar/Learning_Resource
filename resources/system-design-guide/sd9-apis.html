APIs, microservices and service communication

An API is the contract between parts of a system. Good APIs are predictable, evolvable and safe under retries and abuse. This part covers how to design them, how services find and talk to each other, and when to split a system into services at all.

MediumAdvanced~3 hours

Designing APIs

Intuition

An API is a promise. Once other teams or customers depend on it, every change risks breaking them. Design for the clients' tasks, keep it small and consistent, and plan for change from day one.

REST in practice

REST models the system as resources (nouns) addressed by URLs and manipulated with HTTP methods.

OperationRequestSuccess
ListGET /v1/orders?limit=20200 with a page
ReadGET /v1/orders/123200
CreatePOST /v1/orders201 with Location header
ReplacePUT /v1/orders/123200 or 204
Partial updatePATCH /v1/orders/123200
DeleteDELETE /v1/orders/123204

Rules of good REST design: plural nouns, nested only for true ownership (/orders/123/items), correct status codes, JSON bodies, consistent error shape, stateless requests, and caching headers where safe.

HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{"error": {"code": "invalid_quantity", "message": "quantity must be 1 or more", "field": "items[0].quantity"}}

Idempotency for unsafe operations

POST /payments can be retried by clients and gateways after a timeout. Accept an Idempotency-Key header, store the first result under that key for a day or so, and return it on retries. This is what payment APIs such as Stripe do.

Pagination

Never return unbounded lists.

StyleHowProsCons
Offset?offset=40&limit=20Easy, random page accessSlow for large offsets (database scans and discards), items shift between pages
Cursor (keyset)?after=<last_id>&limit=20Fast and stable, uses an indexNo jumping to page N
Page tokenOpaque server-generated cursorHides internals, can change laterNot human readable

Keyset SQL: WHERE (created_at, id) < (:ts, :id) ORDER BY created_at DESC, id DESC LIMIT 20.

Versioning and evolution

  • Version in the URL (/v1/) or a header. Keep old versions alive for a published deprecation period.
  • Backward compatible changes: adding optional fields, new endpoints, new enum values (if clients ignore unknown). Breaking changes: removing or renaming fields, changing types or meanings, new required inputs.
  • Be liberal in what you accept, conservative in what you send. Tolerate unknown fields.

Error handling and contracts

Use a stable machine-readable error code plus a human message. Document with OpenAPI. Provide request ids in responses to trace problems. Return 429 with a Retry-After header when rate limiting.

How this gets asked

A client times out calling POST /payments and retries. How do you prevent a double charge?

  • Disable retries Clients and gateways will retry anyway.
  • Require an idempotency key and return the stored result on repeats Correct.
  • Use GET instead Wrong semantics.
  • Ignore it Money is lost.

Store the first outcome under the idempotency key and replay it.

Why is keyset (cursor) pagination better than offset for large tables?

  • It supports jumping to any page Offset does that, not keyset.
  • It uses an index and is stable under inserts Correct.
  • It needs no ordering Needs a stable order.
  • It is always cacheable Not the reason.

Offset makes the database skip rows, which gets slower; keyset seeks using an index.

What status code and header do you return when rate limiting?

REST, gRPC and GraphQL

A common shape: public REST or GraphQL at the edge, gRPC between internal services.

Streaming and real-time

WebSocket (two-way), Server-Sent Events (server to client), gRPC streaming (client, server or both), long polling as a fallback (SD2). For fan-out to millions of clients, put a pub/sub system behind a fleet of connection servers (SD14).

Webhooks

Instead of clients polling, the server calls back a client-supplied URL on events. Sign each payload (HMAC), include an event id for deduplication, retry with backoff, and let receivers acknowledge quickly and process asynchronously.

How this gets asked

Which is the best fit for low-latency internal service calls with a strict schema?

  • GraphQL Better for client-driven queries.
  • gRPC Correct.
  • SOAP over email No.
  • FTP No.

gRPC uses compact binary protobuf over HTTP/2 with generated clients.

Self-check

REST versus gRPC versus GraphQL in one line each.

REST: simple and cacheable; gRPC: fast binary typed contracts for internal calls; GraphQL: clients choose fields to avoid over and under-fetching.

Authentication and authorization

Two different questions

  • Authentication (authn): who are you?
  • Authorization (authz): what are you allowed to do?

Common mechanisms

MechanismHowNotes
Session cookieServer stores session, browser holds an idSimple for web apps, needs CSRF protection
API keyStatic secret per clientEasy, coarse, rotate and scope them
OAuth 2.0A user grants an app limited access via tokensStandard for delegated access ("Sign in with ...")
OpenID ConnectIdentity layer on top of OAuth 2.0Gives an ID token describing the user
JWTSigned token containing claimsVerified without a lookup, hard to revoke, keep short-lived
mTLSBoth sides present certificatesService-to-service identity

OAuth 2.0 authorization code flow in one paragraph

The app sends the user to the identity provider. The user logs in and approves scopes. The provider redirects back with a short-lived authorization code. The app's server exchanges the code (plus its secret or a PKCE verifier) for an access token (short-lived) and a refresh token (long-lived). The app calls the API with Authorization: Bearer <access token>.

Authorization models

  • RBAC: users have roles, roles have permissions. Simple and common.
  • ABAC: decisions use attributes of user, resource and context (department, region, time).
  • ACLs: per-object lists of who may do what (documents, files).

Always check authorization on the server for each request, and check ownership of the specific object, or you create IDOR bugs ("insecure direct object reference": changing /orders/123 to /orders/124 shows someone else's order).

How this gets asked

Which statements about JWTs are correct? Select all.

  • They can be verified without a database lookup
  • They are easy to revoke instantly
  • They should be short-lived
  • They are encrypted by default

JWTs are signed (not encrypted by default) and hard to revoke, so keep them short-lived and use refresh tokens.

Changing /orders/123 to /orders/124 shows another user's order. This bug is called:

  • CSRF Cross-site request forgery is different.
  • IDOR (broken object-level authorization) Correct.
  • SQL injection Different.
  • Clickjacking Different.

Always check that the authenticated user is allowed to access that specific object.

Rate limiting

Why

Protect services from overload and abuse, enforce fair use and plans, and control cost.

The main algorithms

AlgorithmIdeaBurst handlingMemory
Fixed window counterCount per calendar window (per minute)Allows 2x bursts at window edgesTiny
Sliding window logKeep timestamps of recent requestsExactHigh
Sliding window counterWeighted blend of current and previous windowClose to exactSmall
Token bucketBucket refills at rate r up to capacity b; each request takes a tokenAllows bursts up to b, then rate rTiny
Leaky bucketRequests queue and drain at a fixed rateSmooths outputSmall

The token bucket is the most common because it permits short bursts while enforcing an average rate.

class TokenBucket:
    def __init__(self, rate, capacity, now=0.0):
        self.rate, self.cap, self.tokens, self.last = rate, capacity, capacity, now
    def allow(self, now, cost=1):
        self.tokens = min(self.cap, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False

tb = TokenBucket(rate=2, capacity=4)          # 2 tokens per second, burst of 4
results = [tb.allow(t) for t in (0, 0, 0, 0, 0, 0.5, 1.0, 1.0, 1.0)]
print(results)

Output

[True, True, True, True, False, True, True, False, False]

Where and how

  • Enforce at the API gateway or edge, per API key, user id or IP. Return 429 Too Many Requests plus Retry-After and rate limit headers.
  • Distributed counters: keep counts in Redis (atomic INCR with expiry, or a Lua script for token bucket) so all gateway nodes share state. Accept small inaccuracy to avoid a central hot spot, or keep local buckets that sync periodically.
  • Different limits per endpoint (login is stricter), per plan and per cost.
  • Decide fail open or closed if the limiter store is down. Failing open protects availability but loses protection.

How this gets asked

A token bucket has rate 2 tokens per second and capacity 4, and starts full. After 4 requests at time 0, how many requests can be allowed at time 1.0?

Tokens refill by 2 x 1.0 = 2, so two more requests are allowed.

Self-check

Why is token bucket popular?

It allows bursts up to the bucket size while enforcing an average rate, with tiny state.

API gateway and service discovery

API gateway

A single entry point in front of many services. It handles cross-cutting concerns once: TLS, authentication, rate limiting, request routing, protocol translation, response aggregation, caching, logging, and canary routing. Examples: Kong, NGINX, Envoy, AWS API Gateway. Keep business logic out of the gateway. Avoid it becoming a bottleneck or a single team dependency by scaling it horizontally and keeping it thin.

Backend for frontend (BFF)

A separate gateway per client type (web, iOS, partner) that shapes responses for that client.

Service discovery

In dynamic clusters, instances come and go, so callers cannot hard-code addresses.

  • Client-side: the client asks a registry (Consul, etcd, Eureka) for healthy instances and balances itself.
  • Server-side: the client calls a load balancer or DNS name and it finds instances (Kubernetes Services).

Instances register on start, send heartbeats and deregister on shutdown. Health checks remove dead ones.

Service mesh

A mesh (Istio, Linkerd) puts a sidecar proxy next to every service instance. The sidecars provide mutual TLS, retries, timeouts, circuit breaking, traffic splitting and metrics, with no application code changes. The cost is complexity and extra latency per hop.

Self-check

What does an API gateway do?

Single entry point handling TLS, auth, rate limits, routing and cross-cutting concerns for many services.

Monolith or microservices

The monolith

One deployable unit. Simple to build, test, deploy and debug, with in-process calls and ACID transactions. Starts to hurt when many teams collide in one codebase, deployments become risky and slow, or parts need very different scaling.

Microservices

Many small services, each owned by a team, deployed independently, with its own data store, communicating over the network.

BenefitCost
Independent deploys and scalingNetwork calls instead of function calls: latency and failure modes
Team autonomyDistributed transactions and data consistency are hard
Technology freedomOperational overhead: many pipelines, dashboards, versions
Fault isolationDebugging across services needs tracing
Testing the whole system is harder

Practical guidance

  • Start with a well-structured (modular) monolith. Split along business capabilities (bounded contexts from domain-driven design) when team size and scaling needs justify it.
  • Each service owns its data. No shared database between services.
  • Avoid chatty calls and distributed monoliths (services that must be deployed together).
  • Use async events for cross-service workflows, sagas for business transactions (SD6), and the strangler fig pattern to migrate gradually: route one capability at a time to the new service.
Trap

Microservices are an organisational scaling tool before they are a technical one. Splitting a small team's product into 30 services slows delivery and adds failures.

How this gets asked

What is a sensible default for a new product with a small team?

  • 30 microservices Heavy operational burden.
  • A modular monolith, split later along business boundaries Correct.
  • A shared database across many services Couples them tightly.
  • No tests No.

Microservices solve organisational scaling; do not pay for them before you need them.

Self-check

What is the strangler fig pattern?

Gradually route functionality from a monolith to new services until the old system can be retired.

Inter-service communication

StyleExamplesUse whenRisk
Synchronous request/responseREST, gRPCThe caller needs the answer nowTight coupling, cascading failure, latency adds up
Asynchronous messagingQueues, eventsThe caller does not need to wait; fan-outEventual consistency, ordering, duplicates

Latency adds along a call chain, and availability multiplies: five services in series each at 99.9 percent give about 99.5 percent. Prefer fewer synchronous hops, set timeouts on every call, and use circuit breakers (SD10).

Interview questions: APIs

11 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic What makes a good REST API?

Resource-oriented URLs, correct methods and status codes, consistent JSON and error shapes, pagination, versioning, idempotency for unsafe operations and clear documentation.

Basic Authentication versus authorization?

Authentication verifies who you are; authorization decides what you may do. Both must be checked on every request.

Medium REST versus gRPC versus GraphQL?

REST is simple and cacheable. gRPC is fast, typed and streaming for internal calls. GraphQL lets clients select fields to avoid over and under-fetching but complicates caching and query cost control.

Medium Offset versus cursor pagination?

Offset is simple but slow for large offsets and unstable when data changes. Cursor (keyset) pagination uses an index, is fast and stable but cannot jump to arbitrary pages.

Medium How do you design rate limiting?

Token bucket per client key at the gateway, with counters in Redis updated atomically, returning 429 with Retry-After, with different limits per endpoint and tier and a fail-open or fail-closed choice.

Medium What is an API gateway?

A single entry point handling TLS, authentication, rate limiting, routing and aggregation for many services, keeping business logic out.

Medium How does OAuth 2.0 authorization code flow work?

The user authenticates at the identity provider and consents; the app receives a short-lived code and exchanges it for access and refresh tokens, then calls the API with the bearer token.

Advanced Monolith versus microservices?

Start with a modular monolith. Move to microservices along business boundaries when team size or scaling demands it, accepting network failure modes, distributed data and operational cost.

Advanced How do services find each other?

Through service discovery: a registry (Consul, etcd) used by clients, or platform DNS and load balancers such as Kubernetes Services, with health checks and automatic deregistration.

Advanced What is a service mesh?

Sidecar proxies next to each service handling mutual TLS, retries, timeouts, circuit breaking, traffic splitting and telemetry without code changes, at the cost of complexity and latency.

Advanced How do you evolve an API without breaking clients?

Make additive changes, tolerate unknown fields, version breaking changes and support old versions for a deprecation window, and use contract tests.
