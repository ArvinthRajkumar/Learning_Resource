Event-driven architecture: CQRS, event sourcing, sagas and the outbox

Large systems often communicate by recording facts and reacting to them. This part covers the patterns built on that idea, when they pay off, and the failure modes (duplicates, reordering, poison messages) that decide whether they work in production.

Advanced~4 hours

Events, commands and queries

KindMeaningExampleCan be rejected?
CommandA request to do something, addressed to one handlerPlaceOrderYes
EventA fact that already happened, broadcast to anyone interestedOrderPlacedNo (it is history)
QueryA request for data, no side effectsGetOrdern/a

Name events in the past tense, keep them small and immutable, and include enough data for consumers to act without calling back (but not whole entities, which couple services). Style choices:

  • Event notification: tiny event, consumers fetch details (low coupling, more calls).
  • Event-carried state transfer: the event carries the data, consumers keep local copies (autonomy, eventual consistency).
  • Event sourcing: the events are the system of record (below).

How does an event differ from a command?

  • They are the same No.
  • An event is a past fact that cannot be rejected; a command is a request that can be Correct.
  • Events are synchronous No.
  • Commands are broadcast Events are.

Events are named in the past tense.

The transactional outbox

Problem: a service must update its database and publish an event, but those are two systems; a crash between them loses the event or publishes one for a rolled-back change (the dual-write problem).

Outbox pattern: in the same local database transaction, write the business row and an outbox row. A separate relay (poller or change data capture on the WAL) reads unsent outbox rows and publishes them to the broker, marking them sent. Delivery is at least once, so consumers must be idempotent.

import sqlite3, json
db = sqlite3.connect(":memory:")
db.executescript("""CREATE TABLE orders(id INTEGER PRIMARY KEY, item TEXT, qty INT);
                     CREATE TABLE outbox(id INTEGER PRIMARY KEY AUTOINCREMENT, topic TEXT, payload TEXT, sent INT DEFAULT 0);""")
def place_order(order_id, item, qty, fail=False):
    try:
        with db:                                   # one atomic transaction
            db.execute("INSERT INTO orders VALUES(?,?,?)", (order_id, item, qty))
            db.execute("INSERT INTO outbox(topic, payload) VALUES('order.placed', ?)", (json.dumps({"id": order_id, "item": item, "qty": qty}),))
            if fail: raise RuntimeError("crash before commit")
    except RuntimeError:
        pass
place_order(1, "book", 2)
place_order(2, "pen", 5, fail=True)               # rolled back: no order AND no event
print("orders:", db.execute("SELECT id FROM orders").fetchall(), "| outbox:", db.execute("SELECT id, topic FROM outbox").fetchall())
broker = []
for rid, topic, payload in db.execute("SELECT id, topic, payload FROM outbox WHERE sent = 0").fetchall():
    broker.append((topic, payload))                # relay publishes ...
    db.execute("UPDATE outbox SET sent = 1 WHERE id = ?", (rid,))   # ... then marks sent (crash in between = duplicate)
db.commit()
print("published:", broker)

Output

orders: [(1,)] | outbox: [(1, 'order.placed')]
published: [('order.placed', '{"id": 1, "item": "book", "qty": 2}')]

What problem does the transactional outbox solve?

  • The dual write of a database change and a message, so neither is lost or sent for a rolled-back change Correct.
  • Caching No.
  • Encryption No.

The event is stored atomically with the data and relayed later.

Idempotent consumers

Brokers give at-least-once delivery, so duplicates arrive (retries, rebalances, relay crashes). "Exactly-once" is achieved by combining at-least-once delivery with idempotent processing: record processed message ids in the same transaction as the effect, or make the operation naturally idempotent (set, not increment).

import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("CREATE TABLE balance(acct TEXT PRIMARY KEY, amount INT); CREATE TABLE processed(msg_id TEXT PRIMARY KEY);")
db.execute("INSERT INTO balance VALUES('a', 100)")
def handle(msg_id, acct, delta):
    try:
        with db:
            db.execute("INSERT INTO processed VALUES(?)", (msg_id,))      # fails if seen
            db.execute("UPDATE balance SET amount = amount + ? WHERE acct = ?", (delta, acct))
    except sqlite3.IntegrityError:
        return "duplicate ignored"
    return "applied"
stream = [("m1", "a", 50), ("m2", "a", -30), ("m1", "a", 50), ("m2", "a", -30), ("m3", "a", 10)]   # duplicates delivered
print([handle(*m) for m in stream])
print("balance:", db.execute("SELECT amount FROM balance").fetchone()[0], "(expected 100 + 50 - 30 + 10 = 130)")

Output

['applied', 'applied', 'duplicate ignored', 'duplicate ignored', 'applied']
balance: 130 (expected 100 + 50 - 30 + 10 = 130)
Exactly-once is about effects

No network protocol delivers a message exactly once. Kafka's "exactly-once" means transactional writes within Kafka plus idempotent producers. The end-to-end guarantee always needs an idempotent consumer or a transactional sink.

How this gets asked

How do you get effectively-once processing?

  • Use TCP Does not stop redelivery.
  • At-least-once delivery plus idempotent handlers (dedupe ids) Correct.
  • Never retry Loses messages.
  • Use UDP No.

Duplicates are inevitable; make them harmless.

Self-check

Where do you store processed message ids?

In the same database transaction as the side effect, so the check and the effect are atomic.

Event sourcing

Instead of storing the current state, store the append-only sequence of events. State is a fold over the events; any past state can be rebuilt; the log is a perfect audit trail.

ProsCons
Full history, audit, debugging "how did we get here"Queries need projections
Time travel and replay to fix bugs or build new viewsEvent schema evolves forever (upcasting)
Natural fit for event-driven integrationHigher learning curve, eventual consistency
Append-only writes are fastDeleting data (GDPR) needs crypto-shredding or tombstones

Snapshots store state every N events so replay starts from the latest snapshot. Use optimistic concurrency (expected version) when appending so two writers cannot silently overwrite each other.

class Account:
    def __init__(self): self.balance, self.version = 0, 0
    def apply(self, e):
        if e["type"] == "Deposited": self.balance += e["amount"]
        elif e["type"] == "Withdrawn": self.balance -= e["amount"]
        self.version += 1
class EventStore:
    def __init__(self): self.events = []
    def append(self, event, expected_version):
        if len(self.events) != expected_version: raise RuntimeError(f"conflict: expected v{expected_version}, store is at v{len(self.events)}")
        self.events.append(event)
    def rebuild(self, upto=None):
        acc = Account()
        for e in self.events[:upto]: acc.apply(e)
        return acc
store = EventStore()
store.append({"type": "Deposited", "amount": 100}, 0)
store.append({"type": "Withdrawn", "amount": 30}, 1)
store.append({"type": "Deposited", "amount": 5}, 2)
print("current balance:", store.rebuild().balance, "| balance after 2 events:", store.rebuild(2).balance)
try:
    store.append({"type": "Withdrawn", "amount": 999}, 1)       # stale writer
except RuntimeError as e:
    print("rejected:", e)

Output

current balance: 75 | balance after 2 events: 70
rejected: conflict: expected v1, store is at v3

How this gets asked

In event sourcing, how is current state obtained?

  • From a table of current rows only That is classic CRUD.
  • By replaying (folding) the events, optionally from a snapshot Correct.
  • From a cache only No.
  • From logs of HTTP calls No.

The event log is the source of truth.

The balance after events +100, -30, +5 is?

Why snapshots?

To avoid replaying the whole history every time; replay from the latest snapshot.

CQRS

Command Query Responsibility Segregation separates the write model (validates commands, enforces invariants, normalised or event-sourced) from one or more read models (denormalised views built for specific queries, updated from events). Read models can use a different store (search index, cache, column store).

events = [
    {"type": "OrderPlaced", "order": 1, "customer": "ana", "total": 40},
    {"type": "OrderPlaced", "order": 2, "customer": "bo", "total": 15},
    {"type": "OrderPlaced", "order": 3, "customer": "ana", "total": 25},
    {"type": "OrderCancelled", "order": 2},
]
spend, status = {}, {}
for e in events:                                   # one projector builds two read models
    if e["type"] == "OrderPlaced":
        spend[e["customer"]] = spend.get(e["customer"], 0) + e["total"]
        status[e["order"]] = ("placed", e["customer"], e["total"])
    elif e["type"] == "OrderCancelled":
        _, cust, tot = status[e["order"]]
        spend[cust] -= tot
        status[e["order"]] = ("cancelled", cust, tot)
print("spend per customer:", spend)
print("order status:", status)

Output

spend per customer: {'ana': 65, 'bo': 0}
order status: {1: ('placed', 'ana', 40), 2: ('cancelled', 'bo', 15), 3: ('placed', 'ana', 25)}

Use CQRS when read and write shapes differ greatly or scale differently. Do not use it for simple CRUD: it adds moving parts and lag.

How this gets asked

What is the main cost of CQRS?

  • Slower writes always Not necessarily.
  • Eventual consistency between the write side and read models, plus extra components Correct.
  • No indexes No.
  • Lost data No.

Read models lag behind writes.

Sagas: distributed transactions without 2PC

Two-phase commit locks resources across services and blocks on coordinator failure. A saga is a sequence of local transactions, each with a compensating action that semantically undoes it if a later step fails.

StyleHowTrade-off
ChoreographyEach service reacts to events and emits the nextDecoupled, but the flow is hard to see
OrchestrationA coordinator (workflow engine such as Temporal or Step Functions) calls each stepExplicit flow, one more component

Compensations must be idempotent and may be non-trivial (refund, restock, cancel shipment; you cannot "unsend" an email). Sagas are eventually consistent and expose intermediate states, so design for them (for example "pending" statuses).

def run_saga(steps, fail_at=None):
    done, log = [], []
    for i, (name, action, compensate) in enumerate(steps):
        if i == fail_at:
            log.append(f"{name}: FAILED")
            for n, c in reversed(done):
                log.append(f"compensate {n}: {c()}")
            return False, log
        log.append(f"{name}: {action()}")
        done.append((name, compensate))
    return True, log
steps = [
    ("reserve stock", lambda: "reserved", lambda: "released"),
    ("charge card", lambda: "charged", lambda: "refunded"),
    ("create shipment", lambda: "created", lambda: "cancelled"),
]
for fail_at in (None, 2):
    ok, log = run_saga(steps, fail_at)
    print("success" if ok else "rolled back", "->", " | ".join(log))

Output

success -> reserve stock: reserved | charge card: charged | create shipment: created
rolled back -> reserve stock: reserved | charge card: charged | create shipment: FAILED | compensate charge card: refunded | compensate reserve stock: released

How this gets asked

What is a compensating action?

  • A retry No.
  • A step that semantically undoes a previously completed local transaction Correct.
  • A lock No.
  • A checkpoint No.

Sagas replace distributed rollback with explicit undo steps.

Self-check

Orchestration versus choreography?

Orchestration uses a central coordinator with an explicit flow; choreography has services react to each other's events.

Ordering, partitions and poison messages

  • Brokers preserve order per partition. Use the entity id (order_id) as the partition key to keep one entity's events in order; there is no global order across partitions.
  • A consumer failure on one message must not block the stream forever: retry with backoff, then move it to a dead letter queue (DLQ) for inspection and replay.
  • Backpressure: if consumers lag, scale them (up to the partition count), batch, or shed load; watch consumer lag as a key metric.
  • Schema evolution: use a registry (Avro, Protobuf, JSON Schema) and compatibility rules: add optional fields, never reuse field numbers, version event types, and upcast old events when reading.

How this gets asked

How do you keep one order's events in sequence in Kafka?

  • Use one partition per message No.
  • Use the order id as the partition key Correct.
  • Sort in the consumer Cannot recover lost order.
  • Use more consumers No.

Order is guaranteed only within a partition.

Self-check

What is a DLQ for?

To park messages that repeatedly fail so they do not block the stream, for inspection and replay.

When not to use events

Events add latency, ordering puzzles and debugging effort. Prefer a simple synchronous call when you need an immediate answer, strong consistency or a small system. Use events for fan-out, decoupling teams, absorbing bursts and building derived data.

Key idea

Write the fact and the event in one transaction (outbox), deliver at least once, process idempotently, partition by entity for order, compensate instead of locking across services, and monitor consumer lag and the dead-letter queue.

Interview questions: Event-driven design

15 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic Event versus command?

A command asks one handler to do something and can be rejected. An event records something that already happened and is broadcast to any interested consumer.

Basic Why do message consumers need to be idempotent?

Brokers deliver at least once, so retries, rebalances and relay crashes cause duplicates. Idempotent handlers make duplicates harmless.

Medium What is the dual-write problem and how does the outbox pattern solve it?

Updating a database and publishing to a broker are two systems, so a crash can lose one. The outbox writes the event into a table in the same local transaction, and a relay publishes it afterwards.

Medium How do you achieve effectively exactly-once processing?

At-least-once delivery plus deduplication: store processed message ids in the same transaction as the effect, or make the operation naturally idempotent.

Medium Explain CQRS and when it is worth it.

Separate write and read models, with projections updated from events. Worth it when read and write shapes or scale differ greatly; not for simple CRUD because of eventual consistency and extra moving parts.

Medium What is event sourcing and what are its costs?

Storing every state change as an immutable event and deriving state by replay. Benefits: audit and time travel. Costs: projections for queries, schema evolution of old events, and handling deletion requests.

Medium Saga: orchestration versus choreography?

Orchestration uses a central coordinator that calls steps and triggers compensations; choreography has services react to each other's events. Orchestration is easier to see and debug; choreography is more decoupled.

Medium How do you preserve ordering in a partitioned log?

Use the entity id as the partition key, so that all events for one entity go to one partition. Ordering is not guaranteed across partitions.

Medium What is a dead letter queue?

A place to put messages that exceed their retry limit, so a poison message does not block the stream and can be inspected and replayed.

Advanced How do you evolve event schemas safely?

Use a schema registry with compatibility rules: add optional fields, never reuse or retype fields, version event types, and upcast old events on read.

Advanced What are snapshots in event sourcing?

Periodic captures of aggregate state so rebuilding replays only the events after the latest snapshot.

Advanced How do you prevent two writers corrupting an event-sourced aggregate?

Optimistic concurrency: appends carry the expected version and are rejected if the stream has moved on.

Advanced What is consumer lag and why monitor it?

The gap between the latest offset and what a consumer group has processed. Growing lag means consumers cannot keep up, so scale them, batch, or investigate slow handlers.

Advanced Why is exactly-once delivery impossible over a network, and what does Kafka claim?

A sender cannot distinguish a lost message from a lost acknowledgement. Kafka offers idempotent producers and transactions within Kafka; end-to-end effects still need idempotent consumers.

Advanced When should you avoid an event-driven design?

When you need an immediate response and strong consistency, in small systems, or when the team cannot yet operate brokers, tracing and replays.
