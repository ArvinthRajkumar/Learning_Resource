def downtime(avail):
    mins = (1 - avail) * 365 * 24 * 60
    return f"{mins / 60:.1f} h" if mins >= 60 else f"{mins:.1f} min"
for a in (0.99, 0.999, 0.9999, 0.99999):
    print(f"{a * 100:g}% availability -> {downtime(a)} of downtime per year")

How this gets asked

Requests per day divided by 10^5 gives rough average QPS. For 8.64 billion requests per day, average QPS is about (in thousands)?

8.64e9 / 86,400 = 100,000 QPS.

Which is faster?

  • SSD random read About 100 microseconds.
  • Main memory reference Correct, around 100 ns.
  • Cross-continent round trip Tens of milliseconds.
  • Disk seek Milliseconds.

Memory is orders of magnitude faster than SSD.

Two services in series, each 99.9% available. The combined availability is about:

  • 99.9% No.
  • 99.8% Correct, 0.999 x 0.999 is about 0.998.
  • 99.99% No.
  • 100% No.

Dependencies in series multiply, so availability drops.

Self-check

Availability of 99.99% allows how much downtime per year?

About 52 minutes.

A tiny estimation toolkit

import math
def estimate(users, actions_per_user, bytes_per_action, read_write_ratio, retention_years=5, peak=3):
    writes_day = users * actions_per_user
    write_qps = writes_day / 86400
    read_qps = write_qps * read_write_ratio
    storage_tb = writes_day * bytes_per_action * 365 * retention_years / 1e12
    bandwidth_mbps = (write_qps + read_qps) * bytes_per_action * 8 / 1e6
    return dict(write_qps=round(write_qps), peak_write_qps=round(write_qps * peak), read_qps=round(read_qps), peak_read_qps=round(read_qps * peak),
                storage_tb=round(storage_tb, 1), bandwidth_mbps=round(bandwidth_mbps))
print("URL shortener (100M new URLs/day? no: 100M/month):", estimate(users=3_300_000, actions_per_user=1, bytes_per_action=500, read_write_ratio=100))
print("Chat (50M users, 40 msgs each, 200 B):          ", estimate(users=50_000_000, actions_per_user=40, bytes_per_action=200, read_write_ratio=1))
print("Photo app (10M users, 2 photos, 2 MB, 20 views):", estimate(users=10_000_000, actions_per_user=2, bytes_per_action=2_000_000, read_write_ratio=20))

A feed where likes may be a few seconds stale suits:

  • Strong consistency everywhere Unnecessary cost.
  • Eventual consistency Correct.
  • Two-phase commit Overkill.

When do you pick a log (Kafka) over a queue?

When you need ordered streams, replay and many independent consumers.

Annotated mock 1: design a pastebin-lite chat

Below is how a strong 35-minute answer unfolds for "Design a group chat service". Notes in italics are the thinking behind each move.

  1. Clarify (3 min). "One-to-one and groups of up to 500? Text only or media? Message history? Online status? How many users?" Show you separate scope from nice-to-have. Assume 50M DAU, 40 messages each, delivery in under 500 ms, history kept 1 year, at-least-once with ordering per conversation.
  2. Estimate (3 min). 2B messages/day is about 23,000 per second on average, 70,000 at peak. At 200 B each that is 400 GB/day, 150 TB/year. Numbers justify the architecture: this needs partitioned storage, not one database.
  3. API and data (4 min). WebSocket for send and receive, REST for history. messages(conversation_id, message_id, sender, body, ts). Partition key conversation_id keeps one chat's messages together and ordered.
  4. High-level design (8 min). Clients keep WebSockets to gateway servers; a session registry (Redis) maps user to gateway; a chat service assigns a per-conversation sequence number, writes to a Cassandra-like store, and publishes to the recipients' gateways; offline users get a push notification and fetch history on reconnect.
  5. Deep dive 1: ordering and delivery (6 min). Sequence numbers per conversation, client acks, resend on reconnect from the last seen sequence, idempotent message ids to dedupe retries. Hits "at least once plus dedupe".
  6. Deep dive 2: groups (5 min). Small groups fan out on write; very large channels fan out on read or via pub/sub topics. Same trade-off as the news feed.
  7. Failures and trade-offs (4 min). Gateway crash: clients reconnect through the load balancer and resync. Hot conversation: it is bounded by one partition, which is acceptable. Storage growth: tier old messages to cheap storage.

Likely follow-ups. "How do you do read receipts?" (events per conversation, counters aggregated lazily). "End-to-end encryption?" (keys on devices, server stores ciphertext, loses server-side search). "Multi-region?" (home region per user, async replication, conflict-free per-conversation ordering by the home region).

How this gets asked

In the chat design, why partition messages by conversation id?

  • It is random No.
  • It keeps a conversation's messages together and ordered on one partition Correct.
  • It saves storage No.
  • It encrypts them No.

Ordering is per partition.

Self-check

How do you deliver chat messages reliably?

Per-conversation sequence numbers, acks, resend from the last seen sequence on reconnect, and idempotent message ids.

Annotated mock 2: design a rate-limited public API

Prompt: "Design an API platform that serves 100,000 requests per second with per-customer limits and usage billing."

  • Clarify: limits per second and per month? Burst? Fail open or closed? Real-time billing accuracy or hourly aggregates?
  • Core: edge load balancer, API gateway (authentication, rate limit, routing), backend services. Limits use a token bucket per API key in Redis with an atomic Lua script; a local in-memory approximation reduces Redis load with periodic sync.
  • Billing: do not bill on the request path. Emit a usage event per request (or batched counters) to Kafka, aggregate in a stream processor into hourly buckets, store in a warehouse, and reconcile with gateway logs. Idempotent event ids.
  • Deep dive: limit accuracy versus latency (exact global counters cost a network hop; sharded counters give approximate limits); cross-region customers; noisy neighbours and isolation (separate pools for large customers).
  • Failure modes: Redis down (fail open with local limits for safety); billing pipeline lag (late events, watermark and corrections); abuse (IP reputation, WAF).

Likely follow-ups. "How do you change a customer's limit instantly?" (config pushed through a pub/sub invalidation). "Prove the invoice is right." (immutable usage log, idempotent ids, daily reconciliation against the gateway's own counters).

How this gets asked

Why not bill customers on the API request path?

  • Billing is unimportant No.
  • It adds latency and couples availability to billing; emit usage events and aggregate asynchronously Correct.
  • Gateways cannot count They can.
  • Bills should be random No.

Use idempotent events and reconcile.

What is the best response when you do not know a number?

  • Stay silent No.
  • State an assumption, label it, and show how the design changes if it is wrong Correct.
  • Refuse to estimate No.
  • Guess wildly without saying No.

Self-check

Name three common interview mistakes.

Skipping requirements, naming technology without reasons, and ignoring failures.

Final checklist

  • Requirements: functional, non-functional, out of scope, SLO.
  • Numbers: QPS, peak, storage, bandwidth, cache size.
  • API and data model, with keys and indexes justified by the access pattern.
  • High-level picture: client, edge, services, data, async, observability.
  • Two deep dives with trade-offs and alternatives.
  • Failure handling: retries with idempotency, timeouts, circuit breakers, redundancy, backups, disaster recovery.
  • Scaling story: what breaks at 10x and what you do.
  • Security, privacy, cost, and operability (metrics, alerts, runbooks, deployments).
Key idea

Good answers follow a repeatable path, justify every choice with a number or a requirement, and spend their time where the risk is. Rehearse aloud with a timer: structure matters as much as content.

Interview questions: Trade-offs and mocks

13 questions. Try to answer aloud in under a minute, then reveal. Tags show the level. All questions are also in the interview bank.

Basic How would you structure a 45-minute system design interview?

Requirements and scope (5 min), estimates (5), API and data model (7), high-level design (10), deep dives (12), failures, scaling and wrap-up (6).

Basic Roughly how much downtime does 99.9% availability allow per year?

About 8.8 hours; 99.99% allows about 52 minutes.

Medium What if you do not know a number the interviewer asks for?

State a reasonable assumption out loud, label it, and show how the design would change if it were different.

Medium How do you decide between SQL and NoSQL?

Start from access patterns, consistency needs and scale: relational for transactions and ad hoc queries; wide-column or key-value for massive partitioned writes with known queries.

Medium When would you choose a queue over a synchronous call?

When the work can be delayed, bursts need smoothing, there is fan-out, or you want to decouple failures from the caller.

Medium How do you show that you considered failure?

For each component say what happens if it is down, slow or wrong, and name the mitigation: replication, retries with idempotency, timeouts, circuit breakers, backups.

Medium How do you scale a design from 1x to 10x?

Find the first bottleneck from the numbers (CPU, database writes, network, memory), then apply the cheapest remedy: cache, replicas, partitioning, queues, or bigger machines.

Advanced How would you design chat delivery to be reliable?

Per-conversation sequence numbers, client acknowledgements, resend from the last seen sequence on reconnect, and idempotent message ids to deduplicate retries.

Advanced How do you handle billing for an API platform?

Emit idempotent usage events asynchronously, aggregate in a stream processor, store immutable records, and reconcile against gateway logs.

Advanced Give an example of trading consistency for availability.

A shopping cart or feed can accept writes on any replica and converge later, while payments and inventory choose strong consistency.

Advanced What are the signs of an over-engineered design?

Microservices, sharding and multi-region for modest numbers, many technologies without reasons, and no discussion of operational cost.

Advanced How do you incorporate cost into a design?

Estimate compute, storage and egress, identify the dominant cost, and pick levers such as caching, tiering, reserved capacity and compression.

Advanced How do you respond if the interviewer challenges a choice?

Restate their concern, compare the alternative on the requirement that matters, and either defend with numbers or adapt with a clear explanation of the change.
